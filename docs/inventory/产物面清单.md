## 2. ★★ 枚举过程本身就挖出的三个发现

### 发现 A：**Prisma 有 225 个模型，但 0 个 enum** ⇒ 状态是"自由字符串"

`grep -cE "^enum " schema.prisma` = **0**，而模型有 225 个。结合已知的 `ORDER_STATUS` / `INVOICE_STATUS` /
`APPROVAL_STATUS` 常量，说明**状态值以字符串存在库列里，合法性靠代码里的常量表维护**。

★ 这正是"低端设计"清单里的典型项（**状态当自由文本**）：库层无法约束、写错一个字母就产生一个
"没人认识的状态"，而且**没有任何数据库级守卫**。→ 归 **② 类（细节不专业）**，但要评估是否已造成 ①。

### 发现 B：**38 个 View（页面）vs 59 个导航模块** —— 两个数字对不上

`View` 枚举 38 项、`moduleRegistry` 59 条 `id`。两者**不是一对一**。可能是"一个 View 下有多个模块"，
也可能是**两边各自维护了一份清单**（本仓反复出现的"同一件事多份真源"）。

★ 需人工确认一次，再决定：是设计如此，还是**又一处双真源**。

### 发现 C：**232 个前端组件文件** —— 这是"面"的最大来源，也是最难枚举的

后端路由能靠 `router.xxx(` 数出来；**前端组件数不出"面"**：一个组件里可能有 5 个按钮、3 个页签、
2 个弹窗，每个都是独立可操作面。**静态扫描数不出来，只能靠爬运行中的 DOM。**

★ ⇒ 结论：**"面"的最终真源是运行中的 DOM，不是源码。** 源码枚举只是**下界**。

## 6. 状态机展开（第 5 节第 1 项，已完成）

### 6.1 事实

| 状态机 | 位置 | 状态数 | 走不走共享校验器 |
|---|---|---|---|
| **Invoice（发票）** | `server/src/statusTransition.ts` | 5（Draft/Issued/PartiallyPaid/Paid/Cancelled） | 是（它就是共享的） |
| **Shipment（运单）** | 同上 | 8（Draft/Booked/Loading/Shipped/Arrived/Cleared/Delivered/Cancelled） | 是 |
| **Order（订单）** | `server/src/orders/orderLifecycleService.ts:31` `ORDER_TRANSITIONS` | 6（Pending/Confirmed/Production/Shipping/Delivered/Alert） | **否，自己一套** |
| 报价 / 采购 / 报关 / MES / 增值税票 / BOM / 开发 / CRM / 内部交易 / 样品 | 各自 service | 未逐个展开 | 其中报价、采购**用了**共享校验器 |

**共享校验器 `validateStatusTransition(entityType, from, to)` 的调用方**（9 处，非测试）：
`agent/orderShipFlow` · `agent/toolRuntime` · `agent/invoiceIssueFlow` · `shipping/shipmentMutationService` ·
`procurement/procurementService` · `finance/invoiceMutationService` · `finance/route` · `quotations/quotationService`

### 6.2 ★ 我一度以为是 ① 类缺陷，**查完发现不是**（如实记录）

**怀疑**：共享校验器里写的是
`entityType === 'Invoice' ? VALID_INVOICE_STATUS : VALID_SHIPMENT_STATUS` ——
看着像"传 Order 会被静默当成 Shipment 校验"。

**查证结果：不是缺陷。** 理由两条：
1. 函数签名是 `entityType: 'Invoice' | 'Shipment'`（**联合字面量类型**）⇒ **类型系统挡住了传错**，
   编译期就报错，不存在运行期静默走错分支。
2. 它对未知 `from` 是 **fail-closed**（`INVALID_CURRENT_STATUS`，不静默放过）—— 这是**好设计**。

★ 结论：**这是本仓少见的"设计良好"样本**，应作为正面参照，而不是问题项。
★ 方法论价值：**"看着可疑"必须先查证再定性** —— 差点把好代码报成缺陷。

### 6.3 真问题（② 类）：**订单状态机没有走共享校验器**

`ORDER_TRANSITIONS` 独立实现在 `orderLifecycleService.ts`，与共享的 `INVALID_*_TRANSITIONS` **两套并存**。
- 这不是 ①（订单的转移守卫看起来是完整的，有 `allowedTargets` 检查）
- 是 **②（同一件事两份实现）**：将来加一个订单状态，要记得改两处；改漏了就是隐性缺陷
- ⇒ 归 **② 必修**：**把订单纳入共享校验器**（不重构设计，只做"收敛到一处"）

### 6.4 ★ 连带发现（① 类候选，待证）：**库层没有状态约束**

Prisma **0 个 enum**（§2 发现 A）⇒ 所有状态列都是 `text`，**库层无 CHECK 约束**。
共享校验器是**应用层**守卫；任何绕过它直接写库的路径（脚本、迁移、手工 SQL、未登记的通道）
都能写进一个"没人认识的状态"，且**没有任何东西会报错**。

⇒ 这是 **① 类候选**（会让数据错），但**需要先证"存在绕过路径"**，不能凭推理定罪。
★ 待办：扫一遍"直接写状态列而不经过校验器"的路径（含 `scripts/` 与迁移）。

## 7. ★★ 状态守卫覆盖面：**125 / 151 个"写 status"的文件不引用任何校验器**

### 7.1 怎么数的（可复算）

```bash
# 写 status 的文件（非测试）
grep -rlE "status: '" server/src --include="*.ts" | grep -v __tests__ | wc -l        # → 151
# 其中「不引用任何校验器」的
for f in $(grep -rlE "status: '" server/src --include="*.ts" | grep -v __tests__); do
  grep -qE "validateStatusTransition|ORDER_TRANSITIONS|VALID_[A-Z_]*STATUS" "$f" || echo "$f"
done | wc -l                                                                          # → 125
```

**151 个文件写 `status`，其中 125 个（83%）不引用任何状态校验器。**

### 7.2 其中属于**业务状态机实体**的（不是普通标志位）

| 模块 | 文件（示例） |
|---|---|
| 订单 | `orders/orderLineMutationService.ts` · `orderChanges/orderChangeRequestService.ts` |
| 出运 | `shipping/orderShipmentBatchService.ts` · `shipping/shipmentDelayService.ts` |
| 报关 | `customs/tradeDocumentLifecycleService.ts` · `customs/compositeDocumentService.ts` |
| 索赔/授信 | `claims/creditNoteService.ts` · `credit/creditService.ts` · `credit/bankruptcyService.ts` |
| 生产 | `mes/processChainService.ts` |
| 导入 | `import/persistOrders.ts` |
| 事件联动 | `events/linkages/L2CreateShipment.ts` · `L3IssueInvoice.ts` |
| **★ Agent（AI 代操作）** | `agent/quotationFlow.ts` · `agent/orderLineUpdateFlow.ts` · `agent/orderChangesFlow.ts` · `agent/customsFlow.ts` · `agent/creditFlow.ts` |

### 7.3 ★ 定性：这是 **① 类候选**，但**尚未定罪**（必须逐路径证）

**为什么不能直接定罪**（按"看着可疑先查证"的纪律）：
- 写 `status:` ≠ 做状态转移。**创建时给初始状态**是合法的，不需要校验。
- 有些 `status` 列**根本不是状态机**（例如 `reportDefinitionService` 的启用状态、`permissionService` 的标志位）。
- 要定罪必须证：**通过某条路径，能让一个实体进入"转移表不允许的状态"**。

**为什么仍然高度可疑（三条独立理由）**：
1. **库层零约束**（§2 发现 A：225 模型 / 0 enum）⇒ 应用层是**唯一**的守卫，而它覆盖不到 83% 的写点。
2. **`agent/` 的 5 个 flow 直接写状态** ⇒ AI 代操作是本仓的**新入口**，而它没有走状态机校验。
   这是"未登记通道"的同类风险（本仓已因客户专用通道吃过一次）。
3. **本仓已有前科**：订单金额口径 17 处各写各的、客户专用通道未登记 ⇒
   "同一个规则散在多处"是本仓**反复出现**的失败模式，状态守卫正是同一族。

### 7.4 建议的证法（下一步）

对**每一类状态机实体**，取 2–3 条"不引用校验器"的写路径，**实际构造一次非法转移**：
- 若被拒 ⇒ 说明守卫在别处（可能是服务内部调用），该路径**不是缺口**
- 若通过 ⇒ **① 类缺陷成立**，且能列出**具体可达路径**（这比"覆盖率低"有力得多）

★ **先证后判**：不写"125 个文件有缺陷"，只写"125 个写点未经共享校验器，其中 N 条已证可产生非法状态"。
