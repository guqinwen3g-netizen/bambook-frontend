## 一、★★ 判定顺序（四问，按顺序问，跳步就会误判）

### 问 1：业务上**该不该有**？

按真实业务链判断这个节点在这个状态下是否**必然**有内容。

| 情形 | 例 | 结论 |
|---|---|---|
| 业务上**必然有** | 已确认出运的订单 → 必然有运单 | 继续问 2 |
| 业务上**还没有到** | 刚创建的订单 → 没有 QC 报告 | **合法空态**，跳到问 3 |
| 业务上**可能有也可能没有** | 有客户要保险、有的不要 | 跳到问 3（必须能表达清楚） |

### 问 2：软件**有没有入口**把它补上？

| 情形 | 归因 | 处置 |
|---|---|---|
| **有入口**，只是没人录 | **数据缺口** | 补数据（**不改代码**） |
| **没有入口**，业务上又该有 | ★★ **软件缺陷（真断点）** | 改代码 —— 这是最该修的 |
| 有入口但填不进去 / 填了不生效 | ★★ **软件缺陷** | 改代码 |

### 问 3：**空态表达**合格吗？（针对合法空态）

| 表现 | 归因 |
|---|---|
| 空白一片 / 显示 `0` / 显示 `-` | ★ **软件缺陷** —— 违反「取不到数据不得回落 0」的明令；用户分不清「没数据」与「坏了」 |
| 显示「尚未录入」+ 给出录入入口 | 合格 |

### 问 4：是不是**孤儿 / 越流程**数据？

经 seed 或 E2E **绕过 API 直写库**产生的记录，既不是软件缺陷也不是正常数据。
判据：该记录**没有任何合规入口能产生它**，或它的父记录已被软删。
处置：**登记为孤儿，不修代码也不补数据**（补了只会掩盖真问题）。

## 二、★★ 我的三种当场验证手段（用来定性，不靠争论）

| 手段 | 做法 | 能证明什么 |
|---|---|---|
| **注入法** | 用合规入口（或 API）补一条数据，再看界面 | 补完能正常显示 ⇒ **软件没问题，是数据缺口**；补完仍不显示 ⇒ **软件缺陷** |
| **对照法** | 找一个**同状态且有数据**的单对比 | 有数据的那单显示正常 ⇒ 是数据缺口 |
| **API 直查法** | 绕过前端直接查接口 | 接口有数据、前端不显示 ⇒ **前端渲染缺陷**；接口也没数据 ⇒ **数据缺口** |

★ 走查中遇到"点进去没内容"，我默认**先做 API 直查**（10 秒出结果），再决定补数据还是改代码。

## 五、一条纪律

**不因为"库里没数据"就改软件的显示逻辑去迁就**（比如把空态隐藏、把 0 改成"暂无"以外的假数）。
数据缺口就补数据；软件缺陷才改代码。两者混淆会导致：**真缺陷被"补条数据就好"掩盖掉**。
