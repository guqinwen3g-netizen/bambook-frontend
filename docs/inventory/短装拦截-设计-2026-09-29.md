## 一、一页结论

| | |
|---|---|
| **要建的** | 一个**行级**短装判定 + 一个**审批放行**通道 + 把仓库里那个**死状态**（`ShortShipped`）接上 |
| **不新建模型** | ★ `ShipmentOrderAllocation.status` 里**本来就有** `ShortShipped`，`exception` 列也在 —— **全仓无任何代码写它们**（实测证据见 §三.3） |
| **判定单位** | ★ **订单行**（`OrderLine`）—— 因为"少做"是**该行总量**的事；`OrderShipmentBatch` 是**订单级**且**没有行明细**（证据见 §三.4） |
| **拦截时点** | ★★ **该行最后一次出运被确认为已发运的那一刻**（`Shipment.status → Shipped`）；分批时**只要还有未发运的票就不判** |
| **放行** | 审批单（`ApprovalRequest`，`actionType='order:short-ship-exemption'`，`targetType='OrderLine'`）：业务员发起 → 审批人（DR-007 解析）批准 → 再确认出运即放行 |
| **留痕** | 放行成功后写该分配的 `status='ShortShipped'` + `exception`（写明"客户同意少发"与审批单号） |

## 二、取数口径（与溢出侧**共用同一套标准**，不许各写各的）

| 项 | 口径 |
|---|---|
| 标准来源 | 与**溢装**完全同一个解析器：`resolveLineTolerance` + `gateToleranceOf`（客户标准 P0 → 已录我方标准 → 出厂默认 → 未判定） |
| 允许下限 | `allowedMin = 行数量 × (1 − pct/100)`（对称；`checkTolerance` 已在算 `allowedMin`） |
| 已发量 | ★ **口径真源 = `shared/orderLineShippedQty.ts`**（累计 `ShipmentOrderAllocation.actualQty`，**排除已取消票**）—— 不许另写一份累计 |
| 未判定 | 与溢装同口径：门禁按 **0** 处理（下限 = 合同量）★ 但**这是"更严"方向**，且出厂默认上线后只有三条可达路径（见公差设计稿 §十一.1） |
| 单位 | 沿用既有"单位不可互算就报错，不硬算"（`normalizeQtyToBase`） |

★ 关键一致性：**同一条 `pct` 必须同时管住上限与下限**。若短装用一套、溢装用另一套，
就会出现"系统允许 ±1% 却拦了 −3%"这类自相矛盾 —— 那是本仓 G6.3（多套并行真源）的同族。

★★ **一处必须更正（本设计稿第一版写错了，实测后改）**：
  · 第一版写「溢装门禁已经在这两处」—— **不成立**。实测两个门禁的**落点不同**：
    - `assertOrderLineNotOverAllocated`（溢装 / `ORDER_LINE_OVER_ALLOCATED`）= **分配写入时**

    - `assertShipmentReleaseGateOrThrow`（DR-012/014 出运**放行**门禁，与容差无关）= **Shipped 流转时**
      （`shipmentMutationService.ts:295` / `:447`）。
  ⇒ 所以短装**不是**"挂在溢装旁边"，而是**与放行门禁同处**（同一个状态流转、同一个事务）。
    它们共用的是**公差标准链**（`pct` 来源），不是同一个调用点 —— 这一点写清，免得下一个人按错落点找。

### 3.2 累计已发量在哪算（**不许新写一份**）

### 3.3 `ShortShipped` 是**死状态**（实测）

全仓 `status='ShortShipped'` **无任何写入方**。命中仅：
白名单 `allocationService.ts:76`（只在 `:545/:642` 做合法性校验）、`schema.prisma:3227`、
前端类型 `services/shipmentService.ts:229`、前端标签 `components/ShipmentManager.tsx:2703`、`out/`、`dist/`。
⇒ 本批不是"新建模型"，而是**把这个死状态接上**（与 `customerAgreementMoq` 同一类病）。

### 3.4 为什么不按"批次"判（★ 实测过才这么定）

`OrderShipmentBatch`（`schema.prisma:3260-3295`）是**订单级**：有 `plannedQty`/`isFinalBatch`/`shipmentId`，
但**没有行明细**（全仓只有 `InvoiceOrderAllocation.batchId` 引用它）⇒ **判不了"哪一行少做了多少"**。
⇒ 批次只保留一个用途：**「末批」是一个"收尾"信号**（`isFinalBatch`），而**本设计用行侧的自然收尾**
（该行再无未发运的票）替代它 —— 少一个跨模型依赖，且对"没建批次"的订单也成立。

## 四、行为规格（实现要照这个写）

```
触发：某张 Shipment 被确认为「已发运」（两条写路径都算）
  逐条处理本票**有 actualQty 的分配**所对应的订单行：
    1) 若「该行还有未发运的非取消分配」 ⇒ ★ 不判（分批发货，后面还有票）
    2) 否则（本票就是该行的收尾）：
         allowedMin = 行数量 × (1 − pct/100)     ← pct 走公差标准链（与溢装同一套）
         shippedQty = 该行累计实际发运量（排除已取消票）
         if shippedQty + 1e-6 >= allowedMin  ⇒ 通过
         else:
           if 存在 approved 的短装放行审批单 ⇒ 通过，并写该分配 status='ShortShipped' + exception
           else ⇒ ★★ 拦下：
                · code = ORDER_LINE_SHORT_SHIPPED（需登记进 errorCodes）
                · 自动发起（防重）一张审批单：actionType='order:short-ship-exemption',
                  targetType='OrderLine', targetId=lineId,
                  payload = { contractQty, shippedQty, allowedMin, pct, toleranceSource, shipmentId }
                · 错误文案给全：少了多少、下限是多少、谁定的标准、下一步（已为你发起短装确认单，审批通过后重试）
```

### 4.1 四条**不许**做的（边界）

1. **不许**在"排计划/建分配"时判下界（分批发货第一票必然少于合同量 ⇒ 会误拦第一票）。
2. **不许**把"未判定"当成"没超" —— 门禁按 0 卡（下限 = 合同量），方向与溢装相反但同样是 fail-closed。
3. **不许**自动改单（把合同量改小）或自动生成扣款/索赔 —— 只拦、只留痕、只提供建议。
4. **不许**另写一份"累计已发量"或另一套 `pct` 取数。

### 4.2 与既有机制的关系（不打架）

- **溢装**（`allocationService.ts:423-430` / `:500-508`）：不改。
- **行级覆盖 / 客户标准 / 出厂默认**：共用同一个 `pct`。
- **订单视图**（`orders/toleranceService.ts:96-105`）：已经会显示 `under_limit`；本批让"出口"也拦住它。

### 7.3 ★★ 落地时撞出来的一个**真缺陷**（不修的话门禁等于白拦）

`shipping/route.ts` 的 PATCH 用一张**本地** `statusCodeMap`，查不到就 `|| 500`。
短装码**不在那张表里** ⇒ 业务规则阻断（409）会被渲染成**"服务器内部错误"（500）**
⇒ 业务员看到 500 只会反复重试，**永远不会**去走"客户同意少发"的审批。
修法：这一枚码的档位**只问注册表**（`httpStatusOfCode`，缺码即抛），
**不**顺手加进本地表（那会给 B32 棘轮凭空多登记一处本地 code→status 映射）。
★ 并已用**源码级契约测试**钉住（3 例：档位分支在、`|| 500` 不许回来、门禁必须在 Shipped 分支里、审批单必须在事务外）。

## 八、追加（2026-09-29 21:0x）：**数量完整性**两个缺口 —— 使用方拍「也拦」

### 8.1 使用方口径（原话，逐字）

> 「如果说没有这一步知道这个实际出运数量的话，那就说明程序设计有缺口，**有很大的缺口**。
>  因为常规操作人工操作的时候，你出运前肯定是要有这个划码的。或者就是要有这个数量的清点，
>  就至少知道比如说我有多少件衣服要发，然后或者说我有多少匹面料，然后每匹面料有多少米，
>  这些清单是肯定要有的。然后包括要订仓啊，这些肯定之前要知道这个准确的数量，
>  **所以不存在说不知道这些数量，然后又要发起这个出运的情况**。
>  如果说现在是不知道数量就能出运的话，那就是中间有巨大的缺口存在。」

⇒ ★★ 这段话把**两个**缺口一起点了名（我原来只准备处理第一个的后半截）：
| # | 缺口 | 本批处置 |
|---|---|---|
| 1 | 有明细，但**实际出运量没填**（只录了计划量） | ★ **拦住**（先填数量） |
| 2 | 本票**一条出运明细都没有** | ★ **拦住**（先录明细） |

★ 这与本机制原来的设计（§五 的"数据不全 ⇒ 不判短装、静默跳过"）**相反**，按使用方口径改。

### 8.2 ★★ 为什么要和"短装"分成两个出口（而不是都走审批放行）

| | 事实清楚度 | 缺什么 | 出口 |
|---|---|---|---|
| `ORDER_LINE_SHORT_SHIPPED` | **清楚**：就是少了 | **客户同意** | 审批单放行（DR-007 解析审批人；批准后重试即通过） |
| `SHIPMENT_ACTUAL_QTY_MISSING` | **不清楚**：数量没录 | **数量本身** | 拦住，**不发起审批单** |
| `SHIPMENT_NO_ALLOCATION_DETAIL` | **不清楚**：没有明细 | **明细本身** | 拦住，**不发起审批单** |

★★ 若让后两者也走审批，等于**把"不知道发了多少"洗成"客户同意少发"** ——
   审批单解决不了"数据没填"，这正好是本仓最忌讳的"用一个正确的流程回答一个错误的问题"。
   ⇒ 已写成源码级契约测试（"审批单的触发条件里只许出现短装码"）。

### 8.3 ★ 关键区分：`null` = 没录，`0` = 录了、确实没发

判据落在**列的语义**上，不新造字段：
- `ShipmentOrderAllocation.actualQty IS NULL` ⇒ **没录** ⇒ 拦在"先填数量"；
- `actualQty = 0` ⇒ **录了 0**（例：这一票该行确实一件没发）⇒ 进**短装**判定 ⇒ 该走审批走审批。

★ 若把 `0` 也当成"没录"，那么"确实一件没发"这种真正的短装会被降级成"请去填个数"——
  业务员填个 0 再来一次，就永远绕过了短装拦截（比不拦更糟：它看起来像拦住了）。

## 九、追加（2026-09-29 21:2x）：把"出口档位"这件事按仓规收口（★ 被两条既有守卫逼出来的）

### 9.1 起因：我第一版把 409 又写成 500

`shipping/route.ts` 的 PATCH 出口原来是一张**本地** `statusCodeMap` + `|| 500`。
短装码不在那张表里 ⇒ **业务规则阻断（409）会被渲染成"服务器内部错误"（500）**：
业务员看到 500 只会反复重试，**永远不会**去走"客户同意少发"的审批 —— 门禁等于白拦。

### 9.2 三次尝试，最后落在仓规上（过程如实记录）

| 版本 | 写法 | 结果 |
|---|---|---|
| ① | `code === SHORT_SHIP_BLOCKED_CODE ? httpStatusOfCode(code) : (本地表 ?? 500)` | 被 `compositeStatusTiersB68` 判红：**"本地表查不到就问注册表"是对的，但兜底数字不许住在调用点** |
| ② | `本地表 ?? lookupErrorCode(code)?.status ?? 500` | **仍判红**：`?.status ?? <数字>` 这一族形状在 `shipping/route.ts` 里**必须为零**（v2.47 复核 I-3 的判据） |
| ③ ★ 定稿 | `本地表 ?? httpStatusOfCode(code)` | ✅ 绿。**档位只从注册表拿，缺码即抛 = 编程错误**（与同文件 document-set 那处同一契约） |

### 9.3 ★★ 由②→③ 逼出来的一个**真缺陷 + 真修复**

`httpStatusOfCode` 缺码会**抛**。而实测 `ShipmentMutationErrorCode` 里**有 6 枚码从来没登记进注册表**：
`INVALID_INITIAL_STATUS` · `INVALID_SHIPMENT_STATUS` · `INVALID_SHIPPING_METHOD` · `CREATE_FAILED` · `DELETE_FAILED` · `COMMIT_TRANSACTION_FAILED`。
⇒ 换成③之后，这 6 枚码一旦真的返回就会**抛错 —— 而 PATCH 处理器没有 try/catch**，
  那就是"请求回不到响应"（比 500 更糟）。**所以③与"补登记这 6 枚码"是一次改动，不能只做一半。**

★ 顺带修掉一处**既有的档位错误**（不是本次引入）：这 6 枚码原先一律经 `|| 500` 渲染，
  于是"运输方式不合法"（用户改一下就好）会被显示成"服务器内部错误"。
  现在按性质定档：校验类 **400**、失败类 **500**。
