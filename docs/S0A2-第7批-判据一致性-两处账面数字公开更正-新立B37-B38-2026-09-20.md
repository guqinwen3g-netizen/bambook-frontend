### 2. B33 两处误判剔掉 ⇒ **53 → 51 处 / 23 → 21 文件**（公开更正）

### 3. B34 判据从正则换成括号配对扫描 ⇒ **121 → 149 处 / 31 → 33 文件**（公开更正）
旧正则 `Object\.assign\(\s*new Error\([\s\S]{0,240}?\),\s*\{([^}]*)\}\s*\)` **整类漏**两种常见写法：
- ① 属性对象里出现任何 `}`（嵌套对象、`...(cond ? { a: 1 } : {})`）；
- ② 实参列表带**尾逗号**（`{…},\n)` ⇒ `\s*\)` 直接失配）。

新判据做真括号配对（跳过字符串与模板串、按顶层逗号切实参、忽略空实参）。
**先验真再落笔**：13 个文件逐条打印命中点的属性对象，全部确认是真实 `Object.assign(new Error(...), { code: ... })` 且无 `statusCode`。
- 最大单文件 `shipping/allocationService.ts` **7 → 21**；差值 **28 处全为虚低、无一处反向**；
- 与复核报告的独立重量**逐域相同**：finance **45** / shipping **31** / suppliers **3**（= 它们给的 79）⇒ 两支实现互证；
- 守卫里加一条**"旧正则漏的两种形状必须被新判据数到"**的对照，并**显式记账虚低量 28**（不许悄悄换基线）。

同时把复核的"无回归"结论依赖的三件前提转成可证伪用例（**D47**，处置栏 P1/P2/P3）：
- **P1** `shipping/allocationService.ts` 合票抛点靠本文件 `:549` 那层 catch 吸收 + 两个码在 `shipping/route.ts:752-753` 已明写 **409**；
- **P2** `finance/allocationService.ts` 两处抛点（`:230` / `:235`）**只靠** `finance/allocationMutationService.ts:28` 的 `PASSTHROUGH_ERROR_CODES` 白名单；

★ **复核结论本身也被复核掉一条**：报告原话"`assertConsolidationAllowed` 零生产调用方"，
实测它在本文件内被 `createAllocation` 调 **2 次**（`:506` / `:527`），只是外部没有消费者。
