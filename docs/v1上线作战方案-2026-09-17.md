## ⚠️ 方向修正（Kevin 2026-09-17 拍板，以此为准）

本文初稿把重心放在「部署落差」上，**这是把信号看反了**。Kevin 的纠正：

> 现在根本不是程序验收收尾的问题，更不是部署的问题。**现在还在开发阶段**。
> 最重要的，是确保程序的设计、实现、交互、使用功能、页面、业务逻辑，
> **与实际的业务能够完美匹配、真正投入生产**。
> 部署窗口和数据库备份，是**确认投入生产状态时**才要考虑的事（生产目前只有演示数据，随时可推）。

据此重写重心：**当前的头号目标是「业务匹配度」，不是「部署完备度」**。
原五阶段中，部署相关的 1/2 阶段**降级为最后一步（阶段 D）**，前置全部让给业务匹配迭代。

**为什么我原来会偏**：生产分叉（307 commit + 3 个安全修复未上线）是个很响的信号，
自动化核查容易把它当成主要矛盾。但「代码没上线」是可以一次推解决的；
「程序跟业务不匹配」只能一轮轮对齐，且**必须由业务方参与** —— 后者才是长坡。

## ⚠️ 方法论修正（Kevin 2026-09-17 第二次拍板，同样重要）

> 实际业务操作当中有**多变性、多样性**。如果按一个固定死的一条业务线或剧本去做验收测试、做分析，
> 那它就只是一个特定的剧本，对于整个程序的验收和提升**毫无作用**。
> 判断要全方面多样化，结合专业的业务场景与业务判断 ——
> **你不是一个 demo 的验收员，而是真实这家公司要实际操作使用的人，做最全面最严苛的判断。**

**我错在哪**：上一节我把「业务对表」设计成 12 条业务线逐条走 —— 那本质还是 **happy path 剧本集**。
真实业务 80% 的麻烦不在主干，而在**变异**：分批出运、拼柜、少收汇、改单、延期、索赔、
多币种、不同贸易条款、客户指定货代、反复打样…… 固定剧本一条都碰不到，跑通了也不说明系统可用。

**正确的方法**：不是走线，而是**对撞** ——
把「系统写死的假设」和「真实业务的变异」并排，看哪里会撞墙。

```
系统侧的假设（我能扫描）  ×  业务侧的变异（只有 Kevin 知道）  →  撞墙项 = 真正的差距
```

**维度矩阵**（替代流程线）。每个环节不问「能不能走通」，而问「有多少种变化、系统承不承得住」：

| 维度 | 可能的变异 |
|---|---|
| 一张订单怎么出 | 整单一次出 / 分批出 / 并到别的单一起出 / 客户自提 / 空运 / 快递 |
| 一个柜怎么装 | 整柜单票 / 拼柜多票 / 多客户拼柜 |
| 钱怎么收 | 一次全收 / 分次收 / 少收（扣费）/ 多收 / 第三方代付 / 逾期迟收 |
| 币种 | 单币 / 双币（采购买人民币、卖美元）/ 汇率波动 / 两次汇率并存 |
| 改单 | 改数量 / 改价格 / 改交期 / 加单 / 减单 / 取消 |
| 异常 | 质量异议 / 索赔 / 退货 / 短装溢装 / 延期 / 工厂没做完先出一半 |
| 客户 | 直接客户 / 贸易商 / 客户指定货代 / 客户自有仓 |
| 样品 | 一次通过 / 反复打样 / 不确认就投产 / 分批寄样 |

**判定口径升级**：不判「能不能走通」，判「**实际干活的人会不会出错账、会不会卡住、会不会骂娘**」。
重点看**异常与变异**，主干流程反而不用反复验。

## 〇、修正后的判断：现在缺的是「业务契合度验证」，不是「部署」

功能都做了（模块级全绿），但**「做对了」不等于「是业务要的样子」**：
字段含义、流程顺序、口径算法、交互顺手程度、页面信息密度 —— 这些**我的脚本一律验不出来**，
脚本只能验「没报错」。真正能判定的只有用这套系统干真实活的人。

所以最高效的路径不是我先写验收清单再部署，而是：
**用真实业务跑一遍 → 记录每一处「跟实际不一样」→ 快速改 → 再跑**，循环到 Kevin 说「这就是我要的」。

## 一、总纲：从「功能驱动」切到「业务匹配驱动」

**立即停止开新功能批次。** 剩下的力气全部用于：让程序长成业务的样子。
部署（含备份、窗口、回滚）放在确认要投入生产时再做 —— 生产目前只有演示数据，随时可推，不是风险项。

## 二、修正后的四个阶段（业务匹配为主，部署最后）

### 阶段 A：真实业务对表（最关键，立即启动）

**目标**：用真实业务把系统走一遍，把「系统要求 / 系统算的」和「实际业务有的 / 该算的」逐处对上。

三种启动方式（成本从高到低，价值从高到低）：

| 方式 | 怎么做 | 适合 |
|---|---|---|
| **A1 真单实走** | Kevin 口述一单真实业务（客户 → 报价 → 订单 → 样品 → 出运 → 报关 → 收汇 → 结案），我照着录进系统走完整流程，每一步记录偏差 | 最准，能暴露字段缺、顺序错、口径错 |
| **A2 流程对表** | 我把系统里的完整流程列成清单，Kevin 逐条判「实际业务是不是这样」 | 最快启动，不需要真实数据 |
| **A3 自助走查** | Kevin 自己操作系统干一遍活，把每一处「不对劲」记给我 | 最贴近真实手感，但要占他时间 |

产出：《业务匹配偏差清单》，每条按三级分类：
- **阻断级** —— 业务走不下去（流程断了、必填字段业务根本没有）
- **口径级** —— 不报错但算错/含义不对（**最危险**，静默错账）
- **体验级** —— 交互别扭、页面信息不对、该有的入口找不到

### 阶段 B：按偏差批量修（快修快验）

按 阻断 → 口径 → 体验 的顺序修，每批保持「门禁全绿 + 落账」的现有纪律。
每修完一批，回到阶段 A 复走确认 —— **迭代速度是这个阶段的核心指标**。

### 阶段 C：循环到「这就是我要的」

判定标准只有一条：**Kevin 用真实业务走完一遍，说「这就是我要的」**。
不是我验完，也不是测试全绿。

### 阶段 D：部署（确认投入生产时才做）

到这一步才谈：窗口、数据库备份、迁移、回滚。**生产目前只有演示数据，随时可推，不是当下的风险项。**
- 前置：9/3 之后 10+ commit 动过 schema（生产一次没 migrate 过）→ 部署前必须跑迁移
- 前置：全仓无备份脚本 → 先补 `scripts/backup-prod-db.sh`
- 3 个安全修复（SSE 通知串台 / 门户登录防爆破 / 上传白名单）随这次一起上

## 四、必须你拍板的三个问题（其余我全包）

1. **生产库现在有没有真实业务数据？**（有真人建的订单/客户？还是只有演示数据？）
   - 有 → 备份必须做实、迁移要挑窗口、回滚预案要演练
   - 只有演示数据 → 部署风险大幅下降，可以随时推
2. **部署窗口**：系统现在有没有人在用？（有的话要挑没人用的时段）

## 五、为什么这是「最高效」的路径

- **不做新功能**（收益≈0，且在扩大部署落差）
- **先钉 DoD**（避免验收阶段返工 —— 那是整个项目最贵的返工）
- **部署前置做完备**（上线失败回滚一次 > 花半天做准备）
- **你的三项输入全部并行**，不占关键路径
