# Bambook 业务与产品执行清单

创建时间：2026-10-05 02:39:38（北京时间）。

执行授权更新：2026-10-05，用户授权本线程持续完成两份清单中已确认的全部内容，由本线程 sub-agent 统一实施与验收，不再派回隔壁独立会话。先完成原主页与审批清单、通过验收并提交，再按完整闭环推进本清单。各条历史“暂不派发”标记不再阻止已确认内容执行；仍待讨论的业务政策不得擅自定案。

## 1. 客户专属面料使用校验（已确认，身份校验实施中）

- 客户与属主身份均明确时，只按组织 ID 判断。同名不同 ID 不得放行；同 ID 改名仍识别为属主。名称不作为覆盖身份冲突的授权依据。
- 历史缺客户 ID 的关联标为“属主身份待核对”，提供核对绑定入口，不静默猜测归属；保留既有记录可读。需要新增受保护引用时，先完成身份核对或提供有效授权。
- 允许属主客户明确授权指定其他客户使用。保存产品、属主、被授权客户、适用业务范围、有效条件和授权证据引用，记录实际登记人和时间；内部领导批准不得冒充属主授权。
- 在报价、订单、样品和出运各个实际引用入口统一执行校验；授权必须准确覆盖本次客户、产品与动作，未授权或依据不可核验时给出具体阻断原因及核对入口。
- 授权修改或撤回保留旧版本。新引用检查当前有效授权；已承诺业务不得因撤回自动篡改或取消，提示责任人核对后走原业务变更流程。
- 页面明确显示专属属主和本次使用依据，不只显示通用报错。
- 检查：同名不同 ID 阻断、同 ID 改名允许、历史身份待核对、指定客户有效授权允许、范围不匹配拒绝、撤回后新引用拒绝且旧单历史保留。

## 2. 产品归档与活跃业务（已确认，排队执行）

- 将归档与删除使用限制分开。归档停止新业务引用，客户专属属主、授权、已确认成果与历史规格依据继续保留；不能靠软删专属关联使后续校验变为无产品可查并放行。
- 归档前显示已关联且未完成的报价、订单、开发和出运，按当前可见权限列出影响；不向无权限账号泄露详情，影响核对失败时不冒认无关联。
- 尚未被客户接受的报价保留历史，但再次发送或接受时必须核对归档状态，通过恢复产品或明确更换产品/修订报价处理；普通报价批准不能忽略归档限制。
- 客户已接受但尚未转订单的报价，允许按客户已接受的冻结版本转单；必须有可核验的原产品身份、规格和专属使用依据。依据缺失时先补核对，不改用最新档案、不凭品名猜测。
- 已确认订单及生产、出运、售后继续按原承诺版本和原授权依据履约，遵守原有质量、库存及资金门禁；归档不得自动取消业务，也不得默默解除客户专属限制。
- 归档后的历史详情能回读原名称、规格、授权和关联业务；新报价、新订单普通选品不显示为可选活跃产品。已接受报价转单的限定承接不是任意新引用豁免。
- 检查：归档预览影响业务、专属限制未消失、未接受报价不得直接继续、已接受报价原版转单、生产出运历史可读、原依据缺失明确阻断。

## 3. 开发项目、订单内的报价与规格依据（已确认部分执行；待定政策不执行）

- 已明确的业务定位：报价针对已有开发项目或订单中的规格形成商业报价，不另建一份脱离来源的产品资料。可以保留独立报价记录、编号和历史，但操作必须围绕对应业务。
- 当前实现：报价单头已有可选开发项目、订单、订单条目关联；报价明细主要保存编码、描述、数量、单位和价格，未保存完整来源规格版本。开发入口带入项目和部分描述，没有明确带入具体成果版本。
- 当前实现：报价转单检查已接受、是否重复转单等条件，然后创建新订单；没有按原订单关联区分“原订单改价”与“新增订单”。
- 拟执行：逐行绑定实际来源条目及本次规格版本；从来源带入规格，商业条件在报价中填写。支持一个业务内多个条目，不能只靠单头关联推断每行对应什么。
- 拟执行：区分开发报价形成新订单、已有订单的价格/条款变更、基于历史订单创建返单；原订单变更通过变更流程生效，返单明确创建新单并保留来源。
- 拟执行：客户接受时冻结对应规格、报价版本及商业条件；来源后续变动显示差异，不能自动替换客户接受的依据。涉及已确认条款的变化沿用客户确认最终版本的规则。
- 拟执行：服务端核验来源存在、客户一致、条目所属、可见及操作权限；多来源关联须有明确关系，不能接受任意 ID 拼接。历史无来源记录保留可读并提供核对入口。
- 已确认：开发尚未完成时，允许引用明确的阶段规格报价；逐条列明未定项并在客户可见的报价内容中展示。记录具体产品条目、规格版本及适用的工厂方案/开发轮次；工厂尚未确定时明确标注未定，不虚构绑定。
- 同一规格允许多个商业方案；报价采购数量与开发打样数量分别保存，不能默认继承打样数量作为采购数量。规格修改先在来源形成新版本，再引用修订报价。
- 客户接受报价不等于允许生产；订单继承接受版本后仍执行确认样、工厂核定和生产放行条件。
- 已确认：订单直接继承客户接受的产品条目、规格版本、数量、单位、价格、币种及已约定付款/交货条件；修改时展示差异并走变更确认，不重新手录替代原依据。
- 已确认：订单补齐报价未定的履约字段；改变客户已接受承诺时需要客户确认，内部负责人安排按内部权限处理。未定技术项继续明确标注并形成待办，相关生产环节确认前不得放行，不自动读取最新档案补值。
- 已确认：由负责业务员登记客户接受的具体版本和证据，允许部分条目接受；按 3A、3B 的范围与证据规则实现。

## 3A. 部分接受与生产放行（已确认边界执行，具体接入须核对）

- 允许客户只接受报价中的部分条目，逐条记录接受范围；未接受部分保持待确认，不整体标为已接受。
- 允许同一订单中已满足条件的条目或批次先生产，其余继续等待；放行依据和数量范围必须留存，不将部分放行展示为整单全部可生产。
- 待细化：生产放行核验规格、适用确认样、工厂、数量范围及订单约定的商业条件；缺项显示责任人和处理入口。
- 已确认：放行后变更只作用于明确选中的条目和数量，已生产部分另行处理，原记录保留可追溯；不得用最新版本覆盖已有生产事实。
- 待细化：未开工部分变更后重新核验放行条件；已开工部分明确进度、数量、处置及费用/交期影响；已完成或出运部分通过适用返工、退货、售后流程处理。逐批展示所用规格版本。
- 已确认：涉及已放行批次的规格、数量或工厂变更，须由跟单负责人登记工厂已收到并接受新版指令的依据，才算交接完成；未确认持续保留待办，工厂无法执行时记录原因并交回处理。
- 待细化：变更前核实工厂实际进度、数量与核实时间；区分“已要求暂停”和“工厂已确认暂停”；新版指令明确适用批次和替代的旧版本。
- 客户接受登记责任、证据要求及部分接受已确认，按 3B 执行。仍待定：新增变更审批权限政策、变更费用/交期承担、剩余报价有效期政策，以及历史缺来源记录的具体补核方式；保留现有合法权限和规则，不由 agent 自行设定。

## 3B. 全局客户确认证据（已确认；共享基础实施中，全站接入随后执行）

- 适用于报价、规格、样品及其他需要记录客户确认的业务，不限于报价；由负责业务员登记，必须附可追溯依据，内部批准不代替客户确认。
- 邮件方式：在系统邮件阅读界面选中客户明确确认的文本，通过“作为确认证据”入口提交；保存原邮件完整正文快照、选中原文及定位、邮件来源标识、发件人/收件人、主题、邮件时间、登记人及登记时间。详情展示重点段落并可展开原邮件；保留相关附件引用，明确确认所依据的附件版本。
- 截图方式：用户上传原始截图作为证据；登记来源说明、客户确认人、确认时间和登记人；保留原图可查看，不把识别出的文字替代原图。
- 两种方式使用同一登记界面，明确确认事项、关联业务条目、版本和接受范围；预填关联后由用户核对提交，不能仅划词或上传就自动批准/改业务状态。
- 已确认：保存时必须当场绑定准确的业务、确认事项、条目及版本；不提供“保存后稍后关联”或待关联证据池。未选定有效对象时不得提交；取消操作不形成正式证据记录。
- 邮件入口优先推荐邮件已关联客户/订单/开发项目下待客户确认的事项，展示可辨认的名称、编号、版本及负责人；用户核对选择，不自动绑定。无合适推荐时按业务编号、客户或产品等搜索，先定位业务再选确认事项；只返回有权访问的对象，客户范围可以明确调整，不以自动客户匹配排除合法目标。
- 提交校验目标权限、版本和状态；同一来源证据可引用于不同明确事项，避免重复存储原件。同一目标版本/确认事项重复提交返回已有记录或提示核对，不产生重复确认；网络重试须保证同次操作不重复写入。
- 已确认：提交前展示拟登记的确认结果及适用条目/版本；一次提交一致性地保存证据关联与客户确认记录，成功后更新业务详情和对应确认待办，其他未满足审批或生产条件继续保留。失败不显示已完成，支持安全重试；不要求用户到另一处重复登记确认。
- 已确认：登记人核对证据与目标版本；明确不匹配时先纠正选择或处理差异，不得将旧版证据登记为新版确认。系统检查可验证的版本关联，不能声称能自动判定任意邮件或截图的真实确认含义。
- 已确认：报价按条目登记接受范围；规格与样品按本次确认的具体参数/项目登记，允许部分确认，其余继续待确认。颜色确认不能代替手感、尺寸或整体质量确认，任何客户确认均不得直接冒充生产放行。
- 证据按关联业务权限访问；原邮件快照与原图保留，更正通过新增记录保留历史，不覆盖原依据。邮件存在于个人邮箱不代表其他账号天然有权读取邮箱。
- 待核对：现有邮箱阅读/同步能力、正文选区定位、邮件及截图存储、附件版本引用、现有确认证据字段与各业务接入入口；据此拆分执行任务。
