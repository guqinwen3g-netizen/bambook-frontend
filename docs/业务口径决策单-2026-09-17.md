## A 组 · 客户索赔 / 贷项（外贸财务主线）

> **本组用大白话写，可直接给业务方看。**

### A1. 客户投诉了，先支持哪几种处理方式？ —— ✅ **已定（2026-09-17 14:51）**

> **业务方答复**：「售后问题非常复杂多样，**不能说只是金额折算这一个方案就可以让系统完善**，
> 而是确实需要**考虑到各种情况，并且都要真实可用完善**。具体的专业性设计还得依赖你去做。」

⇒ **口径：四种全部要做（不做"只做折让"）**；专业设计由我方提出、业务方确认。
⇒ **交付节奏**：**范围不砍**，建议**分两期上线**（一期「折让 + 退货退款」/ 二期「换货补发 + 返修」），
　理由不是省事，而是**「真实可用完善」要求每条都验证到位**，四条同时上线出问题难定位。
　**每期都完整可用**，不是半成品。

**背景**：客户收到货不满意，要跟你们"讨个说法"。**系统现在一种处理方式都没做** ——
只能靠财务**手工去改发票金额**把账抹平。而这正是我们这两天修掉的「**僵尸票**」的成因
（票上写着"还欠 100 元"，其实早就抹平了，系统看不出来）。

四种处理方式，**区别只在一件事：动不动钱、动不动货**：

| 处理方式 | 大白话 | 动什么 |
|---|---|---|
| **折让** | "这批色差我们认了，**给你少收 5000**" —— 货不用退 | **只动钱** |
| **退货退款** | 客户把货**退回来**，你把**钱退给他** | 动钱 + 动货 |
| **换货补发** | 客户把货退回来（或就地报废），你**重新做一批发过去** | **只动货** |
| **返修** | 客户把货退回来，你**修好再发回去** | **只动货** |

### A1-附. ★ 专业设计骨架（我方提出，待业务方确认）

**① 一次客诉 = 一个「售后案件」，案件里可以同时有多条处置。**
关键判断：真实客诉常常是"100 件里 30 件退货、70 件折让"，**不是一种客诉对应一种处理**
⇒ 模型必须是「**一个案件装多条处置**」，而不是"一种客诉类型对应一套流程"。

**② 钱、货分开走，各自只有一张单：**

| 腿 | 谁汇进来 | 落成什么单 |
|---|---|---|
| **钱** | 折让、退货退款 | **一张退款单**（客户拿到的就是这张正式单据） |
| **货** | 退货退款、换货补发、返修 | **一张退货入库单** |

**③ 退回来的货必须记清去向**：报废 / 换货补发 / 返修。
**不记清，货就在账上凭空消失**（库存与实物脱钩）。

**为什么这样比"四种各做一套"更稳**：
- **钱只有一条线** → 对账简单，不会扯皮"这笔钱是哪条处置退的"
- **货只有一条线** → 库存不会重复加、也不会漏加
- **案件是总账** → 客户问"上次那批货怎么处理的"，一个案件全看得到

**④ 「真实可用完善」的 5 条验收标准（不是"能跑就行"）：**

| 标准 | 含义 |
|---|---|
| **有单据** | 每条处置都要能打出一张纸（客户/车间拿着能办事） |
| **有审批** | 谁能批、批到多少，写死在系统里，不靠人记 |
| **有留痕** | 谁改的、什么时候、为什么，全留 |
| **能撤销** | 谈崩了/开错了能退回去（**不能开了就下不来**） |
| **真库验过** | 拿真数据跑通、跑完清干净，不只是单测绿 |

**不做的后果**：客户折让只能靠手工改发票金额抹平 —— 那正是本批修掉的「僵尸票」成因
（票面与实际净额脱钩，账龄、逾期天数、信用额度全被它污染）。

### A2. 赔的这笔钱，客户**怎么拿到**？ —— ✅ **已定（2026-09-17 14:56，按行业标准）**

> **业务方授权**：「这个你也按照**最专业的行业的设计和理论**去做就可以。」

**行业标准答案：不是二选一，而是「一张凭证 + 一次结算」。**

外贸实务里客户折让/退货的标准凭证就是**贷项通知单（Credit Note, CN）**；
ERP 行业（**SAP 的 Credit Memo · Odoo 的 Credit Note · NetSuite 的 Credit Memo**）做法完全一致：

> **CN 是一张独立单据（独立单号），开出来挂一个「未核销余额」；
> 该余额可抵扣该客户的下张发票，也可现金退给客户；余额扣到 0 即结清。**

用大白话：**CN 是"欠条"，抵扣或退款是"还钱"** —— 先有欠条，再决定怎么还。**两件事都要做。**

**定案**：**开独立的退款单（CN），且它可被核销（抵扣/退款）**。
- 开单理由：它是**客户做账的凭据**，也是**追责依据**（"这 5000 是哪次客诉退的"）。
- 行业里**没有**"只抵扣不开单"的做法。

### A3. 退款单开出来之后，怎么算「结清」？ —— ✅ **已定（同一套理论）**

**现状的毛病**：系统只会算"发票有没有付清"，而退款单金额是**负的**，永远算不平
⇒ 它永久挂在应收里，**把账龄、逾期天数、信用额度全污染**。

**行业标准**：退款单**有自己的状态语义**，不套用发票那套"已付/未付"：

| 状态 | 含义 |
|---|---|
| **未核销** | 刚开出来，还欠客户这笔钱 |
| **部分核销** | 抵扣/退了一部分，还剩余额 |
| **已结清** | 余额扣到 0 |

**定案**：退款单走**独立状态**（未核销 → 部分核销 → 已结清），**不复用发票的 `Paid`**。
—— 这正是现在实现卡住的根因（`amount ≤ 0` 的票永远到不了 `Paid`）。

### A4. 供应商索赔怎么「结清」？ —— ✅ **已定（应付侧对称设计）**

**定案**：应付侧做**完全对称的一套** —— 供应商赔你钱就开一张**负向应付单**，
同样挂「未核销余额」，结清逻辑与 A3 一致。**不再单独讨论。**

### A5. 撤销索赔的流程 —— ✅ **已定**

**定案**：**撤销 = 作废该退款单 + 同步解开联动**（退货入库单状态回退、案件状态回退、审计留痕），
前端明确提示「此操作将撤销索赔」。
> 原则：**不能开了就下不来**（对应 A1-附 的验收标准「能撤销」）。

### A3. 贷项票的**终态**是什么？（现状是个死结）
- **现状**：`amount ≤ 0` 的票**永远到不了 `Paid`**（永久停在 `Issued`）。
- **选项**：(a) 改 `recalcInvoiceStatus`：`amount ≤ 0` 视为「开完即结清」→ `Paid` ·
  (b) 新增 `Settled` 语义 · (c) 贷项票不参与状态机（独立 status）。
- **推荐 (a)**：语义最直白，且不动状态机。
- **不做的后果**：贷项票会**永久挂在应收里**，账龄与逾期天数被它污染（已实测）。

### A4. 供应商索赔（贷项票）怎么「结清」？★ **与 A3 是同一口径，建议合并判**
- **现状**：**已上线**的供应商侧实例（`CLM-` 负向 Payable 票）永远停在「已开票」，没有任何办法变成「已结清」。
- **选项**：(a) 引入「**已冲抵**」终态：负额票在 `settleReturn`/对账动作时直接标为已冲抵 ·
  (b) 允许用**付款核销**负额票（放宽 `AMOUNT_EXCEEDS_INVOICE` 符号判据）—— 语义怪 ·
  (c) 不改，接受永久挂账。
- **推荐 (a)**。
- **不做会怎样**：净额是对的，但**财务对账时会一直看到它**，且「撤销索赔」没有出口（见 A5）。

### A5. 撤销索赔的流程怎么做？
- **现状**：作废这张票 = 撤销索赔，但**退换货单不联动**、动作名也不叫「撤销索赔」。
- **选项**：(a) 作废时**同事务联动**：`claimInvoiceId` 置空 + 退换货单状态回退 + 审计留痕 +
  前端提示「此操作将撤销索赔」· (b) 禁止直接作废，另建「撤销索赔」动作（需先建动作+权限+UI）· (c) 只加提示文案。
- **推荐 (a)**。
- ⚠️ 选 (b) 前必须**先把动作建出来**，否则就是死锁（现状：作废是**唯一**出口）。

### A6. 0 元应收票要不要直接拒？ —— ✅ **已定（技术约定）**

⚠️ **但不能**用「拒绝 0」替代判据修复 —— **负额贷项是合法的**（A2/A3 的设计就建立在负额上）。
