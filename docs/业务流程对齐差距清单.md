## 0. 总体判断

- 系统已有的底子是好的：跨页跳转协议 `crossModuleNav`（约 15 个消费方）、事件总线 L1-L10、报价转订单 / 开发案转订单两条真闭环、`docs/design/03-业务规则/核心业务流程.md` 主流程真源、DR-054「每个业务事实只有一个真源」的收敛方向。
- 割裂感的来源可归为四类，每类都有明确落点：
  1. **确认链双轨**：DR-054 新锚点（SampleBatch.confirmStatus）与旧锚点（SampleNode/GarmentSampleRound）并行活跃，前端两套面板同时挂着；
  2. **关联是单向/只写的**：转出去的链路有（开发→订单），但订单侧看不到来源、报价和开发之间零关联；
  3. **前端孤岛**：约 10 个模块自拉数据，不进顶层快照、不接 crossModuleNav；
  4. **多真源未收敛完**：样品模型 6 套并存（DR-054 进行中）、开票途径 4 条互相重叠、文档口径滞后于代码。

## 六、业务口径确认与 Backlog v0（2026-09-11 与业务逐条对齐）

> 本节记录业务方对清单中所有 `[需业务确认]` 条目的裁决与认知修正，是「差距事实 → 可执行修复」的桥。裁决来源：公司业务负责人逐条口头确认。基线不变（24f0366）。

### 6.1 已确认的核心业务模型（部分修正清单§0/§一的描述）

1. **开发的本质 = 开发一个产品**，不绑定单个客户，含内部开发；一个开发内可有多轮批次/版本。
2. **confirm（确认）= 从轮次中选定"批准通过的那版"**——确认的是**版本**，不是批次的抽象状态；确认后 → 产出**产品档案（ProductAsset）**。**一次开发可有多个确认样**（批次 A / 版本 A 都算成功）→ **每个确认样自动转一个产品档案，并各封一个样**。
   - ⚠️ **纠正 G1-8 描述**：真源是「**确认样 → 产品档案**」，不是「封样转档」。code 里 "convert-to-asset 从 seal" 的锚点与业务语义不符。
3. **封样（seal）= 为某个 design 指定"标准样"的物理实物确认**，独立动作，不直接产生产品档案。
4. **报价 = 关联审批单，本身不带规格/BOM**。报价指向某个项目/订单/具体条目，可多粒度发起。
5. **报价审批层级规则（重点，新增）**：单条目也可申请报价（确认某款价/某配件价）；大报价可拆成小条目逐个批；**最终必须把"总报价"整单报出并再"总审批"一次**。合并规则：总报价内**所有小条目都批过 → 总报价默认全批**；**只要有任一小条目未批 → 总报价必须连带审批**，并提示"仅剩此条未批，其余已批"，避免重复审批困惑。
6. **PP 样/大货样属生产，不属开发环节**（修正 G1-6：当前代码把 pp/top/ship 排除在批次确认回写之外**符合口径，属正面项，不改**）。
7. **样品两种"寄送"分离（G1-13）**：开发流程内寄样（客户要求开发→寄给客户确认）**归开发**；业务员自带样品出库寄送**归样品库出库**。样品收费链 = 样品→开发→报价→财务发票。
8. **核心价值闭环**：报价（粗）→ 订单（确认价）→ 生产/样品确认/出运 → 回款（业务员认领）→ **订单结案（"绿"）** → 利润 = 回款 − BOM 成本。*生产细节（MES/QC 阶段）= 可选状态补充，可折叠/可 ignore，不驱动核心链*。

## 七、三层对齐 + 批次化落地工作章程（2026-09-11 业务方拍板，工作方法论唯一章程）

### 7.1 三层框架（任何工作展开前先对齐这三层）
- **L1 框架层（为什么）**：北极星、底座设计、需求大方向、波次规划 —— 定方向与边界。
- **L2 业务口径层（要什么）**：整套业务流程的**每个颗粒度、每个细节** —— 核心，持续探讨、零差错，系统是业务的忠实代理。
- **L3 现状层（有什么）**：软件**实际状态** —— 前端/后端/接口/数据结构/体感/可操作性，只看真实代码与真实行为。

### 7.2 对齐 + 批次化落地流程
1. **三层对齐**：L2 期望 − L3 现状 = 差距（§一~§五即产物）。
2. **差距 → Backlog**：每条给裁决（确认/修正/砍掉/延期），排序分级（§六 Backlog v0）。
3. **一个批次一个批次落地**：每批聚焦一个"最小可交付业务事实"，走 **定向现状核准 → 设计 → 实现 → 门禁全绿 →（可选）部署**；每批结束三层重新对齐一次，防止往回漂。

### 7.3 铁律
- **先对齐后落地**：未做 L3 现状核准的事项不进入实现批次。
- **原地核算、不空转**：L3 现状核准只碰与该批口径强相关的点，不做全量重扫。
- **文档漂移随批清**：任何涉及模型/状态机/口径的改动，同批回写文档（D-1~D-4）。
- 当前重心 = **完整交付主线业务**；风险联动、数据中心统一数据源等非重点项登记延期（§6.4）。

### 10.2 版本与范围切分（v1 = 上线零缺口）

### 10.3 关键业务规则定案
1. **订单结案绿** = 全额核销自动判定：发票全部回款核销完毕订单自动变绿，无人工动作。**→ ✅ 已落地（2026-09-13）**：主链路实跑发现实现原为「业务员**手动**确认结清」（`orderServiceV2.settleOrder`），与定案冲突（全库 69 单 0 结案）；业务方拍板按定案改为自动。现核销变更后自动同步：应收发票全部 `Paid` → 自动写 `settledAt`（`settledBy='system:auto-settle'`）+ 审计留痕；撤销/调减核销致未结清 → **自动退回**，**人工结案的记录不动**。人工「确认结清」端点保留作兜底（无应收发票的订单）。详见文末「结案绿」条。
2. **回款认领双通道**：财务登记收款→可主动核销到发票→订单自动绿；财务未操作时，业务员可实时查看新收款并自行认领对应发票。付款确认始终财务主动。
3. **多币种**：USD 收款 / RMB 付款双币种，订单级锁汇率，汇兑差异入利润。
   - **收款门禁单币种口径（2026-09-13 业务方定案）**：订单收款恒为销售币种；末批发运收款门禁（`totalPaidOfOrder`）若遇该订单收款发票**混合币种**或**与门禁币种不符** → **报错拦截**（409 `FINAL_PAYMENT_GATE_CURRENCY_MISMATCH`），**绝不跨币种直接相加**；不做隐式汇率折算（`Order` 无锁汇率字段，`Invoice.exchangeRate` 折算链未定案）。管理员可 `skipGate` 豁免并留痕。已落地。

#### 10.4.1 六角色 ↔ 系统内置角色映射（2026-09-12 业务方定案）

- **不新增角色**，按现有 7 个内置角色落位：**系统管理员（role-admin）= 领导；超级管理员（role-super-admin）= 老板**。业务定案的"老板/领导"一格在系统里是两个层级：领导（admin，业务审批/电子签/全局总览，兼系统配置）与老板（super-admin，最高权限 + 唯一可看薪酬）。
- 其余对应：业务员 = role-sales；销售主管 = role-sales-manager；财务 = role-finance；QC = role-qc；单证/后勤 = role-logistics。
- **数据范围 = 系统里配的小组**（Team / TeamMember / TeamDataGrant 表已存在）：主管看本组，业务员看自己 + 被按单分配给他的；**不是"同部门互相可见"**（部门只保留展示与审批链用途）。按单分配（TeamDataGrant）作兜底，目前仅 relations 域消费，需全域推开。
- **撤回（O-1）口径**：谁提交的谁撤 + **领导可撤**（业务方 2026-09-12 追加澄清：**销售主管就是领导，同一档**）。驳回是独立动作，不复用撤回权限。
  - 待收口：目前主管与老板一样可撤任何人的申请，「只撤本团队」的收窄由第二批三档数据范围引擎提供。
- **敏感字段维持现状**：领导（admin）可见 成本/利润/佣金/税务底值，**不可见员工薪酬**；薪酬仅老板（super-admin）。成本/利润对业务员一律遮罩。
- **Agent / API Key 身份口径（业务方定案，架构级）**：**把 AI 当员工看**——员工通过前端 UI 操作系统，AI 通过 MCP/API 操作系统，二者只是入口不同，**权限取决于该 AI 自己的账号与身份**。因此 API Key 不是"万能钥匙"，必须绑定到具体主体账号（有角色、有数据范围），多 Key 多身份；权限一律走角色矩阵，不设旁路。
  - **生产处置决定（2026-09-12，接手 Agent 定夺，已核实）**：Mac Mini 生产现状 = `BAMBOOK_REQUIRE_AUTH=true`、未配置任何 `BAMBOOK_AGENT_API_KEY_*`。**v1 暂不配 Agent 主体**。依据：① Agent/MCP 属 v2；② 前端业务调用统一走 `apiService.requestJson`（JWT + API Key 同时带），登录后有真实主体，新增的 orders/procurement/bom 读 scope 不影响；③ 现在配一个"通用服务账号"等于给任何持有 SDK key 的人开绕过员工身份的旁路，与本条定案相悖；④ 未绑定主体的失败模式是显式 401/403（可观测），不会静默出错数据。
  - **预案**：v2 接 AI / 第三方系统集成时，在用户管理建一个员工账号（如「AI 跟单助手」），服务端配 `BAMBOOK_AGENT_API_KEY_MAP="key=userId"`，权限 = 该账号角色矩阵。**不开任何旁路**。

#### 10.4.2 单据可见性：随订单推导（2026-09-12 业务方弹窗定案）

- **口径**：跟单单据与成本单据的可见性**随关联订单**——能看到某张订单，就看得到它的 BOM、采购单、生产 / QC / 出运 / 报关。
- **动因（代码现实）**：这类单据**没有归属人字段**（`PurchaseOrder` 只有自由文本 `buyer`；`BOM` 只挂 `productAssetId/orderId/quotationId`），无法用通用「ownerId ∈ 用户集」的行级范围过滤，只能由「关联订单是否可见」推导。
- **实现**：新增基础件 `auth/orderVisibility.ts` —— `resolveVisibleOrderIds()` 复用订单可见性唯一真源（`orderService.buildOrderListScopeWhere`：客户跟进人 ∪ 按单分配 ∪ 小组共享）解析出白名单；`null` = 不受限（全权角色 / dev 旧口径），数组 = 白名单（**空数组 = 一张都看不到**，与 null 语义不可混）。解析失败 → **fail-closed + error 日志**（静默放行等于泄漏）。
- **叠加方式**：白名单一律用 `AND` 叠加，**不占顶层 `OR`**（各域 search 已占用 OR，裸 OR 会互相覆盖——QA-SEC-1 踩过）。
- **详情防直读**：列表、详情、单据预览、来料记录一律按关联订单把关，命中外单 → 404（不泄露存在性）。
- **退化口径（本批判断，登记待确认）**：
  1. **无关联订单的 BOM**（自建 / 只挂产品档案，B-2 起允许留空）→ 走产品档案「图书馆」口径可见（否则业务员刚建好的成本核算表立刻从列表消失），成本字段仍受 `sensitive:cost` 遮罩。
  2. **无关联订单的采购单** → 严格不可见（采购价属成本核心，宁可保守）。
