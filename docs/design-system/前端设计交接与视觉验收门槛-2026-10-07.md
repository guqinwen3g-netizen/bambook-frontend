# 前端设计交接与视觉验收门槛

日期：2026-10-07  
状态：部分原则已确认，其余细节仍为设计提案。用户已确认跨页视觉统一和设计质量要纳入前端要求，并在 §10 明确四项硬约束；已确认原则以 `.qoder/skills/bambook-ui/` 为唯一执行真源。本文其他具体卡片尺寸、图标映射和验收细节仍未逐项确认，不表示现有页面已经达标。

本轮范围：用户要求先理解并复核 BDS HTML 和设计要求的完整性，**暂不修改软件本体**。本次补充保存用户要求、源码证据和设计缺口，并在 §9 保存用户随后提供的订单页截图复核；§10 记录用户对 Preview 参考范围及四项前端硬约束的确认。不把文字补充当作视觉验收通过。本文仍不是覆盖全站所有页面的定稿施工图。

## 1. 先说清问题在哪里

Bambook 已有 BDS、页面骨架、标题栏、间距和组件规范。当前缺口主要在执行链：模块设计文稿详细描述了业务状态和功能，却没有把每个页面必须采用的视觉结构、共用组件和实际呈现检查，作为 coding agent 的硬性交付物。结果是不同模块各自拼入口、容器和控件；“功能做完”就被当成完成。

前一轮源码抽查曾见到开发入口使用纯文字按钮、订单和 QC 各自使用不同卡片。2026-10-07 本次重新读取时，订单和 QC 已引用 `BusinessDomainWorkspace.tsx` 的共享入口，说明代码仍在变化，不能继续用旧抽查描述当前全站。共享组件只能约束其覆盖的局部；页面壳、上下文区、滚动区、业务内容和操作区仍须逐页核对。本轮未取得新渲染截图，不判定当前界面已经达标。

问题也不只在执行链。上一版本文过分集中于入口卡片，没有完整确定整页的几何、信息结构、操作编排和跨页对应关系。即使逐条照做，也仍有产生混乱页面的空间，不能据此承诺视觉一致。

因此，不把要求写成“注意美观”。前端设计必须是开工方案的一部分，实现和验收都必须包含它。

## 2. 每个页面交给 coding agent 前必须给出的设计内容

模块设计文稿须按页面和状态说明以下内容。不得只交功能大纲或组件清单：

1. **页面层级**：页面壳、统一标题栏、业务入口、当前工作区、内容分组和滚动区域分别是什么；当前上下文标识与可点击切换项如何区分。
2. **内容结构**：每个分区采用主容器、连续列表、表格、字段组还是留白加标题；为什么需要分隔线或卡片；不得让实现方临时决定“这里加线还是加卡片”。
3. **排版与几何**：标题层级、正文层级、卡片及控件尺寸、对齐、行高和间距引用哪个 BDS 配方。页面级标题统一使用 `PageHeader`；标题高度和主内容边距由共享布局规则决定，页面不得自行补位。
4. **逐项操作**：每个按钮、选择器和字段的名称、位置、主要/次要层级、启用条件、悬停/焦点/选中/禁用/加载/错误状态与点击后的页面变化。
5. **图标和图像**：给出具体图标资产及语义、尺寸、容器和摆放位置。优先使用项目已安装的图标库和既有品牌资产；不让实现方临时挑图、用 emoji 代替或画一套新图形。
6. **页面状态**：至少覆盖正常、空数据、加载中、失败/阻塞、无权限，以及流程尚未解锁时的表现。若业务采用逐步推进，未来步骤只显示在进度导航中，当前视图不预先铺出未来表单和内容；已完成步骤可回看，继续推进由业务员明确操作。
7. **屏幕适配**：写明主要桌面尺寸下的列数、换行、滚动区和窄宽度降级方式；不得依赖偶然换行或内容高度撑开页面。

设计方使用现有 `styles/bds/tokens.css`、`styles/bds/components.css`、`styles/bds/layout.css`、`components/ui/PageHeader.tsx` 及本目录已有的应用规则确定具体样式。缺少配方时先补共享组件或写明设计决定，再开工；不允许用页面局部的任意值拼出相似效果。

### 2.1 用户本轮明确要求：一致性包含整页几何

用户要求切换页面后明显属于同一个产品；不能只保证颜色、圆角和材质相同，却允许容器偏移、文字尺寸漂移和标题栏高度变化。

每类页面的设计样板必须给出以下约束，并标出尺寸由哪一层负责。模块文稿引用具体样板及其变体，不再把这些问题交给实现者自行选择。

| 对象 | 必须确定的内容 | 当前证据与待补点 |
|---|---|---|
| 页面外壳 | 页头与正文的左右起点、可用宽度、顶部起点、主滚动区域 | 当前 BDS 的 `--p-pagehead` 为 20/28/16，页面壳也带 padding；必须明确各自包裹范围，避免重复缩进。不能仅要求“都用 PageHeader” |
| 标题栏 | 总高度、文字基线、标题与右侧控件的对齐、没有操作时的占位、长标题与窄屏策略 | 当前 `.bds-pagehead` 用 flex-end 和 padding，没有固定总高度。高度不能未经样板确认就写成 64px 或宣称已统一 |
| 内容栅格 | 主内容宽度、列数、列宽、列间距、分区纵向间距、窄屏降级顺序 | 同类页共用栅格；允许命名且明确用途的变体，不允许每个模块临时用不同 max-width 和 padding |
| 容器层级 | 哪个是独立任务、哪个仅是同一任务下字段组、何处用卡片/连续行/表格/留白 | 先按信息关系分组；不因字段多就套一层卡片，也不因页面空就补横线或容器 |
| 排印 | 页面标题、分区标题、记录标题、字段标签、字段值、状态、金额分别绑定字号、行高和墨色 | 当前 token 为 xs 12、sm 14、base 16、lg 18、xl 20。每个信息角色明确映射，禁止逐页以“差一点更合适”为由换字号 |
| 控件与行 | 同一行控件高度、按钮间距、表单列宽、标签位置、表格列对齐及行密度 | 采用明确语境配方；长名称、长编号、多状态和多操作不能靠偶然换行决定布局 |
| 稳定性 | 空态、加载、无操作、错误及长内容时哪些几何保持不变，哪些可增长 | 所有标题、操作和字段都按对应样板占位与增长，不能仅验证短数据的正常首屏 |

以上是必须完成的设计项，不是已完成测量的结论。尚缺的数值和构图必须在设计样板中定下，不能以“遵循 BDS”代替。

### 2.2 用户本轮明确要求：去掉说明噪声，保留完整业务信息

操作界面不在每个标题、容器或控件下面附一段解释。清楚的名称和布局已经表达的含义，不再重复写成注脚；权限实现、数据同步机制、设计理念和程序内部逻辑进入设计/代码文档。BDS 展厅作为说明文档可以解释组件，展厅说明文字不能直接成为业务页面文案。

减少说明不等于删减数据。每条重要业务信息都要有可定位的位置、明确的标签、真实的值及必要的单位/时间/关联对象；用字段组、对齐列、状态和记录组织，不把多项事实拼成长段文字。列表摘要与详情全文的分工由逐页规格明确，不能把本应在列表直接判断的信息隐藏到详情中。

| 内容 | 处理规则 |
|---|---|
| 当前对象、准确版本、工厂、数量/单位、交期、QC 结果、需求方确认、当前阻塞等业务事实 | 按对应模块设计完整呈现；影响当前操作的事实在当前任务区直接可见 |
| “先进入工作区再选择任务”“工作域不改变账号权限”“本页用于跟进……”等重复解释 | 默认不占常驻正文；通过清晰入口、标题、导航和实际权限行为表达 |
| 必要的校验与阻塞 | 保留具体事实及可执行反馈，例如“尚未收到船样确认”；不写通用流程教学段落 |
| 不常用术语的必要帮助 | 确有理解障碍时提供按需帮助；不把所有被删除的说明重新塞进 tooltip |
| 长编号、合同要求、QC 结论和确认依据 | 设计换行或明确的全文入口，不能用截断、变小字或弱化墨色造成信息丢失 |

每个页面须有“业务字段 → 显示区域 → 显示层级 → 完整值如何查看”的对应表。文案精简后用此表检查信息完整性，不用屏幕字数判断是否完整。

### 2.3 操作编排提案：每个位置有确定的作用

以下是设计方对用户要求的展开，需在页面样板中实际验证，不能标作用户已逐项批准的布局。

| 区域 | 位置和用途 |
|---|---|
| 页面标题栏 | 左侧标识所在模块；右侧放页面级操作和既有全局通知。无当前表单依赖的新建类动作按现有 BDS 规则归此处 |
| 导航与当前上下文 | 返回、当前对象、任务切换分清层级；导航不伪装成提交按钮，当前上下文不伪装成可切换控件 |
| 搜索与筛选 | 放在数据区上方的固定工具区；搜索、状态、筛选等有稳定顺序，不混入流程推进按钮 |
| 当前步骤任务区 | 相关资料、输入和校验放在一起；依赖本区输入的保存/提交留在该区，按现有面板操作归属规则处理 |
| 表单/步骤操作尾部 | 固定按钮顺序与对齐；次操作在前，主要推进操作在右。返回导航不随意挤入提交组，同一操作不在页头与页尾重复堆叠 |
| 列表/表格记录 | 对象信息在信息列，同行操作在稳定的尾部操作列；不要因某条记录可用按钮数量不同就挤歪数据列 |
| 危险与低频操作 | 与常规推进操作分组；更多菜单只承载适合收纳的低频操作，不能把当前关键动作藏进去 |
| 居中 | 用于完整的入口选择、空态或聚焦任务构图等已指定场景；不临时把某一组业务按钮居中以填空 |

按钮规格须逐项写出：名称、所属对象/范围、位置槽位、顺序、样式等级、是否常驻、启用条件、反馈及结果。主操作数量按独立任务区判定；大批导航、筛选和业务动作不能全部采用同样的实心按钮。

## 3. 共用业务入口设计提案

开发与寻样、订单管理、QC 工作台都需要先选择面料或成衣。三处入口属于同一种导航任务，必须复用同一套视觉组件和状态语法：

- 面料与成衣是首要业务选择：每个选项都有清楚、醒目的图标和业务名称；说明仅在必要时加入。两个选项在尺寸、内边距、对齐、文字层级和交互反馈上完全一致。
- 桌面并排呈现，空间不足时自然改为单列；卡片整体可操作，焦点环、悬停和按下状态可辨，并保留键盘可达性。
- 选定业务域进入工作页后，当前业务只在紧凑上下文位置标识一次，不再放第二组面料/成衣大选择器、介绍区或入口卡。更换业务通过低权重的返回入口操作完成。样品/生产、列表/报告等真正的域内任务切换另按任务需要设计。
- 订单的历史类型查阅等次级入口不能与面料/成衣主入口争夺视觉重心。
- 复用这套入口语法不等于三处文案和数据相同；进入工作页后显示实际业务内容，不重复讲解模块用途。

### 共用入口组件提案

建议组件名：`BusinessDomainChooser`。三个模块共用此结构，不各自手写入口按钮或卡片。

| 位置 | 建议规格 |
|---|---|
| 页面标题 | 复用 `PageHeader`；主标题分别为「开发与寻样」「订单管理」「QC 工作台」；不在标题栏下另叠英文 overline |
| 入口说明 | 不强制额外增加「选择业务类型」标题或说明。模块标题和两张入口卡已足够表达选择时，不再重复解释；确有必要的说明在样板中单独评判 |
| 入口网格 | 两张等宽等高卡片；桌面两列、窄屏单列；列间距 16px，卡片内部间距按 16px 和 24px BDS spacing token 排布；两张卡片左边缘与本页其他主内容对齐 |
| 卡片表面 | 统一使用 `.bds-card.interactive`，内边距 24px；不再混用普通按钮、局部横线卡片或第三种容器 |
| 图标 | 每卡左上使用 48×48px 的 BDS accent-tint 图标底，图形 24×24px；面料统一用 Lucide `Layers`，成衣统一用 Lucide `Shirt`。全站三处映射一致 |
| 标题与说明 | 卡片标题 16px/300；如保留必要说明则用 14px/300；标题与图标区相隔 16px，说明与标题相隔 4px。卡片右侧放 16px 的前进箭头；整卡是唯一点击目标，不在卡内再放重复按钮或“进入工作区”文字 |
| 交互状态 | hover/pressed 复用 `.bds-card.interactive`；键盘 focus-visible 使用 `--focus-ring-strong`；不可用时采用共享 disabled 配方并说明原因，不靠变淡但仍可点 |
| 次级入口 | 订单的「查阅其他历史类型」放在主入口网格之后，使用文本型次级动作；QC 的驻地/业务线设置位于主选择之后的独立次级区，不与两张入口卡同级 |

| 页面 | 卡片标题 | 卡片说明 |
|---|---|---|
| 开发与寻样 | 面料开发与寻样 | 建立面料开发案、安排工厂试样并跟进版本 |
| 开发与寻样 | 成衣开发 | 建立成衣开发案、安排工厂打样并跟进版本 |
| 订单管理 | 面料订单 | 查看和推进面料订单及其条目履约 |
| 订单管理 | 成衣订单 | 查看和推进成衣订单及其工厂履约 |
| QC 工作台 | 面料 QC | 处理面料样品评审与生产检验 |
| QC 工作台 | 成衣 QC | 处理成衣样品评审与生产检验 |

上述说明文案是候选内容，不要求全部常驻显示；入口标题已经清楚时可直接省去说明。任务是否需要先锋样、船样、皮头样等仍按订单条目已确认的业务要求显示。

## 4. 编码阶段的边界

coding agent 按已定页面规格实现，不兼任产品视觉设计师。可以在既有 BDS 组件内完成布局；如果当前组件确实表达不了规格，先提交具体差异（目标、限制、受影响页面）并由设计方更新方案，再改实现。不得自行把入口降级成普通按钮、用新的容器替换共享配方、改变标题和间距体系，或把前端验收简化成“页面能打开”。

视觉统一不要求所有页面长成同一张模板。页面可以按任务密度选择工作台、列表或详情结构，但同一类元素要有稳定含义：标题栏、业务入口、内容容器、工具行、表格、表单和状态提示分别遵循各自的共享配方。

## 5. 必须分开的验收结果

实现交付时分别报告功能、交互、视觉三类结果；一项通过不能代替另外两项。

- **功能**：字段、权限、校验、状态流转和跨模块数据符合模块方案。
- **交互**：导航、按钮、表单、进度门禁、返回和恢复行为按方案工作。
- **视觉**：在实际应用里，以同一视口并排检查入口页和主要工作区；截图随交付保留。检查标题栏高度与基线、内容边距、分区层级、容器/分隔线用法、字体层级、间距节奏、控件尺寸、图标尺寸及状态反馈。不能只检查一张首屏；应覆盖该页面已实现的关键状态。

源代码检查、token 扫描和自动化测试可证明部分约束，不能单独证明页面整齐、层级清楚或具有设计质量。只有源码、测试而没有实际呈现证据时，结果写为“功能已实现，视觉待验”；产品负责人或独立评审者看过实际界面后，才记录视觉验收状态。不得把这份门槛或一张截图说成全站 UI 已验收。

## 6. 第一轮复核顺序

1. 先用上述规格统一开发、订单、QC 的面料/成衣业务入口。
2. 再按统一页面壳和标题栏，对照每个模块的主工作区，检查容器层级、间距、排版和主要操作位置。
3. 按“开发与寻样、订单管理、样品仓库、QC、出运与单据、财务”的业务连接顺序逐页复核；修完一个真实任务链，再进入下一个，不以单张卡片优化代替链路验收。

每一轮只登记已核对的页面与状态。没有渲染和操作证据的页面保持待验。

## 7. BDS HTML 本轮源码复核

复核目标为 `styles/bds/showcase.html`（设计系统展厅），并对照同目录 demo、现行 tokens/components/layout 和应用层规范。本节仅记录当前源文件能够证明的事实；未取得本轮渲染画面。

| 发现 | 当前源码证据 | 对本次要求的影响 |
|---|---|---|
| 已有较完整的基础元件，整页样板覆盖不足 | 展厅有配色、字体、按钮、表单、容器、表格及状态示例；`#page` 的完整组合主要是报价页，其他多为局部布局示意 | 不能据此判断入口、订单条目履约、QC 任务、样品库在切页时保持一致；需要同一体系下的多页业务样板 |

## 8. 验证要求：让用户看到一致性，而不是接受口头保证

先在独立设计样板中完成可评判结果，再决定软件本体的改造。样板至少覆盖：业务入口、列表/台账、对象详情、当前履约步骤、编辑表单/弹窗；并选开发、订单、QC 等真实业务内容套入相应样板，验证同类页面的对应关系。

每个样板须同时交付：

1. **无设计注脚的实际界面**：用真实业务密度填充，展示产品使用时看到的内容。尺寸标注、解释和评审意见在旁边的规格区，不掺入产品画面。
2. **几何对应表**：同视口、同主题下记录标题栏、正文起点、主容器边缘、字体角色、操作位置与间距；说明共享约束和必要变体。并排或叠加检查是否漂移，字体要已实际加载。
3. **信息完整性对应表**：每个必要业务事实可找到；精简文案后逐项核对，不以减少字段换取干净。
4. **操作对应表**：每个按钮、筛选、切换有确定位置、层级、范围和状态；当前下一步一目了然，未来步骤遵守已确认的渐进展示。
5. **内容与状态压力检查**：正常与长数据、多条目、多操作、空态、加载、失败/阻塞和窄宽度；不能只靠理想短文案的单张首屏成立。

用实际渲染结果判断构图、秩序和审美，用尺寸表检查一致，用业务字段/操作表检查无遗漏。三者同时成立，才说明这套设计可以指导编码。源文件修订、文档字数、组件数量和 token 检查结果均不能单独证明这一点。

### 9.3 本页设计提案：将空间交给订单内容

以下为设计方提出的具体编排，尚未以新样板验证，也不表示用户已批准每个尺寸。

| 层级 | 保留的内容和位置 | 去掉的内容/具体尺寸提案 |
|---|---|---|
| 既定标题栏 | 沿用已定外壳、标题与页面级操作位置；录入订单、导出台账、通知保持各自层级 | 去掉重复的 Order Desk；不为此次整改增加另一套标题栏 |
| 单行工具区 | 左侧一个低权重返回入口动作及一次当前业务标识“面料”，后接搜索、状态筛选；全部与表格左边缘对齐 | 删除独立“面料订单”介绍区、用途说明、“业务工作区”标签和再次二选一的分段器；当前业务只出现一次 |
| 工具控件 | 先采用现行 BDS 搜索标准宽度290px作为样板起点；状态选择160px；40px等高、12px控件间距；工具区与表格间16px | 搜索不得通过 flex:1 无限伸长，状态不再被压到单独的 w-28。窄窗口先让搜索缩至可用下限，再采用已设计的换行，不能把筛选挤坏；最终尺寸看样板实际效果后确定 |
| 列表 | 紧接工具区，占余下主要工作高度；保留必要业务列和逐条操作 | 不补统计卡、横幅、介绍容器或其他无业务信息的层次；列宽、排序、状态及操作依据正常数据明确设计 |
| 列表页脚 | 需要分页/加载更多时，在列表容器底边单独保留48px样板高度；计数在左，分页/加载动作在右；与列表滚动内容分开 | 页脚内不再留一大块无内容空间；零条记录且没有可分页内容时，不重复显示0/0和空分页区 |

在可用空间仍有剩余时，留白保持中性，不用继续拉长搜索、增加说明或放大选择器填满。空间利用率以用户能看到和操作多少有效业务内容衡量，不以每个区域都铺满为目标。

## 10. 用户确认的全站前端硬约束（2026-10-07）

`dev-ui-preview.html` 只是视觉参考样板，不是产品交付目标，也不要求在本体内推荐、嵌入或保留 Preview。以下规则进入 UI skill 的 E19–E21，coding agent 必须遵守：

1. **界面不放注释噪声**：不加设计说明、注脚、教程、权限机制解释或“本页用于……”等文字。必要业务字段、单位、状态、阻塞原因和操作信息必须完整保留；删的是解释性噪声，不是业务信息。
2. **顶部统一成一个共享页面骨架**：标题栏与搜索/筛选工具区作为同一套模块化布局，固定高度、边界和间距参考 Preview；页面只填标题、全局操作、搜索和筛选等槽位，不再各自拼接顶部层级、缩进和留白。
3. **组件统一、规范化**：同类组件的结构、视觉和交互规则在共享层定义；新页面消费共享组件，不复制局部实现。共享组件不足时先补共享层。
4. **列表底栏统一**：表格/列表底部采用 Preview 相同的信息结构，左侧显示准确对象统计，右侧分页，固定贴列表容器底部并与滚动内容分离；无结果时不显示无意义的 `0/0` 或空分页。

本轮已在浏览器实际打开 Preview 的成衣订单台账（样例数据）查看布局；未归档截图，也未对全站页面或状态完成视觉验收。该次查看只用于确认参考样式，不能替代产品本体截图验收。

### 9.4 由此补齐的全局约束

- **入口选择具有阶段性**：选择页负责醒目且清楚地选择业务；进入工作页后，导航和上下文缩成低权重、低占高的结构。入口的视觉权重不能一路复制到工作页。
- **每层必须增加新信息或必要操作**：重复标题、说明、标签、切换项不能因“这是通用组件”而默认保留。
- **控件按用途分配空间**：明确首选宽度、上限、收缩下限和溢出策略，禁止把 fill/flex:1 当作所有搜索框的默认设计答案。
- **列表边界完整设计**：标题、工具区、表头、滚动体、空态、页脚及外壳安全间距一起决定，不能只设计首屏上半部分。
- **共享规则也须接受审查**：共享组件、token 或历史“验收值”出现问题时修正其设计依据，不能以复用和扫描通过替代审美判断。
- **交付需要真实内容样板**：这张空态只足以拒绝当前画面；新的布局须同时验证零条、少量、多条、长字段、多状态/多操作及窄窗口，才能确认可推广。
