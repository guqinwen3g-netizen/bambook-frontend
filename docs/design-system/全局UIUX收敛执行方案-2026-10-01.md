# Bambook 全局 UI / UX 收敛执行方案

日期：2026-10-01。状态：仓库盘点已完成首轮，设计基准尚未重新验收，批量迁移尚未开始。

## 1. 本轮决策与范围

用户明确要求：先完整学习、归纳整个 UI / UX 设计体系，再逐页、逐容器、逐按钮、逐卡片、逐文字收敛。唯一设计改造豁免是 Dashboard / 全景看板。其他页面全部进入跟进、优化和修复范围。

这是一项持续的设计体系与产品交互整治，不再按“发现哪里文字大就改哪里”推进。统一的是角色、规则、组件和交互；不同任务仍应有不同的信息密度和页面结构。

- `39e29499` 售后索赔修复：保留已提交事实与技术验证记录；用户仍不满意，状态重新打开为 **待返修 / 未视觉验收**。不得晋升为标准样板。
- `6077e6ca` 全局样式整理：仅是历史提交，不代表所有涉及页面视觉合格。
- 本轮只读检查生产源码并建立方案/台账，不修改业务 UI、全局 token 或其他 Agent 的业务改动。
- 不以旧文档中的邮件、工具、模板、管理后台、开发工具豁免覆盖本次要求。非 Dashboard 可达 UI 均纳入。邮件/打印产物按各自介质约束审查，不强塞浏览器 CSS；对应生成器、编辑器、预览、按钮仍完整审查。
- 历史不可达代码单列“待确认 / 非运行面”，用可达性证据判定，不把未访问的页面标成完成，也不为审计恢复已退役移动产品。

### Dashboard 保护边界

Dashboard 本体不重新设计，不作为本次强制迁移对象。共享字体、token、按钮、全局 CSS、外壳改动可能间接改变它，因此每次共享变更必须做保护性对照。不能用“Dashboard 豁免”来免除回归检查，也不能借公共组件收敛顺带改变 Dashboard。确需隔离时在明确主题/组件边界内处理，不复制一整套设计系统。

### 售后索赔重新打开的问题

- 内容角色仍由页面局部字号/颜色堆出来；缩成小字并不等于视觉层级成立。
- 列表、详情、金额区、表单缺少明确的共享组合配方，容器用途区分不足。
- 执行已有处置时使用新增表单 `dispForm.kind` 判断仓库/工位要求（ClaimManager.tsx:102–104、184–203），应改成执行对象自己的契约。
- 案件切换缺少详情 loading、旧数据隔离和竞态保护；写入动作缺少各自 pending/防重复操作状态。
- 仓库、工位直接要求输入内部 ID，需复用实体选择模式并覆盖无数据/无权限状态。

后四项是交互/业务衔接风险。必须在受控测试数据中复现与修复，不把它们当成审美问题掩盖，也不在真实财务记录上试点。

## 3. 怎样学习与归纳 BDS

### 3.1 证据先于新规范

先收集：用户明确裁决、仍认可的视觉参考、原始 BDS/组件展示、生产运行截图及计算样式、现有共享实现。每条证据注明角色和置信度：规范依据 / 视觉参照 / 实现事实 / 历史方案 / 待验证假设。

现有实现不是天然正确；旧 showcase 不是自动通过的视觉目标；售后索赔和刚被用户指出的问题页面属于反例。外部设计研究仅补现有资料缺口，不引入新的品牌风格。没有准确矢量源时用 DOM 几何和计算样式作测量证据，不为排版审计重绘 SVG。

产出一张规则权威表：

`规则 ID → 内容角色/场景 → 当前决定 → 来源 → 适用范围 → 替代旧规则 → 实现位置 → 正例/反例 → 验收状态`

### 3.2 七层设计契约

1. **产品与任务**：用户到这里完成什么；主要对象是谁；首要动作是什么；信息是否重复，说明是否真的有用。
2. **页面骨架**：列表详情、数据表工作台、档案卡集合、流程详情、多段表单、消息工作区、分析报表。规定导航、分区、滚动、详情、操作位置与密度。
3. **内容层级**：身份、关键值、正文、字段标签、辅助说明、状态、异常、动作；给出按场景的组合而非 h 标签到字号的粗映射。禁止把所有文字统一缩为 12px。
4. **容器与材质**：页面面板、区块、列表行、数据卡、字段组、凹槽、浮层；明确何时不用盒子，嵌套层级、圆角与内距关系，以及材质/边界/对比。
5. **控件组件**：Button/IconButton、Field/Select/Date、StatusBadge、Metadata/KeyValue/Amount、Card/Section、表格/列表、Empty/Error/Loading、Dialog/Drawer/Preview。优先收敛现有组件，不新增平行框架。
6. **交互行为**：默认/悬停/按下/选中/聚焦/禁用/加载；选择对象归属、快速切换、请求失败、取消返回、草稿保留、重复提交、权限与业务门禁。
7. **可访问性与适配**：长中文、英文、混排、金额、日期、单位；键盘与焦点、可访问名称、文本对比、缩放、浅深主题。明确桌面最小 1080×760 的现行契约，不暗自恢复移动端。

### 3.3 用可见样例证明规范可用

建立生产同源的内部验收场：相同字体、CSS 级联、主题、原语、真实密度内容。每个组件族同时展示普通、长内容、空/错/禁用/加载态；每个模式展示主要任务和异常路径。

先完成规则冲突裁决及参考提案，再产出一屏对照供用户校准方向。用户已否定的版本不充当基线。常规实现与复验由执行方持续推进；仅视觉方向有实质分歧或业务含义需决定时集中提出具体选项。

## 4. 覆盖台账与验收单位

最终单位不是文件或首页，而是：

`入口 → 子视图 → 容器实例 → 共享组件/变体 → 内容角色 → 交互状态 → 证据 → 缺陷 → 修复提交 → 独立复验`

- 每个按钮登记角色：主操作、次操作、行内、图标、危险/确认、切换；具体实例仍检查语义、位置、权限和状态。
- 每个容器登记职责、父级、材质、内距、内容分组、滚动边界；不得一概套 Card。
- 每个文本区域登记角色、字级、字重、墨色、行高、对齐、截断与完整值获取方式。
- 共享组件修复可一次改善多个实例，但各页面仍检查内容、组合与状态，不能靠“用了组件”自动销号。
- 低风险重复实例可复用组件测试证据；每个实例的角色映射必须被覆盖。高风险表单/财务动作、特殊长内容与异常状态逐项验。

页面状态至少包括：正常、首次加载、局部加载、空数据、筛选无结果、失败可重试、只读/无权、长内容、选中/切换、新建/编辑、校验错误、提交中、成功/失败、关闭取消/草稿、弹窗/抽屉、浅深主题。

登录、注册、侧栏、页头、命令面板、通知/Toast、全局确认/输入弹窗、上传下载与预览、AI 附属面板单独登记。Dashboard 仅受共享改动保护性检查。

## 5. 长程批次与退出条件

不用一次大改覆盖整个系统，也不按未经验证的页数承诺日期。按依赖分阶段，每个阶段拆成可复验小批次。完成两个代表样板后，根据实测工时、缺陷密度和返修率给剩余范围估时。

| 波次 | 工作 | 交付物 | 退出条件 |
|---|---|---|---|
| W0 范围与保护 | 全入口/子页/全局面盘点；标记现役/不可达；工作区归属与 Dashboard 保护 | 页面/状态台账、基线快照、共享依赖表、未提交业务改动隔离清单 | 无漏入口；豁免仅 Dashboard；不能把未知当已通过 |
| W1 学习与裁决 | 生产证据、旧规范冲突、内容/容器/控件规则归纳 | 权威表、BDS 角色契约、正反例、争议/假设记录 | 每项核心规则有依据；展示与生产差异被解释；关键方向可核对 |
| W2 共享组件 | 在现有层级上补角色 API、密度/状态/slots；修守卫盲区 | 生产同源验收场、组件/变体台账、组件契约测试、位置级债务账本 | 正反样本能被守卫识别；视觉、键盘、异步状态通过；Dashboard 无意外变化 |
| W3 代表样板 | 售后索赔重做；开发详情；订单工作区；设置表单。每次仅推进 1–2 个相互独立表面 | 原图/目标/实图对照、模式配方、业务交互证据 | 独立审查通过；用户否定项已重新处理；未通过的模式不向全局扩散 |
| W4 订单履约 | 数字档案、样品、报价、生产、采购、库存、QC、货运、报关、单据、MES 可达面；联检开发和订单 | 各页子视图、表单、浮层、状态闭环 | 不只看首页；跨模块进入/返回/对象上下文正确 |
| W5 财务经营 | 财务/发票、定价、BOM、风险、报表、驾驶舱；索赔财务联检 | 金额/账务数据呈现、密集表格、操作门禁及分析页模式 | 金额和币种不误读；写操作受控验证；不把技术通过当视觉通过 |
| W6 客户协作平台 | 关系、CRM、供应商、季节、营销、邮箱、日历、AI、数据中心、工具、后台、人事；设置/登录/注册回归 | 页面子树完整迁移、所有公共面应用检查 | 输出介质约束有记录但产品 UI 不漏审；角色/权限/模式完整 |
| W7 收尾与防回退 | 全域复验、重复样式清理、遗留桥接退役、文档与验收场同步 | 最终覆盖账、剩余缺陷、基线版本和变更规则 | 所有在役非 Dashboard 表面有证据；无未解决严重问题；历史记录保留 |

W4–W6 内部按高使用频率 × 业务风险 × 共享收益排序，不机械按导航顺序。某域先发现严重错误可提前修，但遵守同一组件和状态契约。

## 6. 每批执行闭环与分工

1. 总控选定页面子树、依赖组件和状态范围，分配唯一写入所有者。
2. 只读审查者先看源证据与实际界面，写问题清单，再读实现方解释。
3. 组件负责人只改约定的共享层；页面负责人只改分配页面，不跨域覆盖他人工作。
4. 共享组件有依赖时先落共享提交，再迁移调用方，不让多个 Agent 同时改 token/CSS。
5. 保持字段、API、权限、业务状态含义；真正的 UX 状态错误单列契约和行为测试，不混进“纯视觉”改动。
6. 实现后检查真实截图、操作、长内容、加载/错误/权限态；修复者不能自己给审美结论盖章。
7. 独立复验发现不通过就追加返修记录；不抹掉上轮问题和用户否定记录。
8. 每批单独提交、说明测试环境对应 checkout/commit；台账更新问题、证据、验证结果和下一批。

并行上限建议：1 总控 + 1 共享组件线 + 1 页面线 + 1 独立审查线。不同页面可并行只读盘点；不要为了并行让多个执行者各造风格。当前共享工作区仍有其他业务开发，禁止 git add -A；提交逐文件/必要时逐 hunk 分离。

## 7. 四类验收，不混为一谈

| 验收 | 证明什么 | 不能证明什么 |
|---|---|---|
| 静态/构建 | 编译、组件归属、令牌合法、无新增逃逸 | 画面好看、信息易读 |
| 组件/交互测试 | 选择、焦点、禁用、请求竞态、取消/草稿、重复提交控制 | 所有真实页面都合格 |
| 浏览器视觉 | 同视口/主题/数据的层级、密度、留白、光学对齐、溢出、材质 | 单张截图证明全部状态和业务正确 |
| 方向认可/独立复验 | 风格方向得到认可，实际产物符合契约 | 一次认可永久免除未来回归 |

机器规则按具体位置登记，不用全局数量抵消；截图差异用于发现变化，不用像素分数代替审美。不得为了变绿放宽规则或删除有意义的交互测试；同样不得用错误实现的字符串断言固化错误。

收尾指标：入口覆盖、子视图覆盖、组件实例角色映射、必要状态覆盖分别计算。当前只有入口登记可统计；其他分母仍在补齐，不公布虚假的“已完成百分比”。
