5b. **token 类型混淆：客户 token 被内部守卫放行（commit `feb0112`，2026-09-15 18:5x 已修）**

    客户门户 token 与内部 token **共用同一 `JWT_SECRET`**（`customer/authService.ts` 明写）。
    两侧校验此前**不对称**：
    - 客户侧 `verifyToken` 校验 `kind === 'customer'` → 拒内部 token ✓
    - 内部侧 `extractActorFromRequest` **只 `jwt.verify` 验签、不验类型** → 接受客户 token ✗

    代码注释声称「内部路由因缺 roles/permissions 天然拒绝」——**该假设从未被测过**，实测不成立：

    | 守卫组合（两侧同密钥） | 客户 token |
    |---|---|
    | `requireAuth` 单独 | **200 放行**（actor 无 userId/roles/permissions） |
    | `requireRole(...)` | **500**（`payload.roles.some` 崩在 undefined） |
    | `requireAuth` + `requirePermission` | 403（此路径本身安全） |

    即：客户门户用户拿自己的 JWT 打内部接口，requireAuth 型路由放行、requireRole 型路由直接 500。

    **修复**：`extractActorFromRequest` 补对称类型校验（必须带非空 `userId`、且 `kind !== 'customer'`），
    fail-closed；`requireRole` 对缺失 `roles` 兜底为 `[]`（不再崩 500，退化为 403）。
    已确认全仓内部 token 均为 `{userId, roles}` 形态，不会误伤。

    **⚠️ 写这类测试的假绿陷阱**：`middleware.ts` 在**模块加载时**就固定了 `JWT_SECRET`，
    在测试文件里再改 `process.env.JWT_SECRET` 已经太晚（ESM import 提升），
    会导致两侧密钥不同、验签失败 → **全部 401 的假绿**（看着"很安全"，实则没测到）。
    必须显式用同一密钥签发两种 token。（第一版探针就踩了这个坑。）

      而守卫有 **30s 状态缓存** —— 首次请求已缓存 `blocked:false`，
      紧接着停用再打，命中缓存 → 仍是 200。
   → **教训：读到"安全机制失效"先怀疑自己的探针，把缓存/时序因素排除后再定性。**

6f. **待定夺：改密/重置密码后旧 token 不失效（需一次加字段迁移）**

   全仓无 `tokenVersion` / `passwordChangedAt` / `revokeAllSessions` 一类机制。
   token 自持 `roles/permissions`，TTL 7 天；`accountStatusGuard` 只查
   `status` 与 `deletedAt`。
   - **已覆盖**：停用 / 软删 / 离职交接 → 即时失效（6e 已实测）。
   - **未覆盖**：管理员重置密码、用户自助改密 → **旧 token 在剩余 TTL（最长 7 天）内继续有效**。
     场景：账号疑似泄露后改密，攻击者手上的旧 token 仍可访问。
   - **也未覆盖（同源）**：角色/权限下调后，旧 token 里的 `roles/permissions`
     在剩余 TTL 内继续生效（`requireRole` 直接读 `payload.roles`）。

   建议修法（**需你拍板，因为要动库结构**）：
   给 `UserAccount` 加可空字段 `passwordChangedAt`（纯新增列，迁移风险低），
   守卫比对 token 的 `iat` 早于该时间即 401；角色变更可复用同一机制
   （加 `permissionsUpdatedAt` 或直接按 `updatedAt` 判定）。
   在拍板前**不擅自加迁移**——生产建库走的是 `docs/生产部署-schema基线流程.md`。

6g. **贸易单据 PDF 可匿名下载：敏感子树拦截被三种写法绕过（2026-09-15 22:0x 已修）**

   `/api/uploads` 由 `express.static` **无鉴权**直读，原来用 5 条字面量挂载拦截：
   `app.use('/api/uploads/trade-documents', 404)` …
   注释写得很到位（"商业发票/箱单/提单等 PDF 含客户与价格数据，禁止无鉴权直读"），
   **但拦截本身是漏的**——`app.use` 按**原始 URL** 做前缀匹配，而 `express.static`
   会先**解码**、再把重复斜杠当单个处理，然后才落盘查找。视角不一致即产生绕过。

   **实测（本机真实文件）**：以下三种写法**全部返回 200**，匿名拿到
   **248,896 字节、`%PDF` 头的商业发票 PDF**（`TD_...-CO-2026-0001-v1.pdf`），
   同目录另有 PL 装箱单等共 8 份贸易单据、2 张报价图：
   - `/api/uploads//trade-documents/xxx.pdf`（重复斜杠）
   - `/api/uploads/trade%2Ddocuments/xxx.pdf`（编码连字符）
   - `/api/uploads/trade-documents%2Fxxx.pdf`（编码斜杠）

   **修复**：新增 `server/src/lib/uploadsGuard.ts`，站在**与 static 相同的视角**判定
   （先解码 → 折叠重复斜杠 → 取首段 → 小写比对；含 `..` 一律拒绝，合法 URL 不含 `..`）。
   `index.ts` 改为 `app.use('/api/uploads', createUploadsGuard())` 挂在 static 之前。

   **验证**：五种写法（含大小写变形）全部 404；`products/` 等公开资源仍可读，无回归；
   真机冒烟 6/6 绿、页面异常 0。回归测试 `uploadsGuard.test.ts` 11 例
   （**已证伪**：还原旧字面量写法，恰 3 条绕过用例转红、8 条对照保持绿——
   与真机观察完全吻合）。

   → **教训：凡是"某中间件按字面量前缀匹配"的拦截，都要问一句"下游是不是先解码/归一化"。
   两个组件视角不一致的地方，就是绕过生长的地方。**

6h. **system-assets 文件路由：公开面不受素材类型约束、且无根目录兜底（2026-09-15 22:3x 已收口）**

   这不是"现在就被打穿"，而是**顺序型隐患**——`GET /api/v1/system-assets/:id/file` 注册在
   统一鉴权守卫**之前**，既无注释说明、也不限 `kind`。代码形态与"忘了挂守卫"完全同形。

   **定性为「保留公开读」而非「补鉴权」的依据**（两处硬证据，不是推断）：
   - 顺序实证：`/file` 匿名 → **404**（走无守卫分支），`/` 匿名 → **401**（走守卫分支）——
     同一 router 内两种响应，证明前置是有意为之而非漏挂；
   - 前端 `utils/publicAssets.ts` 把该 URL 解析为公开素材，**登录页壁纸依赖登录前可加载**，
     一旦套鉴权，登录页直接取不到图。

   **收口内容**（`server/src/system-assets/route.ts`）：
   1. 写明"刻意前置"的原因与边界，避免下一个人误判成漏洞又改回去、改回去又炸登录页；
   2. 仅 `kind === 'wallpaper'` 走公开直读，其余类型 `next()` 落回守卫（匿名 401）；
   3. 落盘路径加 `uploadDir` 根目录约束，`filePath` 含 `../` 越界一律 404 并记 error 日志。

   **验证**：新增 3 例（非 wallpaper 匿名→401 / 逃逸路径→404 且不吐内容 / hidden 与软删→404），
   `route.test.ts` 合计 11 例全绿；**已证伪**：还原旧实现后，前 2 例立即转红——
   旧代码下匿名可读任意类型素材（`application/pdf` → 200）、并能吐出 `uploadDir` 之外的文件

   → **教训：本地库无 `systemAsset` 行 ⇒ 无实害，但不能据此判"没问题"。
   顺序型隐患不看当前数据，只看"未来新增的素材类型会不会被顺带公开"。**

6j. **`/api/fetch-url` SSRF：白名单只校初始 URL，可回读内网（2026-09-15 23:0x 已修）**

   原实现是「初始 URL 字符串黑名单」（`isBlockedInternalUrl` 内联在 `index.ts`），
   已挂 `sdkAuth` 登录门，但**两个绕过实测成立**：

   | 写法 | 修复前 |
   |---|---|
   | `http://127.0.0.1:9999/` | ✅ 被拦（对照） |
   | **`http://httpbin.org/redirect-to?url=http://127.0.0.1:9999/`** | **❌ 读到内网标记服务响应** |
   | `http://[::ffff:127.0.0.1]:8081/` | **❌ 未拦截，请求到达本机 8081** |

   根因：① `fetch` 默认跟随 3xx，黑名单只在**第一跳**生效；
   ② IPv4-mapped IPv6 既不在 hostname 黑名单、也不是四段点分十进制。
   （十进制 `2130706433` / 八进制 `0177.0.0.1` / 十六进制 `0x7f.0.0.1` 反而已被拦——
   WHATWG URL 会归一化成 `127.0.0.1`，这点原实现是幸运的。）

   **修复**：新增 `server/src/lib/ssrfGuard.ts`，收口三件事——
   a. 地址字面量判定（v4 私网/回环/链路本地/CGNAT；v6 回环/ULA/链路本地/
      `::ffff:` v4-mapped / `64:ff9b::` NAT64 / `2002::` 6to4）；
   b. **DNS 解析判定**（域名解析出的每个 A/AAAA 都过一遍，防域名指向内网）；
   c. **逐跳校验**：`safeFetch` 手动跟随重定向（最多 3 跳），**每一跳都重做 a+b**。
   被拦截抛 `SsrfBlockedError`，端点按**类型**分诊回 400（而非 500）。

   **验证**：`ssrfGuard.test.ts` 17 例全绿；**已证伪**——退回旧行为后恰 5 例转红
   （2 条重定向用例正是因去掉逐跳校验才红）。
   真机复测（重启后端后）：5 种绕过写法全部 400；`example.com` 直连 200、
   `httpbin.org/redirect/1` 200，**功能未误伤**。

   **踩坑两条**：
   - `const [g0,g1,g2,g5,g6,g7] = groups` 是**按位置**解构（取到下标 0..5），
     导致 v4-mapped 判定永远落空——必须显式下标。第一版就踩了。
   - 一度把 `198.18.0.0/15`（benchmark 段）纳入拦截，结果**全部公网域名被误拦**：
     本机 DNS 代理（fake-ip）把所有域名解析到该段。已移除该规则。

   → **教训：SSRF 防护的默认是"只校第一跳"，而 `fetch`/`axios` 的默认又是"自动跟随"。
   两个默认撞在一起，防护等于没有。凡代抓外部 URL 的端点，必须逐跳校验。**

6k. **客户门户：拼柜运单可能跨客户泄露（**待你拍板**，暂不改语义）**

   门户整体作用域**做得好且一致**：`/api/v2/customer` 每个查询都带
   `customerRelationId: relationId`，连 `/orders/:id`、`/invoices/:id` 也把作用域**写进 `where`**
   （而不是"先查出来再判断"，后者更容易漏）。单据 PDF 也做了状态门禁（Draft/Cancelled 不下发）。

   **唯一个口子在 CI/PL（运单维度单据）**：
   - `documentService.ts:110-114` 先用 `id` 直接取运单（不带作用域），
     再调 `shipmentBelongsToCustomer()` 补校验；该函数本身是**严的**
     （直接 `customerRelationId` 命中，或经 `shipmentOrderAllocation` 反查到本客户订单）；
   - 但判断用的是 `findFirst`（第 68 行）——**运单里只要有任一订单属于我就放行**；
   - 随后 `assembleDocumentSetData()` 第 222 行 `shipmentLine.findMany({ where: { shipmentId } })`
     **不带任何客户过滤**，渲染的是整张运单。

   ⇒ 拼柜（一票运单含多个客户订单）场景下，客户 A 的装箱单/发票里**可能带出客户 B 的订单行**。
   服装外贸拼柜常见，不是理论场景。

   **三个口径，请拍板**（我不擅自改业务语义）：
   1. **严格**：运单内若含非本客户订单 → 404（最安全，但可能误伤拼柜客户的正常查看）；
   2. **过滤**：只渲染本客户订单行（体验最好，需改渲染数据链路，改动面较大）；
   3. **维持现状 + 业务约定**：承诺"不把不同客户的订单拼进同一运单"（零改动，靠流程约束）。

   当前生产库为空、门户无数据 ⇒ **无实害**；但门户账号一开通就可能触发，属上线前应定口径项。

6l. **客户门户登录无任何防爆破（2026-09-15 已修）**

   主站 `/api/auth/login` 有 15 分钟/5 次的滑动窗口限流，**门户 `/api/v2/customer/auth/login`
   一处都没有**——而门户恰恰是**对外**入口，且按定义无法再加鉴权。
   叠加门户账号常用弱口令（如彩排用的 `Customer@123`），等于开放凭据填充。

   **修复**：复用现成的 `auth/loginRateLimiter`（与主站同口径：15 分钟窗口 / 5 次失败、
   按 `IP+邮箱` 双维建键、成功即清零），挂到门户登录；被封锁时直接 429 `RATE_LIMITED`
   **且不查库**。选项化注入，便于测试。

   **验证**：`customer/__tests__/route.test.ts` 新增 3 例（第 6 次起 429 / 换邮箱不受牵连 /
   成功后清零），12 例全绿；**已证伪两次**：
   ① 短路 `check` → 前 2 例转红；② 只去掉 `reset` → 第 3 例转红。
   （第 3 例在第 ① 种证伪下必然仍绿，因为 check 已被整体短路——所以补做了定向证伪。）

   **真机复测**（按 PID 强杀旧进程、确认新 pid 后）：连打 7 次不存在账号的错密码 →
   前 5 次 401 `INVALID_CREDENTIALS`，**第 6、7 次 429 `RATE_LIMITED`**；换一个邮箱 → 401
   （不受牵连）。与单测结论一致。

   **注意**：限流是**进程内内存**计数，多实例部署时每个实例独立计数（门槛按实例数放大）。
   当前单实例部署无影响；若将来横向扩容，应改为 Redis 计数。

6m. **SSE 通知全员广播：发给 A 的通知会送到所有在线用户浏览器（2026-09-15 已修）**

   `NotificationEvent` 里带着 `recipientIds`，但 `realtime.ts` 的 `publishNotificationEvent`
   **从未使用它**——直接 `for (const client of clients)` 全员广播。
   而 REST 侧 `/v1/notifications` 是**严格按 `actor.userId` 隔离**的
   （`requireUser` 中间件，注释即"列出当前用户通知"）。同一份数据两套口径。

   **后果**：任何在线用户都能实时收到发给别人的通知——含**标题、正文、订单号、跳转链接**。
   审批流场景尤其敏感（"PO-2026-0001 的付款申请等待你审批"会推给不相关的人）。
   前端 `NotificationCenter.tsx:264` 也**没有**按 recipientIds 过滤，收到即入未读徽章。

   **修复**：`addRealtimeClient(res, userId)` 记录连接归属；通知只推给
   `recipientIds` 命中的在线连接；无 userId 的连接（纯 API-Key）收不到通知
   （与 REST 侧要求一致）；`recipientIds` 为空视为调用方漏传，**丢弃并告警**
   （fail-closed——宁可丢一条实时提醒，也不能把 A 的通知送到 B 的浏览器）。
   `data-change` 事件仍全员广播（只含 entity/action/ids，是设计意图）。

   **验证**：新增 `src/__tests__/realtime.test.ts` 7 例；**已证伪**——退回全员广播后
   恰 4 条投递用例转红、3 条"数据变更仍广播"对照保持绿。
   真机冒烟（按 PID 强杀旧进程、核对新 pid 后）：`/api/v1/events` 未鉴权 → 401；
   带 API-Key 连接 → 正常收到 `event: ready`（流本身未被改坏，无 userId 连接正常建立）。

   → **教训：接口上"带着 recipientIds 字段"和"真的用它过滤"是两回事。
   凡是"看起来有作用域"的数据结构，都要追到**消费端**确认它到底有没有被用上。**

6n. **知识库上传无类型白名单：任意类型可落盘（2026-09-15 已补，低危加固）**

   全仓 8 处 multer 配置里，**7 处都有 `fileFilter`**（印章图 `ALLOWED_SEAL_MIME`、
   产品图、技术包、QC 报告、报价图、壁纸、数据迁移），唯独 `ai/knowledgeDocumentsRoute.ts`
   **没有**——任意类型、最大 50MB 都能传上来（`resolveDocType` 只是给文件打标签，不做限制）。

   **现状缓解**（所以是加固项、不是可直接利用的漏洞）：
   - 落盘目录 `knowledge-documents` 已在 `uploadsGuard` 的敏感子树里，匿名静态读取被拦；
   - 下载走 `res.download` → `Content-Disposition: attachment`，浏览器不渲染；
   - 上传需 `knowledge:write` 权限。

   **修复**：补 `knowledgeDocumentFileFilter` 白名单（文档/图片/归档，约 35 种扩展名），
   拒绝 html/htm/svg/js/exe/sh/php 等脚本与可执行类型；双扩展名以**最后一个**为准
   （`合同.pdf.html` 拒、`合同.html.pdf` 收）。multer 错误明确成 **400**
   （`INVALID_FILE_TYPE` / `FILE_TOO_LARGE`），不再被全局处理成 500。

   **验证**：`ai/__tests__/knowledgeUploadType.test.ts` 8 例；**证伪两次**——
   ① 让过滤器一律放行 → 5 条拒绝类用例转红；② 摘掉 `fileFilter:` 那行 → 接线守卫用例转红
   （防后人删掉这行而测试仍绿）。

   → **教训：一处"没有白名单"往往是**遗漏**而不是设计——判断方法是看同类配置怎么做。
   本路由是 8 处里的唯一例外，那就是 bug。

## 五、勿再踩（本轮新增，全量见 memory）

1. **TokenPayload 只有 `userId`**——读 `actor.id` 即 bug（管线 500 根因，全仓已清 5 处）。
2. **API 测试全绿 ≠ UI 可用**：mock 传对字段就绿，真人登录才炸。每条主链至少一次真浏览器走查。
3. ts-node 重启旧进程可能不死继续服务（日志新、响应旧）——**重启后必须核对监听 pid + 实际响应**，不能信日志。
   **本轮又踩了一次**：`pkill -f "ts-node src/index.ts"` **匹配不到**（实际进程名是 `node`），
   旧 pid 继续占着 8081，新起的进程抢不到端口静默退出，于是"日志看着起来了、响应还是旧代码"——
   表现为刚修好的限流在真机上不生效，差点误判成修复无效。
   可靠做法：`lsof -nP -iTCP:8081 -sTCP:LISTEN` 取 pid → `kill -9 <pid>` → 等到端口真正释放

11. **错误分类靠类型不靠文案**：`handleError` 按错误消息字符串匹配判 400/404/500，

20. **SSRF 防护的默认是"只校第一跳"，HTTP 客户端的默认是"自动跟随重定向"——两个默认撞在一起，
    防护等于没有**（6j：`/api/fetch-url` 白名单齐全，仍被外网 302 打到内网）。
    凡代抓外部 URL 的端点，必须 `redirect:'manual'` + 逐跳重校（并限跳数）。
21. **数组解构是按位置，不是按下标名**：写 `const [g0,g1,g2,g5,g6,g7] = arr` 拿到的是
    下标 0..5，不是 0,1,2,5,6,7。6j 第一版因此让 IPv4-mapped IPv6 判定永远落空，
    **而单元测试因为"恰好没覆盖到"而全绿**——这类静默失效只能靠"先证伪"暴露出来。
22. **加严 IP 黑名单前先确认本机 DNS 行为**：本机 DNS 代理（fake-ip 模式）会把所有域名
    解析到 `198.18.0.x`，一度把 `198.18.0.0/15` 纳入拦截后**全部公网域名 400**。
    改判定规则后必须补一条"公网仍放行"的真机对照。
