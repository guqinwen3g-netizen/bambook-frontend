## 二、★★ 本批的实质判断：**形状相同 ≠ 文案相同**（D52）

这四处**形状完全一样**（``fail(CODE, `固定文案: ${原文}`)``），很容易"套一个模板清掉"。**不能**。
因为**每个 `catch` 的覆盖面不同**，而"能不能承诺写入状态"完全由覆盖面决定：

| 站点 | `try` 内的写路径 | 能不能承诺 |
|---|---|---|
| `qcChainService.ts:553` | 唯一写 = `$transaction`（`:498`），之后只有 `logger.info` + `return` | ✅ 可以承诺「本次未确认任何改动」 |
| `qcChainService.ts:381` | `$transaction`（`:302`）**之后还有** `getGarmentSampleGate` 读（`:377`） | ❌ **不许承诺** —— 报告可能已落库，只是门禁结论没取到 |
| `migration/dataMigrationService.ts:122` | **根本没有写入**（纯解析，无 DB、无事务） | ❌ 不许承诺；但**必须保留** `.xlsx` / `.csv` 格式指引 |
| `garmentDevelopmentService.ts:216` | 唯一写 = `$transaction`（`:112`），之后只是拼返回对象 | ✅ 可以承诺 |

⇒ **规矩**：B39 的文案**逐处按该 catch 的实际覆盖面**判断，**不许按"同型"统一处理**。

### ★ 我在本批自己犯了一次，并当场更正

第一版我用**正则**推 `try` 边界（取"站点之前最后一个 `try {`"），结果把 `:381` 判成了
**内层通知用的 `try`（`:351`）**，差点得出"事务之后没有别的代码"的错误结论。
**改法**：读原文（`:301` 才是外层 `try`）。
⇒ 教训与 §9 历次同源：**正则推断控制流不可靠**；判"catch 覆盖到哪"必须**读原文**，或至少用正则**定位候选**再人读确认。

### ★ 一条判据例外：`零拉丁词` 是启发式，不是法条

执行用例里我用「文案不得含 ≥3 字母的拉丁词」当"原文上屏"的指纹。`migration` 那处的正确文案**必须**含
`.xlsx` / `.csv`（格式指引是业务信息）⇒ **显式 allowlist**，而不是为了过断言把格式名删掉
（那会把"清泄漏"做成"降可用性"）。这条已写进 **D52**。

## 五、自评

- **代价**：4 处文案花了 3 个文件的侦察 + 3 份测试（其中 1 份要单开文件绕命名空间导入）。
  贵的部分**不是文案**，是**每处都要读控制流确认 catch 覆盖面** —— 而这正是 D52 要固化的东西。
- **收获**：如果按"同型统一模板"清，`qcChainService.ts:381` 那处会写出「本次未确认任何改动」，
  而**报告其实可能已经落库** ⇒ 业务员按这句话去重做，会得到 409「该轮报告已存在」——
  **一句假结论换一次误操作**。
- 一句判断（供 Kevin 复核时质疑）：**B39 的 54 处不能按"处数"排期**。
  每处的真实成本 = 读控制流（判断能不能承诺）+ 补 logger + 写中文 + 补执行覆盖，
  而**其中"读控制流"这一步无法用正则替代**（本批我自己就被正则骗了一次）。
