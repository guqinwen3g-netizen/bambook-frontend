### 2. ★ 发现并修掉「第一刀没修到钱」（本批最重要）

**上批只改了报出来的字段，没改钱。**

- `computeTaxRefundFigures` 的 `exportAmountFob` 确实剥离了，但 `refundableVat` 仍在按行
  **`totalAmount`（申报毛额）**累加 → **退税额照旧虚高**，`refundableRate` 还会凑出 13.47%
  这种不存在的「退税率」。上批的接线测试只断言 FOB 字段，全绿 —— **字段对了、变量名对了、钱没对**。
- 修法：行金额按 `k = FOB / 毛额` 缩到 FOB 口径再乘汇率与退税率（= 运保费按行金额占比分摊；
  报关单上运保费只有整单一栏，没有按行明细）。单行时就是精确相减；多行不同退税率也不会把运保费全砸到某一行。
- 实测（真库演练，100000 CIF / 运费 3000 / 保费 500 / 汇率 7.2 / 退税率 13%）：
  | | 修复前 | 修复后 |
  |---|---|---|
  | FOB | 100000（毛额冒充） | 96500 |
  | 退税额 | **93600（虚高）** | **90324** |
  | 退税率 | 13.4715%（凑出来的） | 13% |
- 新增 3 条钉住「钱」的测试（含多行不同退税率的分摊），证伪：去掉 `stripRatio` → 2 条立刻转红。

用户会卡在反复试。改为独立报缺码 `fob_not_positive`（`核对申报总额与运保费是否匹配`）。

## 二、口径（接手人勿改）

**剥离规则**（真源 = `server/src/finance/receiptFobReconciliationService.ts:83-90`，退税侧 `stripToFob` 对齐）：

| 成交方式 | 处理 |
|---|---|
| FOB / FCA / EXW | 不剥（申报额即 FOB） |
| CFR / CPT | 剥运费（缺 → 不给数） |
| CIF / CIP | 剥运费 + 保费（缺任一 → 不给数） |
| DDP / DAP / DPU | 不猜 → `trade_terms_unsupported`，不给数 |
| 未填成交方式 | 按不剥处理（保守；与 T7-3 一致） |
| 剥离后 ≤ 0 | 不给数 + `fob_not_positive`（数据异常） |

**报缺码全集**（8 个）：`no_lines` / `fx_rate` / `hs_rebate_rate` / `line_total` /
`freight_missing` / `insurance_missing` / `trade_terms_unsupported` / `fob_not_positive`

**钱的口径**：`refundableVat = Σ(行金额 × k × 汇率 × 退税率/100)`，`k = FOB / 毛额`；
`k` 取不到（毛额 ≤ 0）→ 不给数。

**⚠️ 三处副本**：术语分组在 T7-3 真源 / 退税侧 / 前端 `CustomsManager.tradeTermsNeedStrip` 各一份，
**改一处必须改三处**（`components/customsFobStrip.test.ts` 已把这条注释变成会失败的门禁）。
