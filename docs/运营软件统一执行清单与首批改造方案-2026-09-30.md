## 1. 本次审核的决定

建议批准一个有边界的开发批次：面料与成衣均完成“开发明确结束—费用待齐—整案核对—收费/减免决定—财务接手”的连续操作。同时产出驾驶舱页面方案，不在本批重建地球页或全部工作台。

本批通过不代表整套软件完成。未满足全局验收、未经用户批准，不承接真实生产业务。原持续目标中的工厂领退料/逐工序耗用主线不恢复；不以旧目标自动继续。

依据：本会话最新明确决定及《完整运营目标与现状核对-2026-09-30.md》。历史设计沿用；冲突按本次明确纠正登记，不无声覆盖原文。现有代码、数据库和界面证据决定实现状态，历史“已完成”标签不作当前通过证明。

## 2. 全局执行清单

优先级：P0为可能造成错账错货、越权、数据丢失或核心操作阻断；P1为跨岗位连续操作；P2为在前两者成立后的体验完善。发现P0不代表立即越过当前授权开工，应在审核批次内先处理相关问题。

| 工作包 | 保留与复用 | 已有证据/待核查 | 建议安排 |
|---|---|---|---|

| 库存物流单证 | 货权/位置/数量、直发、分配关系、CI及装箱单 | 同买家跨单组运、余料、修订版本及实际动作待核验 | 与履约及财务联验 |
| 业务财务及经营 | 收付核销、正式账套衔接、成本阶段区分 | 人工核销确认、样品减免/抵扣、四类售后、服务成本归集、报表口径 | 分批接通；不自建完整总账税务 |
| 全局交互 | 原页面及权限结构 | 就地建档、统一查找、跨页位置保留、批量检查、任务转交、并行状态、附件版本 | 随每个场景交付，不另做空壳平台 |

## 3. 首批交付结果

### 员工操作

1. 开发过程中，登记每轮打样、寄送、测试等已知实际费用，挂到对应开发案及样品来源。可记录尚未收到的账单事项，未知金额不写零。
2. 业务员明确暂停/恢复或结束开发。结束记录结果、原因和未完事项安排；成功、失败、客户放弃均保留费用处理责任。样品确认不自动等于整案结束。
3. 开发详情显示已登记费用、待到费用、核对结果及收费/财务进度。开发可结束而费用待齐。
4. 费用到齐后明确核对整案完整性；确认绑定当时费用明细。补记/更正导致未生效的核对须重新进行。
5. 业务员逐案提出综合收费金额或减免，留依据与决定人，适用现有授权。客户曾经免收不自动覆盖新案，成本不因免收减少。
6. 财务收到对应工作，打开即可看到来源、核对结果、收费决定；确认符合条件后生成应收草稿，沿现有签发、收款、核销路径处理。免收清楚显示无应收，不虚构发票或付款。
7. 未确认收费不算客户欠款，未知成本不算零，开发结束不算财务结清。

### 页面方案

- 开发详情原“登记费用”保留；增补同一详情内的费用区，不新开平行费用模块。
- 费用区顶部同时展示开发状态、费用处理状态；金额按币种分别汇总，不裸加美元与人民币。已登记小计与最终核对金额区分。
- 明细分“已登记”“待到/待核对”，可追到样品/批次/凭据；补账单由原事项进入并关联新增费用，避免双计。
- 结案弹层展示实际未完事项和处置安排，保留已有完成校验；不额外制造所有事项必须完成的阻断。
- 财务继续使用收费事项/场景入口，但共享同一收费资格及明细来源，不能通过另一入口绕过核齐/收费确认。
- 只把任务放到既有且可验证的待办入口；如当前机制不具备持久任务能力，先提交最小任务契约，不用通知或toast冒充交接完成。

## 4. 实现边界与拟定契约

以下是实施前需核定的技术契约，不要求用户选择表名/API名，不预先建立新平台。

| 业务动作 | 必须表达的信息 | 必须满足的约束 |
|---|---|---|
| 结束开发 | 来源案、结果/原因、操作者、未完事项安排、预期版本 | 原状态及权限校验；失败不半结案；不丢原样品确认依据 |
| 登记待到费用 | 业务来源、费用项目、跟进人、预计反馈时间、状态 | 可无金额；不得伪装已发生零金额记录 |
| 补齐账单 | 待到事项、成本记录、金额/币种、日期、凭据 | 稳定请求键；重试不重复成本；来源一致 |
| 核齐费用 | 全部费用范围、明细版本、未完事项、核对人/时间 | 后端检查待到项；没有项不自动核齐；数据失败不按空集合继续 |
| 确认收费 | 本案、收费额/币种、减免及依据、决定人、核对版本 | 成本和收费分开；授权明确；旧版本不能批准新金额 |
| 财务接手 | 收费决定、来源范围、责任人、处理状态、目标记录 | 可续办；通知失败可补送；重复操作不多建任务/应收 |

现有CostRecord是实际金额事实，保留；待到事项不强塞零金额。BillingItem可沿用收费决定语义，但当前只关联主成本记录的方式是否足以表达整案所有费用需核查，不能只占用一条就声称整案防重完成。InvoiceLine、来源唯一键和已有审计复用；必要调整先说明兼容和回退方式。

收费已生效后补记费用保留原收费/发票事实，走明确调整；本批不得静默自动加收。业务员减免权限沿既有授权核对，不能擅自默认无限额或一律领导审批。只有实际制度冲突才提问。

## 5. 实施前必须消除的技术不确定项

- 查明现有任务、通知、派生待办和权限能力，形成一个可承担责任及续办的交接方案；不能仅凭schema未见Task就宣布必须新建任务系统。
- 检查所有开发阶段更新入口、样品/开发开票入口及Agent通道是否执行同一约束，避免仅修一个按钮。
- 检查整案费用汇总分页：现候选函数默认100行、最多300行，最终汇总和核齐不能只针对当前页。
- 来源查询错误当前部分路径catch为空数组；最终核齐必须区分“确无记录”和“未成功加载”。
- 核对已确认成本/收费记录的历史引用与反向变更；不批量重写旧数据，不擅自删除本轮之前改动。
- 暂停开发、结束原因、权限和凭据如已有承载先复用，字段/API草案及数据迁移清单在代码改动前落盘。

这些是本批准备工作，不转化成要求用户答技术选择题。发现需要扩大业务范围时先回报，不自行扩成MES或全局重构。

## 6. 驾驶舱并行设计交付

保留地球页。驾驶舱作为登录工作入口，兼岗汇总授权任务并可切角色；管理者区分本人待办与团队需介入事项；等待反馈独立分区，到期提醒；按期限/业务影响排序且理由可见。

提供页面布局、任务卡信息、简单侧栏处理/复杂详情跳转、返回上下文、空态/加载失败/权限状态，以及整页和局部滚动方案。先复现已反馈滚动问题，查明主容器及固定高度嵌套；不以源码类名推测代替实测。首批费用待办成为真实任务样例，不能靠虚构卡片宣称驾驶舱可用。

## 7. 首批验证表（原验收要求；当前证据见下方实施状态）

| 场景 | 预期证据 |
|---|---|
| 面料与成衣各两轮样品，快递账单待到，开发完成 | 正确结束开发，费用仍待齐，财务无法提前生成本案综合应收 |
| 补到账单、核齐、部分减免 | 成本保持完整，收费独立正确，财务拿到同一来源及金额 |
| 客户放弃并免收 | 结束原因保留，费用完整，显示无应收而非虚假已收 |
| 长期等待后恢复 | 原样品、费用、责任和记录保留，无自动收费 |
| 空金额、明确零金额、美元/人民币并存 | 空不能被当0；明确零可按规则记录；币种分别核对 |
| 重复补记、结案、确认、财务建草稿 | 不重复成本/任务/应收；失败可恢复；必要真实并发验证 |
| 核齐后变更费用、旧页面提交 | 旧确认不能套用变更后内容，不覆盖已生效事实 |
| 越权、跨订单/客户来源、其他开票入口 | 服务端拒绝，不靠隐藏按钮；正常授权可办完 |
| 费用超过单页、来源加载失败 | 全量汇总正确，错误显性阻止最终核齐，不假装齐备 |
| 同组数据前端至数据库再到财务 | 开发详情、核对任务、收费决定、应收和核销可追溯；退出后可续办 |

本批由开发在授权本地测试环境完成技术与操作验证，不要求员工承担找基础缺陷工作。全过程无生产发布或对外发送，不宣称真实生产试用完成。

## 8. 审核后推进顺序

1. 固定当前改动清单与检查点，完成上文技术契约和已有能力复用检查。
2. 后端事实/状态/权限/幂等与开发详情操作一起补齐，面料成衣并行。
3. 接入费用核对任务与财务同源收费路径，验证跨岗位连续操作。
4. 交付驾驶舱页面方案及可复现的交互问题清单。
5. 对照验证表交付证据、遗留项与下一批建议。未通过的修复后重验受影响上下游，不以测试数量宣告系统完工。

历史审核条件：本批已获用户批准开工；该批准不代表软件可以上线，也不恢复工厂 MES 旧路线。
