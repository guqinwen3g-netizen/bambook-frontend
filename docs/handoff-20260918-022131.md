### 3.2 ★★ 改单只写主档、明细行零同步（**出错账** ✗）

```
客户把 1500 件砍到 1200 件，改单审批通过后：
  主档 quantity    = 1200   ← 改了
  明细行 Σquantity = 1500   ← 没动
  金额             = 11325  ← 仍按 1500 件算
⇒ 客户要 1200 件，我们按 1500 件收钱。不报错。
```

根因：`ORDER_FIELD_MAP` 只映射 Order 单列，`orderLine` 全程 **0 处**写入。

## 六、本会话踩到的坑（高价值）

### 6.1 ★★ 两次差点 cry wolf（都排除了，记录以免重犯）

| 疑似 | 真查结果 |
|---|---|
| `ORDER_FIELD_MAP.unitPrice → quoteAmount` 看着像「单价写进金额列」 | **不是 bug** ✓ —— `afterDelta.unitPrice` 里装的是**总金额**（`case 'price'` 的 `afterAmount`），映射正确，只是 key 名误导 |
| `FinanceManager.tsx:1614` 用黑名单 `status ∉ {Paid,Cancelled,Draft}` 而非真源白名单 | **不是 bug** ✓ —— 现有 5 个枚举值下**恰好等价**（脆弱但没错） |

> 判据还是那句老话：**先问「如果这是操作者有意为之，这笔数对不对？」**

### 6.2 技术坑

- **★ 守卫正则第一版是个空集**：写成 `contractAmount\s*\?\?\s*quoteAmount`，
  匹配不到真实写法 `num(o.contractAmount) ?? num(o.quoteAmount)` ⇒ **恒绿永不触发**。
  放宽成 `contractAmount[^;\n]{0,30}\?\?[^;\n]{0,30}quoteAmount` 后
  **立刻抓出第 6 个漏网消费点**（`dashboardService` 收入口径）。
  ⇒ **守卫写完必须构造能踩红它的输入跑一次**（老教训，再次应验）。
- **★ 走查脚本自己也会造第二套口径**：初版脚本用 `quoteAmount` 代表「前端取值」
  ⇒ 前端收编后脚本**假红**。改成**直接 import 生产同一份真源**，脚本不带第二套口径。
- **★ 增强逻辑不能把主流程搞挂**：联动第一版没 try/catch，
  mock 环境 `tx` 无 `orderLine` ⇒ **整个改单事务被打失败**（3 个测试红）。
  已改为失败降级为「只写主档」+ error 告警。
- **单价精度 vs 总额精确不可兼得**：`OrderLine.unitPrice` 是 `Decimal(18,4)`，
  反算单价存盘被截到 4 位 ⇒ `Σ(qty×存盘单价)` 与 `ΣnetValue` 有 ~0.03/行残差。
  **选总额精确优先**（开票收款依据），残差用显式容差承认，不掩盖。
- **`launchctl stop` 在沙箱里 `Not privileged`**，停不掉 8081（只能 `kickstart -k` 重启）。
- **后端重启后要等 ~10-15 秒**（ts-node 无 watch，启动慢），探测别只 sleep 6。
