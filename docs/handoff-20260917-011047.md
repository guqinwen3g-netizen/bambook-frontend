## 一、本批在做什么：① CIF 退税未剥离运费保费（最高危）

**问题**（L2 变异验收查出的 1 号高危）：
`server/src/customs/taxRefundCalcService.ts` 把报关单申报毛额**直接当 FOB** 用于算退税
（变量名还叫 `exportAmountFob`，实为 CIF 口径）→ **CIF/CFR 单退税额系统性虚高，且不报错**。

**Kevin 拍板的口径（两个关键决定）**：
1. **运保费登记在报关单**（不复用运单的实际费用）—— 税务认报关单上填的数
2. **剥不出来就不给数 + 明确提示**（fail-closed），绝不拿含运保费的金额冒充 FOB

## 三、已实现的口径（接手人勿改）

**剥离规则**（复用 T7-3 既有口径，**不另立一套**）：
`server/src/finance/receiptFobReconciliationService.ts:83-90` 是真源，
退税侧 `stripToFob` 与之对齐：

| 成交方式 | 处理 |
|---|---|
| FOB / FCA / EXW | 不剥（申报额即 FOB） |
| CFR / CPT | 剥运费（缺 → 不给数） |
| CIF / CIP | 剥运费 + 保费（缺任一 → 不给数） |
| DDP / DAP / DPU | 不猜 → `trade_terms_unsupported`，不给数 |
| **未填成交方式** | **按不剥处理**（保守；与 T7-3 一致） |
| 剥离后 ≤ 0 | 不给数（数据异常） |

**报缺码**：`freight_missing` / `insurance_missing` / `trade_terms_unsupported`
（新增到 `TaxRefundGapCode`，UI 会显示「去补什么」）

**前端副本**：`components/CustomsManager.tsx` 的 `tradeTermsNeedStrip` 是**副本**，
改术语分组必须**同时改后端**（否则「界面说必填、后端不剥」）。

## 四、本轮踩的坑（接上批 21 条，共 23 条）

22. **migration 链是坏的，不能跑 `prisma migrate dev`**：
    `20260523033000_add_fabric_profile_moq_fields` 在 shadow db 上失败（FabricProfile 表不存在）
    → P3006。本仓做法是**手写幂等 SQL migration**（见 `20260916200000_add_inventory_ownership`
    的写法：`ADD COLUMN IF NOT EXISTS`）+ **直接 psql 执行** + `prisma generate`。
23. **psql 不认 `?schema=public`**（invalid URI query parameter）→ 连接串要先剥查询串：
    `CLEAN="${DATABASE_URL%%\?*}"`。
    （另外：`.env` 用 `eval $(grep ^DATABASE_URL .env)` 解析最稳；别用 `tr -d 0x22`，那是错的。）
