## 三、如何自清（以及"什么不算自清"）

1. **整库重来**：`npx tsx scripts/seed-company-sim.ts --reset`（先清后播）。★ 代价要写清：这会**清掉现库那份 47,371 行的演示集**，走查环境里所有人手填的东西一起没 —— 所以它在"交付前最后一次铺库"才用，不作为日常清理。
2. **清演练残留 ≠ 清演示数据**：`scripts/clean-drill-residue.mjs`（默认 dry-run，`--apply` 才真删）与 `scripts/audit-drill-residue.mjs`（只报告）针对的是 `TEST-`/`TEST_`/`DRILL`/`E2E-` 那一族；`SIM-` 是**常驻演示集**，两个脚本同一立场：**不与残留相加、也不顺手删**。
   ★ 残留侧现在挂在 §12.1 第 22/23/24/25/26/39 条等使用方拍（见 §9 B239）。
3. **谁写进去的谁负责按精确 id 撤**：本条就是本文件的 §四 在做的事。

## 五、这份说明还没覆盖什么（首版自限）

1. **§3 知识库形态矩阵 → 逐格对照**：哪些形态（FCL / 多收 / CPT / 混合结算 …）由 seed 覆盖、哪几格只能靠演练件造，**还没做这张对照表**（G2 的 42 格证据普查做过，但没有和 seed 的剧情格一一挂钩）。
2. ~~**复现顺序的验证**~~ ⇒ **v3.162 已跑通并留证**（见 §六）：`db push` 建空库 → `seed:base` → `seed-company-sim` → 三条联动回填，全在**克隆库**上执行，现库一个字没动。★ 收回的只是"没跑过"这句；**逐字段/恒等式级的复现**仍然没做（§六第 3 格写清了量到哪一层）。
3. **数据量与时间的对应**：seed 用 W1–W13 相对周，铺库时按当天日期落 ⇒ 隔 6 周再看，"进行中/待办"会漂出窗口（★ 本批 QC 空页就是这个机制的第一次实锤）。**没有"按走查日期重新对齐窗口"的口径**，要么改 seed 生成相对日期，要么走查前重铺 —— 这条要请使用方拍。
4. 各域子生成器（`orders.ts` / `fabric-orders.ts` / 采购链 / 报关链）**字段级**的形态说明：只写了规模，没写"每格值从哪来、恒等式怎么保证"。
5. **现库演示集每天在涨、涨的部分没全部归因**：同日两次量同一栏 47,371 → 50,826（+3,455）。能确认的只有一条通路（nightly 简报给 SIM 账号发通知，实测每天约 +270 条）；**其余成因未查**，所以"演示数据集是一张静态快照"这句话**不成立**。⇒ 走查件的"数据基线"只能按日期记，不能按张数记。

## 六、从零铺出走查环境：v3.162 在克隆库上跑通并留证

★ **为什么要单独做这一格**：§一那两条命令以前是**照脚本注释转述**的。部署时如果这条路跑不通，"可一键部署的包"就是一句空话；如果跑通了但铺出来的东西和现在用的库不一样，① 的走查环境也不可复现。

1. **跑法（命令按顺序，全程只在克隆库上）**：`createdb -O bambook panda_hub_seed_0927` ⇒ `npx prisma db push --skip-generate`（建出 **225 张表**）⇒ `npm run seed:base`（六段全 exit 0）⇒ `npx tsx scripts/seed-company-sim.ts`（exit 0，脚本自己打出 `✅ 二期联动抽链核对全部通过` 并附三条联动回填命令）⇒ 三条回填逐条 exit 0（`全库 active EntityLinks: 360` → `Total active EntityLinks: 648`、`受影响产品: 0`）。★ 每一步都先 `select current_database()` 断言目标，再动手。
2. **对撞（演示集逐张比）**：统一一把尺 `id like 'SIM-%'`，扫克隆库里**全部 225 张有文本 `id` 的表** ⇒ **现库 3,465 行 / 克隆库 3,465 行，91 张表有演示行，差集 0 张**。★ 这把尺不是恒真的：同一批表的**总行数**两边差得很远（`Order` 1,069 vs 69、`UserAccount` 63 vs 13、`PaymentVoucher` 545 vs 41、`Notification` 51,366 vs 0）⇒ 证明读的是两个库，而演示集这一刀完全相等。
3. **逐字段只抽查了一张表**：`Order` 的 69 条 SIM 行 **id 集合完全相同**，抽查 8 个字段（status/quantity/quoteAmount/poNumber/type/customer/product/currency）⇒ 只有 `status` 在 **4 行**上不同（`SIM-FORD-011/013`、`SIM-ORD-040/050` 现库是 Shipping、克隆库是各自的初始态）。★ 归因清楚：这 4 行现库 `updatedAt` 落在 09-13~09-17（真实时间戳），克隆库是 seed 写进去的整点 ⇒ **差在"现库被后续业务写入动过"，不是 seed 不可复现**。⇒ 所以本格只敢签"**行级**复现"，不敢签"**逐字段**复现"。
4. **两条只属于环境的坑（不是产品结论）**：① `scripts/audit-drill-residue.mjs` 里 dotenv 是 **`override: true`** ⇒ 它**只认 `server/.env.local` 那个库**，我在命令行注入别的 `DATABASE_URL` 会被它覆盖，第一次"克隆库读数"其实又读了一遍现库（两边都是 50,826 才让我发现）。⇒ 想让它量另一个库必须改 env 文件，不改就别用它做跨库对撞。② 克隆库 `Notification = 0` ⇒ 从零铺出来的环境**通知中心是空的**（那些通知由 nightly 简报产生，克隆库没跑调度器）；这是"环境完整度"的一格，不是 seed 的缺陷。
5. **用完已回收**：`dropdb panda_hub_seed_0927`，`panda_hub_local` 全程未写（B243 那条新迁移**仍然没在业务库执行**，结构变更按 §8.2 走发布路径）。
