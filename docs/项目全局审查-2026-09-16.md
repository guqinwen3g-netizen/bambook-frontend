# 项目全局审查：离 v1 验收上线还有多远（2026-09-16）

> 这是一次**基于实测证据**的体检，不是印象评分。所有数字都是本会话实跑拿到的。
> 结论先行，证据在后；判断错的地方也在文末如实更正。

## 〇、结论

**方向是对的，功能已经够了；但「可上线状态」差得比「功能」远得多 —— 代码到生产的通道是断的。**

三句话：

1. **功能面**：v1 清单（主线单据网 + 财务四件 + 主数据 + 客户门户 + 周边七模块 + QC + 自制单据 + 通知中心）
   **逐项都有交付**，没有整块空白。功能完成度我估 **~95%**。
2. **但生产上跑的不是这些功能**：生产 Mac Mini 磁盘上的代码停在 **9 月 3 日 05:32**（远程 `ls -l` 实测），
   此后 **307 个 commit / 164 个 feat+fix** 从未上线，其中包含 **3 个安全修复**。
3. **所以现在的真实状态是**：功能做完了，但没人在生产上见过它们；所有验收都是**在本地库**上做的。
   「验收上线」这件事，目前**没有可验收的对象**。

## 一、方向对不对：对

最近 40 个 commit 里 16 个 feat，按时间倒序是：货权 UI、报表库存数据集、H16 客户门户三缺口、
转售同事务、HS 工具链、T7 四条钱算错、D2、D7、T6、T3、T2、T1……**全部落在既定 v1 口径内**
（真源 `docs/业务流程对齐差距清单.md` §10），没有跑偏去做 v2 的 AI Agent / 知识库 / 供应商门户。

质量红线也守住了，这几条是硬骨头，做对了：
- **跨币种不裸加**（T7-①），汇率锚点只有结汇汇率 —— 本批货权汇总沿用同一条纪律
- **事务原子性**（D7-① 转售双侧同事务），消灭「样品已扣、应收未建」
- **人工操作留痕**（货权变更落 `set_inventory_ownership` 审计）
- **门控一致性**（本批堵掉 `summary-by-ownership` 绕过 `inventory:read` 的旁路）

## 二、是否有序：方法论有序，但有一个断点

**有序的部分**（这是真优点，别丢）：三层对齐 + 批次化 + 每批门禁全绿 + feat/docs 成对落账 +
每批有完成回报和可复跑的真库验收脚本。最近 40 commit 里 21 个 docs，文档密度很高。

**断点**：部署。三轮 handoff 都在同一句话上原地踏步 ——
`031500`「全部只提交未部署」→ `232437`「312 commit」→ 现在 **315**。

而且比 handoff 记的更严重：handoff 只说「本地领先 315」，我实测了**生产侧**——

**生产代码已 14 天没动过**，9/3 之后的所有交付都不在上面。

## 三、差距盘点（分四层，从大到小）

| 层 | 现状 | 差距 |
|---|---|---|
| **① 部署**（最大） | 生产停在 9/3，307 commit 未上线 | 通道是断的；没有一份「部署前核对清单」，没人对此负责 |
| **② 验收** | 空库「从 0 上线」是**既定上线场景**，但全流程走查只在 **9/14** 跑过一次（`docs/上线彩排-空库从0-2026-09-14.md`） | 之后 300+ commit 未复跑，且**没有回归机制**（一次性动作，不是门禁） |
| **③ 质量债** | 服务端全量偶发红从「1 例」扩到 **7 个文件的集合**；依赖漏洞 14 个 | 门禁可信度在下降，大家开始习惯「红了先复跑再说」 |
| **④ 功能** | v1 清单逐项有交付 | 小。剩余都是等外部输入：HS 7 个税率、拼柜口径、CIF 造数 |

**挂账是在收敛的**（这点要说清楚）：T7 五条、H16 三缺口、D2、D7 都已清完，
剩下的从「待办」变成了「**等外部输入**」（等你给税率、等你拍板拼柜）。

**顽疾（≥3 轮没清）**：① 部署落差（3 轮原地）② 拼柜跨客户泄漏口径（3 轮卡着）
③ 邮件通道（判为「小事情」后一直没清，卡着账号双通道）④ 服务端偶发红（在恶化）。

## 四、建议：转入「上线收口模式」

**我的判断：功能已经够了，应该停止开新批次，把接下来所有力气放在「让它上线并被验收」。**

按收益排序：

1. **打通部署（最高优先）** —— 先出一份「307 commit 部署前核对清单」：有没有必须先跑的建表/迁移、
   有没有需你确认才能上的功能、部署窗口与回滚方案、3 个安全修复的验证方式。
   **这一步不做，后面所有验收都是空转。**
2. **空库全流程复跑** —— 9/14 之后代码变了太多，既定上线场景必须重跑一遍，
   并把它**固化成门禁**（而不是一次性彩排）。
3. **收三个外部输入** —— HS 7 个税率（工具链就绪，填完一键补录）、拼柜口径拍板、
   CIF 造数验收（可与 2 合并）。
4. **质量债** —— 偶发红定位根因（7 个文件已登记）、依赖漏洞 14 个。这层可以在上线后补。

**不建议**：现在再开新的功能批次。边际收益已经很低，而且每多一个 commit 就多一分部署落差。

## 五、本次审查的纠错（如实记录）

1. **「报表引擎没有前端」是误判**（我上一批的完成回报也跟着写了，已改）。
   `ReportCenter.tsx` 一直通过 `services/reportService.ts:125`（`/v1/reports${path}`）消费引擎，
   8 个数据集在 UI 上都可用。误判成因：用「组件层 grep `/v1/reports` 字面量」判断接线，
   而路径是 service 内部**模板串拼出来的**，字面 grep 命中不了。
   → **教训已回写：判断有没有接线，要顺着 import 追到 service 内部，不能靠字面 grep。**
2. **「端点存在性探测」方法作废**：公网 `GET /inventory/__nope__` 也返回 401（全局认证门），
   所以 401 不能证明端点存在。生产版本最终是靠远程 `ls -l` 定的。
3. 子 agent 报的「空库 schema 漂移 / 双库迁移不同步」需复核：`server/.env` 与 `.env.local`
   实测指向**同一个库**（9/16 已更正过一次），「双库迁移」这个说法本身可能是空操作。
