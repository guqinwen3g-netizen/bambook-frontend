## 一、说人话：修掉之前是什么局面

CRM 有两套路由同时挂在服务上：`/api/v2/crm/...`（新，带权限判定）和 `/api/v1/crm/...`（旧，只判断"你有没有登录"）。
⇒ 只要走 V1 那几个地址，**任何登录账号**都能：

- 给任意客户**新增/改/停用信用额度**（`POST /:relationId/credit-limit`、`PATCH /credit-limit/:id/status`）；
- 增删改**品牌线**、**沟通记录**、联系人、跟进、商机、客户等级。

而且旧 V1 的 `authenticate()` 对"只带 API-Key、没有人的身份"的请求也直接放过 ⇒ **一个脚本拿一把 API Key 就能改信用额度**，出了事审计里只有 `system`。
这不是"理论风险"：财务/质检/物流角色的账号本来就**不应该**有 CRM 写权限（权限矩阵里他们确实没有），此前只是没人挂那道判定。

## 三、修法：让 V1 不再绕过 V2 已经在执行的那条口径

不新造政策、不新造判定实现 —— V1 直接组合 V2 用的那**同一份**原语：

```ts
const requireJwtWrite = requireJwtForWrite({ requireAuth: options.requireAuth, apiKeys: options.apiKeys });
const requireCrmWrite = (req, res, next) =>
  requireJwtWrite(req, res, () => requirePermission('crm:write')(req, res, next));
```

20 个写路由逐个改成 `router.<verb>(path, requireCrmWrite, handler)`。

三条"为什么这样写"：
1. **为什么不直接挂 `requirePermission('crm:write')`**：V1 没有 `router.use(createModuleAuthGuard(...))`，`req.actor` 从来不会被赋值 ⇒ 直挂会把**合法 JWT 一起 401**（写面全废）。`requireJwtForWrite` 正好补这一步（它负责把 actor 落到 req 上）。
2. **为什么不自己手写"没身份就 401"**（我第一版就是手写的）：那是把 `requireJwtForWrite` 已经实现过的判定**重抄一遍** ⇒ 两份真源。
   本批实测两者等价：`extractActorFromRequest`（`auth/middleware.ts:67`）只在拿到"带非空 `userId` 的内部 JWT"时才返回 actor，客户 token 与裸 API-Key 一律 `null` ⇒ 换用共享原语后 `src/crm/` 全域 **60 例全绿**，行为未变。
3. ~~**dev 不鉴权模式**：`requireAuth=false` 时 `requireJwtForWrite` 直接 `next()`，与 V1 原 `authenticate()` 的口径一致 ⇒ 现有以 `requireAuth:false` 建的测试不会平白多红。~~
   ★ **v2.41 更正（复核 I-3，这句原先是假陈述）**：`requireJwtForWrite` 那一步确实 `next()`，但**下一环 `requirePermission('crm:write')` 不放** ——
   `auth/permissionGuard.ts:101` 的 dev 放行要求 `authSource` 为 `dev` **且**不是写类 scope，而 V1 从不赋 `authSource`（就是上面第 2 条承认的那件事），`crm:write` 又是写类 scope
   ⇒ 实测：`requireAuth:false` 下无凭证 `POST /api/v1/crm/:id/contacts` **改前 400（真进 handler）→ 改后 401**（`Login (JWT cookie or Bearer) required before scope check.`）。
   与 V2 的实际行为一致 ⇒ 不是新分叉，但这是**第二条可见行为变更**，见 §4.3。教训同源：**我把"看着合理"当成了"已实测"**。

## 四、判据与证据

### 4.1 判据怎么派生（不手写清单）

`server/src/crm/__tests__/crmV1WriteScopeB69.test.ts`（7 例）：
- **分母从源码派生**：读 `crmRoute.ts` 源码枚举写路由 ⇒ 与"挂了 `requireCrmWrite` 的写路由"求差集，差集非空即红 ⇒ 以后新增写路由忘挂门，**门禁当场红**（不是等下一轮人工复核）；
- **拒绝矩阵从 RBAC 派生**：不持权角色列表由 `getDefaultScopeListForRole`（真源）算出，断言 403 且响应体含 `INSUFFICIENT_SCOPE`；
- **阳性对照**：持 `crm:write` 的角色 × 全部 20 个写路由必须**不被挡**（不是 401/403）⇒ 防"把门焊死也算绿"；
- **档位归因**：持权角色若拿到 403，只允许来自**行级数据范围层**（DR-042），不许来自 scope 层 ⇒ 防"过严"伪装成"正确"；
- **裸 API-Key 一律 401**（20/20）⇒ 钉住"有 Key ≠ 可写"。

### 4.2 变异证据（把缺陷放回去，看会不会红）

### 4.3 可见行为变更（不许悄悄发生）

财务 / 行政 / 物流 / 质检 角色的账号，此前在 **6 个"只有 V1 有"的写端点**（品牌线、沟通记录）上是**真能写**的（V2 没有对应面 ⇒ 它们从来没被权限层看过）。本批之后这些请求返回 **403 `INSUFFICIENT_SCOPE`**。
前端 **不按角色隐藏**这些入口 ⇒ 按钮照样在，点了才报错。
★ **v2.41 复核更正两条**：
- **M-1**：上表"V2 的写端点 **11** 个"是**去重路径**口径，`(method, path)` 对是 **14** 个 ⇒ `20 = 14 + 6` 用的后者那把尺。两个数不是同一口径，别再相减。
- **M-2**：这里"前端不隐藏"原先的证据（`lib/modulePermissions.ts` 里搜 `crm` 命中 0 次）**无效** —— 该文件由 `VIEW_TO_MAIN_SCOPES` 派生，按设计不含任何字面 scope。
  有效证据是根 `lib/rolePermissionMatrix.ts` 里 `View.CRM → crm:read / crm:write` 这条映射在全域找不到 UI 消费者。结论不变，证据换掉。
  同一条更正还有一处：**QC 连 `crm:read` 都没有** ⇒ 入口对 QC 本就隐藏，"按钮仍在、点了才报错"只适用于 **FINANCE / ADMIN / LOGISTICS**。
- **I-3**：另多一条可见变更 —— **dev 模式（`requireAuth:false`）下无凭证**的 V1 CRM 写从 400（真进 handler）变 **401**（见 §三.3 那条被划掉的假陈述）。与 V2 实际行为一致 ⇒ 不是新分叉，但要单独入账。
⇒ "按角色隐藏 CRM 写入口"是一条**要跟的后续**，但它属 UI 面且**本 worktree 无法浏览器实测**（无 env、后端起不来）⇒ 按 S2 记为**未覆盖**，不用"代码看着对"顶替实测。

## 六、没做什么

- **没删 V1、没把 V1 重定向到 V2**（那是接口面重构，要单独一批：V1 的响应体形状与 V2 不完全同）；
- **没动行级数据范围层**（DR-042 那套 L2 判定只在 V2 有，V1 依旧只做 scope 判定 ⇒ V1 的行级越权**仍是缺口**，已记进 B69）；
- **没给 6 个 V1 独有写端点补 V2 对应面**（要不要并入 V2 属接口收敛决策 ⇒ 已按"待 Kevin 拍板"登记在 B69 的 owner 格）；
- **没做前端按钮显隐**（见 §4.3 未覆盖）；
- 没跑写库的验收脚本、没碰生产库、没重装依赖、不 push、不部署；`:8081` 与主目录 1c 遗留改动一字未动。
