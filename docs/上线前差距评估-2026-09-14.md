## 一、上线执行层（新的真实空白，最高优先）

### G1 生产库 schema 部署策略矛盾 ✅核实（上线阻塞）
- **事实**：本地表结构真源 = `pg_dump --schema-only` 克隆（不跑 migration，工作章程明文）；但生产部署脚本 `ops-deploy-main-api.sh:28` 跑 `npx prisma migrate deploy`。
- **推演**：schema-only 克隆会带 `_prisma_migrations` **表结构但不带 56 行历史记录** → 生产首次 `migrate deploy` 会从头重放 55 个 migration → 全部报"表已存在"失败。
- **解法（二选一，上线前定案）**：①生产库建好后执行基线回填（`prisma migrate resolve --applied` 逐个标记，或直接 insert 历史行）；②生产库改用「空库 + migrate deploy 全量建表」而非克隆。推荐 ①——与本地权威结构逐字节一致。

## 三、操作风险小项

### G6 订单状态推进无二次确认 ✅ **已修+实测**（commit 0997210）
重状态（出运中/已交付/标记异常/异常恢复）弹确认框（含可选备注留痕），轻状态保持直推。浏览器实测：Production 单点「推进到『出运中』」→ 弹窗出现 → 取消 → 状态未变。

### G7 报关单号强制显式传参 ✅核实（已登记）
`POST /v1/customs/declarations` 路由要求显式 declarationNumber，服务层自动生成（CD-YYYY-NNNN）能力被路由挡住。前端总传号所以未暴露，但任何自动化/集成会踩。放开为「传了校验唯一、不传自动生成」。
