```bash
ls prisma/migrations | tail -30
```
**判据**：凡是含 `ALTER TABLE ... DROP COLUMN` / `DROP TABLE` / `UPDATE ... SET`（数据回填）的迁移，
**逐条评估并记录回滚方式**（本仓迁移多为手写 SQL，没有自动回滚）。

### 4. （可选但推荐）在生产库上先做一次"迁移演练"

```bash
# 用备份恢复到临时库，在临时库上跑迁移，确认不报错
createdb panda_hub_migrate_dryrun
pg_restore --dbname=panda_hub_migrate_dryrun --no-owner --no-acl /Users/Shared/BambookBackups/bambook-<ts>.dump
cd server && DATABASE_URL="postgresql://bambook:<pwd>@localhost:5432/panda_hub_migrate_dryrun" npx prisma migrate deploy
dropdb panda_hub_migrate_dryrun
```
> 这一步能把「迁移在生产库炸了」的风险挪到可丢弃的临时库上。

### 5. 装定时备份（**一次性**，装完以后每天 02:00 自动跑）

```bash
cp server/scripts/com.bambook.postgres-backup.plist ~/Library/LaunchAgents/
sed -i '' "s|CHANGE_ME_HOME|$HOME|g" ~/Library/LaunchAgents/com.bambook.postgres-backup.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.bambook.postgres-backup.plist
# 立刻验证一次（别等明天 02:00）
launchctl kickstart gui/$(id -u)/com.bambook.postgres-backup
sleep 5 && tail -4 /Users/Shared/BambookBackups/backup.log     # 应出现 "backup ok"
```
**判据**：`backup.log` 里出现新的 `backup ok` + 备份目录多一份新 dump。
> ⚠️ **不要只看 `launchctl print` 显示 loaded 就算成功** —— 必须看到日志里有新的 `backup ok`（本会话的教训：装了没跑 = 没装）。

## 四、回滚预案

| 场景 | 动作 |
|---|---|
| 前端坏了 | 回滚 `ops-upload-webapp.sh` 上传的前端包（上一个版本） |
| 后端代码坏了 | 回滚 `ops-upload-package.sh` 上传的后端包 + 重启 |
| **迁移已跑、要退回** | ① 停后端 ② 用第 1 步的 dump 恢复（`pg_restore --clean --if-exists`）③ 回滚代码 ④ 起后端。**这是最后手段，会丢迁移后产生的数据** |
| 只是某条迁移有问题 | 手写反向 SQL（本仓迁移是手写 SQL，**没有自动回滚**）⇒ 所以第 3 步要逐条记录回滚方式 |

### 6.1 关键教训：**部署必须走局域网，公网通道对大包不可用**

| 通道 | 结果 |
|---|---|
| 公网 `https://ops.jiangsupanda.com` | ❌ **HTTP 524**（Cloudflare 100s 上限）。实测 3.5MB 上传耗时 **129.5s / 速度 27KB/s** ⇒ 本机上行带宽是瓶颈 |
| **局域网 `http://192.168.110.3:8088`** | ✅ **HTTP 200，35 秒完成** |

> ⚠️ Ops Panel 的 `deployUploadedPackage` **没有分块上传**（只有 webapp 有 `deploy-webapp-chunk`）
> ⇒ 只要包 > 2.7MB，公网通道必然 524。**内网部署是唯一可行路径。**
