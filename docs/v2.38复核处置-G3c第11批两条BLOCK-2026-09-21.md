## 一、一句话说明白（业务后果）

1. **收信同步失败时，系统会对用户说一件不存在的事**：如果第一封邮件就失败，那这封邮件其实**一封都没落库**，而界面文案写的是"部分邮件已写入，请先核对" ⇒ 用户会去邮件列表里找**根本不存在**的邮件，管理员也照这个方向查。
2. **"脚本有没有先装载本仓数据库配置"这条门禁只查了"文件里出现过"，没查"是不是在连库之前"** ⇒ 把装载语句挪到连库之后，门禁照样全绿。也就是说，上一批号称"从靠人复核变成门禁当场红"，实际只做到一半。

## 二、BLOCK-1：同一枚错误码在两种现场说两件事

### 2.1 病灶与真实控制流（D52 逐处读，不机械替换）

`server/src/email/emailSyncService.ts`：
- 每封邮件**各自一个事务**（`$transaction(async (tx) => …)`），关联登记（`syncEmailReferences`）与审计（`writeRouteAuditLog`）都在事务**内**、用的是 `tx`；
- 这两步失败被包成 `SYNC_REF_FAILED` / `AUDIT_FAILED` 抛出 ⇒ 循环里 `if (err?.code === …) throw err` **中断整批**；
- `synced++` 在事务**成功之后**才执行。

⇒ 当**第一封**就失败时 `synced === 0`，那封已随事务回滚，"部分邮件已写入"就是假话。而审计/关联登记失败通常是**系统性**的（第一封即中招），这不是尾部边角场景。

### 2.2 复核者给的方向有一处不成立（照原方向做不出来）

复核写「`:373/374` 处 `synced` 就在手上 ⇒ 按 `synced>0` 分支」。实测**不成立**：`let synced` 声明在 `try {` 的**块内**，而 `catch` 是兄弟作用域 ⇒ 在 catch 里读 `synced` 是引用不到（块级 `let` 不跨 catch）。
所以本批的修法是**两件事**：① 计数器声明上移到函数体顶端（外层 catch 才拿得到），② 文案表按提交数分叉。

### 2.3 改法（判据只留一份实现）

- `OUTWARD_MESSAGE` 的值类型改为 `string | ((p: EmailSyncProgress) => string)`，`EmailSyncProgress = { committed: number }`；两枚"发生在逐封提交环节"的码各自给出**已写入 N 封**与**一封都没有写入**两条文案，其余码不变；
- `buildEmailSyncError(code, detail, progress)` —— 第三参**必填**，7 处调用点逐一传 `{ committed: synced }`（漏传是编译错，不是运行期才发现）；
- 诊断原文仍只进日志（`{ code, detail, committed }`），对外文案仍与异常内容无关。

### 2.4 为什么这个形状不会再退化成假话

新增的两枚码文案**必须由 committed 决定**。测试按同一枚码打两个现场：
- `committed=0` ⇒ 必须含"一封都没有写入"，且**不得**出现 `已写入 N 封`；
- `committed=2` ⇒ 必须含"已写入 2 封"，且**不得**出现"一封都没有写入"。

⇒ 任何"退化成一句固定文案"的改法会当场红其中一条。旧测试的反面对照是对**已产出的字符串**做 `replace`（把真判据整段删掉它照样绿）——那种空转对照本批删掉了，换成"同码换计数、两句必须不同"。
另加**服务层**两条真链路（把失败注入到指定那一封）：第一封就失败 ⇒ 对外不得说已写入；前两封已提交、第三封失败 ⇒ 对外必须报"已写入 2 封"（这条同时证明计数真的从循环带到了 catch，不是常量）。

## 三、BLOCK-2：普查守卫对"构造之前"没有牙

### 3.1 病灶

`scripts/acceptance-selfcheck.test.ts` 的 `ENV_FUNNEL` 只判"这个文件的代码行里**出现过** `loadEnvForScript(`"，而台账/文档把它写成"构造 client **之前**" ⇒ 判据与声明不一致。复核实测：把 `acceptance-batch1-a3b1b4.mjs:66` 的调用挪到 `new PrismaClient()` 之后，24 例仍全绿。

### 3.2 改法（按行序判，不按"出现过"判）

- 判据对象收窄到**实例化**：`new [\w$.]*PrismaClient(`。为什么不是"文件里提到 @prisma/client"：Prisma 是在**实例化**时才读 env，`require('@prisma/client')` 写在装载之前不构成债 —— 按"出现过"判会把已合规的文件报成债（第一版就犯过一次假阳性）；
- 另加一条兜底臂：代码行里出现 `@prisma/client` 字样却**完全没有**装载入口 ⇒ 计入"未过 env"（抓住"import 后换别名 new"的写法）。实测今日该臂命中 0 个文件 ⇒ 不收窄覆盖、只增加牙；
- `noEnv`（没接）与 `lateEnv`（接晚了）分成两条债、两条断言，失败消息各自点名文件与行号；
- 正面对照从两种形状扩到**四种**：① 完全没过 env；② dotenv 路径写死主 checkout；③ **接了 env 但接在构造之后**；④ **已接 env 却仍硬编码主 checkout 路径**（这才是本批真实回归形状 —— 旧版 `bad2` 一条同时落进两个判据，`absPath` 臂其实没被独立钉住）。

### 3.3 分母改成一份实现（复核 MINOR-7）

`scripts/lib/acceptance-selfcheck.mjs` 新增 `acceptanceScriptFiles(root, { includeE2E })`：
- 批量执行器 `run-all-acceptance.mjs` 改为调用它（此前自己写一份 glob）；
- `scriptPorts()` 里那**第三份**同样 glob 也改为调用它；
- 普查用 `includeE2E: true`（更宽口径），并新增一条断言：**普查分母必须覆盖执行器分母** ⇒ 一侧扩了另一侧漏，门禁当场红。旧版只有 `>= 60` 的地板，对 80→61 的塌陷不敏感。

实测（本批）：执行器 `--list` 仍 **78** 条（改前改后一致）、`SKIP` 3 条、普查分母 **80**、`scriptPorts` 仍 `3000,8081`。
