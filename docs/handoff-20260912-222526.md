## 一、不可推翻的业务口径（改代码前必读）

1. **盖章 = 交互式签署，不是静默自动盖**
   审批人打开单据 → 阅览到盖章位 → 在该位置点「签字确认」→ **一步同时完成盖章 + 批准**。
   不存在「审批通过时后台偷偷盖章」的路径。

2. **盖章范围按「有没有文件」判定，不按「四件」名单**
   - 会盖章（对外/正式单据）：报价单 Quotation / 订单确认书 OrderConfirmation / 合同 Contract / 付款申请单 PaymentRequest。
   - **只过权限、不盖章**（纯程序内风控）：订单变更、MOQ 豁免、价格偏离、DR-013 例外、内部交易价、Agent 工具审批。

3. **付款申请单要做 PDF**（每张申请单对应一份文件）；**订单变更单不做 PDF**（程序内事项，不产生对外文件）。

4. **签署人 = 审批人本人**，无代签（对齐 §10.4 P-7）。

5. **G3-4 回款闭环**：业务员必须看到回款（认领 → 订单结案「绿」）；利润 = 回款 − BOM 成本。

6. **领导/老板必须有印章图库 UI 入口**（不能只留 API 给开发用）。

7. **fail-open 原则**：印章解析/渲染失败只 `logger.warn`，**绝不阻断单据生成**（与通知接线同口径）。

## 三、回款认领（§10.3-2）架构

### 服务端（`33c8886`）
- `server/src/finance/receiptClaimService.ts`
  - `listClaimableReceipts(prisma, { visibleOrderIds, limit? })`：只返回 **Receipt 凭证 + 仍有未核销余额 + 挂在业务员可见客户上**的收款；**未挂客户的收款不下发**（防跨客户金额泄漏）。
  - `claimReceipt(prisma, {...})`：**五道安全边界**
    1. 仅 `type=Receipt` 且未核销完；
    2. 仅**自己可见订单**的应收发票（复用 `resolveVisibleOrderIds`，与 §10.4.2 同口径），空白名单 **fail-closed**；
    3. 凭证已挂客户时**客户必须一致**（防把 A 的钱认到 B 头上）；
    4. **币种一致**，不做自动换算；
    5. 金额 ≤ min(凭证未核销余额, 发票未收余额)（终判仍在 Serializable 事务内）。
  - **复用既有 `createAllocation`**（Serializable 事务 + 审计 + 状态重算 + 事件），**不另造一套核销**。
- `server/src/finance/route.ts` — `GET /receipt-claims` + `POST /receipt-claims/claim`，均挂 `requireInvoicesRead`。
- 通知：`notificationService` 类型标签表补 `receipt_claimed: '回款认领待复核'`。

### 权限裁定（重要，别乱加 scope）
业务员不持有 `invoices:reconcile`（仅财务/管理员）→ 认领走 **`invoices:read` + 服务层 fail-closed**，属**受限写**（仅作用于自己可见发票的未核销余额、走 Serializable 事务、审计留痕、通知财务、财务可撤销）。
**新增 scope 会联动角色矩阵 + 双端同步守卫（GAP-R2），成本高——确需收紧再单独立项。**

### 前端（`055d415`）
- `components/finance/ReceiptClaimsPanel.tsx`（自包含）：拉待认领收款 → 选应收发票（按币种/客户预筛，**服务端权威校验**）→ 金额上限 = min(凭证未核销, 发票未结) → 认领 → 通知财务复核。
- `components/FinanceManager.tsx`：`FinanceTabId` 加 `receiptClaims` + `FINANCE_TABS` 入口（HandCoins）+ `isSelfContainedTab`/`statusStats` 补齐 + 内联 `refreshInvoices`（认领后重列发票刷新 `openAmount`）。
- `services/receiptClaimService.ts` — 前端 service。

## 五、踩坑清单（本轮血泪，别重犯）

1. **同一文件的多次 Edit 不要并行** —— 并行编辑会互相覆盖：`text-[12px]→text-xs` 被并行的 `text-[13px]→text-sm` 覆盖掉了，漏一轮才补干净。**同文件一律顺序改。**
2. **本地 8081 后端跑源码不热重载** —— 旧进程会让新端点被 `GET /:id` 兜底成「发票不存在」，误判成「路由没写」。**HTTP 冒烟前先确认进程是新建的。**
3. **设计令牌守卫（三连）**：
   - 任意字号 `text-[11px]~text-[18px]` 禁用 → 用语义类 `text-xs/sm/base/lg`；
   - 原生 `<select>` 禁用（M4）→ 用 `CustomSelect`；
   - 裸 `rounded` 禁用 → 用 `rounded-control` / `rounded-field` 等 BDS 刻度类。
4. **服务函数签名别在「位置参数」与「单对象」之间漂移** —— 定义 `(prisma, params)` 却按单对象调用 → `TS2554 Expected 2 arguments, but got 1`。**定义与调用一次对齐。**
5. `params: { limit = 50 }` 在**类型注解**里给默认值是语法错（**TS1131**）→ 写 `limit?: number` 再在函数体内兜底。
6. **系统角色常量是 `role-admin`**（不是 `admin`）→ 伪造 token 冒烟时角色串写错会得到「正确的」403，容易误判成权限 bug。
7. **合同 composite 曾漏传 ctx** —— `composite/preview.html` 与 `generate.pdf` 没把 `{ type, sourceRef, signer }` 传给 `renderServerDocument`，导致合同签了也不盖章（批次 5 已修）。
8. **伪造 JWT 时系统角色必须放 `roleIds`，不是 `roles`** —— `TokenPayload` 里 `roles: AgentRole[]`（admin/sales…）与 `roleIds?: string[]`（`role-super-admin`…）是**两个字段**。把系统角色塞进 `roles` → `getDataScopeResolver` 判不出 `'all'` → `resolveVisibleOrderIds` 返回 `[]`（而非 `null`）→ **认领/列表全部 fail-closed 成空**，极易误判成「功能坏了」或「库里没数据」。本轮为此白查一轮。
9. **prisma 造数/取数的坑**：`PaymentVoucher` 建行需显式 `id` + `paymentMethod` + `createdAt/updatedAt`（BigInt，无默认值）；`Invoice`/`PaymentVoucher` 的 `appliedAmount`/`openAmount` 是**路由派生字段不是 DB 列**，`select` 会报 `Unknown field`，须自行 `groupBy invoiceAllocation` 计算。
