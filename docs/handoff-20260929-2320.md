## 二、★ Kevin 今天拍的口径（逐条，含要点）

### 2.1 公差标准双轨制（`docs/inventory/公差标准机制-设计-2026-09-29.md` §十一）
- **内部标准要有出厂默认值**：不设置也直接用参考数值（±5/3/2/1% 分档），后续可改。
  ★ 这**推翻**了同日上午"先留空"的拍板；**幅宽扣款不给默认**（没有可引用的参考数值）。
- 取数链：`①行级覆盖 → ②客户标准(P0) → ③a已录我方 → ③b出厂默认 → ④未判定`；容差**双向**（短装+溢装）。
- 客户标准录入入口：路由 `GET/PUT /api/v1/tolerance/customer-standard` + 客户档案「溢短装标准」分区。

### 2.2 短装拦截（原话提炼成不可颠倒的顺序）
> `短装事实 → ① 反映客户 → ② 客户同意少发 → ③ 我方才能确认本笔出运 → ④ 发货 → ⑤ 结案`
- ⇒ **卡在"确认出运"**（不是事后追认、也不是每次分配都判）；分批出运时**只要该行还有未发运的票就不判**。
- **放行留痕 = 走审批单**（沿用 MOQ 豁免 `ApprovalRequest`/DR-007），不是"写说明+附件"、不是"只提醒不卡"。

### 2.3 数量完整性（口述原话）
> 「不存在说不知道这些数量，然后又要发起这个出运的情况……如果现在是不知道数量就能出运，那就是中间有巨大的缺口存在。」
- 明细里 `actualQty` **为空** ⇒ 拦住（先填数量）；本票**一条明细都没有** ⇒ 也拦住。
- ★★ 这两枚**不许走审批放行**（缺的是**数据**不是客户同意；审批解决不了"没录数量"）。

### 2.4 幅宽扣款（两条都改变了建模）
> 「第三方测试是指 ITS 之类的嘛，**这些不用我们管**……如果是 QC 的话，**这不是属于第三方 QC，是属于我们内部的 QC 团队**，
> 服装面料我们都会派 QC 出去查货验货的。这部分我们肯定是**自己去在 QC 的工作过程当中把它记录下来的**。」
- ⇒ 幅宽的载体 = **我方 QC 查货的验货记录**（`InspectionReport`），入口在 **QC 工作台**；**不是**第三方送检单。
- **扣款基数 = 该订单行的货款金额**（`OrderLine.netValue`）。
- 客户标准原文（库内已抽取）：`可用幅宽 ≥147CM；偏差 ≤3%→扣10% · ≤4.5%→扣25% · ≤6%→扣30%`。

## 六、今日踩过的坑（★ 复用价值最高的一段）

1. **`shipping/route.ts` 的本地档位表 + `|| 500` 会把 409 渲染成 500**（业务员只会反复重试，永远走不到审批）。
   正解 `本地表 ?? httpStatusOfCode(code)`；★ 但**必须同时**把该路径可能返回的码全部登记（缺码即抛，而 PATCH 处理器**没有 try/catch** ⇒ 请求回不到响应）。
2. **`gateToleranceOf` 的"未判定"给的是 `pct: 0`，不是 `null`**（数量口径"按 0 卡"）⇒ 判据必须是 `unresolvedReason != null`，

3. **`serviceMessageWrapRatchet`**：对外文案里不许内插 `.message`（哪怕是领域文案）⇒ 先算好一段话再赋值。
4. **源码扫描型守卫会读注释** / **JSX 文本里的 `**粗体**` 会原样上屏** / **JSX 里裸 `>` 和 `★`** 都会炸（★ 在 `sampleQcChainRuntimeQa` 的禁 emoji 字符集 `\u{2600}-\u{27BF}` 里，且它**只扫那几个 UI 文件**）。
