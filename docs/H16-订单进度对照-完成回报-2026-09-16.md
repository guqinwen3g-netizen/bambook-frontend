## 一、为什么降级（我的判断）

现状核准时我判断 ③ 是三个缺口里**成本最高、价值最不确定**的一个：

- 它要建**消息通道**（客户留言 → 内部查看 → 可能还要双向回复，那就是轻量 IM）；
- 而 B2B 场景下客户**更倾向直接找业务员**，门户内留言的实际使用率通常不高。

所以本批**不做双向反馈**，改为回答客户真正关心的那件事：

> **我的货什么时候到？有没有延误？**

## 二、口径（我定的）

**输出**：订单交期（承诺客户的 `dueDate`）+ 计划/实际离港与到港 + **交期达成判定**。

| status | 含义 | 判定 |
|---|---|---|
| `on_time` | 如期/提前交付 | 已交付且实际完成日 ≤ 交期 |
| `delayed` | 交付延误 | 已交付且实际完成日 > 交期 |
| `overdue` | **已逾期未交付** | 未交付 且 今天 > 交期 |
| `pending` | 进行中未到期 | 未交付 且 今天 ≤ 交期 |
| `unknown` | 未登记交期 | 无 `dueDate` |

**两个关键细节**：
1. **参照日不同**：已交付用**实际完成日**（`ATA` 优先，回退 `ATD`）算偏差；未交付用**今天**判是否逾期。
2. **已交付但运单未登记实际日期 → 不猜**（`deviationDays = null`），只给结论 + 说明"无法计算偏差"。

**多运单取极值**：最早 `ETD` / 最晚 `ATA`（分批出运时代表整单进度）；**`Cancelled` 运单排除**。

**数据边界**（与 `timelineService` 同口径）：只给对外节点；**不给**内部延误原因、工厂与供应商、成本运费、内部备注与审批。
