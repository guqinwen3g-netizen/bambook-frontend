## 一、本批发现的真 bug：一张 **0 元应收票** 就能把客户**永久挡单**

### 1. 病灶（一句话）

「未结清应收」判据原先在 **6 处**手写 `type='Receivable' && status ∈ {Issued, PartiallyPaid}`，
**不看金额、也不看未结额（open）**；而 `amount` 的符号守卫只禁**负数**、**放行 0**
（`invoiceMutationService.ts:63-82`：`POSITIVE_ONLY_FIELDS={exchangeRate}`、`NON_NEGATIVE_FIELDS={amount}`）。
→ 一张 **0 元应收票**（真 API 可建，实测 **201**）被当成「未结清逾期应收」。

### 2. 后果链（**全部是代码事实 + 真库实测**）

| 环节 | 事实 | 真库证据 |
|---|---|---|
| ① 虚增逾期 | `creditService.maxOverdueDays` 计入它的账龄 | 被测客户**只有 1 张 0 元票** → `maxOverdueDays = 65`（应为 0） |
| ② 挡单 | `checkCreditAvailable` 命中 `maxOverdueDays > 60` | `blocked=true` / `blockCode=OVERDUE_60_DAYS` |
| ③ **永不解冻** | `recalcInvoiceStatus` 的 Paid 判据是 `amount.gt(0) && Σapplied ≥ amount` ⇒ **amount=0 时永不 Paid** → 虚增的逾期**永不清零**；自动解冻 `thawAutoFrozenIfSettled` 要求 `maxOverdueDays ≤ 60` ⇒ **永不满足** | `recalcInvoiceStatus → 'Issued'`（S4） |
| ④ 连带误判 | `riskService` 客户风险画像 + 坏账扫描同样计入；`receivableOverdueDetector` 会发「逾期未收清」催办 | 同源判据（代码扫描） |

> **③ 是本批最要命的一环**：不是「显示错误」，而是**没有任何自动路径能解除**——
> 业务员开不了新单，只能找总领导手工解冻；解冻后下一轮扫描又会重新冻结（票还在）。

### 3. 修法：**收成唯一真源**，而不是逐处加条件

- **新增** `server/src/shared/openReceivable.ts`：
  - `RECEIVABLE_OPEN_STATUSES = ['Issued','PartiallyPaid']`
  - `openReceivableWhere(extra)` —— 含 `amount: { gt: 0 }`；**核心判据写在 `...extra` 之后**
    （调用方传同名字段**不能**把守卫悄悄关掉 —— 有测试钉住）
  - `hasOpenAmount(v)` —— 循环内兜底守卫（mock / 手写 SQL / 内存行场景 where 不生效）
- **7 处消费点改用它**（分布在 5 个文件）：`credit/creditService.ts`（`maxOverdueDays` + `runAutoFreezeScan`）·
  `scheduler/tasks/receivableOverdueDetector.ts` · `risk/riskService.ts`（客户画像 + 坏账扫描）·
  `customer/route.ts`（客户门户「未结清张数」）·
  **`events/linkages/L5AutoAllocate.ts`（`resolveTargetInvoiceId` —— 第 7 处，本批顺带发现）**。
  > ★ 第 7 处的病灶与其余 6 处**不同源但同墙**：它按 `issueDate` 升序**只取第一条**候选票，
  > 若最老那张是 0 元/负额票 → 下游 `remaining ≤ 0` 直接 `return { ok:true, created:null }`
  > （**静默不核销**，只有 info 日志）→ 后面那张真正该收的正额票永远轮不到 →
  > **钱收了却没核销**：应收虚高、账龄虚高、信用额度占用虚高。

### 4. ★★ 明确「**不该**」装守卫的地方（别一把梭）

判据有两类语义，装错地方会**制造新错**：

| 语义 | 装守卫？ | 例 |
|---|---|---|
| 「是否逾期 / 是否需催收」的**判定** | ✅ 装（排除 0/负额） | 本批改的 7 处 |
| 「应收净额汇总 / 账龄」的**聚合** | ❌ **不能装**（负额贷项必须计入，否则净额虚高） | `financeServiceV2` 应收应付汇总 · `reportService` 账龄 · `computeNetOpenReceivables` |

`dunningService` 另有 `open > 0.005` 门槛 → 天然安全，未动。

## 六、坑（本批新踩，接手人直接复用）

1. **★★ 同一判据散落 N 处 —— 修法不是「逐处加条件」**：收成唯一真源 + **结构守卫（源码扫描禁内联字面量）**
   + **行为守卫（喂边界值）**。三步缺一不可，否则将来新增第 8 处又手抄一遍。
   **本批实证**：找到 6 处后，写结构守卫时又扫出第 7 处（`L5AutoAllocate.resolveTargetInvoiceId`）
   —— **结构守卫本身就是发现遗漏的工具**，不只是防回退。
2. **★★ 断言必须有「阳性对照」，否则会空过**：只断言「0 元票 → 0 逾期」是**空过的验证器**——
   机制整体没跑起来（查询写错 / 服务没热重启 / 实体没建成）结果同样是 0。必须同时断言「正额逾期票 → 65」。
3. **★ `max`/`min`/`exists` 这类聚合会掩盖单点错误**：同一客户放两张票就区分不出来
   → **被测场景必须用独立客户**（只放那一张问题票）。
4. **★ 真库演练写 `.ts` 用 `tsx` 跑，可以直接 `import` 真服务**（`cd server && npx tsx ../scripts/xxx.ts`）——
   比 `.mjs` 里复制查询强得多。但**别**在演练里调「扫全库 + 给真实用户发通知」的函数
   （如 `receivableOverdueDetector.detectAndNotify`，它会把真实逾期发票也通知一遍）→ 这类只用单测 mock 验。
5. **★ 恢复被证伪的文件后必须 `diff -q` 逐字节核对**，别信「我记得改回来了」。
6. **「新增一次字段读打穿 mock 不完整」又踩一次**：`creditService.test.ts` 的 `makeInvoice` 没 `amount`
   → `hasOpenAmount(undefined)=false` → 票被当「不欠钱」跳过 → 7 红。改服务层后**必须跑该模块全部测试文件**。
7. **`openReceivableWhere` 的核心判据必须写在 `...extra` 之后**：否则 `openReceivableWhere({ amount: { lt: 0 } })`
   会把守卫悄悄关掉（已写测试钉住）。
8. **★ 判「同模块红 = 回归」不能只看模块名，要看「红色断言的输入是否经过我改的判据」**：
   本批服务端全量唯一红在 `orders/orderConfirmGates.test.ts`（订单域，看似与 finance/credit 无关），
   但它的 mock 发票**同样缺 `amount`** → 同源打穿。**改判据后要全局搜「谁会喂它数据」**，
   包括**跨模块**的 mock（`grep -rn "amount" --include=*.test.ts` 之类的反向排查比读模块名可靠）。
