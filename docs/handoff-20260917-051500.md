## 一、本批做了什么

### 0. 一句话

**L2 高危 3 号「第三方代付」= 允许 + 留痕（不阻断）** 全链路落地：
判定真源 → 后端三通道留痕 → 事件 + 通知 → 前端两个录入面 → 单测 → 真库演练 → 双证伪。

**★ 顺带在真库演练里抓到 2 个真缺陷**，都是同一种形态：**单测全绿，但生产路径不生效**
（详见 §一.6 与 §四.1、§四.2）。这两个是本批最有价值的产出 —— 单测覆盖率再高也没抓到。

### 1. 口径（Kevin 已判，2026-09-17）

实际打款人 ≠ 合同客户 是**真实业务**（母公司代付 / 货代代付 / 境外关联方付汇）。
硬拦的后果 = 业务员绕开系统 → **连留痕都没有**（风险从「可见」变成「不可见」）。

→ **放行 + 写痕**。账龄与授信仍归**合同客户**（`Invoice.customerRelationId`）。

### 2. 字段事实（勘察结论 —— **推翻了上一批 handoff §五.1 的一半前提**）

| 上一批的推测 | 代码实况 |
|---|---|
| 「`PaymentVoucher` 是否已有 payer 字段（先核 schema）」 | **没有**。`payerRelationId` / `payerName` 只存在于 `Shipment`，且写入时一律 = 客户自己 → **全仓零业务逻辑** |
| 「`applyAllocation` 的 `select` 里已查了 `customerRelationId`，可用」 | 对，但**漏了 `customerName`** —— 正是本批真库演练抓到的 bug ① |
| 落点 | 用 `PaymentVoucher.customerRelationId`（**DR-016 语义 = 实际打款人 / counterparty / billTo**）承载「谁付的钱」，**未改 schema** |

### 3. 判定真源：`server/src/finance/thirdPartyPaymentGuard.ts`（新增，零依赖纯函数）

**为什么单独成文件、零 import**：前端要 `import` **同一份**判定（否则前后端两份实现必然漂移）。
真源若住在带重依赖的模块里，前端 import 会**穿透 tsconfig 的 `exclude: ["server"]`**，
把服务端类型错误污染到前端 `tsc` 门禁。范式照 `allocationCustomerGuard.ts`。

```ts
export function detectThirdPartyPayment(voucher, invoice): ThirdPartyPaymentDetection | null
export function normalizePartyName(v?: string | null): string
export function toThirdPartyPaymentAuditFields(d): Record<string, unknown>
```

**判定顺序**：

| # | 条件 | 结果 |
|---|---|---|
| ① | 双方**都有** `customerRelationId` | 只比 relationId（强判据 `basis: 'relationId'`）；相等 → null（不是代付） |
| ② | 一侧缺档案 | 退化为比名称（`basis: 'name'`） |
| ③ | 名称也缺 | **不判定**（宁可漏报，不误报） |

**口径隔离**（防止把「付供应商货款」误判成代付）：
`invoice.type` 存在且 ≠ `Receivable` → null；`voucher.type` 存在且 ≠ `Receipt` → null。

**★ 刻意宽松（本批踩过的设计坑）**：`type` 字段**缺省时仍然判定**。
前端 `ClaimableReceipt` 类型**没有** `type` 字段 —— 若写成「缺省即不判」，
前端徽标**永不亮**而所有测试**全绿**（又一条空过的验证器）。已用测试钉住。

`normalizePartyName()` = trim + 折叠连续空白 + 转大写，**不剥公司后缀**
（剥后缀是启发式，会把「ABC TRADING」和「ABC LOGISTICS」判成同一家 → 误报比漏报更伤业务员信任）。

### 4. 后端留痕挂在**内核**（三通道共用）—— 老毛病「收口点错位」的正面防守

核销有**三条通道**，历史上副作用只挂在其中一条 → 走另一条静默少做一步（本仓最高产的一类 bug）：

| 通道 | 入口 | 是否留痕 |
|---|---|---|
| route | `POST /api/v1/finance/allocations` → `allocationMutationService.createAllocation` | ✅ |
| Agent | `reconcileFlow` **直调** `applyAllocation` | ✅（挂内核） |
| Agent | `toolRuntime` **直调** `applyAllocation` | ✅（挂内核） |

→ 留痕挂在 `server/src/finance/allocationService.ts` 的 `applyAllocation` **step 5b**，
**同事务**写审计行：

```ts
const thirdPartyPayment = detectThirdPartyPayment(voucher, invoice);
if (thirdPartyPayment) {
  await writeRouteAuditLog({
    prisma: tx, actorId, source,
    operation: 'third_party_payment_detected', operationType: 'link',
    targetType: 'InvoiceAllocation', targetId: allocId,
    after: { allocationId: allocId, invoiceId, voucherId, appliedAmount: appliedAmountStr,
            ...toThirdPartyPaymentAuditFields(thirdPartyPayment) },
  });
}
```

**事件**（`allocationMutationService.publishAllocationEvents`）：
`ThirdPartyPaymentDetected` —— 但**只有 route 通道会发**（Agent 两通道直调内核，不经这里）。
**这个已知局限已显式写进函数注释**，避免后人以为「事件发不出来 = 坏了」。
**承重留痕是内核那条审计行**，事件/通知只是加分项。

### 6. ★ 真缺陷 ②：业务校验码被兜成 **500**（真库演练 T5 抓到）

`toAllocationError` 是**白名单**式映射，不在名单里的码兜成 `CREATE_FAILED` → route 映射 **500**。

| 码 | 修前 | 修后 |
|---|---|---|
| `CURRENCY_MISMATCH` / `AMOUNT_EXCEEDS_*` / `INVALID_*_STATUS` / `MISSING_*` | **500**「服务器错误」 | **400** + 真码 |

**危害**：财务看到「服务器错误」以为系统坏了，实际只是「币种不一致」——
**报错不指向真问题 = 用户卡住**（正是 §〇 口径 2 的判定项）。
修法：`AllocationMutationErrorCode` 补齐内核业务码 + 抽出 `PASSTHROUGH_ERROR_CODES` 常量数组 +
route `statusCodeMap` 补 400 + 新增演练 **T8 护栏**。

## 四、坑（本批新踩，接手人直接复用；已同步进 skill）

### 1. ★★ mock 必须尊重 Prisma 的 `select`（否则「接线漏字段」永远测不出）

本批真库演练 T7 抓到：`applyAllocation` 的 `tx.invoice.findUnique` **select 少了 `customerName`**
→ `invoiceCustomerName` 恒为空 → 判定顺序的 ② 分支（名称兜底）**在生产里永远走不到**。

**而两套单测全绿**：
- 纯函数单测**手工传完整对象** → 当然绿；
- ledger 接线测试的 mock **无视 `select` 直接返回整行** → 也绿。

→ 修法三件套：① select 补字段；② 给 ledger 测试的 mock 加 `project(row, select)` 投影；
③ 新增专钉「名称兜底」的用例。

**通用教训**：写 Prisma mock 时，`findUnique/findFirst/findMany` **必须按 `select` 裁剪返回**。
无视 select 的 mock 会让「生产 select 漏字段」这类 bug 在单测里**结构性地不可见**。

### 2. ★★ 断言前必须先证「前置条件存在」

演练 T2 首版断言「代付审计行 = 0」，但等待条件恒不成立（L5 自动核销把凭证核到了**另一张**票）
→ **被断言的核销压根不存在** → `count === 0` **恒真** → 断言空过。
修法：新增 `REL_CUST2`（该客户名下**只有一张**应收票 → L5 目标唯一）
+ **先断言分配行确实存在**，再断言「代付审计行 = 0」。

**判据**：任何「某计数为 0 / 某集合为空」的断言，前面必须先有一句证明**母集合非空**。

### 3. ★ 建 `Receipt` 凭证会触发 **L5 自动核销联动**，会和手动核销抢余额

`PaymentVoucherCreated` → `L5AutoAllocate`：核销到**该客户最早未结清的 Receivable 票**，
金额 = `min(凭证剩余, 发票剩余)`。若演练既要建 Receipt 凭证、又要手动核销同一张凭证
→ 谁先谁吃光 → 结果不确定（T2 首跑就是这么被打成假红的）。

做法：**要么**别手动核销、直接断言 L5 落库后的结果；**要么**让演练凭证的客户
**没有**匹配的未结清应收票（L5 会 no matching invoice 跳过）。

### 4. ★ 全树扫描类前端测试在并发全量下会**超时假红**

163 文件并发时超 **5s 默认超时** → 两个文件同时红。

修法：显式 `}, 30_000)`；并把 `readdirSync(dir)` 改成 `readdirSync(dir, { withFileTypes: true })`
省掉逐条 `statSync`。
**判据**：隔离绿 + 全量红 + 用例本身在做全树 I/O → 先怀疑超时，别改逻辑。

### 5. ★ 业务校验码不在白名单里会被兜成 **500**

见 §一.6。**通用判据**：凡是「错误码 → HTTP 状态码」的**白名单**式映射，
每加一个新业务码都要问一句「它不在名单里时会变成什么？」——
答案是 `500 服务器错误`（用户以为是系统坏了），而不是 `400 参数错`（用户知道要改什么）。

### 7. 环境坑（沿用）

- `launchd` 托管后端**不继承 shell env** → 不能用环境变量开关做证伪，只能改代码 + `kickstart -k`。
- `launchctl print` 在沙箱里看不到输出 → 靠 `/api/health` 的 `tts.prewarmAt` 变化 + 循环重试（约 9×2s ready）。
- `ts-node` **无 watch** → 改完必须 `launchctl kickstart -k gui/$(id -u)/com.bambook.dev-server`。
- BSD `grep` **不支持 `\|` 交替**；`zsh` 下 glob 失败会**中止整条命令**（用 `;` 分隔而非 `&&` 太脆）。
- 测试文件里**别用中文标识符**（`const新增` → esbuild 解析歧义 → `ReferenceError`）。
- `vi.mock` 的相对路径是**相对测试文件**解析的 —— 路径写错时 **mock 静默不生效**、
  跑的是**真实模块**（本批 `receiptClaimService.test.ts` 存量就踩了这个：`'../notifications/…'`
  应为 `'../../notifications/…'`）。**新增 mock 后请确认它真的生效**（例如故意让 mock 返回哨兵值）。
