## 0. 验收标准（先定判据，再谈结论）

沿用本项目已定红线，并按服装外贸 ERP 的账务底线细化为四层：

| 层 | 判据 | 性质 |
|---|---|---|
| **L1 账务正确性** | 金额 / 币种 / 汇率 / 单位（米·码·公斤）必须正确；同一实体同一字段跨页一致 | **一票否决**（错了就是错账） |
| **L2 单据链完整性** | 引用不悬空、日期不倒挂、数量不超发、资金闭环（发票额 = Σ核销额） | 一票否决 |
| **L3 可达性与渲染** | 每个视图可打开；真数据下不出 NaN / undefined / Invalid Date；**加载态不得伪装成 0** | 阻断 / 体验 |
| **L4 权限边界** | 六角色 × 关键动作，越权必须被拦 | 一票否决 |

**方法纪律**：每一条结论必须有**真库数字**或**截图**支撑；**误报比漏报更伤信任**，宁可写「未覆盖」。

# 第 2 批：业务变异对撞（2026-09-19 下午）

上一批判据里 L1~L4 全通过，但那是**规则层**。本批按 Kevin 定的「对撞」法：拿**系统写死的假设**去撞**业务侧变异**，

## 6.1 撞出的真缺陷：短装批次**永远结不清**（已修）

**系统假设**：`OrderShipmentBatch.settleStatus` 的结清判据是 `paid >= batch.amount`
（`orderShipmentBatchService.ts` `recalcSettlement`），而 `batch.amount` 是**计划额**
（schema 原文：「本批**计划**结算金额 = 订单额 × plannedRatio%」）。

**业务变异**：**短装** —— 实际出运 < 计划。这在纺织服装是常规情形（甲方另有 **±5% 溢短装条款**，
`docs/设计/09-路线图/第二轮PRD需求池.md` REQ2-03）。短装时「已开票额」就是实际出运额，
**必然小于计划额** ⇒ `paid >= 计划额` **永远不成立** ⇒ 批次**永远停在 partially_settled**，
并被 `dunningStageService` 的「到期未结清末批」**反复误催**（客户其实已按实际出运付清）。

**真库实锤**（新增干跑脚本，用**生产同一份服务**在事务里跑完即回滚）：

| 批次 | 计划额 | 已开票 | 已收 | 库内状态 | 旧判据重算 |
|---|---|---|---|---|---|
| `SIM-FORD-004 #1` | 158,080 | **153,337.60** | 153,337.60 | `settled` | **`partially_settled`** ← 自相矛盾 |

⇒ 全库 67 批中 **1 批**不一致；**「票额 < 计划额且已收齐」这一类恰好 1 条**（其余 38 条是正常的部分收款，与短装无关）。

**判据是刻意还是漏考虑？** 查测试：`orderShipmentBatchService.test.ts` 只覆盖 `开票额 == 计划额`
的顺利路径，**短装场景完全没有用例** ⇒ 属**实现漏考虑的边界**，不是刻意口径。

**修法（最小且不回退）**：抽出零依赖真源 `settleBasisOf(计划额, 已开票额)`
＝ **已开票 ⇒ `min(计划额, 已开票额)`；未开票 ⇒ 计划额**。
- **只在短装时放宽**；溢装（开票 > 计划）取 `min` = 计划额，**与旧行为逐字节一致**；
  也避免合票时（`allocatedAmount` 缺省按发票全额计入）分母虚高导致永不结清。
- 同一判据原本散落两处（状态派生 + `serialize` 的进度/尾款余额）⇒ **收成一味真源**，
  否则会出现「状态已结清、页面仍显示未收 4,742.40」的自相矛盾。

**影响面核查**：`settleStatus` 唯一实质消费者是**催办扫描**（`dunningStageService:104`）；
门禁**不使用**它（同文件注释明写「进度只做展示不做门禁真源」）⇒ 本改动**不放开任何闸门**，只减少误催。

**验证**：干跑不一致 **1 → 0**；新增守卫 **11 例**（纯函数 5 + 集成 6，含阴性对照「只收一半不得判 settled」）；
**已证伪**（改回计划额 ⇒ 短装用例变红，还原后 34 例绿）；`shipping + finance + scheduler` **94 文件 / 1071 例全绿**。

## 6.2 撞出的口径分裂：`bankFee` 在付款侧与字段注释之间语义相反（**未修，需拍板**）

**事实（真库 + 代码双向取证）**：
- 101 条资金凭证中 **41 条填了银行手续费**（37 收款 / 4 付款，20~25 同币种），
  且这 41 条 `appliedAmount` **全部等于 `amount`**（即按全额核销）。
- `amount` 的 schema 注释是「凭证金额（实际入/出账金额，**已扣手续费前**）」⇒ 实收应为 `amount − bankFee`。
- 但 `pricing/profitSheetService.ts:271` 对**付款**凭证算杂费用的是
  `amount + bankFee`（把手续费当成 `amount` **之外**的额外支出）—— 与上面那句注释**相反**。
- **收款侧的 bankFee 全仓零消费**：grep 全部命中只有「报表字段 / API 提示 / 校验白名单 / 界面展示 / 付款侧杂费」，
  **没有任何地方**按 `amount − bankFee` 算实收、结汇或利润。
- 系统**没有费用承担方字段**（无 OUR/BEN/SHA）⇒ 无法表达「这笔手续费谁承担」。

**后果（口径级候选）**：若收款手续费由**卖方**承担（电汇 SHA/OUR 的常见情形），
则把手续费也算作已收 ⇒ **应收被提前结清、利润虚高**（每笔 20~25，系统性、静默）。
若由**买方**承担，则 `bankFee` 仅作记录，当前行为正确。

**未擅自改的理由**：这取决于**费用承担方**这一业务口径，且两种解释下 `amount` 的净/毛语义相反 ——
属于必须由业务方拍板的口径问题，我不猜。**建议**：① 增设费用承担方字段（OUR/BEN/SHA）；
② 明确 `amount` 是毛额还是净额，并让收款侧与付款侧用同一口径。

## 7.1 缺陷本体（两个洞，不止一个）

旧写法三件事**分散在事务内外**：`事务外 count+1 取号` → `事务外建审批单（payload 含号）` → `事务内落库`。

| # | 洞 | 后果 |
|---|---|---|
| ① | 取号 `count+1` 是**先读后写** | 并发读到同一 count → 同号 → 撞 `requestNumber` 唯一键 → **P2002，申请创建失败** |
| ② | 审批单在**事务外**先建且失败不回滚 | 落库回滚后**孤儿审批单**（审批台有单、业务单不存在） |

## 7.2 ★ 第一版修法被真库证伪（本轮最有价值的一条教训）

第一版按测试规格实现「**取号进事务 + 撞号换新号整体重试**」：
- 单测 **7/7 转绿**（假库能复现竞态，重试确实恢复）
- 但**真库 5 路并发实测：3 成功 / 2 失败（500）**，失败原因是「重试 3 次仍失败」

根因：`count+1` 不是「偶尔撞一次」，而是**并发下系统性同号** ——
重试者**又读到同一 count**，重新算出同一个号，3 次重试全部撞墙。

> ★ **教训**：**有界重试治标不治本**。当竞态的根因是「非原子读改写」时，
> 重试只是把失败概率降低，不会消除；**必须换成原子原语**。
> 而且——**单测全绿**完全掩盖了这一点（假库的竞态窗口比真库窄）。

## 8.5 bankFee 口径分裂 —— 决策材料（**真库取证**）

**代码事实**：`bankFee` 全仓**只有一个消费点** —— `profitSheetService.ts:286`
`杂费 = Σ付款凭证(type=Disbursement) (amount + bankFee)`；**收款侧零消费**。

**真库数据**（只读实测）：

| 侧 | 条数 | Σamount | ΣbankFee | 现状 |
|---|---|---|---|---|
| 收款 Receipt | 37 | 980,569.10 | **880.00**（USD 545 + EUR 335） | 核销**按毛额**（`applied == amount`）37/37 ⇒ 手续费**被静默忽略** |
| 付款 Disbursement | 4 | 396,396.80 | 60.00 CNY | 已计入成本（`amount + bankFee`） |

⇒ **同一笔手续费，两侧方向相反**：付款侧加成本、收款侧不减收入。影响 **36 个订单 / 37 张发票**。

**⚠️ 取证能证明什么、不能证明什么（本段 2026-09-19 晚**自我更正**）**

初稿我写「**决定性取证**：`凭证额 = 发票额 − 手续费` 命中 0 条 ⇒ 手续费是另计收费」——
**这条推理不成立**。那 37 条的手续费**全是固定值 20.00 / 25.00**（两批），
说明数据是**脚本生成的合成夹具**；它只能证明「手续费被存成了**独立字段**」（这是 schema 设计），
**证不了真实银行是「从款里扣」还是「另计收」**。⇒ 该结论**降级为「待业务确认」**。

**代码层面能确定的（与数据无关）**：`bankFee` 全仓**只有 1 个消费点**（付款侧 `amount + bankFee`），
**收款侧零消费** —— 即**无论采哪种口径，收款侧的手续费目前都不产生任何影响**。
这才是真正要修的那一条。

**两种口径下「收款侧正确做法」分别是**：

| 口径 | 含义 | 收款侧正确做法 |
|---|---|---|
| **(甲) 从款里扣**（BEN） | 客户汇款 X，银行扣走 F，我方实收 X−F | 核销额应为 `amount − bankFee`（否则**多计收入**） |
| **(乙) 另计收费**（SHA/OUR） | 客户付全额，银行另向我方收 F | 核销按 `amount` ✓，但 F 须**单列成本**（否则**漏计成本**） |

⚠️ schema 注释 `amount` = 「实际入/出账金额，**已扣手续费前**」读起来像 (甲)，
而付款侧的 `amount + bankFee` 读起来像 (乙) —— **注释与代码本身就矛盾**，
且系统**没有费用承担方字段**（无 OUR/BEN/SHA，无法表达「谁付手续费」）。
⇒ **必须业务拍板**，不能从数据推断。

**建议（供拍板）**：
1. **先修与口径无关的那条**：收款侧手续费必须有归宿（先堵住「静默无影响」）；
2. 增设 `feeBearer`（OUR/BEN/SHA）字段，明确手续费承担方；
3. 若定 (乙)：**手续费一律单列「银行手续费」成本项**（两侧一致），
   **不要**去改核销额（核销额改动会牵连账龄/授信/批次结清）；
4. 存量 41 条历史影响：Σ 880.00 / 60.00 —— **金额很小**（占比 0.09%），可不动存量、只修口径与后续单据。

> ⚠️ 数据来源为 `SIM-*` 种子夹具（手续费为固定值 20/25），**不是真实银行流水** ——
> 「另计收费」这个结论对**代码路径**成立，对**真实业务习惯**仍需业务确认。

## 12.2 ★ 发现我自己一条**弱断言**（且违反了本仓**已写明**的规则）

原来的「换货补发」断言只验「产物存在」。本批改成验**继承**时发现：

> 原票用的是 `shippingMethod: 'Sea'` / `type: 'Export'` —— **正好等于「无原票时的默认值」**
> ⇒ 即使继承**完全坏掉**（恒取默认），断言照样通过。**这是一条恒真的弱断言。**

**修法**：改用**非默认属性**的原票（`shippingMethod: 'Air'` + 自定义收货人）⇒ 能区分「真继承」与「取默认」。

```
✗ ★ 换货补发未继承原票属性 — shippingMethod=Sea（期望 Air）
```
还原（逐字节一致）+ 重启 → 转绿（28/0/0）。

> ★ **这条规则本仓 REFERENCE.md 早就写了**：
> 「`actual`（现值）与 `expected`（期望值）**必须来源不同** —— 同一个来源 = 检查恒真 = 没写」。
> 我这次踩的正是它的一个变体：**期望值恰好等于「实现取默认值时的结果」**。
> ⇒ **判据**：写「继承/派生/默认兜底」类断言时，**输入必须取非默认值**，
> 否则断言无法区分「真的派生了」与「取了默认」。

## 15.7 ★ 部署链路的**第三个**盲区：增量跳过只比 `size` ⇒ 「同大小内容变更」**永久不部署**

审部署链路时发现（读 `scripts/ops-upload-webapp.sh` 的跳过逻辑）：

```bash
remote_size=$(awk -F'\t' -v k="$rel" '$1==k{print $2; exit}' "$MANIFEST_TABLE_FILE")
if [[ -n "$remote_size" ]]; then
  local_size=$(stat -f%z "$f" 2>/dev/null || stat -c%s "$f")
  if [[ "$local_size" == "$remote_size" ]]; then   # ★ 只比 size —— 没有 mtime、没有 hash
    echo "./$rel" >> "$DIFF_EXCLUDES_FILE"          # ⇒ 跳过打包
```

而服务端 manifest 端点（`/api/admin/webapp-manifest`）只返回 **`{ 路径: 字节数 }`**：
```ts
files[rel] = fs.statSync(path.join(dir, entry.name)).size;   // 只有 size，无从比对内容
```

⇒ **若某文件「内容变了、字节数没变」，它会被永久跳过，生产静默保持旧内容、且不报任何错。**
典型触发：SVG 里 `#fff` → `#000`（同长）、JSON 改一个同长字段、替换同长字符串。

**严重度：中低**（触发频率低、且多数变更落在 `assets/`（content-hash 命名，同名即同内容，天然安全）；
`index.html` 已显式永不跳过）—— **但它是「静默」的**，正是本仓最忌讳的那一类。

### 已做：把它**变成可发现**的（而不是盲改部署脚本）

新增到 `scripts/check-production-assets.mjs` 的**内容新鲜度比对**：
对**非 `assets/`** 的文件（≤1MB）取生产内容与本地逐字节比对 ⇒
**大小相同而内容不同 = 陈旧**，显式报警并给出「需手工重传该文件」。

**证伪（证明这个盲区真实存在、且检测器有效）**：把本地 `public/pwa-icon.svg` 做一次
**同字节数**的字符替换（571B → 571B），检测器立刻报：
```
✗ 陈旧：pwa-icon.svg（大小同为 571B，内容不同）
```
还原后回到 0 陈旧 ✓。

> ⚠️ **我没有改部署脚本**。改动它需要**真跑一次部署**才能验证，而部署是对生产的写操作
> ⇒ 盲改的风险大于收益。**建议的修法**（留给你/下一会话）：
> ① manifest 端点**增加 `hashes` 字段**（向后兼容：老客户端忽略新字段）
> ② 客户端**优先按 hash 比对**、manifest 无 hash 时**退回 size**（行为与现在一致）
> ③ 用本批的检测器在真部署后复核
