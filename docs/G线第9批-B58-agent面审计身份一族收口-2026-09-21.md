> 唯一权威基准：`docs/交付目标与验收标准-2026-09-20.md`（版本读文首，本批后 = **v2.31**）；数字唯一出处是它的 §9.1。

## 一、这批在解决什么（业务后果，不是代码形态）

agent（审批 → 提交）那条路上，**34 处**把 `'agent'` 当身份传下去。其中 32 处最终落进
`AuditLog.actorId`，而那一列在真库里有外键 → `UserAccount(id)`（`AuditLog_actorId_fkey`，
`ON DELETE RESTRICT`，本批只读复核仍在）。`UserAccount` 里**没有** `agent` / `unknown` / `api` 这三行。
⇒ 这 32 处不是"审计里名字不好看"，而是**审计那笔写必然失败、整条业务写入跟着回滚**：
用户和模型看到的是一句"数据库错误"，真相是有人把一个不存在的账号写进了身份列。
本批前只有 B50-1a/1b 踩到的 2 处修掉，其余 32 处一直在这片地面上（同族第三次现形）。

## 二、做法（一个来源、一个落点，不逐处抄字面量）

| 环节 | 改动 | 为什么是这里 |
|---|---|---|
| 唯一取值 | `audit/routeAudit.ts` 导出 `SYSTEM_AUDIT_ACTOR='system'` + `auditActorFrom(params)` | 历史哨兵 `api`/`unknown`/`agent` 都无账号行；`system` 是 seed 的"系统服务"。**"哪个字面量才是合法身份"此前被抄了 3 次**，收成一个导出 |
| 身份来源 | `toolDispatchRegistry.registerCommitTool`：`actorId: approval.requesterId \|\| SYSTEM_AUDIT_ACTOR` 放进 `CommitContext` | 审批请求人是**唯一有依据的真人**；registry 已经查了 `approvalRequest`，让 26 个 flow 各自再查一遍 = 同一个取值两份实现（本仓头号病）。同时删掉 `commitTransaction` 里那段自查 |
| 26 个 flow 站点 | `actorId: 'agent'` → `actorId: auditActorFrom(params)`（并给各 params 补 `actorId?: string`） | 落点不变、只换取值来源；`detail.source` 里 `agent:` 前缀一个字没动 ⇒ "来自 agent 面"这个事实仍可读 |
| 6 处直连工具 | `actorId: SYSTEM_AUDIT_ACTOR`（`finance.create_invoice` / `create_voucher` / `apply_voucher_to_invoice` / `relations.create` / `shipping.create_shipment` / `shipping.update_tracking_status`） | 它们的签名是 `registerTool` 的 `(prisma, input)`，`executeTool(prisma, call)` 这一层**根本没有 actor 参数** ⇒ 透传真人要改这条对外签名（新契约），按 D49 不在本批顺手做，立 **B63** |
| 2 处仅留痕 | 保留 `'agent'`（`appendShipmentEvent` → `ShipmentEvent.actorId`、`deductShipmentStockInTx` → `StockMovement.operator`） | 真库 `information_schema` 实测这两列**无外键**，是无关系约束的留痕列；把它们也"收敛成 system"反而会丢掉"这是 agent 生成的"这条信息 |
| B55 顺带 | `orders/orderLifecycleService.ts` 三处审计 `actorId: actorId \|\| 'api'` + 门禁 `actor` 兜底 → `SYSTEM_AUDIT_ACTOR` | `'api'` 同样无账号行，与本批同族（台账 B55 的审计腿） |

**按 D49 没做的事**：没有为"`actorId` 不许是字面量 `'agent'`"新增全仓棘轮/判据 —— 新形状先立账（B58 行 + B63），
判据形式等 M3 之后一并定；本批只交行为测试（下面 §三）。
