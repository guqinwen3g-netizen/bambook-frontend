# 开发管理 · 业务模型（Kevin 口述 · 2026-10-05 19:40）

> **本文是开发管理的设计依据**，优先级高于该模块的任何既有实现与文档。
> 顾问此前对 `source` 的理解（customer-sample / customer-colorcard / internal 三分法）**已被 Kevin 明确否定**。

> **2026-10-06 设计讨论补充（优先于下文旧写法）**：轮次是一批开发要求/打样安排，可派给任意数量的工厂；某轮某工厂的实体成果是大版本（如 `R1-A`）。无新实物的小修改使用点号小版本（如 `R1-A.1`），引用大版本的原实物，客户或内部需求方必须对小版本单独确认，不能继承大版本确认。客户确认由客户作出、业务员记录；内部开发由内部需求方确认、业务员记录。正式 QC 才在系统中发起任务并由 QC 提交报告；微信、电话等非正式沟通不建立 QC 任务或“无需复检”记录。转订单/生产必须指向准确且已确认的版本或小版本，不得静默回退到大版本。**数字档案转档**：版本正式 QC 通过后即可申请转为产品档案；是否获得客户/需求方确认不影响转档资格，QC 通过但客户未选用的版本仍可作为公司产品方案留档。开发人员从该版本详情发起“转为产品档案”，将版本规格、工厂来源和实物关联传给数字档案；档案岗位补齐档案资料，建档成功后档案编号和链接回到原版本。**样品 MVP 联动**：实物首次在开发版本下登记，保存后自动出现在样品管理中，双方关联同一条实物档案，不重复登记；每条样品记录必须登记数量和单位，同版本、同形态可有多件。米样按米计量，手织样与色样按“份”计量，剪下部分按寄出一份处理，不追踪余料面积。MVP 不增加“未入库/在途”等状态，也不扩展非必要例外流程。开发页的“寄样确认”动作一次完成业务操作：为准确版本选择实物并登记本次寄出数量；保存后样品管理自动生成/更新同一实物档案的出库记录并扣减对应剩余数量，无需样品管理员二次确认或在样品管理重复发起。寄样费用计入开发案并归属该案需求方案人。**试样通知及费用/财务交接**：每一轮对每一家工厂生成一份通知单；面料开发标题为“面料试样通知单”，服装开发标题为“服装开发通知单”，标题区分业务类型而不另设重复类型字段。创建工厂任务时复制当时的轮次共同要求，任务内容随后按工厂独立维护；改轮次共同要求不自动覆盖已创建任务，需要同步时由业务员逐厂更新并重新生成对应通知单。通知单携带本轮共同要求及对应工厂的完整打样要求、样品形态、数量和单位、要求完成日期及参考附件，不得用共同要求代替工厂差异要求。业务员在开发模块逐厂生成通知单并下载/打印，之后在线下自行发送；MVP 不记录发送状态、发送时间或回执。样品制作费按版本下每条样品登记行记录一笔总额，不拆分单件单价；每次寄样分别记录寄样费，开发案费用汇总由制作费与全部寄样费组成并归属需求方案人。全案费用补齐后，业务员从开发模块一次性发起财务操作；财务在财务模块接收并开票，票据及开票结果关联回原开发案，业务员在开发模块查看票据并据此向客户收款。

## 一、开发案的「由头」（立项原因）——多维分类，不是三分法

**Kevin 原话要点：**
> 「开发案的由头可以是各种各样的……我们内部要去开发呀，比如说我们负责服装业务的要求，
> 我们这边负责面料业务的去开发一个面料；或者我们客人过来找、客人来样来让我们开发，
> 或者客人单纯的想让我们去有一个方向上去开发。」

**⇒ 正确的分类是三层，且必须先分大类和发起方：**

| 层 | 取值 | 依据 |
|---|---|---|
| **① 大类：开发什么** | **面料** / **服装**（`type` 已有：fabric/garment/pp/trim） | 「首先一个大分类，这个 development 是开发某一个面料还是某一个服装，**这两个大类首先要搞清楚**」 |
| **② 发起方是谁** | **我方内部** / **客户要求** | 「再去去看它是**我们内部发起的这个开发**，还是说像是**客户要求的这个开发**」 |
| **③ 客户给的是什么** | **有明确来样**（＝去复刻） / **只给定参数方向**（＝我方设计） | 「他是**有明确来样的呢**，就是相当于我们去复刻嘛；还是说他是**只给定了参数方向**呢，让我们去这边去设计」 |
| ④ 其他 | Kevin：「还有其他的……也不太清楚」 | **⇒ 顾问需判断专业上还有哪些分类** |

**★ 修正记录**：`schema.prisma` 现值`source = customer-sample | customer-colorcard | internal`
**这把"大类"和"发起方"混进了同一个字段，且漏了"只给参数方向"这一类。** 必须重做分类。

## 二、轮次与版本 —— ★ 最容易被做错的一层

**Kevin 定调原话（★ 这是整个模型的地基）：**
> 「**但凡有这个开发版本，它必须要有对应一个实物样。**」
> 「假设你改了一个微调的参数，但又没有打实物样，但后续你就当成有两个版本了，
> 结果这两个版本都要**抢一件实物样**……因为这个实物样是要**给每一个版本都要封样**的，
> 相当于要有这个留样的，那到时候你就**两边都抢不过来了**。」

**⇒ ★ 修订后的核心结构：轮次 → 工厂设计版本 → 实物样品。**
- **轮次**承载一批共同的修改要求、目标和背景；同一轮可以交给多个工厂。
- **版本**是某轮某工厂产出的设计结果。服装每个大版本对应一件实体样衣；面料一个版本可包含多种实物形态。
- **实物样品**挂在版本下，记录样品形态、数量、仓库位置、封样和借寄状态。
- **小版本**是服装主版本下无新实物的调整记录，可供下游引用，但不重复占用实物或封样。

### 完整命名规则（★ Kevin 亲自举例确认）

| 记法 | 含义 | 有实物? |
|---|---|---|
| **R1-A** | 轮次 1，A 工厂打的样 | ✅ 大版本 |
| **R2-B** / **R2-C** | 轮次 2，B / C 工厂打的样 | ✅ 大版本 |
| **R4-A** | 轮次 4，A 工厂打的样 | ✅ 大版本 |
| **R4-A.1** | 在 R4-A 基础上加了个小需求/微调 | ❌ 小版本（有 remark 记录） |

**★ 「轮次」怎么算新（Kevin 亲自举例）：**
> 「第一轮我们给客户去打一批样，这一轮给了 **A、B、C 三个工厂**去试样，
> 出来就叫它 **R1 A、B、C 三种**。
> 第二轮，客户来了一些修改意见，我们从里面挑一个最相似的，
> 或者说 **B、C 两个工厂都挺相似**，那第二轮就有了 **R2 B、C**；
> 或者说**只有 A 是相似的**，那第二轮就只剩 **R2-A** 了。
> 然后客人可能确认了一个，比如 **R4-A**，也就是 A 工厂的**第四轮**打的这个样。
> 然后在 R4-A 的基础上，他又加了一个小需求，那就变成了 **R4-A.1**。」

**⇒ 轮次的语义：** 一轮 = 客户/内部给出一批修改要求 → 挑选相似版本 → 交给选中的工厂再打 → 每家工厂形成自己的设计版本。该轮要求是共享上下文，不代表整轮只有一个版本。
**⇒ 轮次号可以跳号**（R1 直接跳到 R4 允许，因为 A 工厂可能连做了四轮）。
**⇒ 一轮可以有多个版本（多工厂），也可以只有一个。**
**⇒ 小版本（.1）也能被下游引用**：「后续大货或者说其他的就根据他这个去下」。引用时必须指向准确小版本，且该小版本须单独确认。

### ★ 面料 vs 服装 是两套模型（19:45 追加 · Kevin 强调「一定要把两个模型全部搞清楚」）

**Kevin 原话（面料侧）：**
> 「面料的开发样品有多种多样，根据客户需求来的。
> 比如我们 R1 给了三家工厂，那就有 **R1-A、R1-B、R1-C**，
> 然后它**每家工厂又产出了多种样品**，
> 比如说**色样**（lab-dip）、**手织样**（handloom）、**米样**（yardage）……
> （`SampleBatch.sampleType` 现值：`lab-dip | handloom | yardage` 正是这三种）
> 这些都会有不同的样品。」

**Kevin 原话（服装侧）：**
> 「服装上样品比较简单，基本上就是**成衣的这一件**这种样品形式，
> 或者最多有比如**套装**这些形式。」

**★ 面料几乎不用「小版本」：**
> 「**面料上通常不会我不去打第二轮实物样**，直接让你做一个微调、口头让你调整。
> **面料上一般很少有口头的调整**，除非他要改个什么颜色的那种。
> **通常情况下，面料上是不存在再去 -1 或者 -1 这种情况的。**」

**⇒ 面料与服装的真实差异（★ 这决定要不要建两套模型）：**

| 维度 | **服装** | **面料** |
|---|---|---|
| 样品形态数| 1~2 种（成衣一件 / 套装） | **多种**（色样 / 手织样 / 米样…由客户需求定） |
| 一个「版本」含几件实物 | 每个成衣设计版本对应一件实体样衣（套装可作为一个样衣单元） | **一个版本可含多种形态的样** |
| 小版本（-1 微调） | **常用** | **几乎不用**（要改就重打样） |
| 关键标识 | 版本号 | **版本号 + 形态**（R1-A + 色样 / + 手织样 / + 米样） |

**⇒ 代码现状印证：**
`SampleBatch.sampleType` 表达的是实物样品形态；它本身不应兼任轮次或设计版本。
⇒ **轮次、工厂设计版本、实物样品需要独立记录并通过 ID 关联。**
⇒ 且有面料专属扩展字段（`dyeLotNo` 缸号 / `colorRating` 色差评级 / `sideDiff` / `endDiff` / `defectCauses` 疵点成因）
⇒ **这印证了 Kevin 的判断：面料是"一批多形态"，模型与服装不同。**

**⇒ ★ 已确认的关键决策：**
**面料一个工厂设计版本可挂多种形态的实物样**（R1-A 可同时有色样、手织样、米样）；成衣一个大版本对应一个实体样衣。

⇒ 由此产生两种建模方式：
| 方案 | 做法 | 风险 |
|---|---|---|
| **甲：两套模型** | 面料走「一批多形态」结构，成衣走「一件一版本」结构 | 干净，但两套逻辑要各自维护 |
| **乙：一套模型 + 字段区分** | 同一结构，用 `sampleType` 区分面料多形态 vs 成衣单件 | 省事，但**正如你说的"经常会搞混在一起"** |

**Kevin 倾向（已明确表态）：**
> 「我觉得可能做**两个模型**会保险一点，否则的话……**我实际观察会发现经常会搞混在一起，
> 最终在软件的不断自主开发过程当中**（出问题）。」

⇒ **★ 已确认按两种样品业务规则实现，并共享清晰的轮次、版本、实物关联层级。**

## 三、开发过程的本质

> 「无论是面料也好服装也好，**它的开发的本质就是**：
> 我们**朝着一个方向**，然后还有一些**参数**、还有一些**需求**，
> 然后去找**不同的供应商，一个或者多个**，**打一轮或者多轮**，
> 然后**样品**……然后样品也可以有多种形式。」

**⇒ 五个要素：方向 + 参数 + 需求 + 多个供应商 + 一轮或多轮打样。**

## 四、★★ 内部 QC 是客户确认的前置门禁（开发案内部的流转）

**Kevin 原话：**
> 「在去发起这个确认之前，**肯定是要先我们内部的 QC 要给样品要做 QC**，
> 就是要**先通过我们内部样品就是发起 QC**，
> 然后 **QC 通过了之后，我们再去发给甲方/开发提出需求的那个人，让他去确认这个版本能不能通过**。」

**⇒ 开发案内部的四步流转（★ 这是本模块的主干流程）：**

```
① 开发案打样（轮次 → 版本）
        ↓
② 内部 QC 检验   ← 面料QC / 服装QC 分开领任务、分开汇报
        ↓
③ 客户/需求方确认版本      ← 只能 QC 过了才发出去
        ↓
④ 确认 → 结案（结在某个版本上）
```

**⇒ QC 在开发管理里是「无头任务」的典型**（见总纲 §二之七）：
- **QC 任务从开发管理派发**（面料 QC 领面料任务，服装 QC 领服装任务）
- QC 在自己账号里检验、汇报
- **业务员在开发管理里能看到 QC 结果产生的最终状态**

## 五、★ 结案在「某个版本」上，且不只确认版本能用

> 「这个版本通过了嘛，那就是给他确认了，**这个案子理论上就算是结了**。
> 然后它这个结**主要是结在某一个版本上面**。」

> 「**不是说只有那个确认的那个版本有用**。
> 比如说我可能**确认的之前那个版本我觉得也挺好的**，
> 我这边有业务员或者我们公司的人**想把它也转成一个产品档案**，
> 就是后续**推给别的客户**也可能会用到，反正我们样品都做了，那也很正常。」

**⇒ 结论（★★ 推翻顾问此前的理解）：**
1. **结案 = 某一个版本被确认**（不是整个案子所有版本一起完）
2. **多个被确认的版本 → 可以各自转成产品档案**（一个案子可产出 N 个档案）
3. **转档案的粒度 = 版本级**（不是案子级）
4. **产品档案 = 一个具体的设计方案/参数**（Kevin：「它是一个具体的这么一个设计」），
   用来**推给别的客户**

**2026-10-06 补充：转档资格以正式 QC 通过为准，不要求客户/需求方已确认。**客户未确认或未选用不代表该设计没有产品档案价值；符合 QC 条件的版本仍可留作公司产品方案。

**⇒ 对代码的直接要求（顾问核实后发现的缺口）：**
`ProductAsset` 目前只有 `source`（枚举字符串）+ `sourceDetail`（**自由文本**「开发案号/名称…」），
**没有任何字段结构化指向「哪个案子的哪个轮次的哪个版本」**。
⇒ **同一案子转两个版本，档案分不出谁是谁；回查只能读字符串。必须补结构化来源。**

## 六、★★ 开发管理必须向外连的三条线

### 6.1 样品实物 → 仓库管理（实物与档案双身份）

> 「开发过程当中产生的实物样品，它既是我们开发管理当中产生的**版本**，
> 也就是相当于某一款设计、一种参数、一个档案，
> **它也是真正的一件实物**。所以这个涉及到实物，那就涉及到这个**仓库管理**，
> 所以我们会有**专门针对样品的这个仓库管理**。」

**⇒ 同一个「样品」有两个身份，必须同时存在且互联：**
| 身份 | 含义 |
|---|---|
| **档案身份** | 设计方案 / 参数 / 标样（可转产品档案） |
| **实物身份** | 仓库里真实存在的一件东西（有数量、有寄出记录） |

**⇒ 关键联动（Kevin 举的三个例子）：**
1. **寄出**：「在开发管理当中把这件样品寄出去了，寄给客人去使用了，
   那它的**库存实物当中肯定就没有了**」
2. **设为标样 / 转产品档案**：「应该**自动连接上那个实物**，
   把它那个实物也可以……**它就是相当于有这么一个物理的东西，它可以连得上**」
3. **实物消耗要回写**：寄出 = 实物出库

**⇒ 设计要求：样品必须有「实物身份 ↔ 档案身份」的双向可查。**

### 6.2 开发费用 → 财务开票 → 业务员追款 → 销账 → 案结案（★ 完整的业务流转）

**Kevin 原话（这是本项目第一次讲清的「专业业务流转」）：**
> 「开发过程当中产生的**财务费用**这一块，
> 就是要**连接到让财务当中去开票**。财务那边去开好对应的发票，
> 还有对应的金额、交易双方这些基础的资料。
> 之后**业务员针对这个开发案让他去收款**。」

> 「这就是相当于中间有一个**业务流转**——
> **要让转给财务去做票据上面的事情**，然后**反过来让业务员去追款**。」

> 「财务那边假如收到款了，**财务会自动去匹配**看看是哪一个金额。
> 如果说**把这个账销掉**的话，**业务员那边可以更明确地知道，
> 我这个开发案算是最终结案了**，因为这个款项最终也解决了。」

**⇒ ★ 完整闭环（开发案的「最终结案」与「版本结案」是两回事）：**

```
开发费用发生
   ↓ 发起
财务开票（交易双方、金额、基础资料）        ← 转交财务
   ↓
业务员追款                                ← 转回业务员
   ↓
客户打款 → 财务自动匹配 → 销账
   ↓
★ 财务销账 ⇒ 业务员明确知道「这个开发案最终结案了」
```

**⇒ 设计要求：开发费用模块必须能向财务发起开票，并接收销账回执作为「最终结案」依据。**
