# D7-① 米样转售：双侧**严格同事务**收口 · 完成回报

日期：2026-09-16　｜　批次：遗留项 ④（`createBillingItem` 事务化）

## 一、改前缺陷

`sampleLengthService.convertToResale` 走两段**各自独立**的事务：

```
step1 事务：样品侧扣减 + to_resale 流水 + 审计        ← 先提交
createBillingItem 事务：BillingItem(sourceType='Sample')  ← 再单独提交
```

任一侧失败就留下半成品。当时的实现是「失败时返回 `billingItem: null` + `warning`，
提示人工补建应收」—— 不静默，但**数据已经是脏的**。

还有一处更隐蔽的脆弱：`step1` 事务回调里 `return fail(...)` 是**正常返回**，
事务**照常提交**。当前所有 `return fail` 恰好都在写操作之前，所以无害；
但只要有人在写之后加一个 `return fail`，就会静默落脏数据。

## 二、改法

### 1. 新增 `createBillingItemInTx(tx, params)`（一律 throw）

`billingItemService.ts` 拆成两个函数，**刻意不合并**：

| 函数 | 语义 |
|---|---|
| `createBillingItemInTx(tx, params)` | 业务逻辑全在此；失败**一律 throw**（带 `__billingFail` + `code` + `httpStatus`） |
| `createBillingItem(params)` | 开事务 → 调 InTx → 把 throw **映射回 `Result`**（既有 HTTP 契约**不变**） |

**为什么不用 `opts.tx`（原计划的形态）**：在事务里「返回 `ok:false` 让调用方自己判断」
是个陷阱 —— 调用方一旦忘了看返回值，外层事务就照常提交出半成品。
`throw` 天然把外层事务带崩。拆成两个函数后各自语义单一，**不可能误用**。

### 2. `convertToResale` 改为单一事务

样品侧扣减 + 流水 + 审计 + `createBillingItemInTx(tx, …)` 全在**同一个** `$transaction` 内；
事务内失败路径全部改用 `throwFail`（不再 `return fail`）。
外层 `catch` 同时识别 `__convertFail | __billingFail`，**透传内层具体 code**
（保留 `COST_ALREADY_BILLED` 这类诊断，不糊成 500）。

`warning` 字段保留但恒为 `null` —— 同事务后已无「半成品」语义，契约不破（前端零消费该端点，实测无依赖）。

## 四、后续项（本次**未**改，已核实非活跃 bug）

`convertToBulk` 事务回调里同样存在 `return fail(...)` 的脆弱模式。
已逐条核实**当前不可达**为真 bug：

- `ITEM_NOT_FOUND` / `NO_WAREHOUSE` 都在任何写之前返回；
- `UNIT_MISMATCH` 唯一可能的位置在自建库存项之后，但自建项的 `unit` 直接复制 `sample.lengthUnit`
  → 对自建项永不触发（既有单测之所以没暴露，是因为它用的是**已存在**且单位为 `YD` 的库存项）。

即：**没有活跃缺陷**，但模式脆弱 —— 若日后有人改动自建分支的单位来源、或在写之后新增校验，
就会静默留下孤儿库存项。建议与「事务内失败一律 throw」的纪律一并收口（无行为变化，
故当前写不出会转红的测试，不宜作为「已验证」的改动混入本批）。
