# T7-2 · ③三单一致核对 —— 定向现状核准（2026-09-16）

> 章程要求：实现前先定向现状核准。**本文只做核准 + 提方案，未动代码。**
> 口径 C 已拍板：「比金额 + 数量 + 品名，不一致**只预警**不阻断」。
> **但核准发现：口径 C 的字面要求在系统当前数据模型下无法直接落地**——三单的字段能力不对等，
> 且真库数据印证了这一点。需要重新定义「比什么用什么数据源」，见 §四。

## 一、三单在系统里的真实载体

| 单据 | 模型 | 关联锚点 | 金额 | 数量 | 品名 |
|---|---|---|---|---|---|
| **装箱单** | `TradeDocument(type='PackingList')`（`schema.prisma:5886`） | `shipmentId` | `totalAmount` 字段**存在** | ✗ **无行明细** | ✗ |
| **商业发票** | `TradeDocument(type='CommercialInvoice')` + `sourceInvoiceId` 回链财务 `Invoice`（`:5903-5905`） | `shipmentId` | `totalAmount`；**真源 = `Invoice.amount`**（2026-08-21 架构裁决「财务 Invoice 为商业发票唯一真源」） | ✗ `InvoiceLine` 只有 `amount/currency/description`，**无 quantity**（`:2566-2579`） | 半有（`InvoiceLine.description`） |
| **报关单** | `CustomsDeclaration` + `CustomsDeclarationLine[]`（`:5652-5737`） | `shipmentId` | `totalValue` / 行 `totalAmount` | ✓ 行 `quantity` + `unit` | ✓ 行 `productName` + `hsCode` |

**结论**：**只有报关单有完整的行级明细**。箱单在系统里只是「号码 + 状态 + 日期 + 金额(空)」的**登记**，
内容（件数/重量/体积）**一个字段都没有**；发票侧的行级明细（`InvoiceLine`）也**没有数量**。

## 二、真库证据（`panda_hub_local`，2026-09-16 实测）

```
TradeDocument 按 type：
  CommercialInvoice   n=48   withShipment=48   withAmount=48     ← 金额齐
  PackingList         n=48   withShipment=48   withAmount=0      ← 48 张全无金额
  BillOfLading        n=48   withShipment=48   withAmount=0
报关单 48 张（全部 Released，如 SIM-CD-001…048）| 报关行 68 条
财务应收发票 51 张 | InvoiceLine 仅 1 条                          ← 发票行级明细基本没启用
装运行 86 条 | 逐箱 96 条                                          ← 数量/包装的真源在运单侧
```

两点关键：
1. **箱单 48 张的 `totalAmount` 全为空**——这不是数据缺失，而是**业务上装箱单本来就不该有金额**
   （装箱单是包装/数量清单，不是金额单据）。所以「三单比金额」对箱单**不适用**。
2. **`InvoiceLine` 只有 1 条**，且该表**无 quantity 字段**——发票侧比数量/品名**做不到**。

## 三、运单侧才是「数量/包装」的真源

箱单要表达的内容（件数、毛净重、体积、逐箱明细）在系统里落在**运单**上，而非 `TradeDocument`：

| 数据 | 真源 |
|---|---|
| 总件数 / 毛重 / 净重 / 体积 | `Shipment.totalPackages / grossWeight / netWeight / volume` |
| 装运行（品名 / 数量 / 单位 / 箱数 / HS） | `ShipmentLine`（`:3091`，含 `productName/quantity/unit/cartons/hsCode`） |
| 逐箱明细（箱号 / 尺寸 / 重量 / 体积） | `ShipmentCarton`（`:3259`）+ `ShipmentCartonItem`（箱内分配） |

## 四、口径 C 需要重新定义（**待拍板**）

按数据能力，可落地的「三单一致」实际是**两组比对**：

### 组 1 · 金额组：发票 ↔ 报关单
- 发票侧：`TradeDocument(CommercialInvoice).totalAmount`，或**回链的财务 `Invoice.amount`**（真源）
- 报关侧：`CustomsDeclaration.totalValue`（或行 `totalAmount` 合计）
- 比：金额 + 币种。**箱单不参与**（无金额，业务上也不该有）

### 组 2 · 数量/包装组：报关单 ↔ 运单（箱单的数据底座）
- 报关侧：`Σ CDLine.quantity`、`totalPackages`、`grossWeight`、`netWeight`
- 运单侧：`Σ ShipmentLine.quantity`、`Shipment.totalPackages`、`grossWeight`、`netWeight`
- 比：数量合计 + 件数 + 毛净重
- **品名**：`CDLine.productName` ↔ `ShipmentLine.productName`（两边都有品名，可逐行匹配）

### 可选 · 组 3 · 单号互链完整性
三单是否**都已生成且互相挂上同一 `shipmentId`**（真库 48 组全齐；缺单本身就该预警）。

## 五、❓ 待拍板（三个问题，答完即可开工）

1. **箱单侧的数量/包装，用「运单数据」对吗？**
   依据：`TradeDocument(PackingList)` 里没有任何件数/重量字段，箱单的内容真源本来就在运单
   （`Shipment` + `ShipmentLine` + `ShipmentCarton`）。
   - (a) 对，箱单侧就用运单数据（推荐——不新增字段、不改造，48 组真库数据现成可比）
   - (b) 不对，要在 `TradeDocument` 上补件数/毛净重字段（要迁移 + 补录，且与运单重复）
2. **发票侧是否只比金额（不比数量/品名）？**
   依据：`InvoiceLine` 无 quantity、真库只有 1 条行级明细。
   - (a) 只比金额 + 币种（推荐）
   - (b) 还要比品名，用 `InvoiceLine.description`（真库只有 1 条，实际比不出东西）
3. **比对范围就按 §四 的组 1 + 组 2（+ 可选组 3）吗？** 还是有其它必对项
   （如 HS 编码、原产国、目的国、贸易条款）？

## 六、实现预案（口径拍板后即可开工，规模：中）

- 新建只读服务 `server/src/customs/tripleDocumentConsistency.ts`：
  入参 `shipmentId`（锚点），产出 `TripleDocDiscrepancy[]`，**severity 恒为 `warning`**（口径 C：只预警）。
- 路由：`GET /api/v1/customs/shipments/:shipmentId/triple-consistency`（只读，`customs:read`）。
- 复用现有只读范式（与 `reconciliationService` 同风格：纯只读、Decimal 累加、同币种内比对）。
- 前端：运单详情或报关单详情就地展示差异清单（挂载点实现时定）。
- 测试：单测钉住"金额差 → warning 而非 critical"、"缺单 → 报缺"、"同币种内比对"。
