## 0. Verdict (one line)

**确认缺陷 (confirmed defect)** — constructed: the guard **does fail open** and the **soft delete
commits**, on a real Postgres transaction, using the real production function.

## 2. Is a throwing count reachable, and does something else in the same tx roll it back?

Engine: **PostgreSQL** (`schema.prisma:6 provider = "postgresql"`), Prisma **5.22.0**
(`prisma --version`, package.json pins `^5.10.2`). Probe DB: `panda_hub_local`,
PostgreSQL 16.13, `localhost:5432` (dev DB; production was **not** touched).

**This is the question that decides severity, so it was measured, not assumed**
(`/tmp/b14-work/pg-tx-probe.cjs`, every statement inside a tx that is force-rolled-back;
only session-local TEMP tables touched):

| Probe | Injected error | Next write inside the same tx | Result |
|---|---|---|---|
| **P-A** | DB/engine-level statement error (`SELECT count(*) FROM b14_no_such_table…`) | `INSERT INTO <temp>` | **WRITE THREW (P2010 → Postgres `25P02` "current transaction is aborted")** → tx unusable → rollback |
| **P-B** | Prisma **client-side** validation error (`tx.order.count({where:{__b14_bogus_field__:1}})`) | `INSERT INTO <temp>` | **WRITE SUCCEEDED**, read-back `[{c:2}]` → **tx fully usable** |

Consequences, stated precisely:

* **Neutralised class** — errors that reach Postgres and fail there: connection loss, statement
  timeout / `57014`, deadlock `40P01`, missing table/column at the DB level (`P2022`), and Prisma's
  own interactive-tx expiry (`P2028`). For all of these, **the very next statement
  (`tx.order.update` at `:192`) throws, Prisma rolls back, and the fail-open is harmless.**
  These are the *most frequent* real-world causes — which is exactly why "有依赖的订单被软删"
  must **not** be asserted as a routine occurrence.
* **Fatal class** — errors raised by the Prisma client *before* SQL is sent. Then the transaction
  is untouched (P-B), the guard sees `0`, the write succeeds, the callback returns normally
  (`:225`) and **Prisma commits**.
  Reachability of this class here is **structural, not theoretical**: `tx` is annotated `any`
  at `:163`, so *none* of the five `where` clauses is type-checked. A schema/client drift on any of
  those field names (rename/remove `Invoice.deletedAt`, `InvoiceOrderAllocation.orderId`, …) is a
  **runtime validation error instead of a compile error** → swallowed → permanently blind for that
  one model, while deletes keep "succeeding".
* Note the asymmetry the swallow creates: if the *model delegate itself* disappears
  (`tx.invoiceOrderAllocation` undefined), the TypeError is raised **while building the array**,
  i.e. outside the per-promise `.catch` → it propagates → rollback → fail-**closed** by accident.
  A rejected promise fails open; a synchronous TypeError does not. Confirmed as CASE 4 of the unit
  probe. So the current shape is neither uniformly safe nor uniformly fatal — it is *randomly*
  fail-open depending on where the error surfaces, which is itself the G3 violation.

## 3. Construction (what the guard actually does when a count throws)

### 3a. Unit probe, real production function, repo's own mock-prisma style
`/tmp/b14-work/b14-delete-guard.test.ts` + `/tmp/b14-work/vitest.config.ts`, run with the repo's
vitest 2.1.9 (root pinned to `/tmp/b14-work` so nothing is written into the repo; winston logger
mocked out and that mock asserted, because its transports use a relative `logs/` path).
The mock store models COMMIT/ROLLBACK: tx writes are staged and applied **only** if the
transaction callback returns — the same convention the repo's own
`orders/__tests__/orderLifecycleRoute.test.ts:61` uses (`$transaction: async fn => fn(tx)`).

```
✓ POSITIVE CONTROL: 2 live invoices, count OK -> refused, nothing persisted
✓ CASE 1: order HAS 2 invoices, invoice.count() THROWS -> guard passes, delete COMMITS
✓ CASE 2: each single thrower, one at a time
✓ CASE 3: invoice.count throws but a shipment exists -> still refused
✓ CASE 4: model object missing (sync TypeError) -> propagates, rollback
✓ CASE 5: no dependents + one count throws -> delete legitimately succeeds
Tests 8 passed (8)
CASE1 store: {"committed":true,"orderDeletedAt":"1789844342600",
              "invoicesStillLive":["INV_B14_1","INV_B14_2"],
              "auditActions":["unlink_quotation_conversion","delete_order"]}
```

i.e. the swallowed `0` reaches `:182`, the guard passes, and the **soft delete lands in the
committed store** with two live invoices left pointing at the deleted order, an audit row and the
quotation unlink also applied.

### 3b. End-to-end, real Postgres + real Prisma + the real production function
`/tmp/b14-work/b14-e2e.cjs`. Fault injected for real: a **Prisma client generated from a scratch
copy** of `schema.prisma` (`/tmp/b14-work/drift`, output `/tmp/b14-work/gen`) with
`Invoice.deletedAt` renamed — i.e. exactly the drift class `tx: any` fails to catch.
Fixture (order + one live invoice) is created **inside the same transaction** by raw SQL, the
transaction is ended with a sentinel throw, so **nothing persists**.
`prismaShim.$transaction = fn => fn(tx)` only replaces Prisma's commit switch; every statement is a
real statement on one real Postgres transaction.

```
MODE: drift
fixture live invoices for this order: 1
tx.invoice.count(...): THREW PrismaClientValidationError
deleteOrder -> ok = true | error = undefined
DB STATE INSIDE TX: [{"order_deleted_at":"1789844762365","live_invoices_after":"1","audit_rows":"1"}]
REPORT: {"apiSaidOk":true,"orderSoftDeletedInTx":true,"liveInvoicesAfter":"1","rolledBack":"yes (sentinel throw)"}
post-clean (expect all 0 => nothing persisted): { invoicesDeleted: 0, ordersDeleted: 0 }

MODE: control   (repo's own client, identical fixture)
tx.invoice.count(...): returned 1
deleteOrder -> ok = false | error = HAS_DEPENDENTS
DB STATE INSIDE TX: [{"order_deleted_at":null,"live_invoices_after":"1","audit_rows":"0"}]
```

**The assertion that matters, answered:** with an order that genuinely HAS a dependent and one
count call throwing, **the delete proceeds and the transaction reaches its normal return ⇒ it
commits.** The control proves the guard is otherwise correct (positive control), so this is not a
"nothing ever passes" artifact of the harness.

## 4. Why this is 确认缺陷 and not 确认无害 — and why it is still not "已发现数据丢失"

* 确认无害 would require either "the fail-open value never reaches a decision" (false — `:182`) or
  "an unavoidable later throw in the same tx rolls it back" (false — measured: P-B and §3b show the
  later statements run and land; only the *engine-error* subclass is rolled back, P-A).
* 无法构造 does not apply — it was constructed twice, once with the engine's real semantics.
* Not a data-loss claim, because:
  1. the subclass that survives to commit is the **client-side/drift** subclass, not the routine
     infra subclass (connection/timeout/deadlock ⇒ rollback, P-A);
  2. a read-only forensic sweep on `panda_hub_local` (`/tmp/b14-work/forensic.cjs`) found
     **1000 soft-deleted orders and 0 of them with a live dependent** across all five guarded
     relations (Invoice / InvoiceOrderAllocation / Shipment / ShipmentOrderAllocation /
     PaymentVoucher) — no observable past instance **on this dev DB**;
  3. production was not queried at all (and this doc forbids touching it).
* What is confirmed without qualification is the **G3 L-A violation itself** (`catch(() => 0)` on a
  guard path, continuing to write), now backed by construction instead of by shape alone — which is
  what §0.4 and G3 现状③ asked for. Suggested rewording of B14: 级别 **待验证 → 阻断候选（M0 修）**，
  描述改为"已构造确认：守卫在客户端侧错误下失败放行且删除提交；引擎侧错误因 PG 25P02 回滚而无害".
  Comparison with B6 ("① 是显示，③ 是数据") now holds: ③ is a data-path defect, confirmed.

## 5. Recommended fix (for the confirmed case) and blast radius

**Fix — one line each, five times: stop swallowing.**
```ts
// orderLifecycleService.ts:176-180 — drop `.catch(() => 0)`
const [invoiceCount, invoiceAllocCount, shipmentCount, shipmentAllocCount, voucherCount] =
  await Promise.all([
    tx.invoice.count({ where: { orderId, deletedAt: null } }),
    tx.invoiceOrderAllocation.count({ where: { orderId, deletedAt: null } }),
    tx.shipment.count({ where: { orderId, deletedAt: null } }),
    tx.shipmentOrderAllocation.count({ where: { orderId } }),
    tx.paymentVoucher.count({ where: { orderId, deletedAt: null } }),
  ]);
```
* Precedent inside this repo, same guard, correct shape: `orderChanges/orderChangeRequestService.ts:1110-1116`
  (its "fail-closed 依赖守卫 … 与 deleteOrder 五路校验同口径" — the sibling already does it without `.catch`).
* Then make the failure an *explicit, coded* refusal rather than an anonymous Prisma error, because
  `:229` (`if (e.code)`) currently forwards raw Prisma codes (`P2010`/`P2028`) as `error.code`
  — a drift failure would surface to the UI as a mystery code:
  `catch` the `Promise.all` and `throw Object.assign(new Error('依赖校验未完成，删除已阻止（请稍后重试或联系管理员）'),
  { code:'DEPENDENCY_CHECK_FAILED', statusCode:503 })` inside the tx callback so it rolls back.
* Maps that must learn the new code (they are hand-maintained duplicates — three of them):
  `OrderLifecycleErrorCode` union + `ORDER_LIFECYCLE_ERROR_HTTP_STATUS` (`:103-123`, the
  `Record<…>` that is compile-forced), `orders/route.ts:533` `statusCodeMap`,
  `orders/routeV2.ts:296` map, `orderServiceV2.ts:786-791` `codeMap`.
  Caveat worth fixing in passing: `HAS_DEPENDENTS` is **not** in the union nor in
  `ORDER_LIFECYCLE_ERROR_HTTP_STATUS` (it survives only because `e` is `any` at `:229` and
  `route.ts:533` carries its own copy) — do not assume the compile-forced map covers the delete path.
* Regression test to add with the fix: mock `tx.invoice.count` rejecting while the store holds a live
  invoice ⇒ expect `ok:false` + no `order.update` + no commit. The repo already has the healthy-path
  positives (`orders/__tests__/orderLifecycleRoute.test.ts:122-145`, three of the five routes) but
  **no error-injection case** — which is precisely why 阳性对照 alone never exposed this. Also covers
  the G5/R-rule "拒绝路径须有阳性对照" in the other direction.

**Blast radius — does fixing it break deletes that used to work?**
* **No legitimate delete changes behaviour.** Verified three ways: unit CASE 5 (no dependents + a
  throwing count → still succeeds *today*), unit POSITIVE CONTROL and §3b `MODE: control`
  (dependents present → refused today and after the fix), and the real-DB fixture runs.
* The **only** behaviour change is on the previously-blind path: a delete that would have quietly
  soft-deleted an order with live dependents now returns 5xx and writes nothing. On a dev/test DB
  that is the whole point (fail-closed + a visible error); if a transient infra error coincides
  with a user pressing 删除, that user now sees a retryable error instead of a silent success.
* No existing test asserts the fail-open (`grep mockRejected` across `orders`/`agent` tests: only
  audit/sync/tx-failure cases), so removing the catches breaks no current expectation.
* Unchanged: `HAS_DEPENDENTS` coverage stays 5-way, so **G4.4 缺口② (no `OrderShipmentBatch`) is NOT
  addressed by this fix** — separate item, still 待构造.
* Same-family sites to sweep in the same batch (L-A candidates found by
  `grep -rn "catch(() => 0)" server/src`, non-test): `orders/orderLineMutationService.ts:248`
  (`tx.entityLink.count` → 0 decides whether links are deactivated immediately before a **hard**
  `tx.orderLine.delete` at `:253` — same class, different object), `orderChanges/orderChangeRequestService.ts:303`,
  `exceptions/exceptionService.ts:233`, `agent/toolRegistry.ts:1080`. Display-only (L-B, not in scope):
  `devPanel/route.ts:60-61`, `agent/route.ts:43-46`.
* Follow-up that would upgrade this finding (not done here): the same read-only forensic query
  (`/tmp/b14-work/forensic.cjs`) run against **production** by whoever is allowed to, plus the
  G6-style guard script so the pattern cannot come back.

## 6. Explicitly not verified

1. **Production data**: nothing was read from or written to production; production DB was never
   connected to. The 0-inconsistency figure is for `panda_hub_local` (localhost dev) only.
2. **Real infra errors were proxied, not reproduced literally**: P-A used an engine-level statement
   error to stand in for connection loss / deadlock / statement timeout. All three abort the
   Postgres transaction the same way (P-A shows the mechanism), but no socket was actually severed
   and no concurrent deadlock was actually manufactured.
3. **The drift client is a stand-in for a future migration mistake**, not a bug present today:
   §1 confirms all five fields exist in the current schema. So "已发生的数据丢失" remains unproven
   and unclaimed.
4. **Prisma version parity with production unconfirmed** — `package.json` allows `^5.10.2`, local
   CLI reports `5.22.0`, and B3 (构建号未确认) is still open, so the committed build's exact Prisma
   version is unknown; aborted-tx semantics are a Postgres property (SQLSTATE 25P02) and stable
   across 5.x, but that is an inference, not a measurement, for the deployed build.
5. **The other 4 guards' behaviour under the drift class was constructed only for `invoice`**
   (§3b). The swallow shape is identical on all five lines, but only that one was run end-to-end.
