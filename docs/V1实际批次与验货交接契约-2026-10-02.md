# V1 实际批次与验货交接契约

状态：实际批次身份模型迁移9已提交并通过旧数据升级演练；API producer 正在实施。QC 覆盖与报告修订模型迁移10正在整理，尚无完成的原生闭环或验收。不能把模型或本文件登记为功能通过。

## 现有事实与依据

- `样品管理域设计.md §13.8` 的同开发案两工厂成果分别转成两个订单；这不是同订单两生产批次。
- 该文档 §14.1 已授权按订单行、工厂、实际稳定批次判断生产资格，拆批不继承批准，订单级状态只汇总。第4项明确验货、出运独立判定，不能用产前样放行替代大货验货，也不能给所有品类新增产前样要求。
- 当前 `ReleaseScope` 已有行、工厂、`productionBatchId`、数量、单位、规格与修订；实际生产批次尚无独立实体。`ProductionPlan` 是工序排产，`OrderShipmentBatch` 是财务出运计划，二者不能按名称替代实物批次。
- 当前 `QCAssignment` 只定位订单；`InspectionReport` 按订单与检验类型唯一。QC 完成写入 `INR__订单ID`，出运门禁消费整单 Final。`shipmentId` 可空字段本身不能证明批次覆盖。
- `ShipmentOrderAllocation` 的订单行与数量是真实实运分配依据，但没有实际生产范围关联。一次分两运单不证明两个批次分别验货。

## 实体与数据合同

实际批次采用受控的新实体 `ProductionBatch`，不另造第二套订单或样品。初建至少记录 `id、orderId、orderLineId、factoryRelationId、rangeStart、quantity、unit、revision、confirmedSourceType、confirmedSourceId、specSnapshot、sourceFingerprint、state、createdBy、createdAt、updatedAt`。这些值在事务内从当前真实订单行和允许的工厂关系读取、校验，不接受备注、名称或浏览器快照作为归属证据。数量定义受控生产范围，不能据此声称已生产、已入库或已发运。`rangeStart` 由服务器在当前有效分区的首个空隙中选定，使用订单行已有单位和至多四位小数；不套用客户出运容差。拆批子范围完整、连续、数量精确覆盖父范围；父范围退出当前适用集合，历史事实保留。当前有效分区不重叠、不超过真实订单行数量。

工厂选择遵守现有订单、确认来源与工厂的一致性合同。多工厂开发转单继续走各自真实成果和各自订单；不借本次批次模型放宽已通过的来源、客户、商品或工厂拒绝控制。

QC 的范围明确分为 `whole_order` 与 `production_batch`。新任务和报告保存由服务器冻结的范围快照：订单行、实际批次 ID、工厂、数量与单位、批次修订、真实规格/来源指纹。不适用产前样的合法批次仍能独立验货，不强制绑定 `PpSampleRelease`。复验产生新报告修订和前序引用，保留已批准报告；当前资格是投影。`totalUnits/sampleSize` 是验货或抽样计数，不能替代面料的米数、码数、重量等商业范围数量。

整单报告保留整单语义。新批准冻结实际覆盖的行、规格、数量和工厂；后续增加或修改的范围不能自动继承旧批准。历史无完整覆盖信息的报告保留并标明待核，不伪造当时批准范围。

实运分配新增范围关联清单，归属真实 `ShipmentOrderAllocation`；一条行分配可对应多个实际批次。每条关联保存实际批次、修订、分配数量、单位和来源依据。所有关联数量之和与实运行分配一致，同批次全部有效预留/发运不超可用量。取消只解除未执行预留或追加受控冲回，不删除已发运事实。不得用 `OrderShipmentBatch`、运单号、箱号或 notes 猜实际生产批次。

## API 草案与角色交接

1. `GET/POST /api/v1/production-batches/orders/:orderId/lines/:lineId`：读取或创建本行真实批次；创建体仅接受 `batchCode、quantity、unit、expectedLineFingerprint、requestKey`；版本、真实来源、受控规格与工厂由服务器读取，客户端不得覆盖。批号是业务可读标签，实际身份由服务器生成。当前 `OrderLine` 没有修改时间字段；不借用订单时间冒充行版本。GET 返回由真实订单客户/工厂/开发案和行来源/规格/数量/单位生成的范围依据指纹，写入时锁后重算核对，明确它不是单调时间版本。现有当前权限与父单 L2 每次重验。
2. `POST /api/v1/production-batches/:batchId/split`：提交 `expectedRevision、expectedLineFingerprint、requestKey、children[{batchCode,quantity}]`；在父单、订单行与批次锁内检查归属、数量及不重叠，追加拆批事件。未知结果只能核对或重放原参数与原键。
3. QC 指派与完成 API 增加明确 `coverage、productionBatchId、expectedBatchRevision`；任务、报告、范围快照和必需审计在同一事务。QC 与业务签署仍使用当前真实账号及现有分工，不引入自批或默认豁免。
4. 实运分配 API 增加 `productionBatchAllocations`；服务器读取真实批次和当前适用验货依据，对每个被运范围判断既有 Final 条件。订单汇总供展示，A 批合格不能放行 B 批；B 批待整改不能自动冻结无关的已合格 A 批。

现有整单操作继续明确显示整单覆盖。页面复用已有 BDS 控件、字段配方、错误与请求恢复方式，只增加真实范围选择和必要的覆盖信息；不重排整个页面或发明新的卡片风格。

## 进入实现与验收的条件

先核对当前生产、QC、分配与出运的事务锁顺序、权限真源及数量单位函数，再按独立所有权分段实现。迁移须加字段/实体保留旧历史，先在隔离的现存数据副本演练；不在共享或生产库直接试验。

真实 PG 和原生页面至少验证：同订单两实际批次的不同 QC 结果与独立出运；整行拆批旧批准失效；新范围数量/单位/工厂/规格冲突拒绝；无产前样适用品类仍按既有规则验货；复验保留原批准与报告；并发超量预留拒绝；未知回执原键恢复；任务、报告、附件、打印件、实运分配和角色切换中的范围一致。原有整单、私有附件、当前授权、源故障、审计回滚与出运控制全部保留。

实施顺序：先交付并验证中性批次身份与完整分区，再扩展现有 QC 覆盖与报告修订，随后把 SOA 实运分配与 ShipmentLine 实际库存数量准确对齐，最后补齐 BDS 页面与真实角色操作。原整单报告的当前补证入口与不可变复验历史一起实现。上述内容不算当前已实现能力，不以人工验收代替软件层补齐。

## QC 覆盖与报告修订字段合同

沿用 `QCAssignment` 与 `InspectionReport`。两者增加 `scopeType、scopeKey、productionBatchId、productionBatchRevision、scopeSnapshot、scopeFingerprint、requestKey、commandHash`。报告再增加 `revision、supersedesId、contentFingerprint`，唯一键改为订单、检验类型、实际范围与报告修订。批次标识使用单独字段，不嵌入检验类型、备注或运单号。旧记录只标为 `whole_order` 的第一修订，其覆盖快照仍空；迁移不补签、不补证、不改原业务列。

新指派必须在锁后从实际当前订单行/批次读取范围并冻结，实际指派人和请求键共同恢复未知回执。完成报告产生新的实际报告ID与修订，引用前序报告；原报告内容、客户/业务批准和签字保持可查。指派给A批的QC在任务读、报告计数、附件和打印件上均只获得A批授权；既有真实整单L2保持原合同。业务决定绑定实际报告ID、修订、内容与范围指纹，由原负责人或实际部门主管承担；不能用QC角色、请求体业务批准布尔或新复验内容复用旧签字。

旧整单初始写入选择器的内部形状需要与新四列唯一键同步；这一步只是存储兼容，不能据此声称最新修订消费或不可变复验已完成。后续原生完成、审批、当前资格及实运消费须统一读取适用范围的当前修订并重验范围。

## 实物入库与实运分配的执行合同（2026-10-02 收口）

当前批次模型只说明受控范围，不能冒充已生产或已入库。新增受控的 `ProductionStockReceipt` 保存实际登记入库的批次 ID/修订/完整范围快照与指纹、真实订单行、仓库、库存项、原 Inbound 流水、数量/单位、登记日期/凭据说明、登记人、请求键与冻结命令；库存项和入库流水仍沿用现有库存账。每笔入库独立库存项，按稳定身份关联，不能借同 SKU、批号名称、全订单 L11 入库或备注匹配。原中性批次的累计实物入库不能超过其受控数量；有实物入库后不允许用中性拆批改写原收货范围。此前未入库的历史订单保持既有兼容路径，不替历史补造入库事实。

`GET /api/v1/production-batches/:batchId/stock-receipts` 返回本批次当前真实范围、范围指纹和已登记入库及库存余额。`POST` 提交 `expectedBatchRevision、expectedScopeFingerprint、warehouseId、quantity、unit、movementDate、receiptReference、ownership、unitCost、currency、requestKey`。数量必须为 Decimal(18,4) 正十进制字符串，不隐式换算；成本允许显式未知 null，显式零保持零，币种与货权须明确，不套 CNY 或 Owned 默认。日期和凭据说明记录的是隔离测试中的合成实物观察，不代表真实工厂动作。实际后勤按现有 inventory:write、orders:read、账号状态、签名权限上限及当前订单 L2 执行；当前权限在 Source→Order→Lines→Batch→Warehouse 锁后重读。范围、库存项、原入库流水、不可变收货记录和必需审计同事务；原键重放只回原回执，参数变化409。入库事实不自动通过 QC、PP、客户确认、付款或生产阶段门禁。

既有 SOA POST/PATCH 增加 `requestKey、expectedAllocationUpdatedAt（修改时）、productionBatchAllocations[{productionBatchId,expectedRevision,expectedScopeFingerprint,stockReceiptId,plannedQty,actualQty,unit}]`。计划与实际分别精确匹配本条 SOA 数量；批次预留累计不超其受控数量，实际出运不超被关联收货的可用库存；更新不能静默丢掉既有物理范围关联。Source→排序 Order/Lines→排序 Batch→Shipment→SOA/SPA→Reports→Stock 的共同锁内重验当前权限、范围和数量；实际发运针对本票真实批次消费最新适用 Final，沿用 S/S、RC、LC、定金、运输字段、短装和受控例外合同，不为所有订单新增 PP 要求。装运行带出本票分配数量，不带出整行合同数量。发运库存准确扣原收货库存；取消未发运只释放预留，已发运追加原出库的反向流水并保留 SPA/scopeSnapshot/原收货/QC/审计历史。

本合同是实现与用例的依据，尚不代表 producer、实际库、页面、岗位闭环或 V1 验收通过。新增模型采用只增不改的迁移，须独立旧库升级、原业务数据保全和同版验证。

## 实际批次分配事务核心的执行补充

本段固定本轮实现口径，不声明独立 PG、HTTP、页面或出货闭环已经通过。复用现有 `ShipmentOrderAllocation` 和一条分配/一批次唯一的 `ShipmentProductionAllocation`（SPA），不新增模型，不删除旧关联。一个批次允许关联多笔原生收货和多个仓库：SPA 的 `scopeSnapshot` 存 `schemaVersion:1、allocationVersion、scopeType、scopeKey、scopeFingerprint、scopeSnapshot、receiptAllocations`。其中 `scopeSnapshot` 是当前真实批次覆盖快照；`receiptAllocations` 每项保存原收货 ID、原仓库/库存项/Inbound ID、收货数量/单位/批次修订/范围和命令指纹，以及本项计划与实际数量。空 `stockReceiptId` 只代表尚未实收的计划身份。同批次同收货 ID 或多个空身份不能重复。公开关联不带原入库成本或完整私有入库回执。

原 SOA POST 提交真实 `orderId、orderLineId、unit、requestKey` 和明确批次关联；PATCH 必须提交精确 BigInt 字符串 `expectedAllocationUpdatedAt` 与新 `requestKey`。原关联未提供时保留原来的受控清单，不用当前 GET 列表伪造“原提交命令”；此时修改数量或单位若不能与原关联精确匹配就拒绝。命令白名单拒绝未知字段，数量仅允许 Decimal(18,4) 非负十进制字符串，不接受 Number、指数、空白或舍入。null 明确未知，0 明确零；每项及整条分配至少有一项数量已知。SOA 已知计划/实际总量要求相应每项已知并精确求和，未知总量不得借部分已知项冒充确定合计。所有单位严格与真实订单行/批次一致，不隐式换算。

占用按最细收货身份计算：未发运的 reserved 项取 `max(plannedQty,actualQty)`，计划与实际不相加；其中一边为 null 时仅有另一边的已知占用，不能声称未知边已经为零。再把各身份的占用汇总到批次。计划在收货 A、实际在收货 B 时两份身份仍分别占用，必须显式调整原计划才解除 A 的占用，不能用批次聚合 max 吞掉它。shipped 项只计实际量。全批次累计不超受控数量；每笔原收货累计预留/已运不超原收货量，未发运的预留累计还须不超该原库存项当前 quantity 减 lockedQuantity。分配本身不创建收货、库存锁、出库、QC、PP 或已生产事实。

旧新混用在同一真实 Order/Line 锁内核查当前行及整单粒度的其他非 Cancelled SOA，其父 Shipment 必须未删除且未 Cancelled。原关联没有可验证的 SPA、完整版本审计与数量/来源对应时，只有原计划量和实际量均明确为 Decimal 零才可排除；null 或缺失不是零，其他情况 409 提示先核对原分配物理来源，不做比例分摊或历史清洗。当前 PATCH 正在补绑定的同一原 SOA 排除自身，保留原记录恢复入口；其他旧 SOA 仍须核对。可验证 SPA 继续按原精确批次/收货计量，原键回放仍先返回其不可变回执，不以新出现的旧关联改变原命令结果。

来源锁采用一次完整多订单集合：实际开发/封样/样品/资产来源父项 → 排序 Orders → OrderLines/ReleaseScopes → 排序全部相关 ProductionBatch → Shipment → SOA/SPA → 原 ProductionStockReceipt → 排序 Warehouse → InventoryItem。当前票全部 SOA 及目标订单都先核可见性；锁后来源集合漂移 409，当前 active/未删除 User、实际 grants、签名 permissionCeiling（包括空数组）、orders:read、shipments:write 和所有父单 fresh L2 再读；库存等待完成后再核一次。写事务使用 ReadCommitted 以免锁等待后的撤权仍读取旧 MVCC 快照。分配阶段不消费报告批准；后续实际发运应在 SOA/SPA 后、库存前锁并核最新适用报告，保留既有 S/S、RC、LC、定金、运输、短装及例外规则。

实际量大于零必须有真实 `ProductionStockReceipt`。服务器核原命令/指纹、冻结 ACK、准确创建 mandatory AuditLog、真实原 Inbound，以及当前原库存项的订单、仓库、单位、物料、批号和货权归属。原收货冻结范围与当前批次须一致，来源变化不能借新请求静默继承。`Transferred` 原货权保留，不新增 Owned-only 政策。跨仓调拨产生的其他库存项没有本合同中的原收货承接锚，不能按同 SKU、数量或备注猜来源；需后续明确承接合同，本片拒绝自动替换。

新写仅允许 Draft/Booked/Loading，售后补发/返修真实 FK 运单使用独立售后合同。取消未发运 SOA 的 PATCH 只把原 reserved SPA 标 released，保留原数量、收货与快照并追加版本审计；已 released/shipped/reversed 行不原地复活或覆写。普通备注编辑也保存完整 before/after 版本。SOA 更新时间严格递增，同事务维护原 Shipment.orderId/businessLine 首条分配投影、既有订单行 Float 展示缓存和 mandatory 审计；Float 缓存不参与批次或库存的精确门禁。取消运单、已发运冲回、装运行数量与 scoped Final 的消费者仍是后续独立切片，不能用本片分配成功证明它们已闭环。

稳定 transactionId 为 `physical-allocation:` 加 SHA256 规范 JSON `{actorId,shipmentId,operation,requestKey}`，在 Shipment 锁下查精确原审计。operation 为 `create_physical_shipment_allocation` 或 `update_physical_shipment_allocation`。命令 hash 为规范 JSON `{operation,shipmentId,allocationId,actorId,command}` 的 SHA256：CREATE allocationId 为 null，PATCH 为实际原 SOA ID；command 是服务器白名单与十进制规范化后的原提交参数，保留 PATCH 缺省字段语义。规范 JSON 递归排序对象键，数组保持原序，BigInt/Decimal 使用准确字符串。

审计 after 冻结 schemaVersion、allocationVersion、主体/父项/请求键、完整原 command、commandHash、完整 ACK 和 ACKhash；before 保存原 SOA/全部 SPA/版本。成功 ACK 返回原 SOA 字段，加 `productionBatchAllocations、operation、actorId、allocationVersion、requestKey、commandHash、commandSnapshot、replayed`。原键同参数仅返回该原 ACK 并把 replayed 改 true，不以当前投影替代；同键改参、损坏审计或不连续历史 409。回放先于当前批次资格判断，但仍要求当前真实账号、权限上限和父项 L2。所有业务写与审计同事务，必需审计失败全回滚；没有原审计不是成功证明，400/409 也不是银行/系统此前未执行的通用证明。

`writePhysicalShipmentAllocation({prisma,shipmentId,allocationId?,actor,input,ip?,tx?})` 自有事务才返回安全 `{ok:false,error:{code,message,status}}`；外部 tx 必须抛出异常，调用者不得在已持 Shipment 锁后才调用并反向取得来源锁。`allocationRequiresPhysicalContract` 是当前账号与父单 L2 下的分发检测：目标、当前票其他 SOA 和 header 来源的任意历史 ProductionBatch 或本票既有 SPA 都不能降级旧链，不只检查当前 hint.orderId。它不替代写事务中相同父锁下的最终来源检测；旧内部 legacy writer 的现代来源拒绝边界及后续消费者需同版集成验证。

旧写共用 `lockLegacyShipmentAllocationWrite(tx,{shipmentId,allocationId?,orderId?,actor?})`：在原业务事务内按同一完整来源集合取得父锁和 Shipment 锁，重读来源集合后查任意历史 ProductionBatch/本票 SPA，存在即 409。HTTP 提供的 actor 仍必须过当前权限与上限/L2；未提供 actor 仅保留旧内部可信 scalar 调用接缝，不是 HTTP 免授权，也绝不能创建或修改现代 SPA。此锁内检查封住路由“尚无批次”检测与实际旧写之间并发新建批次的窗口；它不另开事务、不改变旧 QC/PP 业务政策。
