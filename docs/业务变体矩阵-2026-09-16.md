## 一、维度清单

### D1 运输方式

| 取值 | 现状 | 证据 |
|---|---|---|
| Sea / Air / Land / Rail / Courier | 🟡 字段存在，不驱动行为 | `schema.prisma:2954` `shippingMethod`；用途仅 `reporting/datasets.ts:186`（报表枚举）、`agent/toolRuntime.ts:6128`（必填校验）、`shipping/documentSetService.ts:397`（当字符串传出打印）、`shipping/shipmentStatsService.ts:143`（统计分组） |
| **整柜 FCL / 拼柜 LCL** | ❌ 未建模 | 枚举里没有；`agent/mcp/manifest.ts:537` 示例误写 `shippingMethod: 'FCL'`（示例本身是错的） |
| 空运特有：主单/分单（MAWB/HAWB） | ❓ 待确认是否需要 | `AirWaybill` 只作为单据类型存在（`customs/customsService.ts:218`），无主单/分单字段 |

**拍板口径（2026-09-16，Kevin）**：

1. **拼柜（LCL）常见，本轮要做「同柜多票/合票」**。
   ⚠️ 现有 `OrderShipmentBatch`（`schema.prisma:3120`）是**订单 ↔ 运单**的分配关系，
   语义是「一张订单分几票出」，**不是「多票合一柜」**。两者不可复用，需要新概念（柜/航次维度的聚合体）。
2. **运输方式驱动必填字段**：
   - `Sea` → 必填船名航次（`vesselOrFlight`/`voyageNumber`）；整柜另需集装箱号/封条号
   - `Air` → 必填航班号；**不需要**集装箱号/封条号
   - `Courier` → 必填跟踪号（`trackingNumber`）；**不需要**港口字段
   - `Land`/`Rail` → 必填承运方与车牌/车号（与 D4 拍板 3 的工厂侧承运信息同组字段）
   现状：**全部可选、无按方式校验**（`shippingMethod` 仅出现在必填校验之外的报表/统计/打印用途）。
3. **运输方式决定单据套**：`Sea` → B/L（`BillOfLading`）、`Air` → AWB（`AirWaybill`）、`Courier` → 无需提单。
   现状两种提单都在人工可创建列表里靠人选（`customs/customsService.ts:218,221` `MANUALLY_CREATABLE_DOC_TYPES`）。

**⚠️ 连带修正：FCL/LCL 不能塞进 `shippingMethod` 枚举。**
`agent/mcp/manifest.ts:537` 的示例写 `shippingMethod: 'FCL'`——**这个示例本身是错的**，
因为「整柜/拼柜」是**装载方式**，与「海运/空运」是**运输方式**，两个正交维度
（一票可以是 Sea + LCL，也可以是 Sea + FCL）。需新增独立的装载方式字段，并修正该示例。

### D2 贸易术语（Incoterms）

| 项 | 现状 | 证据 |
|---|---|---|
| 承载字段 | 🟡 自由文本，且只在报价/订单/报关单上，**运单上没有** | `schema.prisma:3939` `Quotation.deliveryTerms String?`（注释 `FOB Shanghai \| CIF ...`）；`Order.deliveryTerms`；`CustomsDeclaration.tradeTerms`；`Shipment` 模型（`schema.prisma:2946-3010`）无此字段 |
| 驱动行为 | 🟡 全服务端**只有一处**分支 | `shipping/documentSetService.ts:361-368`：`/CIF\|CIP/` → 认定卖方投保 → 按货值 ×1.1 推算投保金额，缺货值则报 missing |
| 价格口径 | 🟡 有 FOB/EXW 两个价格字段 | `schema.prisma:827-828` `fobPrice` / `exwPrice` |

**拍板口径（2026-09-16，Kevin）**：

1. **本轮只升 FOB / CIF 两组为枚举**（CFR 随 CIF 同组处理），其余术语（EXW / FCA / DAP / DDP）归入 `Other` + 自由文本，**只存不驱动**。
   → 避免范围炸开；升枚举是驱动行为的前提，自由文本永远驱动不了。
2. **四项行为全部要驱动**（这是本轮最重的一格）：
   - **运输责任划分**：FOB → 客户指定货代、我方不负责主运费；CIF → 我方订舱并付运费。**直接决定 D4 陆运段该不该建**。
   - **单据套要求**：CIF → 必须出保险单且投保金额按货值 ×1.1；FOB → 不要求。
     现状只做了金额推算（`documentSetService.ts:362`），**缺「CIF 无保险单则阻断」这道门**。
   - **报关一致性校验**：`CustomsDeclaration.tradeTerms` 必须与 `Order.deliveryTerms` 一致，不一致则拦或警告。现状两字段各写各的、零校验。
   - **费用归集口径**：FOB 下我方发生的陆运/进仓费计入**成本**；CIF 下运费计入**应收**。牵动毛利与报关 FOB 价口径。
3. **H12 建模到「订舱 + 陆运」两段**（不做截关提醒/货代仓签收确认那一层）：
   - 订舱段：订舱号 / 舱位确认 / SO 号 / 截关截单时间
   - 陆运段：约定运抵货代仓时间 / 实际送达 / 车牌司机（与 D4 拍板 3 的「工厂侧承运信息」是同一组字段，合并建模）

**❓ D2-Q4（核实后重写——我原先的前提是错的）**

我原先以为「归到 Shipment 费用字段」是轻量方案、进不了毛利。**核实结果相反**：

- `Shipment` 四类费用字段确实存在：`freightAmount/freightCurrency`（`schema.prisma:2979-2980`）、
  `insuranceAmount/insuranceCurrency`（`:2981-2982`）、`customsAmount/customsCurrency`（`:2983-2984`）、
  `otherCharges/otherChargesCurrency`（`:2985-2986`）。
- 它们**已经无条件聚合进订单毛利**：`OrderProfitSheet` 口径注释 `schema.prisma:4794`
  「运费 = Σ 运单（非 Cancelled）freight+insurance+customs+otherCharges」，
  实现在 `pricing/profitSheetService.ts:8`（口径声明）、`:150-156`（取全部非 Cancelled 运单，
  **没有任何 Incoterms 分支**）、`:211-214`（`buildProfitOverview` 折 CNY 汇总为 `freightCost` → `grossProfit`）。
  另有 `pricing/freightReestimate` 用同一真源做运费涨价模拟。

**所以真正的口径问题是两个方向的错账**：

1. **CIF 下毛利被低估**：CIF 的运费/保险费是我方**代客户垫付、应向客户收取**的，
   现状却和 FOB 一样一律计入 `freightCost` 当成本 → 收入端只有货款发票，成本端却背了全程运费。
2. **FOB 下毛利被高估**：FOB 我方仍会发生陆运费/进仓费（D4 拍板的主力路径），
   这些钱现状**没有任何采集入口**（H12 整段 ❌，陆运段不存在）→ 根本不进 `freightCost`，毛利虚高。

**拍板口径（2026-09-16，Kevin）**：**CIF 下我方垫付的运费/保险费不计入成本，改为向客户开一笔运费应收。**

连带影响（三条，都是真工作量）：

1. `pricing/profitSheetService.ts:150-156` 必须按 Incoterms 分支：CIF 运单的 `freightAmount/insuranceAmount`
   **不进 `freightCost`**；FOB 运单的照进（且要能被采集到，见 D4/H12）。
2. 需要一条「运费应收」开票路径：现状 `Invoice` 无费用类型区分（`schema.prisma:2407-2460`），
   要么加发票类型/行类型，要么允许一张运单对应一笔独立的运费发票并锚回 shipmentId（与 H14 的缺口同源）。
3. ⚠️ **已有订单毛利会变**：`OrderProfitSheet` 是 `orderId @unique` 幂等覆盖（`schema.prisma:4799`），
   改口径后重算即变数。上线前需对存量订单跑一次重算并留对照，不能静默改数字。

### D3 付款条件

| 项 | 现状 | 证据 |
|---|---|---|
| 枚举 | 🟡 存在，零行为分支 | `schema.prisma:2711` `paymentMethod String // TT \| LC \| OA \| DP \| DA \| Cash \| Other`；全部用途为凭证必填校验（`agent/paymentVoucherMutationFlow.ts:88`）、报表列（`reporting/datasets.ts:158`）、默认值（`paymentRequests/paymentRequestService.ts:328` `?? 'TT'`） |
| 账期 | 🟡 存着，不驱动门禁 | `schema.prisma:643` `paymentTermsDays`、`:3149` `finalPaymentDueDays`（尾款账期，注释说 watchdog 按此扫描） |

| 付款条款文本 | 🟡 自由文本 | `schema.prisma:3940` `paymentTerms String? // T/T 30% deposit ...` |

**核实补充（2026-09-16）**：

- `paymentTermsDays`（客户档案账期天数，`schema.prisma:643`）**全服务端只有写入、零读取**——
  仅 `crm/crmService.ts:92`（入参类型）与 `:879`（写库）两处命中。典型「写了没人读」。
- `Invoice.dueDate` **从不自动推导**：由调用方传入（`finance/sceneInvoiceService.ts:150`、
  PATCH 白名单 `finance/route.ts:100`、形式发票 `proformaInvoiceService.ts:185`）。
- ⚠️ **两个下游对「空 dueDate」的处理相反**（v0.1 只写了报表那一半，并把结论说过头了）：
  - **账龄 / 今日动作清单**：dueDate 为空时**回退 `issueDate`**（`finance/reportService.ts:96`、`:623`，口径声明 `:7`、`:533`）→ 一张没填到期日的发票**当天就落进逾期桶**（虚增逾期）。
  - **催款清单**：`daysOverdue = dueMs != null ? … : 0` 再 `filter(x => x.open > 0.005 && x.daysOverdue > 0)`（`finance/dunningService.ts:152-153`、`:163`）→ 空 dueDate **永远不进催收**（漏催）。
  ⇒ v0.1 那句「当天就进催收清单、直接产出错误的催款动作」**不成立**（催收恰好不收它）。真实缺陷是**同一张票报表判逾期、催款判正常**，属「多入口口径不一致」。**仍是必须修的错账**，只是错的方向与后果不同。

**拍板口径（2026-09-16，Kevin）**：

1. **L/C 做全套门禁**：
   - 订单确认时若 `paymentMethod='LC'` → **必须已登记信用证**，否则不得确认；
   - **装运前**核对 LC 条款：最迟装运期、有效期、金额溢短装 tolerance、单据要求；
   - 不符点（Discrepant）**阻断发运**，走 H11 例外放行（不另造一套例外机制）。
   → 现状全无；`LetterOfCredit` 模型完整（`schema.prisma:5705-5735`）且已能进单据套
   （`documentSetService.ts:379-384`），所以这是**接线活，不是建模活**。
2. **T/T 定金比例结构化 + 驱动放行门禁**：
   - 报价/订单上新增 `depositRatio` 数字字段（`paymentTerms` 自由文本保留，作为合同原文）；
   - **未收足定金 → 不得进入生产、不得发运**，接到 H11 现有门禁框架（`shipmentEligibilityGate`）里，
     不新建门禁系统。
   → 前提：自由文本里的比例系统读不出来，所以**结构化是不可绕过的前置步骤**。
3. **O/A 账期驱动到期日**：开票时按客户档案 `paymentTermsDays` 自动算 `Invoice.dueDate`（**允许手改**，
   手改后不被自动覆盖），让四阶段催收（`dunningService.ts`）与账龄五桶真正按合同账期跑。
   → 顺带消除上面那条「缺失 dueDate」的**双向**错账（报表虚增逾期 + 催款漏催），并让两处对空值口径一致。
   **本轮不做**超额授信联动（`creditExceptionGate.ts` 已存在，保持现状不扩范围）。

### D4 发货物理路径 —— ✅ **口径已拍板（2026-09-16），建模待做**

| 取值 | 现状 | 本轮定位 |

| 货代仓集货（拼柜） | ❌ 无概念 | 见 D1-Q1（拼柜是否常见，待答） |

**现状说明（事实依据）**：`Shipment` 有 `carrierRelationId`（货代/船公司，`schema.prisma:2989`）、`portOfLoading`、`bookingDate`，但**没有任何字段表达「这批货物理上从哪走、谁安排、是否进过仓」**。状态机是一条线性路径（`statusTransition.ts:29-38` Draft→Booked→Loading→Shipped→Arrived→Cleared→Delivered），所有物理路径共用。

**拍板口径（2026-09-16，Kevin）**：

1. **主力 = 工厂直发**。→ 建模重心在 **H12（放行 → 订舱 → 陆运 → 运抵货代仓）**，而不是 H8/H9（成品入库→扣库存）。
   H8/H9 仍要做，但按「次要路径」做，不追求 MES 级精度。
2. **「先进仓再发」必须联动库存**：出仓动作生成 `StockMovement(referenceType='Shipment')` 并扣减 `InventoryItem`；
   运单取消/改期需回滚。→ 这条接线的是 `StockMovement.referenceType`（`schema.prisma:5150` 枚举里**已含 `'Order'` 与 `'Shipment'`**，但 `referenceType:'Shipment'` **零写入方**）与 `InventoryItem.lockedQuantity`。
   ⚠️ **v0.1 说 lockedQuantity「零消费者」是错的**：Lock/Unlock 在服务层**已完整实现**（`inventory/inventoryService.ts:562-569` `case 'Lock'` 校验可锁定量、锁定不改 `quantity`；`:570-575` `case 'Unlock'`；Transfer 出库按 `quantity - lockedQuantity` 判可用 `:578-583`）。
   ⇒ 缺的不是机制，是**没有任何业务代码发起 Lock/Unlock**（目前只有通用手工流水端点调得到）。同理，扣库存的单一入口 `createStockMovement`（`:498`，带 CAS + `balanceBefore/After` + 审计）**已存在**，**严禁绕过它直改 `quantity`**。
   ⚠️ 前置依赖：成品要先在 `InventoryItem` 里有账（H8 入库段），否则无库存可扣——**所以 H8 不能因为「次要」而整段不做**。
3. **工厂直发要记工厂侧信息**：工厂发货日期 + 承运方 + 车牌/司机联系方式。
   用途：陆运费对账、货损追责、客户门户显示「已离厂」。

### D8 品类：面料 / 成衣 —— ⚠️ **我此前完全漏掉的一格（2026-09-16 由业务方纠正后补入）**

> 这不是一个次要维度。面料与成衣在**样品形态、开发流程、计量单位、大货形态、单据要求**上全线不同：
> 面料是米样/匹头样/船样、按米码计量、有匹号；成衣是产前样/大货样/尺码样、按件计量、有尺码配比。
> 一条不区分品类的主线，必然在其中一条上算错。

**已核实：区分在「前半程」存在，在「后半程」完全丢失**

**拍板口径（2026-09-16，Kevin）**：

**D8-Q1 → 面料与成衣同等重要，两条都必须交付。** 原话：

1. **不存在「先通一条」的选项**。任何只做面料或只做成衣的方案都不满足交付标准。
