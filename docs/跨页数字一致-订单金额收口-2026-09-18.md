# 跨页数字一致 —— 订单金额口径收口（2026-09-18）

> Kevin 痛点原话：**「跳来跳去，数字要一致」**
> 判据：**同一实体同一字段在不同视图是否一致**（不是「报价 vs 开票」那种不同概念的对比）

## 一、现象（真库实锤，非推演）

一张单 `SIM-SO-1054`：1800 件 × 11.75 = **21150**。走一次「改价」审批通过后：

| 视图 | 取值 | 显示 |
|---|---|---|
| 前端概览页 `Dashboard.tsx` | `quoteAmount` 裸用 | **18000** ✗ |
| 服务端驾驶舱 `dashboardService` | `contractAmount ?? quoteAmount` | 21150 |
| 四单勾稽 `reconciliationService` | `totalNet ?? quoteAmount` | 21150 |
| 出运批次 `orderShipmentBatchService` | `totalNet ?? quoteAmount` | 21150 |
| 季节 ROI `seasonService` | `contractAmount ?? quoteAmount` | 21150 |
| 订单详情 | `totalNet` | 21150 |

⇒ **1 : 5 分裂**。用户从概览页点进订单详情，同一个订单两个金额。

更严重的是**改数量**（`SIM-SO-1002` 实测）：

```
客户把 1500 件砍到 1200 件，改单审批通过后：
  主档 quantity   = 1200   ← 改了
  明细行 Σquantity = 1500   ← 没动
  金额            = 11325  ← 仍按 1500 件算
```
⇒ **客户要 1200 件，我们按 1500 件收钱。不报错，直接出错账。**

## 二、根因（两条，都是「收口点错位」）

### 根因 1：订单金额 5 个出口、3 组口径，没有真源

`quoteAmount` / `contractAmount` / `totalNet` / `totalActual` / Σ明细行 `netValue`，
四个模块各取各的，没人管谁是老大。

### 根因 2：改单只写主档一个字段，明细行与派生金额一律不动

`ORDER_FIELD_MAP`（`orderChangeRequestService.ts`）只把变更字段映射到 Order 单列，
`orderLine` 全程零写入 —— 数量、单价、金额全部留在旧值。

## 三、Kevin 拍板（2026-09-18）

1. **以明细行为准** —— 订单金额 = 明细行合计，主档金额由明细行派生，不手工填。
2. **跟着改，金额重算** —— 改数量/改价后明细行同步改、金额重算。

## 四、修法（收口，不逐点补）

### 4.1 唯一真源 `server/src/shared/orderAmount.ts`（零依赖纯函数）

取值次序即真源次序：① Σ明细行 `netValue` → ② `totalNet` → ③ `quoteAmount`。
兼容 `number` / 数字字符串 / **Prisma.Decimal**；非有限值返回 `null` 不用 0 兜底。
另提供 `findOrderAmountConflict()` 做「主档 vs 明细行」打架自检。

### 4.2 收编 6 个消费点（不是 5 个 —— 第 6 个是守卫上线后抓出来的）

| 文件 | 原口径 | 现在 |
|---|---|---|
| `dashboardService.ts` 销售额 ×2 | `contractAmount ?? quoteAmount` | `orderAmountOf` |
| `dashboardService.ts` 交付预警 | `contractAmount ?? quoteAmount` | `orderAmountOf` |
| `dashboardService.ts` **收入（毛利）** | `shipmentAmount ?? contractAmount ?? quoteAmount` | `shipmentAmount ?? orderAmountOf` |
| `seasonService.ts` ×2 | `contractAmount ?? quoteAmount` | `orderAmountOf` |
| `reconciliationService.ts` | `totalNet ?? quoteAmount` | `orderAmountOf`（转 Decimal 保下游语义） |
| `orderShipmentBatchService.ts` | `totalNet ?? quoteAmount` | 委托真源（保留同名包装不动调用点） |
| `components/Dashboard.tsx` ×4 | `quoteAmount` 裸用 | `orderAmountOf`（跨层引用零依赖纯函数） |

> ⓘ `dashboardService` 收入口径**保留** `shipmentAmount` 优先 —— 那是「收入确认以出运为准」的
> 业务语义，收编的是它的**回退链**，不是业务语义。

### 4.3 改单联动 `server/src/orderChanges/orderAmountRecalc.ts`

改数量 → 按各行原数量占比分摊（数量取整）+ 金额重算；
改价 → 目标总额反算单价 + 各行金额重算。
**尾差兜底在最后一行**，保证 Σ明细行 = 目标值（否则反过来破坏硬恒等）。
主档 `quantity` / `totalNet` / `contractAmount` / `quoteAmount` 全部由明细行派生同步；
**`totalActual` 不动**（它是出运实绩，改单改的是计划）。

## 六、踩到的坑（本轮）

1. **差点两次 cry wolf**（都排除了，没误报）：
   - `ORDER_FIELD_MAP.unitPrice → quoteAmount` 看着像「单价写进金额列」，
     实则 `afterDelta.unitPrice` 里装的是**总金额**（`case 'price'` 的 `afterAmount`），映射是对的，只是 key 名误导。
   - `FinanceManager.tsx` 用黑名单 `status ∉ {Paid,Cancelled,Draft}` 而非真源白名单，
     但在现有 5 个枚举值下**恰好等价**，不是 bug（脆弱但没错）。
2. **守卫第一版的正则是个空集**：写成 `contractAmount\s*\?\?\s*quoteAmount`，
   匹配不到真实写法 `num(o.contractAmount) ?? num(o.quoteAmount)` ⇒ 恒绿永不触发。
   放宽成 `contractAmount[^;\n]{0,30}\?\?[^;\n]{0,30}quoteAmount` 后**立刻抓出第 6 个漏网消费点**。
3. **走查脚本自己也会造口径**：初版脚本用 `quoteAmount` 代表「前端取值」，前端收编后脚本假红。
   ⇒ 改成**直接 import 生产同一份真源**，脚本不带第二套口径。
4. **单价精度与总额精确不可兼得**：`OrderLine.unitPrice` 是 `Decimal(18,4)`，
   反算单价存盘被截到 4 位 ⇒ `Σ(qty × 存盘单价)` 与 `ΣnetValue` 有分位残差（实测 0.03/行）。
   **选择总额精确优先**（总额是开票收款的依据），残差在测试里用显式容差承认，不掩盖。

## 七、未覆盖（诚实声明，不打折）

- 改单联动的验证是**函数级 + 真库事务**，**未走完整审批流**（创建申请 → 审批 → apply）。
  审批流端到端联动待补。
- 只收编了「订单**金额**」这一族。**数量**、**应收/已收**的跨页一致性尚未系统做
  （数量已确认恒等；应收真源 `openReceivable.ts` 已存在但**前端侧尚未收编**，前端仍是各自手写）。
- 演示库 69 单的 5 个金额出口**全部相等**（数据太干净），不能据此判断安全 ——
  故所有结论都靠**变异态**坐实，而不是靠现有数据。

### 8.4 这张表当场定下来的三件事

1. **"行为不变的机械合并"这条路不存在**：与真源取值集合完全相同的私有实现 **0 份**（最接近的 `MarketingManager`/`TrackAPanel` 是"无条件放到四位"，与真源"只在非零不足一分时放四位"对 `1305.1234` 一个给 `.1234` 一个给 `.12`）。⇒ 收口必然伴随可见变化，只能按档改口径，不能一把 sed。
2. **只有 A 档不是风格题**：收口前有 **4 份**把"没值/算不出"显示成 `0`（`crmRelationSections` `finance/DunningSheet` `finance/DunningStageBoardPanel` `finance/FinancePaymentRequestsPanel`）—— 催款额、收款申请额、CRM 额度那三格写着 `¥0.00` 时，屏面的意思是"这笔不欠"，而事实是"这笔没数"。这与台账最新那条空值红线（§9 月结对比"缺快照一律 null，不得回落 0"）同一条矩 ⇒ 本批只清这一档，已全部改走真源（现在这张表里 A 档 **0 份**）。
3. **其余各档是屏面口径题，不擅自动**：`码在后` 6 份（并过去会把 `1,234.00 USD` 挪成 `USD 1,234.00`）、`无币种` 4 份、`无空值守卫` 9 份、空值走 `null`/`空串`/`未填` 各 1 份、小数档不同 6 份、无千分位 2 份 ⇒ 这些改了会动使用方已经看惯的形状，属"要不要统一"的范围题，不属"这条读数在撒谎"。

### 8.5 本表未覆盖（照实）

- 尺按**函数名**认落点 ⇒ 换了别的名字（或直接内联 `toLocaleString` 不包函数）的金额渲染不在分母里。屏面侧的内联渲染已有另两把尺（`acceptance-report-export-collision` 那族与利润表小数位那一刀）各管一段，三者不互相覆盖。
- 档位是**读函数体**判出来的，不是跑出来的 ⇒ 它说"这份对空值没守卫"不等于"屏面此刻正在显示 NaN"；要下"某屏面某格现在写着什么"的结论，仍需按 B255 老规矩真点一次。
- 本批没动那 23 份里的任何一份（除 A 档 4 份），也没删任何私有函数 ⇒ 表是排期输入，不是交付清单。
- `services/` 扫描根本批命中 0 处（不是"那边也收好了"，是那边没有这种函数）。
