## 一、这批在解决什么（为什么它挡在 M3 前面）

B35 的病不是"演练数据会脏"，而是**我跑出来的验收数没有资格署这个分支的名**。
上一批（G-3/G-3b）把取证层建起来了（`scripts/lib/acceptance-selfcheck.mjs`：checkout / HEAD / 库 / 端口 / 脏工作树逐条取证，
取不到就判不可信），但**21 个验收与 e2e 脚本自己把主 checkout 的绝对路径写死在代码里**：

- `createRequire('/Users/…/apps/Bambook/server/')('@prisma/client')` —— **22 处**；
- `dotenv.config({ path: '/Users/…/apps/Bambook/server/.env.local' })` —— **2 处**（这一处更硬：连的是**主目录 env 所指的库**）。

⇒ 在本 worktree 里跑这些脚本，数据面与配置面其实来自 `main`，而读数会被记成"s0 分支验收通过"。
台账 B48 量的就是这个（原记 42 → 37 → 33 个文件，**本批复量见 §三**）。

## 二、做法（路径真源只留一处）

1. 自证层新增导出 **`SERVER_DIR = path.join(REPO_ROOT, 'server')`**（`REPO_ROOT` 由模块自身位置解析）；
   21 个脚本的 `createRequire(...)` 一律改成 `createRequire(SERVER_DIR + '/')` ⇒ 绝对路径从 22 处降到 **0**。
2. 新增导出 **`loadEnvForScript(root)`** —— env 的**唯一**装载口，内部复用既有 `readDbTarget`：
   取不到本仓 env 就抛 `ENV_MISSING`，**绝不回退去借别的 worktree**（与既有 `openLocalPrisma` 同一条政策，两处共用一份判断，
   不在脚本里重抄"哪个 env 算本仓的"）。2 个 dotenv 硬编码点改走它。
3. 注入方式按文件实际形状分两路，**不搞一种写法硬套**：有顶层 `import` 的 8 个文件加静态 import；
   其余 13 个（它们本来就在函数里 `await import('node:module')`）在同一处加动态 import ⇒ 共 14 个动态注入点。

## 四、★ 顺手量出来两件环境事实（比"改完 21 个脚本"更重要，M3 开跑前必须先解决）

1. **本 worktree 没有 `server/.env.local`**（只有 `.env.example`；主 checkout 有 20+ 个 env 文件）。
   ⇒ 迁移后这些脚本在这里**会拒绝运行**（正确，但意味着 M3 现在跑不了）。
   要么显式传 `DATABASE_URL=… node scripts/acceptance-x.mjs`（层里已支持且会打进横幅），要么在本仓放一份 env —— 后者是"造数据"级别的授权动作，**不自拍**。
2. **本 worktree 的 `server/node_modules` 是指向主 checkout 的符号链接**：
   `server/node_modules -> ../../Bambook/server/node_modules`（`ls -ld` 实测；`require.resolve('@prisma/client/package.json')` 落回主目录）。
   ⇒ 自证层能署名"哪个 checkout / 哪个 HEAD / 哪个库 / 哪个端口 / 工作树脏不脏"，
   **署不了"这个 Prisma Client 是由哪个 schema 生成出来的"**：`schema.prisma` 是本 worktree 的（有未提交的 1c 迁移），
   生成的 client 却是共享目录里那份 ⇒ 一旦两边字段/迁移不同，验收读数会**静默指向另一个 schema**。
   这正是 B35 想要的"有资格被信任"，现在还差这一条。
