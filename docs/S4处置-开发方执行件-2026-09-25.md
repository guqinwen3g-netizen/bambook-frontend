## 任务 1（P1）`parseTotals` 缺行**静默写 0** —— ★ 策略已定（22:5x）：**报错，不猜**

**位置**：`server/src/import/parsers/peerless.ts:85-92`

```ts
function parseTotals(text: string): { net: number; actual: number } {
  const n = text.match(RE_TOTAL_NET);   // /Tot\. net item val\. excl\. tax\s+[A-Z]{3}\s+([\d.,]+)/i
  const a = text.match(RE_ACTUAL);      // /Actual price\s+([\d.,]+)/i
  return {
    net:    n ? parseEuropeanNumber(n[1]) : 0,   // ← 匹配不到 = 0，不报错
    actual: a ? parseEuropeanNumber(a[1]) : 0,   // ← 同上
  };
}
```

**风险链**（读码可定）：
`RE_ACTUAL` 不命中 ⇒ `totalActual = 0`
⇒ `persistOrders.ts:285` `quoteAmount: parsed.totalActual ?? 0` ⇒ **写 0**
（★ `0 ?? 0` 仍是 `0`）
⇒ `persistOrders.ts:312` `contractAmount: parsed.totalActual ?? null` ⇒ **写 0**
（★ `0 ?? null` 仍是 `0` —— `??` 只挡 null/undefined，**挡不住 0**）
⇒ 而 `:301` `totalNet` 拿的是真实值 ⇒ **真源② 有值，A/C 组读出 0**。

**当前实测**：29 份真 PO **全部命中** `RE_ACTUAL` ⇒ **当前不触发**。
**缺口**：**没有任何用例覆盖"缺行"情形** ⇒ 这条静默兜底**从未被验证过**。

### ★ 策略：**(a) 明确报错** —— 且**不需要任何新机制**

**三条理由（全部读码可定）**：

1. ★★ **错误通道本来就有，是被 `: 0` 绕过的。**
   `parseOrderPdf.ts:14` 的文档注释原文：「**Errors are caught and surfaced via `error`
   field rather than thrown**」；`:32` 调 `parser(text)` 就在这个 try 里（`:34-41` 捕获 ⇒ `error`）。
   `import/route.ts:58-81` 再把 `error` **逐文件**返回前端（`:67` 与 `:75`）。
   ⇒ **只要 `parsePeerless` 抛，错误就自动一路到用户面前，零新增管道。**
   而现在的 `: 0` 让这条**专门为它设计**的通道**永远走不到**。
2. ★★ **同一个文件里已经是"缺必填就抛"**：`peerless.ts:96`
   `throw new Error('Peerless: PO block not found')`、`:98` 同理（Contact block）。
   ⇒ `parseTotals` 的 `: 0` 是**这条链上唯一的静默例外**。修法 = **让它与邻居一致**。
   旁证：`persistOrders.ts:63` 也抛（`poNumber is required`）。
3. ★ **"回退到 net" 是更危险的选项。** 29/29 真 PO 里 `totalNet ≡ totalActual`，
   所以回退**看起来**总对 —— 正因如此，一旦将来某份 PO 的 Actual price 行
   **因版式/OCR 变化而匹配不到**（而金额确实与 net 不同），回退会
   **静默写一个像真的错数**，比写 0 **更难发现**（0 刺眼，假数不刺眼）。
   本仓**已为这类"静默错数"付过代价**（`taxRefundCalcService.ts:19` 漏除 `/100` ⇒ 退税放大 100 倍）。
   ⇒ **不猜。**

### 动作（按此实施）

1. `parseTotals` 改为：**匹配不到就抛**。
   - ★ 文案要求：**中文、可执行、不给假结论**，例如
     「PO 解析失败：未找到「Actual price」行，无法确定成交金额 —— 请核对 PDF 或让供应商重新出具」
   - ★ **不要把正则原文/英文技术串抛给用户**（那是 B33/B36/B37 那一族：内部异常原文上屏）；
     正则细节放 `logger`，`message` 只给人话。
2. **不加**"回退到 net"的兜底。
3. ★ **同族一并处理**：`RE_TOTAL_NET` 缺失同样 `: 0` ⇒ **一并改抛**
   （同一个函数，**别只改一半**）。
4. 加一条**负向用例**（构造不含 `Actual price` 的文本）。

### 验收（可证伪）

  返回值里 `order` 不存在、`error` 是**中文人话**。

  **仍然全绿** ⇒ 证明没误伤。

> ★ **登记一处不一致（不在本任务范围）**：同文件 `:96`/`:98` 两处抛的是

## 任务 5（**P1**，新增）手动编辑路径与真源**不同步** —— 会持续制造分叉

### 可达路径（逐段读码追通，每段都有行号）

**用户在订单详情里改「销售单价」或「数量」⇒ `contractAmount` 变，而 `totalNet` / 明细行不变。**

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| 1 | UI 联动回算 | `components/OrderManager.tsx:889`（调用于 `:2478`） | `applyAmountLinkage`：patch 含 `salesPrice` ⇒ **`contractAmount = salesPrice × quantity`**；含 `quantity` ⇒ 同样重算。**只动 `contractAmount`/`salesPrice`，不动 `totalNet`** |
| 2 | 组装 patch | `OrderManager.tsx:1088` → `:1162` | `updatedOrder = { ...editForm }`；patch = **整个订单对象**（仅去掉 `id`/`lines`/`fieldSources`） |
| 3 | 发请求 | `services/importService.ts:121-135` | `PUT /v1/orders/:id` |
| 4 | 路由 | `server/src/orders/route.ts:430` | ★ **v1 路由**（`/api/v1/orders` → `createOrdersRouter`；`/api/v2/orders` 才是 `routeV2`） |
| 5 | 字段放行 | `route.ts:730-738` + `:746-838` | `stripReadonly` 按 `ORDER_WRITABLE_FIELDS` 过滤 —— **`quoteAmount`:753 · `totalNet`:769 · `totalActual`:770 · `salesPrice`:810 · `contractAmount`:811 全在集合内** |

**为什么必然分叉**：客户端把 `totalNet` **原值原样带回** ⇒ 落库后

⇒ **该路径只对「未批准订单」开放**。已批准订单走 `orderAmountRecalc`，那条**写全三字段** ⇒ 安全。
