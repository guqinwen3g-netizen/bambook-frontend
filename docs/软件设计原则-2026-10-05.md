## 2026-10-07 当前分工补充（优先于下文旧职责推论）

原口述内容保留追溯；后续已确认的职责以[对话决策总账](design/global/2026-10-06/08-2026-10-06-对话设计决策总账.md)和[角色与实际分工](design/global/2026-10-06/05-roles-and-responsibilities.md)为准。

- 模块是业务功能节点，不等于岗位/部门/独立账号。采购、加工、库存及样品管理通常由对应面料/成衣业务组业务员操作，不另设采购员、仓管员或样品管理员及相应资格层。
- QC负责专业检验；后勤单证接手出运交接，制作CI/PL并归档外部文件；财务登记业务已开的CI和供应商票据，处理收付款及核销。财务不制作业务CI。
- 业务员处理前段合同/通知单、开发CI、客户沟通和资料发送。后勤完成出运资料后回到业务员，由业务员对客跟进。
- 操作记录真实账号、来源对象和状态；现有协作权限不代表独立岗位，也不因默认经办归属而一概禁止必要协作。

## 一、核心定位：这是**贸易商**的系统，不是工厂的系统

- 公司主营：面料 / 成衣外贸。**采购 → 加工（供应商做）→ 卖给海外客户**，赚差价与加工费。
- **生产是供应商的事，不归本系统管。**
- 业务员**可以粗浅记一下**生产进度（不是必须，不是重点）。
- 假设未来有供应商端客户端，让供应商自己记 —— ★ **但目前没有开发计划**。
- **★ 当前范围：只做公司端内部员工系统。**

## 二、★ 组织模型：「车站 / 枢纽」——不是「流水线」

**这是 Kevin 亲自给的比喻，是整个软件的组织方式。**

> ⚠️ **2026-10-05 18:10 补充澄清（重要）**：Kevin 明确说「车站」只是**便于顾问理解的比喻**，  
> **不是真的像开车/发车，也不是卡死的一条路**。真实含义是：  
> **各站点之间相互关联、相互联动、相互转接；按实际业务过程推进，  
> 推进到哪里就在哪里继续经手；没到那一步也可以回到上一步继续优化调整 —— 这非常常见。**

- **订单管理（大货订单）是最大的一个"车站"、交叉最多的枢纽。**
- 但 **"不是所有事都从这个站点出发"**。
- 开发、质检、以及各种功能，**都是小岛 / 车站**；**它们四通八达，多维度多方向**。
- 每个车站**都可以开、都可以抵达**，**也能回退**。
- **★ 没有卡死的单向路径 —— 可进可退，可跳转可转接。**

**推论（待确认）：**

- 不能按"单一主线 + 分支"设计导航
- 不能强迫一笔业务从固定起点进入
- 每个模块/车站需要**自己的完整闭环**，且**允许回退到上一步重新处理**

## 二之二、★★ 订单站的定位：一站看全，但专业操作要转交

**Kevin 原话要点：**

> 「在整个订单管理，这是个大的站……从基础的产品，到整个订单，到后续的生产跟进、质量、样品、  
> 所有内容，到后续的票据、催款、回款，**理论上都是在订单管理当中一站看到所有的内容**，  
> 一目了然。我进行到什么阶段、完成了哪些、前面所有业务记录包括变更，一目了然。」

**但同时：**

> 「财务这件事、单据这件事，我们不会在订单板块里直接做，  
> 比如不会在订单管理中把发票直接开出来、或把收账直接记了、款项关联——  
> **这些东西需要跳转到其他界面，甚至其他角色去完成**。」

**⇒ 两条并存的设计原则（★★ 本软件最核心的结构判断）**

| #     | 原则                  | 含义                                                            |
| ----- | ------------------- | ------------------------------------------------------------- |
| **A** | **订单站是"一站看全"的汇总视图** | 业务员在一个页面能看到这单的全部：产品、订单、生产跟进、质量、样品、票据、催款、回款、变更历史。**明目了然、非常清晰** |
| **B** | **专业操作要转交给专业车站/角色** | 财务登记/核销、后勤出运单证、质检操作等**在对应专业模块完成**，要跳转到专业界面、交给专业角色               |

**★ 质检是这一原则最典型的例子**（Kevin 亲自举例）：

> 「质检很明显属于订单大货生产当中的一个环节，但它不是由业务员在订单环节自己操作完的，  
> 而是要**跳到一个更专业的质检工作台**上去完成。」

**⇒ 因此软件需要一种机制：转交（handoff）。** 见 §四之二。

## 二之五、★★★ 业务对象之间是「多对多的网」，不是流程环节（18:40 重大澄清）

**Kevin 明确纠正了顾问的错误提案**（顾问曾提议「把 11 个履约模块按一笔生意分组、标先后顺序」）。

> 「**绝对不可能按一笔生意去分组**，因为它不是连续的站点，就没有完全对应关系。  
> 一个**数字档案**可能对应无数个订单，一个订单里可能对应无数个产品，  
> 每个产品又可能拆成面料辅料，数字档案里可能也是不同档案组合起来的。」

> 「**面料有面料的业务逻辑，服装有服装的业务逻辑**，甚至有时候还会做一些其他的周边业务，  
> 它都有不同的业务逻辑存在的。所以你把它当做并列或者是串联，**那都是不对的**。」

**⇒ 核心结论（★ 本软件最反直觉、也最关键的一条）：**  
**业务对象之间是网（多对多），不是链。禁止把它们编成流程顺序或并排序列。**

**⇒ 同名概念的四种不同含义（以「样品」为例，顾问此前完全没意识到）：**

| 同一个"sample"                 | 实际含义                      | 归属逻辑   |
| --------------------------- | ------------------------- | ------ |
| 开发中的样品                      | 开发阶段产物                    | 开发业务逻辑 |
| 大货出的样品                      | 大货阶段产物                    | 大货业务逻辑 |
| 作为 **reference / standard** | 客户 confirm 的**参数规格 / 标准** | 规格权威   |
| 仓库里的实物                      | 实际物理库存                    | 仓储业务逻辑 |

**⇒ 推论（顾问待验证，不得擅自当结论）：**

- 「数字档案」不是流程的第 N 站
- 「样品」不是单一概念，可能至少要区分 4 种
- 按业务线（面料 / 成衣 / 周边）划分，逻辑是**分岔的**，不是一条主线

**⇒ 对导航的直接影响（待讨论）：**  
如果业务对象是网，那**侧栏按什么排**就不是一个"正确顺序"问题，  
而是要回答「**用户怎么最快找到他要的那个对象**」。

## 二之六、★★ 关系智库 / CRM / 供应商管理 的三层结构（18:40）

**Kevin 强调：「这两个是绝对不同的，千万不能混淆。」**

> 「关系智库里面**不仅仅有客户**，它里面好像有好几大类，所以它相当于你**手机里存的通讯录**。  
> 然后你会把**所有组织的基础信息**全部存上。  
> 包括后续你在任何一个业务环节当中要去填、要去调用的话，  
> 它相当于**数据联通，可以直接调用出来**。」

> 「关系 CRM 是**进一步的**，它会把里面**尤其是客户这一栏**去做更详细的记录和跟进，  
> 包括它会**以业务为导向**，你去主动发现商机也好、发现合作也好，这方面的记录。」

> 「还有**供应商管理**，那也是从关系智库里面的供应商，再去更加详细化、更加专业化地牵出来的一块板块。」

> 「在业务过程当中，主要是**客户这一块要单独去专业地记录，供应商这一块单独地记录**；  
> 剩下来一些其他组织这些东西都是留有基础的档案。」

**⇒ 三层结构（★ 顾问此前误以为"关系智库"与"CRM"是两个平级客户模块）：**

```
第一层｜关系智库（＝ 通讯录 / 组织主数据底座）
   · 包含【客户】【供应商】【其他所有组织】全部基础信息
   · 定位：全公司的组织主数据，任何业务环节可随时调用

第二层｜专业化深化（从底座按对象拉出）
   · CRM 客户管理   → 只针对【客户】做深度记录 + 业务导向跟进（商机/合作）
   · 供应商管理     → 只针对【供应商】做深度记录 + 专业化
   · 其余组织       → 只停留在底座的基础档案，不做专业化
```

**⇒ 第二重用途（★ 为 AI 铺路，Kevin 主动指出）：**

> 「尤其像**单据**当中，或者说后续假如加入 **Agent 操作**的时候，  
> 它会快速找到这些**联系人、黄页**，还有里面详细的地址、联系人，  
> 大概也可以智能提示你可以**一键输入进来**，就是有关联住。」

⇒ **关系智库是「单据自动填充」与「Agent 实体识别」的共同底座。**

## 二之七、★★★★ 业务 = 无数 component 的组合（18:50 根本澄清）

**Kevin 原话要点：**

> 「你一个业务当中，你是有**超级多 component** 组成的……  
> 它们综合起来就是整个的业务。」

**component 的三个尺度（★ 顾问此前完全以"模块/对象"为单位思考，这是错的尺度）：**

| 尺度                    | 例子                                                                           |
| --------------------- | ---------------------------------------------------------------------------- |
| **大 component**       | 产品档案 · 订单 · 发票单据 · 生产相关记录                                                    |
| **中 component**       | **交易方（★ 买卖多方）**：bill to / ship to / 客户 / 供应商 / 代理商（`commission to`）—— **四方** |
| **小 component（最小单元）** | 一次签字 · 一道审批 · 一份尺寸表 · 一份船样 · 面料船样 · 质检结论                                     |

**⇒ 关键更正（推翻顾问上一条记录的表述）：**  
**「关系智库是底座」这句话本身没错，错在说得像它是特殊的东西。**  
**每种 component 都有自己的底座 —— 关系智库只是「角色/组织信息」这一类 component 的底座。**  
**它和产品档案、订单、发票、生产记录、质检、船样、尺寸表一样，都是 component 之一。**

⇒ **★ 不存在"哪个是主、哪个是从"，它们平级，都是这盘棋上的部件。**

**⇒ ★★ 排列/组织的依据（Kevin 亲自给出，这是全软件的排序准则）：**

> 「只能按**在业务过程当中什么时候需要它**，什么时候就是要把它连上、要去给它串上、  
> 要去给它加上，从它那条通道或者这个数据……」

**解读（待确认）：**

- **不是**按"逻辑上它在第几步"
- **而是**按"我在业务过程的什么时候需要它"
- 导航与组织的单位**不是模块，而是「我要处理的业务」**
- 这与 §四之四「我的工作 = 今天要做的 + 逾期的 + 要催的 + 重要的 + 有问题的」直接相连  
  —— **"我的工作"就是「当前需要我串联的 component」**

## 二之八、★★★★★ 「串联」的正确含义：不是一页看全，是每页有推进线（18:55）

**Kevin 明确否掉了顾问此前的错误理解**（顾问曾问"要不要一个专门页面把所有 component 串起来"）：

> 「**不需要一个专门的页面**，因为这是最基础的业务流转当中的这么一个过程。  
> 我们这个完整的软件本身它就是串起来的，而**没有办法全部塞在一个界面里，那也太夸张了**。」

> 「它的**串联不是通过直接一步到位、一眼看到所有东西连在一起**。  
> 我不是在做 **Obsidian 这种可视化数据管理**之类的东西，**没有意义**。」

**⇒ ★★ 串联的正确机制：**

- **软件整体是串起来的**（模块与页面之间本来就有联系）
- **串联体现在每个页面内部有一条「推进线」**，点下去就往下走
- **不是**把几十个 component 铺在一页上
- 关联视图（页面下方的关联区块）**存在，但不是业务流转中最重要的**

**⇒ ★★ 每个业务页面都该有的骨架（★ 顾问从 Kevin 描述中提炼，待确认）：**

| #     | 骨架要素                | Kevin 的原话依据                                       |
| ----- | ------------------- | ------------------------------------------------- |
| **1** | **当前位置**            | 「你已经在推到了这个大货生产完成了」                                |
| **2** | **推进动作（点点推进，直觉）**   | 「非常 intuitive、非常 instructive，**点点就一直相当于感觉在往下推进**」 |
| **3** | **转交节点（★ 页面内显式存在）** | 「你**推到这儿了，接下来会转接给**比如说后勤这些人员去做下一步」                |
| **4** | **等待态（★ 一等状态）**     | 「然后**你这边是等**，那个专业负责质检的人他去做质检」                     |
| **5** | **回读结果**            | 「你再回来看的时候……**你可以看到这边的质检已经出结果了**」                  |
| **6** | **卡住分支**            | 「或者说你**被卡住了**，那你再去跟进这个供应商那边再去怎么做修复」               |
| **7** | **后续出口**            | 「最后可能有一些后续能够跳转的，比如索赔、回款、销账、利润计算」                  |

**⇒ 两条具体路径的形态（Kevin 举例）：**

**开发样路径**：新建开发样 → 按 intuitive 方式点点推进 → 开发完成  
→ 开发样收款 → **转产品档案** → **转大货订单**

**大货订单路径**：新建订单 → 进详情 → 一直跟进  
→ 推到"生产完成" → **发起质检**（转交 QC）→ **等**  
→ QC 在自己账户里出报告 → 回订单页看到结果 → 继续推进 / 或卡住后去催供应商修复  
→ 若遇发票、装箱、订舱等**超业务员范围**的事 ⇒ 发起 → 别人接手 → 回来看到结果 → 继续推进

**⇒ ★ 设计判据（提炼，待确认）：**  
**每个业务页面 = 一条能点着往前走的推进线 + 明确的转交点 + 可见的等待态。**  
**衡量一个页面设计得好不好 = 业务员能不能不离开这个页面就知道「现在到哪了、下一步做什么、要交给谁」。**

**⇒ 对现状的推论（顾问观察，待核实）：**  
189 个未提交改动里那个 Agent 正在做的审批流转 / 通知 / 回读，  
**本质上是这个"转交 + 等待 + 回读"机制的一个具体实例**（领导审批、质检派单）。  
⇒ **机制已在被建设，但散在各处，尚未抽象成可复用的页面骨架。**

## 二之九、★★★ 禁止「统一骨架」抽象（19:03 第三次纠正，★ 铁律）

**顾问的错误提案**：把上面那个 7 块骨架抽象成可复用组件，让所有模块共用。

**Kevin 直接否定：**

> 「应该是**单独的模块**吧，这里你**没有必要去复用什么统一架构**，  
> **没有意义**，因为它本身就是你**针对这个去设计的**、就**开发的这个模块去设计的**。」

> 「大货嘛，你**再单独大货这个模块**上去设计的。包括这后续，  
> 肯定有**大量的调整和针对性的改造**。你**非要用同一骨架，没有意义**。」

**⇒ ★★★ 铁律（本项目最反直觉的工程原则之一）：**  
**★ 不做跨模块的统一抽象 / 不做统一骨架 / 不强行复用。**  
**每个模块按它自己的业务逻辑、自己的操作方式、自己的参与者，单独设计。**

**⇒ 理由（顾问理解）：**

- 每个模块的业务语义不同 → 强行统一会把差异抹平
- 每个模块都会持续有针对性改造 → 统一抽象会变成所有人的负担
- **抽象要先有足够多的实例才成立，而这里实例本身还在变**（见§二之五：业务对象是网，不是链）

**⇒ 允许的共性只有"客观存在的事实"，不是"人为设计的模式"：**

- ★ **「等待」状态可以存在**（Kevin：「OK 的呀，也应该做的」）——  
  因为等待是业务的客观事实，不是设计出来的抽象
- 转交 / 回读 / 卡住 —— 若某模块客观需要就做，不为统一而做

**⇒ 顾问的方法论更正（★ 这才是根本）：**  
**不要问"这个模块该怎么排进某个统一框架"。**  
**要问的是：这个模块**存在什么意义、谁操作、怎么操作、怎么跟别的模块结合、  
以及它在完整业务里处于什么位&#x7F6E;**。**（见 §十 后续方法）\**

## 三、★ 没有全局的「完成」，只有每个车站各自的「完成」

> 原话大意：  
> 「每个车站都可以开、都可以抵达，但它一直不抵达，你也没办法代表它永远没有完成。  
> 比如他在样品开发完成了，那在**他这个岛**上就算结束了，但他没有去推进到大货出运。  
> 每个模块本身有它自己的完整。」

- **一笔业务可以永远停在某个车站**，不进入下游 —— 这是合法的完成状态，不是异常。
- **后续质量索赔等会把之前的记录再关联回来** —— 让"已完成"的记录重新活跃。  
  ⇒ **"是否完成"不是一个布尔值，而是"在某个车站上到达了某个状态"。**

**待确认：** 出运完成 vs 回款完成，是否算两个不同的"车站到达"？  
（Kevin 提到大货订单最终要追溯到**回款 / 发票 / 销账 / 核销**，但又说利润要等"钱全回来"才准。）

## 四、★ 设计目标：极致的直觉性（intuitive）

> 原话：「我们要把这个软件做得非常 intuitive，非常的直观直觉好用。」

**达成直觉的方式（Kevin 描述的路径）：**

1. 登录 → **「我的工作 / My Workspace」** 看到**所有内容与需要处理的事**
2. 从 Workspace 跟进**现有**业务
3. 要开新业务时，**从业务当前所处的环节直接进入**
   - 客户给了订单 → 直接进**订单管理**新建订单
   - 系统发现缺客户 / 缺供应商 → **提示去补全**
   - 发现缺产品信息 → **再去补全产品**
   - 产品也没有 → 先定一个**开发档案**；或**先建一个不完整的产品档案**（允许）

**★ 关键推论：**

- **「先建客户」不是强制前置** —— 熟手会自己先建，但系统不能依赖这个习惯
- **系统必须能"从任何环节进入"，并在缺东西时引导补全，而不是报错拒绝**
- **允许不完整的中间状态存在**（如"不完整的产品档案"）

## 五、起始路径不是固定的（Kevin 反复强调）

**很难说什么是明确的起点。** 已知的起始形态（他举例的）：

| 起点        | 说明                |
| --------- | ----------------- |
| **翻单**    | 客户已下过单，再来一次       |
| **找样**    | 客户来问能不能做（还没决定做不做） |
| **来样开发**  | 客户寄样，按样开发         |
| **按需求开发** | 无实物样，从需求开发        |
| **客户开发单** | 客户给规格/设计稿         |
| **直接下单**  | 规格已确认，直接下单        |

**★ 这条是本项目反复出问题的根源（写给未来的自己）：**

> 「没有意识到这个真的是一个综合的庞大的软件，而非跟随着某个既定程序一步一步推进运行，那样太过死板。」

**⇒ 禁止给线性流程模型让软件去适配。** 那样做出来的软件是死的。

## 六、★ 利润：只能在"钱全回来"之后才算准

- 公式：**利润 = 实际到账 − 综合成本**
- 成本范围：**订单上生产产生的 + 业务过程中产生的全部综合成本**
- **准确利润的时点：等整个结束、且在索赔之前的所有内容全部结束之后**
  - 即 **钱全回来** 才算得准
- （推论：利润是**事后**指标，不是实时指标。）

## 七、★ 软件的意义：门禁串联后自动得出结论

> 原话：「样品有没有确认、质检发起的质检有没有回复、这个过关了、领导那边有没有批准了、  
> 包括短装超装啊，还有这些其他的一些程序上的设定都通过之后，**那他就自然而然知道可以出运了**。」

- **软件的价值 = 把分散的门禁串联，自动得出「这单能不能走下一步」的结论。**
- 不是提供操作界面，而是**给出判断**。
- ⚠️ 待查证（未完成测绘）：现状是否已做到；出运时刻实际检查了哪几项、漏了哪几项。

## 四之二、★★ 转交（handoff）—— 业务在角色之间流转

**Kevin 原话（业务流程的流转经手转接）：**

> 「我这边有一些需要审批的、需要领导才能确认的，程序上要求卡在这边，  
> 那我就发起。领导那边批完之后，我这边就通过了，我就可以进行到下一步。」

> 「比如说我要派给 QC 去对我这边的样品或者大货做质检，审批通过那就**转到 QC 那边**。  
> QC 也可以看到——**他的『我的工作』这边多了这个派单**，然后他就会去处理。  
> 然后他把 QC 的结果回复过来，那我就可以去完成这边的跟进。  
> 业务员这边也都知道我这边申请的东西这边有回复了。」

**⇒ 转交是双向的，且每个人看到的不同但相互关联：**

| 角色      | 转交给他之后，他看到什么       | 他做完之后                 |
| ------- | ------------------ | --------------------- |
| **业务员** | 发起 → 等待中           | 收到回复，继续跟进             |
| **领导**  | 「我的工作」多了一条**待审批**  | 批准 / 驳回 / 修改后批准       |
| **QC**  | 「我的工作」多了一条**质检派单** | 回复质检结论（通过 / 不通过 + 报告） |

**★ 关键：转交产生的「回复」必须回到发起人的「我的工作」里**，形成闭环。  
**每个人看到的内容不同，但相互关联。**

**⇒ 软件需要的能力（★ 目前是否已有，待查证）：**

1. 任意两个角色之间的任务转交
2. 被转交者在自己的「我的工作」看到派单
3. 处理结果自动回到发起人的「我的工作」
4. 结果可能是：通过 / 不通过 / 修改后通过（三种都要能表达）

**流转中已明确存在的几种结果类型**（Kevin 列举）：

- 审批：通过 / 不通过 / 修改后通过
- 质检：通过 / 不通过
- 两者可以交叉：「质检通过但审批没通过」「审批通过但质检没通过」

## 四之三、★★ 团队可见性 —— 业务不是数据隔离的

**Kevin 原话要点：**

> 「我们这个团队，因为团队这个概念也是很重要的，  
> **不是说每个业务员都是独立处理他自己的业务，所有人都是相互隔离的。不是的。**  
> 比如说几个业务员，包括某个小组领导——**小组领导也是属于业务员范畴**，  
> 只是属于业务员当中权限高一点、管东西比较多的一个角色。  
> 反正我可能有团队都在跟进同一个事情。」

> 「我们对都在针对同一市场的某一个品牌客户，那我可能做女装、我可能做男装，  
> **那我们互相之间或许就是一个团队**，因为我们当中有些东西是可以互相帮忙、互相看、互相跟进的。」

**⇒ 三层可见性（待确认是否就是这三层）：**

| 层级     | 谁能看到                   | 依据              |
| ------ | ---------------------- | --------------- |
| **个人** | 只有自己经手的业务              | 本人              |
| **团队** | 同团队的成员**互相可见、可跟进、可帮忙** | 业务团队（销售/跟单销售团队） |
| **领导** | 管更多人的部分权限更高            | 角色              |

**★ 关键修正（这是顾问此前的错误认知）**：  
**「我的工作」不是纯个人待办列表**，它应该包含**团队可见的部分**——  
因为「互相看、互相跟进」是真实业务需要。

- 团队可见的范围，是"只读"还是也能"接手跟进"（转交）？
