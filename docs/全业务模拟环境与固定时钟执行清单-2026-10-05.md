## 固定时钟现状与风险

当前有局部固定时间 fixture，也有多个各自取宿主机时间的业务路径，二者还没有共享时钟服务。`server/src/shared/localDate.ts:1-33` 已规定 `Asia/Shanghai` 本地业务日为唯一日期键真源；但 `server/src/quotations/quotationService.ts:149-155,797-832` 以 `new Date()` 判报价失效并在读时写 `Expired`，`server/src/finance/reportService.ts:72-78,100-107` 默认按宿主机日期计算账龄，`components/ProductionBoard.tsx:53-60` 和 `components/QuotationManager.tsx:282-287` 也直接用浏览器时间算逾期/未回复天数。生产日期、CRM 跟进、库存、报价和财务过期/账龄路径仍需逐域盘点，不能一次性全局替换 `Date`。

`server/src/scheduler/schedulerService.ts:14-20,54-103` 以真实 `setInterval` 每 30 秒 tick，并在每次 tick 创建真实 `new Date()`；`server/src/scheduler/index.ts:48-106` 注册日常过期/交期/逾期提醒，也注册邮件自动同步、汇率和市场报价同步等外部/技术任务。很多业务扫描函数可传入 `today`，例如 `server/src/scheduler/tasks/quotationFollowUpWatchdog.ts:46-55`，但 scheduler 的 `ScheduledTask.run` 目前只接 Prisma，任务默认仍读 host clock。停住虚拟时钟时，现有提醒并不会自动跟着业务日推进；调用一次 `Date.now()` 或冻结系统时间也无法安全解决。

数据库中大量 `createdAt @default(now())`、`updatedAt @updatedAt` 默认使用真实数据库时间，例如 `server/prisma/schema.prisma:2023-2038,4214-4232` 的审批与审计记录。这些是记录落库/审计发生时间，必须保留真实时间。权限过期也必须保持真实时间，例如 `server/src/auth/permissionService.ts:119-125` 的 `expiresAt > new Date()` 与 `server/src/auth/accountStatusGuard.ts:32-35` 的缓存 TTL。JWT 有效期、密码/账号保护、网络 timeout、重试间隔、运行日志、调度器轮询节奏等也都不能随模拟时钟冻结。

## 推荐的隔离时钟方案

将模拟环境作为一个**独立后端进程、独立前端 endpoint、独立 PostgreSQL 数据库和独立应用账号**运行；优先单独本机 PostgreSQL cluster。若基础设施只能复用现有本地 cluster，模拟账号只能连接模拟库，不能继承访问现有业务库的权限。保留现有主环境与 first-batch 修复的进程、数据库和端口。不要把模拟库加到当前 active DB 全局指针，也不要改 `.env` 指向它来“临时用一下”。新进程必须带模拟模式标记，并同时核对 `NODE_ENV !== production`、本机/隔离测试主机、专用 `bambook_sim_*_dev` 数据库名前缀和模拟专用连接账号；任何一项缺失或不匹配都拒绝启动/写入。生产 build/server 即使收到模拟标记也必须 fail closed。

新增一个显式注入的时钟边界，不 monkey-patch `Date`、不改数据库/session 时钟：

- `realNow()` 继续服务身份安全、权限有效期、审计/记录落库时间、网络/重试/运行指标和 scheduler 的真实轮询。
- `businessNow()` 与 `businessToday(timeZone)` 只服务业务规则：交期/逾期、报价有效期、账龄、跟进/提醒、合同/证书/信用证/远期结汇到期、业务表单“今天”默认值、看板相对日期和报表默认 as-of。
- 对同一业务动作同时需要“发生时间”和“录入时间”的地方分开存证：`occurredAtBusiness`（模拟日历上的业务发生时点）与 `recordedAtReal`（真实系统接收/审计时点）。现有 `createdAt/updatedAt` 的含义先逐模型确认，不批量改写历史记录，也不把一项时间默认同时当两种事实。
- clock 状态只存在模拟库中，至少含 `scenarioId`、固定 `timeZone`、`currentBusinessInstant`、`seedVersion/hash`、`generation`、`clockVersion` 和真实 `updatedAtReal`。前端经模拟 API 读取并显著显示“模拟业务时点”；不能用本机系统时间冒充。
- clock 控制只在模拟 runtime 可用，绑定模拟管理权限，并记录不可覆盖的真实操作审计。支持以幂等 request key 显式 `advanceTo`/按步推进；推进应单调。回拨只允许显式 reset/reseed 新 generation，不允许把已有审批、收付或库存流水留在未来后再改小时间。推进失败要有可回读的任务状态与继续入口；重复推进/重试不重复业务副作用。
- scheduler 分出 `real` 与 `business` 任务。真实轮询/timeout/恢复仍由真实时间驱动；业务 watch tasks 收到 clock context，比较模拟日。每次业务时钟推进后提供一次明确的 catch-up tick；通知幂等键至少绑定模拟环境、generation、任务和业务日期。模拟模式禁用真实 SMTP/邮件同步、真实汇率/行情拉取和其他外部写操作，使用可核对的 sandbox adapter 或只读固定响应。

首次剧情建议从 `company-sim/common.ts` 已有 `2026-06-08` 至 `2026-08-30` 13 周时间线开始，业务当前点固定在场景清单中，不从 OS 时间生成。将业务 timezone 明确设为 `Asia/Shanghai`；现有 fixture 的 UTC date builder、各域的 date-only 字段与跨时区边界先对照校验，不能把 UTC 午夜不加审查地当中国业务日。初始固定时点具体到日期和时间后写入 scenario manifest；任何修改都应生成新 seedVersion，历史数据不静默漂移。

## 后续验收门禁

1. **目标库确认**：创建/seed/reset 前检查模拟模式开关、DB host、DB name 前缀、连接身份及 `current_database()`；日志只打印脱敏主机/库名/模式，不打印 URL/密码。生产端点、已用库或未知库必须拒绝。
2. **时间不漂移**：停留在同一模拟时点跨真实小时/日，重复获取页面、财务账龄和提醒列表；输出必须相同。真实登录/授权/超时的测试则通过等待真实时间而按既定安全策略变化。
3. **边界推进**：固定时点依次越过 quote `validUntil`、交期/应收账期、跟进日、工厂证书/信用证/外汇到期、样品/QC/生产期限；验证“前一刻、边界、后一刻”状态和通知，然后重复 tick 验幂等。
4. **双时间核对**：每个会改变业务事实的命令都能明确回答何时发生（business）和何时被系统记录（real）；身份安全期限与审计时间仍可证明真实发生，不以模拟时间伪造。
5. **重置/重放**：同 scenario manifest reset 两次，核对 ID、状态、事件链、账本和 source version/hash；允许运行审计的真实记录时间不同，但业务事实必须一致，并明确比较字段。
6. **闭环证据**：用页面、API 回读、数据库只读核验和操作审计联合证明；任何域缺业务凭证、权限或原生服务入口时作为缺口，不用直接写状态补成“完成”。

## 本轮未验证项

本轮没有启动/改动数据库或环境文件，没有运行 seed、acceptance batch、scheduler 或业务写入。PID `99165` 的 cwd 已读到当前 checkout，但页面实际内容、前后端 revision 对应关系、当前 API 返回的数据源、模拟库 schema/账目是否已有实例、外部连接是否可在隔离模式彻底关闭，均须在阶段 0/1 现场验证。
