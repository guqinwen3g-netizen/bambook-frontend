# H16-② 客户回执：内部侧查看（跨客户列表 + 对账面板第三视图）· 完成回报

日期：2026-09-16　｜　批次：遗留项 ③（H16-② 配套缺口）

## 一、缺的是什么

H16-② 只做了**客户门户**侧：客户能回签、内部收到一条通知。但通知一闪而过，
内部侧**没有任何入口**能看到「谁回签了 / 谁提了异议」——
回执落库之后就再没人看得到，等于把「对账函回签」做成了单向动作。

`reconciliationAckService` 里只有 `listAcks(relationId)`（**必须绑客户**），
全仓无人调用；也没有任何内部路由。

### 三个口径决定

1. **期间筛选用「区间相交」而非严格包含**（`periodStart <= periodTo ∧ periodEnd >= periodFrom`）：
   财务按「9 月」筛时，跨月对账单也应命中，否则要猜客户的账单边界。
2. **`summary` 统计不受 `status` 筛选影响**：一旦按「有异议」筛，若 summary 跟着走，
   「已确认」数就恒为 0，失去对照意义。故 summary 只受客户/期间筛选影响。
3. **列表放「对账」面板的第三个视图，不新开 tab**：回执本就是「对账的结果」，
   且面板已有 `view` 切换结构，插入点与既有 `list`/`fx` 同构，风险最小。

## 四、排查中发现的两件事

### 1. H16-② 的验收脚本会往真库留残留（已修）

复核零残留时发现真库有 **2 条已软删的回执 + 28 条孤儿通知**（期间均为 `2099-01`）。
按创建时间核对（12:35 UTC = 20:35 北京）确认**不是本次产生**，而是**上一轮 H16-② 验收脚本**
的残留：它的回滚只**软删回执**、**不清理通知**，而 `submitAck` 会给每个 active 用户各发一条
`ntf_cra_<ackId>_<userId>`（14 用户 → 每次跑留 14 条）。

已修：回滚改为「硬删回执 + 按 id 前缀删通知」，并把过时的「跑完软删」文案改成「跑完硬删」。
复跑确认 **14/14 通过且零残留**。

### 2. 清理了上述遗留残留

按精确 ID 列出并清理了那 2 条软删回执 + 28 条孤儿通知（期间 `2099-01-01~2099-01-31`，
明显为演练数据、且已软删）。清理后回执域回到 **0 条回执 / 0 条回执类通知**。
