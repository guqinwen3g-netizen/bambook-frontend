# 内部贸易实际成本核对契约

依据已确认 DR-005、DR-006、DR-007、DR-033：服装部成本包含已批准且双方确认的内部面料结算价；面料部内部收入来自内部供料单，不生成对外商业发票。公司报表抵销内部采购/销售，保留真实外部采购、加工及费用。此次记录实施合同；通过仍需固定源码真实 PG 与岗位页面验收。

## 原生供料事实

现有 `OrderInternalTransfer` 主单/镜像与 `memo` 承载 `schemaVersion:2`。主单属于服装订单 incoming，镜像属于面料订单 outgoing。新增冻结的双方稳定订单行 ID；旧客户端未传 ID 时仅允许两侧各有一个准确物料行，多个同码行必须显式选择。未知单位不推定；内部单位须匹配真实面料行。当前订单行 ID、物料、单位、数量全部进入价格版本。

创建审批、双向单据及必需创建审计在同一 Serializable 事务。审批目标为真实主单 ID，内容为完整 server 价格快照和 hash。批准必须准确 action/target/price content，并具有内核真实决定审计：有效主管或总领导、非自批、实际 actor、决定时间、内容 fingerprint 一致。`approved` 字符串或角色显示名称不能证明批准。生效时确认数量/交期须等于冻结版本；变化须重新提交，不能借旧批准改变正式金额。

写操作读取当前 active 且未软删除账号、数据库显式 `order:internal_trade:write`、可信凭证 ceiling、双方订单 L2 范围。单据及两侧订单按固定顺序锁定；确认及必需审计、双方精确订单行回写在同一事务，失败全部回滚。历史旧单缺原生依据保持待核，不补造领导批准。

## 未认账价格修改与重送审

新增 `POST /api/v1/internal-trade/:id/price-revisions`，字段为 `requestId, expectedContentFingerprint, quantity, settlementPrice, dueDate, reason`。操作者、双方订单行、审批人、版本序号、结算金额及目标全部由当前服务端事实取得；客户端传入 actor/reviewer/版本不会赋权。只有 Draft/PendingConfirm 且双方均未认账、未确认、未交付/收货时可提交。生效之后的修改须另走业务变更，不能覆盖已计成本或收入。

新命令按 current active、显式写 scope、可信 ceiling、双 Order L2 核对，锁顺序仍为双方 Order → pair → 旧审批。原 approved/rejected 决议完整保留；原 pending 以完整内容 CAS 变 cancelled 并追加 supersede 审计，取消不是批准决议。新价格以双方稳定行及当前真实范围生成完整 server 内容、递增 priceRevision 和新 ApprovalRequest，真实 masterId 为审批目标。双向金额/memo CAS、新审批、必要审计均同一事务；确认只有新版本真实批准后才可发生。

priceRevisions 追加原冻结内容、原审批完整快照与旧审计 ID、请求规范化参数、真实主体和时间、新审批 ID/内容 fingerprint 及必需审计 ID。每个实际 actor/master/requestId 对应唯一不可变命令。原参数重试返回原执行回执（即使之后已生效）；改参数拒绝。返回 `revision, approvalRequestId, contentFingerprint, previousApprovalId, previousContentFingerprint, requestId, requestKey, requestFingerprint, auditId, replayed`；回执重放仍先核当前授权和双订单范围，并逐项匹配原审计，不以当前状态猜原执行成功。

普通价格批准必须来自当前指派主管/总领导的真实内核决议及当时 canonical role authority。已存在的显式总领导特批独立消费：只有 `boss_final_bypass`、准确 bossFinalBypassBy/At/Reason、原因至少30字、相同真实决定时间及 actor、canonical owner 当时权威和完整内容事实同时匹配才能作为批准。自批禁止；普通 owner 决议、显示名称、长理由或 approved 字符串单独均不能替代此入口。

## 查看与页面接入边界

get/list 均核当前有效账号、数据库权限与 ceiling，兼容 `orders:read` 或显式 `order:internal_trade:write`，并在分页前过滤两侧 Order L2。已批准内部交接价是双方履行业务的交接字段；外部采购及其他实际成本仍受敏感成本权限约束。本批没有改 BDS 或前端；现 FinanceReportsPanel 只有创建/确认/交付，独立收货与价格重送审操作卡仍需既有样式接入，人类审批上下文与跳转也须页面验收。

## 交付与到货

保留 `POST /:id/delivery` 请求和响应形状，新增可选稳定 `requestId/allocationId`。交付必须引用真实已出运 Shipment 和准确面料行分配，累计不超过真实 actualQty 或批准数量；草稿运输不是已交付。每笔 delivery 有稳定 ID、真实分配、单位、命令 hash 与必需审计。

新增 `POST /:id/receipt`：`deliveryId, quantity, receivedDate, requestId`。收货为独立追加事实，具真实 actor 和必需审计 ID；参数重放只读原事实，改参拒绝。累计收货不超该笔交付；短收及差异保留，不覆盖历史。原 delivery 请求含 receivedQuantity 时，同一事务追加独立 receipt 审计，兼容现有页面。

payload.receipts 保存每笔收货，delivery.receivedQuantity/Date/variance 为经过核对的投影。全部真实出运与到货均足额且无差异才 Closed；累计登记运输数量不能代替实际到货。成本消费逐条重验主单/镜像、真实批准、确认审计、出运分配、交付/到货审计与投影；源变化失效。

## 实际成本核对接口与当前源消费

现有 OrderCostReview 输入增加可选 internalTransfers：明确 pair、双方行、delivery 与真实核对附件。缺省属性保持缺省，兼容旧请求 hash；有有效内部单据而没有明确绑定则 pending。金额从服务端真实价格与确认数量事实计算，客户端不可写金额。

收入范围分别记录外部 revenueInvoiceIds、internalRevenueTransferIds；成本范围记录 internalPurchaseTransferIds，防止把合法内部收入误要求为商业发票。服装成本加真实内部结算额，面料收入加真实内部结算额；面料自身外采/加工/其他费用仍走现有真实成本核对。双方 source hash 包含原生批准及决定审计、行范围、单据、出运和收货事实。来源变化使当前核对 stale，原核对历史不覆盖。

公司抵销必须依据相同主单/镜像 pair，不能按金额、备注或物料码猜配；同一 pair 仅一次。未决批准、无价依据、未出运、未到货、差异、来源变动、缺附件保持 pending。日期过滤按既有报表范围保留可见抵销差额。

## 验证范围

真实 PG 探针必须通过实际创建→指派人批准→双方确认→真实出运→到货→双订单实际核对→部门与公司报表，不 seed approved/review flag。商业采购、客户应收及物理出运前置若采用合成源，必须标明证据层级。错误 pair/价格主体/重复/草稿运输/短收/撤权/真实审计 SQL FK 失败的拒绝与零残留为负控；此文档、源码和 mock 通过均不等于业务闭环已验收。
