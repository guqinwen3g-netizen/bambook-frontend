## 一、对账跨币种裸加（`finance/reconciliationService.ts`）

### 现状（已复核，行号无漂移）

**订单级**——累加不看币种：
- `:190-195` `invoicedAmount = invoicedAmount.plus(ioa?.allocatedAmount ?? inv.amount)` —— 循环里**完全不读 `inv.currency`**。
- `:204-205` `paidAmount = paidAmount.plus(pa.appliedAmount)` —— 同样不看币种。

**订单级差异判定**——跨币种裸比（这条矩阵没提，但更致命）：
- `:258` `invoicedAmount.gt(orderAmount.plus(EPS))` → 判「超开 critical」
- `:280` `paidAmount.gt(invoicedAmount.plus(EPS))` → 判「超收 critical」

**客户级汇总**（矩阵指的 `:422-424`）：
```ts
totalOrderAmount:    results.reduce((s, r) => s.plus(dec(r.orderAmount)),    0)
totalInvoicedAmount: results.reduce((s, r) => s.plus(dec(r.invoicedAmount)), 0)
totalPaidAmount:     results.reduce((s, r) => s.plus(dec(r.paidAmount)),     0)
```
逐单累加，**忽略每个结果各自带的 `currency` 字段**（`:361` 明明返回了 `currency: orderCurrency`）。

### 为什么算错（举个具体例子）

某客户两张订单：A 单 USD 10,000，B 单 CNY 50,000。
- 对账页显示「已开票合计 60,000」——这个数字**没有任何货币含义**。
- 更糟的是订单级：一张 USD 发票 10,000 + 一张 CNY 发票 5,000 → `invoicedAmount` = 15,000，
  再拿去和订单额 USD 12,000 比 → 判 **「超开 3,000 critical」**（假的）；
  反过来若订单是 CNY 100,000 → 判「未开票余额 85,000」（也是假的）。

**critical 级差异会直接误导财务把对的单当成错的去查。**

### 唯一的「防护」为什么不够

`:213-234` 确实会记一条 `currency_mismatch` 差异，但 **severity 只是 warning（info 当订单缺币种）**，
而且**只报错、不改算法**——金额照加不误，判定照比不误。

### 修法建议（现成范式就在同文件里）

`:394-417` 的 `fxByCurrency` 已经是**按币种分组**的正确写法（`fx.invoicedByCurrency` → Map 分组累加），
说明「分组」这件事在这个文件里已有先例，照抄即可：
1. 订单级：`invoicedAmount` / `paidAmount` 拆成按币种的 Map，差异判定**只在同币种内比**；
   跨币种时把 `currency_mismatch` 升为**阻断级**（不再参与金额比较），而不是 warning。
2. 客户级：`totalOrderAmount/totalInvoicedAmount/totalPaidAmount` 改为按币种分组的
   `Record<currency, {order, invoiced, paid}>`，前端分币种展示。

**❓ 口径 A**：是否允许**用汇率折算出一个 CNY 合计**？（便于看总量，但引入"用哪个汇率"的新口径：
开票日汇率 / 收汇日汇率 / 期末汇率。）若不允许，就只做分币种展示，不出现合计。

## 四、收汇金额 ↔ 报关 FOB 勾稽 —— 完全不存在

### 现状复核

水单认领/核销链（`finance/receiptClaimService.ts`、`finance/allocationService.ts`）grep
`报关 / declaration / customs` **零命中** → 核销只到**发票 / 订单**层，**完全不碰报关单**。
矩阵判「❌ 完全不存在」**成立**。

### 业务含义（为什么必须有）

出口收汇金额需与报关 FOB 金额勾稽（外汇核销/退税核查的常规要求）：
收汇显著低于报关 FOB 意味着可能有佣金、折让、或未收汇即退税的风险；显著高于则可能有多收/错汇。
**现在系统里这两笔钱各在各的域，永远碰不上面。**

### 修法建议

新增只读勾稽服务：以订单为锚，取 `Σ 收汇（PaymentVoucher type=Receipt，按币种）` vs
`报关单 FOB（CustomsDeclaration.totalValue / 行明细合计，按币种）`，同币种内比对，给差异额 + 差异率。

**❓ 口径 D**：
1. **容差多少**？（行业常见 ±5% 或 ±500 USD 取大者；需业务定。）
2. **FOB 取哪个值**？报关单 `totalValue` 是成交总价（可能是 CIF），而勾稽要的是 **FOB 净额**
   —— CIF 单需要减运费/保费才能比。**减不减、怎么减**要拍板。
3. 超差时**阻断**还是**预警**？

## 五、退税自动推导 —— ⚠️ 与矩阵冲突：已经自动算了

矩阵 §三 写：「退税自动推导 ❌ 两个字段都在却要手填，`createTaxRefundFromDeclaration`
（`customsService.ts:1497`）**不自动算金额**」。

**复核结论：矩阵这行判错了（或已过时）。** 证据：

1. `customsService.ts:1497-1600` 的 `createTaxRefundFromDeclaration` **明确自动算**：
   - `exportAmountFob`：行明细 `totalAmount` 合计 → 回退报关单 `totalValue`（`:1535-1539`）
   - `fxRate`：应收发票汇率 → 回退收款凭证汇率（`:1527-1533`，注释写明"开票当日 → 实际收汇日"回退链）
   - `refundableVat`：按行 HS 查 `HsCode.exportTaxRebateRate` **加权**核算（`:1552-1572`，
     含 `/100` 口径修正——注释记录了"漏除导致退税放大 100 倍"的历史 bug）
   - `refundAmount = refundableVat`（`:1584`）
2. 自动触发链路完整：`events/linkages/L10CreateTaxRefundDraft.ts` 订阅 `CustomsCleared`
   → 调 `createTaxRefundFromDeclaration`；已在 `events/linkages/index.ts:54` 注册，
   `automationConfig.ts:93-98` 有 `L10_create_tax_refund_draft` 且默认 enabled。
3. **时间线佐证**：这段核算代码最后改动是 `ad9ca21`（2026-08-07）引入、
   `e210b5f`（2026-09-14，"退税 100×"修复）——**都早于矩阵（09-16 上午）**。

### 那真实缺口是什么

不是"不自动算"，而是**算不出来时会退化成手填**：
- `fxRate == null`（订单既无应收发票汇率、也无收款凭证汇率）→ `exportAmountCny = null` → `refundableVat = null`
- 报关行**缺 HS 编码**或该 HS 未登记 `exportTaxRebateRate` → 该行跳过，全部行都缺 → `refundableVat = null`

此时生成的退税草稿金额为 `null`，**只能人工手填**——这才是"两个字段都在却要手填"的真实所指。

**❓ 口径 E**：
1. 是否要补**兜底推导**（汇率缺失时查市场汇率 / HS 缺退税率时用 0 或类目默认率）？
   —— 我的建议是**不要静默兜底**（会算出假数字），而是**显式报缺**：草稿标记"缺汇率/缺退税率"，
   并在 UI 上给补齐入口（补发票汇率 / 补 HS 退税率），补齐后一键重算。
2. 重算入口：是否允许对已生成的草稿**重算**（现在 `declarationId` 唯一 + "不可重复生成"拦截）？
