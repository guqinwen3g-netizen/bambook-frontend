# 开发收费跨岗位流转实施方案

日期：2026-09-30。业务基线已由用户确认；以下字段及接口为实施设计，尚未实现或验收。适用于面料、成衣开发。对客开发费账单与内部应收关联；税务发票按具体业务另行处理，不混称。

## 已确认的岗位边界

业务员在原开发案登记费用、保存收费方案、提交财务、补充退回事项、查看单据与跟进客户。财务从个人待办进入同一案的财务处理视图，核对、提出修改意见、制单、核销；不替业务员静默修改商业条件。超出授权的收费/减免通过既有审批机制处理，不默认每案领导审批，也不凭客户历史免收。

业务员持续负责客户沟通；当前核对/审批/制单负责人分别明确。待办派发不等于接收或完成，完成制单不等于签发、发送、到账或核销。费用未齐允许保存收费草稿，但不能提交最终核齐或制单。开发结束、费用核齐、收费处理与收款结清独立展示。

## 状态与事实契约

继续以BillingItem为收费金额真源，不新建第二套金额单。原status仍承担draft/confirmed/invoiced/cancelled的财务含义；增加开发收费办理投影，避免把“已提交”写成“已确认”。拟新增字段：

- developmentWorkflowState：draft、submitted、returned、approval_pending、ready、cancelled，仅开发整案适用。
- developmentWorkflowVersion：单调递增整数，所有编辑、提交、退回、批准与制单请求必须提供expectedVersion。
- developmentSubmittedBy、developmentSubmittedAt：当前轮申请人/时点；历史放入不可变事件。
- developmentAssigneeId：当前处理人；待办从此状态派生，转交需留原因。
- developmentApprovalId：需要例外时指向既有ApprovalRequest；金额、减免、客户、币种、费用核齐版本变化使原审批不再适用于新轮次。

增加开发收费流转事件记录，关联原BillingItem；只记录操作、版本前后、操作者、原因、快照、请求幂等键及相关任务/审批ID，不再存一套可编辑金额。事件与收费投影、待办变化同事务提交。不得以删除旧任务、覆盖旧理由实现重提。

| 动作 | 前置 | 同事务结果 |
|---|---|---|
| 保存草稿 | 有业务写范围；可未结案/费用未齐 | BillingItem保持draft；核齐引用可空；留金额与理由版本，不占用最终收费覆盖 |
| 提交财务核对 | 已明确结案；无待齐费用；有效费用核齐；客户/金额/币种/依据齐全；有效财务接收人 | 锁案与收费，绑定review和成本覆盖；workflow=submitted、status=draft；生成当前轮财务待办 |
| 财务退回 | 当前财务处理人或明确授权代办；当前轮有效 | 必填原因和补充项，workflow=returned；原核对任务留下退回结果；给提交人生成补充待办 |
| 业务补充/重提 | 原业务责任及权限仍有效；退回状态 | 按最新版本编辑；费用变更重新核齐；生成下一轮核对任务，保留前轮记录 |
| 财务核对通过 | 快照一致、费用覆盖有效、必需资料齐全 | 授权内进入ready并确认收费；需例外则approval_pending并交给既有审批 |
| 例外审批完成 | 审批目标与提交快照仍相符 | 通过进入ready；拒绝回到业务补充；失效审批不可继续使用 |
| 制单 | ready、收费confirmed、核齐与审批未失效、权限有效 | 沿用现有应收创建/回填幂等；全免记录无应收结果；完成制单任务，原案更新 |

不能把ApprovalRequest与财务核对合并成一次无理由的“批准”。财务核对可指出问题，不替业务员改价；业务员不能用业务写权限签发应收或核销。

## 接口草案（复用开发案与收费域）

`GET /development/:caseId/billing-workflow`：返回独立进度、本人可执行动作、当前处理人、待补事项、费用核齐摘要、收费草稿及只读流转历史。财务视图按财务来源权限读，业务视图按业务来源权限读；不要求财务拥有products:write。

`POST /development/:caseId/billing-drafts`：扩展现有草稿口，reviewId在草稿阶段可空，保留requestKey与显式金额/减免/币种/依据。

`PATCH /development/:caseId/billing-drafts/:id`：业务员就地编辑本人有权处理的draft/returned；expectedVersion；已提交先受控撤回，已生效进入后续调整路径。

`POST /development/:caseId/billing-drafts/:id/submit`：requestKey、expectedVersion、reviewId、财务接收人。接收人默认依据现有分工，未配置且有多个候选时明确选择，不随机分派。提交人只需相应业务权限，后端独立校验接收人真实权限。

`POST /development/:caseId/billing-drafts/:id/return`：requestKey、expectedVersion、reason、requiredItems；当前财务处理人操作。

`POST /development/:caseId/billing-drafts/:id/verify`：requestKey、expectedVersion、note；后端解析授权与审批规则，客户端不能传“无需审批”绕过。

既有confirm-handoff暂保留兼容，迁移到上述新流程后限制为明确兼容用途，不能两个入口产生不同的审批/确认语义。正式部署前本地数据兼容与历史任务呈现均需验证。

## 页面交接

开发案：顶部四组独立状态；费用区保留已登记/待到账单；收费方案可保存未提交；每个状态说明“当前等谁、缺什么、下一步能做什么”。退回意见定位到具体资料，原输入保留。财务处理中业务员可查看，不能覆盖已提交金额。

财务待办：从任务直达费用与商业收费对照、附件、提交版本和历史意见；可核对通过/退回补充。返回列表后保留筛选和位置。通过核对后显示制单动作，不能先确认金额再假装开始核对。

原案单据区：展示对客账单/应收关联、版本、是否已签发、发送记录、已核销与余额。客户账单只含约定收费项目，不含内部采购成本和供应商底价。下载、签发、发送权限分别检查；本阶段不自动发送，不把内部预览标为已发送。

## 验证顺序

1. 面料、成衣均走：开发中草稿→结束但费用待齐→补账单→核齐→业务提交→财务退回→原案补充重提→财务核对→制单→原案回显。
2. 覆盖授权内收费、逐案全免、需例外审批、审批后金额变化、财务负责人失权/转交、重复提交、跨岗位并发及断网恢复。
3. 实际成本不因减免减少；提交不产生应收；未核齐不能制单；同一版本只生成一次收费覆盖/任务/应收；退回和重提均保留历史。
4. 真实本地账号从前端完成，核对后端请求和数据库结果；不得临时改库或接口补状态后宣称页面走通。
5. 对客账单展示与内部费用隔离独立验；签发、发送、到账、核销分别验，不以发票ID存在证明收费已完成。

当前只是已确认业务方案的实施契约。上述新字段、接口、页面交接和验收未完成，不作上线承诺。下一步先实现可未核齐保存的草稿及业务提交/财务退回重提，随后接授权审批、制单和回显；不再扩展工厂MES。

### 费用凭据字段与接口实施契约

新增 CostEvidence 仅承载费用与不可变文件的明确关联，不替代 CostRecord 金额、KnowledgeDocument 或审批。字段：id、costRecordId、requestKey、requestFingerprint、originalName、storageKey、mimeType、byteSize、sha256、note、createdBy/At；撤销增加revokedBy/At及reason，不删除文件或覆盖内容。相同费用和请求键重试恢复原记录，内容不一致拒绝。文件存现有private-files下development-cost-evidence，下载只能经原案或财务任务授权，不返回存储路径、不自动知识库同步。首批PDF/PNG/JPEG，10MiB，服务端校验文件签名并强制下载；其他票据格式仍待后续扩展，不把首批白名单声称为全部票据覆盖。
