## 2. 为什么这个字段不是装饰（业务后果）

电汇手续费三种承担方式直接决定**同一笔钱的归属**：

| 值 | 含义 | 对我们的账意味着 |
|---|---|---|
| `OUR` | 汇款人承担全部 | 到账额 = 票面额 − 手续费 ⇒ 手续费是**我们的成本**（1a 已单列） |
| `BEN` | 收款人承担全部 | 同上，且通常表现为"到账比发票少" ⇒ 若被当成**少收汇/短款**去催收就是错的 |
| `SHA` | 双方分担 | 只有一部分是我们的 ⇒ 全额计成本会**低估毛利** |

今天三者都按同一种方式处理（一律 `bankFee` 全额进成本），所以 **`SHA` 与 `BEN` 的订单毛利不可信** ——
这正是 D7 要把 `feeBearer` 建出来的原因，不是"多加个字段好看"。

## 3. 需要的结构变更（一条 SQL，非破坏性）

```sql
-- 建议放 prisma/migrations/<ts>_add_fee_bearer/migration.sql
ALTER TABLE "PaymentVoucher"
  ADD COLUMN IF NOT EXISTS "feeBearer" TEXT NOT NULL DEFAULT 'SHA';
```
`schema.prisma` 对应加：
```prisma
/// 电汇手续费承担方：OUR(汇款人全担) | BEN(收款人全担) | SHA(双方分担)（SWIFT 惯例）
/// 缺省 SHA：不假设任何一方全额承担 —— 宁可保守，也不把别人的费用记成我们的成本（G3）
feeBearer String @default("SHA")
```

**为什么默认 `SHA` 而不是 `OUR`**：`OUR` 会把全部手续费算成我们的成本；`SHA` 是三者中最不激进的假设，
与"算不出来就不给数"取向一致。此为自裁，按 §12 规则登记（见本文档末 §6）。
