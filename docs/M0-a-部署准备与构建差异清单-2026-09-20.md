**部署前**
1. 确认目标提交：`git log --oneline -1`（并确认该提交包含预期的批次）。
2. 门禁全绿（G6.1 / R6）：
   ```bash
   cd server && npx vitest run            # 约 13 分钟；勿用 | head（SIGPIPE 提前退出）

   cd server && npx tsc --noEmit && npx tsc --noEmit

   ```
   ⚠ PATH 缺 `/opt/homebrew/bin` 时 `rg` 找不到 ⇒ 令牌检查**空过假绿**，退出码须单独取。
3. schema 若有变更：migration 链已坏（P3006），**禁 `prisma migrate dev`**，走手写幂等 SQL + `psql -f`。
   （本批 S0-A1 无 schema 变更。）

**部署**（局域网，公网必 524）
```bash
BAMBOOK_OPS_URL=http://192.168.110.3:8088 bash scripts/ops-upload-package.sh            # 后端
BAMBOOK_OPS_URL=http://192.168.110.3:8088 BAMBOOK_WEB_SUBDOMAIN=1 bash scripts/ops-upload-webapp.sh   # → webapp-root
BAMBOOK_OPS_URL=http://192.168.110.3:8088 bash scripts/ops-upload-webapp.sh                          # → webapp（老路径）
```

⚠ **两个入口都要传**：历史上正是「两个入口互相丢文件」，B13 的 3 个 404 就长在入口二。

## 4. ★ 本次发现的一个安全缺陷（建议修，但不由我单方面动部署工具）

**「只准备包、不部署」这个动作目前不存在**，而且误触即上线：

| 证据 | 内容 |
|---|---|
| `scripts/ops-upload-package.sh:49-76` | 打包（`tar` → `/tmp/bambook-ops-upload.tar.gz`）与 **`curl -X POST` 上传** 焊在同一段顺序执行，无 `PACKAGE_ONLY` / `--dry-run` 分支 |
| 同文件 `:18-22` | Token **自动从钥匙串读取**（`security find-generic-password -s bambook-ops-token`）⇒ 不会像首次那样弹窗拦一道 |
| `scripts/ops-upload-webapp.sh:71-72` | 同一套钥匙串取 token 逻辑 |
| `Bambook-部署后端.command` / `Bambook-一键全量部署.command` | **grep 无 `display dialog` / `read` / 任何确认**⇒ 双击即静默部署到生产 |

**后果**：这与 §8.2「部署到生产禁止（等 D12）」直接冲突 —— 边界靠人的自觉维持，而不是靠工具维持。
同时 M0-a 的「准备部署包 + 出清单」在现有工具下**无法安全执行**（一执行就变成 M0-b）。

**建议修法（最小、不改变部署语义）**：
1. 两个 `ops-upload-*.sh` 支持 `PACKAGE_ONLY=1`：打包完即退出，打印包路径与大小，不发任何网络请求；
2. `.command` 入口加一次确认弹窗，**明确写出目标提交号与目标环境**，取消即退出；
3. 加一条结构守卫（阳性对照）：`PACKAGE_ONLY=1` 下若脚本发出任何 `curl -X POST` 即判红。

**为什么不直接改**：部署工具是 Kevin 唯一的生产入口，改坏了会在他选定的时点让部署失败。
按「最严解释」登记为新的阻塞项候选 **B16（部署工具无 dry-run 且入口无二次确认）**，
并记入 §12 的 **D15**（自主推进中的自裁项），待其确认后一批内落地。
