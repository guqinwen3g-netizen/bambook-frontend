# 备份恢复与并发核验（P2）

> 边界：只用开发库或本地 / 临时隔离 PostgreSQL；不连正式库、不迁移正式库、不发布、不改定时任务；测试数据全部为模拟数据。
> 本次（2026-10-17）**没有开发库访问权限**，A、B 两部分只在**本地临时 PostgreSQL** 上完成；C 部分没有开发环境地址与访问权限，只用本地桩服务验证了脚本逻辑。

## 一、怎么跑

### 0. 准备隔离库（本地临时 PostgreSQL）
```bash
initdb -D /tmp/bambook-pg -U postgres --auth=trust -E UTF8 --locale=C.UTF-8
pg_ctl -D /tmp/bambook-pg -o "-p 55432 -k /tmp -c listen_addresses=127.0.0.1 -c max_connections=200" -l /tmp/bambook-pg.log start
psql -h 127.0.0.1 -p 55432 -U postgres -c 'create database bambook_local_verify'
cd server
# 与 scripts/init-dev-database.sh 相同：迁移历史不能从空库重放，空库按 schema.prisma 建表，再把全部迁移记为已应用作基线
export DATABASE_URL=postgresql://postgres@127.0.0.1:55432/bambook_local_verify
npx prisma db push --skip-generate
for d in prisma/migrations/*/; do npx prisma migrate resolve --applied "$(basename "$d")"; done
npx prisma migrate deploy        # 应输出 No pending migrations to apply.
# 写入模拟数据（只接受回环地址 + 库名含 verify/test/local/dev/sandbox）
BACKUP_VERIFY_SOURCE_URL=$DATABASE_URL npx tsx scripts/seed-backup-verify-mock.ts
```

### A. 备份可恢复：`server/scripts/verify-backup-restore.sh`
```bash
BACKUP_VERIFY_SOURCE_URL=postgresql://postgres@127.0.0.1:55432/bambook_local_verify \
  bash server/scripts/verify-backup-restore.sh
```
流程：
1. 调用现有 `backup-postgres.sh`（`BAMBOOK_BACKUP_DIR` 指向本次独立工作目录）做一次 `pg_dump -Fc` 备份；
2. 新建临时库 `bambook_restore_verify_YYYYMMDD_HHMMSS_<pid>`，`pg_restore --no-owner --no-acl --exit-on-error` 恢复；
3. 在临时库上跑当前检出代码的迁移检查：`prisma migrate status`（必须 up to date）+ `prisma migrate diff --from-url <临时库> --to-schema-datamodel prisma/schema.prisma --exit-code`（必须无差异）；
4. `scripts/verify-backup-restore-check.ts` 逐项比对原库与恢复库：表数量、全部表逐表精确行数（单列关键表 MistWorkspace / MistCommandReceipt / UserAccount / BusinessSequence / _prisma_migrations）、每个工作空间的 revision、事件数（`state.events`）、业务回执数、版本标记数、state 摘要（md5）；
5. 用恢复库启动一次真实 Mist 服务（`createMistServer` + Prisma，随机端口），`/api/health` 必须 `status=ok, database=ok`；以工作空间所有者身份读取一个工作空间，与用原库启动的同一服务读取结果逐项相等；
6. 退出时（成功或失败）只删除本次创建、名称通过 `^bambook_restore_verify_[0-9]{8}_[0-9]{6}_[0-9]+$` 校验的临时库（`DROP DATABASE ... WITH (FORCE)`）。不删除任何文件或目录（备份与 `report.json` 留在工作目录作证据）。

安全门：必须显式给 `BACKUP_VERIFY_SOURCE_URL`（不读 `.env`）；源库主机不是本机时必须设 `BACKUP_VERIFY_ALLOW_REMOTE_DEV=1` 确认是开发库；源库名必须含 dev/test/verify/local/sandbox/tmp；临时 JWT 签名密钥每次随机生成，只在本次进程内的两个临时服务有效。
可选：`BACKUP_VERIFY_WORK_DIR`、`BACKUP_VERIFY_WORKSPACE_ID`、`BACKUP_VERIFY_KEEP_DB=1`。

### B. PostgreSQL 并发实测：`server/src/mist/workspaceConcurrencyLoad.pg.test.ts`
```bash
cd server
MIST_PG_CONFLICT_TEST_URL=postgresql://postgres@127.0.0.1:55432/bambook_pg_test \
MIST_PG_LOAD_REPORT=/tmp/mist-pg-load.json \
  npx vitest run src/mist/workspaceConflictRetry.pg.test.ts src/mist/workspaceConcurrencyLoad.pg.test.ts
```
与 `workspaceConflictRetry.pg.test.ts` 同一开关，未设置时整组跳过。使用真实 `MistRepository`（2026-10-17 起：写入按工作区在进程内排队 + READ COMMITTED 事务首句行锁 + 自动合并 + 死锁时最多 3 次自动重试；此前为 Serializable 事务）和测试合同的模拟命令 `notes.add`（新增独立记录）、`money.add`（同一金额字段累加），模拟账号 `load-user-*`。Prisma 连接池未指定时按 `connection_limit=60`。
场景（10 与 50 并发各一组）：
- **混合**：每个用户依次提交「新增记录 → 金额累加 → 新增记录」，全部基于开始时看到的同一版本（制造落后版本）；409 时客户端重读最新版本、换新请求编号重试，最多 5 次；之后每个成功请求原样并发重放一次。
- **同字段冲突**：所有用户基于版本 0 同时改同一金额字段，不做客户端重试。
- **同一请求重放**：同一 requestId 由 N 个连接同时提交。

断言：不丢写（每条成功的新增记录恰好一条）；revision 连续（最终版本 = 成功请求数，版本标记 1..N 各一条，业务回执的版本号与之一一对应）；重放拿到同一回执、不重复记账；失败只允许 409 `REVISION_CONFLICT`；金额 = 全部成功累加之和。
指标全部由本次运行实测写入报告：单次请求延迟 p50/p95（每次 `execute` 调用，含服务端内部重试）、端到端延迟（含客户端重试）、客户端重试次数、服务端被回滚的事务数（可串行化失败 / 死锁 / 唯一键竞争，仓储会据此自动重试或转为回执重放）、409 失败数。

### C. 交付核验：`server/scripts/verify-dev-delivery.ts`
```bash
cd server
npx tsx scripts/verify-dev-delivery.ts --frontend=<开发前端地址> --server=<开发主服务地址> [--mist=<开发 Mist 服务地址>] [--expected=<main SHA>]
```
- 前端：首页 2xx；`mist-version.json` 的 `commit` 与 main 一致（短 / 长 SHA 前缀匹配，至少 7 位），且 `localChanges = 0`；
- 服务端：`/api/health` 为 `status=ok`、`database=ok`，`build` 与 main 一致（`unknown` / 缺失均判失败）；
- 可选 Mist 服务：`/api/health` 为 ok；
- main SHA：`--expected` / `EXPECTED_MAIN_SHA` 优先，否则 `git fetch origin main` 后取 `origin/main`；
- 只发 GET；拒绝正式环境主机（默认 `jiangsupanda.com`，`BAMBOOK_PRODUCTION_HOSTS` 可追加）。退出码 0 通过 / 1 失败 / 2 参数错误或拒绝。

**B2. 2026-10-17 写入改为“按工作区排队 + 读已提交行锁”后重测（本地 PostgreSQL 16，同一组 11 个用例全部通过）**

改动：同一进程内同一工作区的写事务排队执行，一次只有一笔在库里等锁（不再占满连接池）；库内事务改为 READ COMMITTED，首句 `FOR UPDATE` 锁住工作区行，拿到锁后读到的就是最新已提交版本，不再因可串行化快照在等锁后整笔回滚（多进程部署同样以行锁为准）。自动合并跨度上限 20 → 500 个版本，写入记录一次批量读取。审批 / 确认 / 放行改为“所办理的那条记录期间没人改过才合并”，签发 / 正式单据仍必须基于最新内容重新确认。审批决定、成员授权、回收站操作也记录写入位置，之后的落后保存不再因“无法确认”被拒。

- 剩下的 409 全部是 50 人同时改**同一个金额字段**：这是有意保留的保护——后到者必须看到对方的修改再决定，不自动覆盖；真实业务里对应“多人同时改同一张单的同一处”。
