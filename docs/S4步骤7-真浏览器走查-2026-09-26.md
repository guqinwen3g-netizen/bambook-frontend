## 四、★ 发现 1（P1）：同时改「数量 + 单价」⇒ **「改价」被静默丢弃**

**真 UI 可达**（实测：场景 B 的 payload 就是从浏览器点出来的）。

**现象**（回放实测）：
```
quantity     = 1500
salesPrice   = 20            ← 用户输入的单价，落了库
contractAmount = 20775
totalNet     = 20775
quoteAmount  = 20775
Σ明细行      = 20775  [{"q":1500,"up":13.85,"nv":20775}]   ← ★ 明细行单价仍是旧值 13.85
```
用户意图 `1500 × 20 = 30000`，实际 `20775`；**且 `salesPrice(20) × quantity(1500) = 30000 ≠ totalNet(20775)`**。

**根因**：`server/src/orders/route.ts` 的 `detectAmountIntent` 优先级
`quantity > contractAmount > quoteAmount > totalNet`，**且只返回一个 mode**。
两者同时被改时 `quantity` 先命中 ⇒ 走 `mode:'quantity'` ⇒
`recalcOrderAmountFromLines` 按**各行原单价**重算 ⇒ 用户改的单价对金额**完全不生效**；
但随后只从 patch 里剔除 `quantity/quoteAmount/contractAmount/totalNet`
（`route.ts` 收口段），**`salesPrice` 不在剔除名单** ⇒ 用户输入的 20 照样落库
⇒ **主档单价与明细行单价互相矛盾**。

**★ 修法不是「换优先级」**：把 `contractAmount` 提到 `quantity` 之前，则改价生效、
**改的数量被丢弃**（`quantity` 会被剔除、明细行仍 1800）—— 同样是丢一半。
真正的修法是**同时应用两个 mode**（`recalcOrderAmountFromLines` 目前只接受单个 `RecalcMode`），
或**检测到两者同时改时明确拒绝/引导**（「数量与单价请分两次保存」），**总之不能静默丢一半**。

**为什么它比 F1 更隐蔽**：见 §5 —— 连 `findOrderAmountConflict` 都看不见它。

## 五、★ 发现 2（P2）：**真源自检 `findOrderAmountConflict` 不看 `salesPrice`**

`server/src/shared/orderAmount.ts:116` 的 `findOrderAmountConflict` 只对撞三条：
`Σ明细行 ↔ totalNet / contractAmount / quoteAmount`（**`:134` / `:137` / `:140`**）。
**它不检查** `salesPrice × quantity ↔ totalNet`，也**不检查** `salesPrice ↔ 明细行 unitPrice`。

⇒ 发现 1 的「主档单价 ↔ 明细行单价」矛盾，**对现有守卫完全不可见**
（守卫判据是逻辑空集的那一类）。
⇒ 建议：把 `salesPrice ↔ 明细行单价` 一并纳入该真源自检（**在真源里加，不要另写第二套**）。

## 六、★ 发现 3（P2）：无明细行订单改价 ⇒ 三列仍分叉

回放对照（手搓 payload）：`contractAmount 10020` / `quoteAmount 1001.5` / `totalNet null` / 无明细行。

根因：`recalcOrderAmountFromLines` 对「无明细行」**显式返回 null**
（`orderAmountRecalc.ts` 注释：「无明细行：没有可分摊的载体，保持主档单点写入（既有行为），不制造假一致」）
⇒ `route.ts` 收口段 `if (recalc)` 不成立 ⇒ 四键**不被剔除** ⇒ patch 原样落库 ⇒ 分叉。

**这不是新增缺陷**（修复前同形），但两点值得登记：
1. 它是**静默**的（`logger.warn` 用户看不到），屏面无任何提示；
2. **规模不小**：测试库 `1069` 张订单里 **`1000` 张无明细行**（有行的只有 69 张）。
   顺带实测：**全库 `salesPrice` 非空数为 0**（1069 张全空）。
