## 一、缺陷：撤销的权限被代码原样洗回

判定顺序是"**DB 说没有 ⇒ 再问代码 ⇒ 代码说有 ⇒ 放行**"：

| 位置 | 旧行为 |
| --- | --- |
| `server/src/auth/permissionService.ts` `hasScope` 2a | 快照命中才 `return true`，**未命中不 return false** |
| 同函数 2c | `return fallbackHasPermission(roleIdsFromLegacy, scope)` —— **少传第三参数 `runtimeUserScopes`** |
| `server/src/_shared/rolePermissionMatrix.ts` `hasPermission` | 于是落到 `DEFAULT_ROLE_PERMISSION_MATRIX[role][scope] === true ⇒ true` |

快照本身是**登录时从 DB 聚合**的（`auth/route.ts:86` 的 include 链、`agentPrincipal.ts:122`）
⇒ 这不是"重登才生效"的延迟问题，是**重登了也没用**。

`hasScope` 里新增一行短路（超管特权保留、零行角色仍可回退），配 `server/src/auth/__tests__/scopeRevocationRewash.test.ts` 4 例：

| B 面：快照为空 ⇒ 仍回退为 `true` | **一刀切删兜底**（会锁死那 10 个零行角色） |
| 超管（`owner`）短路仍为 `true` | 修撤销时顺手把超管关在门外 |

★ 配对（角色 / scope）**全部从真源反查**（`DEFAULT_ROLE_PERMISSION_MATRIX` + 为测试导出的 `_internal_legacyToRoleId`，沿用本文件既有 `_internal_*` 约定）：
写死字面量的话，映射一改这条探针就变成"谁都不会红的死断言"——这是本仓老病。
第一版就因此**挑不出配对并直接抛错拒绝运行**（`role-*` 每一行只有 `true` 值 ⇒ "该角色没有的档"必须跨行取并集做差），这正是"无输入不许下结论"该有的行为。
