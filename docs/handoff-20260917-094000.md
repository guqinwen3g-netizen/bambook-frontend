## 一、结论（一句话）

**供应商索赔生成的负额应付票（`CLM-YYYY-NNNN`）是一张「死票」：永远到不了 `Paid`、
不能被付款核销，而唯一的出口「作废」会让索赔静默失效、且退换货单侧不联动。**

它是批次 6 那个 bug 的**对偶面** —— 应收侧靠「信用门禁」放大成挡单，应付侧没有门禁，
所以后果轻一档，但**「永不结清 + 出口只有作废」这个结构性缺陷完全一样**。

### 1. 它是怎么产生的

`procurement/materialReturnService.confirmReturn`（`type='claim'` 且 `status='shipped'` 时）：

```ts
const invoice = await tx.invoice.create({
  data: {
    type: 'Payable', status: 'Issued',
    amount: -Math.abs(Number(row.amount)),   // ★ 负额
    invoiceNumber,                            // CLM-YYYY-NNNN
    ...
  },
});
```

**注意两点**：
- 它是**服务层直接 `tx.invoice.create`**，**绕过 API 的金额符号守卫**
  （`invoiceMutationService` 的 `NON_NEGATIVE_FIELDS={amount}` 让 API 建不出负额票，实测 400）。
  → 也就是说，**这类票只可能由服务层产生**，API 层永远看不到它的创建。
- 注释声称「贷项通知单——对账单自然冲减应付」。**净额那半句是对的**（见 §二 S4），
  但「自然冲减」掩盖了「这张票自己永远不结清」。

### 2. 四个代码事实（全部真库实测，见 §二）

| # | 事实 | 依据 |
|---|---|---|
| F1 | `recalcInvoiceStatus` 的 Paid 判据是 `amount.gt(0) && Σapplied ≥ amount` ⇒ **amount<0 时永不 Paid**，永远停在 `Issued` | S2 |
| F2 | `applyAllocation` 的守卫是 `appliedAmount.gt(invoiceAmount) → AMOUNT_EXCEEDS_INVOICE` ⇒ 对 amount=−5000 的票，**任何正额核销都满足 `1000 > −5000`** ⇒ **400 直接拒绝** | S3 |
| F3 | 应付净额口径 `getArApSummary` **确实把负额计入**（`sumAmount(apInvoices)` 直接加 `amount`）⇒ 净额**正确** | S4 |
| F4 | `MaterialReturn.claimInvoiceId` 全库**只被 `procurementRoute` 用于「数据变更通知」** ⇒ **没有任何结清/冲销动作消费它** | S6 |

### 3. 两个缺陷

- **缺陷 A（S2 / S6）＝「死票」**：CLM 永远停在 `Issued`。**且无任何出口能收敛** ——
  - `applyAllocation` 正额 → 被拒（F2）
  - 负额核销 → 能写进去，但 `recalcInvoiceStatus` 仍返回 `Issued`（S2 实测）
  - `settleReturn` → **只把退换货单翻成 `settled`，完全不碰票**（代码实读）
  - `cancelReturn` → **只允许 `pending`**，已确认的索赔不可取消
  - 手工 `PATCH {status:'Paid'}` → 被 `STATUS_NOT_MANUAL_SETTABLE` 挡住
  - ⇒ 只剩「作废 / 软删」，而那两个是**撤销索赔**语义（见缺陷 B）
  → **后果**：应付账龄/对账单里永远挂着一张 `-5000` 的未结清票；`payable.count` 虚增 1。
  **钱不错**（净额对），但**状态永不收敛** —— 属**口径级/体验级**，不是挡单级。

- **缺陷 B（S5b）＝「账实不符 + 语义陷阱」**：作废 CLM 后，`MaterialReturn` **不联动** ——
  退换货单 `status='confirmed'` 且 `claimInvoiceId` **仍指向那张已 `Cancelled` 的票**
  → 退换货单侧显示「已索赔」，票侧显示「已作废」。
  → **账实不符**，且**没有任何出口能修正它**。

  > ⚠️ **本批自我纠错（重要）**：我最初把 S5 写成「作废 → 应付净额凭空 +5000 = 错账」。
  > **这个定性过重了** —— 如果操作者是**有意撤销索赔**，那笔 +5000 **是正确的记账**
  > （欠供应商的钱回来了）。真正的缺陷是**「无联动 + 无护栏 + 动作名叫『作废发票』」**，
  > 让操作者可能不知道自己撤销了索赔。**别把口径问题报成算术错。**

### 4. ★ 为什么**不能**简单加护栏（本批最重要的修法约束）

看起来最直接的修法是「给 `cancelInvoice` 加一句：被索赔单引用则禁止作废」。
**但那样会把唯一的出口堵死成死锁，比现状更糟**：

```
已确认索赔单的 CLM
  ├─ applyAllocation 正额        → 拒（F2）
  ├─ 手工 PATCH Paid             → 拒（STATUS_NOT_MANUAL_SETTABLE）
  ├─ settleReturn                → 只翻状态，不释放票
  ├─ cancelReturn                → 只允许 pending（已确认的不可取消）
  └─ 作废 / 软删                  → ★ 唯一出口 ← 加护栏就堵死这里 ⇒ **永久死结**
```

**所以正确修法必须先有业务口径**（见 §四）。这也是「加护栏前先确认出口存在」这条纪律的
第一个真实案例 —— 详见 §六 坑 2。

### 新增 11. **供应商索赔（贷项票）怎么「结清」？**（缺陷 A，对应批次 6 口径 4 的应付侧）

> 这与批次 6 的口径 4（「负数发票怎么算结清」）**是同一个口径**，只是这次有了**已上线的供应商侧实例**，
> 建议**合并一起判**。

### 新增 12. **撤销索赔的流程怎么做？**（缺陷 B）

现状：作废这张票 = 撤销索赔，但退换货单不联动、动作名也不叫「撤销索赔」。

- (b) **禁止直接作废**，要求走一个**新的「撤销索赔」动作**（需先建该动作 + 权限 + UI）
- (c) **保持现状**，仅加提示文案

> ⚠️ 选 (b) 前必须先把「撤销索赔」动作建出来，否则就是 §一.4 的死锁。

### 新增 14. **整单分配（`orderLineId=null`）跨行怎么分摊校验？**（2026-09-17 11:25 开主线 B 时撞到）

`shipping/allocationService.ts:302-303` 的**整单分配**分支：

```ts
const perLineQty = newActualQty / lines.length;          // 按【行数】均分
const perLineAllocated = totalAllocated / lines.length;
if (perLineAllocated + perLineQty > allowedMax) throw ORDER_LINE_OVER_ALLOCATED;
```

**代码自相矛盾**（所以判不出「是不是 bug」）：
- 第 262 行注释：「整单分配：**按订单所有行汇总校验**」← 说要做汇总
- 实现：**按行数均分**再逐行比上限
- 错误文案：「本次**均分**」← 承认是均分
- 测试注释（`shipping/__tests__/allocationService.test.ts:309`）也描述了均分机制

**后果（两种，方向相反）**：
- 行数量**低于均值**的行 → 均分**高估**其份额 → **误拒**（例：订单 1000+100 两行，整单分配 1100 → 均分 550 > 100 ⇒ 拒，但它其实合法）
- 行数量**高于均值**的行 → 均分**低估** → **校验形同虚设**

**选项**：
- (a) 按**行数量比例**分摊（最自然）
- (b) 按**剩余可出运量**比例分摊（已有部分分配时更公平）
- (c) **保守代理**：整单分配量不得超过「剩余量最小的那一行」的剩余（防用整单分配绕过行上限）
- (d) **保持均分**（若确为有意设计，请把第 262 行注释改成「均分」以免误导）

> ⚠️ 另发现一个**独立**缺口（同一函数）：**行级分支不把整单分配计入累计**
> （行级 query 只按 `orderLineId` 过滤，`orderLineId=null` 的行看不见）
> ⇒ 「先整单分配满额、再逐行分配」可**双重分配**。修它会让校验**变严**，可能挡住今天能过的流程 → 需口径。

### 新增 15. **离职/终止员工能否重新「入职」（返聘）？**（同上，开主线 B 时撞到）

  - (c) 允许返聘但要求走**独立的「返聘」动作**（新建动作 + 权限 + UI）

> ⚠️ **不要「顺手先修一半」**：看似可以只加「在职则拒绝」而不管返聘，但

## 五、坑（本批新踩，接手人直接复用）

1. **★ 块注释里的 `**/path**` 会提前终止注释**：写
   `/** … **/api/v2/finance/summary**（…） */` 时，`**/` 里的 `*/` **结束块注释** →
   后面的中文变成代码 → esbuild 报 `Unexpected "（"`。**注释里别写 `**/xxx`**（用 `//` 行注释或去掉星号）。
2. **★★ 加护栏前必须先确认「出口存在」，否则制造死锁**：见 §一.4。
   检查手法：把该实体的**所有**状态出口列一遍（`grep` 所有写 `status` 的路径 + 所有 `cancel/delete/settle`），
   逐个确认「加护栏后还剩几条路」。**一条都不剩 = 别加。**
3. **★ 演练的前置状态必须与「真实态」一致，否则假通过**：S5 第一版被
   `HAS_ALLOCATIONS` 拦下 → 看着像「有护栏」。真实态是 `allocCount=0`。
   **做法**：构造性输入用完**立刻删掉**，并加**前置断言**把这个前提钉住。
4. **★ 区分「口径问题」与「算术错」**：本批我先把 S5 报成「凭空 +5000 = 错账」，
   实则「有意撤销索赔」时那笔增加**正确**。判据：
   **先问「如果这是操作者有意为之，这笔数对不对？」** —— 对 ⇒ 是口径/体验问题；
   不对 ⇒ 才是算术错。**别 cry wolf。**
5. **V2 财务路由挂在 `/api/v2/finance`**（不是 v1）：`GET /api/v2/finance/summary`。

### 1. 普查口径（必须先定义清楚，否则数字不可比）

**「消费点」= scope 字面量出现在会改变运行时行为的代码里**（服务端 `requirePermission('x')`

**不算**消费点的「**登记 / 描述类文件**」（只声明存在或给人看，不改变行为）——
这是本次最容易搞错、也最容易**假绿**的地方：
