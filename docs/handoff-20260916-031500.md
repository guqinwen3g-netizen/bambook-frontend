## 零、开工前 8 条规矩（违反会直接返工）

1. **工作区是共享的**。开工先 `git status`；只 stage 具名文件；**绝不 `git add -A`**；**不要 push**（部署是用户的拍板项）。
2. **一次只做一批**。批内跑完：双端 `npx tsc --noEmit` 0 错 → 定向 vitest 绿 → `npm run check:tokens` → 真库跑一遍并**完整回滚** → feat+docs 成对提交 → 回报，等放行再开下一批。
3. **定性必须 `file:line`**。handoff 给的行号都已核实，动手前自己再看一眼；凡是没读到代码就下结论的，标 ❓ 并停下来问。
4. **测试要能证伪**：写完用例，把实现改回旧行为，用例必须转红。**「测试全绿」不等于「做到了」**。
5. **改后端必须重启**：本机 8081 是 ts-node，无文件监听。`pkill -f "ts-node src/index.ts"` 匹配不到（进程名是 `node`）→ 用 `lsof` 取 pid → `kill -9` → 确认端口释放 → 起 → 核对新 pid ≠ 旧 pid。**「3 秒就绪」本身就是警报**（冷启动约 20s）。
6. **隔离复跑分批**，一次 2~4 个模块，否则会被 SIGTERM（exit 137）。
7. **不要动依赖**（含 `npm audit fix`）。14 个已知漏洞在用户手上，xlsx 那条要换源，属拍板项。
8. **口径拿不准就问**，不要挑「看起来合理」的那种实现。本轮返工成本主要来自「按错靶子把功能做出来了」。

## 二、本轮踩到的 6 个坑（**直接抄，别重踩**）

1. **订单主档字段更新是 `PUT` 不是 `PATCH`**：`server/src/orders/route.ts:425` 只注册 `router.put('/:id')`，内部是部分更新语义（`stripReadonly` 白名单 + `tx.order.update`，会写 `fieldSources` + 审计）。**发 PATCH 返回空体 404**，看着像「订单不存在」。写 `null` 可清空字段（回滚靠它）。前端封装见 `services/apiService.ts` 的 `updateOrderFields`。
2. **源码级扫描测试必须先剥离注释再断言**。否则说明注释里提到「不能写什么 / 原先有个什么被摘了」就会误红，进而逼人删掉说明注释。范式：`components/order/orderShipmentEligibilitySection.test.ts` 与 `components/t5EntryPruning.test.ts` 的 `stripComments()`。
3. **两种契约断言性质相反，别混用**：
   - 「入口/字段**不存在**」→ 扫**剥离注释后的代码**；
   - 「口径说明**还在**」→ 扫**含注释的原文**（它守护的就是那段文字）。
4. **源码级断言证明不了「接线接上了」**：T4 的 G3 变体（把 `setGateBlock(extractGateBlock(error))` 改成 `setGateBlock(null)`）第一次**没转红**，因为断言只是「文件里有这个字符串」。解法：把判定抽成**纯函数**再给它行为测试。
5. **`check:tokens` 的 `L6 icon size`（基线 73 → 当前 75）在干净 HEAD 上就是红的**，不是谁弄坏的。验证方法（比 git stash 安全，不碰当前工作区）：
   ```bash
   git worktree add /tmp/bmb-head HEAD && cd /tmp/bmb-head && bash scripts/check-design-tokens.sh
   git worktree remove /tmp/bmb-head --force
   ```
   L3（68→60）、L7（6→0）也是存量漂移，方向是变好。
6. **订单页写权限与读权限是两套 scope**：出运资格回显是 `qc:read`（销售/销售经理/管理员/QC/物流都有，实测可读；**财务只能读、不能写**）；样品写是 `products:write`；订单字段写是 `orders:write`（**销售有、物流没有**）。

## 四、本轮新增的拍板口径（2026-09-16 业务方现场定，**不要再改**）

1. **船样 vs 匹头样的时点**（决定了两者写不同的真源）：
   - **船样（S/S）**：后整理刚出来、第一卷布就能剪 ⇒ **早**。写 `Sample(type='ship')`。
   - **匹头样（RC）**：**每一卷布各剪一小块**验色差；必须大货全部做完、准备出运前才剪得出来（实操常是「做完一半先剪一半」）⇒ **明显晚于船样**，属「投产后才发生」，**不进建单表单**，只在订单详情就地登记 `Order.fabricSampleSentDate/fabricSampleConfirmedDate`。
   - ⚠️ 门禁三条件真源**不对称是刻意的**：ss 读 Sample 表、rc 读 Order 字段。订单上的 `sampleSentDate/sampleConfirmedDate` 是第三套建模（watchdog 催办读它、门禁不认它）—— **已知口径分裂，未决**。
2. **电子画册（Lookbook）属于营销域**，留在营销页：它是**营销物料（不卖）**；产品档案里都是**可卖的产品**。产品档案侧不要加画册入口。
   （此前 handoff 把它列为「错挂在营销页」的待摘入口，经业务澄清后**作废**。）
3. **报关单必须锚定运单**：「不关联运单（手工录入）」入口已摘。理由：报关一定有对应出运（拼柜是多票报关锚一个柜，不会反过来），且空库从 0 上线不存在补录历史报关单场景；锚不到运单，D2 一致性校验就永远做不起来。**服务端仍允许 `shipmentId` 为空**（只摘入口不删服务能力）。
4. **一次性例外在同订单分批出运期间保持有效**（不是用一次就作废），到批条写的到期日为止。出运门禁刻意不调 `consumeException`（`shipping/shipmentEligibilityGate.ts:22-23`）。**这不是 bug，别顺手改。**
5. **产品档案的现货字段**（业务方原话）：「产品档案相当于一款产品的所有信息、所有详情」；现货数量**理想态是由库存关联显示**，而不是在产品档案上手工填 → 属**新功能**（要接库存取数），不在 T5 范围。落地前那两格保持现状（可填）。
