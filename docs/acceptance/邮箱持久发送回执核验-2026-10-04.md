# 邮箱持久发送回执候选核验

2026-10-04，当前候选已验证，尚未安装到公司测试 API。智能邮箱仍封存，但属于 V1 必须交付范围。

员工可能在一次发送等待期间重复点击，或者服务器已接受邮件但本地审计失败后重试。原服务没有持久占位，已用合成 SMTP 复现两条路径都会重复发送。候选先在独立事务提交 Email 唯一发送占位，冻结原正文、To/CC/BCC、发送身份及请求 Message-ID，再联系 SMTP。未知结果保留占位并拒绝再次传输；成功接收证明先独立保存，再把原生 Sent、审计及发送回执状态原子提交。后者失败只补本地事实，不重新发送。

成功证明要求 SMTP 完整接受冻结的 To、CC、BCC 集合，没有 rejected/pending。仅有 Message-ID 不算接受证明；邮件服务器接受不等于收件箱最终投递成功。持久记录不能删除、替换原内容或回退状态。原独立 `/email/send` 入口返回 410，不能绕过原生发件箱及发送记录；代码搜索未见产品消费者调用该旧入口。

## Agent 发送接线的有限独立核验

Agent 与 MCP 的 `email.send` 首次审批读取原生 Outbox 正文及完整收件人快照，审批 hash 绑定内容；批准后恢复原审批，不按今天的邮件重新造审批。发送采用当前可信执行身份和签名权限上限，原 requester 只作出处。旧通用 Agent 回执仅强制原结果核对，不能缓存成功或重置后重发。

发送密码保持临时内存，一次消费并绑定 actor、原邮件、SMTP user及已审批内容hash；错绑定不消费原件，首次客户端伪造credentialRef拒绝。accepted/sent回读不需要新密码，claimed/unknown不自动重发。两个runtime入口在策略拒绝、事件、日志及审批持久化之前清除嵌套pass和顶层password，未执行的MCP计划也安全投影。
