## 四、坑（本批新踩，接手人直接复用；已同步进 skill）

1. **★ finance 发票路由是 `router.post('/')`** —— 建票走 `POST /api/v1/finance/`
   （**不是** `/api/v1/finance/invoices`），作废走 `POST /api/v1/finance/:id/cancel`。
   照搬别的域的路径会吃 **404** 并误判成「门禁/接口坏了」。
   写脚本前先 `grep -nE "\.(get|post|patch|put|delete)\(" server/src/<域>/route.ts` 核一遍。
2. **★ fire-and-forget 的异步重算会让负向用例假红**：发票创建后的批次重算是
   `notifyShipmentBatchSettlementRecalc(prisma, ...).catch(...)` —— **不 await**。
   建完单立刻读快照当 `before` → 读到「上一笔重算还没落定」的中间态 → 随后它落定 →
   断言「被拒后快照未被改动」**假红**（本批真踩到）。取 `before` 前必须
   `waitFor(快照 == 预期基线)` 轮询落定。
3. **★ 一个演练里「承重断言」通常只有一两条，要如实标注**：真库证伪时**只有承重断言转红**。
   作废路径下 `paid` 必为 0（有核销的票根本不让作废）→ `settleStatus` 恒 `unsettled` →
   那条断言**不具区分度**。若把护栏也标成 ★，后人看到「证伪只红一条」会误判成「测试没钉住」。
4. **★ `order_auto_settle` 审计 0 条 ≠ hook 坏了**：真库**没有一笔真实核销把票核到 Paid**
   （那 10 单「全 Paid 未结案」是 `SIM-ALLOC-*` **seed 直写库**造的，绕过 API）。
   **空过的验证器等于没有验证器** —— 不能拿「0 条」当 bug 证据，要靠代码事实 + 构造会踩它的输入。
5. **`InvoiceAllocation` 是硬删除模型**（无 `deletedAt` 列）：`recalcSettlement` 里过滤它会
   触发 PrismaClientValidationError，源码已注释说明 —— 别"顺手补上软删过滤"。
6. **`AuditLog` 没有 `source` 字段**：`writeRouteAuditLog` 的 `source` 落在 `detail` 里；
   `groupBy(['source'])` 会报 `Invalid value for argument by`。
7. **后端重启核对**：`launchctl print gui/501/com.bambook.dev-server` 在沙箱里**看不到输出**；
   可靠办法是看 `/api/health` 的 `tts.prewarmAt` 是否变化（每次重启都会刷新）+ 循环重试直到 200
   （ts-node 冷启动约 5–15s）。

### ★ 本批踩到的「验证器空过」（值得单独记）

写 `recalc-stale-batch-snapshots.mjs` 时，`computeExpected` 里把**算出来的**
`invoiced/paid` 同时塞进了 `actual` 和 `expected` 两个字段 —— 于是 `actual ≡ expected`，
**金额差异永远测不出来**，只剩 `settleStatus` 还能比对。首跑 dry-run 只报 1 个不符（真值 5 个），
差点据此得出「只有 1 个批次需要收敛」的错误结论。
**教训**：构造 `actual`（现值）与 `expected`（期望值）时，必须确认两者**来源不同**
（一个读库、一个算出来），否则就是在自己跟自己比。
