## 3. S0 · A 服务端错误模型（收敛到已有真源，不新造出口）

### 3.1 现状（实测）

统一出口**已存在**：`server/src/shared/routeError.ts` 的 `safeRouteError()`，配套棘轮守卫
`server/src/shared/__tests__/routeError.test.ts`（逐文件计数冻结基线，2026-09-17 为 272 处 / 25 文件）。

**注意：既有棘轮对本 spec 点名的 5 个域是盲的。** 其正则为
`/res\.status\([^)]*\)\.json\([^\n]*e\?\.message/g`，**要求同一行出现字面量 `e?.message`**。
两种写法都因此逃过计数（2026-09-20 执行 Task 1 时实测确认）：
- `risk`：先 `const msg = e?.message`，下一行再 `json({ message: msg })` —— 跨行，漏计；
- `hr` / `dashboard` / `reporting`：写的是行内 **`err.message`**（不是 `e?.message`）—— 字面量不匹配，漏计。
  这 3 个文件内 `e?.message` 出现 **0 次**，故旧基线里命中 0/0/0。

⇒ 直接按现棘轮收敛这 4 个域，**基线一动不动，会产出「修完了但没人知道」的假绿**。
该守卫文件自己在 `:36-44` 就记录过同类事故（窄口径 203 / 宽口径 252，49 处不可见）。
**连带推论**：`err.message` 与 `e?.message` 的判据差异是全局性的，旧棘轮在**整个仓库层面**都在低估
（例如基线里 `crm/crmRoute.ts` 记 27 处，而行内 `err.message` 写法的其它文件可能整片不可见）——
S0-A1 Task 6 落账时须复核旧棘轮是否需要再一次加宽。

本次另按**文件级**实测。判据（不依赖脆弱的行数统计，也不误伤日志里的 `err.message`）：
**定义了 Express Router 的文件里，若存在 `catch` 内的状态码响应，就必须引用错误真源
（`shared/routeError` 或 `lib/asyncHandler`）**。实测**违规 46 个路由文件**，
清单已由脚本冻结为守卫基线（见施工单 Task 1）。

四个真缺陷：

1. **识别规则过窄**。`routeError.ts:62` 判「业务错误」靠 duck-typing：`typeof code === 'string' && typeof statusCode === 'number'`。
   而全仓 **12 个自定义 error class** 无共同基类（`HrError`、`CrmValidationError`、`StockMovementCasConflictError`、
   `StageGateError`、`TemplateNotFoundError`、`TemplateRenderError`、`SsrfBlockedError`、`SealValidationError`、
   `CreditBlockedError`、`GateBlockedError`、`FabricCalcValidationError`、`RoleWriteRejectedError`），
   不满足该形状者会被当未预期异常 ⇒ 业务文案被吞、状态码兜成 500。
2. **10 个域各有一份「用中文字符串猜状态码」的 helper，且关键词清单互不相同**：
   `risk/riskRoute.ts:80`、`qc/qcRoute.ts:104`、`seasons/seasonRoute.ts:77`、`pricing/pricingRoute.ts:96`、
   `suppliers/factoryRoute.ts:76`、`businessLines/businessLineRoute.ts:43`、`customs/documentTemplateRoute.ts:46`、
   `products/lookbookRoute.ts:49`、`products/fabricRecommendationRoute.ts:43`、`email/signatureRoute.ts:54`。
   ⇒ **同一句错误文案在不同域会得到不同 HTTP 状态码**（如含「至少」的文案在
   `fabricRecommendationRoute` 判 400、在 `riskRoute` 判 500），且都把 `e.message` 原样放进响应。
3. **响应体两种形状并存**（flat `{ error, message }` 与 nested `{ error: { code, message } }`），
   都是既有前端契约 —— 收敛时**必须保持原形状**，不得顺手统一。
4. **`shipping/shipmentMutationService.ts:130-144` 的 `passThroughCodes` 白名单手维护**，
   新增 code 忘记登记即静默退化为 fallback code。

### 3.2 设计（收敛到既有管道，而非改写数百个 catch 点）

**关键发现：本仓其实已有两套错误出口，且管道那套几乎没人走。**
- `lib/asyncHandler.ts` 提供 `asyncHandler()` + **`globalErrorHandler`**（Express 4 参错误中间件，
  `index.ts:1909` 已 `app.use` 挂载，`index.ts:306` 另挂进程级 `registerUnhandledRejectionGuard`）。
  它已经做了「未预期异常 → 通用文案、明细只进日志、P2025 → 404」。
- **但全仓只有 `customer/route.ts` 一个文件在用 `asyncHandler`** ⇒ 管道活着，路由不走。
  各域自己 `catch { res.status(500).json({ message: err.message }) }`，等于**把本该流入管道的错误截断了**。

⇒ 收敛方向确定为：**让路由流入既有管道**（删本地外泄 catch + 用 `asyncHandler` 包裹），
而不是给每个 catch 点补一个安全映射。前者是**减代码**，后者是维持 700+ 个手写站点。
`shared/routeError.ts` 不废弃，**降级为「需要保留原响应形状时的映射函数」**，且与管道**共用同一张码表**。

**⚠️ 执行更正（2026-09-20 批次级 R5 戳出，此处如实回写）**：上面这句是**目标终态**，不是本批实际达成的状态。
实测路径被拆成两段，本批只走了第一段：
- **第一段（已做）**：域的 catch 留在原地，但内部改走 `resolveError` 码表 ⇒ 外泄文本收口 + 状态码不再靠猜。
  `risk` 域即此形态（`riskRoute.ts` 的 `handleError` 未删）。
- **第二段（未做）**：删掉 catch、用 `asyncHandler` 让错误流进管道 ⇒ 真正的"减代码"。**未做的原因不是偷懒**：
  删 catch 会让**未登记的业务文案**被兜成通用提示（吞掉给用户看的话），必须先满足两个前置 ——
  ① 该域所有面向用户的业务码进表；② 域内测试能证明"删了 catch 用户看到的字没变"。
  现状是 `asyncHandler` 仅 3 文件 / 30 处接入（分母 80 文件、约 1118 端点）⇒ **本批不得声称"已减少外泄面"**；
  全仓仍有 **267 处 `message: err.message` 直上响应体（41 文件）**，其中 `hr/route.ts` 一个文件 36 处。
  另：auth 中间件（`auth/moduleGuard.ts`、`auth/permissionGuard.ts`）对**所有**端点用 **flat** `{ error, message }`
  回答 401/403 并携带内部 scope 标识 ⇒ 它既是形状不一致，也是 G7.5「找谁」的缺口。
  ⇒ 登记为 **B22 / B23**（见 plan 的后续批次与权威文档 §9）。

- **A1 统一契约（最关键一步，一处生效）**：升级 `globalErrorHandler`，使其与 `safeRouteError` 同语义 ——
  ① `code: string` + `statusCode: number` 的业务错误 → **透传 code/message/status**；
  ② **`details` 必须透传**（`GATE_BLOCKED` 409 携带的 `gateDetails` 是
  `ShipmentGateBlockedPanel` 的输入，丢了就把已交付的出运门禁前端打断）；
  ③ 其余 → 通用文案。此步先做，否则把路由接进管道会** regression 掉现有业务提示**。
- **A2 错误码注册表 `shared/errorCodes.ts`**：与 `routeError.ts`、`asyncHandler.ts` 同层共用，
  每个 code 声明一次 `{ status, 业务文案, 是否可携带 details }`。
  把「203 处业务文案」从逐 catch 点手艺活转成**每码一份表**。
- **A3 先加宽守卫，再谈收敛**：新增**文件级守卫**（判据见 §3.1），把当前 **46 个违规路由文件**
  冻结成豁免清单（只许减不许增）。没有这一步，收敛 5 个域不产生任何可核对信号（§3.1 盲区）。
- **A4 十份 `isClient` helper 一并清除**：它们靠中文子串猜状态码、跨域结论不一致（§3.1 缺陷 2），
  收敛后整类删除；域内文案归入 A2 注册表。
- **A5 12 个 error class 定型**：逐个核准是否满足 `code` + `statusCode`；不满足者补齐（**不新增 `throw`、不改抛出点**）。
- **A6 摘除豁免，按域收敛**：`risk` → `dashboard` → `reporting` → `hr` → `marketing`，
  每域一个可回归的批次，做完即从豁免清单摘一行。
- **A7 明文禁令：不得做机械替换。** `routeError.ts:38-40` 已警告：
  许多站点的 `e.message` 本身就是有意给用户的业务文案（如「币种必填」），机械替换会吞掉它。
  **逐处核准后收敛**；删 catch 前必须先确认该文案在 A2 注册表里有对应的码与文案。
- **A8 结构守卫**（三条，各自带阳性对照）：
  ① route 内不得出现 `msg.includes('<中文>')` 式的状态码分档；
  ② `status(5xx)` 响应体不得拼 `e.message`；
  ③ 抛出的 code 必须存在于注册表。

### 3.3 数据流（收敛后）

service 抛错误 → 路由**不再自己 catch** → `asyncHandler` 把 rejection 交 `next(err)`
→ **`globalErrorHandler`（`index.ts:1909`）按 A2 注册表映射**：
业务错误透传 `code`/`message`/`status` 与 `details`；未预期异常回通用文案，原始栈只进日志。
**注意键名是 `details` 而不是 `gateDetails`** —— 见下方 ⚠️ 迁移前置约束。
响应形状**按域保持现状**（flat `{ error, message }` / nested `{ error: { code, message } }` /
`{ ok:false, error, message }` 三种都是既有前端契约，本次不统一）。
前端 `readError`（`services/exceptionService.ts:163`）按 code 消费、保留 `details`。

**⚠️ 迁移前置约束（Task 3 执行时发现，后续批次不得忽略）**：`resolveError` 把明细归一成 `details` 一个键，
但**已上线的出运门禁链路用的是 `gateDetails`**：`shipping/route.ts` 返回 nested
`{ error: { code, message, gateDetails } }`，前端 `services/shipmentService.ts:64,77` 的 `extractGateBlock`
**要求 `gateDetails.orders` 存在**才认这条门禁响应。
⇒ **`shipping` 域在下列两件事做成之前，禁止接入 `globalErrorHandler`**：
① 迁移时同时保留 `gateDetails` 原键名，或 ② 先扩 `extractGateBlock` 让它同时接受 `details`。
否则门禁面板会**静默失效** —— 用户只看到一句提示、看不到「哪个订单缺哪条」，
正是矩阵 §二 H11 那条缺陷的复现。S0-A1 只收敛 risk/dashboard/reporting/hr/marketing 五域，不触发本约束。

### 3.4 波及面

新增 1 文件（`shared/errorCodes.ts`）；实质改动集中在 `lib/asyncHandler.ts`（A1 契约）、
`routeError.ts`（接注册表）、5 个域的路由（**删代码为主**）、12 个 error class 的携带字段。
**不改 schema、不动业务判定逻辑 ⇒ 无迁移、无回填、不碰存量数据。**
