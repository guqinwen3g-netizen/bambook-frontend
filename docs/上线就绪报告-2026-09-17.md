## 三、风险（逐条核实）

| 项 | 结论 |
|---|---|
| **29 条迁移的破坏性** | ✅ **几乎为零**：全量扫描只有 **1 条** `DROP INDEX IF EXISTS "ProductAsset_sku_idx"`（有 `IF EXISTS` 兜底）；其余**纯新增**（29 条合计建 **26 张新表**）。**无** DROP TABLE/COLUMN、**无** SET NOT NULL、**无**改类型、**无** DELETE/TRUNCATE ✓ |
| **迁移账本漂移** | ⚠️ **唯一真实风险**。本仓**已知**：库曾用 `db push` 领先账本（六表 + 部分列未记账）⇒ `migrate deploy` 会报 `duplicate column / relation exists` **并中止部署** ✗ |
| **漂移的补救** | ✅ **已有工具**：`server/scripts/fix-migration-ledger.ts`（**默认 dry-run** 出报告；`--apply` 才补账）。**在 Mac mini 上跑** |
| **回滚** | 以新增为主 ⇒ 回滚 = 回退代码（多出来的表/列无害）；`DROP INDEX` 那条需重建索引（低危） |
| **本机 dev server** | 不影响生产（本机是开发机；生产在另一台 Mac mini 的 `~/bambook-main-api/`）|

## 四、★ 上线前**必须确认**的两件事（我从本机无法确认）

### 1. Mac mini 上有没有 `com.bambook.ops-panel-auto`？

旧记：它「**每分钟拉 GitHub main，push 即上线**」。
- **本机已确认没有**这个 LaunchAgent ✓（`launchctl print` → "Could not find service"）
- ⚠️ 但它若**仍在 Mac mini 上跑** ⇒ **`git push` 会直接触发生产部署** ✗
- ⇒ **push 之前必须先在 Mac mini 上确认**：
  ```bash
  launchctl print gui/$(id -u)/com.bambook.ops-panel-auto   # 存在则说明会自动部署
  ```

### 2. 生产库的账本漂移程度？

在 Mac mini 上跑（**只读**，dry-run）：
```bash
cd ~/bambook-main-api && npx ts-node scripts/fix-migration-ledger.ts
```
输出「已记账 / 未记账（需补账）/ 仍缺失」三态 ⇒ 决定要不要先 `--apply` 补账。
