## 二、L2 #17「未投产取消被挡 / 已出运反而能取消」—— 勘察 + 真库演练 + 修掉其中真 bug

### 1. 设计真源 vs 实现（对撞）

`docs/design/03-业务规则/订单变更规则.md` §2A.1 原文：

| 阶段 | 变更权限 | **取消/暂停权限** |
|---|---|---|
| **草稿/待审批** | 业务员可直接修改/撤回 | **业务员可直接取消/暂停** |
| 已批准（正式承诺） | 须走正式申请与审批 | 须走取消/暂停申请与审批 |

→ 设计明确要求「**Pending 订单业务员可直接取消**」。系统里有没有这条路？

### 2. ★ 三条路逐条对撞（`scripts/acceptance-pending-cancel-path.mjs`，真库实测）

| 路 | 代码事实 | **实测** |
|---|---|---|
| ① `DELETE /api/v1/orders/:id`（UI 文案是「**归档**」） | `orders/route.ts:519` `requireRole('owner','admin','manager')` | **sales → 403**（前端 `canArchiveOrder = hasRole('owner','admin','manager')` → 按钮对业务员不可见） |
| ② `POST /api/v1/order-changes {changeType:'cancel'}` | `APPROVED_ORDER_STATUSES` 不含 Pending（`orderChangeRequestService.ts:86/336`） | **sales → 400 `ORDER_NOT_APPROVED`** |
| ③ `POST /orders/:id/status-transition {toStatus:'Cancelled'}` | `VALID_ORDER_STATUSES` 只有 6 态、**不含 Cancelled**（`orderLifecycleService.ts:24`） | **400 `INVALID_STATUS`** |

**⇒ 业务员对 Pending 订单的「取消」零路径**（三条路全堵），而设计明确要求有。

**更糟的是 UI 会误导**：`OrderChangeRequestsSection.tsx:477` 对非已批准状态显示
「**当前状态可直接编辑**；仅已批准订单…需走本审批链」—— 可编辑 ≠ 可取消，业务员会以为能取消。

### 3. 反向不对称（同一处状态判据的另一面）

- `APPROVED_ORDER_STATUSES = ['Confirmed','Production','Shipping','Delivered']` **含 `Delivered`**
  → 已交付（订单状态机里的**终态**）反而**可以**发起取消申请（**实测 201，订单 → `CancelRequested`**）。
- `deleteOrder`（`orderLifecycleService.ts:117-191`）**只查依赖（发票/分摊/出运/凭证）、不查状态**
  → owner/admin/manager 可对**已批准订单**直接软删 = **绕过 DR-010 整条审批链**
  （无影响汇总、无审批、无结案处置）—— **实测 Confirmed 订单 `DELETE` → 200，`deletedAt` 置位**。

### 4. ★★ 修掉的真 bug（**不需要口径**）：守卫态推进返回 **500**，应为 409

**演练 S11 首跑实测**：订单处于 `CancelRequested` 时推进状态 → **HTTP 500**。

**根因 = 本仓第**三**次踩「错误码 → HTTP 白名单漏码」**：
`orders/route.ts:561` 的 `statusCodeMap` 漏了 `ORDER_LIFECYCLE_GUARDED` / `ORDER_ALREADY_CLOSED`
—— 这两个码由 `throw` 抛出、**刻意不进 `OrderLifecycleErrorCode` 联合类型**
（`orderLifecycleService.ts:55-58` 有注释说明「扩展需跨域协调」），
于是 `map[code] || 500` 兜成 **500** ⇒ 用户看到「服务器错误」，
而不是「请先完成或撤回取消申请」→ **卡住 + 骂娘**。

> 前两次：`allocationMutationService.toAllocationError`（`-051500` T5）、`invoiceMutationService.toError`（`-074500`）。

**修法（不只补码 —— 从结构上断掉第四次）**：

1. **映射收成唯一真源** `orderLifecycleService.ORDER_LIFECYCLE_ERROR_HTTP_STATUS`，
   类型 `Record<OrderLifecycleErrorCode | OrderLifecycleExtensionErrorCode, number>`
   ⇒ **少一个键就编译不过**；V1 路由改为读它（不再各写一份 map）。
2. `agent/orderLifecycleFlow.ts`：把两个码纳入 `OrderLifecycleFlowErrorCode` + 补 `userAction` 文案
   （此前 `userActionMap[code]` 取不到 → `userAction: undefined`，同一根因）。
3. **回归门禁**：`orders/__tests__/orderLifecycleRoute.test.ts`（+4 例，含 `PauseRequested`/`Closing`/`Paused`）
   + `orders/__tests__/orderLifecycleErrorStatusMap.test.ts`（映射完整性结构守卫，4 例）。

**未改（明确留白）**：V2 `PATCH /orders/:id/status` 经 `orderServiceV2.ts:681-682` 已映射成 409，
但**码被泛化成 `INVALID_TRANSITION`**（前端无法区分「守卫态」与「非法转移」）—— 体验级，未动。

### 1. ★★ 「同模块红」不能当偶发 —— 我上批就是这么漏掉回归的

### 2. ★★ 新增一次 Prisma 读 = 打穿所有「mock 不完整」的既有路由测试

`tx.invoiceAllocation.aggregate` 在既有 mock 里不存在 → `TypeError` → 路由 500（表现成「业务逻辑坏了」，
实际是 mock 缺方法）。**改服务层后跑该模块的**全部**测试文件。**
另：`statusTransition.test.ts` 的 `invoiceFindUnique` 是**无状态** mock（`update` 后仍返回旧行）——
**状态断言必须用有状态 mock**，否则「重算」断言恒真。

### 3. ★ 第三类「错误码 → HTTP 白名单漏码」，这次把根断掉了

三次同坑（`toAllocationError` / `toError` / `orders/route.ts`）。
**根治手法**：把映射收成**唯一真源常量** + `Record<完整联合类型, number>` ⇒ 少键编译不过。
**但前提是「完整联合类型」真的完整** —— DR-010 那两个码被**刻意排除在类型外**，
所以「编译期强制」对它们**失效**，必须显式并进来。
**判据（通用）**：`map[code] || 500` 这种写法，先问「**运行时真会出现的 code 集合**」是不是等于
「类型里声明的 code 集合」—— 不相等就是下一个 500。

### 4. ★ `throw` 出去的错误码不会进「返回类型」的联合类型

`deleteOrder` / `transitionOrderStatus` 里的守卫都是 `throw Object.assign(new Error(...), { code, statusCode })`，
`statusCode` **在 catch 里被丢掉**（`OrderLifecycleError` 没有这个字段）→ 路由只能靠 map 重建。
所以**守卫码必须和业务返回码一样被登记进映射**。

### 5. 真库演练的新形态：`缺口（待口径）` 与 `失败` 分开计数

发现「系统行为已确认、改不改要业务拍板」的项时，别用 `fail()` —— 那会让脚本永远红、失去复跑价值。
用独立的 `gap()` 计数，汇总行单独列出。**别让待口径的项污染「脚本健康度」。**

### 6. ★★ 前端有一批「扫描服务端源码」的契约测试 —— 改服务端源码会打红前端门禁

`components/*RuntimeQa.test.ts`（`orderLifecycleRuntimeQa` / `invoiceMutationRuntimeQa` /
`paymentReconcileRuntimeQa` / `mainChainRuntimeQa` / `financeVoidDeleteRuntimeQa` …）
用 `fs.readFileSync('../server/src/**.ts')` 读**服务端源码文本**做正则断言。
本批把路由里的内联 `statusCodeMap` 换成共享常量 → `orderLifecycleRuntimeQa.test.ts:210`
断言 `INVALID_STATUS: 400` 字面量仍在路由里 → **红**（服务端全绿也拦不住）。

**做法**：改服务端源码后，先 `Grep "\.\./server/src/"` 找出所有扫源码的前端测试跑一遍
（`npx vitest run components/<命中文件>`，几秒钟）；**不要**只看服务端门禁就宣布完成。
改断言时**保持原意**（本批从「路由里有字面量 map」改成「路由委派真源 + 真源含这些键」，
并加一条反向断言 `not.toMatch(/statusCodeMap/)` 防回退）。

### 7. 环境坑（沿用）

服务端测试与 dev 服务**共用同一个 Postgres**（`server/src/test-setup.ts` 加载 `.env.local`）
→ **演练与全量测试不能同时跑**（会互相清行）。
`launchd` 托管后端不继承 shell env · `ts-node` 无 watch 必须 `kickstart -k` + 健康检查循环
（实测 10×2s = 20s ready）· 沙箱 `curl` 必须 `--noproxy '*'` · BSD `grep` **不支持 `\|`**（本批又踩两次）·
`zsh` 下未加引号的 glob 会中止整条命令 · heredoc 里 `${...}` 仍会被 zsh 展开（改用 Write 工具写脚本）。
