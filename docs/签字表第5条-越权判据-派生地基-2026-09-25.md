## 一 真源与完整性（实测，2026-09-25）

RBAC 有**两份**：

| 角色 | 路径 | 用途 |
|---|---|---|
| **单一权威真源** | `lib/rolePermissionMatrix.ts`（42,812 B） | `server/scripts/seed-rbac.ts` 首次部署写 DB |
| **服务器侧快照副本** | `server/src/_shared/rolePermissionMatrix.ts`（43,148 B） | 守卫运行时 fallback（`permissionGuard` / `permissionService`） |

副本的头文件自己写着：「**当修改 `/lib/rolePermissionMatrix.ts` 时 必须 同步更新此文件内容**。否则：seed 脚本（用 workspace lib 真源）与 服务器守卫（此副本）矩阵不一致。」——**这正是本仓头号病（多套并行真源）的高危形状**。

**本批实测结论：两份是一致的。** 方法与读数：

```
剥掉块注释 / 行注释 / import 之后，去掉全部空白字符再比：
  两份长度都是 19331 字符，**完全相等** ✓
差异只有 25 行，全部是头注释与 import 路径（`../types` vs `./_typesView`，因相对路径不同而必然不同）
```

⇒ **权限值这一层没有分歧**（这是个**阴性**结论，但值得记：下次不用再怀疑一次）。
⚠️ **未核**：那条"必须同步"的纪律**有没有守卫**（`rolePermissionMatrix.test.ts` 存在，本批**没读它是否覆盖"两份同步"这一条**）⇒ 下一批补。

## 四 下一批：派生表要怎么做（取数路径已定）

1. **关键写操作清单**：从路由的 `requirePermission('<域>:write'…)` 取 —— 实测形状（`orders/routeV2.ts`）：
   `post('/')` / `put('/:id')` 等 = `requireWrite, requirePermission('orders:write')`；只读是 `':read'`。

2. **逐 cell 派生** allow/deny：角色 × 写操作 → 该角色权限集是否含该码（含 scope/敏感字段维度）。
3. **与历史 3×3 证据对撞** ⇒ 输出**已覆盖 / 未覆盖**两张清单（第 5 条要的正是"3×3 不能代替"的那部分）。
4. ⚠️ 派生是**静态**结论（权限集 × 路由要求）；**要证"真的拦住了"仍需运行时证据** ——
   两者要分开报，别把"派生=允许"写成"实测=拦住了"。
