## 1. 问题的真正形状：两个正交轴（我上一版最大的错）

| 轴 | 问的是 | 手段 | 现状 |
|---|---|---|---|
| **广度轴** | **有没有漏** | 面清单：从**产物**枚举 | 空（"全部"现在是手写的） |
| **深度轴** | **够不够好** | 评分：从**角色视角**、挂证据 | 空（现在只有过/不过） |

★ **两个轴互不替代**，只补一个都不成立：
- 广度够、深度不够 ⇒ 全都"能用"，但**不好用**、设计低端（正是使用方说的"貌似能通过但没有意义"）。
- 深度够、广度不够 ⇒ 少数功能打磨得很好，**大半没看过**（正是使用方说的"还会漏很多"）。

★ 所以推进必须**同时**沿两个轴走，且**先立轴、再填格子**。

## 2. 三个参照物（缺一不可）——★ 最大的天花板在第二个

| 参照物 | 回答的问题 | 来源 | 现状 |
|---|---|---|---|
| **① 产物** | 现在**有什么** | 源码路由 / 运行中 DOM / Prisma DMMF / 各注册表 | 可枚举，**未做** |
| **② 业务领域模型** | **应该有什么** | 真实单据、KB、原需求文档、你的经验 | **散落，未收拢** |
| **③ 场景规格** | 具体**该等于几** | 从 ② 独立生成 | 无 |

### ★★ 关键认识：没有 ②，"漏了功能"永远发现不了

产物枚举只能告诉我**已有什么**。要发现"该有却没有的"，必须有一个**独立于这份代码的领域参照**。

**但这个参照不需要使用方动手** —— 它**已经在现有材料里**，只是没人把它收拢成一张表：
- `BusinessDocu/00-Entities/` 的 **86 份真实单据**（真实业务长什么样）
- KB 的 **22 处**（业务规则的口头记录）
- 原需求文档、`company-sim/` 的场景设定

★ 把它们**收拢成一张"业务能力清单"**（客户/报价/订单/采购/生产/质检/出运/报关/收汇/索赔/库存/报表… 每项下应有的能力与规则），
这张表**与产物清单对撞**，两个方向都会出东西：
- **实现了但清单里没有** ⇒ 可能是"没人提要求却做了"（也可能是我收拢漏了）
- **清单里有但没实现** ⇒ **真缺口**（这就是"漏了功能"能被发现的原因）

## 3. 我上一版漏掉的一整个维度：数据 / 时间 / 并发

企业级软件最狠的 bug 不在"点不点得动"，在**并发与时间**。上一版一个字没提，这里补上：

| 项 | 为什么致命 |
|---|---|
| **并发** | 两个人同时改同一张单 / 同一张票核销两次 |
| **幂等** | 重试、双击、网络抖动后重复提交 |
| **部分失败** | 一个事务里第三步失败，前两步是否回滚（本仓已多次踩） |
| **定时任务** | 跑两次会怎样？漏跑一次会怎样？ |
| **历史数据** | 老数据在新逻辑下是否仍算得对（本仓踩过：百分比量纲、时间列哨兵） |
| **不可逆动作** | 作废、结清、发货——错了能不能回来 |

★ 这一维度**不靠"看屏面"**，靠**针对性构造**（并发双写、重放、注入失败）。它是独立的第 5 个工作层。

## 4. 评分体系：从"过/不过"到"角色 × 维度 × 证据"

### 4.1 角色（从业务来，不从代码来）
业务员 · 跟单 · 财务 · 仓管 · 管理员 · 老板 · 客户（外部）

### 4.2 每个角色一张 **job-to-be-done** 清单（他要干成什么事），不是功能清单

### 4.3 每个面按 7 维打 0–5 分，**每分必须挂证据**

| 维度 | 问的是 | 锚点示例（防"分数漂移"） |
|---|---|---|
| 做得到吗 | 该角色能否完成 | 做不到 = 0 |
| **做得快吗** | 几步 / 几次点击 / 多少字段 | ≤3 步 = 5 · 4–5 步 = 4 · 6–8 步 = 3 · >8 步 = 2 |
| 看得懂吗 | 标签/状态/下一步是否显然；错误是否给"怎么办" | 提示含下一步 = 5 · 只报错 = 2 |
| **错得回来吗** | 误操作可否撤销 | 有撤销 = 5 · 无 = 1 |
| 数字可信吗 | 多屏同数；来源可见 | 同数且可见来源 = 5 |
| 边界对吗 | 空/零/负/超大/重复/无权限 | 每态未处理扣分 |
| **设计是否低端** | 裸码上屏 / 暴露英文枚举 / 要记 ID / 无批量 / 要手抄数字到别处 | 命中一项 ≤3 分 |

★ **锚点必须先写死再打分** —— 否则同一件事今天 4 分明天 2 分，分数就没有可比性。

### 4.4 ★★ 最要紧的一条纪律：**打分时"只看屏面"**

不许读源码找办法。因为**我知道代码**，一读源码就会"替软件圆场"，而真实用户没有这个特权。
★ 这一条把"我作为开发者"切换成"**我作为那个角色的真人**"，正是使用方要的。

### 4.5 诚实标注：这个分数是谁的判断
- 它是「**我以该角色身份、按可观察证据给出的判断**」，**不等于**业务方的判断。
- 但每分**挂证据** ⇒ **可被抽样复核、可被你推翻**。这是它能成立的原因。

## 5. 优先级函数与停止线（上一版没有，等于没有策略）

**优先级 = 风险 × 使用频度 × 不可逆性 ÷ 成本**

| 分层 | 达标线 |
|---|---|
| 财务链（开票/核销/收付汇/索赔/结账） | **必须 A 级**（有外部参照） |
| 出运链（订单→生产→质检→出运→报关） | **必须 A 级** |
| 权限与越权 | **必须 A 级** |
| 日常业务操作（报价/订单/库存/客户） | **必须 B+** |
| 边缘报表、集成、设置项 | 可 B |

★ **没有停止线的策略 = 无限期 = 没有策略。**

## 6. 闭环与回流 —— ★ 本项目最大的历史风险

现状：台账已有 **31 条待拍板**。若再产生几百条发现而**没有决策路径** ⇒ **更大的坟场**。

★★ **策略上最危险的不是"发现不了"，是"发现了没人拍"。**

所以必须**先立决策路径**（在做 P0 之前）：

```
发现 → 分级（阻断/缺陷/口径/低端设计/建议）
     → 每级指定"谁能拍" + "多久内拍" + "不拍的默认处置"
     → 修复 → 复评 → 销账
```

★ **"不拍的默认处置"必须写死**（例：超期未拍的**口径类**默认取"现状 + 显式提示"；**阻断类**默认阻塞上线）。
否则"待拍板"就是无限期悬空，等于没发现。

## 7. 证据必须可重放（否则做完就腐）

每条结论 → 指向：**脚本 + 输入数据指纹 + 当时截图**。
代码一变 ⇒ 指纹变 ⇒ **受影响的结论自动失效并重新排队**。

★ 没有这一条，证据是一次性的；三个月后没人知道哪些还成立。

## 8. 风险与失败模式（预判我自己会怎么失败）

| 失败模式 | 症状 | 对策 |
|---|---|---|
| **广度错觉** | 枚举出 1,800 项就以为"全了" | 枚举器本身会漏（动态注册路由、条件渲染控件）⇒ 用**两种独立方式**枚举（源码扫描 + DOM 爬取）**互相对撞**，差集就是漏 |
| **评分漂移** | 同一件事今天 4 分明天 2 分 | **先写死锚点**再打分 |
| **自己给自己圆场** | 读源码 → 替软件解释 → 分数虚高 | "只看屏面"纪律 + **抽样复核**（你抽 10 条看证据） |
| **修不完** | 挑软的修，难的留坟场 | 停止线 + 决策路径 + **默认处置** |
| **工具自嗨** | 时间花在建框架，没看软件 | **时间盒**：每个工作包限时，到点必须出结论 |
| **广度代替深度** | "1,800 项全绿"却不好用 | 分数是**主判据**，绿只是最低门槛 |

## 9. 工作层（重新分层，与 v1 的 P0–P7 对应关系见括号）

| 层 | 名称 | 作用 | 依赖 | 需要外部条件吗 |
|---|---|---|---|---|
| **L-A** | **产物枚举**（v1 的 P6） | 定义"现在有什么"，给出**总数** | 无 | 不需要 |
| **L-B** | **业务能力清单**（v1 未单列，新加） | 定义"应该有什么" ⇒ 才能发现**漏** | 无（材料已在） | 不需要 |
| **L-C** | **场景规格 + 独立生成**（v1 的 P1） | 定义"该等于几" ⇒ 破循环论证 | 无 | 不需要 |
| **L-D** | **套件可信度**（v1 的 P0） | 保证后面的绿是真绿 | L-A | 不需要 |
| **L-E** | **屏面同数多屏**（v1 的 P2） | 用户视角的数字一致性 | L-C | 需一份当前代码的前端（我起） |
| **L-F** | **一单到底整链**（v1 的 P3） | 业务链真的走得通 | L-C, L-E | 不需要 |
| **L-G** | **数据/时间/并发**（v1 漏掉的，新加） | 并发、幂等、部分失败、定时、历史数据 | L-A | 不需要 |
| **L-H** | **角色化评分**（v1 的 P7） | 定义"够不够好" | L-A, L-B, L-E | 不需要 |
| **L-I** | **交付可复现**（v1 的 P4） | 换台机器能不能用 | 无 | 不需要（本地全新目录） |
| **L-J** | **体验探针**（v1 的 P5） | 把真人的部分压到 10 分钟 | L-E | 不需要 |

**推进顺序**：`L-A + L-B + L-C + L-D 并行 → L-E → L-F + L-G → L-H → L-J`（L-I 任意时间并行）

★ 注意 **L-A 与 L-B 必须并行**：只做 A 会漏功能，只做 B 会漏现状。**两者的差集才是最有价值的东西。**

## 10. 诚实成本与边界

**成本**：这是**周级**工作，不是一次性任务。分期：
1. 地基（L-A/L-B/L-C/L-D）—— 不需要使用方参与
2. 广度销账（面清单逐条）+ 深度评分（按优先级）—— 不需要使用方参与
3. 闭环（修 → 复评）—— **这里开始需要业务拍板**（见 §6 的决策路径）

**永远做不到的**（不假装）：
1. "顺不顺"的最终判断 —— 只能人给（L-J 把它压到 10 分钟）
2. **真实业务数据的权威性** —— 没有真单据时，数字结论的上限是 **B 级（内部自洽）**
3. **"没想到的需求"** —— 只能靠 §2 的领域参照**缩小**，不能消除
4. 生产上线的风险 —— 不能自动，也不该自动

**能保证的**：每一个面都被**看过、打过、挂了证据**；分数**可被抽样复核**。
**不能保证的**：分数一定"对"——它是判断。但**带证据的判断**与"拍脑袋"是两回事。

## 12. 2026-10-01：整套软件正式交付验收方案与覆盖登记

### 12.1 目标和推进方式

本轮已明确目标：所有业务相关页面的全部必要业务功能实现，业务全过程、岗位转接和数据联通完整闭环，覆盖实际多样操作及各模型测试。Agent 负责验收方法、覆盖盘点、用例设计、推进顺序和质量判断；用户观察过程与结果，不承担给出专业推进意见的责任。仅公司真实业务事实或取舍存在未决时，先查既有决策，再核对必要事实。

“从零开始”落实为重新建立当前版本的全局验收分母、预期和证据。现有代码、原设计、历史决策和有效测试保留并复核；历史“已完成”不自动计入本轮通过项。

纠正刚提出的单页起步方式：先完成全局验收设计，再按依赖顺序核验、修复和回归。页面只是覆盖对象之一，每批必须对应业务能力、角色、模型、交接与场景；一个页面或小闭环不能代表整体交付。

### 12.2 需求与实现双向核对

先回答公司各岗位“需要完成什么”，再对照程序“实际能完成什么”。需求依据包括产品定位、模块原设计、业务规则和决策、真实单据、已确认变体，以及 2026-09-30 和本轮用户纠正。代码负责说明实现，不能按当前输出反写业务正确答案。

核对三侧：

1. **需求侧**：应有能力、全部操作、数据、规则、角色、输出及业务结果，包含应该存在但尚未有页面的功能。
2. **实现侧**：导航及运行中页面、子视图、详情表单弹窗、API/服务、模型、任务事件、Agent 和外部入口。源码扫描与实际界面互相核对遗漏。
3. **差异侧**：缺失、部分实现、规则冲突、多入口行为不一致、未经认可的新设计、无法证明当前可用。

覆盖所有业务页及必要的账号权限、配置、资料、数据、任务等辅助能力。面料与成衣分别验收；AI、邮箱、知识库、门户目标保留。Dashboard 的 UI/UX 豁免保留。已有明确边界继续登记，不擅自扩展工厂 MES、完整总账税务；也不因旧版本范围较小而静默遗漏当前需求。

### 12.3 七类相互关联的验收账本

先在现有能力矩阵、业务变体矩阵、规则决策、数据模型导航和验收剧本中补齐对应记录，再用统一 ID 关联。必要的机器表作附件，不另建一套平行权威方案。

| 账本 | 必备字段和内容 | 要证明什么 |
| --- | --- | --- |
| 需求与能力 | ID、来源、适用业务、全部动作、规则、预期结果、页面、实现差异 | 应该交付的完整分母；发现缺失功能 |
| 页面与操作面 | 主入口、子视图、详情表单、角色可见动作、状态、输出、对应需求 | 每页每个必要功能都被覆盖 |
| 角色与权限 | 岗位任务、数据范围、允许/拒绝动作、兼岗转交、审批范围、人工/API/Agent 约束 | 谁能做、谁不能做；后端真实拒绝越权 |
| 模型与规则 | 实体关系、权威来源、必填唯一关联、金额数量单位、状态转换、版本历史、不变量 | 数据结构及业务模型正确 |
| 跨域与岗位交接 | 上游动作、事实事件、接收者、负责人截止、下游条件、回执、失败恢复、反向影响 | 业务能够持续推进，变更正确传递 |
| 变体与场景 | 适用条件、合法/非法组合、角色步骤、输入、独立预期、异常、涉及账本 ID | 覆盖真实业务多样性与联动 |
| 用例缺陷与证据 | 用例 ID、测试层、前置数据、断言、实际、版本环境、证据、缺陷修复回归 | 结果可重跑、可复核、可追溯 |

关联链为：需求 → 业务规则/角色/模型/交接 → 适用场景 → 用例 → 结果与证据 → 缺陷 → 修复 → 回归。

每项状态分开登记：未盘点、待定预期、待实现、待测、通过、失败、受阻、不适用。未测不是通过；不适用有业务依据；真实公司业务取舍先核既有决策，确实未决才补事实，不能标为不适用缩小分母，也不把专业方法和测试顺序交用户决定。

### 12.4 多样业务、状态与角色覆盖

核对 `业务变体矩阵-2026-09-16.md` 的八维度及 2026-09-30 新规则，保留历史并登记冲突。例如开发费用按最新整案结案收费、原案发起及财务接手口径核验，不直接采用旧逐次寄样开票建议。

至少覆盖并继续补充：

- 面料/成衣；来样、询价打样、成熟产品直接下单；多方案版本、多轮反馈、成功/放弃/终止。
- 实际使用的贸易条件、付款条件、运输方式、USD/CNY 和对应单证要求。
- 多供应商、成品物料加工服务、供料余料、订单明细、独立批次、多产品及规格。
- 分批采购交付、同买家跨单组运、一柜多票、工厂直发、实际入仓再发、货权位置分离。
- 待批准、待资料、待到费用、暂停恢复、取消、变更、返工、质量异常及售后。
- 部分收付、预收预付、减免抵扣、差额处理、核销冲回、交付与财务分别收尾。
- 业务员、采购跟单、QC、仓储物流、财务、管理及适用外部岗位的任务；单岗兼岗、人员转交、权限变化、客户供应商数据边界。
- 空数据、边界值、旧数据、双击重试、并发、断网、部分失败、重启续办、定时任务。

先明确合法组合、非法组合及预期，不机械排列不可能的业务。每条业务分支与状态转换建立正反用例；金额数量、权限、质量放行和跨域等高风险组合设专项用例，不能由低风险抽样代替。

场景族示例（不是完整用例分母）：

| 场景族 | 连续岗位操作和关联断言 |
| --- | --- |
| 开发与收费 | 两轮打样、费用待到 → 开发结束及未完安排 → 补账单、整案核齐 → 收费/减免方案 → 财务接手或退回 → 授权制单收款 → 原案及报表回读；成本和收费事实分开 |
| 报价订单与变更 | 开发/成熟档案报价或直接下单 → 确认 → 修改规格价格数量交期 → 影响判断及授权 → 下游采购生产及单据采用正确依据和版本 |
| 多供应商分批履约 | 单条订单对应多供应商批次 → 供料加工 → 检验 → 部分放行出运 → 剩余履约；数量、质量、位置、货权、成本、待交余额分别正确 |
| 出运单证与核销 | 同买家多单部分明细组运 → CI/箱单 → 多笔款分配 → 定金差额处理 → 收尾；不跨买家错合票，不重复分配数量款项 |

同一案例持续使用同一组业务数据和真实岗位操作，不中途换成补好的单，不以管理员全权账号代替岗位。每个交接点同时验证下一岗位能发现、能接手、依据完整、结果回到来源，以及被退回/拒绝/失败后如何继续。

### 12.5 各层测试与模型验证

| 测试层 | 职责 | 证据界限 |
| --- | --- | --- |
| 规则与模型单测 | 算术、单位、判断、状态合法性、版本、边界 | 不单独证明真数据库或真实岗位可用 |
| API/服务契约 | 输入输出、身份权限、范围、错误与多入口同规则 | 不单独证明界面操作完整 |
| 真数据库集成 | 关联唯一性、事务回滚、并发幂等、历史、事件任务一致性 | 不用 mock 返回值证明真库回滚 |
| 页面与 UI/UX | 列表详情表单、全部动作、状态反馈、筛选输出、可访问性、滚动和设计语言 | 组件测试、截图不单独证明整链 |

模型层逐项核对实体和引用、创建读取修改删除、约束、状态生命周期、金额数量精度、历史版本、软删除和关联保留、事务及并发。并非所有实体都应该能删除或任意修改；按该模型业务规则测试允许和禁止操作。

关键业务不变量包括：不能重复占用/出运数量，不能重复分配款项，客户币种不能错归，审批绑定实际版本和范围，正式历史依据不随档案编辑漂移，失败不能留下半张主单或孤儿交接。具体断言从规则独立生成。

审查既有测试真正证明什么。源码字面量守卫不能冒充行为测试；复用有效用例，不按测试数量判断交付，也不为全绿放宽正确断言。

### 12.6 全局执行与修复回归流程

1. **验收设计**：整理需求和实际能力、角色、模型、交接，建立独立预期、变体和用例追溯，报告分母与差异。Agent 持续补齐专业设计，用户可随时查看过程。当前仍在这一阶段，不因等待方法或页面优先级意见而停工。
2. **环境数据准备**：固定候选版本、配置、数据指纹、岗位账号、隔离测试范围。每案有前置和收尾，不拿真实经营单据试错；运行环境和证据身份对应。
3. **首次全局执行**：按矩阵系统测试，完整登记未实现、失败、受阻和未跑。先以岗位界面判断是否可用，再向服务、数据库追查；代码层测试独立执行。探索记录不能冒充通过证据。
4. **缺陷修复**：每条绑定需求、用例、角色、模型及上下游。风险决定修复先后，不能缩减交付范围；真实口径问题共同确定，不默认现状就通过。
5. **回归联验**：重跑原失败用例、相关正反分支、上下游和共用规则。代码变化使受影响旧证据失效；修复收拢后，在同一候选版本完整回归。
6. **共同交付核对**：提交完整覆盖账、缺陷关闭和岗位连续操作证据，用户随过程查看并参加最终核对。生产部署/真实试运行另按既有授权及切换规则执行。

实施可按页面分批，但每批从全局矩阵领取完整范围、记录影响并回写覆盖。先全局设计，再分批执行，最后全局回归；不能边看到哪处边自定规则修改哪处。

### 12.10 专业推进顺序

下面是依赖顺序，所有已纳入能力仍须全部验收，不以先后缩减范围。面料、成衣在每批分别办理和记录。

1. **补齐全局设计和环境**：逐动作盘点、独立角色预期、模型状态与不变量、既有测试语义；建立隔离DB、文件、队列及专用测试邮箱，固定代码/配置/数据指纹。后端全量测试不得在共享业务库上运行。
2. **第一次全局执行**：先核所有入口和操作面，再按下述依赖链连续办理，同时记录所有其他必要功能的单项结果；未实现、失败、未跑、受阻全部入账，不立即看到一处就自定规则修改。
3. **基础至业务形成**：账号权限与统一身份/资料/规则 → 两线开发样品及整案费用 → 产品/BOM/定价/报价与直接下单 → 订单确认变更、采购生产交接。
4. **履约至结算异常**：多供应商采购/加工 → 物料供耗损余/库存 → 两线QC与范围放行 → 多路径分批组运/单证/报关 → 票款核销与成本 → 索赔返修补偿及分别收尾。
5. **横向能力及全局回归**：待办交接、驾驶舱/风险/报表、日历、季节营销、邮件/知识/门户/Agent、人事和必要辅助工具按对应案例核验；缺陷每次回归影响上下游，最终同一候选版本全部必测项再执行。

每次修复先给出具体触发、独立预期、影响范围和复验用例，再改必要实现。功能优先，既有BDS是每次改动的约束；逐页收拢已记录视觉问题，避免功能修复另创容器、文字和选择方式。Dashboard仅UI/UX豁免。用户看结果与过程，Agent承担分析、验证和质量判断。
