## 四、批次 3 五条的要点

### C1（`de7acd04`）—— ★ 清单描述被订正
- 清单原文「`CustomsDeclaration` 无柜号字段」。**实测：柜号字段本来就有**（`Shipment.containerNumber`/`sealNumber`，`schema.prisma:3028-3029`，已用于装箱单/报关单据模板、客户门户、货运页）。真缺口 = **没有「按柜号聚合」的能力**。
- 修法：**只读**聚合服务（票/客户/件重体 + 关联报关单/退税，不串柜）+ **柜内矛盾检测**（ETD/卸货港/船名/航次不一致；**空值不参与** —— 未填 ≠ 不一致，宁可漏报不可误报）+ 未填柜号单独列出（**不硬塞进某个柜**）。
- 刻意不做：柜内「封条号重复」检测 —— 同柜多票共用封条是**正常**的。
- 路由 `GET /api/v1/shipping/stats/containers`（**两段式**：单段 `/containers` 会被 `/:id` 抢匹配）。

### C2（`b5bff550`）
- 真库实测驱动：`shippingMethod` 是自由文本零校验（75 张票 `Sea 67 / Air 7 / Sea Freight 1`）。
- **两档口径**：写入 `coerceShippingMethodForWrite`（严格；中文/别名/脏值/FCL/LCL → **归一**而非拒绝）+ 展示 `normalizeShippingMethod`（宽容，只影响分组与展示，**不改库**）。
- **不回溯历史行**：只校验本次写入值（否则改一条老票的备注都会被拒）。

### C3（`750447e8`）—— ★ 实测比清单描述更严重
- 清单写「出运侧只算上限」。真身是 **`OrderLine.shipmentQuantity`（溢短装面板唯一数据源）只被内部交易写过，出运模块从不写它** ⇒ 面板永远「未发货」、条款从不判定 = **永远绿的假面板**。
- 修法：真源 `shared/orderLineShippedQty.ts` + 5 个收口点（分配增删改 + 票取消 + 票软删），口径与出运上限校验**同源**。

### C7（`5f8bb7c4`）
- A3 修了 CN 抵扣的**内核**，缺的是**入口**（原路径：索赔处置 5 步 + 语义错位）。
- 真源 `finance/writeOffService.ts`：**同一事务**内开 CN + 立即抵扣（为此给 `createCreditNote`/`applyCreditNote` 加可选外部事务参数，并修正其内部读要用 tx）。
- **有上限** `min(票面×5%, 等值 500 CNY)`（⚠️ 默认值待业务确认，可用 env 覆盖）。

### C4（本提交）—— 唯一带 migration 的一条
- 已核实 `InventoryItem` **无 orderId**、全库无备货痕迹。
- **migration `20260918100000_add_inventory_order_anchor`**：`InventoryItem` 加 `orderId`(可空) + `stockPrep`(默认 false) + 新表 `InventoryOwnershipChange`。**纯加列/加表**，存量行自动成为「未归属、非备货」（与现状语义一致），回滚 = DROP。
- 为什么单独一张留痕表而不是复用 `StockMovement`：归属变更**不改变数量**，而 `StockMovement.quantity` 必填 —— 塞 0 会让流水看起来像「数量 0 的调整」。
- 四动作**前置条件互斥**（认领 vs 挪货 vs 退回 vs 备货），留痕能区分意图；目标可填**订单 id 或 PO 号**（业务员手上是 PO 号）。
- 前端库存页「订单归属」行（徽标 + 四个动作，`inventory:write` 门控）。
