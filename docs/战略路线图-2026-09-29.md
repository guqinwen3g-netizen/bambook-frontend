## 零、一句话战略判断

> **Bambook 已经不缺功能了，缺的是「一条能走到头的业务主线」和「一次真正的上线」。
> 接下来不是继续加东西，是收口：冻结范围 → 打通主线 → 上线 → 用真实业务验收 → 再谈长形态。**

继续按现在的打法（每修一件撞出 1.5 件新的、每批被守卫反咬 9 次、1469 提交未上线），
**再打两周，业务价值仍然是 0**。

## 一、项目现在处在哪个阶段（不是你以为的那个阶段）

### 1.1 资产规模（本机实测）

| 维度 | 数字 | 维度 | 数字 |
|---|---|---|---|
| 后端路由 | **367** | Prisma 模型 | **225**（enum **0**） |
| 前端 View | **38** | 导航模块 | **59**（与 View 对不上） |
| 前端组件 | **401** | server 源文件 | **1071** |
| 测试文件 | **818** | 脚本 | **196** |
| 过程文档 | **558 篇 / 16 MB** | 单份权威基准 | **2.5 MB** |
| 本地未推送提交 | **1469** | 今日提交 | **155**（功能类 **5**） |

### 1.2 业务需求规模

`BusinessDocu`：**99 份 PDF + 18 XLS + 3 DOCX**，一条链：
`客户 PO → 销售合同 → 采购合同 → 大货批准 → 生产 → QC → 发货通知 → 出运 → SHIPMENT REPORT → 收汇 → 结案`

### 1.3 ★ 阶段判定

**225 个数据模型，服务一条 11 节点、99 份单据的业务链。**
供给严重过剩，但**有效供给不足** —— 因为：

- 该有的**规则**没有（体积重、QC 阈值、回潮率、大货批准…）；
- 已有的**字段**没接界面（缩水率、计费重量…）；
- 每一段都有，**串不起来**（看一单要跨 5~6 个模块）。

⇒ **这不是"开发后期"，是「功能堆砌期」的末尾，必须强制切换到「收口期」。**

## 二、六个战略判断

### 判断 1 ★★★ 两类工作的比例必须倒过来

| | 现状 | 应为 |
|---|---|---|
| 新增能力 : 贯通与交付 | **9 : 1** | **1 : 9** |

今日 155 提交里功能类只有 5 个 —— **每 1 条业务能力 = 约 30 个提交的记账成本**。

### 判断 2 ★★★ 当前第一风险不是 bug，是「业务价值 = 0」

未 push（1469）· 未部署 · 生产未迁移 · 仓库仍 Public。
**不上线，前面所有完善都等于没做。** 这一条压倒其余所有判断。

### 判断 3 ★★ 复杂性已开始反噬产能（有量化证据）

- 每修 1 件事平均撞出 **1.5 件**新的（结构性，不是偶发）
- 每批被守卫反咬 **9 次**，其中 **4 次**是纯合规性论证（不是产品缺陷）
- 交接件 13 KB、权威基准 2.5 MB —— **文档已大到不可读**

⇒ 边际成本在恶化。**守卫一个都不删**（它抓到的 409→500 那条极值钱），但**不再为它重复付费**。

### 判断 4 ★★★ 验收标准被悄悄替换了

明令判据：`Kevin 用真实业务走完说这就是我要的`。
实际判据：`门禁全绿 + 交接件写完`。

**门禁绿是必要条件，不是充分条件 —— 而且它永远不会红。**
这个替换是危险的，因为它能无限期地制造"进展良好"的假象。

### 判断 5 ★★ 产品形态的真正缺口是「没有一单到底的视图」

59 个模块按**功能**铺开，业务是按**订单**串起来的。
业务员现在无法在 30 秒内回答：「这单到哪了、有没有问题、差多少钱」。
⇒ 形态目标：**从「模块导航」转向「以订单为中心的任务驱动」**。

### 判断 6 ★★ 这个项目需要一次「减法」，不是加法

225 模型 / 0 enum、38 View vs 59 模块、订单状态机两份实现 —— 都是**过度建设**的证据。
战略纪律：**v1 不重构（成本不可控），但立刻停止扩张**。
任何新能力必须先回答：**它在这条主链的哪个节点上？** 答不上来就不做。

## 三、目标形态：什么才算「做完了」

### 3.1 v1 完成的三层定义

| 层 | 定义 | 判据 |
|---|---|---|
| **L1 主链通** | 11 节点一单到底，数字对 | 一单真实业务从 PO 走到结案，**金额/数量/日期全部对得上** |
| **L2 看得见** | 一屏看全一单 | 打开一单，30 秒内能说出「到哪了 / 有什么风险 / 差多少钱」 |
| **L3 用得上** | 已上线、有真实数据 | 业务员连续使用一周，**不再需要问开发** |

### 3.2 反定义（这些**都不算**做完）

✗ 功能清单打勾 　✗ 门禁全绿 　✗ 文档齐全 　✗ 提交很多 　✗ 测试覆盖率高

## 四、三阶段路线

### 阶段 A · 收口上线（目标 3~5 天）

| 项 | 内容 |
|---|---|
| **目标** | 冻结范围 → 做完 → 上线 → 真实业务走一遍 |
| **做** | ① 冻结 v1 清单（**≤6 条**，见 §4.1）· ② 开发环境**影子验收**（真实单据逐字段重演）· ③ 部署 + 生产迁移（**先备份、留回滚**）· ④ Kevin 录一单真实业务 |
| **不做** | 任何新能力 · 任何重构（**②-2「0 enum」明令推迟**）· 客户门户上线 |
| **退出判据** | **Kevin 用一单真实业务走完，说数字对**（不是我说对） |
| **风险对冲** | 仓库 Public → 改用内网部署包或直接改 Private；生产迁移 → 先 `pg_dump` 验证可恢复再动 |

#### 4.1 建议冻结的 v1 清单（≤6 条，判据：不做会**算错钱 / 卡住 / 出错账**）

| # | 事项 | 为什么必须 |
|---|---|---|
| ①-3 | **<20kg 按体积重**（规则） | 运费会算错 |
| ①-10 | `OrderLine` 补 4 个真实报表字段 | 出运报告对不上 |
| ①-8 + ②-3 | **QC 阈值 + 标准号** | 判不了合不合格；①-9 依赖它 |
| ④ | **金额那一轨**（L/C 门禁按金额判） | 收汇命门 |
| ③ | 缩水率 / 计费重量接界面 | 已立项，半天工作量，顺手清掉 |

**明确推迟 v1.1**：②-2（0 enum，结构性大改）· ①-11 回潮率（采购侧）· ①-2 大货批准（语义待确认）· ①-6 空运罚则 · ②-1 状态机双实现 · ①-9。

### 阶段 B · 真实运行（2~4 周）

| 项 | 内容 |
|---|---|
| **目标** | 在真实使用中暴露**口径级**问题（不报错但算错的那类最危险） |
| **做** | 只修**阻断级 + 口径级**；体验级一律进清单不改 |
| **不做** | ★★ **这一阶段不开发任何新功能** —— 否则永远进不了阶段 C |
| **退出判据** | 连续 **7 天**无阻断级、无口径级问题 |
| **纪律** | 每天更新 `v1收敛台账.md` 第一行「剩 N 件」 |

### 阶段 C · 形态长成（v1.1+）

| 项 | 内容 |
|---|---|
| **做** | ① **订单驾驶舱**（一屏看全一单）· ② 客户门户上线 · ③ 剩余能力**按业务价值排序**逐条做 |
| **排序原则** | 会算错钱 > 会卡住 > 会骂娘 > 可以更专业 > 可以更好 |
| **不做的** | ②-2 这类结构性重构 —— 除非它开始真的造成错误 |
