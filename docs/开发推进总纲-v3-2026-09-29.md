# 开发推进总纲 v3 —— v1 补完（不重塑）· 可数、可复核、可重放

> 2026-09-29 · 开发方起草 · **本文件取代** `测试推进方案-2026-09-29.md`(v1) 与 `测试推进策略-v2-2026-09-29.md`(v2)。
> v1 是工具清单，v2 是"验收"策略且**跑偏成"要不要重塑"**；v3 把**范围界定 + 测试方法 + 推进节奏**合成一份可执行总纲。

---

## 1. 范围界定（最高约束，先立这个，其余都服从它）

**使用方原话**：「时间迫切 ⇒ 不可能彻底重塑。现在软件的状态**就是 v1（Bambook 一代）的整体规划设计**。
里面的细节、操作、交互、功能，**在现有基座上彻底完善并 100% 交付**。**不要跨越太远**，
别因为要求高就做颠覆式判断。」

⇒ **v1 的设计是给定的，不评判、不重塑。** 正确的问题不是"这设计对不对"，
而是「**这设计被完整、正确、专业地实现了吗**」。

**v1 做什么 / 不做什么：**

| 做 | 不做 |
|---|---|
| 在既有结构内**补完**细节、操作、交互、功能 | 新增模块、改信息架构、重排业务流程 |
| 把每条业务规则**让系统强制** | 重新设计领域模型 |
| 把每个数字**做到多屏一致** | 重构金额口径的"设计"（但**收敛到一处**是必修，见 §2①） |
| 把每个交互做到**专业细节标准** | 提出"更好的产品形态" |

---

## 2. ★★ 发现的三分类（这条把"不要跨越太远"变成可执行的边界）

**每一个发现，先分类，再处置。分类先于动手。**

| 类 | 定义 | 判据 | 处置 |
|---|---|---|---|
| **① 没实现完 / 实现错** | 该有的行为缺失或算错 | **会让数字错 / 会让人越权 / 会丢数据** | **v1 必修** |
| **② 实现得对但低端** | 行为对，细节不专业 | 裸码上屏、暴露英文枚举、要手抄数字到别处、无撤销、错误提示不给下一步、要记 ID、无批量 | **v1 必修** ←「彻底完善」的主体 |
| **③ 设计本身可以更好** | "这模块该合并""这流程该重排" | 不影响 v1 的正确性与可用性 | **记 v2 backlog，不阻塞 v1** |

★ **判据很干脆**：问"**这块现在会不会让数字错、让人越权、让人丢数据**"——
- 会 ⇒ ①，v1 必修
- 不会但用起来难受 ⇒ ②，v1 必修
- 都不会，只是"可以更好" ⇒ ③，**只记录，不动手**

★ **v1 交付 ≠ 没有改进空间**，而是「**设计意图 100% 完整正确地实现了**」。

## 3. 认知：两个轴 × 三个参照物

### 3.1 两个正交轴（缺一不可）

| 轴 | 问的是 | 手段 |
|---|---|---|
| **广度** | 有没有漏 | 面清单：从**产物**枚举 |
| **深度** | 够不够好 | 评分：从**角色视角**、挂证据 |

★ 广度够深度不够 ⇒ 全都"能用"但不好用；深度够广度不够 ⇒ 少数很好但大半没看。

### 3.2 三个参照物

| 参照物 | 回答 | 来源 | 现状 |
|---|---|---|---|
| **产物** | 现在**有什么** | 源码路由 / 运行中 DOM / Prisma DMMF / 各注册表 | 未做 |
| **业务能力清单** | 业务**需要什么** | 86 份真实单据 + KB 22 处 + 原需求 + `company-sim/` | 材料在，未收拢 |
| **专业基准** | **细节该做到什么程度** | 我以专业者身份写，**你抽样批** | 未写 |

★ **产物清单 × 业务能力清单 的差集** = "漏了什么"（两个方向都是发现）
★ **产物 × 专业基准 的差集** = "细节不够专业在哪"

---

## 4. 专业基准：怎么写、怎么用、你怎么批

**它不是设计稿，是验收尺。** 逐业务域（客户/报价/订单/采购/生产/质检/出运/报关/单证/收汇/索赔/库存/成本/报表/权限/审计）列出：

1. **该域必须由系统强制的规则**（前置条件、后置条件、不变量、例外、权限、留痕）
2. **该域的专业做法**（例：分批出运尾差归谁、多币种按什么汇率入账、索赔的账务闭环）
3. **该域常见的低端设计**（例：状态当自由文本、靠人工记 ID、金额拆两字段各算各的）

★ **你的参与方式**：**批它**，不是从零告诉我业务。逐条判「要 / 不要 / 以后要」。
批判的成本远低于创作——这是"不让你动手"的正确解法。

★ 每条标注「**行业基准，非你的要求**」，避免我把行业惯例当成你的需求。

## 5. 改造：在既有结构内补完

**四类问题四种处置，不能都当"修 bug"：**

| 类型 | 处置 | 完成判据 |
|---|---|---|
| ①a 算错/漏拦 | 修 + **补一条能红的守卫** | 不再复现，且守卫有牙 |
| ①b 口径散在多处 | **收敛到单一真源**（不重构设计） | 只剩一处，且旧出口有守卫 |
| ② 低端细节 | 按专业基准逐条改 | 该面评分达线 |
| ③ 设计可更好 | **只记录** | 进 v2 backlog |

★★ **改造的判据是「角色的任务是否更快更稳地完成」，不是"分数涨了"。**

---

## 6. 验证：四层

| 层 | 证明什么 | 手段 |
|---|---|---|
| **屏面同数多屏** | 用户看得见的数字一致 | 真浏览器读 **DOM 文本**，与独立生成的期望值对撞 |
| **一单到底整链** | 业务链真的走得通 | 一个客户一张单，全程**屏面操作**、不换数据、不做 DB 手术 |
| **数据/时间/并发** | 企业级最狠的 bug | 并发双写、重放、注入失败、定时、历史数据、不可逆动作 |
| **角色化评分** | 够不够好 | 七维 0–5 分，**每分挂证据** |

### 6.1 评分锚点（先写死再打分，防漂移）

| 维度 | 锚点示例 |
|---|---|
| 做得快吗 | ≤3 步 = 5 · 4–5 步 = 4 · 6–8 步 = 3 · >8 步 = 2 |
| 看得懂吗 | 提示含下一步 = 5 · 只报错 = 2 |
| 错得回来吗 | 有撤销 = 5 · 无 = 1 |
| 设计是否低端 | 命中"裸码/英文枚举/记 ID/无批量/手抄"任一项 ≤3 |

★★ **最要紧的纪律：打分时"只看屏面"，不许读源码找办法。**
我知道代码，一读源码就会**替软件圆场**，而真实用户没有这个特权。
这一条把"我作为开发者"切换成"**我作为那个角色的真人**"。

### 6.2 诚实标注
分数是「我以该角色身份、按可观察证据给出的判断」，**不等于业务方的判断**；
但每分**挂证据** ⇒ **可抽样复核、可被推翻**。

## 7. 优先级与停止线

**优先级 = 风险 × 使用频度 × 不可逆性 ÷ 成本**

| 分层 | 达标线 |
|---|---|
| 财务链（开票/核销/收付汇/索赔/结账） | **必须 A**（有外部参照） |
| 出运链（订单→生产→质检→出运→报关） | **必须 A** |
| 权限与越权 | **必须 A** |
| 日常业务操作（报价/订单/库存/客户） | **必须 B+** |
| 边缘报表、集成、设置项 | 可 B |

★ 没有停止线 ⇒ 无界工作 ⇒ 等于没有策略。

---

## 8. ★ 决策路径（防坟场）—— 这是本项目最大的历史风险

现状：台账已有 **31 条待拍板**。再堆几百条发现而没有决策路径 ⇒ **更大的坟场**。
★★ **最危险的不是"发现不了"，是"发现了没人拍"。**

**开工前必须先立（我可以先起草，你只需确认）：**

```
发现 → 分级（①阻断 / ①缺陷 / ②低端 / ③设计 / 口径分叉）
     → 每级指定"谁能拍" + "多久内拍" + ★"不拍的默认处置"
     → 修 → 复评 → 销账
```

★ **"不拍的默认处置"必须写死**，否则"待拍板"= 无限期悬空 = 等于没发现：
- **口径分叉**：超期未拍 ⇒ 默认取「现状 + 在界面上显式提示口径」
- **②低端**：超期未拍 ⇒ 默认按专业基准改
- **①阻断**：不存在"不拍"——它阻塞交付，必须拍或明确降范围
- **③设计**：超期 ⇒ 进 v2，不影响 v1

---

## 9. 证据必须可重放（否则做完就腐）

每条结论 → 指向：**脚本 + 输入数据指纹 + 当时截图**。
代码一变 ⇒ 指纹变 ⇒ **受影响的结论自动失效并重新排队**。

★ 没有这一条，证据是一次性的；三个月后没人知道哪些还成立。

## 10. 推进节奏

### 阶段 0 · 认知（**不需要你参与**）
- 产物枚举（源码扫描 + DOM 爬取**两种方式互撞**，差集即漏）→ 面清单 + **总数**
- 业务能力清单（从 86 份单据 + KB + 原需求收拢）
- 专业基准（我写）
- 三者对撞 → **候选清单**

**判据**：面清单总数是个数；三类差集都列出来了。

### 阶段 1 · 靶子成型 → 交付两份给你批
- **《v1 补完清单》**：每条 ①/②，按"会让数字错/会越权"排序
- **《v1 交付判据》**：面清单总数 · 已补完数 · 残留数
- **《v2 backlog》**：③ 全部进这里，**不混进 v1 的账**

**判据**：靶子上每一条都能对到"哪个面、哪条规则、哪个证据"。

### 阶段 2 · 补完（按优先级逐面）
- 每面：专业基准比对 → 补齐 → 验证（屏面 + 回归）
- ★ **改一处、验一处、回归一片**（现在的 85 条分片**不够当回归网**，需先补）

**判据**：①清零；②达线；回归网无新增红。

### 阶段 3 · 整链与并发
- 一单到底整链 + 并发/幂等/部分失败/历史数据/不可逆

**判据**：至少一条链从报价走到收汇结清，全程屏面操作、有连续证据。

### 阶段 4 · 交付验证
- 换机重装（全新目录，不需要生产环境）+ 体验探针（把真人压到 10 分钟）
- **《v1 交付报告》**：每条结论**自报等级 A/B/C**

## 11. v1 完成定义（可数）

> **每一个面都被看过；每一条业务规则都被系统强制；每一个交互都达到专业细节标准；
> 每一个数字在多屏一致；没有一条 ① 或 ② 残留；至少一条整链走通；换机可跑。**

**当且仅当**下列同时成立，才允许说"v1 可交付"：
1. **① = 0**（阻断与缺陷清零）
2. **② 达线**（按 §7 分层）
3. **屏面数字**与外部参照逐条一致（差异清单为空）
4. **整链**至少一条走通，有连续证据
5. **换机重装**能跑通
6. 报告里**没有把 B 级读成"能交付"**

## 12. 风险与反证（自我批判——使用方要求"反复推敲"）

| 风险 | 症状 | 对策 |
|---|---|---|
| **又跑偏成"重塑"** | 开始提"这个模块该合并" | §2 三分类：③ 一律只记录 |
| **广度错觉** | 枚举出 N 项就以为"全了" | 两种枚举方式**互撞**，差集即漏 |
| **评分漂移** | 同一件事今天 4 分明天 2 分 | **锚点先写死** |
| **自我圆场** | 读源码 → 替软件解释 → 分数虚高 | "只看屏面"纪律 + **抽样复核** |
| **修不完** | 挑软的修，难的留坟场 | §8 决策路径 + **默认处置** |
| **工具自嗨** | 时间花在建框架，没看软件 | **时间盒**：每工作包限时，到点必须出结论 |
| **回归网不够** | 改一处坏别处，没人发现 | 阶段 2 前先补回归网 |
| **我判断"够专业"但业务不认** | 分数与业务直觉冲突 | 每分挂证据；**你抽样 10 条即可推翻** |

## 13. 诚实边界（不假装）

1. **"顺不顺"的最终判断** —— 只能人给（体验探针把它压到 10 分钟）
2. **真实业务数据的权威性** —— 没有真单据时，数字结论上限是 **B 级（内部自洽）**
3. **"没想到的需求"** —— 只能靠业务能力清单**缩小**，不能消除
4. **v1 设计层面的不足** —— 我**只记录**（进 v2），**不在 v1 里动**
5. **"打造最强好用"里有一半是产品设计，不是测试** —— 测试证明"对"，产生不了"好"；
   v1 的目标是「**既有设计被专业地实现**」，不是「设计最优」

## 14. 开工第一天做什么（具体到可执行）

1. **起草《决策路径与默认处置》**（§8）—— **第一件事**，因为它是防坟场的闸门
2. **起一份当前代码的前端**（独立端口，不动现有走查环境）—— 屏面验证的前提
3. **产物枚举第一刀**：后端路由 + 前端路由 + Prisma 模型 → 出**总数**
4. **业务能力清单第一刀**：从 86 份单据 + KB 收拢第一批域

★ 这四件**都不需要你参与**，且做完之后**"漏没漏"就有一个数**。
