# 测试推进方案 —— 从「代码自洽」到「软件可交付」

> 2026-09-29 · 由开发方起草，**全程不需要使用方动手**（人的参与只保留两处：最终验收签字、生产上线）。
> 本文件是 `docs/交付目标与验收标准-2026-09-20.md` 的**可执行对应物**：那份写"应该是什么"，
> 这份写"怎么跑出证据来"。

---

## 一、差距的定性（先说清现在到底缺什么）

现有证据**只覆盖到"代码自洽"**。用"证据分层"表示：

| 层 | 判据主体 | 现状 |
|---|---|---|
| L1 存在性（页面/接口在不在） | 路由、文件 | ✅ 有证据（门禁 + 85 条验收） |
| L2 算术（服务层算得对不对） | 函数返回值 | ✅ 有证据（7627 条单测 + API 验收） |
| **L3 屏面数字**（前端显示的是不是那个数） | **DOM 文本** | ❌ 基本没测 |
| **L4 交互可达**（点得动吗、走得通吗） | **一次真实点击序列** | ❌ 只有"元素在"的断言 |
| **L5 业务链**（一单从报价走到收汇结清） | **同一份数据的连续状态** | ❌ 只有分片，且分片之间互相干扰 |
| **L6 体验与可交付**（换个人/换台机器能不能用） | **另一个人的行为** | ❌ 完全没测 |

**L3–L6 够不到，不是"测得不够多"，而是三条结构性根因：**

- **根因 ① 判据是"代码形状"不是"用户看到什么"** —— 7627 条断言的是 `ΣnetValue = Σ(qty×单价)` 这类
  **内部恒等式**。它证明"服务算得自洽"，证明不了"屏面上那个数是对的"。今天挖出的"跨页数字不一致"
  就是典型：API 全对，用户看到的对不上。
- **根因 ② 数据和判据同源 ⇒ 循环论证** —— 数字的"正确性"都拿**同一批合成种子**去判，种子错判据跟着错，
  而且**永远绿**。所以"没有真实业务数据"不是行政问题、是**判据问题**：没有外部参照，"算得对"无定义。
- **根因 ③ 写码的人 = 写判据的人 ⇒ 共享盲区** —— "我没想到的，我就不会去测"。今天那 8 条过期脚本、
  2 处数据泄漏、1 条永远红的判据，全是这个根因的产物：**套件在腐烂，而绿的读数看着一样好看。**

## 二、目标形态：什么叫"证明完了"

**一份《软件验收报告》，每条结论都能追溯到一份可复算的证据（脚本 + 截图 + 文件）。**

并且每条结论必须**自报等级**，不许混着说：

| 等级 | 含义 | 例 |
|---|---|---|
| **A · 已证明（有外部参照）** | 参照物**独立于被测代码**生成 | "按场景规格应显示 ¥37,050，屏面读到 ¥37,050" |
| **B · 有证据（内部自洽）** | 只有内部恒等式 | "Σ净额 = Σ(数量×单价)" |
| **C · 无证据** | 没测或测不了 | "顺不顺" |

★ **报告里不许出现"A"以外的话被读成"能交付"** —— 这就是今天"门禁全绿 ≠ 软件对"的根治办法。

## 三、三个转变（方案总纲）

1. **参照物外置**：从"拿库判库" → "**拿业务场景规格判库**"（规格独立生成，与代码不共源）⇒ 破根因 ②
2. **判据上移**：从"服务层恒等式" → "**屏面可见数字**" ⇒ 破根因 ①
3. **链不断**：从"85 条分片" → "**一条连续整链** + 分片只做回归" ⇒ 破根因 ③ 的一半（另一半靠突变自检）

## 四、五个工作包（P0–P5）· 全部由开发方自动执行

### P0 · 套件可信度（**先做，否则后面全是假绿**）

| 项 | 内容 |
|---|---|
| **证明什么** | "现在的绿是真的绿" |
| **判据** | ① **恒绿判据**（从没红过的）占比 → 必须 0；② **僵尸判据**（从没真跑过的，如被 skip / 打不到后端）占比 → 必须 0；③ 每条判据**有牙**（注入一个应让它红的缺陷，它真的红） |
| **怎么自动** | 跑批前先跑 `acceptance-selfcheck`；对每条判据做**突变自检**（本仓已有雏形，扩到全量强制）；历史矩阵（`scripts/.acceptance-matrix.json`）做"上轮也红"的基线对比 |
| **产出** | `docs/套件可信度报告.md`：每条判据标 `有牙 / 无牙 / 僵尸 / 待修` |
| **依赖** | 无 |
| **本程已做的地基** | 修 8 条过期脚本 · 建"批跑→清残留→隔离复跑"的正确顺序 · 建 B32 棘轮 |

### P1 · 业务场景规格（**外置参照物**）

| 项 | 内容 |
|---|---|
| **证明什么** | 数字对不对，有**外部参照** |
| **判据** | 从规格**独立推导**出的每个节点的期望数字 |
| **怎么自动** | 写 `scenarios/*.yaml`（客户 / 价格 / 折扣 / 税率 / 汇率 / 分批 / 账期 / 佣金 …）；<br>再写一个**生成器**从规格产出两样东西，**两样都不读代码、不读库**：<br>① **源单据**（PO、发票、报关单、银行水单 → 落成真 PDF/Excel 文件）<br>② **期望值表**（每个节点该显示多少） |
| **为什么破循环** | 参照物来自**业务场景规格**，不是来自被测库 ⇒ 库错、码错都会露出来 |
| **产出** | `scenarios/` + `expected/` + `fixtures/`（真单据文件） |
| **依赖** | 无（★ 使用方已说"数据自己模拟"，且已有 `company-sim/` 的 `SIM-` 数据集可挂） |

### P2 · 屏面同数多屏走查（**用户视角，最能红**）

| 项 | 内容 |
|---|---|
| **证明什么** | "跳来跳去数字一致"——**用户看得见的那个数** |
| **判据** | 同一张单，在 N 个页面**读 DOM 文本**，与 P1 期望值逐个对撞 |
| **怎么自动** | Playwright 真浏览器 + 真登录；覆盖：概览 / 订单详情 / 订单列表 / 报价 / 对账 / 资金日历 / 导出 xlsx 与 PDF（**从文件里读回数字**） |
| **产出** | `屏面一致性报告.md` + 每屏截图 + 差异清单 |
| **依赖** | 需一个**当前代码**的前端（见 §六 环境） |
| **★ 关键** | 现有 UI 脚本只断言"元素在"，本包**改成断言"文本等于几"** —— 这是"能红"与"不能红"的分界 |

### P3 · 一单到底连续整链（= 台账 §11 第 1 条的可执行版）

| 项 | 内容 |
|---|---|
| **证明什么** | 业务链**真的走得通** |
| **判据** | 一个客户、一张单：报价 → 转单 → 采购 → 生产 → 出运 → 报关 → 开票 → 收汇 → 结清，**每步都从屏面操作**，中途**不换数据、不做 DB 手术** |
| **怎么自动** | 一条长脚本，**不调用内部 API 抄近路**（能抄近路就证明不了"用户走得到"）；每步：操作 → 截图 → 读屏面数字 → 对 P1 期望 |
| **产出** | `docs/整链证据-<场景>.md`：每步截图 + 那一步的数字 |
| **依赖** | P1（规格）、P2（读屏面数字的能力） |
| **★ 判据** | **85 条分片合起来 ≠ 这条** —— 今天已实测：分片之间互相干扰，前面的残留会改后面的结论 |

### P4 · 交付可复现性（换台机器从零装）

| 项 | 内容 |
|---|---|
| **证明什么** | "可交付" |
| **判据** | 在**全新目录**：克隆 → 装依赖 → 迁移 → 灌种子 → 起服务 → 冒烟，**全程不看开发者的提示** |
| **怎么自动** | 一个脚本在干净目录里走完，记录每步耗时与卡点；对"漏了哪步会失败"做**反向验证**（故意跳过某步，确认它真的会红） |
| **产出** | `docs/换机重装报告.md` |
| **依赖** | 无（★ 不需要生产环境，本地全新目录即可） |

### P5 · 体验探针（**把人的参与压到 10 分钟**）

| 项 | 内容 |
|---|---|
| **证明什么** | "顺不顺"——**这一层机器测不了，但可以量化到接近** |
| **怎么自动（代理指标）** | ① 完成一个任务要**几步 / 几次点击 / 多少表单字段**；② **错误提示**是否给了"下一步怎么办"（本仓已有错误文案规范，可自动判）；③ **空态**是否有引导；④ **首屏耗时**；⑤ **一次成功**（不做多余操作就能完成） |
| **怎么把人的部分压小** | 产出一份**任务卡 + 勾选记录表**（"请给客户 A 报一个新价并转成订单"），真人**只需按卡操作一遍并勾选**，不需要懂系统 —— 10 分钟量级 |
| **产出** | `docs/体验探针报告.md` + `任务卡/`（打印即用） |
| **依赖** | P2 的浏览器能力 |

## 五、依赖与排期

```
P0 套件可信度 ──┐（必须先做：否则后面全是假绿）
                ├─→ P2 屏面同数多屏 ─→ P3 一单到底整链 ─→ 《软件验收报告》
P1 业务场景规格 ─┘                        ↑
P4 交付可复现性（独立，可并行）
P5 体验探针（依赖 P2 的浏览器能力）
```

- **P0 / P1 / P4 可立即开始，互不依赖，且不需要任何外部条件。**
- **P2 需要一台"当前代码"的前端**（见 §六）。
- **P3 依赖 P1 + P2。**
- **P5 最后做**（它依赖 P2 的浏览器能力，且它的产出主要是给真人用）。

| 依赖 | 现状 | 我的建议 |
|---|---|---|
| **一台跑当前代码的前端** | `:3002` 上跑的是 **s0a 旧树**的前端（与 `:8090` 同源） | 我在**另一个端口**（如 `:3100`）从 main 起一份，**不动你现有的走查环境** ⇒ 无需你操作 |

★ 除此之外**没有需要你动手的环节**。人的参与只剩两处：**最终验收签字**、**生产上线**（后者本就在纪律里）。

## 七、诚实的边界（这些永远自动化不了，别假装能）

1. **"顺不顺"的最终判断** —— 只能人给。P5 把它从"一个项目"压到"10 分钟填表"。
2. **真实业务数据的权威性** —— 没有真单据时，所有数字结论的上限是 **B 级（内部自洽）**，不是 A 级。
3. **生产上线的风险** —— 不能自动，也不该自动（纪律）。
4. **"没想到的需求"** —— 自动化测不出"该有的功能没做"。这要靠 P5 的真人任务卡暴露。

---

## 八、判定标准：什么叫"可以交付"

**当且仅当**下列四条同时成立，才允许说"可以交付"：

1. **P0 通过**：恒绿判据 = 0、僵尸判据 = 0、每条判据有牙。
2. **P2 通过**：屏面数字与外部参照**逐条一致**（不一致的清单为空）。
3. **P3 通过**：至少一条业务链**从报价走到收汇结清**，全程屏面操作、无 DB 手术、有连续证据。
4. **P4 通过**：换台机器从零装能跑通。

★ 在 1–3 做到之前，"软件是对的"**没有证据**；在第 6 节那份真数据拿到之前，
"算得对"的上限是 **B 级**，报告里必须**如实标注**。

## 九、我现在就能开始的（不需要任何外部条件）

1. **P0**：套件可信度自检 + 突变自检全量强制 + 出报告
2. **P1**：业务场景规格 + 独立生成器（源单据 + 期望值表）

4. **P2 的准备**：从 main 起一份前端（独立端口）+ 把现有"元素在"断言改造成"文本等于几"

**建议的开工顺序：P0 → P1 → P2 → P3 → P5**（P4 并行）。
