## 2. Step 0 注册表加固：5 条钉子 + 每条的可证伪性

### 2.1 为什么要加固（缺陷不是「没测」，是「测了但恒真」）

`resolveError` 查表支的实现是：

```
status:  spec?.status  ?? 500
message: spec?.message ?? GENERIC_ROUTE_ERROR_MESSAGE
```

Task 2 时代共 7 条用例，**全部**落在「5xx 码」或「业务错误自带 statusCode」两条路径上 ⇒ 把 `spec?.status`、`spec?.message` 整段删掉、只留 `?? 500` 和通用文案，**旧用例照样全绿**。这就是 T1（期望值不得抄现值）与 G6.4 要杀的对象。

### 2.2 五条钉子与实跑变异

| # | 钉子 | 变异 | 旧用例 | 新用例 |
|---|---|---|---|---|
| ① | 表内 4xx/5xx 码的 `status` 必须来自表（`not.toBe(500)` 专杀兜底） | 变异 A：`status: 500` | ✅ 全绿（**这就是洞**） | ❌ `NOT_FOUND 的 status 不是表内值: expected 500 to be 404` |
| ② | 命中注册表的文案必须 ≠ 通用文案；并先证明**表里没有任何一条抄成通用文案**（否则②恒真） | 变异 A：`message: GENERIC…` | ❌（`:42` 那条确实抓到了 500 码这一支） | ❌ 同时红，且把「恒真前置」钉成显式断言 |
| ③ | 响应形状 `toStrictEqual`（多一个 `details: undefined` 键也红） | 变异 B：`details` 键无条件存在 | ✅ 全绿（`toEqual` 忽略 undefined 键 = 洞） | ❌ 红 |
| ④ | `details` 与 `gateDetails` 并存时以 `details` 为准 | 变异 B：优先级反转 | ✅ 全绿（旧用例只测「单独存在」两种） | ❌ 红 |
| ⑤ | `errorCodes.ts` **必须零 import**（此前只有 `errorCodes.ts:13-14` 的散文注释，谁加 import 都不红） | — | — | 真用例 + 阳性对照（§2.3） |

变异 A/B 各跑一次，共 **5 红 / 其余绿**，之后 `cp` 复原并 `git diff` 确认生产文件零差异，复跑 `Tests 51 passed (51)`。

### 2.3 ⑤ 的阳性对照（四种引用写法都要抓到）

判据函数 `findImportOffenders()` 抽成模块级**单一实现**，真用例与对照**共用同一份**——避免「对照里另抄一份正则，正则被改坏时对照仍绿」这种假对照。
四条正例逐条 `toHaveLength(1)`：`import {x} from`、`require(`、`export {y} from`、`import('./heavy')`；
三条反例 `toEqual([])`：注释里的 import/require 字样、`export interface` + `export const`。

计划书把 ⑤ 放在 `errorCodes.test.ts`，并要求该文件顶部补 `fs`/`path`。我把它放在 `routeErrorSourceGuard.test.ts`，理由：那个文件已有 `stripComments`，放过去可避免**第三份** `stripComments` 逐字副本（本仓头号病是多份并行真源，见 memory「先查已有真源再提新建」）。判据本身与计划书一致（四种写法 + 剥注释）。

## 4. 对我自己既往数字的更正（这条比加固更重要）

我在 2026-09-20 早些时候写进权威文档 §9 B15 的「第 1 次 3 个文件红 / 第 2 次 5 个文件红」——**提取方法是错的**：当时用 `grep -oE "src/.*\.test\.ts"` 从整份日志里抓文件名，而 vitest 会在**通过**用例的 `stdout |` 行里也打印文件名 ⇒ 抓出来的是「日志里出现过的文件」，不是「红的文件」。
