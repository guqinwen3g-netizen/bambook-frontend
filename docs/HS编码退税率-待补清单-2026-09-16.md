## 三、⚠️ 顺带发现的第二个根因：**编码书写格式不一致**

盘点时发现档案与报关行的写法**不同**：

| 来源 | 写法 | 示例 |
|---|---|---|
| `HsCode.code`（档案） | **无分隔符** | `52093900` |
| `CustomsDeclarationLine.hsCode`（报关行） | **带点** | `6204.43.00` |

原来的匹配是**精确字符串比较** → 两者必然失配。**这意味着：即使按本清单补了退税率，
若档案里写成不带点的形式，仍然匹配不上、仍然算不出退税。**

**已修复**（`taxRefundCalcService.ts` 的 `normHs()`）：匹配时**去掉点与空白后比较**，
带点/不带点两种写法都能命中（中国海关 HS 为 10 位如 `5209.39.00.00`，实务中两种写法都常见）。
已加单测钉住（正反两个方向的格式不一致各 1 例），并证伪（去掉归一化 → 2 例转红）。

**补录建议**：与报关单**保持同一种写法**（建议带点，如 `6204.43.00`），
减少人工核对时的困惑——虽然系统已兼容，但**人看的时候不必再去数位数**。

## 四、补录入口（推荐走脚本，见 §四之二）

- **UI**：报关/外贸模块 → HS 编码档案 → 新增/编辑（字段「出口退税率(%)」）
- **接口**：`POST /api/v2/customs/hs-codes`（`customs:write`）
- 补录时 `isActive` 须为 `true`（查询只取 active 的）

### 四之二、补录脚本（默认 dry-run，自带回验）

**2026-09-16 复核**：真库仍是「档案 1 条 / 报关行 7 个编码**连档案都不存在**」，
故是 7 条**新增**（不是 7 处编辑），每条还需 `description` + `category`（均必填）。

手工点 7 次有两个**肉眼看不出的静默失败**，故改为脚本：

| 陷阱 | 说明 |
|---|---|
| ① **位数/写法不一致** | 归一化只去「点与空格」、**不比位数**。档案写 `6204.43.0000`(10位) 而报关行是 `6204.43.00`(8位) → 归一化后 `6204430000` ≠ `62044300` → **补进去也查不到退税率** |
| ② **归一化后重复** | 档案里同时有 `52093900` 与 `5209.39.00` → 命中哪条不确定（注意 `createHsCode` 的查重是**精确字符串**，不会拦这种重复） |

```bash
# 1) 从真库生成待填模板（7 条，rebateRate 全为 null）
node scripts/hs-rebate-import.mjs --emit-template docs/hs-rebate-rates.json

# 2) 业务/财务按税则填写 rebateRate + category 后，先预检（不写库）
node scripts/hs-rebate-import.mjs --rates-file docs/hs-rebate-rates.json

# 3) 确认无误再写入，脚本会**自动回验**（真实报缺端点）
node scripts/hs-rebate-import.mjs --rates-file docs/hs-rebate-rates.json --apply

# 4) 只回验（不写库）
node scripts/hs-rebate-import.mjs --verify-only
```

**⚠️ 脚本不提供任何退税率默认值** —— rate 缺失/非数字一律拒绝。
退税率是税则事实，**必须由业务/财务确认**（历史上有 16/15/13 多档）。
脚本负责的是「录入 + 证明真的生效」，不是「猜数」。

## 五、补录后怎么验证

**方式一（脚本，推荐）**：`--apply` 会自动跑回验（档案覆盖率 + 抽样报关单报缺端点）。

**方式二（手工）**：

1. 打开任一报关单 → 调 `GET /api/v2/customs/declarations/:id/tax-refund/gaps`
   —— 对应 HS 的 `hs_rebate_rate` 缺项应**自动消失**（gaps 是实时计算的，不需要清缓存）。
2. 对已有退税单（`Draft` / `Rejected` 状态）调
   `POST /api/v2/customs/declarations/:id/tax-refund/recalc` → 金额应被自动补上。
3. 注意：真库那张退税单当前是 **`Reviewing`** 状态，**不允许重算**（已提交的申报数据不可悄悄改）；
   需先由业务方打回（`Rejected`）或新建草稿。

### 五之二、端到端已实证（2026-09-16）

因为真库那张退税单是 `Reviewing`（recalc 被状态约束拒绝），**「补录后金额真的算得出」在真库上无法验证**。
故建了自回滚演练：`scripts/acceptance-hs-rebate-drill.mjs` —— **16 通过 / 0 失败**：

| 锚点 | 实测 |
|---|---|
| R1 补录**前** | `gaps` 含 `hs_rebate_rate`（ref=该编码）且 `refundableVat = null` ← **复现了阻断** |
| R2 补录**后** | 缺项自动消失；`refundableVat = 9360`，且脚本**独立重算** `10000 × 7.2 × 13% = 9360` 相符 |
| R3 recalc 落库 | `refundableVat / refundAmount / refundableRate` = `9360 / 9360 / 13` |
| R4 幂等 | 再跑一次 `applied=false`、`diff=0`、金额不变（`fill_missing` 不覆盖已有值） |
| R5 口径 A | 金额链可手算复现，**未引入任何新汇率** |

演练用编码是 `9999.99.99`（明显非真实税则编码），**绝不拿生产那 7 个编码试写编造税率**；
跑完按精确 ID 硬删，真库零残留、`HsCode` 档案仍为 1 条。

**结论**：补录链路已证明可用，**唯一的剩余输入就是那 7 个确认税率**。

## 六、影响面

- **不补**：所有出口退税金额算不出（草稿金额为空），退税申报无法基于系统数据完成。
- **补全后**：`L10` 联动（报关放行 → 退税草稿）生成的草稿**直接带出正确金额**，人工只需复核。
