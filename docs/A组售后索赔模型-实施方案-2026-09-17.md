## 一、设计骨架（口径已定，不再讨论）

```
一次客诉 = 一个「售后案件」ClaimCase
   └── 多条处置 ClaimDisposition（可同时存在：100 件里 30 件退货、70 件折让）
          ├── 钱这条腿 → 汇总成一张「退款单」CreditNote（客户拿到的正式单据）
          └── 货这条腿 → 一张「退货入库单」ReturnReceipt（货回来了，去向必记）
                              └── 去向：报废 Scrap / 换货补发 Replace / 返修 Repair
```

**四条不可动的原则**：
1. **钱只有一条线**（一张退款单）→ 对账不扯皮
2. **货只有一条线**（一张退货入库单）→ 库存不重不漏
3. **案件是总账** → 客户问"上次那批货怎么处理的"，一个案件全看到
4. **退款单有独立状态**：`未核销 → 部分核销 → 已结清`（**不复用发票的 `Paid`** —— 现状卡死就在这）

## 二、Schema（新增 4 张表 + 1 个号段）

> ⚠️ **本文件只写设计，未落迁移**。迁移动的是**有真实业务数据的库**，
> 必须按仓库既有流程：`prisma migrate dev` 生成 → 本地库跑通 → 上线前 `migrate deploy`。

```prisma
/// 售后案件（一次客诉一条）
model ClaimCase {
  id            String @id            // CLM-CASE__${shortId}
  caseNumber    String @unique        // 号段 CLM-（已存在于 businessNumberService 的 VALID_PREFIXES）
  customerRelationId String?          // 客户（Relation）
  customerName  String?
  sourceOrderId String?               // 关联订单（可空：客户可能只投诉不指订单）
  sourceInvoiceId String?             // 关联发票
  /// 登记 → 处理中 → 待审批 → 已处理 → 已关闭 / 已撤销
  status        String @default("Registered")
  problemDesc   String                // 问题描述
  attachments   Json?                 // 照片/文件
  reportedAt    String                // 客户报诉日 YYYY-MM-DD
  reportedBy    String                // 登记人 userId
  closedAt      String?
  deletedAt     DateTime?
  createdAt     BigInt
  updatedAt     BigInt
}

/// 案件下的一条处置（一个案件可多条）
model ClaimDisposition {
  id            String @id
  claimCaseId   String                // 关联 ClaimCase
  /// Allowance(折让) | ReturnRefund(退货退款) | Replace(换货补发) | Repair(返修)
  kind          String
  /// 数量（退货/换货/返修必填；折让可空）
  quantity      Decimal? @db.Decimal(18, 4)
  unit          String?
  /// 金额（折让/退货退款必填；**正数表示"退给客户多少"**，落库时转负向票）
  amount        Decimal? @db.Decimal(18, 4)
  currency      String?
  /// 退货去向（仅动货的三种必填）：Scrap | Replace | Repair
  returnDisposition String?
  /// 关联产出：退款单 / 退货入库单 / 补发出运单 / 返修工单
  creditNoteId       String?
  returnReceiptId    String?
  replacementShipmentId String?
  repairWorkOrderId  String?
  status        String @default("Draft")   // Draft → Approved → Executed / Cancelled
  createdAt     BigInt
  updatedAt     BigInt
}

/// 退款单（贷项通知单 CN）—— 独立单据 + **独立状态**
model CreditNote {
  id            String @id            // CN__${shortId}
  creditNoteNumber String @unique     // 号段需**新增**（见 §五.1）
  customerRelationId String?
  customerName  String?
  claimCaseId   String?               // 来源案件（可空：也支持非客诉的纯折让）
  currency      String
  /// 原始金额（**正数**，语义 = 应退客户）
  amount        Decimal @db.Decimal(18, 4)
  /// ★ 未核销余额（= amount − Σ核销）。**结清判据 = 余额为 0**，不是复用发票的 Paid
  openAmount    Decimal @db.Decimal(18, 4)
  /// ★ 独立状态：Open(未核销) | PartiallyApplied(部分核销) | Closed(已结清) | Cancelled(已作废)
  status        String @default("Open")
  issueDate     String
  /// 核销记录（抵扣某张发票 / 现金退款），独立子表更规范；此处先列最小字段
  appliedToInvoiceId String?
  refundedAt    String?
  deletedAt     DateTime?
  createdAt     BigInt
  updatedAt     BigInt
}

/// 退货入库单（货这条腿）—— 去向必记
model ReturnReceipt {
  id            String @id
  receiptNumber String @unique        // 号段需新增（或复用 RT-）
  claimCaseId   String
  warehouseId   String                // 入哪个仓
  /// Scrap(报废) | Replace(换货补发) | Repair(返修) —— **必填**
  disposition   String
  status        String @default("Draft")  // Draft → Received → Dispositioned
  receivedAt    String?
  createdAt     BigInt
  updatedAt     BigInt
}
```

**索引**：`ClaimCase(customerRelationId, status)` · `ClaimDisposition(claimCaseId)` ·
`CreditNote(customerRelationId, status)` · `ReturnReceipt(claimCaseId)`。

## 三、服务层（建议文件）

| 文件 | 职责 |
|---|---|
| `claims/claimCaseService.ts` | 案件 CRUD + 状态机 + 处置明细增删 + **撤销（= 作废退款单 + 解开联动）** |
| `claims/creditNoteService.ts` | 开单 / **核销**（抵扣发票 or 现金退款）/ 余额与状态推进 / 作废 |
| `claims/returnReceiptService.ts` | 退货入库（**走 inventoryService 的入库流水**，不自己写库存）+ 去向标记 |
| `claims/claimSettlement.ts` | **钱/货两条腿的联动收口点**（唯一入口，禁各处置各写一套） |

**★ 收口点纪律（本仓反复踩过）**：所有副作用（开退款单、写库存、推进案件状态）
必须挂在**一个共用内核**上；`route` 与 Agent 三通道都调它 —— **不要逐个入口补**。

**关键接口**：
```ts
createClaimCase(input, actorId): Result<{ case }>
addDisposition(caseId, input, actorId): Result<{ disposition }>   // 按 kind 分派校验
approveDisposition(dispositionId, actorId): Result<{ disposition }>
executeDisposition(dispositionId, actorId): Result<{ ...产出单据 }>
  // ★ 内部走 claimSettlement：折让/退货退款 → 开退款单；退货退款/换货/返修 → 开退货入库单
applyCreditNote(noteId, { toInvoiceId } | { refund }, actorId): Result<{ note }>
cancelClaimCase(caseId, actorId): Result<{ case }>   // 作废退款单 + 退货入库单回退 + 留痕
```

**审批（口径 A7）**：**任何金额都汇总领导批** ⇒ 处置审批走 `approvals/` 内核，
`aftersales:approve` 作为 **UI 能力标签**（口径 B1：非强制门禁）。

## 四、验收（口径 A1-附 的 5 条标准，逐条可验）

| 标准 | 怎么验 |
|---|---|
| **有单据** | 退款单可打印（CN 模板，`templates/docTemplates/` 加一个）+ 退货入库单可打印 |
| **有审批** | 处置提交 → 走 `approvals/` 内核 → 领导批 → 才能 execute（未批 execute 必须 409） |
| **有留痕** | 每步写 `auditLog`（**字段是 `action` 不是 `operation`**）+ `EntityLink` |
| **能撤销** | 撤销 = 作废退款单 + 退货入库单状态回退 + 案件回退 + 留痕；**且撤销后余额不再挂账** |
| **真库验过** | `scripts/acceptance-claim-model.ts`：真库建案 → 四条处置各跑一遍 → **自回滚 + 独立复核零残留** |

**真库演练必守**（本仓教训）：演练数据用明显假标识（`9999.99.99` / `DRILL-` 前缀），
按精确 ID 硬删并**独立复核零残留**；注意 service 会**顺带写** `auditLog` / `notification` / `EntityLink`，回滚要一并清。

## 五、开工顺序（建议 4 个批次）

### 批次 A-1：schema + 号段 + 服务骨架（**不接路由**）
1. `prisma migrate dev` 生成迁移（4 张表）
2. **号段**：`CreditNote.creditNoteNumber` 需要前缀 —— 检查 `businessNumberService.VALID_PREFIXES`：
   **`CLM` 已在册**（可复用），`RT` 也在册 ⇒ 退款单用 `CLM`，退货入库单用 `RT`，**不新增前缀**。
   ⚠️ 取号必须走 `nextBusinessNumber`（**含软删行的占用校验**）—— 别手写 `count+1`（见 P2-1 的教训）
3. 服务骨架 + 单测（状态机、余额推进、撤销）

### 批次 A-2：路由 + 审批接线 + 前端（**一期只做「折让 + 退货退款」**）
- 一期范围：`Allowance` + `ReturnRefund`（另两种处置 `kind` 先**拒绝**并提示"二期支持"）
- 路由：`POST/GET /api/v1/claims`、`POST /api/v1/claims/:id/dispositions`、
  `POST /api/v1/claims/dispositions/:id/approve|execute`、`POST /api/v1/credit-notes/:id/apply`
- 前端：案件列表 + 登记表单 + 处置明细 + 退款单打印入口

### 批次 A-3：二期（换货补发 + 返修）
- 需牵动**车间**：补发走出运单、返修走工单 ⇒ 先确认「返修工单」是新建还是复用现有生产模块

### 批次 A-4：真库演练 + 门禁
- `scripts/acceptance-claim-model.ts`（自回滚 + 零残留复核）
- 跨层对撞测试（前端预筛 ⟺ 后端校验同口径）

## 六、开工前必须确认的 3 件事（**不是口径，是现状核查**）

### 1. `CLM` 前缀可用性 —— ✅ **已核查（2026-09-17，真库只读）**

```
Invoice 表内 'CLM-%' 行数 = 0          ← 业务表零占用
SEQ_CLM_2026 已存在，seq = 8           ← 序列已用到 8
新表（ClaimCase/CreditNote/ReturnReceipt/ClaimDisposition）均不存在 ← 干净起点
```

⇒ **可用，且不会撞号**：序列**领先于**业务表（那 8 个号取走后未落库），
新开的退款单会从 **`CLM-2026-0009`** 起 ✓
> ⚠️ 但取号**必须走 `nextBusinessNumber`** —— 它的 `occupied` 追平机制正是为这种
> 「序列与业务表不同步」设计的；**别手写 `count+1`**（P2-1 的教训：那会撞号）。

### 2. 退款单的「现金退款」出口 —— ⏸ **待定（需与财务域对齐）**

口径 A2 说余额可"抵扣下张发票"或"现金退款"。**现金退款要不要走付款凭证（PaymentVoucher）？**
若要，需与财务域对齐（付款申请/凭证链路，属 H 组工作流）。
**建议**：一期**先只做「抵扣发票」**（覆盖绝大多数场景），现金退款留二期 ——
但**这不是砍范围**，是排期（同 A1 的交付节奏原则）。

### 3. 负额发票的既有状态机 —— ✅ **已确认，且本方案天然绕开**

`recalcInvoiceStatus` 对 `amount ≤ 0` 的票**永远到不了 `Paid`**（现状卡死点）。
本方案**新建 `CreditNote` 表、不复用 `Invoice`** ⇒ 天然绕开该问题 ✓
⚠️ 但要确认**没有别处**仍在把"贷项"当 `Invoice` 处理 ——
已知两处需在开工时复查：`MaterialReturn.claim`（供应商侧负向 Payable 票）·
`shared/openReceivable.ts`（未结清应收判据，已含 `amount > 0` 守卫）。
