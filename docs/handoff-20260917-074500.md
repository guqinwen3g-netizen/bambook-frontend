### 3. 连锁链条（全部是代码事实 —— 这才是「少收」为什么是**高危**）

```
客户少付 150 → 核销 9850 → Invoice.status = PartiallyPaid（核销零容差：total.gte(amount) 才 Paid）
   ↓
① 催办/账龄：status ∈ {Issued, PartiallyPaid} 且 open > 0.005 → **永远在逾期清单里**
   （dunningService.loadOverdueInvoices；那个 0.005 只是半分钱阈值，挡不住 150）
   ↓
② 信用 usedAmount = Σ open（净额口径）→ **永久占用额度**
   ↓
③ 60 天后 riskWatchdog.runCreditRiskScan → 自动冻结该客户授信
   （creditService.maxOverdueDays 只按 status 过滤，**连 open 都不看**）
   ↓
④ 唯一的自动解冻路径 thawAutoFrozenIfSettled 要求 maxOverdueDays ≤ 60
   → **永远不满足 → 永不解冻** → 业务员开不了新单 → **骂娘**
   ↓
⑤ 风险评分：>180 天 −20 分；bad_debt 预警（dedupKey 只报一次）
```

**另一个被消费的不变量**：`riskService.ts:422` 的「按期回款率」以
`status === 'Paid' && settlementDate != null` 为口径 → **Paid 的票必须有结算日**，否则被静默漏统计。

### 4. ★★ 修掉的真 bug：`updateInvoice` 改金额**从不重算 status**（无歧义，不需要口径）

**病灶**：`PATCH /api/v1/finance/:id` 允许改 `amount`（`INVOICE_PATCH_FIELDS` 里有），
但 `updateInvoice` **从不调用 `recalcInvoiceStatus`** —— 而 `Invoice.status` 是**派生字段**
（真源 = Σ `InvoiceAllocation` vs `amount`，见 `allocationService.recalcInvoiceStatus`）。
**派生字段不在写入点重算 → 状态与净额脱钩。**

**为什么这是「业务上真会发生」的路径**：财务处理客户少收时，系统里**唯一**能「抹平」的手段就是改发票金额。
而这条唯一的路会留下脏数据 —— 真库演练实测（`scripts/acceptance-invoice-amount-recalc.mjs`，修前 3 红）：

| 场景 | 修前 | 修后 |
|---|---|---|
| 改到 **= 已核销**（open 归零） | open=0 但 status **停在 PartiallyPaid** = **僵尸票** | status → **Paid** |
| 改到 **< 已核销**（如 800 < 900） | **放行** → open = **−100** = 超额核销 | **409 `AMOUNT_BELOW_ALLOCATED`**（拦在写之前） |
| 已 `Paid` 的票改**大**（1000 → 1100） | open=100 但 status **停在 Paid** =「已结清」的票其实还欠钱 | status → **PartiallyPaid** |

**修法（`server/src/finance/invoiceMutationService.ts`）**：

1. **amount 变化时**：先取 Σ`InvoiceAllocation`；`newAmount < Σapplied` → **拒绝**
   （维持 `applyAllocation` 已强制的 `Σapplied ≤ amount` 不变量 —— 这不是新口径，是补上既有不变量的缺口）。
2. amount 落库**之后**调 `recalcInvoiceStatus` 重算 status（必须在之后：该函数自己读 `invoice.amount`）。
3. 重算成 `Paid` 且 `settlementDate` 为空 → 补 **最后一笔核销的 `appliedDate`**
   （**不是「今天」** —— 改金额不等于今天结算；取真源 = 核销明细），保住 `riskService` 按期回款率的口径。

**顺带修的第二处（同一类陷阱第二次出现）**：`toError` 也是**硬编码白名单**，
新码 `AMOUNT_BELOW_ALLOCATED` 不在名单 → 兜成 `UPDATE_FAILED` → route 映射 **500**（真库演练 S5 抓到）。
修法：抽 `PASSTHROUGH_ERROR_CODES` 常量 + 补码 + route `statusCodeMap` 补 409。
> 前一次是 `allocationMutationService.toAllocationError`（`handoff-051500` 的 T5）。
> **本仓已两次踩同一坑** → 已写进 skill：**每加一个新业务码都要问「它不在名单里时会变成什么？」**

## 四、坑（本批新踩，接手人直接复用；已同步进 skill）

### 1. ★★ 不要用 `if (false && cond)` 来「关掉」一段代码做证伪

TS 会把该块判为**不可达代码**，从而**丢弃之前的类型收窄** ——
本例里块内的 `normalized.data` 立刻报 `TS2339: Property 'data' does not exist on type '... | { ok:false; error }'`
→ **ts-node 启动失败** → 后端 40s 起不来、演练报 `fetch failed`，
**极易误判成「代码写坏了 / 演练脚本坏了」**（本批真踩到，白查一轮）。

**正确做法**：改**条件里的值**让它恒不成立，保持代码可达 ——
例如把 `if (nextAmount.lt(applied))` 改成 `if (nextAmount.lt(new Prisma.Decimal(0)))`。
（顺带：`if (false && x)` 若块内**不依赖外部类型收窄**（如只是几个 await 调用）则不会报错 ——
所以「A 证伪能跑、B 证伪起不来」这种不对称结果更容易让人误判。）

### 2. ★ 建 `Receipt` 凭证会触发 L5 自动核销 —— 演练要**先建凭证、后建票**

`PaymentVoucherCreated` → L5 核销到该客户**最早的未结清 Receivable 票**。
若先建票再建凭证，L5 会把凭证自动核销掉，随后的手动核销就吃 `AMOUNT_EXCEEDS_VOUCHER_REMAINING`。
本批演练：V1/V2 **先建**（那时客户名下还没有票 → L5 走 `no matching invoice` 跳过）；
**票 C 用独立客户档案 `REL_C`** —— 否则建第二张凭证 V2 时 L5 会把它核销到票 A/B 上。

### 3. ★ 「错误码 → HTTP 状态码」白名单漏码 —— **本仓已两次踩同一坑**

`toAllocationError`（`handoff-051500` T5）与 `toError`（本批 S5）都是硬编码白名单，
漏码 → 兜成 `CREATE_FAILED`/`UPDATE_FAILED` → **500**（用户看到「服务器错误」而实际只是参数/状态问题）。
**每加一个新业务码都要问「它不在名单里时会变成什么？」** 并同时补 route 的 `statusCodeMap`。
守护：本批的 ③ 路由层单测 + 演练 S5 就是回归门禁。

### 4. ★ 真库「0 条」不等于「场景不存在」—— 真库是 seed 演示数据

27 张 PartiallyPaid 的尾巴全是 50%/70% 整档（脚本造的），**小尾巴 0 张**。
不能据此说「少收不用管」。**判据只能是代码事实 + 构造会踩它的输入。**

### 5. ★ mock 的 `invoice.findUnique` 必须有状态（否则重算断言恒真）

`recalcInvoiceStatus` 自己读 `invoice.amount`。若 mock 的 `findUnique` 恒返回**旧**行，
「改金额后重算」的断言就是在假数据上**恒真**（= 空过的验证器）。
做法：让 mock 的 `update` 合并进闭包状态，`findUnique` 返回当前态。

### 6. 环境坑（沿用）

`launchd` 托管后端不继承 shell env（不能用 env 开关证伪）· `ts-node` 无 watch 必须 `kickstart -k`
+ 健康检查循环重试（实测 9×2s = 18s ready）· 沙箱 `curl` 必须 `--noproxy '*'`
（`HTTP_PROXY` 会让本地 8081 返 502）· BSD `grep` 不支持 `\|` · `zsh` 下未加引号的 glob 会中止整条命令。

## 五、下一步（建议顺序）

### ★ 需要 Kevin 一句话的口径（本批的**核心待决项**）

**「客户少收的那部分钱，系统该怎么销账？」** —— 现状：**没有任何销账能力**，
唯一能抹平的手段是「改发票金额」，而那条路刚被本批修好（不再产生僵尸票），
但它**改的是票面金额**（发票是给客户的凭证，金额不该随便改）且**没有原因留痕、没有审批**。

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 单一「差额核销」动作** | 一个端点 + 原因枚举（尾差 / 银行手续费 / 质量扣款 / 汇差 / 坏账），按金额与原因决定审批层级，复用悬空的 `invoices:approve:writeoff` | 改动最小、**一次覆盖三个层次** | 原因枚举要一次定全 |
| **B. 分两条线** | 小额尾差半自动销账（无审批）+ 大额走 `aftersales:approve`（客诉扣赔）+ 坏账走 writeoff | **最贴设计文档既有口径** | 要做 3 套（售后模块整个不存在） |
| **C. 贷项通知单 CreditNote** | 开负数发票冲减，原票被 CN 核销 | **最贴外贸实务**（质量索赔通常开 CN），审计链最完整 | 改动面最大（IOA / 批次结算 / 退税联动全要跟） |
| **D. 只提示不建模型** | 核销时提示差额，让财务自己决定 | 最省事 | 等于不解决（财务仍只能改金额） |

**我的建议：A（可后续演进到 C）** —— 理由：三个层次共用一套「原因 + 审批 + 留痕」骨架，
覆盖 L2 #8 与 L2 #16 的一半；C 的联动面（批次结算/退税）本批已验证是高风险区，宜单独批次做。

**配套要一起判的**：

1. **尾差阈值**（若选 A/B）：多少算「尾差」可以免审批？绝对额（如 ≤50 USD）/ 票面比例（如 ≤0.5%）/ 两者取小？
2. **销账后发票状态**：复用 `Paid`（判定点不用改，但「销账」与「实收」在状态上不可区分，只能靠审计行区分）
   还是新增 `WrittenOff`（语义准，但要扫全部 `status='Paid'` 消费点 + 前端 + 报表）？
3. **`bankFee` 在 Receipt 侧要不要参与核销**？现状：**记了但零消费**（真库 37 条、合计 880.00，全部已 reconciled）。
   要不要「凭证金额 − bankFee = 可核销额」？
4. **撤销核销后 `settlementDate` 要不要清**？（既有行为是「不清」，本批未动）
