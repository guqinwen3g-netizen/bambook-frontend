## 二、三个 ❓ 拍板项的建议（行业惯例）

### ❓1 空运是否要 MAWB/HAWB —— **建议：要，两个都加（nullable）**

行业事实：空运提单是两层结构——航空公司出 **MAWB**（给货代）、货代出 **HAWB**（给发货人）。
外贸业务对账/查货时两层单号都可能被问到（货代给发货人的通常是 HAWB，向航司查货用 MAWB）。
现状 `Shipment` 只有 `trackingNumber`（快递场景），`vesselOrFlight` 承载航班号。

**建议**：`Shipment` 加 `masterBillNo`（MAWB）+ `houseBillNo`（HAWB）两个可空列。
海运单 `billOfLadingNo` 是否同批加：海运 B/L 目前没有字段（containerNumber 有了，B/L 号没有）——
行业上海运 B/L 号是必录项，建议同批补 `billOfLadingNo`。三个列都是纯快照文本，零风险。

### ❓2 订舱是否多票并舱 —— **建议：不建独立 Booking 实体，用"共享订舱号"表达**

行业事实：并舱（LCL 拼箱/多票一柜）在货代侧是一个 booking 对多个 shipper 的货。
本系统 `Shipment` 已经是"票"粒度，且 DR-016 已建模了订单↔票的合票（ShipmentOrderAllocation）。

**建议**：订舱字段直接放 `Shipment` 上（1:1 常态）；并舱 = 多张运单填**同一个订舱号**（+ 同一
`containerNumber`，字段已有）。不唯一约束、不建 Booking 表。
理由：建独立 Booking 实体要引入 Booking↔Shipment 关系表、订舱状态机、并舱分摊——为目前
"一票一订舱为主、偶发拼柜"的业务量是过度建模；共享订舱号已满足"按订舱查询所有票"的诉求。
若未来并舱分摊费用成为常态，再升级为实体（迁移成本低：字段值平移进 Booking 行）。

### ❓3 「进仓」与 T3 仓库/货代仓货权 —— **建议：不并批，货代仓不建库存账**

行业事实：货进货代仓（进仓）后货权仍在发货人或已随单据转移给买家，但**不在我方库存账里**——
货代仓是受托保管，不是自有仓。T3 的库存账（InventoryItem，单一写入口 createStockMovement）
管的是自有仓（Main/Auxiliary）的收发存。

**建议**：进仓在本批只做**时间线记录**（陆运段的"实际送达货代仓"即进仓时刻），不建
InventoryItem、不动 Warehouse 货权语义（D7 货权字段继续挂起，另立批次）。
T6 与 T3 的边界一句话：**货离开我方自有仓（T3 Outbound 扣账）→ 进入物流段（T6 记录），
两个域不共享账**。

## 三、数据模型设计

### T6-a 订舱段（Shipment 加列，一张迁移）

```
Shipment 新增（全部可空，零破坏）：
  bookingNo        String?  -- 订舱号（我方/货代侧；并舱 = 多票同号）
  soNumber         String?  -- 船公司 SO（Shipping Order）
  spaceConfirmedAt BigInt?  -- 舱位确认时间（epoch ms，同库 BigInt 时间戳惯例）
  cutOffAt         String?  -- 截关时间（YYYY-MM-DD HH:mm；含日期时间的用字符串列与 etd/eta 风格一致）
  docCutOffAt      String?  -- 截单时间
  billOfLadingNo   String?  -- 海运 B/L 号（❓1 建议：同批补）
  masterBillNo     String?  -- 空运 MAWB
  houseBillNo      String?  -- 空运 HAWB
```

- 不加状态机：订舱确认与否由 `spaceConfirmedAt` 是否有值表达；`Booked` 状态继续是流转门槛
  （订舱段字段在 Draft/Booked 任何状态都可填，不与状态机耦合——补录场景友好）。
- 不加唯一约束（并舱需要同号）。
- 权限：随 `shipments:write` 既有门。

### T6-b 陆运段（新表，一张迁移）

```
model ShipmentLandTransport {
  id              String @id      -- SLT__ 前缀
  shipmentId      String          -- snapshot FK → Shipment.id（一票一段，方案见下"多段？"）
  direction       String @default("factory_to_forwarder")  -- 工厂 → 货代仓（D4 拍板 3 主路径；
                                   -- 预留 forwarder_to_port 等方向值，本批只用默认值）
  plannedArrivalAt String?        -- 约定运抵货代仓时间（进仓约时）
  actualDeliveredAt String?       -- 实际送达（= 进仓时刻，时间线记录）
  plateNo         String?         -- 车牌
  driverName      String?         -- 司机
  driverPhone     String?         -- 司机电话
  carrierName     String?         -- 车队/承运商（冗余快照，不强制 Relation FK，与全库 snapshot 风格一致）
  inlandFreightAmount    Decimal? -- 陆运费（D4：FOB 进成本、CIF 走应收——见"毛利口径"）
  inlandFreightCurrency String?
  warehouseFeeAmount     Decimal? -- 进仓费
  warehouseFeeCurrency   String?
  notes           String?
  createdAt/updatedAt BigInt     -- 无软删：随 Shipment 生命周期，错了整行改
  @@index([shipmentId])
}
```

- **一票一段**（upsert 语义）：当前业务一票出运就一次工厂→货代仓的陆运。真有多段（提柜/还柜）
  再升多行，字段不浪费。
- **费用列只采集不分支**：陆运费/进仓费在此登记（采集入口），**进毛利的口径切换不属本批**
  ——它和"毛利表 CIF Incoterms 分支"是同一刀（D4 连带 1 + T2 回报 ❓1），需先补录存量、
  一起切。切换前这些费用字段只是"记录在案"，不改变任何现有毛利数字。
- 与 T3 边界（❓3）：本表不碰库存。货代仓不建 Warehouse 行、不建 InventoryItem。
