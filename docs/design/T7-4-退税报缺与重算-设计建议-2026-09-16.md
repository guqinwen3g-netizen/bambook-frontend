## 一、先定性：「出口单含退税再累加」是对账层面，不是毛利层面

业务方原话（在回答「对账多币种怎么处理」时说的）：
> 「……中间涉及到一个退税的问题，因为如果是出口单的话，大部分都是会最终要含退税，然后再加起来的。」

**判断：这是「对账 / 内部结算」层面的事**，理由三条：

1. **语境**：这句话是在讨论**对账**时说的，不是在讨论报价或成本。
2. **业务实质**：出口业务的**实际回笼资金 = 客户付的货款（收汇） + 国家退的税**。
   退税是**钱真的回来了**，不是报价里的一项成本。所以它该进"这单最终收回多少钱"的口径。
3. **与已拍板口径 A 天然一致**：口径 A-3 说「**已结汇的**按结汇汇率敲定」——
   退税同理，**只算已到账的**（`TaxRefund.refundDate` 有值 / status = `Refunded`），
   未到账的不预提（预提等于用没到手的钱做结算，与 A-3 的保守精神冲突）。

**落地口径**：
```
对账「内部结算口径」= 已结汇折 CNY（T7-1 的 settledCny） + 已退税 CNY（新增）
```
两者都只计「已实现」的钱，都不做任何估算折算。

**同时明确边界（避免混淆）**：**毛利层面**是另一件事 ——
T2 回报 ❓1 那个「陆运/进仓费是否进成本」的 Incoterms 分支切换，是**成本侧**，
与退税（收入侧）不同域，不要混为一谈。本判断**不改变**任何毛利口径。

## 二、T7-4 设计：现状 → 三件套

### 现状（已核准）

`createTaxRefundFromDeclaration`（`customsService.ts:1497-1600`）**已经会自动算**
（FOB / 汇率 / 按 HS 加权退税额，见 T7 现状核准 §五——矩阵说它"不自动算"是判错了）。
真实缺口是：**算不出来时静默存 `null`** —— 用户拿到一张金额全空的退税单，**不知道为什么空**。

两类算不出的情形：
- `fxRate == null`（订单既无应收发票汇率、也无收款凭证汇率）→ `exportAmountCny = null` → `refundableVat = null`
- 报关行**缺 HS 编码**或该 HS 未登记 `exportTaxRebateRate` → 该行被跳过；全跳 → `refundableVat = null`

### 1️⃣ 「缺什么」**实时计算，不存库**

新增只读函数 `describeTaxRefundGaps(prisma, declarationId)`，返回：

```ts
interface TaxRefundGap {
  code: 'fx_rate' | 'hs_rebate_rate' | 'line_total' | 'no_lines';
  label: string;          // 给人看的一句话
  howToFix: string;       // 去哪儿补
  ref?: string;           // HS 编码 / 行号
}
```

三类缺项：

| code | 触发条件 | 补齐入口 |
|---|---|---|
| `fx_rate` | 订单无应收发票汇率 且 无收款凭证汇率 | 给发票补 `exchangeRate`，或给收汇凭证补 `exchangeRate` |
| `hs_rebate_rate` | 报关行的 `hsCode` 为空 / 该 HS 的 `exportTaxRebateRate` 为空 | HS 编码档案补退税率 |
| `line_total` | 报关行 `totalAmount` 为空 | 报关单补行金额 |

**为什么不存库**：缺失是**当前状态的函数**——补齐后应当**自动消失**。
存库会陈旧（要额外失效逻辑），还要加字段做迁移。实时算的成本极低（报关单行数很少），
且**零迁移**。退税单详情接口直接带上 `gaps`，UI 显示「缺 3 项：结汇汇率 / HS 6109 退税率 / 第 2 行金额」+ 补齐入口。

### 2️⃣ 重算入口：默认**只填 null，不覆盖人工值**

`POST /api/v1/customs/declarations/:declarationId/tax-refund/recalc`

- **默认 `mode = 'fill_missing'`**：只填**当前为 null** 的字段（`fxRate` / `exportAmountFob` /
  `exportAmountCny` / `refundableVat` / `refundableRate` / `refundAmount`），**已有值一律不动**
  —— 这样人工填过的金额不会被系统冲掉。
- 可选 `mode = 'force'`：全部重算；**先返回 diff**（哪些字段会从 X 变成 Y）由人确认，
  不直接落库（避免"一键重算把人工审核过的数改了"）。
- **状态约束（审计要求）**：只允许 `Draft` / `Rejected` 状态重算；
  `Submitted` 之后（`Reviewing` / `Approved` / `Refunded`）**拒绝**并说明原因
  —— 已提交/已批准的申报数据不能悄悄改。
- 幂等：同一报关单重算多次结果一致（纯函数式重算）。

### 3️⃣ 与现有自动推导的关系

- 自动推导（`L10` 联动，报关放行时触发）**保持不动**——它仍然在放行那一刻尝试生成草稿。
- 新增的 `gaps` + `recalc` 是**补救通道**：当时缺数据 → 后来补齐 → 重算。
- 幂等仍由 `declarationId` 唯一 + "不可重复生成"拦截保证（重算走 update，不新建）。

## 三、T7-2 / T7-3 遗留 4 项，我的判断

| # | 问题 | 我的判断 | 理由 |
|---|---|---|---|
| 1 | 真库 10/10 超差要不要深挖 | **不深挖，但要留脚本** | SIM 是生成数据，深挖得到的是数据生成器的规律，不是业务规律。真问题还是真噪音，**只有真实数据能回答**——验收脚本留着，生产数据一接就能跑 |
| 2 | 未收汇订单是否该报 | **保留报警，但加 dueDate 门槛** | 只对「**已过应收到期日**仍未收汇」的单报警。还没到期的单报警是噪音，**而预警一旦被无视就等于失效**。需引入 dueDate，属小扩展 |
| 3 | 前端挂载点 | **对账工作台（三合一）** | T7-2 三单一致、T7-3 收汇↔FOB、T7-1 多币种对账本质都是「财务核对」，放同一处才形成**核对工作台**；散到运单/订单详情里，用户得记着去三个地方看 |
| 4 | CIF 分支要不要造数 | **造一次，用完即删** | CIF 剥离是口径 D 明确要求的，而真库 48 张报关单**全是 FOB → 该分支真库零覆盖**；不造的话这段逻辑要到生产才第一次运行 |
