# 订单变更规则

> **PRD 关联**：§9.7 订单变更 5 类（①数量 / ②金额 / ③交期 / ④客户 / ⑤产品）+ 前后值 diff UI + AuditLog 留痕
> **落地状态**：❌ 全部 5 类变更当前直通无分级审批；✅ AuditLog 字段级 before/after 留痕模型已存在（实际仅部分路由写入 before/after）
> **DR-009 关联**：商业订单批准与生产放行分离——商业批准后即可采购先行，生产放行须 QC 通过 + 客户确认 + 产前样封存 + 主管手动确认
> **DR-010 关联**：已批准订单变更与取消控制——取消/暂停/改价/改数量/改交期均须走正式申请与审批；取消先进「取消申请中」，暂停先进「暂停申请中」
> **DR-007 关联**：审批路由按组织归属——负责团队销售主管或总领导审批；每次只需一位有效审批人

## §2A DR-010 已批准订单的取消与暂停控制

> **核心决策**（DR-010）：草稿/待审批订单可由业务员撤回、取消或暂停。领导批准订单后，订单进入正式承诺状态：取消、暂停、改价、改数量、改交期均不得由业务员直接修改，必须走正式申请与审批。

### 2A.1 订单生命周期与变更权限

| 阶段 | 变更权限 | 取消/暂停权限 |
|------|---------|-------------|
| 草稿/待审批 | 业务员可直接修改/撤回 | 业务员可直接取消/暂停 |
| 已批准（正式承诺） | 不得直接修改，须走正式申请与审批 | 须走取消/暂停申请与审批 |

### 2A.2 取消流程

| 步骤 | 状态 | 说明 |
|------|------|------|
| 1 | 取消申请中 | 业务员提交取消申请，系统汇总合同、面料采购、样品、生产、付款与库存影响 |
| 2 | 审批 | 销售主管或总领导为最终业务审批人；采购、QC、财务仅确认各自影响 |
| 3a | 直接结案 | 无不可逆承诺时，批准后直接结案 |
| 3b | 结案处理中 | 已有采购或生产承诺时，批准后进入结案处理中，完成供应商、物料、客户责任和财务损益处置后才可关闭 |

### 2A.3 暂停流程

| 步骤 | 状态 | 说明 |
|------|------|------|
| 1 | 暂停申请中 | 业务员提交暂停申请，必须记录原因、责任人和预计恢复日期 |
| 2 | 审批 | 销售主管或总领导批准后生效 |
| 3 | 暂停中 | 到期未恢复自动提醒，禁止无限期挂起 |
| 4 | 恢复/取消 | 恢复需确认条件满足；取消转取消流程 |

## §2B DR-009 商业订单批准与生产放行分离

> **核心决策**（DR-009）：商业订单批准（合同齐备 + 交期确认 + 主管批准）后即可启动采购先行，生产放行是独立步骤，须 QC 通过 + 客户确认 + 产前样封存 + 主管手动确认。

### 2B.1 七步分离链

| 步骤 | 名称 | 前置条件 | 审批人 |
|------|------|---------|--------|
| 1 | 商业订单批准 | 客户合同或等效订单依据齐备、交期确认 | 销售主管或总领导 |
| 2 | 采购先行 | 商业批准后即可启动面料采购及相关开发 | 标准流程，非紧急例外 |
| 3 | 生产放行 | 内部 QC 通过 + 业务员已登记客户确认 + 产前样已封存 | 销售主管或总领导手动确认 |
| 4 | 实际开工 | 面料实际可用并完成排产 | 生产排产确认 |
| 5 | 出运 QC | 大货生产完成后 QC 评审通过 | QC |
| 6 | 出运批准 | QC 通过后仍须手动批准「允许出运」 | 销售主管或总领导 |
| 7 | 履约终点 | 出运、合同履约、客户收货、财务结清分开记录 | 按贸易术语判定 |

### 2B.2 关键原则

| 原则 | 说明 |
|------|------|
| 定金不门禁 | 定金仅记录和跟踪，不作为统一采购门禁 |
| 封样不以面料到位为前提 | 生产放行不等待大货面料到位 |
| 出运 QC 独立 | 样品 QC 与大货出运前 QC 是两道独立、不可替代的质量门禁 |
| 贸易术语不默认 FOB | 每张订单必须记录实际贸易术语、指定地点和适用版本 |

## §2 5 类变更 × 审批矩阵（DR-007 组织归属版）

### 2.1 5 类变更字段归属

| 类别 | 涉及字段（Order 或 OrderLine 级） | 判定说明 |
|------|-------------------------------|---------|
| ① 数量变更 | Order.quantity / OrderLine.quantity（含 sizeBreakdown 内部数量变化） | 「整单总量变化」或「单行/单尺码数量变化」→ 统一按行级 before/after 百分比计算 |
| ② 金额变更 | OrderLine.unitPrice / Order.totalNet / Order.totalActual / currency | 单价变动、汇率变动、整单打折/加价 等导致金额变化 |
| ③ 交期变更 | Order.dueDate / Order.productionDate / Order.clientDate / OrderLine.exMillDate / OrderLine.deliveryDate / Order.productionPlanDeadline / delayNoticeDeadline | 任何对外交期字段 / 内部生产死线变化均触发；字段内部 String 日期直接对比 |
| ④ 客户变更 | Order.customer / Order.customerCode / Order.customerRelationId / Order.billTo*（结款方）/ Order.consignee*（收货方）/ Order.shipTo*（送达方） | 客户主体 / 结款 / 收货 三方任何 FK 或 Name 变更均属高风险；客户变更直接影响应收归属与信用额度占用 |
| ⑤ 产品变更 | Order.product / Order.type / Order.businessLine / OrderLine.materialCode / OrderLine.itemNo / OrderLine.styleNo / OrderLine.description / OrderLine.bomItems | 产品/面料/款式/BOM 结构变更 → 影响采购/BOM/生产工艺，属最高风险档之一 |

**同时命中多类（如客户+产品+数量同时改）**：**合并为单条 ApprovalRequest**（payload `hitChangeTypes: ["①","④","⑤"]`），审批人为负责团队销售主管或总领导（DR-007，每次只需一位有效审批人），避免审批人多次点。

### 2.2 审批分级规则（DR-007 组织归属版）

> **DR-007 核心**：审批路由以负责团队销售主管或总领导为准，替换旧版固定 L1/L2/L3 金额阈值层级。每次只需一位有效审批人；总领导拥有跨团队兜底权。

| 审批人 | 触发条件 | 解析逻辑 |
|------|---------|---------|
| 销售主管 | 所有变更类型（①数量/②金额/③交期/④客户/⑤产品） | 业务员归属的团队/部门主管（UserAccount.departmentId → Department.head）；负责该业务线与客户 |
| 总领导 | 跨团队兜底 + 被销售主管驳回的申诉 + 战略特批 + 任何量级客户/产品变更的兜底 | 跨团队兜底审批人；不依赖技术角色身份，通过业务审批 scope 授权 |

**变更比例算法细节**（供审批人参考，不作为硬性阈值）：
- ① 数量比例：`|new_qty - old_qty| / old_qty`（old_qty=0 视为新增行 → 按该订单行金额比例折算）
- ② 金额比例：`|new_amount - old_amount| / old_amount`（amount=unitPrice×quantity 或 Order.totalNet）
- ③ 交期天数差：`abs(days(newDate) - days(oldDate))`（单位：天；Date String 解析 YYYY-MM-DD）

## §4 AuditLog 留痕规范（✅ 模型已存在，需写入规范化）

### 4.1 字段级变更 → 单字段单行 AuditLog

每次 Order 变更（哪怕一个字段）→ 写 N 条 AuditLog（N=变字段数）：

```
AuditLog {
  operationType: 'update'
  fieldPath: 'lines[2].quantity'   (支持点/数组路径)
  beforeValue: 1000                (JSON 标量)
  afterValue:  1200
  transactionId: 'OST_xxx' 或 'APR_xxx'   (串联同一审批/同一变更的所有字段 log)
  targetType: 'Order' / 'OrderLine'
  targetId:   orderId / lineId
  actorId:    发起人
  action:     'order_change_request' / 'order_change_approved' / 'order_change_rejected'
}
```

三种 action：
- `order_change_request`（提交变更审批 → before=旧值 after=新值）
- `order_change_approved`（审批通过 → 实际 commit 再写一条，或复用 request + approvedAt 标记）
- `order_change_rejected`（审批驳回 → after=原 before，记录驳回人 + 理由）

## §6 触发矩阵（5 类 × 3 级 × 动作 × 门禁 × 异常分支）

| # | 触发条件 | 动作 | 门禁（Gate） | 异常分支（Fail-Closed） |
|---|---------|------|-------------|----------------------|
| 1 | Order/OrderLine 字段被修改（API 路由命中 update） | ❌ 第一步（缺口）：before 快照（变更前从 DB 查旧值）→ after 新值 → fieldPath 级 diff → 分类矩阵（命中 ①②③④⑤ 哪些？） | ❌ 识别后计算审批级 Lx；若需要审批（不是 no-op 变更）→ 进入审批事务前，**禁止直接 commit 变更**（当前直通就是这里无门禁） | 并发冲突（两人同时改同 Order 不同字段）→ before 快照取 DB 实时值 → 冲突检测：两人读的 before 相同 → 后提交者需重新加载 before 再算 diff（乐观锁 version）|
| 2 | diff 结果 = no-op（after === before 全字段） | 跳过审批，Toast「无变更」| 无 | 浮点数/Decimal 精度误差（100.00 vs 100.0000）→ 归一化比较（Decimal 用 equals 方法，String 日期 trim 后比较） |
| 3 | diff 命中 ①②③ 变更（数量/金额/交期） | ❌ 创建 ApprovalRequest actionType=`order:change` → reviewer=负责团队销售主管 → 挂起 Order → UI diff 面板展示 | ❌ ApprovalRequest.status ≠ approved → 禁止 DB commit 变更（before 不被覆盖）| 审批人离职/账号 disabled → 自动升级到总领导兜底 |
| 4 | diff 命中 ④客户 / ⑤产品 变更 | ❌ ApprovalRequest → reviewer=负责团队销售主管或总领导 | ❌ 同上，fail-closed | — |
| 5 | 命中多类变更合并（如 ①+③+⑤）| ❌ 单条 ApprovalRequest（不重复多条），payload.hitChangeTypes 列全命中类，UI diff 面板分区展示 | ❌ 单条审批通过 → 一次性 commit 所有字段（原子事务） | 部分字段通过部分不通过（无此概念：全 approve or 全 reject，若要改部分字段发起人要撤回后分两次提交） |
| 7 | 审批通过 status=approved | ❌ DB 事务：批量写入 Order/OrderLine 字段更新 → 批量写 AuditLog（operationType=update, fieldPath, before/after, transactionId=ApprovalRequest.id）→ Order.status 从 PendingChange 回 Confirmed/Production（变更前状态） | 事务失败（并发写 Order 导致唯一键/外键错）→ 全回滚 + ApprovalRequest 标记 transaction_failed，需重提 | — |
| 8 | 审批驳回 status=rejected | ❌ ApprovalRequest 写 decisionNote → AuditLog 记录驳回 → Order.status 恢复变更前（PendingChange 标志清除）→ before 快照丢弃（不写 DB） | 无（驳回是合法路径） | 驳回后销售再次提交相同 diff → ApprovalRequest payload 标记 `resubmitCount: N`，第 3 次自动升级审批人（销售主管 → 总领导） |
| 9 | 「撤回变更申请」发起人操作 | ❌ 软删或取消 ApprovalRequest → Order 解锁回到可编辑态（但不 commit 任何变更）| 撤回只能发起人（actorId === ApprovalRequest.requesterId）或审批人驳回 | 审批人已 approved → 不可撤回 |
| 10 | DR-010 已批准订单取消申请 | ❌ 订单进入「取消申请中」→ 系统汇总合同/采购/样品/生产/付款/库存影响 → 生成 ApprovalRequest actionType=`order:cancel` → reviewer=销售主管或总领导 | ❌ 未批准 → 订单保持当前状态，不得取消 | 影响汇总失败（关联数据查询异常）→ 取消申请标记 `impactSummaryFailed: true`，需人工介入 |
| 11 | DR-010 已批准订单暂停申请 | ❌ 订单进入「暂停申请中」→ 记录原因/责任人/预计恢复日期 → 生成 ApprovalRequest actionType=`order:pause` → reviewer=销售主管或总领导 | ❌ 未批准 → 订单保持当前状态，不得暂停 | 预计恢复日期到期未恢复 → 自动提醒发起人和审批人，禁止无限期挂起 |
| 12 | DR-010 取消批准后结案处理 | ❌ 无不可逆承诺 → 直接结案；有采购/生产承诺 → 进入「结案处理中」→ 完成供应商/物料/客户责任/财务损益处置后才可关闭 | ❌ 结案处理中 → 订单不可编辑，仅可查看处置进度 | 处置超时（30 天未完成）→ 自动升级提醒总领导 |

## §11 业务规则关联（22 条交集）

| 规则 | 关联点 |
|------|--------|
| §9.1 MOQ | quantity 变更（①）导致 MOQ 阈值 / 豁免比例变化 → 重新走 MOQ 校验 + 可能叠加 MOQ 豁免审批 |
| §9.2 价格审批-③改价±5% | unitPrice 变更 → 同时命中本规则 ② 金额变更审批 + 价格审批 ③ → **合并单条 ApprovalRequest（取最高级）**，不重复两遍 |
| §9.2 价格审批-④低于成本价 | 产品变更（⑤）改 BOM/material → 成本变化 → 单价仍不变可能触发 ④ 低于新成本价 → 叠加审批 |
| §9.4 信用控制-① 60 天冻结 + ③ 额度占用 | 客户变更（④）切到新客户 → 新客户 CreditLimit.status=Frozen 或额度不足 → 变更被额外 block（即使 L3 批了客户变更，新客户额度也必须 OK） |
| §9.3 质量门禁 | 产品变更（⑤）改面料 → PreCutChecklist 原 4 项可能基于旧面料完成 → 改产品后 Checklist 需重置（4 项全部→false，重新走裁剪前确认） |
| §10 交期与生产 延期通知 | 交期变更（③）+15d 阈值 → 自动触发 delayNotice 邮件/客户通知 + delayNoticeDeadline 重算 |

## §13 DR-013 受控例外 × 订单变更 / 取消 / 交期锁死 门禁验收

> **决策来源**：[DR-013](../10-评审与决策/2026-08-16-设计评审决策记录.md#dr-013-全局业务门禁的受控例外推进)
> **核心铁律**：DR-010 已批准订单变更→取消→暂停→交期锁死的所有门禁，审批被拒后不得静默阻断无出路，必须提供 EXC 入口；但交期锁死（Shipping 后改交期）属硬防篡改，不提供 EXC 直接跳过，必须先走「订单状态回退 Confirmed」审批（另一条审批链）。

| 验收编号 | 场景 | 前置条件 | 执行步骤 | 期望结果（DR-010 权限边界 + DR-013 指定实体） | 失败路径 |
