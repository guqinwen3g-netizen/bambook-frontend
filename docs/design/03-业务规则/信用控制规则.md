## §2 四规则详述 + 账龄桶定义

### 2.1 规则 ②：Customer Tier ABCDE 评定（✅ 已实现）

**CustomerTier 模型**（schema.prisma:538-566）：

| 字段 | 含义 | 值/类型 | 说明 |
|------|------|---------|------|
| level | 分层等级 | Bronze / Silver / Gold / Platinum / VIP | 5 档（Bronze 最低，VIP 战略客）；对应设计中常称 ABCDE（A=VIP / B=Platinum / C=Gold / D=Silver / E=Bronze） |
| criteria | 评定依据 | String? | 如「年采购额 > 100 万 USD + 无逾期」 |
| discountRate | 权益：折扣率 | Decimal(5,2)? | 5.00 = 5%（用于价格审批 ① 折扣判断时减去 Tier 合法折扣） |
| paymentTermsDays | 权益：账期（天）| Int? | Net30 / Net60（发票签发后 X 天内到期） |
| creditPriority | 权益：信用优先级 | High / Normal / Low（默认 Normal）| 额度紧张时，High 优先保留额度；Low 优先触发冻结 |
| evaluatedAt / validUntil | 评定日 / 有效期至 | YYYY-MM-DD | validUntil=null 为长期有效；assignCustomerTier 时旧 tier 自动过期（crmService.ts:705-717） |

**评定流程**（✅ 已实现 crmService.ts:699-773）：
1. 事务内更新旧 tier：validUntil=evaluatedAt（把仍有效/未过期的都过期）
2. 创建新 tier：写入 5 档字段 + 权益
3. AuditLog 留痕
4. 发布 CustomerTierAssigned 事件（含 level/discountRate/creditPriority）供下游通知/额度调整参考

### 2.2 规则 ③：额度占用/释放（✅ 已实现，释放闭环待补）

**CreditLimit 模型**（schema.prisma:421-451）：

| 字段 | 含义 |
|------|------|
| totalLimit | 总信用额度（客户最多可赊账总额） |
| usedAmount | 已用额度（未收款发票累计，由 calculateUsedCredit 实时计算） |
| currency | 币种（默认 CNY） |
| status | Active / Frozen / Expired / Revoked |
| validFrom / validTo | 额度有效期 |
| approvedBy / approvedAt | 审批人 / 时间 |

**占用计算**（✅ 已实现 crmService.ts:810-823 calculateUsedCredit）：
```
已用 = SUM(Invoice.amount)
WHERE Invoice.deletedAt = null
  AND Invoice.status ∉ {Paid, Cancelled, Void}
  AND Invoice.type = 'Receivable'
  AND Invoice.Order.customerRelationId = <relationId>
```

**创建新额度时同步 usedAmount**（✅ 已实现 crmService.ts:275）：setCreditLimit 事务内先 calculateUsedCredit，再写新 CreditLimit.usedAmount。

**释放缺口（⚠️ 未闭环）**：
- PaymentVoucher 核销收款（type=Receipt + Allocation 关联 Invoice）→ **当前无代码**触发 CreditLimit.usedAmount -= 已核销金额
- 临时兜底：setCreditLimit（每次财务手动调额时）会重新 calculateUsedCredit 刷新 usedAmount，但非实时

**超额事件**（✅ 已实现 crmService.ts:316-330）：创建额度若 usedAmount > totalLimit → 发布 `CreditLimitExceeded` 事件（type / totalLimit / usedAmount / exceedAmount）。

#### 2.2.1 额度释放闭环触发链路（§9.4-③）

**触发源**：PaymentVoucher 的核销写入 InvoiceAllocation（M:N 中间表，见财务域模型组 §6）。

**完整链路（正向释放 + 反向占用）**：

```
┌───────────────────────────────────────────────────────────────────────┐
│  ① 正向释放（收款核销 → 额度释放）                                      │
│  InvoiceAllocation.created（afterInsert hook）                         │
│       │                                                                 │
│       ▼ 按 Invoice.customerRelationId 汇总                              │
│  重算该客户「已核销总金额」变化量 Δreleased                               │
│       │                                                                 │
│       ▼ 同步更新 CreditLimit                                            │
│  usedAmount_new = usedAmount_old - Δreleased                            │
│  （底层口径：客户所有未核销 Invoice.amountOutstanding 之和实时重算）      │
│       │                                                                 │
│       ▼ usedAmount 减少即为额度释放                                     │
│  同步 append-only 写入 CreditLimitHistory                               │
└───────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────┐
│  ② 反向占用（订单确认 → 预占额度；订单取消 → 释放预占）                  │
│  Order.status: Draft → Confirmed                                        │
│       │ （如启用预占开关，默认开 credit_enable_order_reserve=true）     │
│       ▼ 按订单金额预占 usedAmount                                       │
│  usedAmount_new = usedAmount_old + Order.totalAmount                    │
│       │                                                                 │
│       ▼ 同步写入 CreditLimitHistory                                     │
│  triggerType = 'order_confirm'                                          │
│                                                                         │
│  Order.status: Confirmed → Cancelled                                    │
│       │  （释放之前预占的额度）                                          │
│       ▼ 按原订单金额释放预占                                             │
│  usedAmount_new = usedAmount_old - Order.totalAmount                    │
│       │                                                                 │
│       ▼ 同步写入 CreditLimitHistory                                     │
│  triggerType = 'order_cancel'                                           │
└───────────────────────────────────────────────────────────────────────┘
```

**审计留痕（CreditLimitHistory append-only）**：
每次 usedAmount 变化（无论增减）都必须追加写入 `CreditLimitHistory` 表，字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String @id | `CLH__${shortId}` |
| creditLimitId | String | 关联 CreditLimit |
| customerRelationId | String | 冗余快照，方便按客户查历史 |
| before | Decimal(18,4) | 变化前 usedAmount |
| after | Decimal(18,4) | 变化后 usedAmount |
| delta | Decimal(18,4) | 变化量（after - before，释放=负数，占用=正数） |
| changedBy | String | 操作人 userId（系统调度=system） |
| triggerType | String | 触发类型枚举：`'payment_allocate'` \| `'order_confirm'` \| `'order_cancel'` \| `'manual_adjust'` |
| triggerId | String? | 触发源单据 ID（Allocation ID / Order ID / 手工调整备注 ID） |
| remark | String? | 中文备注（例：「PaymentVoucher PAY-20260815-003 核销 INV-20260801-007 释放 ¥50,000」） |
| createdAt | BigInt | epoch ms |

> **一致性保证**：CreditLimit.usedAmount 的所有写操作必须在同一事务内同步 append CreditLimitHistory；不允许直接改 usedAmount 不写历史。`calculateUsedCredit()` 作为 reconciliation 兜底，每晚调度重算对比 usedAmount 实际值，偏差超过阈值（>¥1）自动告警并生成 `triggerType='manual_adjust'` 的修正记录。

### 2.3 账龄桶定义（看板展示✅，未接入门禁）

账龄 = today - Invoice.dueDate（若 dueDate 缺省则 = today - (Invoice.invoiceDate + Tier.paymentTermsDays)）

| 桶名 | 天数范围 | 风险颜色 | 动作建议 |
|------|---------|---------|---------|
| Net 0-30 | (0, 30] 天 | 绿 Normal | 正常待收 |
| Net 31-60 | (30, 60] 天 | 黄 Warning | 销售催收 + 跟进记录 |
| Net 61-90 | (60, 90] 天 | 橙 High | 财务介入 + 规则①冻结新单触发 |
| Net 91-120 | (90, 120] 天 | 红 Critical | 停止所有业务 + 律师函准备 |
| Net 120+ | >120 天 | 黑 Extreme | 规则④坏账识别触发 + 计提坏账准备 |

### 2.4 规则 ①：60 天逾期冻结新单（❌ 未实现）

**触发定义**：某 Relation 存在至少一张 Receivable Invoice，其账龄 ∈ Net61+ 桶 → 自动：
1. CreditLimit.status = 'Frozen'（原 Active → Frozen）
2. 写 AuditLog（action=`credit:60d-overdue-freeze`）
3. 发布 `CreditFrozenForOverdue` 事件 → 通知财务/销售/对应客户业务员
4. **门禁**：Order 创建 / Quotation 创建 / convertToOrder → 读取该 relation 下 CreditLimit.status=Frozen → block 创建 + 弹窗「该客户存在 ≥60 天逾期，请财务解冻后再下单」

**解冻路径**（也未实现）：财务手工或自动调度：当 Net61+ 桶全部结清（或客户付部分款 + 特批）→ CreditLimit.status 回到 Active + AuditLog 解冻记录。

### 2.5 规则 ④：坏账识别（❌ 未实现）

**触发条件（AND）**：
- 存在 Receivable Invoice 账龄 > 180 天
- 近 90 天无 FollowUpRecord.type ∈ {Visit, Call, Meeting}（即催收无进展）
- 或收到客户破产/清算/失联书面通知（手工打标 Relation.tags += `坏账嫌疑`）

**动作**：
1. CreditLimit.status = 'Revoked'（永久吊销，非冻结）
2. Relation.stage = 'Churned'（枚举已存在 schema.prisma:345）
3. CustomerTier 标记 validUntil=today（权益同步失效）
4. 财务计提坏账准备（财务模块凭证联动）
5. 发布 `BadDebtIdentified` 事件 → 管理层通知

| # | 触发条件 | 动作 | 门禁（Gate） | 异常分支（Fail-Closed） |
|---|---------|------|-------------|----------------------|
| 1 | assignCustomerTier（新 Tier 评定） | ✅ 旧 tier 过期 → 新 tier 创建 + 审计 + CustomerTierAssigned 事件 | 无（评定本身是管理行为，不 block） | evaluatedAt 格式非 YYYY-MM-DD → 默认拒绝；缺权限则 403（当前未实现角色校验，未来补 Role=财务/管理层）|
| 2 | setCreditLimit（授予/调整额度） | ✅ 旧 Active→Expired → calculateUsedCredit ✅ → 新额度创建 + 超限发布 CreditLimitExceeded | 建议补（未实现）：新 totalLimit > 上限（按 Tier：Bronze≤50w / Silver≤100w / Gold≤300w / Platinum≤800w / VIP 无上限）→ 需老板审批 | calculateUsedCredit 聚合无 Invoice（该客户无应收记录）→ usedAmount=0 合法，不报错 |
| 3 | Invoice 创建（Receivable 型，关联订单客户 relation） | ⚠️ 额度占用当前**无实时**更新；仅下次 setCreditLimit 或 calculateUsedCredit 手动触发时刷新 | ❌ 待接入：创建 Invoice 后，if (newUsedAmount > totalLimit) → CreditLimitExceeded 重复发布 + 建议自动转 Frozen（高额度超限） | Invoice.orderId.customerRelationId 为 null → 无法归属 relation，跳过额度累计 + Toast 标记「未绑定客户」 |
| 4 | PaymentVoucher + Allocation 核销收款（⚠️ 释放缺口） | ❌ 待实现：Allocation 写入时，Invoice.amount - 已分配 → CreditLimit.usedAmount -= 本次核销金额 | 无（释放是正向动作，不 block） | 核销超额（核销 > Invoice 未付）→ 不允许，先在 Allocation 层拒绝 |
| 5 | 调度每日 03:00 扫账龄（❌ 待实现 60 天冻结） | ❌ 扫所有 Active CreditLimit：查 Relation 关联的 Net61+ Invoice 非空 → 改 status=Frozen + AuditLog + CreditFrozenForOverdue | 每日调度 idempotent：已 Frozen 的客户不再重复发布事件 | 调度失败（DB 连接超时）→ 次日补偿 + 告警运维；不影响手工订单创建（❌ 但订单创建门禁需独立再查一次账龄，防调度遗漏） |
| 6 | **Order 创建**（❌ 60 天门禁缺口） | ❌ 预查：该 customerRelationId 是否存在 Net61+ 未结清 Invoice 或 CreditLimit.status=Frozen → 两者任一命中 → block 创建 | ❌ 命中 Net61+ / Frozen → Order create 路由抛错「客户存在 ≥60 天逾期，需财务解冻」；customerRelationId=null 时建议警告但不 block（小单/现金单场景） | customerRelationId 对应 Relation 被软删 → 按「未知客户」保守 block，除非订单类型=Cash（无账期） |

| 8 | 调度坏账识别（❌ 未实现） | ❌ 每日扫 Net180+ + 90 天无跟进 → CreditLimit=Revoked / Relation.stage=Churned / Tier 过期 + 事件 | 建议补角色：仅财务/管理层可手工打坏账标签，系统自动识别需加审批人 override 开关（防止误判） | 误判（客户刚付款未核销）→ 支持「恢复」操作：Churned→Customer + Revoked→Active（保留历史 audit 全部记录）|

## §13 DR-013 受控例外 × 信用门禁（60 天逾期冻结 / 额度超额）验收

> **决策来源**：[DR-013](../10-评审与决策/2026-08-16-设计评审决策记录.md#dr-013-全局业务门禁的受控例外推进)
> **Fail-Closed 铁律**：EXC 批准 ≠ 改 CreditLimit.status 或改 Invoice.dueDate（伪造"没逾期"）；只能在创建**指定订单**时临时放行冻结门禁；信用数据、账龄桶、额度数据**一字不改**。EXC 必须由财务容器 + 总领导二级审批（不是业务员主管，因为信用属财务合规域）。

| 验收编号 | 场景 | 前置条件 | 执行步骤 | 期望结果（财务审批权 + 信用数据零修改） | 失败路径 |
|---------|------|---------|---------|---------------------------------------|---------|
