## §2 三道门禁详述

### 2.1 门禁 ①：裁剪前 PreCutChecklist 4 项（seq=6，✅ 已落地）

**PreCutChecklist 模型字段**（schema.prisma:2457-2472）：

| 字段 | 含义 | 类型 | 默认 | 谁来勾选 |
|------|------|------|------|---------|
| gradingConfirmed | 推码确认（尺码跳码表正确，含放量/缩率） | Boolean | false | 跟单/技术 |
| consumptionConfirmed | 耗料确认（单耗/排版图/面料利用率核算正确，避免超领） | Boolean | false | 跟单/物控 |
| patternConfirmed | 样板确认（最后一轮 fit/pp 样板客户签字确认，无遗留修改点） | Boolean | false | 业务/开发 |
| preProductionMeeting | 产前会议（与工厂/面料/辅料开产前会，交期/质量/特殊工艺达成一致） | Boolean | false | 生产部主持，跟单+QC 列席 |
| meetingNote | 产前会议纪要 | String? | null | — |
| confirmedBy / confirmedAt | 确认人 / 确认时间 | — | — | — |

**推进逻辑**：`stageService.ts:270-283` advanceStage 进入 pre_cut_checked 时：
1. 查 PreCutChecklist（orderId 唯一），不存在直接报错 PRECUT_CHECKLIST_INCOMPLETE
2. 4 布尔字段 AND，缺哪个 → 中文拼接缺项名（推码确认、耗料确认、样板确认、产前会议）
3. 全部通过 → stage.status=done

### 2.2 门禁 ②：厂前样（PP Sample）双签（seq=7，⚠️ 部分落地）

**双签定义**：产前样 pp_sample_approved 阶段完成必须两方签字：
- `ProductionStage.signedByProduction`（schema.prisma:2444）：工厂/我方生产部签字（确认工艺可执行、设备/人员排产到位）
- `ProductionStage.signedByBusiness`（schema.prisma:2445）：业务部签字（确认客户已批 pp、颜色/手感/尺寸与客户确认件一致）

**后端校验**（stageService.ts:285-292 ✅ 已实现）：advanceStage 时两者同时非 null 才通过，缺哪个中文提示。

**签字 API**（stageService.ts:582-620 ✅ 已实现 signStage 函数）：
```
signStage({ orderId, stageKey: 'pp_sample_approved', signType: 'production' | 'business', signerId })
```

**前端缺口（⚠️ 未实现）**：
- Production pipeline 泳道 pp_sample_approved 阶段卡片无签字按钮（应区分生产/业务两个按钮，根据当前用户角色显示有权限的按钮）
- 签字状态 UI：灰色「待签字」→ 蓝色「生产部已签」→ 绿色「双签完成」三态
- 签字人信息 tooltip：悬停显示签字人 + 时间

#### 2.2.1 双签按钮组 UI 规格说明（§9.3-② 产前样）

**双签按钮组**：在 pp_sample_approved 阶段卡片右下角渲染两个独立签字按钮（水平排列，gap-2）：

| 按钮 | 未签字态（默认） | 已签字态 | 权限控制 |
|------|------------------|---------|---------|
| **QC签字**（原生产部签字） | 灰色 `bds-btn-secondary-disabled` 文案「QC签字 待签字」，tooltip=「点击以 QC 身份签字确认产前样工艺可执行」 | 绿色 `bds-btn-success-solid` 文案「QC已签：张三 · 2026-08-15 14:30」，圆点 indicator +，悬停显示签字详情 | 仅 QC 角色可见可点（`qc:write` scope）；其他人按钮 disabled 灰色不响应点击 |
| **业务确认签字**（原业务部签字） | 灰色 `bds-btn-secondary-disabled` 文案「业务确认 待签字」，tooltip=「点击以业务员身份签字确认客户已批 PP 样」 | 绿色 `bds-btn-success-solid` 文案「业务已签：李四 · 2026-08-15 15:12」，圆点 indicator +，悬停显示签字详情 | 仅 `Order.ownerId`（业务员本人）或其部门 `Department.managerId`（销售主管）可见可点；其他人按钮 disabled |

**两个按钮都点击变绿（均已签字）后**，门禁解锁条件通过，`advanceStage(pp_sample_approved)` 不再抛 `PP_SAMPLE_NOT_SIGNED` 错误。

**签字逻辑流程**：
```
用户点击对应签字按钮
  │
  ▼
弹窗（二选一，UI Lab 统一签名组件）：
  · 方案 A（推荐，简单快速）：确认对话框
    标题「确认以「张三（QC角色）」身份签字？」
    文案：「此操作将永久记录签字人与时间戳，不可撤销」
    按钮：[取消] [确认签字]
  · 方案 B（合规留痕）：canvas 签名板
    提供手写签名画布 + 清除 + 保存按钮，签名 base64 存入 signatures.signatureImage
  │
  ▼ 确认签字后
  调用 signStage({ orderId, stageKey: 'pp_sample_approved', signType: 'qc' | 'business', signerId })
  后端写入 InspectionReport.signatures JSON（兼容 ProductionStage 字段）：
  {
    qcSignedAt: "2026-08-15T14:30:00.000Z",
    qcSignerId: "user_abc123",
    qcSignerName: "张三",        // 快照，防改名
    qcSignatureImage: "<base64>", // 方案 B 时存在
    businessSignedAt: null,
    businessSignerId: null,
    businessSignerName: null,
    businessSignatureImage: null
  }
  （同时向下兼容 ProductionStage.signedByProduction/signedAtProduction 等字段写入）
```

**后端校验**：
`StageService.checkPreCutReady()`（对应 pp_sample_approved 门禁）同时校验 signatures JSON 中 `qcSignedAt` 与 `businessSignedAt` **两个字段都非空**才算通过；任一为空则抛 `PP_SAMPLE_NOT_SIGNED`，中文提示缺哪个（例：「产前样需 QC 签字 + 业务确认双签，当前缺 QC 签字」）。

**UI 视觉纪律**：
- 未签字：按钮 `bds-btn-secondary` disabled，背景 `--surface-muted`，文案 `--text-tertiary`，左侧带空心圆点 `○`
- 已签字：按钮 `bds-btn-success-solid`，背景 `--badge-approved-bg`，文案 `--badge-approved-text`，左侧带实心圆点 `●`（6px）
- 签字人姓名与日期：已签字态按钮内紧凑显示，12px 字，`H-28px` 按钮高度；点击已签字按钮不弹窗，只展开 tooltip 详情
- 双签完成后：pp_sample_approved 阶段卡片顶部边框变绿（`--border-success`，3px 顶边），badge 显示绿色「双签完成」

### 2.3 门禁 ③：终期 AQL 0 致命疵点（seq=10，✅ 已落地）

**终期验货 InspectionReport.final 5 道门禁**（stageService.ts:294-319，顺序判断任一失败即 INSPECTION_NOT_QUALIFIED / BUSINESS_APPROVAL_REQUIRED）：

| 道次 | 判断条件 | 阈值 / 说明 | 错误消息示例 |
|------|---------|------------|------------|
| 1 | 终期报告必须存在 | orderId + inspectionType='final' 查不到 → 报错 | 终期验货报告（final）未建立 |
| 2 | result ≠ 'fail' | result ∈ {pass, conditional} 可放行；fail → 需整改复验 | 终期验货结论为不合格（fail），需整改复验 |
| 3 | criticalDefects = 0 | AQL 0 零容忍（致命疵点：断针/毒性/窒息风险/客户品牌标准严重违规）；>0 即整批拒收 | 存在 N 个致命疵点（AQL 0 零容忍） |
| 4a | passRate ≥ 90%（MIN_PASS_RATE = 0.90） | passRate = passedUnits / totalUnits | 合格率 ××% 低于阈值 90% |
| 4b | defectRate ≤ 3%（MAX_DEFECT_RATE = 0.03） | defectRate = (totalUnits - passedUnits) / totalUnits | 不合格率 ××% 超过上限 3% |
| 5 | approvedByBusiness = true | 业务部最终批准发货（防止 QC pass 但客户/业务侧仍有异议） | 需业务部批准发货 |

**终期验货 fail 广播**（stageService.ts:549-567 ✅ 已实现）：
结论从非 fail 迁移到 fail 瞬间（previous.result≠'fail' && result==='fail'）→ notificationService.broadcastNotification：type=`inspection_fail`，level=`critical`，通知对象 = QC + 业务员 + 管理层，链接 `/production?orderId=xxx`。

**自动供应商评分**（stageService.ts:524-545 ✅ 已实现 H1c）：
验货报告保存成功 → 通过 Order.millRelationId → 工厂档案 FactoryProfile → recordAutoEvaluation，评分算法 `inspectionScoreForResult(result, criticalDefects)`。

**大货报告 API 写入路径**（✅ 2026-08-19 收口，qcService.ts `completeAssignment`）：
QC 任务完成接口 `POST /api/v1/qc/assignments/:id/complete` 携带 `report` 数据（result ∈ {pass, fail}）→ 自动创建大货 InspectionReport（final 锚定 `INR__{orderId}` 出运门禁消费锚点 / midline 锚定 `INR__{orderId}__mid`），并回写 QCAssignment.reportId。此前大货报告只能直插 DB，无 API 写入路径。schema 契约：totalUnits/passedUnits/majorDefects/minorDefects 必填 Int 缺省 0（非 null）。详见 [出运与报关模型组 §15D](../02-数据模型/出运与报关模型组.md)。

## §6 触发矩阵（3 门禁 × 动作 × 门禁 × 异常分支）

| # | 触发条件 | 动作 | 门禁（Gate） | 异常分支（Fail-Closed） |
|---|---------|------|-------------|----------------------|
| 1 | advanceStage(pre_cut_checked) 被调用 | ✅ 查 PreCutChecklist → 4 项全 true 校验 ✅ 阶段 status=done + 审计 ✅ 发布 ProductionStageAdvanced 事件 | ✅ 缺任一项 → PRECUT_CHECKLIST_INCOMPLETE，阶段保持 pending，UI Toast 缺项清单 | Checklist 行不存在（历史订单未补录）→ 报错提示「请先完成裁剪前检查」而非静默失败 |
| 2 | savePreCutChecklist 勾选 4 项 | ✅ upsert PCL__orderId → 写 confirmedBy/confirmedAt + 审计 | 无（只记录，推进仍需 advanceStage 显式调用） | 并发勾选（两人同时勾不同项）→ upsert 原子按字段合并，不会互相覆盖 |
| 3 | advanceStage(pp_sample_approved) 被调用 | ⚠️ 后端：signedByProduction && signedByBusiness 校验 ✅ | ⚠️ 后端校验缺签 → PP_SAMPLE_NOT_SIGNED 已实现；前端无签字入口导致 100% 卡在此阶段（当前实际落地缺口） | signStage 签字人无对应角色权限 → 403；未实现，当前仅后端缺签校验 |
| 4 | signStage('production' | 'business') 签字请求 | ✅ 后端：写 signedByProduction/signedAtProduction 或 business 对应字段 | 无（签名接口无额外门槛，建议补角色权限） | 重复签字 → 覆盖旧签字 + 审计 log 应记录「原签字人 → 新签字人」变更 |
| 5 | saveInspectionReport('final') 保存终期报告 | ✅ upsert 报告 + ✅ criticalDefects/major/minor + ✅ result 迁移 fail 瞬间广播 critical + ✅ 供应商自动评分 | 无（保存即写入，不自动推进 qc_shipped 阶段；需用户显式 advanceStage 触发门禁） | orderId 不存在/软删 → ORDER_NOT_FOUND；非法 result（非 pass/conditional/fail）→ 抛错 |
| 6 | advanceStage(qc_shipped) 被调用 | ✅ 5 道门（报告存在/result≠fail/critical=0/pass≥90%+defect≤3%/approvedByBusiness）全通过才放行 ✅ 通过后发布 ProductionCompleted 事件（触发后续运单/单据联动） | ✅ 任一门失败 → INSPECTION_NOT_QUALIFIED / BUSINESS_APPROVAL_REQUIRED；**禁止 shipment 创建** | 报告存在但字段不全（totalUnits=0 导致 passRate=0）→ 报合格率 0%<90%，提示「请先补全验货数量」 |
| 7 | InspectionReport.result 从 pass → fail（整改后复验又 fail = 新事件） | ✅ stageService.ts:549 previous 判断幂等：只有迁移瞬间才广播（重复保存相同 fail 不再通知） | 无 | 两次 fail 间隔短（客户与我方 QC 结论不一致）→ 需两条独立 critical 通知，并在 metadata 带时间戳区分 |
| 8 | approvedByBusiness=true（业务批货） | ✅ saveInspectionReport 参数 approvedByBusiness → 写 approvedAt 时间戳 + businessApprover | 建议补：无对应业务角色（非业务部/管理层/老板）→ 403；当前未实现，任何人可设 true | 业务批准后，qc_shipped 阶段完成前，有人手工改 InspectionReport 字段 → 批准失效需重新批（建议 approvedAt 时间戳早于 updatedAt → 自动 reset approvedByBusiness） |
