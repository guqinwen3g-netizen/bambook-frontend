## §2 事件总线架构

> **代码真源**：`server/src/events/businessEventBus.ts`

### 2.1 架构组成

```
业务事务提交
    │
    ▼
publishBusinessEvent(params)
    │
    ├─ 1. 持久化到 AgentJob 表（jobType=`bev:${type}`, status='queued'）
    │     └─ best-effort，永不抛错（P2002 唯一约束 = 幂等重发，静默接受）
    │
    └─ 2. in-process emit（EventEmitter）
          ├─ 逐个订阅者 try/catch（失败隔离，单个失败不影响其他）
          ├─ 异步订阅者 catch rejected promise（fire-and-forget）
          └─ 同时 emit 到 '*' 通配订阅（监控/调试/审计）
```

### 2.2 核心不变量

| 不变量 | 实现方式 |
|--------|---------|
| publish 必须在事务提交后调用 | 文档契约 + 调用方责任（绝不在事务内调用，避免脏事件） |
| publish 永不抛错 | 持久化失败仅日志；订阅者失败仅日志 |
| 订阅者失败隔离 | 手动遍历 listeners，每个 try/catch；异步 catch rejected promise |
| 事件 payload JSON 可序列化 | 持久化到 AgentJob.payload（Json 字段） |
| 幂等去重（LinkageHandler） | in-process Set（processedKeys）+ 业务层唯一约束 |
| 失败可重试 | execute 返回 not-ok 或抛错 → 从 processedKeys 移除 → 调度器崩溃恢复重放 |

### 2.3 关键 API

| API | 说明 |
|-----|------|
| `businessEventBus.publish(event)` | 发布事件（持久化 + in-process emit） |
| `businessEventBus.subscribe(eventType, handler)` | 订阅特定事件（或 '*' 通配），返回取消订阅函数 |
| `businessEventBus.registerLinkage(handler)` | 注册联动处理器（自动幂等去重 + 失败移除 key） |
| `publishBusinessEvent(params)` | 便捷发布函数（自动生成 eventId + occurredAt） |
| `generateEventId(type)` | 生成稳定唯一事件 ID：`bev_<type>_<timestamp>_<random>` |

## §5 事件发布流程

```
1. 业务事务执行（prisma.$transaction）
   ├─ 业务写操作（创建/更新/状态迁移）
   └─ 审计日志写入
        │
        ▼ 事务提交
        │
2. publishBusinessEvent(params)        ← 必须在事务提交后调用
   ├─ generateEventId(type)            → bev_<type>_<ts>_<random>
   ├─ 构造 BusinessEvent 对象
   └─ businessEventBus.publish(event)
        │
        ▼
3. 持久化到 AgentJob 表
   ├─ jobType = `bev:${event.type}`
   ├─ status = 'queued'
   ├─ payload = event（JSON）
   └─ P2002 唯一约束 = 幂等重发，静默接受
        │
        ▼
4. in-process emit（EventEmitter）
   ├─ emit(event.type) → 逐个订阅者 try/catch
   ├─ emit('*') → 通配订阅（监控/调试）
   ├─ LinkageHandler 执行（registerLinkage 注册的）
   │   ├─ idempotencyKey 去重（processedKeys Set）
   │   ├─ execute(prisma, event) → 调用下游 service
   │   └─ 失败 → 移除 key → 允许调度器重试
   └─ NotificationService 执行（eventBindings 订阅的）
       └─ notifyFromEvent(event) → 渲染 + 投递通知
```

**调用时序**（`server/src/index.ts` 启动时）：
1. `initializeNotificationBindings(prisma)` — 注入 prisma + 通知订阅
2. `registerAllLinkages()` — 注册 9 条联动执行器
3. `registerWorkflowEventTriggers(prisma)` — 注册工作流事件触发器
4. `startScheduler(prisma)` — 启动调度器（注册 23 个定时任务）

## §8 调度器重试机制

> **代码真源**：`server/src/scheduler/tasks/retryLinkages.ts`

### 8.1 崩溃恢复任务（createCrashRecoveryTask）

| 维度 | 内容 |
|------|------|
| 任务 ID | crash_recovery |
| 执行时机 | 启动时执行一次（crashRecoveryDone 标记） |
| 扫描范围 | AgentJob where status='queued' AND jobType startsWith 'bev:'，批量 50 条 |
| 动作 | 逐条 `businessEventBus.publish(event.payload)` 重放 → 标记 status='completed' |
| 失败处理 | 标记 status='failed' + error 字段，避免反复重试坏数据 |
| 幂等保证 | publish 内部 P2002 去重 + LinkageHandler idempotencyKey 去重 + 业务层唯一约束 |

### 8.2 清理任务（createCleanupTask）

| 维度 | 内容 |
|------|------|
| 任务 ID | cleanup_queued_jobs |
| 执行时机 | 每小时 |
| 扫描范围 | AgentJob where status='queued' AND jobType startsWith 'bev:' AND scheduledAt < (now - 5min) |
| 动作 | 批量标记 status='completed'（正常流程中已由 in-process handler 处理完毕但未更新状态的记录） |

### 8.3 重试限制

| 维度 | 内容 |
|------|------|
| 最大重试次数 | 无显式上限（崩溃恢复仅启动时执行一次；in-process 失败后 key 移除，下次相同事件重新触发） |
| 失败隔离 | LinkageHandler execute 返回 not-ok 或抛错 → processedKeys.delete(key) → 下次同事件可重试 |
| 坏数据保护 | 崩溃恢复时 payload 无效（无 type 字段）→ 直接标记 completed 跳过 |

> **注**：任务描述中的 `retryLinkages.ts` 实际包含 `createCrashRecoveryTask` + `createCleanupTask` 两个任务。无独立的"最大重试次数"配置——崩溃恢复是启动时一次性重放，非持续重试。

|------|------|
| 触发事件 | OrderConfirmed |
| 幂等 key | `auto:L6:${orderId}` |
| 执行动作 | 查找匹配模板 BOM（Confirmed/Archived, description 含产品名）→ 复制物料行+成本估算；无模板则创建占位 BOM |
| 业务层幂等 | 查询该订单是否已有 BOM，有则跳过 |
| 输出 | Draft BOM（需人工补充/确认） |

### 11.6 L7 BOMConfirmed → 创建采购需求草稿

| 维度 | 内容 |
|------|------|
| 触发事件 | BOMConfirmed |
| 幂等 key | `auto:L7:${bomId}` |
| 执行动作 | BOM 物料行 → PurchaseLine（materialCode/description/quantity/unit/unitPrice=unitCost），创建 Draft 采购单 |
| 业务层幂等 | 查询该 bomId 是否已有采购单，有则跳过 |
| 输出 | Draft 采购单（供应商为空，需经办业务员指定） |

### 11.7 L8 MaterialReceived → 自动入库

| 维度 | 内容 |
|------|------|
| 触发事件 | MaterialReceived |
| 幂等 key | `auto:L8:${receiptId}` |
| 执行动作 | 查询采购单行 → 为有 materialCode+receivedQty 的行创建/更新库存项 + 入库流水（Inbound） |
| 默认仓库 | 优先 Main 类型 active 仓库 → 任意 active 仓库 → 无则跳过告警 |
| 业务层幂等 | 查询 StockMovement where referenceId=receiptId，有则跳过 |
| 输出 | 库存项 + 入库流水（referenceType=PurchaseOrder, referenceId=receiptId） |

### 11.8 L9 QuotationAccepted → 报价转订单草稿

| 维度 | 内容 |
|------|------|
| 触发事件 | QuotationAccepted |
| 幂等 key | `auto:L9:${quotationId}` |
| 执行动作 | 复用 `quotationService.convertToOrder()`（统一建单逻辑） |
| 业务层幂等 | convertToOrder 校验 convertedOrderId，已转化抛错被捕获 → 视为幂等成功 |
| 输出 | Draft 订单（需人工审核后确认） |

### 11.9 L10 CustomsCleared → 创建退税申报草稿

| 维度 | 内容 |
|------|------|
| 触发事件 | CustomsCleared |
| 幂等 key | `auto:L10:${declarationId}` |
| 执行动作 | 复用 `customsService.createTaxRefundFromDeclaration()`（统一核算逻辑） |
| 核算数据链 | 报关单行明细 + HS 退税率 + 发票/订单汇率快照 + 运单实际离港日 |
| 业务层幂等 | createTaxRefundFromDeclaration 校验 declarationId 唯一，重复触发抛错被捕获 → 幂等成功 |
| 输出 | Draft 退税申报（需人工提交审核） |

## §X ApprovalPolicy 规则驱动升级方案（DR-007 落地 · 决策点 3-A + 6）

> 本章节定义 approvalPolicy 从「legacy always manual（前端手工选审批人）」升级为「服务端规则驱动 resolveReviewerByDepartment」的完整迁移路径。

### X.1 现状：ApprovalRequest.reviewerId 仍可由前端传入（legacy always manual）

| 维度 | 现状描述 |
|------|---------|
| reviewerId 来源 | 前端表单手工选择审批人 → 传入 `POST /api/v1/approvals` body.reviewerId |
| approvalPolicy 全局值 | `manual always`（所有审批类型均无规则解析，完全依赖前端传入） |
| 服务端兜底 | **无**：前端不传 reviewerId → DB 写入 null（schema.prisma:1814 字段为 nullable） |
| 风险 | 前端选错审批人、绕过审批层级、无组织归属校验、跨团队越权审批 |

### X.2 目标：全部审批单在服务端通过 resolveReviewerByDepartment(userId) 规则函数解析 reviewerId

| 项 | 规则函数定义 |
|----|-------------|
| 函数名 | `resolveReviewerByDepartment(requesterId: string): string` |
| 默认解析逻辑 | `UserAccount.departmentId → Department.managerId`（= 付款申请人所属部门的主管） |
| fallback 兜底条件 | ① requesterId 无 `departmentId`（无部门） ② `Department.managerId` 为 null（部门无主管） ③ requesterId 所属部门为「财务」→ 返回系统管理员 ADMIN（总领导兜底） |
| 单次审批约束 | 返回值为**单个 userId**，一次性只需一位有效审批人（不生成多人会签/或签） |
| 覆盖范围 | **全部 ApprovalRequest 类型**：付款凭证（pay_lt5/pay_gt5 兼容名）/ MOQ 豁免 / 价格审批（①-⑤）/ 订单变更 5 类 / 信用解冻 / 取消暂停 等 |

### X.3 迁移步骤（四步走 · 平滑兼容）

| 步骤 | 动作 | 实现位置 | 风险控制 |
|------|------|---------|---------|
| ① | 在 `approvalService.createRequest` 中增加 **reviewerId 非空服务端兜底**：前端传了 reviewerId 就**覆盖**（兼容 legacy）；前端没传或传 null → 用 `resolveReviewerByDepartment(requesterId)` 计算后写入 | `server/src/approvals/approvalService.ts` createRequest 函数 | 兜底不破坏现有前端手工选审批人的流程；兼容期可并行 |
| ② | **逐步移除前端 reviewerId 选择框**：所有审批发起页面（付款审批发起/MOQ 豁免发起/价格审批发起/订单变更审批发起）移除审批人下拉；UI 改为只读展示「审批人：{解析结果}」，由前端调用 `GET /api/v1/approvals/preview-reviewer?requesterId=xx` 查询解析结果 | `components/*/ApprovalRequestModal.tsx` 各审批发起弹窗 | ① 先在后端到位后再移除前端选择框，避免空值；② 移除后保留 GET preview 接口供 UI 展示 |
| ③ | **ApprovalRequest.reviewerId 列级 NOT NULL 约束加 migration**：在确认 ①② 全量上线、服务端 reviewerId 永不落空之后，加 prisma migration：`ALTER TABLE "ApprovalRequest" ALTER COLUMN "reviewerId" SET NOT NULL;` | `server/prisma/migrations/` 新增 migration + schema.prisma 字段标记为 non-null | 加约束前先跑 dry-run SQL 检查是否有历史 null 行；有则批量回填（null 的历史单按 requesterId 重算 reviewerId 后补上）|
| ④ | **6 个 scope 名标记为兼容保留（文档注明）**：`pay_lt5 / pay_gt5 / lt10_ / gt5_` 等 scope 前缀与阈值/比例相关的命名，全部标记为「兼容保留名」——实质审批路由逻辑与金额/比例彻底无关，全部走 DR-007 统一 resolveReviewerByDepartment | 本文件 + 各规则 md 交叉注明 | 不删旧 scope 常量（避免后端权限 ACL/前端 scope 绑定代码报错），仅文档声明其语义变化 |
