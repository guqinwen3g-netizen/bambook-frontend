## §3 P0 阻断项治理方案（4 项）

### 3.1 P0-① — 调试条治理（生产环境残留"调试用全局错误监听器"）

#### 3.1.1 问题定位

| 项 | 值 |
|---|---|
| **症状** | 任何 uncaught error / unhandled rejection 会在用户屏幕上弹出覆盖 50vh 的红底白字 monospace 调试条（含完整堆栈） |
| **根因** | `App.tsx:L5-L20` 顶部 `INJECTED GLOBAL ERROR BOUNDARY FOR DEBUGGING` 调试代码未做生产环境屏蔽 |
| **影响** | ① 调试代码泄露生产用户屏幕；② 任何运行时异常用户都看到满是堆栈的红色报错 UI；③ 破坏品牌一致性 |
| **问题类型** | 本地实现错误（调试代码未做环境守卫） |

#### 3.1.2 修复方案

**方案 A（推荐）：DevBoundary 替代**

```typescript
// App.tsx
if (import.meta.env.DEV) {
  // 仅开发环境保留调试条
  window.addEventListener('error', debugErrorHandler);
  window.addEventListener('unhandledrejection', debugRejectionHandler);
}
// 生产环境：替换为正式 ErrorBoundary 组件，渲染友好错误恢复界面
```

**方案 B：完全移除调试条 + 接入 React ErrorBoundary**

- 删除 `INJECTED GLOBAL ERROR BOUNDARY FOR DEBUGGING` 代码块
- 接入 `react-error-boundary` 库
- 生产错误 UI：友好提示 + "刷新页面" / "返回首页" 按钮
- 开发错误 UI：保留堆栈 + sourcemap 解析

#### 3.1.3 验收门禁

- 生产 build 中 `import.meta.env.DEV === false` 时调试条不渲染
- 故意抛出 uncaught error → 生产环境显示友好错误恢复界面（非堆栈）
- 故意抛出 uncaught error → 开发环境保留调试条（含堆栈）
- 前端 tsc 零错误 + 全量测试通过 + check:tokens 通过

#### 3.1.4 影响范围

- `App.tsx`（移除调试条 + 接入 ErrorBoundary）
- 新增 `components/ErrorRecoveryFallback.tsx`（生产错误恢复 UI）

### 3.4 P0-④ — 请求超时治理（requestJson 无 AbortController）

#### 3.4.1 问题定位

| 项 | 值 |
|---|---|
| **症状** | 统一请求入口 `requestJson`（`apiService.ts:L304-L315`）用原生 fetch 无 AbortController 超时；仅连接测试 `testConnection` 有 3s 超时（`apiService.ts:L528`） |
| **根因** | apiService 设计时未统一加超时；各调用方零散处理 |
| **影响** | 外贸团队常驻海外、弱网 / 掉线场景，请求可能无限挂起卡死界面 |
| **问题类型** | 本地实现错误（apiService 单点未加超时） |

#### 3.4.2 修复方案

**① requestJson 统一加 AbortController 超时**

```typescript
// apiService.ts L304-L315 重构
async function requestJson<T>(url: string, options: RequestOptions = {}): Promise<T> {
  const {
    timeoutMs = 30_000,  // 默认 30s
    signal: externalSignal,
    ...fetchOptions
  } = options;

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs);

  // 合并外部 signal（若调用方主动取消）
  if (externalSignal) {
    externalSignal.addEventListener('abort', () => controller.abort());
  }

  try {
    const response = await fetch(url, {
      ...fetchOptions,
      signal: controller.signal,
    });
    // ... 既有逻辑
  } catch (err) {
    if (err.name === 'AbortError') {
      throw new NetworkError('请求超时', { timeoutMs, url });
    }
    throw new NetworkError('网络错误', { cause: err, url });
  } finally {
    clearTimeout(timeoutId);
  }
}
```

**② 超时分级配置**

| 操作类型 | 默认超时 | 配置项 |
|----------|----------|--------|
| 读（GET） | 15s | `BAMBOOK_READ_TIMEOUT_MS` |
| 写（POST/PATCH/PUT/DELETE） | 30s | `BAMBOOK_WRITE_TIMEOUT_MS` |
| 文件上传 | 120s | `BAMBOOK_UPLOAD_TIMEOUT_MS` |
| 报表运行 | 90s | `BAMBOOK_REPORT_TIMEOUT_MS` |
| Agent 循环 | 90s（已有 `totalBudgetMs`） | 复用既有 |

**③ 网络错误语义化**

- `NetworkError` 类区分：超时 / DNS 失败 / 连接拒绝 / SSL 错误 / HTTP 5xx / HTTP 4xx
- 错误消息本地化（zh-CN）
- 错误可被调用方捕获并显示给用户（配合 ToastProvider）

#### 3.4.3 验收门禁

- requestJson 全部调用方默认 30s 超时
- 超时后抛出 `NetworkError`，调用方可捕获并显示 toast
- 测试：模拟超时场景（mock fetch delay > timeoutMs）→ 抛出 NetworkError
- 前端 tsc 零错误 + 全量测试通过

#### 3.4.4 影响范围

- `apiService.ts` L304-L315（重构 requestJson）
- 新增 `lib/errors.ts`（NetworkError 类）
- 各调用方：catch NetworkError → 显示 toast（配合 P0-③）
