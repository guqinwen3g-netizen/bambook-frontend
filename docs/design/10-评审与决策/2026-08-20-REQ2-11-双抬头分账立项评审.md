# REQ2-11 双抬头分账（多法律主体核算）立项评审

> **REQ2-11** · 痛度 28 ▲条件（仅双主体公司痛）· 来源 SEC-06 缺口 · 批次三 B 级 · 成本 **L**
> **需求池定性**（§7）：贯穿单据/报表/权限，**需单独立项评审**——本文档即该评审。实施与否、分期节奏由管理层决策。
> **验收标准**：SEC-06——两主体各自出具对账单/利润表。

---

## §1 立项背景

- **甲方场景**：公司实际以两个法律主体经营（如「XX 服装有限公司」+「XX 国际贸易有限公司」），同一客户/供应商可能任一主体签约；月末需按主体分别出具对账单与利润表，报税口径亦分属两主体。
- **现状（调研结论 2026-08-20）**：系统为**隐式单法人架构**——
  1. 公司档案为 SystemConfig 单例 `global::company.exporterProfile`（7 个出口抬头字段，版本化+审计，全公司一份）
  2. 单据编号序列（BusinessSequence/SequenceRegister）全局唯一，无主体维度
  3. 四类涉税单据（Invoice/CustomsDeclaration/TaxRefund/VatInvoice）与 PurchaseOrder/OutwardRemittance **均无"我方主体"字段**（现有 seller/buyer/consignor 等均为文本快照或对方信息）
  4. 报表数据集（reporting/datasets.ts 7 个）与利润表（profitSheetService）聚合口径无主体维度
  5. RBAC 数据隔离维度只有部门/团队/个人，无主体隔离

## §2 可复用基础

| 既有资产 | 复用方式 |
|---|---|
| exporterProfile 版本化+审计模式（2026-08-18 §1A 裁决） | 平移为 LegalEntity 档案的版本化与变更审计范式 |
| DR-005 部门利润 vs 合并抵销（InternalTradeSummary + internalTrade 域） | "转移计价+双边入账+合并抵销"结构可平移到法律主体维度（部门口径→主体口径） |
| SequenceRegister seqType 设计（11 类 + VoidedNumber 占坑） | 扩展复合唯一键 `[seqType, periodKey, legalEntityId]` |
| 单据"对方快照"字段惯例（supplierName/customerName 冗余快照） | 我方主体同样用 `legalEntityId` FK + `legalEntityName` 快照（打印/归档不失真） |

## §3 方案选项

| 方案 | 描述 | 结论 |
|---|---|---|
| A. 全局多主体改造 | LegalEntity 一等公民 + 全单据/报表/权限贯穿 | 终态正确但 L 级成本一次到位，冻结面大（schema 单写者铁律下需多波次），不推荐一步到位 |
| **B. 单据级抬头标注 + 报表分账（推荐）** | P0 建 LegalEntity 档案 + 单据打主体标 + P1 报表/对账单按主体出 + P2 权限/序列细化 | 分期可控，每期独立可验收，与既有快照惯例一致 |
| C. 双账套并行 | 独立部署两套系统按主体分账 | 数据共享（客户/产品/价格）断裂、内部交易无法勾稽，与 DR-005 内部交易能力冲突，否决 |

## §4 推荐方案数据模型（P0 核心）

```prisma
model LegalEntity {
  id           String  @id // 格式：LE_${shortId}
  code         String  @unique // 主体编码（如 LE-A / LE-B）
  nameCn       String  // 中文抬头（发票/报关/退税用）
  nameEn       String? // 英文抬头（出口单证用）
  taxNo        String? // 纳税人识别号
  usccNo       String? // 统一社会信用代码
  addressCn    String?
  addressEn    String?
  bankName     String? // 开户行（承接 exporterProfile 银行四件套）
  swiftCode    String?
  bankAddress  String?
  accountNo    String? // 外币账号
  isDefault    Boolean @default(false) // 存量归属主体（迁移基线）
  status       String  @default("Active") // Active | Archived
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

- **单据标注**（P0 打点，全部可选 FK + 快照）：`Invoice`、`PurchaseOrder`、`CustomsDeclaration`、`TaxRefund`、`VatInvoice`、`OutwardRemittance` 各加 `legalEntityId String?` + `legalEntityName String?`
- **序列分主体**（P2，非 P0）：SequenceRegister 复合键加主体维；P0 阶段两主体共用序列（编号不冲突因前缀一致、主体靠标注区分）是否可接受 → **决策点 D-3**
- **客户/供应商授信**：creditLimit 挂在 Relation 上，双主体共用额度还是分主体额度 → **决策点 D-2**

## §5 分期实施建议

| 期 | 范围 | 验收锚点 | 预估 |
|---|---|---|---|
| P0 主体档案+单据打标 | LegalEntity CRUD（AdminPanel 公司档案升级为多主体列表）+ 六类单据创建/编辑带主体选择（默认 = isDefault 主体）+ 打印单证抬头取主体档案 | 任一发票可按主体抬头打印；两主体各开一张发票 | S-M |
| P1 报表分账 | 对账单（finance/reportService）+ 利润表（profitSheetService）+ 资金日历/应收应付按 `legalEntityId` 过滤出账；合并视图（不过滤）保留 | SEC-06 主锚点：两主体各自出具对账单/利润表，数字与单据明细勾稽一致 | M |
| P2 权限与序列 | 主体维度数据隔离（财务按主体分岗）+ SequenceRegister 主体键 + 付汇/退税申报主体校验 | 财务 A 只见主体 1 账目；编号按主体分序列 | M |

**内部交易衔接（P1 并入）**：两主体间购销（面料主体→服装主体）复用 DR-005 internalTrade 域——`Order.isInternalFabricTrade` 已有双边记账结构，主体化后"部门口径合并抵销"升级为"主体口径合并抵销"，合并利润表 = 两主体利润 + 主体间内部交易抵销。

## §6 风险与决策点（已拍板 DR-048 · 2026-08-27）

| # | 决策点 | 拍板结论 |
|---|---|---|
| D-1 | 是否立项及启动时点 | **双主体事实成立，暂缓至 v1.1 首批**，不阻断 v1.0 投产 |
| D-2 | 客户信用额度分主体还是共享 | **共享** Relation 级单额度（P0 零改动），误伤出现时 P2 再议 |
| D-3 | 单据编号是否分主体独立序列 | **共用序列**，主体靠单据标注区分 |
| D-4 | 存量 3 年历史数据归属 | **全归默认主体（isDefault）**，历史 Excel 无需回溯拆分 |
| D-5 | VatInvoice seller 主体强校验 | **强校验**（Output seller / Input buyer），随 P0 主体档案落地 |

**主要风险**：
- **冻结面**：schema.prisma 单写者铁律下六类单据加列需一次迁移窗口（db push 单批），前后端联动面广
- **报表口径回归**：P1 分账后必须保住"跨模块一致性铁律"（对账单/账龄/资金日历三处数字一致），需扩展既有回归测试
- **打印版式**：单证模板（printDocument）抬头来源从单例切多主体，历史已出单据重打不得变抬头（靠 legalEntityName 快照保证）

## §7 评审结论

- **可行**：方案 B 分期路径清晰，P0/P1/P2 每期独立可验收，复用面（exporterProfile 范式 / DR-005 抵销结构 / 快照惯例）充分
- **不启动则维持现状**：单主体经营下零损失（▲条件性需求）；一旦公司实际启用双主体签约，P0 为最小可用闭环
- **后续动作**：管理层确认 D-1~D-5 后，P0 出正式模块设计文档（04-模块设计/08-设置与后台/法律主体与多抬头分账.md）再动工
