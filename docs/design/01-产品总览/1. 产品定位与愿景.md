## §2 产品愿景

**成为纺织服装外贸 AI 原生的 ERP 级全链路操作系统。**

从面料开发、款式打样、报价接单、采购生产、QC 检验、出运报关、发票核销到收款退税，Bambook OS 以**全量核心业务数据互相关联**为骨架（当前覆盖客户/产品/订单/报价/采购/BOM/运单/发票/收款/核销/开发/QC/报关/退税，后续按需扩展），以**订单状态机**为流程驱动核心（当前 6 状态，后续按需扩展），以 Agent 智能助手为自动化执行层，用半透明 flat 设计语言构建：

- **Cockpit 专属驾驶舱**：按角色差异化呈现——业务员看自己业务进度、销售主管看团队全局、总领导/老板看全公司经营
- **Dashboard 全景看板**：大屏投放式数据可视化（公司电视机展示）

产品主轴为**服装和面料**两大业务域（DR-002）；其他贸易仅为非主业务的轻量归集，不展开为独立业务体系。

**AI 原生的 ERP 级操作系统**：兼容传统 ERP 全部功能（手动录入、审批流、报表），同时由 AI 辅助完成操作与执行。所有业务数据沉淀到统一真源，AI 从第一天起就能读懂整个公司。

## §4 7 角色画像

### §4.1 业务员（SALES）— 前线指挥官（宽泛角色容器）
- **核心定位**：系统设计层面将销售/跟单/开发/设计等多种业务职能统一归纳为业务员角色。系统不关心"你是跟单员还是开发还是设计"，只关心"你是业务员"
- **日常工作**：客户邮件往来、打样登记、报价、订单跟进、催款、开发案例管理、生产进度跟进、QC 协调、款式开发、设计稿管理
- **核心诉求**：客户全量历史一眼看完；报价出单快（<2 分钟）；订单进度不追着工厂问
- **进入路径**：关系智库→客户→报价管理→订单管理→AI 助手
- **departmentId 分组**：✅ 按品牌客户/市场/服装组/面料组自定义分组（如"服装一组"/"面料二组"/"品牌 A 组"/"欧洲市场组"），小组名称和对应客户可编辑可自定义
- **设计优势**：简化权限设计（不需要为跟单/开发/设计单独设角色）；符合贸易公司实际（业务员从接单到跟单一肩挑）；灵活适配（不同业务员可侧重不同职能，通过 departmentId 区分小组）

### §4.2 销售主管（SALES_MANAGER）— 团队守门员
- **日常工作**：审核报价偏差、审批订单变更（交期±7天/数量±10%）、团队业绩看板
- **核心诉求**：报价偏差红灯自动拦截；订单变更双签不掉链子；团队漏斗可视化
- **进入路径**：全景看板→报价审批→订单变更审批→风险管理
- **模块化权限**：可通过 `user_permission_overrides` 追加小组内审批权（如 `quotations:approve:low` + departmentId=小组），实现"业务员 + 小组长"混合身份

### §4.3 财务（FINANCE）— 账房管家
- **日常工作**：发票签发与核销、收付款凭证录入、VAT 认证、退税申报、汇率锁定
- **核心诉求**：业务数据（订单/出运）自动对接到应收账龄；银行水单与发票一键匹配；敏感数字不泄露
- **进入路径**：财务管理→发票管理→定价与利润→退税

### §4.4 QC（QC）— 质量守门人
- **日常工作**：成衣 QC 检验（AQL 抽样/疵点判定）、面料 QC 检验（色牢度/缩水率/克重）、检验报告签发、放行/拒收判定
- **核心诉求**：检验标准一键调用；疵点照片批量上传；检验报告自动关联订单
- **进入路径**：QC 工作台→成衣检验/面料检验→检验报告→放行/拒收
- **departmentId 分组**：✅ 服装 QC 组/面料 QC 组（通过 departmentId 隔离，如"服装 QC 组"/"面料 QC 组"）

### §4.5 后勤（LOGISTICS）— 履约保障官
- **日常工作**：物流信息登记（装箱单/提单号/船期）、单证制作与核对（报关单/装箱单）、发货确认（货物离厂确认）、仓储管理（入库/出库/库存盘点）
- **核心诉求**：装箱单自动关联订单；报关单一键生成；发货确认实时同步
- **进入路径**：货运管理→装箱单→报关单→发货确认
- **权限边界**：无财务权限（不接触收款/付款/发票金额）、无业务权限（不接触客户/报价/订单创建）
- **与财务边界**：后勤负责物流/单证/发货，财务负责发票/凭证/收付款。发票由业务员主导生成（见 §4.9），后勤不涉及发票制作

### §4.6 系统管理员/总领导（ADMIN）— 基础设施工程师 + 经营决策者
- **日常工作**：用户创建与角色分配、数据字典维护、知识库审核、审计日志排障、业务审批（价格变更/订单变更/付款审批）
- **核心诉求**：权限矩阵可视化编辑；字典值批量导入；审计日志全量可查；业务审批权通过 scope 和组织关系授权
- **进入路径**：管理后台→用户/角色→数据字典→知识库审核→审批中心
- **DR-023**：系统兜底权限与业务审批权分离——技术超级管理员身份不等于业务审批权限；总领导的业务审批权通过业务审批 scope 和组织关系授权

### §4.7 超级管理员/老板（SUPER_ADMIN）— 上帝视角
- **日常工作**：SuperAdmin 角色授予、全量数据导出迁移、合规豁免、经营驾驶舱日/周/月复盘、>5 万付款审批、信用额度调整
- **核心诉求**：一键部署到 Mac Mini；所有操作全留痕；不可删除此角色；一屏看毛利润/回款率/准交率/外汇敞口
- **进入路径**：管理后台→权限矩阵→审计日志导出→OPS Panel→经营驾驶舱

### §4.8 角色模块化说明

**模块化权限调整**：通过 `user_permission_overrides` 表实现"业务员 + 小组长"混合身份。

**业务场景**：小张是业务员，但同时也是 3 人小组的组长，需要审批小组内报价偏差（≤5 万）。

**实现方式**：
- 小张只有 `role-sales` 角色
- 通过 `user_permission_overrides` 追加 `quotations:approve:low` scope + `departmentId=小组` 限定
- 系统运行时合并 `role-sales` 默认权限 + `user_permission_overrides` 追加权限

**优势**：
- 精细化控制（可限定 departmentId=小组）
- 无需创建新角色
- 支持动态调整（小组长任命/卸任时修改 overrides 即可）

### §4.9 发票/合同生成流程

**业务流程**：
```
业务员创建 PI/合同 → 一键生成（不带章）→ 提交主管审批
                                    ↓
                            主管电子审批（敲章）
                                    ↓
                            合同生效 → 可下载带章版本
                                    ↓
                            业务员也可下载不带章版本（发客户）
```

**角色分工**：
- **业务员**：主导发票/合同生成（熟悉客户需求，快速生成）；可下载不带章版本（PI 发客户）
- **销售主管**：电子审批（敲章）；把控风险；审批通过后合同生效
- **后勤**：不参与发票制作（发票由业务员主导，后勤只负责物流/单证/发货）

**业务价值**：
- 业务员主导（熟悉客户需求，快速生成）
- 主管审批（把控风险，电子敲章）
- 灵活下载（带章/不带章双版本，满足不同场景）

## §5 5 组导航定位

### §5.1 经营总览（overview, order 10-19）
**定位：老板和主管的决策面板。** Dashboard 全景看板（大屏投放式数据可视化，公司电视机展示）+ Cockpit 专属驾驶舱（按角色差异化呈现）+ 报表中心（自定义报表）。

### §5.2 客户与市场（customer, order 20-39）
**定位：销售的作战地图。** 关系智库（客户/供应商档案真源）+ CRM 跟进记录（沉淀每一次沟通）+ 智能邮箱（邮件自动绑定客户档案）+ 季节/趋势/营销（市场侧长线布局）。

### §5.3 订单履约（fulfillment, order 40-69）
**定位：全公司的流水线。** 产品数字档案是所有业务的真源锚点；开发→报价→订单→采购→生产→QC→出运→报关→单据 是完整的履约链路（采购与投产排期可并行，更完善的链路设计详见[核心业务流程.md](../03-业务规则/核心业务流程.md)）。其他贸易保留采购、销售、结算、附件与审计能力（DR-002），默认仅强制负责人、业务方向、交易对方、记录日期，其余字段按需填写。

### §5.4 财务与成本（finance, order 70-89）
**定位：利润的守门人。** 财务管理（凭证/发票/核销/退税）是基本盘，定价与利润（双轨 Track A/B）是核心武器，BOM 成本核算是底线，风险与合规是保险丝。

### §5.5 平台（platform, order 90-119）
**定位：系统地基 + 支撑模块。** AI 助手（让所有功能用一句话就能调）+ 数据中心/知识库（公司第二大脑）+ 人事管理（HR：人员概览/团队管理/项目分配/工时概览，系统管理员权限控制）+ 业务工具（快捷效率入口）+ 设置/管理后台（权限/字典/审计配置）。

## §7 非目标（Out of Scope）

| 项 | 说明 |
|---|---|
| SaaS 多租户/客户隔离 | 单公司专属交付（DR-001），不建设多租户、客户隔离或跨公司切换；未来新客户独立设计和部署 |
| MTM 独立业务体系 | MTM 自然归入"其他贸易"轻量归集（DR-002），不单独建模或设计 |
| 生产端工位级 MES | 工厂级排产/工时/计件非贸易公司核心能力，降级为可选模块 |
| 移动端 PWA 主形态 | 移动端仅远期只读视图，桌面 Electron 是唯一产品形态 |
| 会计电算化全盘替代 | 不做总账/明细账/三大报表，仅做业务层应收应付 + 凭证导出对接金蝶/用友 |
| 公域电商平台对接 | 不做亚马逊/速卖通等 C 端运营，聚焦 B2B 外贸 |
| 社交协同（IM/Doc 协同） | 不替代微信/飞书，仅绑定业务对象到消息与审批 |

## §8 关键设计原则

1. **真源唯一原则**：每个业务对象只有一个真源表，其他模块只读关联，不允许重复字段冗余
2. **关联先行原则**：任何新建单据必须先绑到上游对象（订单→客户+报价→产品+BOM），不允许游离单据
3. **权限最小原则**：业务员默认仅本部门可见，领导角色（销售主管/总领导/老板）按组织归属范围可见；敏感字段（佣金/成本/薪酬）默认遮罩，按需单独授权（DR-024 领导可视化与权限最小化）
4. **作废不复用原则**：所有业务编号一旦分配不回收，作废仅占坑标记，保证审计连续
5. **设计铁律原则**：所有 UI 必须走 BDS v2.1 语义类，不允许硬编码颜色/圆角/阴影
6. **审批权分离原则**：技术兜底权与业务审批权分离——SuperAdmin 拥有系统级兜底权限，但业务审批权（报价/订单/付款）通过业务审批 scope 和组织关系授权（DR-023 超级管理员与业务审批权分离）

## §9 成功指标（KPIs）

| 指标 | 目标值 | 测量方式 |
|---|---|---|
| 报价出单时间 | ≤5 分钟 | 从打开报价到提交审批的平均时长（含客户/产品/数量/价格/付款条件填写） |
| 订单利润可见延迟 | T+0（出运前即可预估） | 报价→订单→出运 三阶段利润表一致性 |
| 单证错误率 | <0.5% | 报关/发票退回次数 / 总签发次数 |
| 风险预警提前量 | ≥3 天 | 交期拖延/信用超限 首次预警 与 实际逾期天数差 |
| 新人上手时间 | ≤3 天 | 从入职到能独立出报价单（含系统操作培训 + 业务流程熟悉） |
