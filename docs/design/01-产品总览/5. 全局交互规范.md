### §3.2 全局搜索（双入口统一收口方案）

#### 3.2.1 全局搜索双入口统一收口

**现状**：全局搜索能力当前内嵌于 CommandPalette，Sidebar/Header 多处搜索入口体验分裂；现统一收口为 **Header + Cmd+K 双入口**，其他侧边栏一级入口的搜索框全部移除或跳转收口。

**入口一：顶部 Header 常驻搜索框（嵌入式入口）**
- **位置**：顶部 Header 右侧，通知中心铃铛图标的左侧
- **尺寸**：宽 320px，高 36px（`bds-input` 标准高度），左右 padding 12px
- **Placeholder**：「搜索订单/客户/产品/报价… 或 ⌘K」（Mac 显示 ⌘K，Windows 显示 Ctrl+K）
- **UI 结构**：左侧 🔍 搜索图标 + `<input>` 输入框 + 右侧 `⌘` 按钮（点击打开 Cmd+K 浮层并预填当前输入文字）
- **交互行为**：
  - 输入时：下拉建议面板即时显示 = Cmd+K 的 **Top Results** 分组（视图指令前 4 条 + 客户/订单/产品前 5 条，合计 ≤15 条）
  - 按 Enter：若下拉有高亮建议则执行跳转；若无高亮则直接打开 Cmd+K 浮层并以当前关键词触发全量搜索
  - 点击建议项：同 Cmd+K 执行（订单直开详情、其余跳转到模块视图），执行后 Header 搜索框清空失焦
  - 点击右侧 `⌘` 按钮：打开 Cmd+K 浮层并**预填当前文字**，光标在末尾可继续编辑

**入口二：Cmd+K / Ctrl+K 快捷浮层（已实现）**
- 唤起方式：`Cmd/Ctrl+K` 全局快捷键 或 点击 Header 搜索框右侧 `⌘` 按钮
- 与 Header 搜索框对齐：结果面板沿用同一 CmdK 组件（Header 搜索框 = CmdK 的嵌入式入口，共享数据源与过滤逻辑）

**两者 UI 对齐合约**：
- Header 搜索框的下拉建议 = CmdK 的 Top Results 分组结果，渲染样式完全一致（不做两套 UI）
- 点击 Header 搜索框右侧 `⌘` 按钮打开 CmdK 时，当前输入文字自动预填到 CmdK 的 `<input>` 中，光标定位在末尾
- Esc 关闭 CmdK 后，焦点回到 Header 搜索框（如之前聚焦的话）

#### 3.2.2 侧边栏（Sidebar）搜索框统一收口

**原问题**：Sidebar 各一级入口（客户/订单/产品等）各自带搜索框，导致三处搜索体验分裂（Sidebar 内局部搜索 vs Header 全局搜索 vs Cmd+K）。

**收口方案**：
- **移除** Sidebar 各一级入口顶部的独立搜索框（客户列表搜索、订单列表搜索等）
- **替代行为**：用户在 Sidebar 某模块下想搜索时，点击该模块内部的「搜索」图标按钮或直接用 `Cmd/Ctrl+K` → **自动聚焦顶部 Header 搜索框**并激活（若有全局模块上下文则作为搜索过滤器，但默认仍为全库搜索）
- **模块内过滤**：列表页保留「高级筛选 + 当前视图过滤」作为局部过滤能力（例：订单列表按状态/负责人/日期范围筛选），不再提供独立搜索框

> 统一收口原则：**全公司数据唯一全局搜索入口 = Header 搜索框 + Cmd+K 双入口**；各模块列表页用「筛选器」而非独立搜索框，避免搜索语义分裂。

- **过滤逻辑（共享）**：`matches(query, ...fields)` 对每域记录的标题/副标题/编号字段做 `toLowerCase().trim()` 子串匹配，大数据量时走服务端 `/api/v1/search`（GAP-G4）

### §3.3 跨模块 prime 跳转（`primeXxxFromYyy` 模式）

**约定**：跨模块跳转不通过 URL 路由，而是通过 App 层受控 state + 各 Manager 导出的 `primeXxxFromYyy` 函数实现「携带上下文跳转到目标模块的创建/详情视图」。

| 源 Manager | prime 函数 | 目标 | 携带上下文 |
|---|---|---|---|
| `QuotationManager` | `primeQuotationCreateFromDevCase(prime)` | 报价单创建 | 开发案例 ID + 款式 |
| `ProcurementManager` | `primeProcurementCreateFromOrder(prime)` | 采购单创建 | 订单 ID + 物料清单 |
| `ShipmentManager` | `primeShipmentCreateFromOrder(prime)` | 发货单创建 | 订单 ID + 装箱明细 |
| `FinanceManager` | `primeFinanceInvoiceCreate(prime)` | 发票创建 | 订单 ID + 金额 |
| `DocumentCenter` | `primeDocumentCenterGenerate(prime)` | 单据生成 | 订单 ID + 单据类型 |
| `QcWorkbenchManager` | `primeQcAssignmentFromOrder(orderId)` | QC 任务创建 | 订单 ID |
| `RelationsManager` | `primeRelationsOrgDetailPreview(orgId)` | 客户详情预览 | 客户 ID |
| `SuppliersManager` | `primeSuppliersFactoryPreview(relationId)` | 供应商工厂预览 | 供应商 ID |

**读取模式**：目标 Manager 通过 `readXxxPrime()` 读取 prime 上下文，渲染预填表单或直开详情。

### §3.4 `<StatusBadge>` 统一封装组件契约（全局组件）

#### 3.4.1 语义层 API（禁止直接传颜色字符串）

**组件 Props**：
```tsx
interface StatusBadgeProps {
  variant: StatusBadgeVariant;   // 语义值，不传颜色
  children: React.ReactNode;     // 文案（例：「草稿」「已确认」）
  size?: 'sm' | 'md';            // 尺寸，默认 md
  withDot?: boolean;             // 左方加圆点（状态机可视化用），默认 false
  className?: string;            // 外层扩展类名，仅允许间距类名
}
```

**`variant` 语义值清单（20 种，按需扩展，集中维护）**：
```
type StatusBadgeVariant =
  | 'draft'        // 草稿（灰）
  | 'pending'      // 待处理/待审批（黄）
  | 'confirmed'    // 已确认（蓝）
  | 'in_progress'  // 进行中（青）
  | 'blocked'      // 阻塞/门禁未过（橙）
  | 'approved'     // 已审批/已放行（绿）
  | 'rejected'     // 已驳回/未通过（红）
  | 'shipped'      // 已发货（蓝青）
  | 'delivered'    // 已交付（绿深）
  | 'paid'         // 已付款/已核销（绿）
  | 'void'         // 已作废/已取消（红深）
  | 'warning'      // 告警（橙）
  | 'critical'     // 严重/致命（深红）
  | 'archived';    // 已归档（中性灰深）
```

> 扩展新语义时，必须先在 `StatusBadgeVariant` 类型中追加，再在 CSS 变量表中加对应 bg/text 对；**禁止直接在业务代码中用 tailwind 类 `bg-red-100 text-red-800` 或 hex 绕过组件**。

#### 3.4.2 颜色定义（全走 CSS 变量，flat 设计）

- **BDS flat 纪律**：无阴影（`box-shadow: none`）、无边框（`border: none`），flat 纯色 badge
- **圆角**：`var(--r-compact)`（BDS 紧凑圆角，非 full 圆）
- **颜色变量**（全部走 tokens.css CSS 变量，不硬编码）：

| variant | 背景 CSS 变量 | 文字 CSS 变量 |
|---------|--------------|--------------|
| `draft` | `--badge-draft-bg` | `--badge-draft-text` |
| `pending` | `--badge-pending-bg` | `--badge-pending-text` |
| `confirmed` | `--badge-confirmed-bg` | `--badge-confirmed-text` |
| `in_progress` | `--badge-in_progress-bg` | `--badge-in_progress-text` |
| `blocked` | `--badge-blocked-bg` | `--badge-blocked-text` |
| `approved` | `--badge-approved-bg` | `--badge-approved-text` |
| `rejected` | `--badge-rejected-bg` | `--badge-rejected-text` |
| `shipped` | `--badge-shipped-bg` | `--badge-shipped-text` |
| `delivered` | `--badge-delivered-bg` | `--badge-delivered-text` |
| `paid` | `--badge-paid-bg` | `--badge-paid-text` |
| `void` | `--badge-void-bg` | `--badge-void-text` |
| `warning` | `--badge-warning-bg` | `--badge-warning-text` |
| `critical` | `--badge-critical-bg` | `--badge-critical-text` |
| `archived` | `--badge-archived-bg` | `--badge-archived-text` |

> 深浅模式切换：通过在 `html.dark` 下重新赋值同一 CSS 变量实现，不在组件内部判断 `isDarkMode`。

#### 3.4.3 可选尺寸（size）

| size | 高度 | 字号 | 左右 padding |
|------|------|------|------------|
| `sm` | H18px | 10px（`text-[10px]` 或 `var(--f-caption)`） | px-2 |
| `md`（默认） | H22px | 12px（`var(--f-label)`） | px-2.5 |

> 字重：全部 `font-medium`（500），遵守全局 ≤300 铁律不影响 badge 小字可读性。

#### 3.4.4 可选圆点（withDot）

- 当 `withDot=true` 时，在文案左侧渲染一个 6px 同色圆点（直径 6px，`background-color` = 当前 variant 的背景变量）
- 圆点与文案间距 6px；垂直居中对齐
- 典型用途：状态机泳道（Production pipeline）的阶段卡片、订单管线 10 阶段的状态可视化、审批流节点等

#### 3.4.5 契约要求（纪律）

**所有订单管线泳道 / 列表 / 详情页的状态展示**：
- ❌ **禁止**使用内联 tailwind 颜色类（`bg-red-100 text-red-800`、`inline-flex items-center rounded-full ...` 等）
- ✅ **必须**通过 `<StatusBadge variant='draft'>草稿</StatusBadge>` 统一调用
- 状态语义集中在 `StatusBadgeVariant` 一处维护；全局改配色只需改 CSS 变量表，不搜全库替换

**反例（禁止）**：
```tsx
// ❌ 直接写颜色类，绕过 StatusBadge
<span className="inline-flex items-center rounded-full bg-red-100 px-2.5 py-0.5 text-xs font-medium text-red-800">
  已驳回
</span>
```

**正例（必须）**：
```tsx
// ✅ 用语义化 StatusBadge 组件
<StatusBadge variant="rejected" withDot>已驳回</StatusBadge>
```

#### 3.4.6 与现有状态映射（实现参考）

| 老状态语义 | 对应 variant |
|-----------|------------|
| `draft`（中性灰） | `draft` |
| `warning`（黄，待签） | `pending` |
| `info`（蓝，已确认） | `confirmed` |
| `active`（蓝青，生效中） | `in_progress` |
| `success` / `completed`（绿，已完成） | `approved` / `delivered` / `paid`（按业务选） |
| `danger`（红，已取消/驳回） | `rejected` / `void` / `critical`（按严重度选） |

> **实现现状**：状态语义映射函数 `statusSemanticClass` / `statusSemanticText` / `statusSemanticBg` 集中在 `components/rdlBusinessStatusTokens.ts`，现需抽出独立 `<StatusBadge>` 组件封装，各 Manager 停止内联用法。

### §3.6 Toast 反馈

- **用途**：操作成功/失败/警告的即时反馈（保存成功、删除确认、网络错误）
- **位置**：屏幕右上角或底部居中（BDS `rounded-floating` 浮层，不做深浅调转）
- **纪律**：禁止 `box-shadow` 硬编码，仅靠 `RdlSurface` 浮层语义区分层次

## §5 状态机（审批流）

```
                 create（创建时即按 DR-007 组织归属解析 reviewerId）
                 ┌──────────────────────┐
                 ▼                      │
            ┌─────────┐    approve    ┌──────────┐
            │ pending │ ────────────► │ approved │
            └─────────┘                └──────────┘
                │   ▲                       │
        reject  │   │ reopen(n/a)           │ decide
                ▼   │                       ▼
            ┌──────────┐               ┌──────────┐
            │ rejected │               │ decided  │ (终态聚合视图)
            └──────────┘               └──────────┘
```

| 状态 | 字段值 | 触发条件 | 后续动作 |
|---|---|---|---|
| `pending` | `status='pending'` + `reviewerId` 必有 | **创建时即解析 reviewerId**（DR-007：按发起人的 departmentId → 销售主管；若无对应销售主管 → 系统管理员总领导兜底；报价/付款/订单变更等各类审批均走此路由） | 等待对应 reviewer 决策（推送通知到 reviewer 的铃铛 + Electron 原生推送） |
| `approved` | `status='approved'` | reviewer 调用 `/api/v1/approvals/{id}/decide` 通过 | 解锁下游：报价单可转订单 / 付款需求进入财务待执行列表 / 订单取消进入影响汇总流程等 |
| `rejected` | `status='rejected'` | reviewer 调用 `/api/v1/approvals/{id}/decide` 拒绝 | 驳回发起人，携带 decisionNote 说明 |
| `decided` | `decidedAt IS NOT NULL` | approved 或 rejected 后聚合 | 进入审计日志 |

**跨业务审批通过 `actionType` 区分**（状态机本身不变）：
- 价格偏差：`quotation.price_deviation`
- 订单变更（交期/数量/价格）：`order.change_xxx`
- 订单取消：`order.cancel`（DR-010），approved 后触发取消申请中→影响汇总→结案处理
- 订单暂停：`order.pause`（DR-010），approved 后触发暂停生效
- 付款申请：`payment.request`（DR-017），approved 后**进入财务待执行列表**（不是直接付款，由财务执行操作）
- 其他业务审批：后续扩展 `actionType` 枚举即可

## §6 数据模型（ApprovalRequest 关键字段）

真源：`server/prisma/schema.prisma:1807`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `String @id` | 主键，格式 `ar_{timestamp}_{random6}` |
| `requesterId` | `String` | 发起人 UserAccount ID（必有） |
| `reviewerId` | `String` | **审批人 ID（必有，创建时按 DR-007 组织归属解析填充，不允许 null）** |
| `departmentId` | `String?` | 发起人的部门（快照，用于审计和解析 reviewerId 的依据） |
| `actionType` | `String` | 审批动作类型（如 `quotation.price_deviation` / `order.change_price` / `order.cancel` / `payment.request` 等） |
| `targetType` | `String` | 目标单据类型（Quotation / Order / Voucher 等） |

| `decisionNote` | `String?` | 审批备注 |
| `executorStatus` | `String?` | **财务执行状态（仅 payment.request 用）**：pending_execution / executing / executed / failed（DR-017 付款申请审批通过后，财务执行环节用此字段追踪） |
| `executedBy` | `String?` | **财务执行人 ID（仅 payment.request 用）**：财务角色点击"已付款"时记录 |
| `executedAt` | `DateTime?` | **财务执行时间（仅 payment.request 用）** |
| `createdAt` | `DateTime @default(now())` | 创建时间 |
| `decidedAt` | `DateTime?` | 决策时间（approve/reject 时填充） |
| 索引 | `@@index` | requesterId / reviewerId / status / actionType / departmentId / executorStatus 各建索引 |

**DR-007 解析规则**（创建 ApprovalRequest 时强制执行）：
1. 取 `requester.departmentId` → 查询 `Department.managerId`（销售主管）
2. 若有对应 manager → `reviewerId = managerId`
3. 若无对应 manager（无部门 / 部门无 manager）→ `reviewerId = 总领导`（系统管理员兜底）
4. 跨团队审批（如全公司级大额付款）→ `reviewerId = 超级管理员`（老板）兜底，或 DB 运行时自定义总领导角色

## §8 权限矩阵（7 角色 × 审批 + 财务执行分离）

> 7 角色见 `6. 角色与权限矩阵.md` §2。**关键原则**：审批权归业务领导（DR-007 组织归属：销售主管 / 系统管理员总领导 / 超级管理员老板）；财务是**执行角色**（不审批付款申请，只执行 approved 后的付款操作）。

| 角色 | 自己发起的审批 | 待审批（reviewer） | 全部审批只读 | 审批决策权 | 财务执行（仅付款类） |
|---|---|---|---|---|---|
| **业务员** | ✅ 发起（报价偏差/订单变更/付款申请等） | ❌（非 reviewer） | ❌ | ❌ | ❌ |
| **销售主管** | ✅ 发起 | ✅ **本团队**（DR-007 本 department.managerId） | ❌ | ✅ 本团队审批（报价/订单变更交期数量/发货放行） | ❌ |
| **财务** | ✅ 发起 | ❌（非审批角色） | ❌（仅可见涉及自己的执行项） | ❌（不参与审批决策） | ✅ **执行付款**（仅对 approved 的 `payment.request`：点击「已付款」，标记 executorStatus/executedBy/executedAt） |
| **QC** | ✅ 发起（如 QC 问题追责审批） | ❌ | ❌ | ❌ | ❌ |
| **后勤** | ✅ 发起（如物流费用申请） | ❌ | ❌ | ❌ | ❌ |
| **系统管理员（总领导）** | ✅ 发起 | ✅ **跨团队兜底**（DR-007：无销售主管对应部门时） | ✅ 只读（排障审计） | ✅ 全公司审批兜底（含大额付款/订单取消三签） | ❌（不直接操作付款，审批后财务执行） |
| **超级管理员（老板）** | ✅ 发起 | ✅ 全公司 | ✅ 全量只读 | ✅ 全部类型审批（最终兜底） | ❌（不直接操作付款，审批后财务执行） |

**付款审批 + 执行完整链路**（DR-017 付款申请与审批）：
1. **业务员发起** → 创建 ApprovalRequest（actionType=`payment.request`）→ DR-007 解析 reviewerId → status=pending
2. **销售主管 / 总领导审批通过** → status=approved → executorStatus=pending_execution → 出现在**财务待执行列表**
3. **财务去银行系统付款完成后** → 在系统点击「已付款」→ executorStatus=executed + executedBy/executedAt 记录 → 通知业务员和审批人"付款已完成"
4. **若审批拒绝** → status=rejected → 驳回发起人，说明原因

## §16 补充说明

1. **prime 命名由来**：取「priming（启动准备）」之意，即跳转到目标模块时预填创建上下文，区别于普通 View 切换
2. **CommandPalette 离线可用性**：因复用 App 层已加载 state 做客户端过滤，离线模式下仍可搜索已加载数据，新增端点仅用于全量搜索（GAP-G4）
3. **审批 fail-closed 原则**：`quotationService.ts:132-134` 明确「无法解析 requester 时不阻断创建：快照照常落库，priceApprovalId 置空；发送门禁对 block 仍 fail-closed」——即 block 级偏差无审批 ID 时，下游门禁拒绝放行
4. **SSE 降级**：NotificationCenter 30s 轮询兜底，SSE 断连不影响通知最终可达
5. **Electron 原生推送**：`window.bambookNotification.showNative()` 通过 `preload.ts exposeInMainWorld` 注入，Web 浏览器环境下为 `undefined`，自动降级为应用内提醒
6. **DR-007 reviewerId 解析的 fail-open 兜底**：若 Department 查询失败 / managerId 未设置 / DB 异常时，**reviewerId 直接赋值为系统管理员（总领导）**，绝不允许为 null（保证审批一定有责任人接收；后续超级管理员可在后台手动改派）
7. **付款审批 + 执行分离的职责边界**：审批仅判断"这笔钱该不该付"（业务合理性），归销售主管/总领导；执行仅判断"钱有没有从银行付出"（财务操作），归财务。两者不可混用，确保业务领导审批责任与财务实际操作互不越界
