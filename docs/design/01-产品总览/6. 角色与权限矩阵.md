# 角色与权限矩阵 / Role & Permission Matrix

> **2026-10-07 职责纠偏：** 本文件是旧权限文稿，不能整份作为当前组织或有效授权真源。采购、库存、样品管理由业务员经办，不创造采购/仓储岗位；QC、财务和后勤单证保留真实专业分工。源码默认权限、数据库既有授权和具体对象权限须分别核对；下文旧scope表/人数/完成状态不代表本轮已验证。 当前规则见[角色与实际分工](../global/2026-10-06/05-roles-and-responsibilities.md)及[对话决策总账](../global/2026-10-06/08-2026-10-06-对话设计决策总账.md)。


> **DR-023 关联**：超级管理员（SuperAdmin）系统兜底权限与业务审批权分离——技术超级管理员身份不等于业务审批权限；总领导的业务审批权通过业务审批 scope 和组织关系授权
> **DR-024 关联**：领导可视化与权限最小化——领导（销售主管/总领导）默认可见全公司数据，但业务操作权限按组织归属最小化
> **DR-025 关联**：组织/团队/归属影响范围——数据范围规则按组织归属（departmentId → Department.head）解析，不按固定角色硬编码
> **DR-026 关联**：公共资料与内部资料分离——产品/供应商/客户资料分公共资料（全员可见）与内部资料（按归属部门可见）
> **DR-027 关联**：供应商产品能力直写——供应商档案直接维护产品能力（面料/成衣/辅料），不通过产品档案间接关联
> **DR-028 关联**：其他贸易完整记录——其他贸易保留采购、销售、结算、附件与审计能力，默认仅强制负责人/业务方向/交易对方/记录日期
> **DR-029 关联**：出运/履约/收款分开——出运（Shipment）、履约（Order fulfillment）、收款（PaymentVoucher）为三个独立阶段，不混同
> **DR-030 关联**：经营总览页面区块——经营总览提供统一 KPI 投影（订单数/金额/准交率/利润），按业务线（服装/面料/其他）分区展示
> **DR-031 关联**：完整字段清单与流程图规范——设计文档须包含完整字段清单（字段名/类型/约束/说明）与流程图（ASCII/表格），禁止省略

## §2 角色清单（7 系统内置角色，宽泛职能容器，不可删除 isSystem=true）

真源：`SYSTEM_ROLE_IDS` + `SYSTEM_ROLE_META`

> **7 角色设计原则**：宽泛职能容器（不细分岗位），按「业务线（服装/面料/小组）」的 departmentId 进一步切分数据范围和审批路由。面料/成衣按实际团队区分；不从模块或scope反推公司存在采购/仓储岗位。

| Role ID 常量 | DB Role ID | 中文名 | rank | 职能定位（宽泛容器） | 审批权规则 |
|---|---|---|---|---|---|
| `SYSTEM_ROLE_IDS.SALES` | `role-sales` | **业务员** | 1 | 销售一线：报价/跟单/开发/采购申请/付款申请/客户维护；面料/成衣业务组成员负责开发、订单、采购及相关样品/库存操作，不另设采购岗位 | 角色码本身不授业务审批；真实负责人获授权时可在业务范围内审批，包括自己的单据 |
| `SYSTEM_ROLE_IDS.FINANCE` | `role-finance` | **财务** | 2 | 财务执行：登记业务已开CI与供应商票据/应收应付/收付款核销/VAT登记/适用财务事项；**审批权与执行权分离**——财务是「付款执行者」（已 approved 的付款需求去银行付出，然后点已付款），不是「付款审批者」 | 退税申报审批（`tax:approve` 财务专业工作）；票据登记（旧`invoices:write`不能解释为财务制作业务CI）；核销执行；财务角色不自动授予业务审批；按真实账号的适用审批权限确定 |
| `SYSTEM_ROLE_IDS.QC` | `role-qc` | **QC** | 2 | 面料/成衣专业检验、疵点和报告；专业团队、账号与入口分开，QC不承担业务BOM/成本维护 | QC 工作流审批（内部）；BOM/成本只读，旧`bom:admin`不作为新设计授权；QC角色不自动授予业务审批；专业结论与经营审批分开 |
| `SYSTEM_ROLE_IDS.LOGISTICS` | `role-logistics` | **后勤** | 2 | 后勤单证：接收业务出运交接，核实装箱、安排运输、制作CI/PL、归档外部凭证；资料回业务员对客发送，不承接独立采购/仓管岗位 | 单证模板配置（`customs:admin`）；发货登记（`shipments:write`）；后勤角色不自动授予业务审批；适用审批按授权范围执行 |
| `SYSTEM_ROLE_IDS.SALES_MANAGER` | `role-sales-manager` | **销售主管** | 3 | 小团队负责人：服装一组主管、服装二组主管、面料一组主管、面料二组主管、客户品牌组主管等；审批本团队业务（DR-007 组织归属：department.managerId = 本人） | **本团队审批权**（报价偏差/交期变更/数量变更/发货放行/客诉扣赔/采购PO审批/价格变更双签之一）；DR-024：可见全公司数据，操作限本团队 |
| `SYSTEM_ROLE_IDS.ADMIN` | `role-admin` | **系统管理员（总领导）** | 4 | 总领导/总经理/总监级（业务兜底审批人）；宽泛职能：用户角色配置、字典配置、知识库审批 + **跨团队业务兜底审批**（DR-007：无对应部门主管或跨团队大单 → 路由到总领导）；HR 人事管理归此角色 | **全公司兜底审批权**（付款审批兜底/坏账核销/价格变更双签之二/订单取消兜底/信用额度调整/利润率配置/权限矩阵 UI 管理等）；DR-024：可见全公司数据 + 大部分敏感字段（薪酬除外） |
| `SYSTEM_ROLE_IDS.SUPER_ADMIN` | `role-super-admin` | **超级管理员（老板）** | 10 | 最高权限；技术兜底（所有模块 R/W/D/A，权限配置，审计日志全可见，不可删除此角色账户）。**DR-023 严格分离**：技术兜底权限 ≠ 业务审批权；日常业务审批按 DR-007 路由到对应 reviewer（SM/总领导），业务审批不依赖 SuperAdmin 技术身份直接放行 | 全部技术权限；业务审批权通过组织归属授权（如需老板亲自批某张审批，在 ApprovalRequest 中 reviewerId 指向老板的 UserAccount ID，而不是靠 SuperAdmin 运行时特判绕过审批链） |

### §5.2 7 角色 × 默认范围 + 模块特殊规则

> **DR-024 领导可视化**：销售主管 / 系统管理员（总领导）默认数据范围 `all`（可见全公司数据用于决策），但**业务操作权限（写/审批/删除）按组织归属 department 最小化**。

### §5.3 DR-024 领导可视化与权限最小化

| 规则 | 说明 |
|------|------|
| 领导可视化 | 销售主管 / 总领导默认可见全公司数据（数据范围 all）——用于查看跨团队 KPI、利润、库存等做决策 |
| 权限最小化 | 业务操作权限（写/审批/删除）按组织归属最小化（仅本 department / 本团队）——避免跨团队越权改数据 |

### §5.4 DR-025 组织/团队/归属影响范围

| 规则 | 说明 |
|------|------|
| 数据范围解析 | 按组织归属（departmentId → Department.head → Department.managerId）解析，不按固定角色硬编码 |
| 审批路由 | 报价审批/订单变更审批/付款审批全部按 DR-007 组织归属路由到对应部门主管，**不按固定金额阈值**；无对应主管或跨团队时上抬到总领导 |
| 动态调整 | 部门结构调整（managerId 变更、部门拆分合并）时，数据范围/审批路由自动跟随调整，无需手动修改角色配置 |

矩阵为空对象 `{}`，运行时特判：
```typescript
if (r === SYSTEM_ROLE_IDS.SUPER_ADMIN) return true; // 任意 scope 直接放行
```
DB seed 时 `getDefaultScopeListForRole` 返回 `Object.keys(PERMISSION_SCOPES)` 全量 60+ scope。

**DR-023 严格执行**：业务审批链仍按 DR-007 组织归属解析 reviewerId（SM/总领导），**不因为老板是 SuperAdmin 就自动把所有审批路由给老板**（避免老板审批爆炸）。仅当 DB 中某张 ApprovalRequest 的 reviewerId 明确是老板的 UserAccount ID 时，老板才会收到该审批。

## §7 敏感字段可见性矩阵（5 字段 × 7 角色）

> **设计原则**：
> - 业务员：全 ❌（一线不用看成本利润佣金，只看销售价；做报价时由系统校验，不显示成本）
> - 销售主管：成本/利润 ✅（审批报价必须知道成本利润，否则没法审批偏差）；佣金/薪酬 ❌（佣金涉及业务员个人收入，销售主管不该看单个人提成明细）
> - QC/后勤：全 ❌（不接触财务机密）
> - 财务：成本/利润/佣金/税基 ✅（做账、发工资、退税计算必须）；薪酬 ❌（薪酬另外走 HR 专门 scope）
> - 系统管理员（总领导）：成本/利润/佣金/税基 ✅（决策必须）；薪酬 ❌（员工薪酬绝密）
> - 超级管理员（老板）：全 ✅；`hr:salary:read` 指定的 HR 也可见薪酬

| 敏感字段（scope） | 业务员 | 销售主管 | 财务 | QC | 后勤 | **系统管理员（总领导）** | **超级管理员（老板）** |
|---|---|---|---|---|---|---|---|
| `cost`（S:cost）成本/采购价/BOM 成本 | ❌ | ✅ | ✅ | ❌ | ❌ | ✅ | ✅ |
| `profit`（S:profit）毛利/毛利率/利润率 | ❌ | ✅ | ✅ | ❌ | ❌ | ✅ | ✅ |
| `commission`（S:commission）佣金率/佣金金额 | ❌ | ❌ | ✅ | ❌ | ❌ | ✅ | ✅ |
| `salary`（S:salary）员工薪酬明细 | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ✅（+ 指定 HR via `hr:salary:read`） |
| `tax_base`（S:tax_base）进项税/退税计税底值 | ❌ | ❌ | ✅ | ❌ | ❌ | ✅ | ✅ |

> **遮罩规则**：无对应 `sensitive:xxx` scope 时，前端字段渲染为 `****`，后端 API 返回时 `permissionService` 自动遮罩。前后端双层保障。

## §9 权限校验流程（运行时）

```
前端/守卫调用 hasPermission(roleId, scope, runtimeUserScopes?)
        │
        ▼
┌─────────────────────────────────────┐
│ 1. runtimeUserScopes 优先            │
│    if (set.has(scope)) return true  │
└─────────────────────────────────────┘
        │ (set 为空或无该 scope)
        ▼
┌─────────────────────────────────────┐
│ 2. 角色数组遍历（支持多角色用户）     │
│    for (r of roles):                │
│      if (r === SUPER_ADMIN) → true  │
│      matrix = DEFAULT_ROLE_PERMISSION_MATRIX[r] │
│      if (matrix[scope] === true) → true │
└─────────────────────────────────────┘
        │ (全部角色都无该 scope)
        ▼
    return false
```

**关键函数**（`lib/rolePermissionMatrix.ts`）：

| 函数 | 签名 | 用途 |
|---|---|---|
| `hasPermission(roleId, scope, runtimeUserScopes?)` | `(roleId: string\|string[]\|null, scope: PermissionScope, set?: Set<string>) => boolean` | 普通 scope 运行时判断 |
| `canViewSensitive(roleId, field, runtimeUserScopes?)` | `(roleId, field: SensitiveFieldScope, set?) => boolean` | 敏感字段判断（内部转 `sensitive:${field}` scope 调 hasPermission） |
| `getDataScopeRule(roleId, moduleOrView?)` | `(roleId, moduleOrView?: string) => DataScopeRule` | 行级范围 fallback（先查模块特殊规则，无则用 `*` 通配） |
| `getDefaultScopeListForRole(roleId)` | `(roleId: SystemRoleId) => string[]` | seed 用，返回角色全部默认 scope 数组 |

**运行时数据流**：
1. 用户登录 → `/api/v1/auth/permissions` 返回 DB 中 `runtimeUserScopes`（DB RolePermission 表 join 结果）
2. 前端/守卫调用 `hasPermission` 时优先查 `runtimeUserScopes`，为空则 fallback 到 `DEFAULT_ROLE_PERMISSION_MATRIX`
3. `permissionService` 在 API 返回前根据 `canViewSensitive` 遮罩敏感字段
4. `permissionGuard` 中间件在路由前根据 `hasPermission` 拦截无权限请求

## §11 业务规则关联

> **核心纪律**：审批链统一走 DR-007 组织归属解析（departmentId → SM → 总领导兜底），**不再按固定金额阈值分档**。`vouchers:approve:pay_lt5` / `pay_gt5` 仅为兼容保留的 scope 名，实际权限按角色分配，运行时不判断金额阈值。

| 规则 | 关联 scope | 审批路由 | 说明 |
|---|---|---|---|
| **价格审批 ⑤ 双轨偏差** | `quotations:approve` | DR-007：SM（本团队）→ 总领导（兜底/跨团队） | 偏差 > 15% warn 级 / > 30% block 级，自动生成 ApprovalRequest 并按 DR-007 填 reviewerId |
| **付款申请审批（DR-017）** | `vouchers:approve:pay_lt5` `vouchers:approve:pay_gt5` | DR-007：SM（本团队小单）→ 总领导（兜底/大单/跨团队） | **不再按金额阈值分档**；首单供应商 +1 级（SM 自动上抬到总领导）用 `vouchers:approve:pay_new_supplier` scope |
| **付款执行（非审批）** | 无审批 scope，需 `vouchers:write` + `executorStatus` 写权限 | 财务角色专用操作 | 审批 approved 后出现在财务待执行列表 → 财务去银行实际付款 → 财务点「已付款」写入 `executorStatus=executed` |
| **订单变更 交期** | `orders:approve:change_delivery` | DR-007：SM（本部门）→ 总领导（兜底） | 不再按 ≤7 天阈值分档 |
| **订单变更 数量** | `orders:approve:change_qty` | DR-007：SM → 总领导 | 不再按 ±10% 阈值分档 |
| **订单变更 价格（双签）** | `orders:approve:change_price` | **双 reviewerId**：SM + 总领导（2 人都批才 approved） | 价格变更风险最高，强制双签 |
| **订单取消（DR-010）** | `orders:approve:cancel` | DR-007 直接上抬至总领导（不归 SM） | approved 后进入 DR-010 取消流程：取消申请中 → 影响汇总 → 结案处理（流程本身代替多人会签） |
| **订单暂停（DR-010）** | 复用 `orders:approve:cancel` scope 或新增 actionType=`order.pause` | 同取消，上抬至总领导 | approved 后暂停生效 → 到期提醒 |
| **首单供应商采购 +1 级** | `procurement:approve` + `vouchers:approve:pay_new_supplier` | SM → 自动上抬到总领导 | 首单风险高，多一层把关 |
| **坏账核销 / 发票作废** | `invoices:approve:writeoff` | **归总领导（不归财务）** | 直接损失公司利润，风险高；财务仅执行核销动作，无审批权 |
| **退税申报审批** | `tax:approve` | **归财务** | 税务合规专业工作，财务直接审批 |
| **客诉扣赔 / 折让** | `aftersales:approve` | DR-007：SM（本团队）→ 总领导（大金额兜底） | 影响应收金额 |
| **坏账核销 + 首单付款双逻辑叠加** | `invoices:approve:writeoff` + `vouchers:approve:pay_new_supplier` | 审批链上抬至总领导 | 风险叠加 → 更高一层 |

## §16 补充说明

1. **副本同步风险（GAP-R2）**：`server/src/_shared/rolePermissionMatrix.ts` 是为绕过 `server/tsconfig.json` 的 `rootDir=./src` 限制而做的快照副本，文件头明确警告「当修改 `/lib/rolePermissionMatrix.ts` 时必须同步更新此文件内容，否则 seed 脚本与服务器守卫矩阵不一致」。建议未来通过 monorepo workspace 或 path mapping 消除副本。
2. **PL-2B 同部门互相可见**：业务员/销售主管的默认数据范围是 `department`（非 `self`），即同部门同事互相可见客户/订单数据，跨部门隔离。这是贸易公司典型场景（一个销售部共享客户池）。**DR-024**：销售主管数据范围升级为 `all`（可见全公司做决策），但操作仍限本部门。
3. **系统管理员（总领导）敏感字段边界**：总领导 rank=4，**故意不给 `sensitive:salary`（员工薪酬）**，但其他成本/利润/佣金/税基全部有权。避免总领导权限过高看到员工个人工资条（薪酬绝密仅老板 + 指定 HR via `hr:salary:read` 可见）。
4. **SuperAdmin 不可删除**：`SYSTEM_ROLE_META` 中 SuperAdmin rank=10，DB seed 时标记 `isSystem=true`，AdminPanel 不允许删除此角色账户。同样，7 系统内置角色（Sales/Finance/QC/Logistics/SalesManager/Admin/SuperAdmin）全部 isSystem=true，不可删除。
5. **多角色用户支持**：`hasPermission` 接受 `roleId: string | string[]`，支持一个用户绑定多个角色（如某人身兼销售主管 + 临时 QC 主管），权限取并集（任一角色有 scope 即放行）。
6. **7 角色宽泛容器设计原则**：按真实业务组、QC、财务、后勤单证及适用领导权限建模，不把采购/库存模块映射成独立岗位，而是按职能族（一线业务/财务/质检/物流执行/团队领导/总领导/老板）归纳。实际数据范围和审批路由靠 departmentId（服装一组/面料二组/品牌组…）切分，避免角色爆炸 + 不必要的岗位/资格层。
7. **审批与执行严格分离（DR-017 付款模型核心）**：付款审批（该不该付）= 销售主管/总领导 scope；付款执行（钱有没有实际从银行出去）= 财务 `vouchers:write` + executorStatus 写权限。两个步骤 scoped 不同、角色不同、时间不同，严禁混同为「财务审批付款」。
8. **双签仅用于价格变更（高风险）**：订单价格变更直接影响利润且不可逆，是唯一强制 2 个 reviewerId（SM + 总领导）的业务场景。其他审批（取消/暂停/交期/数量/付款）都是单人审批但通过 DR-010 状态流程或 DR-007 上抬兜底保证风险可控，不做多人会签（避免审批瓶颈）。
