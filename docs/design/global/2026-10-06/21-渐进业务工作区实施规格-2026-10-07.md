## 3. 页面与交互

### 3.1 入口

开发入口首屏两个选择：**面料开发**、**成衣开发**。选择前不挂载开发详情或创建表单。面料入口内提供“开发案 / 面料寻样”；成衣入口只进入其自身开发列表。历史 `pp/trim` 保留实际类型标签并进入成衣历史上下文，不新造业务类别。

订单入口首屏两个选择：**面料订单**、**成衣订单**。选择后列对应主单。“同一 PO 面料/成衣”仍是两个主单、两个审批。历史 Other 可提供单独的“历史其他记录”读取入口，不混入新建流程、不据此发明新的履约路径。内部备货/内部供料是所选业务的订单用途，不是第三个业务入口。

带准确对象的工作台/通知深链，服务端读回该对象的实际业务族后直接进入相应入口；不得按链接里的任意 type 值改造对象。无权限、版本已删除或归属冲突时保持可理解的错误页，不能回退到默认第一行/默认工厂。

### 3.2 常驻概况、轨迹、单工作区

详情顶部常驻：真实编号、名称、面料/成衣类型、实际交易对象或内部用途/需求组/接收负责人、负责业务员、当前准确对象、关键数量/单位/交期。概况只显示真实事实及未知提示，不把 `DevelopmentCase.stage` 或 `Order.status` 翻译成下游完成。

轨迹只含节点名称、先后/并行关系、实际已发生标记、当前阻塞摘要。节点有五种展示：待开始、当前待办、已有记录、受阻、事实未知。已有记录可以回看，不能因为最新门禁失效而隐藏旧事实。明确不适用的节点按真实配置标注“不适用”，不能把缺字段当不适用。

一个页面只挂载用户当前打开的一个业务工作区。历史节点点击只切换读取区域；未来节点禁用，仅显示锁定原因，不渲染内部内容、不运行其 effect、不预取其详情、不依赖 `hidden`/`display:none`。滚动到底、键盘 End/Tab、锚点、深链都不能打开未来表单。切换准确版本/订单行/分支时重置当前工作区及未提交表单缓存，保留按原对象键保存的未知回执重试。

门禁完成后显示 **“已满足下一步条件” + 具体继续动作**。收到 QC 报告、确认结果、WebSocket 更新或刷新摘要，只更新门禁与提示，不调用下一写接口、不自动切换工作区、不自动创建生产/出运/库存/票据。

### 3.3 显式继续的最小保存方式（本轮 MVP 选择）

本轮建议用已有 AuditLog 保存“业务明确打开下一工作区”的意图，不增 schema，不把该意图当生产、出运或质量完成事实。这样刷新/另一账号读回仍能识别实际继续，而不会仅因后台收到 QC 通过就跳到未来工作区。

继续意图绑定准确 scope、目标节点、当时门禁依据、真实操作人、请求键和时间。相同键精确重放原 ACK，参数漂移冲突；重放也须当前身份、scope、凭据 ceiling 和来源可见。旧 ACK 只能证明原请求成功，不让已经失效的来源获得新的业务资格。

平行业务可分别激活，例如开发实际确认与正式 QC；页面仍一次只显示一个选中的工作区。回看过去不新增继续意图。现有域动作本来就是用户显式操作的，继续按钮可直接打开其表单并在保存时产生真实域事实；新增意图仅补足纯“继续到下一工作区”而尚无域写入的场景。任何继续接口都不调用 ensure、自动填数量、自动完成、自动寄样或自动生产。

## 4. 开发：以轮次和准确工厂版本为轨迹单位

开发案层显示概况及轮次→工厂任务树；每个工厂大版本和点号版本都是独立可选择对象。选择一个版本后，下表节点才决定其当前内容。轮次不是工厂数，也不是版本数。无准确版本的历史成果独立只读并显示“准确版本未知”。

| 节点 | 内容与当前事实 | 解锁/继续判据 | 明确动作 |
| --- | --- | --- | --- |
| 轮次与本厂任务 | 本轮共同要求、本厂独立要求、样品形态计划、交期、附件、通知单 | 创建/修改须准确案与实际工厂权限；本厂任务必填资料完整才可继续登记成果。 | 建轮/本厂任务、编辑、生成该厂通知文件、继续登记成果。 |
| 成果与实物 | 本版返样来源、形态/数量/单位、实际记录的仓库/位置、制作费用 | 大版本由返样保存创建同一实体库记录；小版本引用准确原实物，不新增库存。缺位置保持未知；不能伪造库位。 | 保存返样、查看统一实物、寄样/费用的实际来源操作、继续正式 QC 或实际确认。 |
| 正式 QC | 本版全部正式评审、当前请求、最新已完成报告、实际 QC 人/时间/结论 | 业务显式申请；专业 QC 在工作台执行。没有申请=未发起；queued/in_progress=进行中；最新完成 NOK=受阻；复评另追加。 | 申请正式 QC/复评、查看报告、记录业务已阅；已阅不等于需求方确认。 |
| 实际需求方确认 | 客户/内部需求方、实际确认人/组织/时间/结果/依据、录入人/时间 | 准确版已存在且能核对真实实物来源；与正式 QC 是独立事实，开发中不强迫先 QC 才记录偏好。小版不得继承父版。 | 录入该版实际确认、查看各次确认与依据。 |
| 产品留档 | 本版准确档案链接、原转档回执 | 只由准确版本最新有效已完成正式 QC pass 解锁；不要求客户选用。 | 从本版明确转档；结果未知时核对原请求，不重造资产。 |
| 后续报价/订单 | 明确选中的准确版、规格和本次商业条件；已有下游回链 | 新订单消费按 `assertDevelopmentVersionReadyForConsumption` 核对本版 QC+有效实际确认；现有 Asset/确认源须确属本案本版。不从整案 approved 推断。 | 选择此版本继续报价/新订单草稿；从准确源带规格，由业务核对后进入主单审批。 |

节点图必须表达 `成果→QC→产品留档` 与 `成果→实际确认` 的并行关系；两者共同为准确版新订单消费提供依据。不能画成“客户确认→才可产品留档”，也不能画成“整案确认→所有工厂版本通过”。不把非正式小改沟通偷偷补成 QC 通过。

寄样可以发生在实际可寄数量范围内，不由一个整案“待寄样”状态授予全部版本寄出权限。费用/CI 是来源旁路工作：实际制作/寄样/收费事实存在时可办理，不要求整个开发已完成，不以财务收清解锁或关闭开发。

## 5. 订单：主单审批后逐行，再按真实工厂分支

### 5.1 主单工作区

主单阶段仅“录入与约定 → 主单审批 → 条目履约概况”。审批依据是准确主单及全部行冻结快照、实际审批记录/实际处理人；Pending/Confirmed 等旧标量仅显示原值，不能单独证明主单已批准。提交后冻结；退回恢复草稿编辑并显示实际原因/待改项；批准后显示逐行“进入条目”按钮，由业务选择条目继续。

主单概况并列每行进度与阻塞，不输出一个掩盖分歧的整单百分比。主单可查看已发生的出运/票据历史，但不挂载跨行履约表单。没有选行时要求明确选择，不用第一个订单行代办。

### 5.2 行与分支工作区

| 节点 | 内容来源 | 当前/解锁判据 | 业务继续 |
| --- | --- | --- | --- |
| 履约安排 | 行准确规格/确认源、履约模式、CMT 含项；成衣工厂/生产线分配与尺码计划；面料唯一工厂；全包内部米数分配 | 真实主单批准、当前行可见；中性工厂分支是计划，不等于开产。全包 PP 另核当前 approved 内部面料行/分配修订与米数守恒。 | 记录安排、分配、进入本行或准确分支样品。 |
| 生产前样品 | 本行 requiredSampleFamilies、准确源与范围、实际样品/报告/确认 | 成衣 PP；面料 EPS；依实际族/父源接口决定可登记性。无 TOP 节点。成衣 PP 实际送审尺码和件数独立于合同尺码矩阵。 | 实际登记、申请 QC、寄样并录入实际确认；两道门均满足才可继续本分支生产动作。 |
| 生产与持续检验 | 准确 ReleaseScope/ReleaseRequest/批准、批次修订；实际生产 QC/问题/复验 | 当前准确来源和放行资格，不用整单十阶段状态；成衣每个有产量尺码的生产 QC 覆盖由现有专业门禁判定。问题仅影响实际受影响分支。 | 有权限业务明确发起/签署已有放行命令；持续查看 QC 并处理本分支反馈。 |
| 完成生产与数量核对 | 分支明确完工事实、最终实际量、适用客户/内部允差、条目所有分支汇总 | 不用某次出运推断完工；未知客户尺码口径不可猜；按实际适用规则读回。 | 工厂通知后业务点击“完成生产”，实际填写最终量；按现有后续规则处理真实差异。 |
| 出运前样品 | 本工厂、本出运批次船样；面料可选 RC 按该行实际要求 | 样品族由准确行要求读取；每个必需族自己的 QC 和需求方确认，不能从其他行/工厂/批次补齐。 | 登记、申请 QC、寄样/确认；满足后只解锁出运交接。 |
| 出运交接与回程 | 准确行/工厂/批次及实际拟发量；共享 `evaluateShipmentHandoffEligibility` 与真实 Handoff | 以现有分支生产、数量、质量及样品预检判据为准；历史不能凭 Order.status 推断。 | 业务明确发起交接；后勤办理装箱/CI/PL；回到业务发送客户；既有回程可独立回看。 |

上表是业务工作区组织，不是强迫所有事实排成一个不可并行序列。生产过程与船样的实际发生时机按现有准确业务门禁；是否允许分批出运按当前行约定/后端能力，不能用页面节点位置新增“一定全生产完成才可开始所有出运办理”的限制。

财务往来作为独立关联区：当前已开的业务 CI、实际财务登记/收款/核销可查看；业务签发/财务登记仍在各自节点。财务状态不得变成主单生产/出运完成标记。变更与历史也是可独立打开的已有事实，不在进度轨迹里假作生产前置或终态。

### 5.3 本轮批准的中性拟发准备区

主线程已批准本轮技术选择：明确选定行、真实工厂分支/当前修订，且已有真实主单批准及该分支当前有效原生放行履约依据后，业务可以明确打开“填写本次拟发范围”。此操作只保存打开输入区的意图，不表示已核验可发，更不是发运。中性批次计划或整单 status 不能作为履约依据。

该区仅挂载准确 batch/revision/factory/unit、用户自填 plannedQty、shippingMethod 与共享 canonical 预检结果。数量默认空，不猜剩余量/全单量。用户主动预检时调用既有 `POST /api/v1/shipping/handoffs/eligibility`；结果绑定原输入。修改任一字段、来源/修订/身份变化即失效，不预先挂载装箱、CI/PL、ATD 等后续表单。真正交接创建仍调用原生命令并再次核验完整范围；实际物流和单据在各自当前节点办理。LC 具体条款尚未被共享预检完整消费时不得显示“LC 已核验”。

### 5.4 本轮批准的人工规格来源

总账 §5.1 L174 明确认工录单为正式来源。本轮新增 `ManualOrderLine` adapter，准确来源 ID 为真实 lineId，不制造 ProductAsset、开发 QC 或客户确认。人工入口保留；无规格基准时显示可操作的补齐提示，不能永久要求先有开发档案。

草稿行由业务明确保存 `manualSpecification: {factoryRelationId, specification, agreementBasis, evidence[]}`，规格文本与实际约定依据必填；沿用本行真实描述/数量/单位、成衣尺码/履约模式。实际工厂必须是有效供应商组织及工厂档案。服务器填录入人、时间、修订、审计 ID 与完整规格指纹，并将 `confirmedSourceType='ManualOrderLine'`、`confirmedSourceId=lineId`、不可变结构化规格基准写入本行；body 不接受确认人/批准人、QC pass 或来源指纹。草稿修改仍经既有 JWT、fresh L2、ceiling、父 Order/Line 锁与审批冻结门禁。

真实主单批准的原生快照必须包含同一 Order/Line、同一规格基准与实际工厂，并存在匹配实际审批人/时间的完成审计，之后才能消费。消费统一 helper 重验当前本行基准、producer 审计、主单批准冻结快照与批准审计；仅旧 Confirmed 状态、其他订单批准、借另一行 ID 或后补/篡改规格一律拒绝。PP/放行仍要求其真实 QC 与实际需求方确认，不因人工源跳过。本轮不事后改写已批准快照；已批准人工规格变化沿正式变更边界办理，未有准确新依据时阻塞新消费、历史只读。

人工 producer 接既有 `POST /api/v1/order-lines`/`PUT /api/v1/order-lines/:id` 的 `manualSpecification` 字段；合法读回仍为真实 line DTO 的 `specSnapshot.manualOrderLine`。供应源、样品父图、批次与放行均消费同一个 adapter，不能每个模块各猜一份人工来源。

### 5.5 实际生产线与工厂单线声明（本轮已授权技术选择）

唯一业务依据为总账 §5.3 L204：“每个工厂/生产线形成该条目的工厂履约分支”及“若不同工厂的生产线不同，产前样门禁按实际开产的生产线落实”。以下字段、命令与保存形式是本轮 MVP 技术选择，不能标成用户过去确认过的字段。

成衣生产分支由经办业务明确填写 `productionLineChoice`，二选一：`{mode:'factory_single'}` 表示实际按该工厂单线整体履约；`{mode:'named_line',productionLineId}` 指向该工厂下真实登记的一条生产线。前者不创建虚拟线、不复制工厂或批次 ID 冒充线 ID。旧记录没有声明时维持 unknown；面料不新增生产线要求。同一成衣行、同一工厂存在实际命名线分配时不能再以单线声明覆盖它。

新增 `FactoryProductionLine` 记录实际工厂、实际线名、可选地点、状态与修订、真实录入人和时间；地点未提供保持 null。业务从准确 Order/Line 上下文列出/登记，订单 fresh L2 与工厂 fresh L2 同时核验。公司档案目录可读不代表可登记生产线；只有工厂归属/协作跟进（或实际全权范围）可写，单纯 read 共享不能写。请求完整输入指纹、原请求键及父源锁内重复核验，body 不接受录入人或权限。

`ProductionBatch.productionLineId`、`productionLineSnapshot` 均 nullable。保存真实选择时冻结模式、工厂、可选实际线 ID/修订/名称/地点、真实声明人/时间与指纹。已有计划明确变更声明须携原批次修订、行指纹与请求键，以 CAS 增加批次 revision；已有最终完工、实物入库或有效发运预留时拒绝改写。拆批只能继承同一实际生产组织身份。旧请求可核对原回执，不把原成功当当前新消费资格。

PP 代表范围冻结同一 `productionLineIdentity`；consumer scope 返回 `productionLineMode`、`productionLineId`、`productionLineRevision`、`productionLineFingerprint`。命名线必须由当前批次、当前修订且同一实际线的 PP 经真实 QC 与需求方确认后消费，其他线、同名不同 ID、旧线/批次修订不能替代。单线实际声明可消费同一真实工厂的整行 PP；未明确生产组织的批次仍可读中性计划，不能由未知推算 PP/出运资格。生产线绑定不制造检验、确认、放行、完工、库存或发运事实。

HTTP：准确 Order/Line 的 `GET/POST /api/v1/production-batches/orders/:orderId/lines/:lineId/factory-production-lines`（GET 必须明确 factoryRelationId）；新成衣 create 必须明示 `productionLineChoice`，面料不接受此字段，历史原建批请求先核对其不可变原回执；`POST /api/v1/production-batches/:batchId/production-line` 明确绑定/变更。默认不选第一线。生产线登记表单由业务主动打开，未来出运表单仍不挂载。原生验收须实际人工规格→主单审批→明确生产组织→PP→QC→需求方确认→放行→出运预检，正反证明跨线/旧修订和撤权拒绝，禁止 fixture 直接造通过事实。

### 5.6 开发样品 QC 的实际认领、转交与附件（本轮已授权技术选择）

依据总账 §6.1（行 306–310）、§6.2（行 320）和 §6.4（行 345–349）：团队可见允许按工厂认领；每次评审保留实际执行人，转交留痕；文字、现场图片及完整 DOC/PDF 报告返回准确开发来源。以下是本轮实施技术选择，不追记为用户过去已确认的字段设计。

- 沿用 `DevelopmentSampleQualityReview.startedBy/startedAt` 表示当前实际执行人与本次接手时间；`reviewedBy/reviewedAt` 保存正式报告实际提交人。认领与转交均追加完整审计，原执行人、接手人、原因、时间和准确版本保留。历史空执行人保持未知，须明确认领后才能新提交，不能靠团队可见性或管理员角色代检。
- 新认领/转交提交稳定 `requestKey`、当前 `expectedStartedBy`（显式 null 或准确账号）、`expectedUpdatedAt`、准确 `sourceFingerprint`、原因，转交另填 `toUserId`。原键锁→案/实物/评审锁→锁后 fresh 当前账号、`qc:inspect`、本专业链 scope、开发源 L2 与凭据 ceiling；接手人须为当前可操作该准确来源的真实专业账号。仅当前执行人能转交，正式报告完成后不能覆盖其执行事实。
- 原请求精确重放返回原审计与 ACK，仍核对当前账号及来源权限，不把回执恢复当作重新获得执行资格。不同输入复用原键冲突；GET 只读，无补写执行人或历史。
- 独立路由挂入 `/api/v1/qc/development-sample-reviews/:id`：`GET handoff-context`、`POST claim`、`POST transfer`、`GET/POST evidence`、`GET evidence/:fileId`。既有 `start/complete` 保留；旧 start 不能抢占已认领任务，complete 必须是当前实际执行人。
- 附件复用 `qcEvidenceStorage` 的私有文件及原回执：实际图片/DOC/DOCX/PDF 字节校验，记录 SHA-256、大小、真实上传人/时间、准确评审 ID 与来源指纹。当前执行人上传；完成报告提交 `evidenceFileIds` 并再次核验原件、上传审计及归属，不能用外链或自填 metadata 伪装文件。旧报告已有文本/链接历史可读，不回填为已核验附件。
- 界面将准确来源与当前执行人、实际操作、附件、转交历史分区。每个原请求按真实账号与服务端地址恢复；提交未知时保留原键和内容。报告附件仅通过有当前准确来源读取权限的私有下载接口返回业务，不暴露私有存储路径。

## 6. 最小接口与判据

### 6.1 新增只读摘要（候选）

1. `GET /api/v1/dev/:caseId/business-workspace?sampleVersionId=...`：先 fresh `products:read` + `authorizeDevelopmentSource(write:false)`；返回案概况、实际轮次/工厂/版本索引、当前选择准确版本的节点摘要。无版本参数时只返回案级任务树，不能默认任选一个版本。
2. `GET /api/v1/orders/:orderId/business-workspace?orderLineId=...&productionBatchId=...`：先真实账号、`orders:read`、当前订单 L2；逐级核对 line.orderId、batch.orderId/lineId、factory 与当前 revision。无行参数只给主单/逐行摘要，不返回虚构整单履约资格。

成功统一 `{ok:true,data:WorkspaceContext}`。错误身份 401、当前无操作 scope 403、准确父源不可见/不存在 404、来源冲突 409、存储/授权不可完整核对 503/既有标准错误。服务端或客户端读取失败均显示“暂不能核对”，不能画成完成/无要求。

`WorkspaceContext` 最小形状：

```ts
type WorkspaceContext = {
  schemaVersion: 1;
  scope: { kind: 'development_case' | 'development_version' | 'order_main' | 'order_line' | 'production_branch';
    caseId?: string; sampleVersionId?: string; orderId?: string; orderLineId?: string;
    productionBatchId?: string; productionBatchRevision?: number; factoryRelationId?: string };
  contextFingerprint: string;
  overview: Record<string, unknown>; // 按 scope 白名单输出真实概况
  currentNodeIds: string[]; // 允许真实并行待办；不代表全部已完成
  nodes: Array<{ id: string; label: string; precedingIds: string[];
    status: 'locked' | 'current' | 'recorded' | 'blocked' | 'unknown';
    hasHistory: boolean; canOpen: boolean; canContinue: boolean;
    blockedReasons: Array<{ code: string; message: string }>;
    evidenceRefs: Array<{ kind: string; id: string; revision?: number; fingerprint?: string }> }>;
  childSummaries: Array<Record<string, unknown>>; // 真实版本/行/工厂分支摘要
};
```

金额、米数、数量与 BigInt 时间沿用准确字符串，不用 Number 破坏原事实。每个 `evidenceRefs` 必须能指回真实报告、确认、审批、分配/放行/批次修订或交接，不把名称/颜色/轮次序号当准确 ID。摘要不给未来表单的字段/对象详情；详情在打开合法当前/历史节点时才向既有接口读取。

### 6.2 显式继续命令（候选，无 schema 增量）

对应上述两个路径新增 `POST .../business-workspace/continue`，只接受准确 `scope`、`targetNodeId`、`expectedContextFingerprint`、`requestKey`。写操作要求 JWT、当前业务写 scope、fresh L2/开发源、凭据 ceiling，事务内锁准确父源后再读当前节点判据。不能用 body actor、前端 canContinue 或旧 token roles 作为权限。

返回 `{ok:true,data:{context,commandAck:{schemaVersion:1,requestKey,scope,targetNodeId,auditId,contextFingerprint,actorId}}}`。ACK 精确核对原对象、原键、目标与审计；未知结果保存原命令，保留“核对原继续请求”入口，即使后来门禁变化也可按真实权限核原回执。不能自动换键后声称原动作成功。

### 6.3 current-step 候选算法

1. 先建立**准确 scope**，再加载其自身原生事实与现有门禁；不是先读整案/整单 stage 再挑符合画面的数据。
2. 有效继续意图只激活其准确父源身份下的目标工作区；纯刷新/外部 QC 报告不产生意图。已有原生业务事实让对应节点成为可回看的已发生记录，缺意图不抹除历史。
3. 新案/新主单无意图时当前为录入/本厂任务；主单提交的实际审批成为当前审批待办。没有真实批准不能进入新履约。
4. QC/实际确认/放行资格变化只影响节点的 `canContinue` 和阻塞原因，**不自动激活下一节点**。用户点击继续后，下一节点才成为当前；页面保持用户选择，更新时不跳到未来。
5. 曾打开且尚未结束的并行节点保留为当前待办；某工厂/条目/分支阻塞不会改写兄弟节点。历史结果可读；最新失效只禁止新消费。
6. 缺明确版本、样品族、批次修订、真实审批或准确来源时是 unknown/blocked；不借父版、其他分支或整单 status 填齐。当前 source identity 改变时重新核对继续意图和实际门禁，旧意图及旧业务事实保持历史。

## 8. 有界验收

1. 面料/成衣入口：默认未选择时两类列表/未来表单均不挂载；选一类只加载该类。深链读回真实业务族；伪造类型/越权源失败。
2. 一个开发轮次两工厂：A 返样→专业 QC pass，A 转档解锁但未客户确认仍能转档；B 未返样仍受阻。A.1 无父版确认/通过继承，实际确认人和录入人分别读回。
3. 收到 QC pass 的摘要刷新后，下一工作区 DOM/网络请求仍不存在；业务明确继续后才挂载。原继续请求提交已成功但断 ACK，精确重试原键返回原审计，参数漂移冲突，权限收回后拒绝。
4. 两行主单一次实际审批：审批处理中不挂载新履约；批准后业务选具体行。一个成衣行有 A/B 工厂，A 的 PP/生产阻塞不盖掉 B；未来出运内容不能靠滚动、Tab、锚点或伪造 deep link 出现。
5. 全包行的当前内部分配 proof 冻结入 PP/放行；取消/缩量/来源改动只阻断受影响新消费，原 PP/放行/生产/出运历史仍能回看。中性分支不是已开产，不强迫面料生产完成才可 PP。
6. 真实完工与分批出运分开：订单主单旧 status 不改变精确分支当前待办；完工只改变生产事实，财务核销不把未来出运标完成。
7. 当前数据权限、L2/团队、scope、ceiling、账号停用、存储故障各有拒绝/未知验证；过去事实不借显示绕写门禁。新 GET 多次读取前后关键业务表/审计行数不变。
8. 浏览器检查 current/history 可操作与未来不可见，不只检查 `hidden` 样式或静态源码；中途改 scope/版本后不携带原表单给新对象。必要 TypeScript/定向测试通过后再提交隔离 PG 与浏览器联调证据。

## 9. 本规格验收口径

本规格当前是实施候选，源码盘点只证明现状。只有各准确 scope 的原生接口/审计回读、未来节点不挂载浏览器证据和不同真实角色的连续流程均通过，才可将覆盖矩阵对应条目标为已验证。纯测试通过、单页外观完成或旧阶段有值均不能替代这些证据。
