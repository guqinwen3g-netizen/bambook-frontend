# 变更与权限规则（历史稿，部分已被后续决定取代）

原稿日期：2026年10月6日。状态说明更新：2026年10月7日。本稿保留原讨论记录；当前有效规则以[对话设计决策总账](08-2026-10-06-对话设计决策总账.md)、[角色与实际分工](05-roles-and-responsibilities.md)及[冲突登记](../../../../artifacts/acceptance-20261007/global-design-coverage-matrix.md)为准。

本文件定义：谁能改、怎么改、改了留什么痕、什么时候必须作废重做。它是 [05-roles-and-responsibilities.md](05-roles-and-responsibilities.md) 的配套规则，供所有模块开工方案直接引用。

不得将本文整份作为已冻结的开工规则。后续已确认的原订单变更、业务/单证制作CI、财务登记核销和业务员经办采购/库存优先于本稿。本文关于主管/领导直接编辑业务内容的权限仍需按当前未决项核定，不能仅从其审批权推断编辑权。

## 一 基本原则：正式依据不可覆盖，只可作废重做

**这是全系统第一条铁律。**

订单、发票、报关单、CI、收付款核销等**已经形成的正式单据，一旦生成，其内容不可修改**。发现错误时的唯一合法路径是：

```
作废原单据（保留，不删除） → 新建单据（关联原单据，原样带过数据）
```

**为什么**：正式单据是财务、报关、客户、银行的依据。改了就对不上账、报不了关、追不回钱。

**不适用本条的情况**：业务对象本身尚未定稿（如草稿报价、开发中样品、尚未确认的订单）可以直接编辑，不需作废重做。区分标准见第四节。

---

## 二 三种身份必须分开记

同一个人在不同场景下做的事，系统里**必须记录为不同身份**，不得合并：

| 身份 | 何时使用 | 记为 |
|---|---|---|
| **审批人** | 在审批动作上签名（批准、驳回、特批） | `role-admin` / `role-super-admin` / 被授予审批资格的其他人 |
| **负责人** | 在日常业务动作上签名（建单、改单、跟进、确认） | 订单主负责人等业务责任归属 |
| **执行人** | 完成实际动作（业务员采购/库存登记、QC 提交结论、财务核销、后勤单证） | 真实经手账号及当时授权；不据模块创造岗位或资格 |

**关键规则**：领导平时进单子改内容，签的是**负责人/经手人**身份，不是审批人。只有在审批动作上才签审批人。

**为什么**：否则以后查"这单谁负责的"会乱 —— 领导日常改过就变成他负责这单了吗？不一定。审批身份和经营责任必须能分开追溯。

## 三 谁可以改，改了怎么留痕

### 3.1 修改权限

| 角色 | 建单 | 改单 | 审批时改 | 说明 |
|---|---|---|---|---|
| **业务员** | ✅ 唯一 | ✅ 唯一 | — | 订单主负责人 |
| **主管** | ❌ | ✅ | ✅ | 日常改=负责人身份；审批时改=审批人身份 |
| **领导** | ❌ | ✅ | ✅ | 同上 |
| **财务** | ❌ | 仅财务字段 | ✅ | 不改业务规格 |
| **QC/后勤** | ❌ | ❌ | ✅ | 仅限本专业域字段 |

**已确认**：Kevin 2026-10-06 —— 主管与领导**不需要走"申请-业务员代改-再审批"**的流程。他们有高权限，直接进单子改即可，变更记录兜底。这样减少了驳回-修改-再送审的沟通成本。

### 3.2 变更记录必填内容

**任何修改都必须产生一条变更记录，包含以下五项，缺一不可：**

| 项 | 要求 |
|---|---|
| 谁改的 | 真实账号 ID + 显示名 +当时的身份（负责人/审批人/执行人） |
| 什么时候 | 精确时间戳，含时区 |
| 改了哪些字段 | 字段名清单，不是"修改了订单"这种笼统描述 |
| **改前值 → 改后值** | 逐字段对照。**不记旧值等于没记** |
| **原因** | 见下方分级 |

### 3.3 改动原因分级

**普通字段**（备注、内部标签、跟进记录等）：原因选填。

**高风险字段，必须填原因，不得为空**：
- 金额、单价、数量、币种
- 交期、日期
- 客户、供应商、工厂
- 付款条件、贸易条款
- 已确认版本的规格参数

**为什么**：这些字段出错会直接造成财务损失或客户纠纷。变更记录的核心作用不是"留痕好看"，而是**出问题时界定责任**。领导改的价格导致订单亏损，有记录才说得清是谁的决定。

### 3.4 变更记录在哪里看

- **平时不主动显示**，折叠在详情页底部
- **点击展开**即可看到完整记录
- **谁都能看**（有该对象读权限的人）：包括业务员自己、同事、同团队成员、主管、领导
- 审批页与订单详情页看到的是同一份记录，不做两套

## 四 什么时候可以直接改，什么时候必须作废重做

### 4.1 状态判定

```
业务对象已定稿？ → 是 → 生成正式单据？ → 是 → 必须作废重做
       ↓否                              ↓否
    可直接编辑              可直接编辑（有状态门禁）
```

### 4.2 分模块的明确边界

| 对象 | 可直接改的阶段 | 必须作废重做的阶段 |
|---|---|---|
| **报价** | 草稿、已发送未接受 | 已接受转订单后；已开出发票 |
| **订单** | 草稿、未确认 | 已确认；但**已发货/已开票的字段只能作废重做** |
| **正式发票** | ❌ 永不可改 | 任何修改一律作废重开 |
| **报关单/CI** | ❌ 永不可改 | 任何修改一律作废重开 |
| **收付款核销** | ❌ 永不可改 | 只能冲回后重新核销 |
| **开发案/样品** | 全程可改（每次改留痕） | 不适用 |
| **成本核算 L3（单笔利润）** | 订单未结案时可重算 | 已结案订单被改动后，必须重算并留痕 |

### 4.3 已开票后要改数量/金额的具体做法

Kevin 2026-10-06 确认：**作废上一条，再重新新建。**

流程：

```
原发票标记「已作废」（永久保留，可查作废人/时间/原因）
        ↓
新建发票（关联原发票，原样带过客户/金额/数量/币种）
        ↓
订单同时可见作废前版本与现行版本
        ↓
已收款记录不受影响 —— 账实对得上即可，不因单据作废而动账
```

**财务影响**：作废重做**不产生资金变动**。已收的钱挂在订单上，新发票照样能核销。财务报表不出现"这笔钱找不到来源"。

## 五 变更不得静默影响已确认内容

**已确认的版本、规格、依据，不得被后续修改静默覆盖。**

- 报价接受后转订单，订单复制的是**那个具体报价版本**的规格，不是"当前最新价"
- QC 通过的是**某个具体版本**，后续改动该版本必须触发重新 QC（见 D05）
- 客户确认的是**某个具体版本**，该版本被改动后确认记录保留原样，并标注"确认对象已被修改"

**原则**：改动不产生"覆盖"，产生"新版本 + 明确的关系"。
