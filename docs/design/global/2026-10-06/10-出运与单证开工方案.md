# 出运与单证开工方案（实现契约 v0.3）

**状态：**业务边界以总账为准；本文件把已确认流程收口为实现契约。工程实现完成后仍须按覆盖矩阵独立验收。
**业务决策真源：**[对话设计决策总账](./08-2026-10-06-对话设计决策总账.md) §3、§5、§6、§8、§9。
**当前目的：**把订单履约到后勤单证、业务对客和财务应收之间的交接转成可执行的页面、状态和数据契约。
**MVP 排除：**电子报关、目的地到货/签收追踪、保险专门流程、在系统生成 Draft/Final B/L、信用证 OCR/自动审核、邮件发送。贸易术语、付款方式及信用证条款作为订单/合同原始业务资料留存；MVP 不由这些资料推导、自动判读额外的出运拦截条件。

> 本文不覆盖或改写总账已确认的业务决定。代码状态名是内部实现枚举，界面需显示清晰中文阶段；字段和页面细节依用户授权由设计方收口，coding agent 不得另造业务规则。

## 1. 目标和边界

出运操作分成四个责任段：

1. **业务员准备并发起：**在订单条目/工厂履约分支确认本批计划出运范围、客户和收货方后提交系统交接；若该分支已全部生产完成，另登记最终实际生产数量。生产完成量尚未知时仍可按工厂本批出运确认发起，不推算总产量。
2. **后勤单证核实并制单：**从货运/出运工作台接收待办，联系工厂取得最终装箱资料，按实际物理出运建立装箱明细、制作 CI 和 Packing List、准备订舱，并登记系统外完成的出口申报状态和凭证。
3. **业务员联系客户：**后勤完成后把 CI、Packing List、订舱/出运信息退回来源业务员；业务员在线下发送开船前需要的客户文件，并在系统登记发送事实。
4. **财务登记账款：**出运 CI 进入财务应收待登记视图；财务登记票据、收款并执行一笔或多笔收款对一张或多张 CI 的核销。财务不负责订单生产、出运是否完结，也不制作 CI。

系统不再要求业务员另做纸面《出运通知单》再交给同公司后勤。出运请求本身就是结构化交接记录，接收方在自己的模块待办中看到。系统复制原订单条目和客户/收货方信息，禁止重新录入同一组基础订单事实。

## 2. 操作对象和追溯关系

| 对象 | 含义 | 创建/维护方 | 必须关联 |
|---|---|---|---|
| 出运请求 | 业务员提出的一次出运交接；包含一个或多个合格来源条目 | 业务员 | 客户、收货方、产品板块、订单条目、工厂分支、请求数量 |
| 物理出运 | 实际一票海运或空运；承载订舱、实际装箱、离港事实 | 后勤单证 | 一个出运请求；实际装箱行；实际运输方式 |
| 出运明细 | 本物理出运中某一来源条目的实装数量 | 后勤单证录入；系统回写累计 | 原订单条目、工厂分支、请求明细 |
| 包装明细 | 某包装件及其内容；按 PL 需要记录包装信息 | 后勤单证 | 物理出运、出运明细/产品、箱号 |
| CI 单据 | 本次实际出运商业发票；按合同/信用证要求划分文件包 | 后勤单证制作 | 出运、合同/信用证、实际出运条目；财务应收记录 |
| Packing List | 本票物理出运的装箱单；需要分列时可拆成多份 | 后勤单证制作 | 物理出运、包装明细；必要时按合同/信用证拆分 |
| 外部出运文件 | Draft/Final B/L、空运运单、信用证、产地证等外部方出具文件 | 后勤单证/授权经办人归档 | 物理出运及适用订单/合同 |
| 出口申报记录 | 系统外办理出口申报的状态和凭据 | 后勤单证记录 | 物理出运、完成时间、外部凭据 |

同一出运的每条明细始终保留来源订单、订单行、工厂履约分支和实际数量。合并出运只合并物理物流批次，不合并或覆盖不同来源业务的履约事实。

## 3. 谁能把哪些订单条目放入同一出运

### 3.1 已确认规则

- 一票出运可以组合多个订单、多个条目。
- 组合的条目必须属于同一客户且同一收货方。
- 面料和成衣必须分成不同出运记录。
- 每个出运明细分别链接原订单条目、工厂分支和批次。
- 订单行可分批出运；业务员根据合同/信用证在订单行明确记录 `partialShipmentAllowed`。明确禁止时，只允许一次性按订单行全量申请出运；禁止系统 OCR/自行推断条款。
- FOB/CIF 均在实际开船/起飞前完成出口清关。贸易术语和付款方式分别按合同记录，不由软件推导出不同申报工作流。
- 出运方式仅海运、空运；不增加独立保险字段或保险门禁。

### 3.2 合并边界和创建校验

1. 出运入口先选面料或成衣；该选择锁定本次出运板块，不能混入另一板块。
2. 首条来源确定客户、收货方、板块和运输方式；后续只允许添加这四项一致、仍有可出运数量且通过逐条目/工厂分支门禁的来源。客户或收货方不同则提示“该条目与当前出运的客户或收货方不同，请另建出运”。
3. 客户、收货方和业务板块直接从已审批订单读取，不在出运请求中新增或改写；要更换收货方先走订单变更审批。
4. 同一次物理出运必须只有一种运输方式，海运或空运。订单业务录入时人工记录合同/信用证是否禁止分批；明确禁止的订单行不能再发起后续分批交接。不做 OCR，也不自动解释信用证。
5. 默认同一客户、收货方、板块、运输方式下的合格条目可以合并。Packing List 默认一票一份，逐行保留来源订单/合同和订单条目；CI 按销售合同/信用证要求分组，同一合同/信用证的多条来源可列在同一份 CI，不自动合并不同合同/信用证。外部客户要求的其他分列由后勤按人工确认的适用范围制作。

## 4. 订单条目侧：生产完成与发起出运

### 4.1 生产完成

工厂确认某一生产分支已全部生产完成后，业务员在该条目/工厂分支的当前步骤点击 **“完成生产”**。弹窗至少包含：

| 字段 | 规则 |
|---|---|
| 实际完成数量 | 必填；按订单行单位录入。客户明确要求按尺码判断时，成衣改为逐尺码录入；否则不增加逐尺码完工数量表 |
| 是否该生产分支已全部完成 | 必须为“是”才可提交此动作；不完整的阶段数不得冒充最终完工数 |
| 工厂确认依据 | 记录业务员确认本批可出运的日期；依据备注/附件选填，不要求上传工厂文件 |
| 完工数量判断时点 | 仅当该订单条目的所有生产分支都登记为完成时，系统才汇总各分支最终完工数量并按客户允差（没有客户标准时按公司内部标准）作条目级判断；超范围须进入需求方接受或补产处理，不能仅因某一个工厂分支完工就提前把全条目判为短产/超产 |

QC 的过程检验阶段数量仅用于风险提醒，不作为最终数量。分批出运本身不构成短产；最终判断使用工厂确认整条生产分支完成后业务员登记的实际完工数量。

### 4.2 发起出运

在符合当前步骤及 QC/需求方门禁的条目或工厂分支内点 **“发起出运”**。多来源条目合并时，允许从货运工作台创建后添加满足第 3 节条件的条目。

**业务员录入字段：**

- 出运客户：默认从来源订单带入，只读。
- 收货方：从来源订单带入并只读；订单上信息有误先走订单变更审批。
- 出运方式：`海运` / `空运`，必选。
- 本次计划出运数量：逐订单行/工厂分支填写，必填，单位跟随订单行。若该分支已登记最终生产量，累计计划出运量不得超过已登记生产量扣除已有出运/有效预留后的数量；若尚未全部生产且最终生产量未知，按工厂对本批可出运量的确认记录计划量，精确可装数量由后勤随后核实。任何情况下都不把未生产余量或计划出运量直接判为短产。若订单行 `partialShipmentAllowed=false`，同一条目必须等所有生产分支完成并完成数量允差/客户接受或补产处理后，只允许一票覆盖其最终可交付总量的出运；不能把“不可分批”误解成最终实装必须机械等于合同数量。已有非取消出运后不能再为该行发起第二票。
- 生产状态：显示已登记的最终生产数量及全部生产分支完成状态；业务员不在出运弹窗重复录入。
- 计划出运日期：选填；不以该日期作为“已出运”。
- 工厂可出运确认日期：必填，由业务员确认本批已具备出运条件；工厂文件/聊天记录附件选填。
- 对后勤单证的备注/附件：选填，用于特殊包装、分票或客户文件要求。

系统保存后生成唯一出运请求编号、按明细锁定本次计划范围、生成后勤待办，并回写原业务条目“已发起出运/待单证处理”。系统不得因为请求已发起而扣减已生产数量或记为已经出运。

## 5. 后勤单证工作台

### 5.1 工作台布局

货运/出运模块提供以下固定视图。业务发起交接后，工作台依据现有 **LOGISTICS** 角色展示物流待办，不新设单证岗位或“单证主管”角色：

1. **待物流接手**：业务新提交、物流尚未接手；显示编号、客户、收货方、面料/成衣、海运/空运、来源订单/条目数及发起人。
2. **物流处理中**：物流已接手，正在向工厂核实本批装箱资料、制作 CI/PL、订舱或登记系统外出口申报凭证。
3. **待业务决策**：实装范围或关键数量与业务请求不一致，物流已填写逐行差异和原因并退回；业务在来源订单处理后再交回物流。
4. **资料已回业务**：物流已完成本阶段单证准备，CI/PL 和相关资料回到原订单；这只表示交接回程完成，不代表客户已发送或货物已出运。
5. **已出运**：按现有 Shipment 事实读取实际 ATD/起飞时间；不继续显示到货、签收、POD 阶段。

物流点击 **“接手处理”** 后记录经办人和时间；重复接手不得覆盖原经办人。处理动作仅限现有 LOGISTICS 角色且具 `shipments:write`；业务发起校验对全部来源订单行的 `orders:write`；差异答复和取消只允许原业务发起人操作，并在每次操作时重新校验来源订单写权限。不新增角色，也不因业务账号具有一般运单写权限而允许其执行物流处理。

### 5.2 出运详情页

页面采用一屏聚焦当前步骤：顶部固定显示出运号、当前阶段、客户/收货方、运输方式、业务发起人；主区按顺序显示 **来源范围 → 核实与装箱 → CI/PL → 出口申报/订舱 → 回业务/等待离港 → 已出运**。已完成步骤可回看；未来步骤只在进度条显示，内容锁定。当前操作完整并保存后才解锁下一步。

详情页面板：

- **来源范围（只读）**：订单号/合同号、行号、产品档案或开发关联、工厂履约分支、订单数量、最终生产完成登记（已登记的最终数量；未登记时明确显示“未知/未登记”）、历史已出运数量、本次业务计划数量、尺码矩阵（仅服装适用）。本批计划量、逐次实际出运量和全量生产完成量必须是独立数据；未登记完工时禁止从计划量或已出运量推算。
- **装箱核实（后勤录入）**：复用既有运单装箱与出运条目数据，不再建立第二套装箱台账。逐箱/卷记录箱号或卷号、包装唛头、来源订单行、款号/布种、颜色、成衣尺码（成衣）、卷长度（面料）、件数、数量与单位、净重、毛重、包装尺寸/体积；按实际工厂资料录入。逐箱/卷合计必须与本票出运条目数量一致；工厂装箱单/确认附件选填。
- **差异检查**：系统将本次实际装箱总量与业务请求数量逐条比较；完全一致显示“与业务请求一致”。如果实装范围或数量不同，后勤不得静默改业务确认的范围，须点 **“退回业务确认”**，附差异行、差异原因及相关凭据；业务员确认修改或取消本次范围后，后勤才可继续。仅补充的箱号、重量等后勤专业字段可由后勤直接更正。
- **CI / Packing List**：显示应出具的文件包，数据带入来源订单、已核实装箱明细和合同/信用证条款；后勤复核、生成可下载文件并维护版本。
- **出口申报**：系统外办理；状态 `未完成` / `已完成`，完成时录入完成日期、申报编号（如适用）和凭证附件。未完成时不得进入“待开船/起飞”。
- **订舱/运输**：后勤登记订舱状态、承运人/货代、订舱号（有号时必填）、计划出运日以及海运船名/航次或空运航班信息（已取得时填写）。状态“已订舱”只表示已安排运输，不表示已出运；没有实际离港/起飞事实时不能标为已出运。
- **外部文件**：归档外部专业方提供的 Draft/Final B/L、空运运单、信用证、产地证等；按文件类型、文件日期、来源合同/出运关联并保留原文件版本。系统不生成这些单据，也不把 Draft B/L 当作实际离港证明。
- **操作记录**：显示经办人、操作时间、状态变更、退回理由、文件版本、业务确认及实际离港信息。

### 5.3 出运单据包规则

- 一票物理出运默认一份 Packing List，汇总实际装箱内容；每行保留来源订单/合同/条目。客户明确要求分列时，可针对实际需要生成不同文件版本并写清各自范围。
- CI 按销售合同/信用证要求分文件；同一合同/信用证覆盖多个来源条目时可在一份 CI 列明本票实际出运内容，不同合同/信用证不自动合并。财务按每一张已签发 CI 登记应收。
- 若业务录入的合同/信用证明确禁止分批，系统阻止对同一受限订单行发起第二次出运；不做 LC OCR 或自动条款解释。
- CI/PL 版本记录单据编号、版本号、生成时间、制单人和适用出运明细。已生成版本不静默覆盖；修改后生成新版本。
- CI/PL 使用现有业务单据模板和生成服务；本轮不新建重复字段仓库。出运界面只补齐当前模板确实需要、且工厂实际装箱资料能提供的字段。

## 6. 单证处理完毕后：业务员发送客户文件

后勤单证点击 **“完成单证并退回业务”** 时，系统校验：

1. 请求范围中的所有实际装箱明细已填并完成系统一致性检查。
2. 适用的 CI 与 Packing List 已生成，且金额/数量来自本次最终出运数据。
3. 出口申报已登记完成并附凭证。
4. 订舱信息已登记。
5. 存在的流程差异已由业务员确认。

满足后，交接进入 **“资料已回业务”**（内部状态 `ReturnedToBusiness`）。这是物流准备阶段的回程状态，不是 Shipment 的实际出运状态。后勤单证不得以此操作替业务员发邮件或联系客户。

业务员收到原业务模块待办，详情显示已生成的 CI/PL 文件、版本和实际出运信息。业务员通过线下渠道发送后点击 **“标记已发送”**，填写收件人和发送日期，允许附邮件/发送凭证（附件为建议项）。每个单据版本分别记录发送事实；文件后续更新时，新版本需重新标记已发送。系统不要求客户回执、不集成邮件发送。

CI 生成后同步给财务形成 **“待登记应收票据”**；票据需包含 CI 文件、金额、币种、付款方、来源合同、出运号和来源订单行。财务登记入口不阻塞业务员发送客户文件或物流实际开船，除合同/信用证业务门禁另有明确要求外，财务状态不得被用来判断订单生产已完成。

## 7. 订舱、出口申报与实际出运状态

### 7.1 出运前

- 海运、空运分别提供自己的基本运输字段，不暴露陆运/铁路/快递/自提选项。
- FOB/CIF 与空/海运方式分别记录，不能将 FOB 等同于“免出口申报”，也不能由运输方式推断贸易术语。
- 实际出口申报发生在系统外。系统只记录 `未完成` / `已完成` 和凭证；FOB、CIF 均要求实际开船/起飞前完成出口清关。
- CI、Packing List 在开船/起飞前提供客户进口清关准备，并由业务员标记已发送。
- Draft B/L 或其他外部预审文件不代表货物已离港，不得使状态变为“已出运”。

### 7.2 实际离港/起飞

后勤在取得船舶实际离港或航班实际起飞信息后点击 **“登记已出运”**，录入实际离港/起飞日期时间及凭证/来源。系统校验出口申报完成、适用 CI/PL 已准备且业务员已登记开船前发送；若任一不满足，阻止完成并指出缺项。Draft B/L、订舱、计划 ETD、CI/PL 生成都不能替代实际 departure 事实。

状态此时改为 **“已出运”**。海运可标实际离港/ATD；空运可标实际起飞时间。MVP 不建立目的地到货、签收、POD、进口清关或保险阶段。

### 7.3 取消/作废

- 后勤尚未接手的 `PendingLogistics` 请求，仅原业务发起人可取消；必须填写原因，系统写入取消事件并释放该请求的计划数量占用。原请求和事件保留，不删除。
- 后勤已接手后，业务不能绕过工作流直接取消。物流发现该票无需继续时，先将请求退回；仅原业务发起人可在来源业务待办中选择“取消本次出运请求”并填写原因。系统只在无有效 CI/PL、无有效订舱、无已完成出口申报、无实际离港/起飞事实时接受取消，并在同一事务中释放尚未实际出运的计划占用。
- 已生成或已对外发送的 CI/PL、已订舱或已完成申报不能被静默删除或覆盖。若已有这些事实，必须先通过对应单据/后勤流程记录作废、取消或更正凭据；MVP 无法确认这些副作用已有效撤销时，取消操作阻断并明确列出需先处理的事实。已实际离港/起飞的出运不可取消，只能保留出运事实并另走业务售后/财务更正。
- `Cancelled` 记录保持可查；取消后如需重新出运，创建新的出运请求并重新走资格门禁，不能复活旧请求或复用已作废文件状态。

## 8. 财务回程和订单读回

- 后勤单证生成出运 CI 时创建/更新关联的应收来源；不可让财务人员先建一张空应收单来作为 CI 的前置条件。
- 财务在财务模块只登记收到的 CI/其他已开票据、实际收款和核销分配。支持一笔客户收款核销多张 CI，也支持一张 CI 被多笔收款分次核销。
- 业务员在原订单/出运页可只读查看 CI/PL 版本、对客发送记录、财务已登记/部分收款/已核销余额；业务员不可直接改财务实收与核销数据。
- 订单条目与出运视图累计每次实际装箱/出运数量；出运事实不覆盖业务员在“完成生产”时登记的最终生产量。订单履约完成与应收结清是不同状态。
- 取消、重开、短装补产、客户接受数量偏差的回程规则须分别保存；不得把财务结清当订单完结，也不得由单证“已出运”自动结清订单所有条目。

## 9. 字段级 MVP 规则

### 9.1 CI（由业务/后勤制单，财务只登记应收）

- 发票编号、发票日期、卖方、买方/收货方、通知方（如适用）、来源销售合同/PO、币种、贸易方式、付款方式、运输方式、起运地/目的地、装运日期或预计日期、货物描述、规格/款号、数量与单位、单价、行金额、总金额、原产地（如要求）、签章/签发人。通过订单/出运记录带入已有信息，最终CI可下载并保留版本。
- 每份 CI 的来源合同、订单行和本次实际出运明细为可追溯关联；数量、单位、单价、金额带入合同/订单和经后勤核实的本票装运事实。若模板需要手工调整，必须留下改后值和版本，不能覆盖原订单或本票实际装箱记录。币种和合同价格按原订单记录；不做自动汇兑或另造税务计算。

### 9.2 Packing List（后勤制单）

- 装箱单编号、日期、卖方、买方/收货方、来源合同/PO、出运方式、起运地/目的地、唛头、箱号/件号、箱内商品/订单行、款号/布种/颜色、尺码（成衣）、卷号/长度（面料）、件数、数量与单位、净重、毛重、尺寸/体积、总件数/总净重/总毛重/总体积。
- 成衣箱内明细逐款、颜色、尺码和数量记录；面料逐布种、颜色、卷号、长度和数量记录。箱号/卷号、包装件数、净重、毛重、体积按实际装箱资料填写；没有适用值的包装属性可留空，出运总量与明细数量须精确一致。

### 9.3 海运/空运信息

- 共用：货代/承运人、订舱号、计划出运日、实际离港/起飞时间、起运港/机场、目的港/机场。
- 海运：订舱号（承运方已提供时）、船名、航次、起运港、目的港；提单作为外部文件归档。整箱/拼箱属性不单独建业务门禁，实际使用时可记在运输备注。
- 空运：航班信息、空运运单外部文件；本方案不要求系统生成 AWB。
- 合同/LC 原件作为业务文件保存；业务员在订单行手工记录是否允许分批出运以及需要的单据拆分范围。其余 LC 条款由业务/后勤人工核对；不自动 OCR/解释 LC。

## 11. 必须覆盖的连续验收用例

1. 一条成衣工厂分支完成生产：业务员录最终生产数量；符合门禁后发起海运；后勤核实装箱、制 CI/PL 和订舱，登记出口申报凭证；业务员标记开船前已发送 CI/PL；后勤录实际 ATD；财务待登记 CI 收到并登记，一笔收款后订单只读显示财务进度而不改变生产状态。
2. 一票出运合并同一客户/收货方的两个订单条目，保留各自数量/工厂/合同来源；CI 依合同拆为两份；PL 默认合并；订单行出运累计分别正确。
3. 试图把不同收货方、不同客户、面料与成衣放在一起，界面不可加入并给出明确原因。
4. 后勤实际装箱数量不同于业务请求：系统提示差异并阻止制单完成；后勤填写原因退回；业务员批准调整后后勤继续。不得出现后勤静默改数量。
5. 条目可继续生产、当前先出一部分：本次出运量写入交付累计，但系统不把尚未生产的数量判为短产。
6. 生产分支全部完成后业务员登记低于/高于适用允差：系统执行订单定义的客户标准优先、内部标准兜底；超范围需客户/需求方接受，未接受短产进入补产路径；按条目数量与出运数量分开计算。
7. 订单样 QC 通过但需求方确认尚未完成时，不能发起正常出运；生产 QC 存在未解除 NOK 时，只阻止受影响分支，不连带阻止同一客户下其他合格分支。
8. Draft B/L 已上传但没有实际离港记录，状态仍不为已出运；计划 ETD 到期也不能自动标为离港。
9. 出口申报未登记凭证、CI/PL 未制作、业务未标记发送任一项缺失时，不能登记开船/起飞。
10. CI 新版本生成后，旧版本和旧发送事实仍可查看；新版本未发送前不可将客户文件状态显示为当前已发送。
11. 一笔回款分配到多张 CI、一张 CI 由多笔回款分次核销；财务页面和对应业务模块分别显示正确的余额，不产生“订单已完成”或自动清账假象。
12. 海运、空运入口字段分别适用；老的 Land/Rail/Courier/Pickup 不能从主流程继续选择；不显示保险流程和到货后流程。

## 12. 实现与验收边界

- 同票仅允许一个客户、同一收货方和同一业务板块；面料和成衣分开。一个订单行可以按多个工厂分支分别保留来源，但 ShipmentOrderAllocation 按订单行汇总；工厂批次预留逐条保存。
- 业务交接按具体订单行/工厂分支提交；交接状态与现有 `Shipment.status` 正交。后勤完成只回业务，不得把运单改成 `Shipped` 或写入 ATD。
- 物流差异退回必须被来源业务明显收到；业务答复后原差异和原数量保留，交接回物流继续处理。
- 对客发送继续复用订单页既有 CI/PL 精确版本归档与线下发送历史；不得复制一套发送流水。实际离港继续复用既有 Shipment ATD 与出口申报凭证门禁。
- 每个数量字段均标注所属口径：订单数量、计划出运数量、后勤确认的箱/卷实装量、逐次实际出运量、最终生产完成数量。未登记的生产完成量显示未知，不可从其他口径倒推，也不阻断允许的分批出运。

## 13. 当前发现的实施前置缺口

只读代码审计发现，现有模型尚缺数项能支撑第 10 节出运门禁的权威事实。交接首片可以建立耐久状态链并返回具体阻塞原因，但不得在这些事实落地前宣称资格链已经完成：

1. **订单行必需样品配置：**订单行当前没有权威的样品族要求字段。订单行新增并冻结 `requiredSampleFamilies`；服装为 `garment_pp`、`garment_ship` 固定必需；面料为 `fabric_eps`、`fabric_ss` 固定必需，`fabric_rc` 为可选且由业务员在录入订单行时明确选中/未选。已有订单缺失该配置时不自动猜测或放行，需通过受控订单变更补齐。
2. **逐样品族资格：**按实际生产批次逐一检查该订单行已配置的所有样品族，必须由准确当前来源覆盖该批次，并同时具有有效 QC `passed` 报告和该次寄送后的需求方 `approved` 确认。缺少、失效、失败、过期或范围不符一律列为该批次阻塞原因。
3. **生产 QC NOK 解除：**增加有来源的未解决问题记录，至少绑定订单行、生产批次、批次修订和失败报告。失败生产检验形成未解决问题；QC 后续复检追加报告并显式引用要解除的问题，成功且范围/修订有效后才关闭该问题。出运资格只查询所选批次未解决问题；读取失败、批次已变更或解除凭据不全时 fail-closed。QC NOK 不阻塞同订单其他独立合格批次。
4. 不得复用 `resolveQcCoverage` 的范围指纹、旧整单 Final-QC gate、`ReleaseScope` 的通用暂停状态或旧样品进度 JSON 冒充上述业务资格。
5. **分批出运条款：**订单行需要人工保存 `partialShipmentAllowed`。新订单进入审批前必须明确填写；旧订单为 null 时出运 fail-closed 并要求补齐。false 表示该订单行只允许一票实际出运，因此只有在该行所有有效生产分支完成、数量允差和需求方接受/补产处理完成后才允许创建唯一一票，计划数量覆盖最终可交付总量；不得用合同数量替代缺失的最终完工数量。true 时可按已生产且未预留/出运的数量分批。此规则由订单业务数据显式输入，不读 OCR 或推断信用证。
- 交互遵守渐进式业务页面原则：固定显示完整进度轨迹；已完成步骤可回看；当前步骤显示且仅显示当前可执行表单；未来步骤只能在轨迹上提示，不显示其字段/按钮；保存并满足门禁才解锁下一步。
- 取消、不可逆已发单据的修订策略及订单主单审批衔接按既有订单权限/审计契约处理；不得通过删除历史记录消除已经发生的交接、对客发送或实际出运事实。
