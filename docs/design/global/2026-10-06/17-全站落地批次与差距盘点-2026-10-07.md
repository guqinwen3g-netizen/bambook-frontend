## 2. 第一批明确实施接口

### A. 业务员订单操作与正式商业承诺边界

依据 08 §5.1、5.2、5.6、5.7、14。真实业务员有 `orders:write` 且在当前订单可操作范围内时，可以维护草稿产品行、选择准确来源、建立/拆分工厂分支和执行业务恢复。每个请求仍从数据库重读账号/权限、保留凭据上限、校验来源范围并在事务内锁原对象。

- 草稿：允许增删产品行、编辑商业字段；提交审批后全部冻结。退回后恢复草稿编辑，保留原审批轮次。
- 正式订单：一般备注/联系信息修正可审计保存；新增/删除条目或改变数量、规格/尺码、币种、价格、付款、交期、目的地、供应责任等必须进入原单变更，不经通用 PUT 偷改。
- 来源选择：已批准商业依据不能静默替换；缺失历史依据不能猜造。工厂分支与 QC 恢复属于履约动作，保留其独立门禁，不要求业务员取得虚构采购/仓储岗位。
- UI 的创建/来源/分支/恢复按钮与服务端能力一致；禁用时显示具体原因。未知回执保留原请求键重试。

验证：业务员可操作自己的合法草稿；待审及正式商业增删被拒；越范围/撤权/受限凭据被拒；履约可由合法业务员继续；备注审计真实前后值；原角色正例不退化。

### B. 开发准确版本 QC、确认与复评

依据 08 §4.1–4.5、6.2、7。`DevelopmentSampleVersion.id` 是准确开发成果身份；大版与点号版各有自己的正式 QC 和需求方确认。实物引用原有 `SampleBatch`/`SampleCardItem`，无新实物小版本不创建假库存。

- 发起正式 QC 明确选择准确版本；报告冻结该版本及被评审实物上下文。点号版没有自己的通过报告时，不继承父通过，不可转档。
- 复评对同一版本追加新任务/报告，原报告保留；不强迫业务造新实物来绕过“一批一报告”。最新有效结果决定门禁，旧请求按原键返回原报告。
- 确认记录分别保存实际确认方类型（客户/内部需求方）、确认人/机构、确认时间、结果及依据；系统另记录入人/时间。确认人和录入人不能混称。
- QC 正式通过的准确版本即可转产品，不等客户选用；查通过报告时精确限定完成审计及该报告，不以无序 `findFirst` 误取发起/认领审计。
- 返样保存即同步相同仓库实物；不新增 QC 后“登记入库”、在途、样品管理员或二次仓库确认。
- 权限由当前开发来源负责关系/团队和专业 QC 能力核验，内部开发无客户不等于无权或全公司可写。

验证：R1-A、R1-B、R1-A.1 各自独立；父 pass 不让小版通过；同版 NOK→复评 pass 保留两份报告；未客户选用也可在 QC pass 后准确转档；真实确认人读回；撤权/其他开发案/重复与未知回执；同一实物仓库数量不复制。

### C. 后勤登记本次实际装运与差异回程

依据 08 §8.1–8.3。新增出运交接下的实际装运命令，由具备后勤单证操作能力的真实账号在已接手的交接中执行，多角色/授权主管仍可协作。计划范围不变；记录逐来源订单行、工厂分支/批次、计量单位及实际量。

- 仅处理中交接可以登记；请求包含稳定幂等键和预期交接修订，服务端重读账号及准确来源后加锁。
- `actualQty = null` 表示未录；零表示已核实为零。数量需非负、单位与来源一致、不超过可用物理范围。
- 计划与实装一致时保存实际事实并开放装箱；有差异则保存核实结果、说明并退原业务员确认，后勤不静默修改拟出运计划。
- 业务接受/调整从原差异任务处理；完成后后勤继续原交接。未知回执重用原键；同键不同内容拒绝；已归档/已实际出运的事实不可覆盖。
- 装箱、CI/PL、出口申报、回业务和对客发送均消费同一准确实装事实；不以“有一张运单”代替可用装运范围。

验证：新交接实际量为空→后勤接手→录实装→装箱→CI/PL；差异退业务并回后勤；并发/重复/过期修订；业务与财务不能绕过后勤动作；原计划和已完成事实保留。

### D. 内部订单身份与外部 PO

依据 08 §5.1、5.2。`Order.id` 是内部关联键，`Order.code` 是内部唯一订单号；`poNumber` 只保存实际客户 PO/合同引用，可空，不自动从订单号、报价号或开发号生成。同一外部 PO 可分别建立面料单和成衣单，独立审批、履约。

- 新手工、开发转单、报价转单及复购草稿由服务端生成内部订单号。历史缺失编号只读显示原 id，不倒填假外部 PO。
- 产品行、库存归属、代理业务命令与开发关联优先提交准确内部 id；兼容输入外部 PO 时，只允许唯一匹配，多个匹配返回明确 409，不能选第一张。
- 所有身份查找仍在当前对象数据范围内执行；限定客户/业务域的外部引用可明确消歧。
- 旧解析导入仍仅为特权历史迁移入口，不能恢复成当前 PO 自动识别功能；不得因共享 PO 改写另一业务主单。

验证：同客户同外部 PO 的面料/成衣双单和内部无 PO 单；准确行归属、独立审批与下游回链；歧义/越权/旧引用/重复请求。

### E. 专业 QC 执行权限

依据 08 §2、7、14。业务派单、回看报告和业务决定与专业检验分开。`qc:write` 保留业务协作；新增 `qc:inspect` 控制正式检验执行，默认仅内置 QC 岗位取得，其他账户须明确授权。管理员身份本身不代替专业执行权限。

- 指派对象必须持有当前专业执行能力；普通业务员不能给自己派单后借“当前执行人”绕过门禁。
- 开始和完成检验均重新读取实际账户及权限上限；开发评审还校验面料/成衣专业链能力，生产检验保持准确来源/工厂分支约束。
- UI 按业务派单与专业执行分别显示动作；旧 token、停用账户和撤回执行授权不能继续提交报告。

验证：业务员自派被拒、正确专业 QC 成功、准确分支约束、撤权与凭据上限；源业务可继续读回真实报告及执行明确恢复。

## 3. 其后批次与全站验收顺序

1. 将上述差距先修成可操作连续链路，再补内部/外部订单身份、履约模式及内部面料米数分配、准确产线与 QC 尺码覆盖、条目步骤 authority 和逐步显露界面。
2. 接通开发 CI/出运 CI→财务、采购/加工审批与回交、异常/复验/数量接受/补产、商业变更和售后历史；明确总账仍待定的商业处置，不捏造用户决定。
3. 其余31入口逐模块设计/实现/验证；共享账号、通知、附件、搜索与报表读取同一权威事实。每个模块单列实际角色和负向权限证据。
4. 真实 HTTP/Postgres 和浏览器验证先使用本目标专用的新隔离集群、合成业务数据和端口，明确核对数据库身份。依 08 §17 的后续明确授权，可在实际 dev 的完整备份恢复、迁移及全剧本演练通过后重建 `panda_hub_dev`，并固定业务时间；Panda Hub Local 和 Empty 不处理。隔离建库证明新环境可运行；迁移升级需要另做旧schema→增量迁移→差异为零及历史数据保持验证，二者不混称。
5. 固定每批源码哈希后跑对应测试、类型与构建；不在同一全量测试运行期间改被测源码。最终按总账正向逐条验收、按新写入口反向查业务依据；有任何缺失、未验证或待定项，不报告全站完成。
