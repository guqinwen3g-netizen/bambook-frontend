# 开发费用 CI 交接实施规格 · 2026-10-07

## 1. 已确认依据与范围

唯一对话决策依据为 `08-2026-10-06-对话设计决策总账.md` §4.5（147–153 行）、§8.3（457/465 行）、§8.4（482–488 行）。业务员在当前开发页开具客户 CI；财务登记已开票据、真实收款和多对多核销；开发页保留原票与账款回读。开发结束不由财务控制。

下文未由总账逐字段指定的实现细节均为**本目标实施选择**，不冒充新增用户确认。不新增数据库模型；复用 TradeDocument、DocumentVersion、Invoice 的来源唯一键和 InvoiceAllocation。

## 2. 页面与渐进操作

开发案当前页增加“开发费用 CI 与回款”区域，与实际成本/费用核齐和收费方案相邻。首先展示真实费用明细、按币种汇总与本案收费方案。费用是实际成本，CI 金额是业务对客收费，禁止由成本自动推断收费或换币。

| 字段 | 数据与校验（本目标实施选择） |
| --- | --- |
| 收费来源 | 当前案的有效开发收费草稿；绑定 BillingItem ID、工作流版本、当前金额/减免/币种及费用覆盖快照；不同案或已有财务票据不可重复开新票 |
| 客户抬头/地址 | 从本案真实客户档案带入，业务核对后填写票面快照；客户 relationId 不允许改为另一客户 |
| 我方抬头/地址/银行 | 从当前配置带入，业务核对；签发必须明确我方名称，银行信息可按实际填写；不伪造默认事实 |
| 币种与净额 | 与收费来源一致，Decimal 四位；净额 = 拟收 − 减免 − 已明确抵扣，须大于零；不修改成本，不自动换汇 |
| 日期/到期/付款条件 | 开票日期必填 YYYY-MM-DD；到期日可空且不得早于开票日期；付款条件业务明确填写，不从贸易术语推断 |
| 费用行 | 固定来源 ID、类型、金额、币种、日期、寄样事实（如有）；票面为整案开发费总额，制作费不强拆件单价 |
| 说明 | 本票收费说明；成本与对客收费差异可见；不同币种成本分组呈现，不裸加 |

按钮：读取/刷新依据 → 保存 CI 草稿 → 查看草稿 → 签发 CI → 查看/下载原票。业务写权限基于 fresh `products:write`、当前客户 owner/team-followup 或实际 all 范围及签名 ceiling；不要求财务写权限。只读业务按真实案/客户可见范围查看。

保存草稿绑定当前收费与费用 fingerprint；编辑草稿新增 DocumentVersion，CAS 当前版本；签发再次锁定并核对案、收费、全部费用来源和版本。已签发版本不可覆盖，不通过财务修改票面。费用后补使旧草稿需刷新；已签发历史原票仍按冻结快照可读，不因后续费用改变而重建。

本切片不新增“必须先结案”“必须财务审核后业务才能签发”的门禁。现有费用核齐/收费审批事实若存在则准确呈现；不把财务制单任务当业务开票许可。零净额是无应收事实，不伪造零金额 CI 或已收款。已进入旧财务开票链的历史收费保留可读，不自动迁移为业务 CI。

## 3. 来源与状态

TradeDocument：type=CommercialInvoice、domain=finance、sourceInvoiceId=null、sourceRef=`business-ci:v1:development:<caseId>:<billingItemId>`。状态 Draft → Issued。案/收费锁保护同来源唯一；documentNumber 唯一。DocumentVersion.content 保存 protocolVersion/sourceKind、案号、收费版本与金额、费用覆盖及 fingerprint、客户与我方抬头、日期、付款条件、签发者/时间、原命令 ID/hash；@@unique(documentId,version) 防版本冲突。

开发页分开显示：CI 草稿/已签发；财务待登记/已登记；已登记应收的 Issued/PartiallyPaid/Paid/Cancelled；已核销和未结余额实时来自实际核销真源，未知读取不得显示 0 或已结清。票据展示在案内，无需用户寻找旧 sampleInvoiceId。

财务待登记增加开发来源清单。登记按钮只消费已签发准确 DocumentVersion，生成 Invoice(sourceType=BusinessDevelopmentCI,sourceId=version.id,status=Issued)。金额、币种、客户、原票号、日期均由原票带入；财务只登记，不再替业务签发。原票版本→应收唯一，重复登记读回原记录，即使后续已部分或全额核销也返回原登记身份。原票保留，登记后回填 BillingItem.invoiceId/number 并记录审计。

收款登记与分配使用现有 PaymentVoucher/InvoiceAllocation；一款多票、一票多款，校验方向/币种/双侧剩余额。开发页只读本案票据关联的核销行及必要收款信息，不暴露同一凭证在其他案的分配。

## 4. 命令、权限与恢复

所有业务 CI 保存/签发使用 stable requestKey、命令 hash、expectedVersion/sourceFingerprint；同账号同原请求恢复原成功回执，异载荷复用拒绝。未知 ACK 保留原命令，页面提供“重试原请求”；不生成新 key 猜成功。fresh actor、签名 ceiling、真实客户/来源访问在事务锁前后复核。禁用/撤权后不可继续写或恢复敏感原结果。

财务共同 access helper 保护发票列表、详情、核销列表与核销写入口：fresh 财务 scope、实际数据范围、对象客户与完整来源 L2。业务凭客户/来源可见读取关联账款；all 财务可处理真实来源；未知/断裂来源对普通业务 fail closed。多角色按实际合并授权，不增加单一角色排他禁令。原始业务 CI 金额/客户/来源在通用财务创建、PATCH、作废/删除路径不得被绕改。

## 5. 验收

两小批定向验证，禁止默认库连接。第一批：真实费用来源→业务保存/编辑/签发→已签发不可覆盖→财务待登记/原版登记→案内票据余额；覆盖过期 CAS、同键异载荷、未知 ACK、撤权、跨案来源。第二批：财务三读和核销写共同权限；普通业务跨客户/未知来源拒绝，财务实际 all 与多角色合法协作通过。

隔离 PG 连续 HTTP 用例由根线程执行：原生开发与费用登记→业务开两票→财务登记→一笔收款分配两票→第二笔款结清其中一票→开发回读原票与真实余额；重复/并发登记不得重复应收，反核销后余额回升；业务结案状态不因收款变更。fixtures 仅基础资料/账号/草稿，不直接写已签发或核销事实。

## 6. 同案后补费用与旧待办退役（本目标实施选择）

依据仍为 §4.5 的持续费用汇总、业务开 CI 和 §8.4 的共同多对多核销。以下不增加用户未确认的财务审批前置条件。

已签发的本案 CI 保留原覆盖范围与票面。后续真实费用登记后，业务在当前“开发费用 CI 与回款”区域展开“补充收费”，显式勾选**尚未被其他有效收费、费用行发票或任何已签发本案 CI 覆盖**的准确费用。列表分别显示来源、原币金额与已覆盖数量；只显示可选范围，未选费用继续保留，不自动计入新票。

补充收费字段：费用选择（必选且不重复）、本票拟收/减免、CNY/USD、收费依据。对客净额须正数；成本按原币保留，不自动换算收费。须存在至少一张可核验的本案已签发 CI，不能冒充首票入口。创建时锁案、准确费用和覆盖记录，核对读取 fingerprint，写新的 BillingItem、选中范围的 BillingItemCostCoverage，以及不可变原命令/来源审计；同原 key 重试返回原收费，异载荷与过期范围拒绝。不得把“允许第二票”解释为同一费用可以收费两次。

新补充方案以 `business_ci_draft` 区分待业务开票的补充草稿，只消费冻结选择范围，不误送旧整案财务审核链。选中费用来源/金额/币种发生变化时，签发拒绝，业务须取消原草稿释放预留后重建；另一笔未选新费用不自动加入。取消草稿保留覆盖历史与审计；已签发票及其覆盖不可释放。新 CI 沿用原签发和财务登记命令，两票各自余额与收款分配回读。本案首票在后续补票后仍可按原冻结依据查看、下载及恢复原请求。

新 CI 成功签发的**同一事务**中，只退役对应 BillingItem 的旧 `finance_handoff`、`billing_supplement`（及尚在等待的 `finance_review`）待办。保留 WorkAssignment 和 metadata 原内容，状态改 `cancelled`，附 `result.outcome=superseded_by_business_ci`、原票/版本/命令/操作人/时间，并逐项写审计；不写“财务已审核”“已收款”或“审批已批准”。已经完成、已取消或别案/别收费的任务不变；原 Approval 与审批事件原样保留，旧审批随后尝试消费时必须因收费当前状态不匹配而拒绝。

增量验收：同案首票→真实后到费用→业务选中一笔（另笔未选保留）→补充收费→第二张原票→两票登记和一款多票核销→各票余额回读。覆盖原请求丢 ACK/并发抢同费用/跨案选择/已覆盖选择/过期范围/来源变化；旧待办退役只针对本票且原审批历史不改，签发失败不能提前退役待办。
