# Bambook 全局业务与分工设计方案

初稿日期：2026 年 10 月 6 日。最近修订：2026 年 10 月 7 日。版本：讨论稿 0.2。

本方案覆盖公司内部员工系统的全局业务对象、模块功能、账号分工、权限、交接与业务操作，作为后续每个模块开工方案的共同依据。系统是面料与成衣贸易公司的协作网络：模块表示业务功能，不自动代表独立岗位；采购、库存等常规操作由对应业务组成员在其负责的业务对象上办理，QC、财务、后勤单证等专业工作交给相应真实专业分工，并在原业务对象上读回结果。

**本稿尚未冻结，不能直接交给 coding agent 开工。** 已确认规则、设计建议与待决定事项分开标注。所有纳入全景的模块均已登记；110 组历史能力仅作为防漏目录，新增功能另列。已只读核对本地开发库 panda_hub_dev 的完整账号、角色、团队与权限定义；本地演练身份不代表生产员工名册。2026-10-06 对话中确认的业务决定以 [对话设计决策总账](08-2026-10-06-对话设计决策总账.md) 为准；旧资料与总账冲突时，必须先按总账校正，不得让 coding agent 自行选择。模块详细页面、字段、选项和按钮规格属于下一层设计。

## 二 已确认的全局原则

### 2.1 公司业务与范围

1. 本系统服务贸易商：向供应商采购或委外加工，向客户销售；工厂承担生产执行。
2. 公司员工端是当前主体。客户门户作为既有外部边界登记；供应商、客户、货代、银行、第三方检测机构不因此成为内部员工角色。供应商客户端没有当前开发计划。
3. 面料和成衣分别设计业务细节。服装中的辅料与面料开发不能因为共用基础档案而混成同一套业务。
4. 工厂设备排程、工位报工和计件工资不纳入主体设计；历史加工记录保留引用边界。
5. 业务财务要完整表达应收应付、收付款、核销、对账、汇兑、成本和费用；首阶段不扩展为完整财务总账及税务申报软件。
6. 旧文档的“v1不做”“占位”等不能直接删除全局节点；节点是否在当前实施范围需按最新明确口径决定。

### 2.2 网络与模块边界

1. 不存在所有业务必经的唯一开始或唯一流程。成熟产品直接下单、来样开发、按参数开发、先寻样、先询价等都可以成立。
2. 模块按自己的对象、参与者和任务单独设计，不给所有模块套统一业务骨架。通用 BDS 控件不决定业务结构。
3. 订单是主要汇总枢纽：一站看到来源、产品、规格、采购、进度、样品、质检、出运、单证、款项、费用和变更；专业操作仍由专业角色完成。
4. 数字档案、订单、开发、样品、单据是多对多关联网络。不能把数字档案安排成固定流程的一站，不能用一个“关联订单”字段替代全部分配关系。
5. 每个模块分别表达完成条件。成果确认、业务结束、实物交付、财务结清不是一个总状态。

### 2.3 专业分工

**质量结论由 QC 提交，正式账务由财务处理，出运物流与单证由后勤单证办理；采购、加工跟进、库存/仓储操作通常由对应业务组业务员实际经办。**

业务员可以写需求、推荐理由、客户意见、商业接受决定及跟进说明，不能将这些内容标成专业质检结果。QC 结论、客户确认、领导审批和实物收货分别留存，不相互替代。

模块、操作、岗位和账号不是一一对应关系。采购管理、库存与仓储模块都保留，但系统不设采购员、仓管员、仓库管理员、样品保管人等独立岗位/角色；相关采购和实物操作由对应业务组的实际经办业务员按对象权限办理。每项操作记录真实账号、对象和操作事实；对象数据范围与审批权限仍单独约束。QC、财务、后勤单证是已有专业分工，不能由业务员录入其专业结论或正式账务。常规QC由业务员直接派发给对应QC；额外检测费用与受控例外才走适用审批（本会话已确认）。

### 2.4 规则与依据

合同具体条款 > 客户标准 > 公司默认，按具体条款覆盖并保存来源与版本。合同缺少某条款不代表整套客户标准失效。零值、不适用、未知、尚未配置必须分别表达。

正式报价、订单规格、质检依据、审批内容和单据保留当时版本。之后修改产生新依据与影响处理，不能静默覆盖已确认内容。批准必须绑定实际版本及适用范围。

### 2.5 交接与回程

业务转交必须同时确定：原业务对象、当前依据、发起人、接收账号或分派队列、处理期限、缺项、阻碍、处理入口、回复结果和返回位置；确属专业任务时再标明对应专业团队/岗位。

跳转页面、通知提醒、聊天、任务已读都不能替代业务转交。接收人要能在自己的账号中发现并处理；发起人要能在原对象和“我的工作”收到结果。普通责任转交在接收确认前仍由原负责人负责；审批按其专门路由处理。

## 三 全局角色 账号 与分工

身份需要分别表达五件事：**谁登录、具备什么角色能力、属于哪些团队、此次业务承担什么职责、能操作哪个对象与版本。**

| 分工 | 主要处理 | 明确不能由该分工替代的处理 |
|---|---|---|
| 面料/成衣业务组业务员 | 对应品类的需求、寻样、开发、供应商采购/加工、客户沟通、报价订单、生产跟进；在相关业务中登记样品及库存实物动作 | 不提交QC专业结论，不做财务正式核销，不制作后勤出运单证 |
| 业务负责人/审批人 | 在本人获授权的面料或成衣业务范围内处理业务审批、团队协调；获授权的负责人可审批自己负责范围内的单据 | 不修改QC专业结果或代做财务登记 |
| 面料QC / 成衣QC | 由分开的专业团队和入口处理对应面料或成衣评审、报告、异常及复验 | 不决定客户商业接受；面料和成衣的专业资格不互相替代 |
| 财务 | 接收业务/后勤已开具的CI与供应商票据，登记应收应付、收付款、多笔核销及对账 | 不制作业务CI/Packing List，不决定订单履约是否完成，不录QC结论 |
| 后勤单证 | 接到业务出运交接后处理货运、订舱及出运/报关单据；完成后把资料交回业务员对客 | 不负责订单前段采购或仓储专岗工作，不替业务员对客沟通，不录QC结论或正式财务核销 |
| 老板及平台管理人员 | 老板按其业务授权审批；平台管理员维护账号、角色、授权、路由与字典 | 技术管理权限本身不替代业务审批、QC或财务专业事实 |

库存与仓储、采购与加工是实际存在的模块和操作集合，不是独立岗位。由实际承担对应订单/业务的业务组成员在系统中办理，业务范围、对象数据权限和审批资格分别控制。样品也由业务员操作，MVP不增设样品仓库管理员或保管人。

内部角色码当前有7类，不意味着实际职责只有7项。账号、角色码、职能和业务任务分配不一一对应。最新开发演练配置有17个内部模拟账号，另沿用1个老板账号；5个客户门户身份独立。详见账号目录，不包含密码。

团队采用显式业务组及实体授权的现有方向：同组协作，主管覆盖所属多组，面料与成衣 QC按其负责组和任务工作。部门归属用于组织与适用审批，不能直接等同客户业务数据范围。团队内“查看”“跟进”“接手”“审批”“导出”必须分别定权。

## 四 核心业务对象与权威责任

| 对象 | 正式依据和责任 | 其他节点如何使用 |
|---|---|---|
| 组织与联系人 | 关系智库维护统一身份；客户、工厂、货代、代理等分别分类 | CRM/供应商深化资料；业务单据关联统一组织 |
| 团队与人员 | 组织团队及权限配置，历史成员关系留存 | 业务归属、任务分配、数据范围、审批路由 |
| 需求与商机 | 业务员记录背景、附件及来源 | 寻样、开发、报价、直接下单分别承接 |
| 寻样任务 | 发起人需求、面料经手人候选与回复 | 发起人确认或要求续找；需要新开发时明确另建关联开发案 |
| 开发案 | 开发方向、品类、发起方、需求来源及业务经手人 | 多轮、多个工厂版本、样品、费用、档案与订单分别关联 |
| 打样轮次 | 共同打样目标与修改要求、参与工厂 | 各工厂形成该轮设计版本；不等于一件样 |
| 工厂设计版本 | 明确规格、工厂、所属轮次与修改关系 | QC、需求方确认、转档和下单绑定准确版本 |
| 实物样品 | 样品档案记录来源、形态、数量/单位及手填位置；样品仓库由业务员操作，不设专职保管角色 | 版本与数字档案可追实物；实物可反查设计来源；MVP不做在途/未入库和盘点调整 |
| 服装小版本 | 主版本下无新实物的清晰调整记录 | 下游可引用；不重复占用同一实物；不自动继承 QC 通过，业务需要正式评审时显式发起 |
| 质量评审与报告 | QC工作台的任务、检验依据、结果、报告和复验 | 原样品/版本/订单批次只读专业结论及处理状态 |
| 客户或需求方确认 | 被确认版本、意见、证据、确认主体与时间 | 不替代 QC、不等同生产放行；外部证据由授权业务员登记 |
| 产品档案 | 具体设计规格与来源、分类、客户编码、材料及图像 | 一个档案可复用于多个报价订单；历史订单保留快照 |
| 报价及报价版本 | 商业条件、明细、有效期、适用成本和规则、批准及发送记录 | 接受或转单引用具体版；不能静默用新价替换旧报价 |
| 订单及明细 | 合同交易方、明细规格、价格数量单位、交期、规则与正式变更 | 采购、生产、QC、组运、CI和收款沿准确明细和版本关联 |
| BOM与成本 | 工艺/成本职责维护版本及计算依据；预计、承诺、实际区分 | 采购需求、报价与利润使用相应阶段依据 |
| 采购及交付 | PO明细、供应商、物料/成品/服务、数量日期和实际收货/验收 | QC、仓储、应付、加工发料及损耗关联 |
| 大货库存 | 仓储流水、货权、位置、质量、可用量与占用分别记录 | 自有/第三方仓出运扣实物；工厂直发不虚构我方收货 |
| 履约及出运批次 | 从订单行选取的稳定履约范围、实际数量与组运分配 | QC、放行、物流、单据和核销范围保持对应 |
| 运单与装箱 | 后勤确认本次货物、箱内数量重量、运输方式和实际路径 | 多订单可同买家组运；每个来源订单读回本身分配 |
| 正式贸易单据 | 授权制单人确认数据版本，签署人签自己的准确文件 | 来源业务、单据中心及允许的对外渠道读取同一正式版 |
| 发票与应收应付 | 财务确认金额、币种、交易方、来源及分配 | 开发案/订单/批次读余额；CI贸易单据与财务应收不是任意互换 |
| 收付款及核销 | 财务确认实际资金、认领与多对多分配；原币/折算依据留存 | 业务员提出匹配建议、追款，原业务自动回读财务结果 |
| 索赔与处置 | 业务员发起，QC认定质量事实，适用审批人批准，专业岗执行 | 原订单、受影响批次、退返货、贷项和款项保留各自事实 |
| 审批及例外 | 合法审批人处理指定对象、版本、范围、理由与有效期 | 业务门禁使用适用批准；不改写质量、库存或到账事实 |
| 任务与通知 | 任务承载责任与实际完成依据；通知承载发现和跳转 | 工作台汇总，完成由源业务动作决定，已读不等同办结 |

## 五 业务如何操作与流转

下列是依据已确认原则拟定的可组合业务操作组织，不是全系统唯一流程。具体新动作与未决细节仍是设计建议，详见待决定事项；各步涉及的进出关系均在交接目录登记。

### 5.1 内部面料寻样

成衣或面料业务员提出要求 → 由面料业务组分派实际经手业务员 → 经手人在数字档案或有权查看的资料中找候选 → 留推荐理由和规格差异 → 返回发起人 → 发起人确认完成，或补充要求继续寻找。

推荐适配意见属于业务判断。需要检验实物质量时，另向面料 QC 发起任务；没有实物或没有评审不得显示“QC通过”。暂无匹配是有效结果，不强行生成虚假产品或开发成果。需要新打样时，明确创建关联开发案，不自动把寻样反馈当作开发版本。

### 5.2 面料与成衣开发

业务员建案并确定方向与资料 → 在具体轮次选择一或多个工厂 → 登记各工厂设计版本及真实样品 → 发起适用面料/成衣 QC → QC在自己的账号评审并提交报告 → 业务员在原版本收到结果 → 通过内部 QC 后向客户或内部需求方请求确认 → 留存确认或修改要求 → 继续打样、形成可引用成果或结束业务。

面料同一版本可有色样、手织样、米样等不同实物形态；成衣大版本对应实体样衣或套装单元。版本名例 R1-A、R4-A-1。轮次、工厂设计版本和实物身份不可混用。工厂编码、同轮多版、形态编码等未定细节列入待决定事项。

QC失败后，业务员取得报告并选择适用的修改、复验或结束动作；系统不擅自生成新实物。没有 QC、QC处理中、QC不通过、需求方待确认、需求方拒绝必须分别表达。

### 5.3 开发结束与费用处理

每个版本可以有自己的确认结果，一个案子可以产出多个有用版本或产品档案。业务结束、版本确认与财务结清分别记录。

沿用整案费用方向：各笔开发成本保留 → 案结束并核对费用 → 费用齐后由业务员按已定业务方式处理开发样品 CI → 财务接收已开票据并登记应收 → 业务员在原案看到票据并追款 → 财务登记资金与核销 → 原案读回结清状态。不得按每轮自动收费，不得把未知费用当零。财务不替业务员开具开发样品 CI。

版本成果完成与费用销账最终结束不能混为同一状态。样品/开发费用 CI 由业务员在开发模块开具；财务只接收已开票据，登记应收、收款和核销。免费内部案和失败/放弃案的费用处理仍需在开发开工方案细化。

### 5.4 成熟产品与直接订单

可以从数字档案、已有开发版本或客户直接订单进入。熟练业务员可以先完善档案，但系统不能强制新订单都重新开发。欠缺客户、产品或技术资料时提供补全路径，草稿阶段允许明确的不完整状态；正式确认时核对必须条件。

报价可以与开发并行。报价过期保留原版，核实条件后生成新版或显式沿用。报价接受后转订单保留明细及商业条件，交付日期必须独立确定，不能拿报价有效期代替。

### 5.5 采购与轻量生产跟单

订单实际需求/BOM → 对应面料/成衣业务组经办人拆分供应商及物料/成品/加工服务 → 适用审批 → PO与交期跟进 → 实际交付 → 适用QC/服务验收 → 按实际路径登记入仓或工厂直送交接 → 对账与付款申请。系统不设置独立采购经手岗位。

委外加工记录发料、耗用、损耗、产出与余料，不做工厂车间执行。供应商预计日期与客户正式交期分开；延期不自动改客户交期。拉黑阻断新业务，不自动取消历史订单和应付款。

### 5.6 订单样品与质量

订单生产样属于订单生产，不塞进开发轮次。成衣产前样和船样、面料先锋样、船样及按订单需求选择的皮头样，分别记录使用目的、确认、实物与检验；成衣不设 TOP 样品评审节点。QC全程以专业任务参与；不把所有样品类型强行套同一门禁。

开裁/生产/出运分别依据适用条件。样品客户确认、QC合格、领导批准是独立结果；某项批准不能令其他项自动通过。例外批准保留范围和理由，但专业质量事实仍如实显示。

### 5.7 库存与物流

库存分别表示货主、物理位置、数量单位、质量状态与预留。样品实物账与大货库存账分别管理；合法转化有双侧来源和流水。

出运可以从同一客户且同一收货方的多个订单选部分明细和数量，形成本次稳定批次及分配；面料和成衣必须拆成不同出运记录。跨客户不合一张 CI。物流方式海/空/陆/铁/快递与 FCL/LCL 是不同维度，不按一种固定物流路线设计全部业务。

放行前汇总该范围适用的样品、QC、审批、付款、短装及单据条件。缺哪条、谁处理、进入哪里、完成后如何回来都必须可见。条件未满足不得用“已读通知”放行。

走仓库的货先预留后实际出库，关联运单；工厂直发不制造虚假入仓。物流取消、改期、退回按执行阶段分别恢复占用或建立实际退回，不能统一倒扣流水。

### 5.8 单证 应收 收款与结清

实际交付与合同依据支撑 CI、Packing List 及适用报关资料；不强制“先报关完成才能开票”。出运阶段 CI/PL 由后勤单证制作；开发样品 CI 由业务员在开发模块制作。财务不制作这些业务 CI/PL，只登记已开票据、应收、收款及核销；供应商开具的国内增值税发票进入应付和付款处理。正式单据保留来源版本、批准签署和作废重制历史。

合同买家、Bill-to、Ship-to、实际付款方、收货地址、合同币种和到账币种分别表达。国外品牌 USD 合同、国内工厂收货且 CNY到账是必须覆盖的合法场景；地址不决定币种，第三方代付有授权依据。

资金独立登记，可分配到多张发票，多笔款也可核销一票。系统提出建议，财务确认后写正式核销；业务员认领或建议不直接修改账务。未知款待认领、少收和费用差额分类，不静默抹平。

业务员在订单及开发案查看可见范围的收款进度。交付结束与财务结清分开；订单满足适用应收结清条件时按既有方向自动反馈，核销冲回引发重算，不删除历史。

### 5.9 变更 异常与索赔

修改正式订单/材料/工厂/价格/交期先记录影响 → 暂停受影响的未执行范围 → 适用审批及必要客户确认 → 授权专业岗执行 → 各关联节点读回新结果。未受影响部分按合同继续；不能一律锁死整单。

质量异常由 QC留专业事实，业务员协商商业处理，领导批准适用方案，后勤处理退返补货，财务处理贷项/退款。索赔结案依实际执行和财务结果，不能一个“批准”覆盖所有后续。

### 5.10 人员与平台支撑

员工离职/停用/调岗 → 明确在手业务、待办和未接收交接 → 确定接收人和授权 → 接收后调整权限 → 保留原签署、操作人和历史。停用账号不等于删除业务责任或历史。

我的工作、日历、邮件、搜索、报表和风险视图使用源业务事实，不建另一套可手改业务状态。AI以绑定身份和有限权限提出或执行授权动作，不取得独立超权。邮件抽取建议与正式业务确认分开。

## 六 权限设计必须覆盖六个层次

| 层次 | 要明确的内容 |
|---|---|
| 身份 | 员工、客户、服务主体；账号状态；登录与会话限制 |
| 入口 | 能否打开模块、详情、附件、预览与搜索结果 |
| 操作 | 新建、编辑、发起、接手、转交、提交专业结果、审批、签署、撤回、删除、导入导出分别定权 |
| 数据范围 | 本人、团队、所辖团队、分配对象、全公司；对象关系不能扩大未授权范围 |
| 字段与文件 | 成本、利润、佣金、薪酬、税基、供应商身份与附件分别限制 |
| 状态与依据 | 当前对象状态、版本、系统权限、团队/数据范围、任务归属和适用审批范围，决定本次动作能否执行；QC等专业动作另校验专业资格 |

按钮隐藏只是一层呈现。相同业务规则必须约束界面、API、AI及导出。进入模块不代表能读全部数据；能读关联订单不代表能改QC或核销。正式签署固定为当前真实主体，不允许自由填别人的签署人ID。

129个源码 scope 是兼容对照，不是新设计授权表；旧标签中的财务主管、数值审批阈值与业务员写QC等必须按最新业务纠正。新模块方案要逐动作说明需要何种职责、范围和状态，不能直接复制旧角色矩阵。

## 七 全局交互与信息呈现

1. 登录后从“我的工作”发现今天、逾期、需要催、重要、有问题的业务，也能进入授权团队协作。待审批、待QC、待财务、待接收分别显示责任人和下一步。
2. 原业务页区分本角色可执行动作与其他角色专业处理的只读结果；转交按钮创建真实任务，查看结果按钮直达正式依据。
3. 从任务进入专业节点时带准确对象、版本和已知资料。返回时保留原筛选、位置、选中对象和编辑上下文。
4. 跨节点关联要显示对象身份和关系意义，不能只显示“查看业务”。不强迫用户重复输入本来已有的客户、规格、金额和来源。
5. 空数据、没有权限、尚未配置、加载失败、尚未收到反馈、不适用分别呈现；不以0、空表或“完成”掩盖不同情况。
6. BDS约束视觉与通用控件。页面布局由对应业务决定；全局不强制相同卡片数量、相同流程条或相同页面骨架。
7. 批量动作先逐项判断并显示可处理与阻断原因，由用户明确选择合格子集。重复提交、并发、失败恢复不生成重复业务事实。
8. 本节为设计要求；每个模块开工方案仍必须给出每个页面、字段、选项、按钮、反馈、加载和异常状态的确切规格。

## 八 交接设计的必填内容

每条交接都要在模块方案中填写下列信息；这里约束设计完整性，不要求全部模块共用一个代码抽象。

| 内容 | 具体要求 |
|---|---|
| 触发 | 谁在什么对象、版本、状态点击哪个准确按钮 |
| 创建结果 | 新任务/新单据/关联引用；必须区分跳转与真正转交 |
| 输入依据 | 已有数据、附件、规格快照、金额单位、期限和待补项 |
| 接收 | 真实接收账号/专业团队或队列、无可选接收人的处理、接收或退回条件 |
| 接收人界面 | 从工作台如何发现，在哪个专业页面打开和处理 |
| 结果 | 成功、失败、退回补充、不通过、取消分别返回什么 |
| 回程 | 原对象的哪个位置显示，哪些人收到任务/提醒，下一步可做什么 |
| 修改影响 | 原版本改变、接收人变更、批准失效、复验等如何处理 |
| 可靠性 | 重复、退出续办、并发、断网与失败恢复保留什么事实 |
| 权限 | 谁可查看、处理、转交、撤回、专业签署及访问附件 |

**开发QC示例约束：**源对象为具体开发案/轮次/工厂版本及适用实物；业务员提交背景和检验要求；面料/成衣QC接收自己的任务并写报告；结果回到原版本及发起人的我的工作；业务员依据通过/不通过继续业务。不得把“登记开发质量”设计成业务员自行填写通过结论的表单。

## 九 后续模块开工方案如何使用全景

设计由本线程承担；coding agent只实现冻结的方案；用户或独立第三方负责实现评审。设计方可以核对自己的文稿一致性和证据出处，不承担实现审核。

在每个模块开工文稿开头列出：全局版本、模块ID、涵盖功能ID、涉及角色和具体账号、所有进出交接ID、使用对象及边界、此次明确不改变的邻接规则。逐条引用，不靠coding agent自行读大量历史文档推断。

模块开工前检查的是**设计是否确定**：

- 本模块全部功能都有明确责任与操作边界。
- 上下游交接有双侧页面、实际操作者、输入、输出和返回位置。
- 所涉及的全局待决定事项已经解决。
- 各角色界面的字段、选项和按钮有确定规格与视觉依据。
- 旧文档冲突已指出替代条目，不让coding agent自己选择。

模块可以分批实现，但不能切断其必要交接。全局设计变化先修改本套文稿和图，再更新受影响模块方案。地图是参考视图，文稿中的规则和明确决定是执行依据。
