## 2. 本批最小业务链

1. 对应业务组从准确订单条目创建采购需求或加工需求。草稿规划不形成供应商承诺、库存、应付或正式 QC 事实；提交供应商承诺时每个来源行必须属于当前有效、已批准的正式订单，依据与当前商业版本一致。
2. 采购和加工分别创建草稿。选择已有草稿合单时服务端逐项核对四个共同条件；同一草稿内每行保留准确来源、产品/工序、规格、数量、单位、单价、要求交期及费用归属。
3. 提交审批，冻结整份承诺快照与来源证明。明确配置的供应商承诺审批人核对后通过或驳回；驳回保留申请和原因，经办修改后另轮提交。
4. 获批后业务生成对应采购单/加工合同，并登记“已线下发出”；该登记只代表我方业务录入，不代表系统已发邮件、供应商在线签收或在线签约。
5. 业务逐行登记供应商线下反馈与承诺交期。承诺日期与已批要求日期不同时，保留反馈原事实并发起商业变更，不能偷偷覆盖已批日期或把单据直接标为已确认。
6. 采购交付按准确采购行登记本次数量及实际接收对象。直送加工方时同一原生命令写准确采购交付和准确加工接料链接，**不写我方库存、不发布可被旧 L8 解释为入库的事件**。
7. 委外加工按准确加工行登记实际原料交接与逐次加工回交。每次独立留存，显示累计与计划差异，不要求预建批次计划，不以一次表单覆盖历史。
8. 财务从准确供应商、合同批准版本及实际履约读取业务依据；由财务按实际供应商发票登记应付并付款/核销。采购/加工履约状态不随付款状态自动变化。

## 3. 本轮必要 MVP 选择与未定政策

- 沿用 PurchaseOrder/PurchaseLine 与 OutsourcingOrder/OutsourcingLine 两种实体；新采购写入只接受 Material/FinishedGoods，加工进入 OutsourcingOrder。采购原料与加工行可明确关联，但永不合为一个合同类型。ProcurementDemand.kind 的 ProcessingService 可继续表达“加工需求”，不得再据此创建加工型 PurchaseLine。
- 四项相等使用真实 supplier Relation ID、规范币种、明确付款条件、明确主要交付地点。付款条件保存实际选项/文字；交付地点保存类型、真实关联 ID（有时）、地址快照与稳定 key。只做确定性规范化，不按供应商名称近似、空值相等、相似地址或 UI 显示标签猜相同。四项未明确时可以保存草稿，但不能合单或提交承诺。
- 不额外要求相同销售主单、产品、工序、规格、数量、单价、交期。准确来源行全部在当前经办人实际业务范围内才可合并；跨主单不得靠 header.orderId 判权限。对应业务组责任及每行权限是授权边界，不伪装成第五个商业兼容条件。
- 每条加工行在草稿明确“已有料源的加工”或“由另单采购并交接”；CMT 明确客户/需求方供料与已含辅料范围，辅料+CMT/全包遵循 19。未经明确来源/模式，不能自动推定我方买料或重复采购已含项目。
- 系统内部编号暂沿用现有 PO 编号机制和 OSO 唯一编号能力，不把新编号样式、法律条款或模板细节记为用户已确认。正式文件必须显示类型、编号、批准版本、来源行、四项共同条件与逐行承诺；不得把加工费排成购货价格。
- 实际数量使用 Decimal(18,4) 字符串，单位明确，无隐式米/码/千克/件换算。只校验有限、正数、精度、确切物理来源未被重复交接及库内实际可用量，不自行加损耗率/数量容差。
- 超收、短收或加工投入/产出差异可以据实登记并显示“差异待处理”。不因差异自动结清、改合同数量、推导合理损耗、补造产出、自动退料、改变应付或认定质量合格。计划不同于实际不是拒记真实事实的理由；差异未处理时不提供“按差异自动完成”的动作。投入/产出单位不同也不推导转换率。
- 本批不定义余料产权、批量领料分摊、损耗追责、退换数量政策和跨库调拨规则。经过我方仓库的步骤必须使用真实库位/批次和既有库存约束；原料仅直送加工方的连续用例可以完整验收，不依赖尚未确定的余料政策。
- 实际交接/点数是业务事实，不等于专业 QC 合格报告。普通业务员不能通过“收货”“回交”字段生成 qc:inspect 事实或解除生产 QC 问题；下游质量门禁仍消费准确版本的专业报告。

## 4. 最小 schema 增量建议（待 root 释放 schema 窗口）

优先新增三个模型，复用现有单据、ApprovalRequest、SystemConfig/History、AuditLog 与库存事实。不为每个页面或每个计划步骤新增一张表。所有历史新增字段 nullable，不回填为批准、已确认、库存或实际交接。

### 4.1 现有实体窄增量

| 模型 | 建议字段/约束 | 用途 |
|---|---|---|
| PurchaseOrder、OutsourcingOrder | `businessOwnerId String?`、`approvedCommitmentRevisionId String?`、`mainDeliveryLocationKey String?`、`mainDeliveryLocation Json?` | 当前真实经办；明确批准依据；主要地点的可核对身份和地址快照。owner 不独立授予权限。 |
| OutsourcingOrder | `paymentTerms String?` | 补齐与采购同口径的四项共同条件；supplierId/currency 已有。 |
| PurchaseLine | 沿用 `orderLineId`，增加 `requestedDeliveryDate String?` | 新写必须准确来源行与独立要求交期；历史 null 不猜。 |
| OutsourcingLine | `orderLineId String?`、`requestedDeliveryDate String?`、`specification String?` | 加工需求、费用、回交准确归属和逐行规格/日期；历史 null 不猜。 |
| 两种单据行 | `supplierCommittedDeliveryDate String?` | 仅作为已记录、与当前批准一致的供应商交期投影；原始反馈与录入人时保存在命令回执/审计中，不把该字段当在线供应商签名。 |
| 两种单据行 | `retiredAt BigInt?` | 获批修订移除的行保留稳定身份与履约历史；不删除重建或混作当前活动行。 |
| ProcurementDemand | 沿用准确 sourceKey/orderId/orderLineId、kind、revision | 加工需求由原生命令分配到加工合同，不再创建混合 PO。 |
| PurchaseDemandAllocation | 现有 purchaseOrderId/purchaseLineId 改为可空；追加 `outsourcingOrderId String?`、`outsourcingLineId String? @unique` | 保留旧表名避免无意义迁移；新行恰好指向采购或加工一类，DB check + 命令校验。不让一个需求分配同时属于两类合同。 |

header.orderId 保留为历史/单来源展示兼容字段；有多主单时不填假主单，授权、审批、金额归属和回交一律读准确行集合。采购/加工现有头部 received/quality 数量只作可重建投影，混合单位不相加成一个“总数量”。

### 4.2 SupplierCommitmentRevision：承诺与审批历史

- `id`；`purchaseOrderId?` / `outsourcingOrderId?` 恰一；`revision Int`；`status` 为 draft/pending/approved/rejected/superseded；`basedOnRevisionId?`；`approvalRequestId?`。
- `snapshot Json`、`contentFingerprint String` 冻结完整共同条件、稳定行 ID、各行来源订单/条目/当前主单批准证明、商业版本/模式/供料证明、项目/规格/数量/单位/单价/金额/要求交期、经办组/人、修改原因及真实 before/after。
- `createdBy/createdAt/submittedAt?/decidedAt?`；唯一约束分别为 `(purchaseOrderId,revision)`、`(outsourcingOrderId,revision)`；approvalRequestId 唯一；索引各 parent/status。
- 初次批准才建立 approvedCommitmentRevisionId。已批后提修改时只写新 draft revision，不提前覆盖已批 parent/line 商业投影；新版本获批时在同一事务切指针和投影，旧版本保留。来源行 ID 稳定，不删除重建已参与承诺或履约的行。
- 每次草稿商业保存追加新的 revision 行，旧草稿快照只读；expectedRevision 精确匹配单据最新 revision 数字，不使用同一编号下悄悄变内容的快照。提交只接受当前最新 draft，把该准确快照置 pending；批准决定不重新拼装可变表数据代替提交依据。pending/approved 快照不再修改。
- 一个单据同一时刻最多一份 pending revision，服务锁与 DB 部分唯一约束共同保证。已经提交的 snapshot/fingerprint/eligibleReviewerIds 不被通用更新替换。

### 4.3 SupplierContractCommandReceipt：成功命令与原 key 回放

- `id`、`actorId`、`requestKey`、`operation`、`contractKind`、`contractId`、`inputFingerprint`、`requestSnapshot Json`、`resultSnapshot Json`、`createdAt`；唯一 `(actorId,requestKey)`。操作、类型、目标和准确行均进入 fingerprint，原 key 不能换目标/换操作/换行。
- resultSnapshot 保存稳定 revision/approval/fulfillment/document IDs 及命令回执，避免当前状态后来改变导致成功回执“消失”。requestSnapshot 保留供应商线下反馈的准确行、实际反馈日期、承诺交期、可选证据、真实录入人时；不虚构供应商在线操作。
- 原始业务事实、审计、投影与成功回执在同一事务提交；不存在“先回 ok 后补事实”。失败事务不占成功 key；结果未知时客户端保留原 key/参数并查询/重放。

### 4.4 SupplierFulfillmentFact：逐行实际交接与回交

- `id`、`commandReceiptId`、`lineSequence Int`、`kind` 为 purchase_delivery / processing_input / processing_return；`commitmentRevisionId`、`orderLineId`、`purchaseLineId?`、`outsourcingLineId?`、`sourceFactId?`、`sourceStockMovementId?`、`materialReceiptId?`、`occurredAt`、`quantity Decimal(18,4)`、`unit`、`materialCode?`、`specSnapshot Json`。
- `fromKind/fromRelationId?/fromWarehouseId?`、`toKind/toRelationId?/toWarehouseId?` 与真实对象/地点快照；`evidence Json?`、`notes?`、`recordedBy/recordedAt`。种类和实际对象决定必填组合，不能用一个自由文本“加工厂”绕过准确关联。
- purchase_delivery 必须准确采购行；processing_input/return 必须准确加工行。一个直送命令原子追加 purchase_delivery 和以它为 sourceFactId 的 processing_input；后者可携带准确采购行链接但数量、来源版本及当前接料权限仍独立核验。源行/目标行不同必须有真实内部供料或其他已存在合法来源证明，不能按物料编码相同猜关联。
- sourceFactId 不是唯一：允许一份实际来源按确定单位分多次交接，但锁源事实汇总有效占用，不能重复消费或超过可交接事实量。加工回交单独记录真实产出，不从原料数量自动复制或推定产量/损耗。
- 每个命令多行事实以 commandReceiptId 归组，唯一 `(commandReceiptId,lineSequence,kind)` 防重，稳定序号与准确行一起进入命令 fingerprint。索引各来源行/加工行/revision/occurredAt。新增事实不可普通 update/delete；错误更正需要显式原事实引用和完整审计，已有库存或下游消费时沿库存更正边界处理，不以删除历史代替。
- MaterialReceipt 仅在实际到我方仓库时复用；新事实直接保存逐行证据，消除只能从 AuditLog 猜收料行的依赖。直送完全不创建 MaterialReceipt、InventoryItem 或 StockMovement，也不发 MaterialReceived。入我方仓库的既有 L8 须校验 native receipt/事实/实际仓库目的地，禁止给旧事件加未知字段后任其忽略。

## 5. 独立审批配置与鲜活权限

### 5.1 审批人配置

复用 SystemConfig（`schema.prisma:7477`）及 SystemConfigHistory（7512），独立 key：`supplierCommitment.approvers.<purchase|processing>.<fabric|garment>`，值 `{schemaVersion:1,userIds:[...]}`。配置入口沿当前 SystemSettings 实际 `dictionary:write` 与当前管理身份双门（`config/systemConfigRoute.ts:134–138`），另建明确供应商审批资格配置 UI/API，不假设现有出口方档案 route 能写任意配置。每次设置校验真实有效用户、expectedConfigVersion、理由，配置值与 History 原子提交；审批读取 tx 内最新值，不用现有 30 秒缓存。配置管理员身份不自动变成供应商承诺审批资格。

**绝不读取 OrderApprovalAuthority 作为供应商合同名单，也不默认选订单审批人、业务主管、admin、owner 或财务。** 未配置、名单失效或无符合当前 scope 的人时阻止提交并显示“尚未配置当前业务的供应商承诺审批人”。审批能力同时要求名单资格与当前 `procurement:approve`；`*` 可满足 scope，但不替代名单配置。若一单存在多个准确业务域，候选人必须对该单全部来源域均有明确供应商承诺审批资格及来源读取权，不能挑一个域的名单代批另一个域。

提交时冻结 eligibleReviewerIds 和配置版本；决定时重新读取账号、scope/ceiling、当前名单有效性、准确全部来源与待审 revision。撤权后不能借旧候选快照审批；新加入者不能直接接手旧申请，需显式退回重提或受审计的重新指派流程。本批 MVP 只支持通过/驳回与退回后重提，不提供审批人直接改商业字段、无人审批、老板模式旁路或泛用 delegate 绕过名单。

### 5.2 每个入口的实际权限

| 动作 | Scope + 当前业务/数据范围 |
|---|---|
| 列表/详情/来源/文件/交接读回 | procurement:read；只返回当前有权的准确来源。整合同/正式文件要求全部行可读，不将其他组行名称、价格或证据通过汇总泄露。 |
| 草稿、合单、提交、修订、线下发出登记、供应商反馈、实际交接/回交 | procurement:write；真实对应业务组当前成员及所有相关行 L2 写范围。processing 不再因 production:write 单独获得供应商承诺写权。 |
| 供应商承诺决定 | procurement:approve + 独立当前配置资格 + 全部准确来源可读；不要求经办 write，以支持有审批权的专门授权账号。 |
| 生成正式采购单/加工合同 | procurement:write + 全部行来源权限 + 当前明确 approved revision；历史版本下载按 read 与历史标识，不当新承诺。 |
| 专业质量结论/问题解除 | 本批交接写入口不拥有该能力；沿既有 qc:inspect + 精确 family/source、问题复验与业务恢复。 |
| 供应商发票、应付、付款、核销 | 沿财务真实 scopes，不以 procurement:write 或合同批准资格代替。 |

认证 actor 仅来自可信路由会话。服务入口拒绝 body.actorId/录入人/角色注入，重新读取 UserAccount 的 active/deleted/当前权限/业务组与数据范围，scope 与凭据 permissionCeiling 同时满足。旧 visibleOrderIds 数组、buyer 名称、header.orderId、role=admin 都不能代替检查。多行命令任一来源无权则整体失败，不能部分落单。

## 6. 冻结、变更与事务顺序

| 当前状态 | 商业编辑/合单 | 正式文件/线下发出/新供应商确认 | 实际履约事实 |
|---|---|---|---|
| 初次草稿/驳回草稿 | 经办可编辑，审计真实 before/after | 禁止；只读草稿预览须明确“草稿，未批准” | 没有已批依据，不能伪造正式履约；历史实际事实单独展示未知依据 |
| 初次 pending | 全冻结，不能增删行/换供应商/改日期/更换快照 | 禁止 | 不能绕过初次审批生成新正式链 |
| approved | 通用编辑禁止；只能建立变更草稿 | 基于当前批准版本生成/登记 | 按准确批准版本逐次追加，不重审 |
| amendment draft/pending | 修改只在新 revision；pending 后该提案也冻结 | 不发新承诺；旧正式文件仅历史读取 | 已有原约定的真实到货/回交可追加到旧批准版本；不能借新未批提案扩大或改换承诺 |
| amendment rejected | 原批准依据保留；提案退回后可修改重提 | 不能把驳回提案当获批 | 原约定事实继续归原批准版本 |

允许待审商业变更期间登记原约定实际事实，是本轮 MVP 对“锁定承诺”和“实际分次不重审”的实现选择；只追加不可改写的事实，不提供商业字段后门。超过原约定的差异只据实标记，不视为批准了新数量/价格/日期。

新命令统一锁序：① `(actorId,requestKey)` 命令锁；② 按 ID 排序的来源 Order/OrderLine；③ 按类型/ID 排序的 PurchaseOrder/OutsourcingOrder（直送同时锁两单）；④ revision/ApprovalRequest（决定入口按同一域锁顺序进入）；⑤ 精确需求/分配/源交接事实；⑥ 必要的真实库存行/流水。先发现只读 ID 集合再按全序加锁，锁内重新加载并校验集合/版本；发现集合变化则 409 重载，不倒序补锁。所有新服务及 legacy adapter 必须使用同一顺序，避免合同→来源与来源→合同互等。

锁前和锁后都检验 fresh actor、ceiling、来源范围、单据/行归属、审批锁与 expectedRevision/approved pointer。批准时必须核冻结 contentFingerprint、审批内容 reviewContentVersion、名单、来源当前批准证明和商业版本；payload 单独 JSON 相同不足以证明来源未变化。已取消/撤销或已改绑来源不准以旧快照发起新动作，旧历史仍可读。

**原 key 重放先当前授权再读取回执**，核 operation/type/target/精确行/参数 fingerprint；相同返回原成功 ID/快照，不重新入库、不追加第二次交接、不改审批。不同返回 REQUEST_KEY_CONFLICT。已成功后审批/商业状态变化不抹去原成功回执；撤权后拒绝泄露旧回执。新 key 按当前 gate 执行。并发同 key 只提交一次；同源并发交接以锁内累计守恒保证。

## 7. API、读回与 UI

### 7.1 原生命令接口

以下路径为本轮 API 选择，返回 `{ok:true,item,commandAck}`；commandAck 含 requestKey/operation/contractKind/contractId/revisionId/approvalId?/factIds?/documentId?，前端逐项核准确身份。读取返回准确 contract/line/revision/fact 与当前允许操作；不能只凭 HTTP 200 或泛用 toast 认为完成。

- `POST /api/v1/procurement/contracts/<purchase|processing>`：requestKey、明确四项共同条件、稳定来源需求/订单行集合、逐行字段。既有草稿合单另走 `POST .../:id/merge-demands`，带 expectedRevision 与每个需求 revision。
- `PUT .../:id/draft`：requestKey、expectedRevision、完整显式提案；获批后不接此通用编辑，另用 `POST .../:id/amendments`，带 basedOnRevisionId/reason/before-after。
- `POST .../:id/submit`：requestKey/expectedRevision；`POST .../:id/record-offline-send`：requestKey/approvedRevisionId/实际发出日期/可选证据。
- `POST .../:id/supplier-feedback`：requestKey/approvedRevisionId、逐行 supplierCommittedDeliveryDate/实际反馈日期/可选证据；交期不符返回明确“需承诺变更”，原反馈保存并链接新提案，不能显示当前批准已变。
- `POST .../:id/fulfillments`：requestKey/approvedRevisionId、本次准确行、类型、实际对象、数量/单位/日期、明确采购↔加工源链接/证据；直送一条命令完成双方事实。
- `GET .../:id`、`GET .../:id/revisions`、`GET .../:id/fulfillments`、`GET .../:id/commands/:requestKey`：当前授权后准确读回。采购/加工来源条目各自可跳回对应事实与费用；不要求前端遍历全库猜关联。

审批中心复用 ApprovalRequest，新增 action `supplier:commitment`、target `SupplierCommitmentRevision`，payload 固定准确类型/合同/revision/fingerprint/来源/配置版本；接 source access、read summary、当前配置候选、内容核对及事务决定。不得仅在“发送”按钮加一个前端 modal，而漏掉审批中心、kernel、agent、旧 MES 和自动工具入口。

### 7.2 渐进式页面

采购与加工入口在相应业务组工作区呈现两种明确类型。列表显示编号/供应商/共同条件、承诺审批状态、当前批准版、线下发出/反馈状态、逐行累计事实与差异提示；履约和财务状态分别展示。

草稿先选准确来源，再选同类型单据/合单候选；不兼容时逐项解释哪一项不同。行表格显示来源内部订单号/行、产品/工序/规格、数量/单位/价格/金额、独立要求日期。供应商反馈逐行显示已批日期与实际反馈日期，改期进入变更比较，不覆盖旧值。

待审页面以冻结只读承诺和“返回修改/审批详情”呈现，隐藏修改/发出按钮；获批才出现正式文件与线下发出登记，随后显示供应商反馈及实际交接下一动作。直送选择真实加工合同/行、接收方与本次量，完成页同时显示采购交付 ID 与加工接料 ID，并明确“直送加工方”。回交页选择准确加工行，填本次数量/单位/时间/对象/证据，读回历史与累计，不预填“全部已完成”或把上次值覆盖。

结果未知保留原 requestKey、表单参数与目标，显示“核对本次提交”入口；原 key 核对成功后读回准确版/行/事实。切账号、切来源、异步迟到或 UI 已关闭时不把旧 ACK 填给当前单据。普通失败允许修正提案并用新 key 明确提交，不自动循环重试。

## 8. 既有入口收敛与建议 owned 文件

schema/types/迁移与共享审批接线先由 root 协调窗口。拟由本 worker 实施的文件应一次性分配，其他 worker 不并改：

- 新原生后端：`server/src/procurement/supplierContractAccess.ts`、`supplierContractPolicy.ts`、`supplierCommitmentService.ts`、`supplierFulfillmentService.ts`、`supplierContractCommandReceipt.ts` 及各自纯测试/隔离 acceptance。权限、四项兼容、revision/fingerprint/锁/原 key 都在服务层统一。
- 必要窄适配：`procurementService.ts`、`procurementDemandService.ts`、`procurementRoute.ts`；`mes/mesService.ts`、`mes/mesRoute.ts` 的 outsourcing 专属方法/路由；`agent/procurementFlow.ts` 的相应执行入口。legacy send/transition/update/receive 必须进入同一 gate，不能留下 production:write 或老 PO ProcessingService 旁路。
- 库存边界：`events/linkages/L8AutoStockIn.ts` 与原生 warehouse 接收适配/定向测试，需要 root 另行锁定文件 ownership；直接交接流程无需修改通用库存政策。
- 前端：`components/ProcurementManager.tsx` 及新增 `components/procurement/SupplierContractWorkspace.tsx`、`SupplierCommitmentPanel.tsx`、`SupplierFulfillmentPanel.tsx` 与组件测试；`services/supplierContractService.ts` 与 ACK 测试。`services/apiService.ts` 仅相应旧 procurement/outsourcing 方法适配块，避免全文件多人编辑。
- root/协作接线：`schema.prisma`/migration/私有 client、共享 `types.ts`、审批列表/route/kernel/decision/source-access/read-detail、文件生成器与 registry、订单来源卡/下游成本投影。worker 给精确 helper/DTO/回执契约后由 root 分配窄修改，不默认抢占。

历史 ProcessingService PO 和无准确来源 OSO 保留可读，展示“历史依据待核实”；不自动拆单、继承批准、补造供应商确认或回交。新对外承诺必须显式建立原生两类合同。旧已存在的真实收料/库存不得删掉或当新记录重放；兼容性验收要证明 legacy 读回保留且 legacy 写不能绕过新门禁。已批文件历史从批准 snapshot 生成，草稿预览不进入正式单据中心；正式生成的版本/摘要/hash 固定，不读可变 parent 重新拼一份假“原批准版”。

## 9. 验证与逐项关闭条件

先纯 mock/组件测试，显式禁连默认业务库；随后由 root 统一隔离 HTTP/PG/真实 JWT 与浏览器验收。fixture 通过原生命令产生来源主单批准、合同批准、供应商反馈、物理交接与 QC；不直接 DB 写成功状态。

| 连续场景 | 必须验证的读回/拒绝 |

| 采购原料→准确加工合同→两边获批→供应商直送加工方→两次加工回交 | 两类合同独立，交接准确行/来源/对象/量；直送后 InventoryItem/MaterialReceipt/StockMovement/入库事件均零新增；逐次回交及准确来源成本读回；重复命令零重复。 |

| 结果未知、同 key 并发、同 key 改行/改数量/跨操作、状态改变后原 key | 只写一次，原 key 精确恢复原 IDs；冲突拒绝；后来新 revision 不抹原成功；库存和加工接料同事务，不出现半边成功。 |
| 差异/单位未知/历史未知/QC 分离 | 不造容差/损耗；据实差异不自动完成/付款/合格；历史缺来源不补算；业务收货不能生成专业 QC pass；费用按准确源行且 CMT 含项不重复采购。 |
