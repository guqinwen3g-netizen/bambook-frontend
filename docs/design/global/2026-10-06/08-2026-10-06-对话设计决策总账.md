#### 1.1.1 以真实业务驱动开发与设计讨论（2026-10-12 长期原则）

**已确认，适用于此后的每次开发与设计方向讨论。**

业务设计与软件设计必须在同一条真实业务链上共同推演，不能先分别询问业务和界面偏好，再把两份答案拼接。以专业业务判断驱动信息、操作、数据、权限、状态及跨模块协作的完整方案，方案明确后再推动开发。

1. **先核实，再提问。** 按当前讨论范围查阅已确认业务决策、已有模拟场景与当前实现；可查证的角色、字段、操作和规则先自行核实，不反复要求用户提供。不能从现有代码反推规则必然正确，也不能为补齐流程臆造角色或业务规则。
2. **沿角色的实际工作逐步推演。** 从该角色登录后的首页、工作入口开始，走到业务完成；不能只描述模块内部页面。业务员持续负责客户业务主线，领导及专业岗位在真实决策或协作节点介入；协作任务交出后，还要说明结果如何回到业务员主线。
3. **每个节点同时核对下列维度。** 这些维度是一项业务操作的共同设计，不是先后独立的业务问卷与软件问卷。

| 节点维度 | 必须说明的内容 |
|---|---|
| 业务目的与责任 | 为什么做、由谁操作、谁持续负责、谁作决策或提供专业结果 |
| 入口与操作 | 从首页或当前工作如何进入、看到什么、可执行什么操作、结果如何反馈 |
| 信息与来源 | 完成判断需要哪些信息，来自哪个真实对象、记录、快照或外部依据 |
| 数据与状态 | 操作写入什么记录、如何关联来源、哪些状态改变、哪些历史事实保留 |
| 权限与门禁 | 谁可见、谁可操作、前置条件是什么、不满足时如何处理 |
| 跨模块交接 | 哪些数据与任务交给哪个角色或模块，接收方在哪里处理 |
| 回程与下一步 | 协作结果如何返回原业务、谁确认继续、下一步具体动作是什么 |
| 实际分支 | 退回、修改、取消、部分完成及其他已存在分支如何处理，并如何回到主线或结束 |

4. **结论分层记录。** 明确区分「已确认规则」「当前实现」「缺口」「待决定项」，标明依据；实现存在不等于业务已确认，模拟场景存在不等于全部分支已验收。只将真正需要用户决策、且无法从现有依据确定的问题提交用户。
5. **完整衔接后实施。** 在本次授权范围内形成业务与软件相互对应的方案，明确各节点、交接、回程及分支后再驱动开发；不能把缺失的业务决定交给实现者猜测。讨论方法不自动授权扩大范围、恢复已暂停任务或启动全系统审计。

#### 1.1.2 当前业务界面设计依据修正（2026-10-12 最新用户裁决）

**已确认方向，覆盖冲突的旧 BDS 风格处方。** BDS 已多次被推翻；遵守旧材料、复用当前组件或引用当前业务页面，不能自证设计合格。当前唯一认可改造完成的是登录界面，它只提供视觉方向线索，不是成熟业务界面的模板；没有任何业务页面可直接照抄为标准。

- **最新否决与纠正：**用户再次明确不认可把整个界面铺满作为设计风格；此约束覆盖列表、详情、表单及其他业务页面，也不认可只缩窄max-width、只删框后整页文字与细线、或靠折叠所有字段掩盖构图。必须有空间感、呼吸空间、留白、排版、明确分区/主次、视觉引导与视觉重心。前两版创建页均不是可扩散模板。
- **先构图再选表面：**按真实任务确定进入先看什么、其次看什么、在哪里行动；主元素有明显而克制的权重，其他退到次要层级。划分必要导航、主要工作、次要上下文，安排阅读顺序、区域间距与组内紧密关系，最后选择容器/字段样式；无容器不等于输入不可辨认。
- **按页型判断：**展示页可利用左右/边缘对齐及中间留白；表单不得机械拆到遥远两侧，保持合理列宽、标签/输入联系与连续完成路径。列表/详情/表单分别推导，不一套布局灌所有页面。时间轴、导航、焦点卡片可承载真实引导，但不要求每页全加，不造装饰步骤。
- 方向为极简、未来科技感；大部分区域无容器，允许为明确 focus 的重点卡片使用容器。小胶囊、badge、chip、彩色标记豁免容器限制。
- 每页先分析业务任务、信息层级、密度、重点与交互，再决定开放区域与焦点卡片；不机械套旧规范，也不把全部区域一律去容器。
- `bambook-ui` 的强制加载、工作方法、业务/权限保护和 E15 分项实渲验收继续执行；冲突风格以本次裁决为先。
- 列表、详情、编辑、财务、出运、报价各自推导阅读路径及结构，必要重组，保留业务流程、权限与历史记录。台账逐页记录理由，改 token 或换卡面不算完成。

**当前具体候选构图，已实现、待视觉认可：**开发创建的主任务是定义本次开发并明确责任/来源后立案，不是同时执行工厂/QC。名称+目标形成唯一主要工作区和视觉重心；下方开放而紧密的归属/来源、期限/补充构成连续填写路径；已知规格为次要补充，不用隐藏全部字段替代构图。创建动作仍在标题栏；客户真实款式标识、未知参数、权限与数据契约保留。不得据透明40px字段/无白框/无脚本错误认定审美合格。原3000明暗、1100窗口和客户分支已有实渲证据，此页仍为未认可候选，未完成全局视觉验收。

**2026-10-12 最新收口：**用户仍未认可此前业务界面与展示候选，当前先盯开发与寻样、订单两个真实模块，逐页完成。列表开放＋详情卡片、表单开放＋旁侧导览；正文与小号灰色辅助文字为主要层级，艺术化彩色大字暂缓；同角色控件统一。去重复说明／装饰性符号及中英双重命名，保留业务原文和专业标识。入口、字段、权限、状态和返回以实际业务核准，不能为了样机擅改。长期全局目标不取消，未经这两模块验证的候选暂不扩散。

### 1.2 推进范围和 MVP 原则

**已确认**

- 当前最优先、需要连成业务闭环的四个板块是：**开发与寻样、大货订单管理、样品仓库、QC**。
- 这些板块不是四个孤立页面：开发和订单产生的实体样品进入统一样品仓库；业务从来源模块发起 QC，QC 在自己的工作台完成并回传报告；通过样品门禁后由需求方确认；履约完成进入出运，由后勤单证接单；出具的 CI 回到财务登记收款；财务负责核销，不负责订单履约是否完成。
- 设计最终应细到实现方无需设计：按钮文案、显示条件、点击结果、字段类型与选项、必填条件、错误反馈、读写对象、权限、状态变化、下一节点及回程。
- 同时坚持 MVP：只加入闭环必需的规则，不因少数例外不断增加待收货/在途、盘点调整、复杂发送回执等状态和流程。
- 当前 MVP 不含邮箱或未读邮件入口、计数与处理流程；未来邮箱应接入“我的工作”，不据此另起脱离业务主线的工作入口。
- **2026-10-14 用户确认**：当前开发的是公司内部使用的**公司端**。供应商端、客户端是后续独立的平台（与公司端数据互通），本阶段不做；公司端不预设对外可见字段或“给工厂 / 客户看的说明”，工厂、客户的沟通在公司端只记录实际方式和内部备注。
- 目前围绕订单、QC、仓库、出运、财务已讨论出大量业务规则，但**四个模块的逐页 UI/UX、全部字段、全部校验和按钮文案仍未全部收口**。本总账记录的是目前对话中真正确认的业务决定，不把尚未讨论的界面细节伪装成已定稿。

- 全景图是帮助设计和实施查找全局节点、角色与交接的参考，不是软件当前要实现的业务模块，也不是推进软件本身的主线。

## 三、跨模块共同设计规则

### 3.1 业务责任与数据归属

**已确认**

- 每个操作在最接近业务发生处发起：业务员处理开发、订单和样品业务时从相应业务模块发起；QC 在 QC 工作台处理评审；后勤单证在出运单证节点制作 CI/PL；财务在财务模块登记票据、收款、应付和付款。
- 开发/订单来源与样品仓库共享同一份实物记录和数量事实，不得在来源页与仓库分别维护两套库存。具体档案粒度按品类区分：成衣逐件；面料按同一产品/开发版本建立档案，并在档案内按样品形态分别记数量或长度。
- 业务操作造成的样品减少或流转应生成来源明确的流水记录；不直接手改库存总数。MVP 不提供盘点调整，因此发现漏记或差异由人工在线下处理，不新设“盘点修正”产品流程。
- QC 报告必须附着于发起它的准确版本、订单行或工厂履约分支；不能只挂在整张订单、客户或工厂上，造成报告无法判断影响哪条业务。
- 主单和财务状态彼此分离：订单可在全部发运前持续履约；财务可收到多笔款并核销多张票据；财务收款/核销不代表生产完成，订单履约完成也不代表款已收清。

### 3.2 逐步显露的业务界面

**已确认**

- 对带业务进度的模块，详情页先展示基础资料、订单/合同或开发案概况，以及一条清晰的阶段进度轨迹。
- 当前步骤和过去已完成的步骤可打开；以前的步骤允许回看。当前步骤是业务员此刻处理的工作区。
- 未来步骤在进度轨迹中可见名称和先后关系，但内容区域锁定，不可浏览、填写或通过滚动提前看到。只有当前步骤资料完整并完成规定的门禁后，下一步才解锁。
- QC 通过、客户/需求方确认等门禁仅解锁后续步骤；需要业务员明确点击“继续”或执行对应动作，不能因为系统收到通过报告就自动生产、自动出运或自动跳步。
- 目的在于把注意力限定在当前待办，后续节点只作为进度提示；已经讨论的开发与寻样也应按该交互原则设计，而不只订单管理采用。

## 四、开发与寻样

> **2026-10-12 更新：**本节早期编号、费用及 QC/转档口径已有最终纠正，优先阅读[第十九节最新裁决](#development-search-20261012)；旧例不得作为完整开工规格。

### 4.1 入口、类型和对象关系

**已确认**

- 开发模块入口先让业务员选择**面料开发**或**成衣开发**，两者在业务对象和流程上独立。
- 关系为：**开发案 → 轮次 → 工厂任务/工厂版本 → 实物样品**。
- 轮次表示一次打样动作或一批共同发出的开发安排。一个轮次可以发给多家工厂；下一轮可有一家，也可有多家。轮次数不取决于工厂数或版本数。
- 每家工厂在该轮任务下产生自己的版本。例如一轮给 A、B、C 三家工厂，可有 R1-A、R1-B、R1-C；轮次是共同开发安排，版本是特定工厂的实际成果。
- 允许服装等开发出现无新实物的小修改版本，以点号表达，例如 R1-A.1。它是可单独识别的修订，不应被当作另一轮。
- 大版本实际产生的实物在开发版本下首次登记。开发页保存后自动产生/关联仓库里同一份样品记录，用户不用再到样品仓库重复建档。

### 4.2 小版本、QC 和确认

**已确认**

- 点号版本非常重要，生产不能只引用 R1-A 而漏掉 R1-A.1。后续生产或转订单若需使用该点号版本，必须指向并确认这个准确版本。
- 原大版本的确认不自动代表点号修改后的版本已确认；点号版本须有自己独立的确认记录。
- 客户开发由客户确认，内部开发由内部需求方确认；业务员负责在系统记录实际确认结果。确认记录必须能识别确认方/确认人、时间、结果和确认依据；录入人不能被误显示成作出业务确认的人。
- 程序只记录正式 QC 流程。微信、电话等非正式小改沟通不要求建 QC 记录；业务员认为要正式 QC 时，显式发起 QC，交给 QC 岗位评审，由 QC 提交报告。
- 不设置由 QC 代替需求方做客户偏好选择的规则。正式 QC 通过与需求方确认是不同的门禁。
- **转产品档案条件只看正式 QC 通过。** 客户或内部需求方是否选用不是产品入档前提；未获客人选用但质量通过的设计，也可作为公司产品保留。
- “转为产品档案”从具体 QC 通过的版本详情发起；建档成功后产品档案编号和链接回到对应版本。不得把整个开发案笼统转成一个版本不明的档案。
- 对小版本是否继承 QC 通过状态，规则是不能自动继承。是否需要正式 QC，由业务员针对实际业务显式发起；系统不将非正式沟通变成隐形状态。

### 4.3 工厂任务和试样通知单

**已确认**

- 一个轮次 × 一家工厂对应一个工厂任务和一份试样通知单。
- 一轮可以有共同开发要求，但不同工厂的式样/要求可能不同。因此每家工厂必须有自己的完整打样要求，不能只靠一个所有工厂共用的通知内容。
- 创建工厂任务时，将本轮共同要求复制到该工厂任务；业务员再按该厂情况修改。副本之后独立保存，各工厂互不覆盖。
- 后来修改轮次共同要求时，不能自动覆盖已经创建的工厂任务。需要同步到哪家工厂，业务员就手动更新那家任务，再重新生成该厂通知单。
- 通知单类型由标题区分：面料使用“面料试样通知单”；服装使用“服装开发通知单”。类型标题无需在正文再重复一个“面料/成衣”字段。
- 通知单信息包括实际样品形态、数量和单位、交期、本轮共同要求、该工厂要求和参考附件；相关内容由业务员核对后生成。
- 业务员从工厂任务操作生成通知单，获得下载/打印文件后线下发给工厂。
- MVP 不记录“已发送”状态，不加确认已发送按钮、不加发送回执流程。通知单只负责生成可用文件。

### 4.4 开发样品、寄样和仓库同步

**已确认**

- 开发的大版本会产生实体样品；实物最初应从开发版本下登记，而不是让业务员先在开发录一次再去仓库重录一次。
- 样品保存后，统一样品仓库自动出现同一实物档案。开发与样品仓库展示/操作的是一个数据实体和数量台账。
- 初始样品登记要记录实物形态、数量及单位。成衣样实际有两件，就必须反映两件；数量不可省略。
- **成衣样按单件管理**：每件都是独立实物、独立编码/档案和位置。即使同一版本同一规格同一来源同批次的两件衣服，也分别记录，后续才可逐件定位和流转。
- **面料样按产品档案归组、按形态登记数量**：同一款面料可在一个档案中看到色样、米样、手织样、样卡/挂钩样等不同形态各自存量；不要求给每张色卡/样卡单贴条码。
- 米样按米记录和寄出，系统根据出库量计算余量；手织样、色样等剪片类按“份”记录和寄出，不追踪剪开后剩余布料的精确面积。
- 不同物理样品类型保留适用单位；成衣按件，米样按米，色样/手织样/样卡等按份。没有在本次讨论确认的单位不由实现方自行硬定。
- 从开发业务发起寄样给客户，操作放在开发模块，因为邮寄费用计入开发案及需求方案人。保存寄样后联动样品仓库扣减相同数量并写流水，不需要样品仓库二次确认。
- 寄出数量不得超过该样品当前可用量，避免出现负库存。
- 样品仓库不加未入库/在途状态；MVP 不展开工厂未寄到或物流中的额外状态。
- 样品仓库没有“样品保管人”或“样品仓库管理员”角色；由业务员负责操作。任何文档不得为仓库职责另造该角色。

### 4.5 开发通知、费用和发票

**已确认**

- 样品制作费用记录在版本下的样品登记行，记录该行的制作费用总额；不要求拆出每件单价。
- 开发中每次寄样单独记录寄样费用，并链接到该次寄样和准确样品数量。
- 开发案费用汇总至少自动汇总所有样品制作费用及每次寄样费用；用户已明确要求保留综合总账与开发案最终发票/财务衔接。
- 寄样费用归属当前开发案，并归到开发需求方案人/负责人名下。
- 开发/样品费用形成对客 CI 时，由业务员在其正在处理的开发模块里操作开具；财务不替业务员创建该 CI。
- CI/其他已开票据随后进入财务待登记/应收视图；财务登记收款并按票据核销，业务员可在开发模块查看发票状态和票据并继续向客户催款。
- 业务模块负责业务发起和业务发票资料；财务模块负责财务账款事实。开发结束/结案不由财务控制。

## 五、大货订单管理

### 5.1 入口、主单、条目和 PO 录入

**已确认**

- 订单管理入口先分为**成衣订单**与**面料订单**，之后进入各自独立的订单业务流程。面料和成衣不在一个订单主单内混合履约。
- 一张 PO/销售合同对应一个订单主单，一个主单下可有多条产品条目。主单保留客户 PO/合同身份，条目保留各自产品、履约责任及进度。
- 若一张客户 PO 同时含面料和成衣，系统中建立两张独立订单，分别走面料和成衣流程，但保存相同客户及外部 PO/合同引用。
- PO 文件上传仅用于证据留存。MVP 不包含 OCR、自动识别、自动抽取内容或据 PO 自动填写订单；订单字段由业务员手工填写。订单来源与录入入口按下文列明，不把上传文件本身视为一条自动转单流程。
- 订单主单和条目要分开：主单展示 PO/合同、客户/交易对象和总体信息；每个条目独立记录产品、规格、履约模式及进度。面料条目按面料规格/颜色作为产品行；成衣条目按款式/颜色作为产品行，尺码及各尺码数量放在尺码矩阵中。产品来源必须可追到产品档案或准确开发版本。
- 主单代表客户 PO/销售合同的整体身份；产品行承载每个可独立履约路径。对外文件和商业条件属于主单/条目各自适当层级，准确字段清单仍须在订单开工规格定稿。
- 销售合同、订单确认等前期业务单据由业务员在业务模块处理；采购合同、委托加工合同等由业务按对应供应/加工业务流程处理，不把开具责任默认转给财务。

订单录入/来源方式（本对话讨论并作为首版来源集合继续推进）：

1. 业务员手工新建客户订单，人工录入订单和条目，PO/合同文件作为证据附件。
2. 从已接受的报价转订单，带入报价资料，由业务员核对后进入订单审批。
3. 从开发成果转订单，必须选中准确的开发版本，并将该版本规格带入产品条目。
4. 从产品档案复购，选择已有规格并录入本次商业条件。
5. 复制历史订单作为新草稿的录入快捷方式；生成新订单/业务记录，不能复制原单的生产、QC、出运、CI、收付款状态。
6. 内部订单，包括内部备货，以及面料组为成衣组创建的内部供货订单。

补单/替换订单作为关联原单的新订单建议已进入讨论；确切类型、字段与何时必须新建，留给订单开工方案明确。上传 PO 附件不应绕过人工录单、订单审批或条目级履约。

### 5.2 审批与正式订单

**已确认**

- 草稿不算订单；业务员录完信息也不等于订单已正式确认或可以生产。
- 订单要经过审批，批准后才成为正式订单并允许进入履约/生产步骤。
- 业务范围内的授权负责人审批：目前业务岗位设想为一位面料负责人、一位成衣负责人；大老板在相应范围也有审批权限。
- 有权限的人都收到同一审批待办。谁先处理，审批实例就由谁作出最终决定；其余审批人看到“已通过/已处理”和实际审批人，不会重复审批。
- 业务负责人/大老板可以审批自己录入或负责的单子；不设“自己不能审批”的人为限制。用户明确反对为了审批而让负责人无权批自己业务的方案。
- 被授权的审批人可按其业务范围审批全部相关单据。面料订单由面料负责人审批，成衣订单由成衣负责人审批；大老板有相应范围内的权限。团队成员和可审批账号的真实名单需按实际账号矩阵配置。
- **审批对象已确认是订单主单**：一次审批覆盖该订单主单及其全部条目；通过后，各条目分别解锁并独立履约。同一外部 PO 若拆为面料订单与成衣订单，则是两张订单、分别审批。不得把订单审批误设计成每个条目单独审批。
- 提交审批后锁定草稿内容；有权审批者处理后其他同一审批待办关闭，页面显示已处理状态及真实审批人。被退回时记录原因、恢复可编辑并允许修改后重提，历史审批记录保留。业务负责人和大老板可审批自己创建/负责的订单。
- 内部订单也走订单审批，不要求客户 PO；审批依据为内部用途、接收团队与负责人、条目、数量、交期、费用等订单自身信息，不额外增加一张申请单。内部供给面料订单可先于成衣订单创建并审批。

### 5.3 履约粒度、订单主页与进度交互

**已确认**

- **订单履约以产品条目行为核心单位，不以订单主单作为唯一流程单位。** 不同条目可能有不同的生产组织方式、QC 要求、工厂、数量、批次和出运时间。
- 用户进入订单列表可看到许多主单；点开主单查看该订单的条目及总体资料；逐条打开条目，进入该条目的完整履约工作区。
- 主单页面直接显示每个条目的履约进度，可使用直观的进度可视化；主单整体进度由条目进度汇总或并列展示，不能掩盖某个条目的阻塞。
- 后续履约操作进入条目详情进行；一个条目被阻塞不应把同订单其他可推进条目都误标为完成或停止。
- 条目详情使用第三节规定的逐步显露交互：未来步骤只在进度轨迹可见，内容保持锁定，当前步骤完成后才出现下一步。
- 一个条目只采用一种履约模式；若业务有不同履约模式，应由人工拆成不同条目，MVP 不让系统自行拆分一个条目并继续承担复杂混合逻辑。
- 一个成衣订单条目允许按产能拆给多家工厂、分批生产。每个工厂/生产线形成该条目的工厂履约分支，生产/检验/样品和出运都能追溯到此分支。分配数量（包括尺码数量）累计不能超过该订单条目数量；未分配数量继续留在条目下，不得超分保存。若不同工厂的生产线不同，产前样门禁按实际开产的生产线落实。
- 一个面料订单条目只由一家工厂生产；面料履约不做多个生产工厂/多生产分支拆分。实际出运如果有数量批次，由业务登记实际出运情况，主履约仍跟踪整条目。
- 同一个成衣条目内有不同尺码时，尺码以尺码矩阵/尺码数量放在该条目中，不按尺码拆成多条订单行。

### 5.4 内部面料需求和履约模式

**已确认**

- 面料组负责创建面料订单，包括供内部成衣组使用的面料订单；不能让成衣组从成衣订单里直接“代买”并绕开面料组。
- 面料订单主单/条目按正常面料业务创建，只是交易/需求对象可以标为供给内部服装组，并指明相应组/负责人。
- 成衣业务创建订单后，从内部供给面料订单列表中选择并链接到**准确的面料订单条目**，同时填清计划分配米数。同一面料供货条目可以分配给多个成衣条目，但累计分配米数不能超过该面料条目的数量；超额时阻止保存，剩余数量保持未分配。面料侧继续按正常采购/加工履约路径推进。
- 内部供给订单由面料组创建，明确供给内部成衣组及相应需求组/负责人；不能由成衣组在服装订单里绕过面料组直接创建面料采购。内部备货可没有外部客户，仍使用订单主单/条目及审批结构。
- 成衣履约路径由条目选择的一种模式决定：
  1. **纯 CMT**：面料来自客户/需求方，工厂负责加工；若 CMT 费用含有辅料等项目，明确记录包含范围，不在系统再重复采购或重复记成本。
  2. **辅料 + CMT**：面料仍非我方采购；服装业务自行组织/采购辅料，辅料成本和 CMT 加工费分别记录。
  3. **全包**：成衣条目关联面料组创建的准确内部面料订单行和米数；服装侧另行组织辅料；加工费单独记录。全包在进入成衣产前样步骤前必须完成准确面料订单行关联和米数分配。
- 用户先认可成衣履约模式的责任边界和全包的面料关联门槛；本总账记录这些业务边界，不宣称相关采购/工厂任务字段的逐项页面设计已完成。
- 面料条目的三类基础供给方式：
  1. 直接采购成品面料，记录采购货物和采购费用。
  2. 采购原料后交工厂加工，原料采购与加工费分别归集。
  3. 佣金模式：客户把货款直接付给供货方；供货方再付佣金给我们。系统不把代收的全部货款误记为我方材料成本或销售回款。
- 佣金模式按最终实际出运金额 × 约定佣金率计算。订单分批出运时，佣金只累计、不按每批频繁向财务结算；全部批次完成出运后，由业务员从订单发起一次佣金结算及对应业务票据，财务统一登记待收款和后续收款/核销。
- 用户明确要求不要在佣金模式上过度耗费讨论时间；后续优先推进四大板块其他尚缺的设计。

### 5.4.1 采购与委外加工的业务边界

**已确认**

- 采购与委外加工属于不同业务类型：采购单记录买入物料/成品及其交付；委外加工单记录原料交给加工方处理及加工结果。两类单据不能因为供应商相同而合成一个业务类型；当原料采购后还要委外加工时，两张单据分别建立并互相链接。
- 采购或加工需求从准确的订单条目发起；可将同一供应商下兼容的多项需求汇总到一张供应商单据，但每一行都必须保留来源订单条目、数量和费用归属，后续履约结果分别回到相应来源条目。兼容条件的字段规则仍待开工方案细化。
- 供应商单据合并条件已确认：采购单与委外加工单各自分组，绝不合成同一业务类型；只有供应商、币种、付款条件和主要交付地点相同，才允许将兼容需求合并。同一张单内，不同产品/工序、规格、数量、单价和要求交付日期可分别保留在各自单据行；每行仍关联准确来源订单条目。
- 原料允许采购后直接送加工厂，也允许先送到我方仓库再交加工厂；系统按实际发生记录来源、交接对象和数量，不强制所有原料先经过我方仓库。
- 一条订单条目已按可执行履约范围拆分到足够细；常规按一次完整交付处理。同一条目发生少数分批到货或加工回交时，允许逐次登记本次数量、累计计算，不覆盖既有记录，也不要求预先建立批次计划。
- 采购单/委外加工单在发给供应商、形成对外承诺前必须审批。提交审批后锁定该单；获批后由业务组生成对应的对外采购单或加工合同并发送给供应商。
- 对外承诺中的供应商、项目、数量、单价或交期等内容发生改变时，须提交修改并重新审批，保留原已批版本/审批记录；按原约定分次记录实际到货或加工回交，不因此重复审批。
- 供应商确认接单后，由对应业务组在单据行记录供应商承诺的交付日期；若供应商确认的交期与已审批承诺不同，按承诺变更规则修改并重新审批。MVP 不做系统内在线发送、供应商签收或回执流程；业务组在线下取得反馈后录入。
- 采购与加工由相应业务组完成，不另造统一采购专岗：面料事项由面料业务组经办；成衣事项（如成衣辅料及 CMT 加工）由成衣业务组经办。内部成衣用面料仍由面料组创建面料订单，成衣条目关联准确面料订单行，不从成衣侧绕过面料组另建面料采购。
- 财务不创建或发出供应商采购单、加工合同；供应商发出国内增值税发票后，财务登记供应商应付和余额、安排付款并处理多笔应付核销。订单/供应商业务履约与财务付款状态分开。

**仍待定，不得让实现方猜**

- 采购单与委外加工单的逐字段表单、单据编号、模板、供应商交期以外的确认字段/凭证、到货/加工结果登记字段、数量差异及损耗处理。
- 采购/加工单据的审批界面、退回修改与重提的逐步交互；已确认审批时点和获批后变更须重审，不代表全部页面细节已定稿。
- 原料进入我方仓库时的批量库存收货、领料与加工余料如何与库存模块衔接；直送加工方的登记不应伪造入库流水。

### 5.5 条目样品、尺码和订单级需求

**已确认**

- 每个订单条目分别保存其需要哪些评审样品/哪些 QC 门禁；即使销售合同通常是一套要求，按条目保存更稳健，避免整单混有例外时发生错误。
- 条目创建时记录所需样品评审种类；不分别设置“需要 QC”和“需要客户确认”两个开关。某种必需样品一旦选定，默认需要 QC 通过且需需求方/客户确认。
- 成衣必须包括产前样和船样；用户明确说成衣没有 TOP 样品评审节点，不另加 TOP 节点。
- 面料必须包括先锋样和船样；唯一可选的面料样品项是皮头样，不另增其他可选样品开关。
- 大货生产检验通常默认需要，只有 QC 通过门禁，不向客户发起偏好确认；它不是与样品类型同样的“QC/客户确认”双开关。用户提到小订单可能例外，但小订单的判定条件、是否免检及谁决定尚未定，不能把“所有订单无例外必检”写死。
- QC 通过是第一道门禁，需求方/客户确认是第二道门禁。两道要求都满足后才解锁下一履约动作，但系统不自动开产/出运；业务员须确认继续。
- 服装尺码矩阵包含订单生产的各尺码和数量。产前样按业务约定的标准尺码制作，系统单独记实际送审尺码和件数，不推定每个生产尺码各有一件产前样。
- 船样按每家工厂、每个出运批次记录一份样品记录；记录实际包含的尺码和件数，可以是一个或多个尺码，以客户要求和实际样品为准。QC 报告记录实际送审的尺码/件数。
- 每个存在生产数量的尺码都必须被生产 QC 覆盖。尺码仍留在一个订单行，QC 报告按实际检验内容逐码记录，不把尺码拆成多条订单行。
- 职责边界已确认：逐尺码规格/质量检验属于成衣 QC；面料由面料 QC 按面料条目及对应要求独立评审。短产/超产允差属于订单数量规则，不作为 QC 的质量结论。
- 订单明确记录生产过程中需要客户/需求方确认哪些样品。示例：面料条目不需要皮头样时，只按船样等必需门禁确认；若条目选择需要皮头样，则该条目发货前也要完成该项要求的 QC 和确认。

### 5.6 订单变更与售后

**已确认**

- 订单审批前直接修改草稿；审批后如客户改变数量、尺码/规格、价格、币种、交期、目的地、付款条件或履约模式等影响商业承诺/生产依据的内容，业务员在原订单发起变更，附修订 PO、邮件或其他依据，系统显示变更前后差异并由原业务审批范围的授权人审批。订单身份/编号保留，不把这种变更伪装成普通新订单。
- 联系人修正、备注补充等不改变商业承诺的普通信息可直接改，但记录修改人、时间和字段修改历史。
- 变更获批后，只影响尚未完成且确实受变更影响的后续工作；无关条目/工厂分支继续。已完成生产、QC、出运、CI、收付款保持其发生时的历史值，不回写覆盖。若变更与已生产/已出运数量冲突，业务先处理未完余量/差异；已出运货物由售后链路处理，不改原出运事实。
- 业务员从订单条目或具体出运批次发起售后记录，记录客户反馈、涉及数量和凭据，继续负责客户沟通。需要质量判断时由 QC 协助；补货/换货产生新的出运，不修改原出运；退款/折让进入财务处理。原订单、CI、收款和出运记录保持历史事实，售后单独显示处理进度。

本对话定了售后的责任与历史原则，但售后状态、完整字段、按钮、退款/折让与换货的逐步表单尚未逐屏定稿，不能视为售后模块已可开工。

### 5.7 生产短产/超产与数量允差

**已确认**

- 订单必须记录适用于该订单的客户短产/超产允差标准；如合同或客户要求已有明确标准，以客户标准为准，达到该标准即视为数量符合，不再额外检查内部标准。
- 只有客户没有给出适用标准时，才采用公司内部标准；实际数量在适用标准范围内即可通过数量判断。
- 实际短产或超产超出适用标准时，业务员必须与客户/需求方沟通。对方确认接受后，该数量差异可通过；对方不接受时，短产须补产/重新投产，补足合同要求数量。
- 允差默认按订单产品条目总量判断；只有客户标准明确规定逐尺码允差时，才按尺码分别校验。此数量判断属于订单履约规则，与 QC 对各尺码的质量/规格评审分开。
- 工厂通知某条目/工厂生产分支的生产已全部完成后，业务员在出运前从该履约分支点击“完成生产”，在弹窗中确认该分支完成状态并登记最终实际生产数量。此操作记录的是生产结束，不代表货物已全部出运或一次出运；若一个订单条目有多个工厂分支，各分支分别完成、分别记录。业务员此时不必收集箱唛、每箱明细等装箱资料；这些由后勤单证在出运准备阶段向工厂核实。
- “完成生产”弹窗的数量录入规则已确认：成衣默认只填该工厂分支的完工总件数；只有订单适用的客户标准明确要求按尺码判断允差时，才展开尺码矩阵并逐码填实际完工数。面料按订单条目已有的计量单位登记最终完工量。
- 成衣订单行继续包含完整尺码矩阵，不按尺码拆订单行；若该条目分给多个工厂，每个工厂生产分支须登记自己的逐尺码计划分配，所有有效分支的每个尺码合计必须精确等于订单行对应尺码数量。将一个工厂分支拆成多个生产子批次时，各子批的逐尺码数量也须精确合计回父分支；面料条目仍只有一个完整工厂分支。
- 工厂分支计划里的逐尺码分配用于说明合同尺码数量如何分到各工厂/子批，不等于要求业务员逐码登记实际完工。最终实际完工默认登记分支总量；只有客户标准明确规定按尺码核验数量允差时，才要求逐尺码登记并按对应尺码合同量判断。系统暂时无法读取该客户标准口径时，不猜测、也不允许提交完工。
- 历史工厂分支缺少尺码计划或尺码完工依据时，视为未知，不从订单总量、其他工厂或出运记录推算填补；需要先由业务核实原始分配/实际情况，才能继续相应的成衣尺码履约。
- “完成生产”按订单条目下的实际生产分支记录：成衣条目分给多个工厂时，各工厂分支分别确认完成并记录各自完工量；面料条目按其单工厂分支记录。只有当条目下所有生产分支均确认完成后，才按各分支最终实际完工量之和对照合同数量作条目级允差判断。
- 数量允差只在工厂确认相关生产分支全部完成、业务取得最终完工数量后核对；不能把出运数量当成生产数量，也不能从一次出运推断整条目已生产完成。QC 在生产检验阶段报告的阶段数量/风险仅作提前预警，不代替“完成生产”时记录的最终数量。
- 业务上必须区分“生产尚未全部完成”和“生产已全部完成但分批出运”：前者尚未生产的数量仍是未完工量，不触发最终短产允差/客户接受流程；后者按累计完工量判断短溢装，已出运/待出运数量继续作为独立的出运记录与余额管理。分批出运本身不能代替或推断“完成生产”状态。
- 生产实际数量和实际出运数量是两个独立事实：短溢装按生产完成量对照销售合同数量及允差；履约交付进度按各次实际出运量累计判断。

**仍待定**

- 客户和公司内部标准的确切字段、单位、上下限及双方均无标准时的系统处理方式。
- 超出标准的超产若客户/需求方不接受时，多余实物如何处置；这与短产补足不同，不能擅自套用补产规则。
- 谁记录客户/需求方接受、需要哪些依据，以及接受/补产完成后如何解锁出运的逐页操作和状态。

## 六、QC 评审与生产检验

> **2026-10-12 更新：**开发样品的负责人/认领、实测报告和三结论规则见[第十九节](#development-search-20261012)；大货未讨论规则不由此自动改写。

### 6.1 QC 组织和入口

**已确认**

- 面料 QC 与成衣 QC 是分开的团队/账号，各自处理本板块的工作。
- QC 人员进入工作台时先选择**面料 QC**或**成衣 QC**入口。主要分隔通过入口和工作上下文呈现，不是靠权限把另一类任务隐藏。
- 每个 QC 域内再把**样品评审**与**生产检验**分成不同的入口/Panel。样品评审应优先展示、易于识别和领取；生产检验是会在生产期间长期存在的任务列表。
- QC 需要到工厂一线检验，所以工厂信息和准确订单条目/版本信息同等重要。工厂维度影响 QC 的任务分配和路线安排。
- QC 团队可按工厂聚合/浏览待办，方便同一家工厂多条任务就近处理、自行认领；任务仍逐条关联准确条目和生产分支。每一条记录保留实际 QC 操作者。

### 6.2 样品 QC

**已确认**

- 开发、订单履约等来源模块从准确版本或条目发起 QC，不让 QC 自己凭空创建来源不明的评审。
- 样品通过 QC 是第一道门禁。正式报告回到来源业务模块及对应负责人待办；在来源页面显著可见评审状态、QC 报告和结论。
- QC 通过后，若该样品需要需求方/客户确认，则业务发起/记录第二道门禁。QC 不能替需求方确认客户偏好。
- 样品 QC 不要求自动解锁后自动开始生产或出运；完成 QC 和确认后，业务员明确继续。
- 不同尺码/实物样应记录实际送审内容；成衣样的尺码和件数须保存。面料样按实际形态/份数或米数记录。QC 报告至少有来源上下文（自动带入）、实际评审/检验环节、结论、文字说明、问题描述及附件；操作者和时间由系统留痕。现场图片和完整 DOC 或 PDF 报告可上传。复评/复检追加新报告，保留之前报告，不覆盖历史。
- 失败的样品评审通过 QC 报告返回业务处理；在报告复验通过且需求方要求满足前，不解锁依赖该样品的履约步骤。

### 6.3 大货生产 QC

**已确认**

- 成衣产前样 QC 通过并完成需求方确认后，业务员确认继续，才解锁正式开产。
- 面料生产启动后的早期实物称为**先锋样**（用户纠正过“先风样”等语音转写）。先锋样先经过 QC 评审，再由需求方确认；两者完成、业务确认继续后，后续大货生产才照常推进。
- QC 在整个大货生产过程中持续记录生产检验。不要把实际检验频次、各道工序、每次到厂时间写死成系统固定节点；现场 QC 自己判断怎么检查、何时复查，并记录检查内容。
- QC 在生产检验中发现数量短溢装问题或风险时，可在当次检验记录中及时汇报，系统通知该条目的业务负责人；业务负责人与客户/需求方沟通并处理。QC 的阶段观察只作早期预警，不替代业务员在生产分支完成时登记的最终生产数量，也不由 QC 决定客户是否接受数量差异。
- 生产检验作为条目/工厂分支下持续存在的一条检验链，不需每次巡检都重新创建独立业务对象。QC 可以不断追加检查记录。
- 生产检查结果 OK：继续追加记录，当前检验记录不停止整个业务；是否继续到下一现场环节由业务及 QC 的实际节奏推进。QC 在每条检验链里可连续记录现场过程，不要求每个工序重新建立一个独立 QC 任务。
- 检查发现问题/不 OK：QC 当次记录问题并提交报告，系统立即反馈到该条目的业务负责人，并暂停受影响的生产履约分支；不能把其他无关条目一并锁死。
- 问题修复后由 QC 再次检查并追加复验记录。满足通过条件后，系统解锁后续步骤并给业务员待办；业务员明确确认恢复继续，不能自动恢复生产。
- QC 报告至少支持文字记录、检查结果、问题描述及图片/相关材料上传；可上传完整 DOC 或 PDF 报告及检验图片。记录与来源条目、工厂、生产分支绑定。
- 生产 QC 持续在面料/成衣生产检验列表中，通常从进入大货生产直到该工厂分支相关货物出运；按现场情况持续追加。其结束/归档边界需在页面开工方案中与最后出运状态一致，不提前因单次 OK 报告而消失。成衣需按每条实际开产的产线关联产前样及相应检验上下文。
- QC 生产检验本身默认 QC 通过即可继续，不要求客户确认生产巡检报告。

### 6.4 QC 待办、回程和报告

**已确认**

- QC 工作台首页先分成衣 QC 与面料 QC 两个入口/账号工作域，每个入口显示待办数量；这不是以权限隔离隐藏另一板块任务。每个域内再分为“样品评审”和“生产检验”两组入口/Panel，样品评审突出显示、优先处理；生产检验是持续存在的跟进列表。
- 样品任务与生产检验列表至少可辨认任务类型、订单号/开发来源、准确条目或样品、工厂/生产地点、批次/生产线（如适用）、发起人、发起时间和当前状态；工厂及地点信息用于现场路线与任务分配。详情页要能看到完整来源条目、工厂名称、具体生产地点和联系方式。
- 业务发起 QC 时提供工厂及具体生产地点，并记录预计检查日期；地点优先从供应商资料带入但允许业务按本次实际安排选择。QC 可按工厂和日期筛选、聚合同厂任务并自行认领就近任务。团队内认领/转交必须保留负责人、实际检查人和转交痕迹；最终可执行的权限边界仍在账号权限矩阵中校对。
- 每个任务有明确唯一的来源条目/版本和工厂/分支；报告写回对应业务节点、准确条目并自动通知对应业务负责人，在业务模块形成明显的报告入口与待办。检查结果 OK 时按连续检验方式继续记录；问题/NOK 时发出异常反馈并暂停受影响的分支。
- QC 团队内部由谁实际完成哪次检查，按操作人留痕；团队可见不等于把负责记录的人合并成一个不明账号。
- 业务模块中的 QC 报告/待办必须明显，不能让业务员去 QC 模块反复寻找结果。
- 样品评审入口与生产检验入口分开。样品评审当前工作紧急、优先处理；生产检验任务可长期保持打开，由 QC 自主跟进。
- 通过只解锁业务员下一步；失败报告、返工和复验记录不覆盖原报告，保留历史。

## 七、样品仓库

### 7.1 仓库覆盖范围和角色

**已确认**

- 样品仓库是全公司各种实物样的统一管理台账，不局限于开发中产生的样品。开发样、订单大货样、客户来样、工厂寄样、参考样和其他实体样品都属于业务范围；本次未定完备的类别枚举。
- 来源模块能确定的样品优先由来源模块创建/登记后自动同步至统一台账；不要求业务员再次到仓库建同一份档案。
- 允许在样品仓库手工补录/建档，给历史遗留、临时来样、系统外产生或需要补录的样品使用。用户取消了“仓库手动新增必须禁用关联来源”的硬限制；不把手动登记封死。
- 用户接受此前讨论的轻量重复提示方向：手工录入时若样品名称、类别、来源、日期相似，可提示存在相似记录，由业务员判断；不能强制阻止合法补录。该防重字段/匹配阈值尚未定为精确公式。
- 系统中不存在“样品保管人”“样品仓库管理员”或其他专职样品管理角色，**由业务员操作**。仓库是物理位置和台账范围，不是账号主体。

### 7.2 档案粒度和形态

**已确认**

- 一条样品档案表达可识别的样品对象；档案展示该对象的来源、类别/形态、各形态现存量、位置及流转记录。
- 成衣样以一件实际衣服为一条独立档案：两件完全相同的样衣仍为两条记录，各有单独编码和存放位置。不得把两件衣服仅作为同一记录里的数量 2。
- 面料样以同一款/同一型号面料为产品档案聚合不同形态的样品，不强迫色样、样卡、挂钩样、手织样、米样逐张建独立条码档案。
- 一个面料产品档案内需分别看到多种形态与各自数量/长度，例如色样若干份、样卡若干份、挂钩样若干份、米样若干米；用户要在同一条目里看到“这个产品的各种样品还有多少”。
- 米样记录实物段与长度，按米出入；其他剪片、色样、手织样、卡片类以“份”记录，不需要为每片面料逐个贴二维码。
- 开发版本和产品档案必须区分：
  - 尚未转成产品的开发成果按准确版本留有独立开发样档案。一个开发案有三个轮次、每轮三个工厂版本，可以对应九个不同版本样品档案，不能把九个版本混成一个开发样。
  - 某个 QC 通过版本转为产品后，产生与该设计/版本对应的产品档案；不同设计/版本转成的产品不合并成一个版本不明的档案。
  - 产品化档案保留公司产品/销售编码及供应商产品编码，使样品能按双方实际使用的产品身份查询和追溯。
  - 一个产品档案内仍可汇总该款产品的各类实体形态样品；页面应能追溯其对应开发版本/工厂来源。
- 位置使用自由文本/人工填写，以适配挂杆、柜子、货架及未来不同存储方式；当前不要求先建立复杂库位层级。
- 顶层类别与细分形态必须能容纳各类样品，但对话尚未确认完整枚举列表。不得把“其他”或任何具体分类值写成已确认分类，除非后续用户拍板。

### 7.3 数量和流转

**已确认**

- 样品仓库台账由初始登记、领出/寄出和归还等业务动作形成数量变化记录，不允许靠一个可以随意覆盖的“库存总数”输入框取代流水。
- 开发模块登记样品后自动入统一台账；订单生产形成样品也从订单/生产来源模块创建并联动；样品管理不重复登记。
- 开发寄样在开发模块完成并同步台账出库；其他一般仓库借出/寄送等没有来源业务专用动作时可从样品仓库操作。
- 样品 QC 直接引用既有样品档案；成衣引用具体单件样品，面料引用产品档案中的对应形态记录。不得为 QC 另造一份样品对象；QC 报告可从来源业务和样品档案追溯查看。
- 出库/借出记录要可追溯经手业务员、时间、样品、数量及去向。归还从对应出库记录发起，支持部分归还；最终详细字段与按钮在仓库开工方案完成。
- 通用借出/寄出区分“预计归还”和“不归还”；有预计归还的，从原出库记录登记归还，允许分次归还并保留每次经手人和时间。
- 手工建立无来源样品是允许的，不能因自动同步而失去补录能力。
- **MVP 明确不做盘点调整**：没有记到、出现数量差异或位置不一致时，不加系统盘点单、差异修正按钮或审批过程。由人工线下处理。
- 样品移位保留原位置、新位置、操作人和时间；库位仍为自由文本，不先建立柜/货架/挂杆等固定层级。
- 不做未入库/在途等状态；不为仓储流程再设计待确认到货岗位。

### 7.4 开发版与产品化样品档案的关系

**已确认**

- 开发样品仓库必须区分“尚在开发阶段的具体版本档案”和“已转为正式产品的产品档案”，不能把一个开发案下多个轮次/多个工厂版本混成一个样品档案。
- 例如一个开发案有 3 个轮次、每轮 3 个工厂版本，应能对应 9 个各自可追溯的版本档案；其中 QC 通过并转为产品的版本，各自形成对应产品档案，其余版本继续留作开发阶段档案。产品档案不能把不同设计/版本合并到无法追溯。
- 每个面料版本/产品档案内仍可分形态登记样卡、色样、挂钩样、手织样、米样等。产品化面料档案要记录公司产品/销售编码及供应商编码；开发版本保留开发案/轮次/工厂版本的来源关系。

### 7.5 样品仓库初次建档与一般出入

**已确认的业务边界**

- 来源业务产生的开发样、订单样等由来源页保存后自动出现在仓库；除此以外，业务员可在样品仓库手工新增或补录。新增表单至少要能录类别/名称、形态、来源或无来源、初始数量/单位、手填位置、照片和备注；字段具体顺序及各类动态字段仍待开工规格落定。
- 成衣按独立实物编号选择后领出/借出；面料按产品档案及其中具体形态选择，按份或米填数量。一般仓库借出可注明去向及是否预计归还；归还从原出库记录发起，可分批归还，保留每次实际数量、操作者和时间。
- 开发流程内的寄样从开发模块发起；订单流程内的业务样寄出应从对应订单履约分支发起；系统联动同一库存记录和流水。样品 QC 直接引用已有档案，不另建一个 QC 样品。
- 位置手填；不做 barcode-per-swatch、在途/未入库、盘点或差异修正。

## 八、出运、贸易单据和财务边界

### 8.1 出运从订单到后勤单证

**已确认**

- 从订单履约到出运有一个系统交接，但不再单独制作一张人工纸面“出运通知单”再交给同公司后勤。业务员从准确订单条目/工厂分支发起系统出运交接，后勤单证在自己的模块收到待办。
- 工厂通知某生产分支全部生产完成时，业务员先在订单履约中点击“完成生产”，确认完成状态并登记最终实际生产数量；该动作不要求业务员提前取得箱唛、每箱规格等装箱详情。
- 业务员从准确订单条目/工厂分支发起出运交接时，确认本次拟出运范围和数量，并提交收货方、客户及必要上下文。生产完成状态/数量与本次出运数量分别记录；允许一个条目分批出运。
- 业务员发起时选择本批计划出运数量；后勤单证随后联系工厂核实本批最终实际装箱情况，录入 CI、Packing List 所需的准确数量/规格和装箱明细，再完成对应单据。后勤单证不代替业务员登记最终生产完成数量，也不静默更改业务员确认的拟出运范围。
- 如果工厂实际可装运信息与业务员的交接数量/信息有出入，后勤单证不得默默改写已确认业务范围；应退回业务员确认调整后再生成最终单据。
- 用户要求由设计方根据行业操作判断“谁收集什么”的合理分工，并认可上述分工：业务员在生产完成时登记实际完工数量、发起出运时确认拟出运范围；后勤单证联系工厂并核实本次最终装箱数据。
- 后勤单证完成装箱核实、CI/PL、订舱及出口申报等出运准备后，必须将已准备的单据和出运信息退回原业务员；客户沟通和对客发送始终属于业务操作，后勤单证不代替业务员联系客户或发送文件。
- CI 和 Packing List 必须在开船前由业务员发送给客户，使客户能提前准备进口清关。MVP 不集成邮件发送；业务员在线下发送后，在订单业务流程中将当前单据标记为“已发送”，记录发送时间和收件人。若单据更新，须对新版本重新记录发送；不要求客户回执。
- FOB 和 CIF 按标准贸易术语都要在开船前完成出口清关。实际申报在系统外办理；出运与单证模块只记录申报完成状态和凭证，不实现在线报关。客户办理的进口清关与我方出口清关是两项不同手续。
- Draft B/L 通常由承运人/货代在收到 Shipping Instructions 后、开船前提供供核对；Draft B/L 本身不代表货物已经出运。以船舶实际开出/实际离港（ATD）记录“已出运”；最终 On-board B/L 等正式提单在开船后归档，具体取得时点以承运人/航线实际流程为准。
- 合格的条目/工厂分支才能发起出运：规定的 QC 样品评审、需求方确认已满足，且不存在未解除的 QC 生产问题。可出运的其他条目/批次不被某一个阻塞条目连带禁止。
- 出运实际数据逐条记录并累计到原订单行/工厂分支。一个条目可以分批出运；交付履约按实际出运数量累计判断。生产短溢装则单独按工厂确认全部生产完成后的累计完工量判断：生产尚未完成、只是分批出运时，未完工量不算短产；全部生产完成、只是分批出运时，出运批次不改变短溢装判断。数量在订单适用的客户标准内即通过；客户无标准时采用公司内部标准。超出适用标准须先取得客户/需求方接受，未接受的短产须补产/重新投产补足；财务收款状态不替代履约数量判断。超标准超产被拒后的多余实物处置仍待定。

**MVP 边界与早期数量预警**

- 用户明确当前 MVP 不包含对整条订单精确跟踪生产进度的能力，不要求业务员持续维护一套完整的逐工序产量流水。此前提出的由业务员在生产跟进页持续累计维护产量的方案不作为当前 MVP 设计。
- 已确认借助 QC 已有的大货生产检验流程做早期数量预警：QC 在现场检查中发现短溢装问题或数量风险时，及时在生产检验记录中汇报，对应业务负责人收到反馈并处理。MVP 不新建完整生产进度模块；QC 报告现场观察和阶段依据，业务员依据订单允差与客户/需求方沟通并决定业务处理，QC 不代替业务作商业接受决定。具体数量字段与报告控件仍待开工规格确定。
- QC 报告中的阶段量用于提前预警，不直接判定订单最终短溢装。最终数量以业务员在“完成生产”弹窗登记、并由工厂确认生产分支全部完成时取得的数量为准，再按订单允差规则判断。
- 面料可在织布结束的胚布阶段提前发现数量风险，但胚布经过染整、后整理后长度/尺寸可能变化，故胚布米数只作早期预警，不能直接当作最终可交付数量。织机态到整理后尺寸会发生变化，见[织机态到成品态机织物尺寸变化研究](http://dl.lib.uom.lk/handle/123/18834)。成衣 QC 在哪一生产阶段能确认阶段量/最终量，以及面料各阶段何时能给出可用数量，仍待按实际流程确定。
- 后勤单证仍独立联系工厂、核实并记录每次实际装箱/出运数量，累计成客户交付进度；实际出运量不能替代业务员登记的最终生产量。用户先前提出的“部分出运/全部出运”标记可用于交付进度，但不是生产短溢装判断条件，是否需要独立控件仍待确认。

### 8.2 出运的组合规则

**已确认**

- 一次出运可组合多个订单、多个订单条目，前提是同一客户且同一收货方。
- 面料和成衣必须拆成不同出运记录，即使同一客户、同一收货方也不可放在一条混合出运流程，因为装箱/运输方式可能不同。
- 每个出运明细仍链接回自己的原订单条目、工厂分支和批次，不能因合并出运而丢失来源履约记录。
- 物理出运批次与商业单据包分开管理：CI 默认按销售合同/信用证要求分别出具，不自动合并不同合同或不同信用证；同一合同/信用证涵盖多个条目时，可以在同一 CI 中列明本批实际出运的对应条目。实际信用证内容优先于系统默认。
- Packing List 默认按一票物理出运汇总实际装箱内容，并在明细中保留各来源订单条目；客户或信用证要求分列时，按要求拆分单据。
- 同一物理出运含多个信用证订单时，系统不得假设同一套正本提单可分别满足各信用证的交单要求。若信用证单据要求冲突，须先调整单据包或出运安排，再完成交接。
- 分批出运是否允许，以该笔订单/信用证的实际要求为准；信用证明确禁止分批时，系统不得把该信用证项下的货拆成多个批次出运。此规则与订单通常可分批出运的通用能力并存。
- 成衣船样按工厂/出运批次登记，一家工厂该批次一份船样记录，允许其中包含一个或多个尺码；面料的船样也按具体条目/工厂批次实际要求管理。

### 8.3 单据制作、对客发送与外部单据

**已确认**

- 业务开发和订单阶段的业务通知/合同类单据由业务员从相应业务模块制作，例如试样通知单、订单确认、销售合同、采购合同、委托加工合同、开发样品 CI 等。
- 出运阶段由后勤单证制作我方能够出具的**CI（Commercial Invoice）和 Packing List**。
- 后勤单证制作 CI/PL 后将文件退回业务员，由业务员通过自己的订单流程联系客户并发送；不得将“制作单据”和“发送单据/对客沟通”合并为后勤单证职责。已生成的出运 CI 同步进入财务待登记应收视图；财务不制作销售 CI/出运 CI，不替业务生成票据，只登记应收、回款与核销。
- 出口报关由系统外的实际办理方完成；MVP 只在出运与单证记录完成状态和凭证，不做电子申报。FOB/CIF 都要求在开船前完成出口清关；客户进口清关由客户准备，业务员须在开船前把 CI/PL 发给客户。
- Draft B/L、最终 B/L、信用证及产地证等由承运人、银行、主管机构或其他专业外部方出具/制作；本公司不在出运模块假装自己生成这些文件，系统可接收/归档外部文件。Draft B/L 通常在开船前依 Shipping Instructions 生成供核对；它不是已出运证明。船实际开出后才登记为已出运，并在取得后归档最终 On-board B/L。
- FOB/CIF 是贸易术语；L/C（信用证）是付款/结算方式，两者分别记录，不能互相推断。信用证是银行按信用证条款、凭相符交单付款的安排；是否需要纸质正本 B/L、正本份数、收件/交单对象，以实际信用证或合同为准，不能因为付款方式是 L/C 就自动认定必需，也不能认为非 L/C 就不需要。需要正本时记录要求及正本收取、交付状态。
- 信用证分批要求必须照实际信用证执行；若其明确禁止分批出运，订单允许一般性拆批不覆盖该限制。
- Packing List 与 CI 是出运核心对客文件，可作为收款依据/提示客户付款；不得将它们混同为财务部门“开票”的专属产物。
- 开发阶段样品费用对应的 CI 由业务员在开发模块开具；出运阶段 CI 由后勤单证开具。财务只登记开好的 CI/票据并处理票款。
- 采购/加工的付款方面，供应商开具国内增值税发票；我方财务据合同、供应商发票/应付记录和公司账户余额办理付款。财务不是给供应商开付款发票。
- MVP 出运只保留合同/订单实际写明的贸易方式与付款方式，不根据 FOB、CIF 等术语自动推断责任、改变流程或额外增加复杂规则；两类术语仍分别按合同实际值记录。出运运输方式只提供海运、空运两种，并按实际方式处理相应出运资料。出口报关/清关仍由系统外办理，并须在实际开船/起飞前完成；系统只记录完成状态和凭证，不在系统内执行申报，也不靠重算贸易术语作门禁判断。
- MVP 不设独立保险字段、保险流程或保险门禁；若某份运单或外部出运资料包含保险信息，作为普通出运附件保存即可。
- MVP 记录出运准备、实际开船/起飞和外部单据归档，不继续追踪目的地到货、签收或 POD 等到货后节点。

**行业规则依据（订单/信用证的实际条款优先）**

- ICC Incoterms 资料：FOB 与 CIF 下卖方均负责出口清关；FOB/CIF 分别约定主运输等责任。[ICC Academy: FOB responsibilities](https://academy.iccwbo.org/incoterms/article/incoterms-2020-fca-or-fob/)；[ICC Incoterms 2020 Checklist](https://library.iccwbo.org/content/clp/Others/incoterms_2020_checklist_2024-update.pdf)
- ICC UCP 600：信用证文本规定适用时，按其单据条款办理；第 18 条规定商业发票应与信用证在申请人、币种及货描等方面相符，第 20 条规定信用证项下海运提单的装船标记、装卸港和正本全套要求，第 31 条规定分批装运规则。[ICC UCP 600 Rules](https://library.iccwbo.org/content/tfb/RULES/tfb-ucp600-rules.htm?AGENT=ICC_HQ)
- 跟单信用证是银行按信用证条款并凭相符单据付款的安排，不是 FOB/CIF 一类贸易术语。[ICC/Wolfsberg Trade Finance Principles](https://library.iccwbo.org/tfb/ps/ICC-Wolfsberg-Trade-Finance-Principless-2017.pdf)
- Draft B/L 通常在提交并校验 Shipping Instructions 后可供审核；开船后的实际装船信息/最终提单另行确认。[Maersk: Review step in Shipping Instructions](https://www.maersk.com/support/faqs/review-step-shipping-instructions)；[Hapag-Lloyd: Documentation](https://www.hapag-lloyd.com/en/online-business/documentation/documentation.html)

### 8.4 应收、应付和核销

**已确认**

- 财务模块查看从业务或出运产生的已开票据，登记其应收状态、收到的多笔款项，并将款项分配/核销到一张或多张 CI。票与款为多对多关系：一张 CI 可由多笔款项部分或全部核销；一笔客户收款也可覆盖多张 CI。
- 财务应收只管发票/票据有没有收到款、如何核销；不负责判断订单是否完成生产或出运。
- 供应商侧记录多个采购/加工合同/应付账目，财务掌握每个供应商未付余额；公司侧掌握账户可用余额。
- 一笔供应商付款可以是累计欠款的一部分，也可以一次结清多笔供应商应付。按付款交易将金额分配核销到一笔或多笔应付账，不能要求“一合同一付款”。
- 合同上的付款条件（例如 TT、到期时间等）影响财务待办和付款计划；付款条件由相关业务合同提供，财务掌握并登记。
- 财务维护的事实包括供应商/客户余额、公司账户余额、已开票、已收/已付和核销，不接管业务履约节点。
- 样品/开发、货物出运等不同来源产生的 CI 都可进入财务共同的收款/核销能力；来源模块保留对原票据的查看和追溯。

| 旧理解 / 曾提出的做法 | 当前有效规则 |

| 只有客户确认后才能转产品档案 | 正式 QC 通过就有资格转档，客户确认不作必需门槛 |

| 一个条目里混合多种履约模式，让系统替人拆分 | 一条目一种模式；需要混合时由业务手动拆条目 |
| 一张 PO 可在同一流程中混合面料/成衣 | 两类入口、两套独立订单/履约；同 PO 时在系统拆成两张并共享 PO/合同引用 |

| 把生产 QC 写成每道工序固定频率和一串刚性审批节点 | QC 自主安排检查节奏并持续追加记录；系统只保存检查事实/异常并执行门禁 |

| 业务员发起出运后由他独自制作全部装箱明细，后勤不核厂 | 业务员先确认拟出运范围；后勤单证联系工厂核实最终数量与装箱资料 |
| 把 FOB 当作无需我方出口报关、只有 CIF 才报关 | 按标准 FOB/CIF 口径，两者都须开船前完成出口清关；本系统只记录外部办理的完成状态和凭证 |

| 样品台账加 MVP 盘点/库存差异修正流程 | 用户明确不做盘点调整 |

## 十四、2026-10-07 角色与模块职责纠偏

用户明确指出，旧全局方案把采购、仓储等操作夸大成独立岗位，容易使后续模块设计误以为公司存在采购经手人、仓管员或仓库管理员。最新有效口径是：

1. 采购管理、委外加工、库存与仓储、样品仓库等模块和操作继续存在；模块是系统功能节点，不等于同名部门、岗位、专职人员或独立账号。
2. 面料采购/加工由面料业务组实际经办业务员处理；成衣订单及其辅料采购/加工由成衣业务组实际经办业务员处理。面料供给成衣组的内部面料订单仍由面料组创建和履约。
3. 大货库存、仓储及样品管理的相关业务操作由对应业务组的业务员按其实际经手的来源业务办理；不设采购经手资格、仓储执行资格、样品保管或样品仓库管理员角色。记录真实账号与业务对象，不虚构仓库责任人。
4. QC团队、财务和后勤单证属于真实专业分工，仍各自在其入口处理专业任务。后勤负责接收业务出运交接后的货运/单证工作，不因后勤账号承担独立仓储岗位。
5. 这一决定取代 2026-10-06 草稿中“职责资格层”“采购/仓储指定主责人名单”和“库存写权限归后勤”的建议。代码默认权限已补齐业务员及业务主管的库存操作能力；保留后勤既有必要协作权限，不把常规经办归属变成排他禁令。数据库既有授权本轮未修改，需另行只读核对后再确认真实账号是否同步。具体操作字段和流程仍在对应模块规格内细化。

2. 部门业务属性支持多选和自由增减：面料业务、成衣业务、面料 QC、成衣 QC，另含财务、后勤单证、营销、综合支持、管理等支持职能。小组从实际所属的有效部门继承属性；账号/岗位的动作权限仍独立维护。业务属性不自动授予审批或其他角色权限；老板保持全公司范围，业务门禁不被绕过。
3. 用户明确要求为现有部门设置：面料业务部=面料业务；成衣业务部=成衣业务；刚创建的综合业务部=面料+成衣业务；原质量部改名“质量管理部”，暂同时设置面料 QC+成衣 QC。用户之后将自行测试拆分为成衣质量部、面料质量部，不能代替用户提前完成拆分。
4. 人事维护补齐编辑/裁撤：部门节点可编辑名称及属性、裁撤；小组节点可编辑名称及所属部门、裁撤。裁撤保留历史引用与单据，不物理删除历史业务。
5. 本次实现的部门裁撤方式：空部门可直接裁撤；已有小组、人员或岗位时须选同公司的有效承接部门，一次事务迁移当前组织归属再停用原部门，小组和人员 ID 保留。历史单据与历史角色授权不重写，不自动增加账号角色。按组拆分时可先新建目标部门，再编辑各小组的所属部门；直属人员需在人员维护处另行安排。
6. 这些属性为分类和业务范围真源；QC操作仍需账号已有QC权限，不因部门勾选QC属性而自动获得QC操作授权。

### 2026-10-08 账号、人员、小组与业务门禁统筹（最新用户纠正，覆盖先前HR新建人员决策）

**用户明确的决定**

1. 公司成员必须与真实用户账号强绑定。人员身份创建只走管理后台“新建用户”，或用户自申请后由后台审批。HR不再有独立“新建人员”入口，不允许通过HR创建无登录凭据的人员账号。
2. HR小组只“添加已有人员”；候选必须是已创建且可用、尚未分配小组的账号，不能把角色本身当作人员。组织树小组详情直接添加成员，全部人员为账号同步名册，不承担创建身份。
3. 角色权限与部门业务属性必须明确区分，由程序自动组合判断；需先完成统一设计，不能逐页手动加例外或使用名称兜底。

**统筹建议（实现前的统一口径，不能作为已落地声明）**

- 唯一人员身份=UserAccount.id；HR员工档案以同一userId附属维护，不复制第二个身份。后台创建/审批成功后同步HR可用名册，未完善档案不再另建用户；待审批、停用、离职及已删除状态不得作为新加组候选。
- 账号角色/显式授权回答“允许哪些动作”；部门业务属性回答“在哪种职能、哪条业务线上任职”；小组归属和显式共享回答“哪些业务对象可见/可经办”；当前业务状态及QC/需求方确认等门禁独立决定“此时是否可执行”。这些条件交集生效，不能取并集放大。
- 任职部门使用账号primaryDeptId作为明确真源。加组须匹配该实际部门；小组所属部门与任职部门不一致必须先明确调岗，不能把两处属性取并集。小组自身只继承部门属性，不维护第二套角色权限。现有多组成员数据需核查，不能在讨论阶段自动删掉历史成员关系。
- 进入面料/成衣开发和新建订单：角色对应动作权限+对应业务属性；需要小组承担业务归属的新增操作另须实际任职组。QC执行：QC动作及已有专业scope+对应面料QC/成衣QC属性。财务/后勤职能可以按岗位权限处理两条业务线的下游任务，不要求其成为面料/成衣业务部门。
- 老板有效全局角色覆盖全部部门业务范围和数据范围，不用加到每组，不因总经办没有某个业务属性被拦；不跳过订单审批、QC或需求方确认。普通管理员不自动等于老板。
- 后端集中解析有效能力与阻塞原因，前端用同一结果控制入口、选项和按钮；后端写入时重新校验，部门/角色/账号状态/成员变化后同步刷新，不能只靠旧登录令牌或前端隐藏。
- 业务属性不会自动授予角色权限；分配角色不会改写部门属性；共享记录不会授予审批/QC签署等动作权限。后台应展示角色与任职属性不匹配的事实，不能暗中补齐权限。

**当前代码核对出的缺口**

- HR POST /personnel 会创建passwordHash为空的UserAccount；应撤销该创建通道及其UI，不能把“确实有UserAccount行”冒充真实可用登录用户。
- HR添加成员现仅检查本组重复，未统一检查用户active、其他有效小组归属和任职部门；需补后端事务校验及前端候选过滤。
- 部门属性已接入内部订单/内部供料、开发目录和部分采购来源校验；QC仍以账号专业scope为主，尚未接入统一部门属性判定。普通订单创建/全站入口也不能据此宣称已全部统一。
- 后台创建/审批存在先创建或激活用户、后验证角色的顺序；角色无效时可能留下部分成功状态，应一并调整为先校验后在事务内完成账号与角色写入。
- 本条目前为设计统筹与代码事实核对，尚未实施撤入口和统一权限改造。

## 十九、2026-10-12 开发与寻样设计收口记录

**范围与证据：**本节依据本轮用户确认及最终纠正补录；是业务与产品设计决定，不是当前代码实现报告或全站验收。与前文、模块旧稿冲突时，本节在开发与寻样及其样品 QC 交接范围内优先；不据此改写未讨论的大货规则。下列“已确认”包括用户明确接受的方案；专业字段的补全授权不等于每个候选字段均已拍板。

### 19.1 首页、责任与完整字段（已确认）

- 首页核心为“轮到我处理、等待协作、异常”，统计和快捷入口次要；**首页正式名称尚未确定**。首页与对应业务模块共享同一状态、数据、处理结果，任一入口操作均同步，并定位准确业务对象。
- 业务员持续负责客户及业务主线，协作有明确交出、接手和结果回程。MVP 无邮箱/未读邮件；未来邮箱接入“我的工作”。
- 每项流程必须同时设计完整业务字段：含义、填写人、必填时机、单位、选项、修改规则和跨节点传递，不能只定流程图。完整字段矩阵及逐页交互仍需核验（见 19.17）。

### 19.2 寻样是独立问答闭环（已确认）

任何找面料的需求均可发起，不限于已有档案。发起人建任务 → 执行面料同事寻找 → 已有档案直接引用；从外部供应商等找到而系统没有的面料，先录档再提交答复 → 发起人确认或退回补充。MVP 到此闭环，不自动接开发、报价、订单或采购。旧“只查询现有档案”及自动延伸后续业务的理解撤回。

### 19.3 任务分派、认领与兜底（已确认）

- 寻样可直接指定合资格面料业务员；未指定则交面料业务负责人负责分配。QC 按来源面料/成衣自动路由对应团队；明确配置面料 QC 负责人、成衣 QC 负责人，与业务负责人分开。
- 负责人兜底分配；业务范围、职责、权限均合格的人员可见待认领任务并主动认领。负责人可分给他人或自领，不是仅负责人可见，也不取消主动认领。
- 待认领不等于本人必须处理；分配/认领后只有一个执行人，并发不得重复接取。正式转交记录原因、历史和通知。无人认领仍由负责人承担责任；负责人未配置应明确提示，不让任务悬空。具体账号、范围判定及并发契约须对照实现核验。

### 19.4 开发入口、来样与寄工厂（已确认）

开发分面料、成衣入口，业务员负责主线；每个工厂任务都有具体要求和通知单。来样指真实实物，有来样才填；参考文件属于资料，不能冒充实物。开发案内直接登记来样，自动关联样品仓库同一实体，无需重复建档。选样寄工厂时记对象、数量、收件及快递信息，我方主动寄样费用必填，并关联工厂任务；多厂分别记录实际寄送。

### 19.5 面料规格、来源与分类（已确认）

- 成分逐纤维记录名称及比例，完整配比为 100%；来样已知成分与开发目标分开。
- 克重保留原值和原单位，常见每码、每米、每平方米等口径换算统一 GSM；长度重量换算必须有对应幅宽，缺数据不得猜。幅宽同样保留原值/单位并自动换算，区分全幅与有效幅宽；具体支持单位及精度仍需字段矩阵核实。
- 纱支规格独立，涵盖经纬纱支、计数制式、股数等适用资料；“组织/花型”合为一个手填字段，可填名称或几上几下，不自动推断、不拆成多个强制框。
- 成分、克重、纱支、组织虽重要，业务员未知时可标“待工厂分析”后下发；已知则填写，填数值时关联单位等信息须完整。开发目标、工厂分析、QC 实测分开，不互相冒充。
- 开发样品不设公差字段或自动偏差合格判定，由 QC 专业判断，不套用大货公差。用途、颜色参考、手感、后整理、性能分别说明；已有文件可附，不强制。手感以实物及文字表达，附件不替代实物。
- 面料分类复用现有产品分类，保留原类名，不擅自归并，不按分类自动推断成分或参数。用户强调 `data/pdml-fabric-import/pdml-fabrics.csv` 为重要基础：本次重新读取原项目该 CSV，确认 CPXL 有 20 个非空原始分类；导入脚本 `scripts/pdml-fabric-import.mjs` 使用 CPXL 映射分类。本工作树未含该 CSV；实施时应以原项目源文件核对分类全集及映射，不据分类推断参数。
- 多色可同案，工厂任务逐色记数量，结果区分颜色；主要规格变成另一款则另建案（用户已接受）。

### 19.6 费用、客户发票与财务（已确认）

- 只记录我方需要付钱的费用。工厂自付寄回不建费用记录；我方主动寄样费用必填。制作费单独记录金额和币种，与邮寄费分开；免费不虚造费用。
- 开发案费用列表明确提供“添加额外费用”，可记到付等支出：金额、币种、说明、日期，可关联任务并汇总。不同币种不直接相加。不设专门到付提示、弹窗或每次追问。
- 业务员在开发案内开开发样品发票，可选择同案各轮对同一客户的收费项合成一票，保留明细、轮次、用途并防重复收费。公司支出不自动等于客户应付。
- 财务接票登记应收、收款和核销，不代开开发票；出运 CI 仍由后勤制单。开发完成与财务结清独立。

### 19.7 成衣标识、尺码和纸样（已确认）

款式名称/标识必填，保留客户真实命名，原文可为单词、代码或组合，不强拆、不以笼统服装描述替代。独立 Style No 选填，Block 名称/号选填，两者均不等于开发版本；服装品类单列。Pattern 不设独立名称/编号字段，部位、尺码等纸样作为技术附件关联实际开发版本。打样尺码支持数字和字母，逐尺码记件数，明确修改点。

### 19.8 尺寸附件、实测与评审（已确认）

- MVP 不做结构化 Excel 粘贴映射或 AI 导入。上传原 Excel、Word、PDF 等常见文档，识别文件类型，保留原件，可打开/下载；支持的格式提供预览，不保证任意格式均可完整预览。未来 AI 转系统尺寸表须人工核对并保留来源，当前不做。
- 尺寸及技术附件绑定准确版本，更新不覆盖旧文件。QC 在系统内逐部位记实测：测量部位、样衣尺码、数值、单位，按原表人工输入并可复用项目，每件分开。
- 实测表独立于评审意见，不把每个测量项强绑照片或意见。意见另按部位/问题记文字、照片；报告分实测表、评审意见、总体结论三个部分。

### 19.9 辅料档案与用料快照（已确认原则；细分字段按授权完善）

### 19.11 工厂通知单与附件包（已确认）

通知单按工厂任务逐家生成，含具体要求、尺寸、件数、交期、面辅料、附件及本次重点。工厂联系人从现有资料带入，允许按本次任务调整。面料、成衣、辅料统一支持多文件打包，提供两个独立下载按钮“通知单”“附件包(zip)”，不得强制把通知单塞进包。包内只有本任务选定版本附件，保留原格式，通知单列明附件。MVP 下载/打印后线下发送，不设发送确认、已读或回执。改要求后重新生成并留旧版本，不覆盖其他工厂任务。

### 19.12 轮次与完整版本编号（已确认，覆盖旧 R1-A / R1-A.1 示例）

轮次是业务员一次集中时间安排的批次，**不是样品迭代次数或产品版本**。同轮各工厂可处于各自新样或修改进度；每家独立持有版本、详情、意见、QC 和确认。共同要求复制后各厂独立修改，不整轮共用修改意见。

| 编号例子 | 含义 |
|---|---|
| R1-A-1 | 轮 1、工厂 A、第 1 次实物打样 |
| R1-A-1.1 | 同一实物基础上的无新实物小修订 |
| R2-A-2 | 轮 2、工厂 A、第 2 次实物打样 |
| R2-B-1 | 工厂 B 在轮 2 首次实物打样 |

工厂字母在同案内稳定；推进轮次不自动增加实物主序号。产生新实物才增加主序号，无新实物的小修改增加小序号。同次做两件是一个版本、两件实物，不是两个版本。可基于非最新旧版继续打样并保留来源。撤回旧 R1-A 简写作为完整编号及仅用 V2 去掉轮次的建议。

### 19.14 开发样品 QC 三结论（已确认）

正式结论为“通过、有保留通过、不通过”，覆盖此前仅通过/不通过的理解。通过和有保留通过均可寄客户、转产品档；不通过不得作为确认样寄客户，也不得转档。有保留通过必须携带问题，在版本、寄样及档案可见；客户认可不把 QC 有保留通过改成通过。资料不足或尚未完检时保持处理中，不强填结论。修改后复评产生新报告，保留旧报告，不自动继承旧 QC 或客户确认。各工厂分别有报告、意见及新任务，不整轮一份。

## 二十二、2026-10-14 成本与利润核算、专业报价与 AI 辅助推荐

**本轮用户确认的架构方向，覆盖“本轮不改 BOM 菜单名”的旧决定；不是计算公式、利润底线或 AI 接线已完成证明。**

- 主模块命名「成本与利润核算」，以订单与周期经营结果为中心；BOM / 用料表只是一种参考成本输入，不代表全部核算。入口分订单核算、周期经营、成本明细、参考成本；内部 bom 路由 / 历史编号暂保留兼容，不重写已有数据。
- 预计、已承诺、实际核算分别保留；应收票面不自动当已确认经营收入，已付款不等于已耗用成本，采购不全部直接计成本，定金不当利润。同一事实不通过采购与付款重复计入；缺依据不记零值，不跨原币无依据相减。
- 专业报价的主要入口在报价条目：成本依据 → 建议报价 → 人工拟报价 / 对客报价分别记录。专业模型支持供应商报价及专业拆解两条路径；成品供应商价不再叠加其已包含的材料、加工费用。面料与成衣使用适用成本结构和准确计价单位，不从首条订单猜口径。
- 供应商报价需要核对规格、数量、单位、税费、交付条件及有效期；专业拆解包含适用的纱线 / 织造 / 染整 / 整理 / 损耗，或面料 / 辅料 / CMT / 包装等。具体专业公式、费用包含范围、收入确认、分摊及结案规则仍待逐场景冻结，不能以通用默认常数或旧行业示例值冒充市场依据。
- 商业推荐因客户及本次交易而异，不硬编码“小客户高加成、大客户低加成、新客户薄利”。可比历史成交、报价 / 还价 / 未成交原因、规格、品质、数量、交期、付款风险、服务成本和业务目标共同提供依据；成本加成率与销售毛利率明确区分。首报价、条件化让步区间、公司审批底线分别展示；AI 不自行决定底线。
- AI 报价为后续接入优先场景：规则 / 公式和计算程序负责可验证的数值、单位转换与门禁；AI 辅助提取、检索、比对、解释与方案推荐，Skill 约束步骤、来源和输出，不替代数据或计算引擎。GPT / DeepSeek 等为可配置提供者；本轮未连接模型、外部价格源或训练服务，不创造推荐数字、固定精度区间或成交概率。
- 从现在逐步准备本次报价条件、报价 / 还价 / 成交反馈、改价理由与最终核算结果的准确承接。未成交不一律归因于价格。数据充足后再判断专门模型 / 校准需要，不把接入大模型当作已学会客户接受价格。
- 报价保存输入、来源、公式版本、AI 建议和人工修改快照；后续参考成本或汇率改变不改已报价记录。最终拟报价由业务员确认，按适用政策审批再对客；AI 仅内部建议，不自动发送、不自动覆盖报价或核算。模型设置管理连接而非承载报价业务，独立定价工具逐步收敛为可复用试算。
- 实施顺序：核算基础与证据 → 报价专业核算 / 准确引用快照 → 报价反馈 → AI 辅助推荐。具体接线、验证与未完成范围继续记录于 Mist 现有迁移手册及 LIVE-PROGRESS.md，不能把本条确认记为全功能交付。
