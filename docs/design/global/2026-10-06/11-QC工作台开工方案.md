# QC 工作台开工方案（草案 v0.1）

**状态：**按已确认的 QC 分工与回程整理；具体检查字段/结果枚举需用户评判后才能冻结。
**业务决策真源：**[对话设计决策总账](./08-2026-10-06-对话设计决策总账.md) §3、§5、§6、§8。
**所覆盖产品入口：**QC 工作台中的面料 QC、成衣 QC；各自再分样品评审、生产检验。
**不在本方案内：**QC 代替客户挑选、替业务接受商业数量差异、固定所有现场工序/频率、质量结果自动启动生产或出运。

> “已确认”为对话决定；“设计提议”为可直接实现的推荐交互，但需用户确认后冻结。旧 QC 代码和旧状态机不是业务规则来源。

## 1. QC 的任务来源、分组与页面结构

### 1.1 来源与团队

- 正式 QC 任务必须由业务从开发版本、订单行/工厂履约分支等准确来源发起；QC 不在无来源页面中凭空新建评审。
- 面料 QC 与成衣 QC 为不同业务团队和账号。进入工作台后先选择“面料 QC”或“成衣 QC”；区分靠独立入口和上下文，不只是用权限把另一板块隐藏。
- 选定业务域后，工作区固定分成两个明显 panel：**样品评审**和**生产检验**。样品评审单独突出，作为优先待办；生产检验是持续存在的列表。
- QC 的任务分配按工厂和地点安排：任务卡明确显示工厂、准确生产/检查地点、联系人，以及准确来源订单条目/开发版本。QC 可在工厂视图聚合同厂多项任务，方便就近安排现场检查；认领后仍逐条报告。
- 所有提交的报告保留实际检查人，不把同队成员操作混成一个团队账号。

### 1.2 页面清单

1. **业务域入口页：**两个入口卡片“面料 QC”“成衣 QC”；显示各自待处理样品数、未结生产检验分支数、NOK 业务待恢复数量。不可合成一个没有板块上下文的总列表。
2. **域内工作台：**顶部切换 `样品评审` / `生产检验`；样品 panel 默认先显示。两类任务分别有状态筛选和工厂筛选。
3. **工厂聚合列表：**按工厂与检查地点分组，每组显示待办条数、最早要求检查时间、地址/联系人；展开后每条任务显示来源、条目/版本、类别、样品/生产线、业务发起人和状态。
4. **样品评审详情：**来源与送审实物只读摘要、工厂现场信息、报告编辑区、附件区、历史报告和当前门禁状态。
5. **生产检验详情：**准确订单条目/工厂/生产线/批次摘要、持续检查时间线、当前检查记录编辑区、历史检查记录、异常暂停/复验/恢复状态。

未来业务步骤遵循总账 §3.2：进度轨迹可见，未解锁的详情区隐藏；QC 工作台本身不因某报告自动替来源模块推进业务。

## 2. 任务卡与筛选字段

样品评审与生产检验共用以下卡片字段：

| 字段 | 读写属性 | 说明 |
|---|---|---|
| QC 任务编号 | 系统生成、只读 | 唯一任务号；报告记录另有递增序号 |
| 所属域 | 来源确定、只读 | `面料 QC` / `成衣 QC` |
| 任务类别 | 来源确定、只读 | `样品评审` / `生产检验` |
| 客户/需求方 | 来源自动带入、只读 | 用于现场前理解业务；不改变需求方决策权 |
| 来源单号 | 来源自动带入、只读 | 开发案/订单号/合同号 |
| 来源准确对象 | 来源自动带入、只读 | 开发版本；订单行、工厂履约分支、批次或产线 |
| 产品/品类 | 来源自动带入、只读 | 面料或成衣及款号/产品编码 |
| 工厂与检查地点 | 来源带入、任务级可改 | 具体工厂、生产现场/地址；默认供应商档案地址，业务员可针对本次检查改选；创建任务后改动应保留修改人和时间 |
| 工厂联系人 | 来源带入、任务级可改 | 现场联络需要；电话/联系方式遵循账号可见范围 |
| 预期检查日期 | 业务发起时填写，QC 可协商调整 | 用于路线规划，不把实际检查日期自动推导为超期判定以外的业务决定 |
| 业务发起人/责任人 | 系统带入、只读 | 报告回传的准确业务人员 |
| 当前 QC 经办人 | QC 认领后显示 | 显示具体账号；记录认领/转交时间 |
| 当前状态 | 系统派生 | 待认领、处理中、待业务处理、待 QC 复验、已通过/关闭等；最终文案待冻结 |

待办筛选建议：日期区间、客户、订单/开发号、工厂、地点、任务类别、状态、经办 QC。搜索允许订单号、款号/产品码、工厂名。列表卡不显示财务字段。

## 3. 发起、认领和现场安排

### 3.1 业务发起

业务员在原业务模块点击 **“发起 QC 评审”** 或 **“发起生产检验”**。表单从当前来源自动带入不可编辑的对象身份；业务员只补充本次任务特有的信息：

- 任务类别及送检环节（由当前业务步骤限定，只能选择该步骤允许的环节）。
- 本次实际送检的样品档案/实物、数量和单位；成衣须记录尺码和件数；面料须记录样态及份数或长度。
- 工厂和实际检查地点；优先带入来源/供应商信息，业务员可为现场实际安排选择别的有效地点。
- 联系人、预期检查日期、给 QC 的检查要求/说明。
- 参考图纸、规格、客户要求或来源附件（自动展示可访问的原始附件；业务员可补充本次专用附件）。

保存前校验来源对象仍有效、实物或条目属于当前来源、样品数量/单位有效、工厂及地点可识别。保存成功后建立 QC 待办并通知对应 QC 域，同时在业务员来源模块生成明显的 QC 状态卡和待办回链。重复提交须回读已有任务，不得重复建单。

### 3.2 QC 按工厂认领

- 未认领任务可按工厂、地点聚合展示。
- QC 点击 **“认领检查”** 后成为本任务经办人，记录人员和时间；同一任务并发认领只能有一人成功，其他人刷新看到当前经办人。
- 经办人可以提交报告；转交权限/主管代派目前没有完全确认，先不自动开放“随意改经办人”。需要改派时保留原经办人与转派人、理由及时间。
- 工厂是路线安排信息，不代表同工厂多项订单合成一个 QC 结论。每项来源仍需独立任务和结论。

## 4. 样品评审 panel

### 4.1 样品任务类型和业务门禁

| 板块 | 必做样品评审 | 可选样品评审 | 结果回程 |
|---|---|---|---|
| 成衣开发/成衣大货 | 开发样按来源版本；大货产前样按每条实际开产产线；船样按实际条目/工厂出运批次 | 本次总账没有确认额外 TOP 样节点，不得增加 | QC 通过后，业务记录需求方/客户确认；业务明确点击继续才解锁开产或出运 |
| 面料开发/面料大货 | 开发样按版本；订单生产启动后的先锋样；船样按实际条目/工厂出运批次 | 仅匹头样可按订单条目勾选“需要”；若勾选，必须有 QC 评审与需求方确认 | QC 通过后，业务记录需求方/客户确认；业务明确点击继续才解锁后续大货生产或出运 |

样品类型和必选关系由订单/开发来源决定，QC 不改需求配置。产前样和先锋样等必要样品同时需要 QC 通过和需求方确认；大货生产检验则默认只需要 QC 记录/通过，不再要求客户确认巡检报告。

### 4.2 尺码和实物覆盖

- 订单款式/颜色作为订单行，多个尺码保存在尺码矩阵中，不把每个尺码拆成独立订单行。
- 产前样通常按订单约定的标准尺码送审；系统记录实际送检尺码与件数，不预设必须每码留一件样。
- 船样按每个工厂/出运批次记录实际包含的尺码和件数；可含一个或多个尺码。
- 送审样品记录必须准确列出本次尺码与实物件数。QC 报告对实际提交的每个尺码分别记录检验结果，不能只给整款一个模糊结论。
- 成衣大货检验对订单行中每个有生产数量的尺码逐码覆盖；没有检查或未通过的尺码显式显示缺口，不能因另一码通过就令整条线通过。
- 面料评审按实际样态记录（先锋样、船样、匹头样等）及数量单位；米样按长度、剪片样按份，不引入未确认的精确面积字段。

### 4.3 报告表单（推荐最小版）

每份样品报告追加保存，不覆盖旧报告，字段如下：

| 字段 | 类型/必填 | 规则 |
|---|---|---|
| 实际检查日期 | 日期时间，必填 | 默认为当前服务端时间，可补录但保留创建时间和操作者 |
| 实际检查地点 | 文本/地点选择，必填 | 默认任务地点，可注明本次实际检查点 |
| 送检项目/尺码 | 来源带入；按实际记录必填 | 成衣每一实际送审尺码一行，面料每个送审形态一行；保留数量/单位 |
| 逐项检查记录 | 结构化简表 + 自由文字 | 检查项目模板按面料/成衣分开；完整项目清单尚待专业字段确认，不能混用一套检查表 |
| 总结论 | `OK` / `NOK`，必填 | 只有全体要求检查对象均符合才能为 OK；有任一关键问题则 NOK |
| 尺码/样态子结论 | 每行 `OK` / `NOK`，必填 | 每个实际送检尺码或样态有独立结果 |
| 问题描述 | NOK 时必填 | 描述现象、位置、涉及尺码/色号/批次；不得只写“不合格” |
| 附件 | 图片、DOC、PDF；可多选 | 支持现场图片和完整检验报告；至少显示文件名、上传人、时间和预览/下载入口 |
| 后续建议 | 选填文本 | QC 提供质量建议，不代业务接受客户偏好/商务差异 |
| 操作者和提交时间 | 系统字段、只读 | 自动审计 |

按钮：

- **保存草稿**：仅 QC 经办人保存未提交记录，来源业务看不到“已通过”；仍显示 QC 处理中。
- **提交报告**：完成必填字段后追加正式报告，计算总结果并回写来源。
- **继续评审/新增复评**：NOK 修改后创建新的报告记录，引用前次问题和报告；任何旧报告不改写。
- **返回任务列表**：保留未保存提醒。

总结果为 OK 时，来源业务得到“QC 已通过，待需求方确认/待业务继续”的待办；总结果为 NOK 时，来源业务得到“QC 未通过，待业务处理”的高优先级待办。QC 不直接在报告里代客户确认。

## 5. 生产检验 panel

### 5.1 持续生产检验链

- 大货生产 QC 不要求每次工厂巡检新建一张孤立任务，而是对准确订单行和实际工厂/生产线建立持续检验链，QC 在链上连续追加检查记录。
- 成衣生产链以 **订单行 × 工厂履约分支 × 实际产线** 为范围；每条实际开产线有对应产前样门禁和生产检查上下文。面料链以订单行 × 唯一生产工厂/履约分支为范围。
- 生产检验链从允许正式开产时创建，持续留在生产 panel，直至对应履约范围已按出运完成；单次 OK 检查不会让任务消失。
- QC 自己决定到厂频率、现场检查工序及复查时点；系统不预设成固定染色、缝制、包装等必经检查节点。

### 5.2 生产检查记录字段

| 字段 | 类型/必填 | 规则 |
|---|---|---|
| 检查时间/地点 | 系统时间 + 实际地点，必填 | 现场事实 |
| 检查阶段 | 自由文本或简短建议选项 + 可选文本，必填 | 不强制固定工序枚举；可用面料/成衣常见建议项快速选择并允许自定义 |
| 检查对象 | 来源带入、必填 | 订单行、生产分支/线、批次；面料可记织造/染整等现场阶段 |
| 尺码覆盖 | 成衣逐尺码，必填 | 覆盖本次实际检查的各尺码；记录检查数量和结果；若未查全，显示未覆盖尺码 |
| 质量结论 | `OK` / `NOK`，必填 | OK 追加记录并继续保持链打开；NOK 触发异常和阻断 |
| 检查项目/观察 | 结构化简项和自由文本，必填至少一项 | 面料/成衣各自模板；具体完整检验项目另由专业规格评定 |
| 阶段数量观察 | 选填数量、单位、说明 | QC 可报告早期短溢装风险；面料胚布长度需标“阶段观察”，不能替代整理后最终数量 |
| 问题描述 | NOK 时必填 | 包括影响范围、对应尺码/款色/工序及建议措施 |
| 图片/完整报告 | 多文件，可选 | 支持图片、DOC/PDF；上传不要求每次巡检另写一份独立长报告 |
| 操作者 | 系统自动记录 | 真实 QC 用户账号 |

### 5.3 OK、NOK、复验和业务恢复

1. **OK：**QC 追加检查记录，生产检验链保持“生产中”，不要求需求方确认报告。
2. **NOK：**QC 填写问题范围并提交；系统立即通知对应业务负责人，暂停受影响的准确产线/工厂履约分支后续步骤。其他无关条目/分支保持可操作。
3. **业务处理：**业务员查看报告并联系工厂/客户处理；QC 结论与业务商业处理分开。系统不能让业务员直接改写 QC 的 NOK 报告为 OK。
4. **复验：**QC 在原链追加复验记录，引用待复验的问题和整改依据。复验结果为 NOK 时继续阻断并产生新通知；为 OK 时满足质量解锁条件。
5. **恢复：**QC 复验 OK 只解除 QC 技术门禁、通知业务员；业务员仍须点击 **“确认继续生产”** 才实际恢复后续业务步骤。系统不得自动续产。

### 5.4 QC 生产检验数量预警

- QC 报告可记录阶段数量观察/风险，以便在现场早期发现短产或超产问题；此字段不生成最终短溢装结论。
- 业务负责人收到信息后按订单允差：客户订单标准优先；客户未订标准时按内部标准；超标准向客户/需求方确认；未接受短产需要补产/重新投产。
- 最终数量仍由业务员在工厂确认整条生产分支全部完成时登记。分批出运不影响最终生产数量判断。
- 面料在胚布阶段记录的米数仅预警；之后染整和后整理可能改变米长，不用其直接判定可交付最终长度。

## 6. 来源模块显示和待办回程

QC 提交后必须同时做到：

1. 报告关联原始开发版本、订单条目、工厂分支/生产线、样品/尺码/批次，不能仅绑定整张订单或工厂。
2. 通知准确业务负责人，并在其“我的待办”/原业务模块出现明显的 QC 回报卡；不要求业务员去 QC 工作台搜索结果。
3. 来源卡显示任务类别、QC 域、当前结论、实际检查时间、检查人、问题摘要、报告附件入口、业务下一步和是否被阻断。
4. QC 报告不可由来源业务修改或删除；后续复验为新报告并与前序记录关联。
5. 通过的样品评审或生产复验只把状态设为“满足 QC 门禁/等待业务继续”；解锁下一业务步骤前必须由业务员执行明确操作。
6. NOK 报告的阻断范围仅到具体来源行/版本/工厂分支/产线；通知内容带出阻断对象，支持业务人员从通知直达详情。

## 7. 权限与记录

| 动作 | 业务员 | 成衣 QC | 面料 QC | 主管/其他 |
|---|---|---|---|---|
| 从来源发起样品 QC / 生产检验 | 有来源业务权限者 | 不可代替业务创建来源任务 | 不可代替业务创建来源任务 | 仅在其业务权限包含来源操作时 |
| 查看任务和来源 | 自己负责/有权限的来源与回程 | 成衣 QC 业务域任务 | 面料 QC 业务域任务 | 只按现存账号/明确授权，不新增推断范围 |
| 认领/写 QC 检查记录 | 不可 | 成衣 QC 账号 | 面料 QC 账号 | 调度/转派细节待真实权限矩阵冻结 |
| 提交、复验报告 | 不可 | 成衣 QC 账号 | 面料 QC 账号 | 不允许冒名提交 |
| 记录需求方确认/继续/恢复 | 有权处理该来源业务的业务员 | 不可代替 | 不可代替 | 不能仅因 QC 主管身份执行业务操作 |
| 查看 QC 报告 | 自己可见来源与其授权范围 | 对应 QC 团队 | 对应 QC 团队 | 按现存角色/对象授权 |

每次发起、认领、转交、保存草稿、提交报告、复验、NOK 暂停、通过解锁和业务恢复都记录操作者、服务端时间、来源对象、前后状态、报告版本和附件引用。重复提交报告不得创建多份；并发认领或旧表单提交必须返回明确冲突并要求刷新。

## 8. 异常与成功反馈文案（建议）

- 来源版本/订单分支已变化：`来源业务已更新，请刷新后重新确认这次评审的对象。`
- QC 团队入口与来源不匹配：`此任务属于面料 QC / 成衣 QC，请切换到对应入口处理。`
- 认领已被他人完成：`该任务已由 {姓名} 于 {时间} 认领，刷新后查看当前安排。`
- 缺少一个或多个尺码：`以下尺码尚无检查结论：{尺码列表}。逐码补齐后再提交报告。`
- NOK 报告缺少问题说明：`检查结果为 NOK 时，必须说明问题和影响范围。`
- 报告提交成功：`QC 报告已提交，{业务员姓名} 已收到回报。`
- 复验 OK：`复验已通过，质量门禁已解除；请业务负责人确认后继续。`
- 权限不足：`当前账号没有此 QC 域的报告操作权限。`

上述措辞可统一进入界面文案规范；不可改成“系统自动生产/自动发运”。

## 9. 必须覆盖的连续验收用例

1. 面料/成衣账号分别进入不同工作域，各自看到自己的任务上下文；入口切换能显示板块区别，而不是把所有任务混成一个面板。
2. 业务员从成衣某订单行某工厂产线发起产前样 QC：QC 卡片显示款号、工厂、地址、联系人、尺码、件数和期望日期；按工厂聚合后 QC 成员认领，其他成员看到认领人。
3. 同款成衣包含 S/M/L 三个尺码：产前样按指定 M 码一件送审；报告记录 M；生产检验分别覆盖 S/M/L，少了 L 结论不能提交“全尺码通过”。
4. 产前样 QC 通过后需求方未确认：业务条目仍停在待确认，不能开产；业务确认并点继续后才解锁生产。
5. 一个订单行拆到两家工厂、三条实际产线：每条产线必须关联自己的产前样门禁；任何一条未通过不阻塞其他已满足门禁的分支。
6. 面料先锋样 QC 通过，业务确认并点继续后才允许后续大货生产；匹头样未勾选时不生成任务，已勾选时其 QC 和需求方确认都成为相应出运/履约门禁。
7. QC 在持续生产检查链追加多条 OK 记录，任务持续存在；在一条记录提交 NOK 后，精确分支暂停、业务收到待办，其他无关分支可继续。
8. 业务处理整改后，QC 追加复验 NOK 再追加复验 OK；历史记录不覆盖；OK 后业务还需手工确认恢复生产。
9. 生产现场报告阶段数量风险并注明面料胚布阶段；系统通知业务但不冒充最终短溢装结论；最终数量到生产全部完成时才登记。
10. 供应工厂、联系人和地点发生修改、任务被重复发起/重复提交、两个 QC 同时认领、过期表单提交及附件上传失败时，来源关联、任务唯一性和历史记录仍正确。
11. QC 报告通过后能在来源订单/开发详情直接查看；NOK 报告的阻断、附件、检查人和复验历史清楚显示；QC 无权替需求方确认或由业务改写报告。
12. 样品评审与生产检验是不同 panel；QC 样品待办突出；生产检验可以长期保留直到对应范围完成出运。

## 10. 需用户评判后冻结的决定

1. **面料/成衣检查项目清单：**建议系统只为常用字段提供对应板块简表，保留自由文本和报告附件，由 QC 按现场自主决定，不强行预设每道工序；需确认是否正是所需 MVP 范围。
2. **成衣逐码覆盖定义：**建议生产大货 QC 对订单尺码矩阵中实际有生产数量的每个尺码逐码记录；少任何尺码就显示未覆盖，不得整条线通过。需确认尺码有数量但本次该阶段未做抽样时是否必须由 QC 选择“未检/待下次”并保持未通过。
3. **任务分配权限：**已确定 QC 可按工厂聚合并自行认领；QC 主管强制指派、撤销认领和跨团队借调是否存在，需按真实团队规则决定。当前方案默认只有同域成员自愿认领，不新造主管角色。
4. **质量结果字典：**建议 MVP 正式结论只用 `OK` / `NOK`；草稿/处理中为任务状态；不设“有条件通过”。是否接受该最小结论集需确认。
5. 用户确认后，将准确字段/选项与权限写回本文件，并同步覆盖矩阵和实施登记。此前不把这些提议当作已冻结业务决定。

## 11. 现有实现的对照重点（非验收）

- 当前 QC 工作台、QC 路由和样品/生产检查服务已有较多代码；组件存在不能证明上述业务域、panel、逐行回程和用户权限已经一致。
- 现有成衣样品门禁服务可能按 `SampleBatch` 合并版本和实物；须按订单/开发来源、版本/实物身份和产线逐一核对。
- 检查结论、报告附件、失败复验、分支暂停和业务手动恢复须使用同一来源对象，不能由页面本地状态代替服务端权威状态。
- 静态盘点未运行浏览器/真实角色连续场景；本方案不是代码完成证据。
