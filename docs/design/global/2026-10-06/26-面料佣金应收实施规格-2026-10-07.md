# 面料佣金应收实施规格

状态：用户全站目标范围内，本轮已授权实施。业务唯一依据为 [08 对话设计决策总账](08-2026-10-06-对话设计决策总账.md)；本文件的字段、接口、锁、回执与分组方式是本轮实现选择，不追记为用户此前确认的页面细则。

## 1. 业务依据与边界

- 总账 §5.3 第 198、203、205 行：条目是履约单位，一个条目一种模式，面料一条目一家真实工厂。
- 总账 §5.4 第 221–225 行：成品采购、原料采购后加工、佣金三种面料供给方式；佣金模式客户直接付货款给供货方，供货方付我方佣金。按最终实际出运金额乘约定佣金率累计，全单所有批次完成出运后，业务发起一次结算及业务票据，财务登记应收与后续核销。
- 总账 §8.3 第 459、465 行及 §8.4 第 482–488 行：业务原票与财务登记分离，款票多对多，收款不替代履约事实。

既有定价 `CommissionPayable` 是我方支付中间人的反向应付，不参与本链。供应商采购/加工应付、客户货款和供货方应付我方佣金不能混记。本轮仅支持面料，不增加成衣佣金。

## 2. 准确条目约定及批准

`OrderLine` 新增三项 nullable 字段，无默认值、无状态回填：

| 字段 | 本轮技术值与校验 |
| --- | --- |
| fabricSupplyMode | `finished_purchase` / `raw_material_processing` / `commission`；历史 null 保持未知 |
| fabricCommissionRate | 明确百分数 Decimal，最多四位小数，`0 < rate <= 100`，仅佣金行填写 |
| fabricCommissionSupplierId | 佣金付款方的真实供应商 Relation ID，仅佣金行填写 |

业务通过草稿条目原生 POST/PUT 登记；服务端校验面料域、供应商真实组织身份及当前业务可见范围。付款供应商由业务明确指定，不按生产工厂名称推断。提交主单时再次校验，真实主单审批冻结全行中的这三项及价格、数量、单位和原规格。已提交/已批准主单的通用条目写入口继续只允许备注，不允许以这些字段绕开变更审批。

历史 null 不解释为正常采购或佣金。旧普通链保持历史兼容；任何佣金消费必须具有准确、可验证的显式批准约定。本轮不另建未经批准的事后费率覆盖入口。

## 3. 全单完成出运及金额

结算读数来自真实主单批准原件和准确原生物理出运，不消费 `Order.status`、手填 `shipmentAmount`、预计 ETD 或旧阶段。

- 每条目须有当前真实生产完工事实；当前有效生产批次全部已有准确完工记录。
- 该订单的有效出运分配均须准确到行/生产批次；对应运单实际 ATD 已发生，准确物理分配状态已 `shipped`，真实装运行/装箱数量一致。
- 每个当前有效批次累计已实际出运数量须等于其实际完工数量；仍有未发实物或在途准备批次时不结算。不将少量首批出运误判全单完成；旧未知分配不能按比例补算。
- 实际金额逐真实装运行按主单批准价格 × 实装数量（Decimal 四位小数）计算；佣金逐行累计实际金额 × 该行批准费率，再按真实付款供应商分组。

全订单只提交一次结算事件。一个订单存在多个真实佣金付款方时，该事件分别生成每个付款方的佣金 CI，保留共同结算事件及全单出运依据，不要求人为拆单。这是本轮技术组织方式。每张原票仅保留本付款方佣金行及其金额，不能混合不同应收方。

## 4. 业务原票与财务登记

- 业务 POST 从准确订单预检返回的指纹发起一次结算。字段为 `requestKey`、`expectedSourceFingerprint`、可选 `dueDate`、说明，不接受自报货款总额、佣金金额、付款方或终态。
- 同一事件在事务内创建 `TradeDocument(CommercialInvoice, domain=finance, Issued)`、准确 `DocumentVersion` 与不可变审计；票据来源前缀为独立面料佣金命名空间，原票记录实际批准/完工/出运/费率/付款方。
- 财务按准确已签发原票版本登记 `Invoice(Receivable, sourceType=FabricCommissionCI)`；金额仅为佣金，结算单位仅为真实供货付款供应商。财务不重开业务 CI。
- 原票及财务原登记的金额、来源、付款方、版本和审批证据不可普通 PATCH/cancel/delete 覆盖。原成功请求仍须当前读取授权，返回原始回执；新增消费需当前准确来源。
- 后续实收使用现有有权公司账户、收款凭证、票款分配能力；只有实际供应商佣金回款可核销该应收，客户直接付供货方的货款不进我方账户或核销。

## 5. 货款应收保护

正常出运 CI 可载明准确实际货物以支持出运；财务不得把其中佣金模式条目的全额货款登记为我方应收。

- 出运 CI 逐选中行冻结供给模式/费率/付款供应商，并在应收登记时核对准确原批准。
- 同主单正常货物行仍可从只包含正常行的准确 CI 登记货款应收，不做整单一刀切。
- 通用手工应收若只给混合主单、没有可核验的准确正常条目依据，须引导选择准确正常货物 CI；不能借“整单金额”绕开佣金行保护。
- 泛 Invoice 接口拒绝手填保留的 `FabricCommissionCI` 来源。旧未知模式不自动重分类。

本轮技术选择：同票同合同存在普通货款和佣金贸易两类责任且无实际信用证时，分别选择该责任完整子包制作贸易 CI，`packageKey` 绑定责任类别；物理 PL 仍保持整票全部实装。存在实际信用证时不推断其允许拆 CI，保留并要求完整合同/信用证包；没有准确允许分包依据时不得自动拆分或修改合同。该整票 CI 可保留货物贸易价值，但含佣金货款的版本不得登记为我方货款 AR。

## 6. 权限、重试与验收

业务需要当前 `orders:write` 和 `shipments:read`，准确订单 L2；财务需要当前 `invoices:write` 与相应读权，准确订单和原票 L2。均保留签名 token ceiling，原请求键锁在父源锁前，锁后重新核当前账号和权限。GET 不补造状态或单据。

纯测试先验证：百分数/币种/实际金额、同单多付款方分组、未知/陈旧主单依据、未全部出运、goods AR 逐行保护、原请求内容冲突、授权撤回与 ceiling。隔离 HTTP/PG 验收必须由真实业务 producer 获得主单批准、实际生产/QC/船样/出运 ATD，再生成一次佣金原票、财务登记、实际银行部分收款/核销及原键恢复；不得直接 seed 已出运、审批通过或已收款事实。全站剧本通过回调接本 producer，driver 不修改其他 driver 的业务状态。
