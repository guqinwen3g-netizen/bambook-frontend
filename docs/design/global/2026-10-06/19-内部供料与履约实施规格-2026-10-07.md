# 内部供料与履约实施规格（2026-10-07）

本轮受托实施规格。业务依据仅为 [08 对话设计决策总账](08-2026-10-06-对话设计决策总账.md)，下列数据库字段、API、版本证明与页面组织是本轮 MVP 技术选择，不倒写为用户过去逐项确认。

## 1. 已确认边界与冲突裁定

| 总账位置 | 本批必须落实 |
|---|---|
| L176、L192 | 内部备货、内部面料供给使用正常主单及条目审批；不要求外部 PO。内部用途、实际需求团队/接收负责人、条目、数量、交期与费用成为审批依据。 |
| L203、L212–215 | 每条目一种履约模式；面料业务建立内部面料单；成衣业务仅引用准确面料行及分配米数。同一面料行可供多个成衣行，累计不得超额，剩余保持未分配。 |
| L217–219 | 成衣三选一：纯 CMT、辅料+CMT、全包。CMT 明确包含范围；全包进 PP 前必须有关联准确内部面料行和米数，辅料与加工费仍分开。 |
| L184–191、L258 | 草稿不是正式订单；整主单审批通过后独立履约；样品 QC 与实际需求方确认后仍由业务员明确继续。 |
| L245–247 | 本批不定义采购/加工合同、损耗、超短收或仓库领料/余料规则，也不迁移旧内部核算历史。 |

总账 L219 没有要求内部面料必须生产完成才可 PP。因此 12 开工稿 L245 的额外硬门槛不用于本批实现；当前只核验真实有效、已审批的内部供给行及准确分配。计划分配不制造库存、到货、内部 CI、应收或付款。

## 2. 本轮 MVP 数据选择

- `Order.orderPurpose`：`external`、`internal_stock`、`internal_fabric_supply`；历史 null 保持未知。内部单保存 `internalPurpose`、`internalDemandTeamId`、`internalReceiverId`，均须真实有效。内部面料供给仅面料域，需求团队明确为成衣业务组；接收负责人须该组当前成员。内部主单没有虚构客户关系与外部 PO，展示名使用实际需求组名称。主单审批冻结这些字段，待审锁定，正式承诺变更沿既有审批边界。
- `OrderLine.fulfillmentMode`：成衣 `cmt`、`trims_cmt`、`full_package`；`cmtIncludedItems` 保存经办明确录入的包含范围。历史 null 不推定 CMT。当前批面料履约继续原有路径，不在本批虚构面料供给模式事实。
- `FabricLineAllocation`：准确 fabric/garment 主单与行，Decimal(18,4) 米数、当前 revision/status、创建/更新人时、命令 requestKey/fingerprint、审计依据。一个成衣行当前只绑定一个面料行（本轮 MVP 选择），一个面料行可分配多个成衣行。修改保留审计完整 before/after；取消留下原记录。每个成功命令有稳定回执；相同 key 相同参数恢复原成功，改变参数拒绝。
- 单位只接受明确米 `M`，不静默把码/千克换算为米；数量正数、最多四位小数。分配时锁面料行并汇总全部有效分配，任何保存都不能超过面料行当前数量。面料行缩量也要保持守恒。

## 3. 权限、命令及读回

所有公开入口只接受路由认证 actor，读取当前数据库账号、scope、L2 数据范围并保留凭据 permissionCeiling。面料供给单创建者须实际面料业务组；内部需求/供给两组不是任意可见订单即获得写权。成衣分配人须能写准确成衣订单且是指定需求组当前成员；供给候选只披露正式、内部供给该组的面料行。面料经办可以读准确源的分配去向，无权借此改成衣订单。权限撤回后旧 key 重放也重新授权，旧事实不被删除。

本轮 API：`GET /api/v1/orders/:orderId/lines/:lineId/fabric-allocation-context` 返回当前履约模式、准确分配、候选行及已分配/剩余米数、版本读取值；`POST .../fabric-allocations` 创建/修订分配（requestKey、fabricOrderLineId、metres、expectedRevision）；`POST /api/v1/fabric-allocations/:id/cancel` 取消（requestKey、expectedRevision）。响应提供 `{ok:true,data:{allocation,commandAck}}`。已提交结果未知时保留原请求及参数，用户核对原请求，不产生新 key 自动重试。

## 4. PP、开产和历史

成衣 PP 的预览/注册/追加和正式生产放行读取同一材料 gate。全包材料 proof 包含准确供给主单/行、分配 id/revision/metres、用途/需求组/接收人。proof 冻结在 PP 父来源及放行依据中；随后取消、缩量、改绑或供给失效，旧 PP 历史仍可读，但不能借旧 proof 发起新的业务推进。不会直接改写旧 QC/确认。

中性工厂/数量分配不等于正式开产，不额外要求材料完成生产。正式开产/放行仍消费准确 PP、QC/确认与材料 proof。非全包也必须显式有模式，不把历史未知当已完成。

## 5. 页面与渐进体验

主单创建/草稿编辑增加订单用途；选内部时出现用途、实际需求团队与接收负责人，外部 PO 不必填且不伪造客户。行编辑明确成衣模式与 CMT 包含范围。条目材料区按模式显示：CMT 显示含项；辅料+CMT 显示辅料/加工责任；全包显示准确供给候选、订单行、总量/已分配/剩余米数及本行分配。只有有权经办出现保存/取消。材料尚未满足时 PP 操作解释阻塞原因；已满足再出现下一动作，不自动开产。

## 6. 本批验收

纯测试先覆盖：精确 Decimal、累计守恒、模式/单位未知、旧 key 精确恢复与冲突、权限 ceiling 与撤回、proof 修订失效。独立隔离 Postgres/真实 JWT HTTP 连续执行：面料业务先创建内部单（无外部 PO）→真实主单审批→两成衣行分别分配→余量与并发超分→准确 PP/QC/实际确认→业务明确放行；缺材料/越权/撤权拒绝；取消或缩量不能继续消费旧 PP，历史可读。业务过关事实由原生命令产生，fixture 不直接制造通过 QC、确认、审批或库存。本批未运行前不标业务完成。
