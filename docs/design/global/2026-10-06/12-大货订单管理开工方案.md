# 大货订单管理开工方案（草案 v0.1）

**状态：**将已确认订单业务模型与进度体验整理成开工方案骨架；主单/条目字段、完整步骤和审批/变更表单仍待用户评判。
**业务决定真源：**[对话设计决策总账](./08-2026-10-06-对话设计决策总账.md) §3、§5、§6、§7、§8。
**相关方案：**[样品仓库](./09-样品仓库开工方案.md)、[出运与单证](./10-出运与单证开工方案.md)、[QC 工作台](./11-QC工作台开工方案.md)。
**MVP 原则：**保留完整订单条目履约和跨模块门禁；不引入自动 PO 识别、逐工序 MES、复杂贸易术语推导或系统自动替业务作接受决定。

> “已确认”来自决策总账；“建议/待定”是为了让用户快速评判而补的界面方案，未确认前不得作为实现方的默认决定。

## 1. 主导航入口和核心对象

### 1.1 入口

进入“订单管理”后先只显示两个独立入口：

- **成衣订单**
- **面料订单**

用户先选业务板块，再进入对应订单列表；列表、创建页、产品类型、履约规则和后续业务流程都分开。不可在同一订单主单中同时出现面料和成衣行。同一份外部 PO 同时包含两类商品时，人工建立两张订单，分别保留同一客户和同一个外部 PO/合同引用。

### 1.2 核心对象

```text
一份客户 PO / 销售合同
 ├─ 面料订单主单（如果有面料）
 │   └─ 面料产品条目（每款面料规格/颜色一行）
 │       └─ 一个工厂生产分支（不做多工厂拆分）
 └─ 成衣订单主单（如果有成衣）
     └─ 成衣产品条目（每款式/颜色一行，尺码数量放矩阵）
         └─ 一个或多个工厂/生产线履约分支
```

- **订单主单**代表一张客户 PO/销售合同或一张内部订单，是审批对象、商业单据主要关联对象及整体概览。
- **产品条目**是后续独立履约单位，保存产品、规格、尺码/数量、履约模式、质量样品要求、数量允差、各环节和出运累计。
- **工厂履约分支**是产品条目下的实际生产安排。成衣条目可分给多厂、多生产线或少数分批；面料条目只能一家工厂。
- **出运批次**是实际物流单位，分批出运与生产是否完成分别记录，使用[出运与单证方案](./10-出运与单证开工方案.md)。

## 2. 新建订单来源

订单列表主按钮是 **“新建订单”**。用户选择来源后进入同一订单结构，来源不同只决定预填值和证据：

| 来源 | 入口与行为 | 自动带入 | 必须人工核对/填写 |
|---|---|---|---|
| 手工录入 | 直接新建订单草稿 | 无 | 主单及条目所有信息；PO/合同文件作为证据上传 |
| 已接受报价 | 从报价单点“转订单” | 客户、产品/规格、报价币种/价格和报价附件 | 本次 PO/数量/交期/条款等商业字段；转入后仍走主单审批 |
| 开发成果 | 从开发版点“转大货订单” | 必须选择准确工厂版本并带入规格、档案回链；草稿来源不要求提前跳过订单行样品/QC/需求方门禁 | 客户/内部需求方、订单数量/尺码、价格和履约信息 |
| 产品复购 | 从数字档案/产品详情点“新建订单” | 产品档案编码、规格和供应商来源 | 本单客户条件、数量/尺码、价格、履约和交付条件 |
| 复制历史订单 | 从订单详情点“复制为新草稿” | 可选复制客户、条目规格、履约模式和历史填写模板 | 新 PO、日期、价格、数量、交期、附件等当次内容；不得复制 QC、生产、出运、CI、审批通过或收付款事实 |
| 内部订单 | 从对应面料/成衣入口新建“内部订单” | 内部需求组和人员（如已有资料） | 用途、接收团队/负责人、产品、数量、交期、费用和履约模式；不要求客户 PO |

上传 PO/合同只保存附件和文件元数据。MVP 不做 OCR、自动识别、自动填单或上传即转订单。附件不得替代业务员手工录入和主单审批。

## 3. 订单列表与主单详情

### 3.1 板块内订单列表

顶部固定显示当前 **成衣订单** 或 **面料订单** 入口标题。列表显示：

- 订单号、客户或内部需求方、PO/合同号、创建/交付日期。
- 审批状态、当前订单主阶段。
- 产品条目数、各条目独立进度；提供可读的阶段条和阻断标记，不只给一个掩盖差异的整单百分比。
- 待业务动作数、QC NOK 数、待出运条目数（如果存在）。

建议筛选：关键字（订单号、客户、PO/合同号、产品编码/款号）、审批状态、条目阶段、业务负责人、客户/内部组、下单日期/交付日期。

主要按钮：

- **新建订单**：选择手工/内部等来源并进草稿。
- **从报价转订单**、**从开发版本转订单**、**从产品档案复购**：来源入口可显示在新建按钮菜单或来源模块，不重复生成不同订单模型。
- **复制为新草稿**：详情页入口，不允许直接复制为正式订单。

### 3.2 主单详情

上方显示订单号、客户/需求组、外部 PO/合同、当前审批/主单状态、业务责任人、创建和修改时间。基础资料可回看；正式订单的商业修改必须走第 11 节变更流程。

主区以产品条目卡/表格列出：行号、产品编码/款号、名称/颜色、数量和尺码摘要、履约模式、各条目当前阶段、工厂分支数量、生产完成/出运累计、阻断/待办。用户点一条进入该条目的独立履约详情；主单不能直接操作条目里的 QC、生产和出运。

主单审批通过后整体状态为“正式订单”，各条目可以独立解锁；一个条目的阻断不改变其他条目状态。主单总览显示逐条并列进度和聚合提醒，不将条目履约压成单一主单进度状态。

## 4. 主单草稿表单

以下是针对面料和成衣入口共用的建议字段。字段粒度要在合同条款和订单行责任之间选择；建议主单值为默认，允许只有确实存在行间差异时在产品行设定不同值。

| 字段 | 类型/来源 | 必填建议 | 规则 |
|---|---|---|---|
| 订单业务板块 | 入口上下文、只读 | 必填 | `成衣` / `面料`；主单所有行保持一致 |
| 订单来源 | 系统选择、只读记录 | 必填 | 手工/报价/开发/产品复购/复制/内部 |
| 客户/交易方 | 客户选择 | 外部单必填；内部单为内部对象 | 订单主单主要交易对象；不得把内部需求人假装客户 |
| 内部需求团队 | 组织选择 | 内部单必填 | 订单由谁提出/接收；内部面料供货单必须能选成衣组 |
| 内部需求负责人 | 人员选择 | 内部单必填建议 | 对应接收业务的负责人；需要从真实账号目录选 |
| 外部 PO/合同号 | 文本 | 外部单必填建议 | 同一原 PO 的面料/成衣拆单可填写相同值 |
| PO/销售合同附件 | 文件上传 | 外部有文件时添加 | 附件作证据，允许 PDF/图片等受支持格式；不识别内容 |
| 销售确认/来源证据 | 文件上传/来源链接 | 按来源 | 报价转单、开发转单保留来源链接；只上传外部材料时不自动创建订单 |
| 订单日期/接收日期 | 日期 | 必填建议 | 人工录入或从来源预填；服务端另存创建时间 |
| 客户/内部要求交付日期 | 日期 | 必填建议 | 需要履约排序；条目间不同日期时可在条目覆盖并记理由 |
| 币种 | 货币选项 | 必填 | 单一主单原则一个主币种；一个订单下不同币种是否可存在待确认 |
| 贸易方式 | 建议下拉 | 外部订单按合同 | 依合同填，如 FOB/CIF；不据此自动改变运输/报关流程 |
| 付款方式 | 建议下拉 | 外部订单按合同 | 如 T/T、L/C；与贸易方式分开录入；信用证本身需上传文本附件 |
| 收货方/目的地 | 客户收货方选择+地址快照 | 需要出运的订单必填建议 | 允许根据合同选择多个收货方是否不同于主单值待确认；有差异时按出运组合规则分票 |
| 主单备注 | 多行文本 | 选填 | 不替代规格、客户条款或 PO 附件 |
| 条目列表 | 产品行编辑器 | 至少 1 条 | 保存草稿时也验证条目基本结构 |

订单号、条目号由系统自动生成；确切编号规则仍需决定。信息不完整时允许保存草稿但不能提交审批。

## 5. 产品条目字段和订单条目行

### 5.1 共用条目字段

| 字段 | 类型/来源 | 规则 |
|---|---|---|
| 条目行号 | 系统生成 | 主单内唯一、可排序；删除草稿行后不复用号码建议 |
| 来源产品 | 产品档案/开发准确版本选择器或手工描述 | 若来自开发必须指向具体准确版本；不得用开发案或“最新版本”泛引用。该准确规格须完成订单规定的 QC/需求方确认门禁后才能开产；若来源不完整，保存为“手工规格”且保留附件依据 |
| 产品编码/款号 | 文本/来源预填 | 一行代表一款面料规格/颜色或一款服装款式/颜色 |
| 产品名称与规格 | 文本及按板块规格摘要 | 面料包括纤维成分、组织/克重/幅宽、色号等业务确认字段；成衣包括款式、面料关联、版型与尺寸资料等；精细字段待专业模板评判 |
| 颜色/色号 | 文本或客户色号选择 | 同一条目只保留一个产品颜色；多色拆行建议 |
| 订单数量 | 正数十进制 | 必填；单位随类别，成衣以件、面料按合同单位；不可为 0 或负数 |
| 单位 | 对应产品单位下拉 | 必填；订单总量、尺码数量、完成量、出运量一致使用，换算另有明示规则 |
| 单价与行金额 | 货币十进制，按合同 | 金额只按已确认商业值；行金额可计算或手工录入，舍入方式待订单规范确认 |
| 交付日期 | 日期 | 默认主单要求，可逐条覆盖；修改正式承诺走审批变更 |
| 条目备注/附件 | 多行文本/附件 | 仅补充背景；正式规格要填到对应字段 |
| 履约模式 | 按板块显示的单选 | 每条目只能有一个模式；行间可不同；一个行不得混用模式 |
| QC / 样品要求 | 来源板块限定配置 | 每条目保存自己的样品/QC要求；不单独分别勾选 QC 和需求方确认 |
| 短产/超产允差 | 客户标准 + 内部标准备用值 | 客户已指定则按客户值，内部值不参与该单最终判断；无客户值时用内部标准；确切字段/范围待定 |

多个履约模式或不同规格应由业务员拆成多条产品行；MVP 不自动拆分或推测如何拆分。正式订单添加/拆除条目按审批变更走，不直接改写现有已履约数据。

### 5.2 成衣条目专用字段

- 尺码表：按客户尺码组创建有序尺码列，如 XS/S/M/L/XL 等；不得将不同客户的尺码语义默认视为相同。
- 尺码数量矩阵：每个尺码一个正整数或 0；所有尺码数量之和必须等于条目总数量；全为 0 不允许提交。
- 颜色：一条只对应一款式/颜色；不同颜色拆行。
- 履约模式三选一：
  1. **纯 CMT：**面料归客户/需求方提供；记录面料所有方/供应路径及 CMT 包含范围，避免对已含项目重复采购或重复记成本。
  2. **辅料 + CMT：**面料不由我方采购；辅料由成衣业务组组织采购，辅料费用与 CMT 加工费分开归集。
  3. **全包：**关联面料组创建的内部面料订单准确行及分配米数；成衣组另外组织辅料；加工费单独登记。进入产前样前必须已绑定有效面料订单行及米数。
- 可拆分工厂/生产线：每个分支填工厂、产线、尺码数量矩阵、交期和本厂要求；所有工厂累计尺码数量不得超过主条目矩阵；有未分配数量时保留待分配余额。
- 每条实际产线开产前都需要对应的产前样门禁；条目不能只用另一产线已经通过的样品自动放行。
- 同一条目一般采用一个履约模式；遇到混合供货的 PO，人工拆成多个产品条目，不能一个条目同时跑纯 CMT 和全包。

### 5.3 面料条目专用字段

- 款式/色号/规格：一行一款面料规格和颜色；多色拆行建议。
- 面料单位：按合同实际单位选择，如米、码、公斤等，且全条目统一；对外短溢允差沿用该单位。
- 面料履约方式三选一：
  1. **直接采购成品面料：**一家具备来源的供应工厂负责提供成品面料，记录采购成本和交付。
  2. **采购原料后加工：**记录原料采购行、委外加工行及对应链接；采购费用与加工费分开。
  3. **佣金：**客户把货款直接支付给供货方；供货方按约定给我方佣金。佣金依最终实际出运金额和佣金率计算，所有批次出运完成后一次向财务提交结算。此方式不把供应方收的货款记为我方销售回款或材料成本。
- 一个面料条目只由一个生产工厂履约；不提供多工厂生产分支拆分。
- 内部供给面料条目需明确“供给内部成衣组”和具体团队/负责人。由面料组创建面料订单，成衣条目引用其准确面料订单行和米数。

## 6. 每条目样品/QC 要求

### 6.1 必需规则

| 面料订单条目 | 成衣订单条目 |
|---|---|
| 先锋样：QC + 需求方确认 | 产前样：每条实际生产线 QC + 需求方确认 |
| 船样：每家工厂/出运批次一份；按实际送审形态/数量记 QC 和需求方确认 | 船样：按工厂/出运批次一份；可含一或多个尺码，实际尺码和件数录入后 QC 和需求方确认 |
| 匹头样：唯一可选；勾选后该条目要求 QC + 需求方确认 | 不出现 TOP 样品节点 |
| 大货生产检验：通常默认需要 QC 通过；不需客户逐次确认 | 大货生产检验：通常默认需要 QC 通过；不需客户逐次确认 |

用户规则：某一种样品一旦需要，默认同时要求 QC 通过和需求方/客户确认；不设置单独 QC 与单独客户确认两个开关。小订单可能是生产 QC 的例外，但判定条件、决定人尚未定稿，不能默认为全部免检或全部无例外。

### 6.2 条目创建表单

每行展示系统模板要求：面料只显示先锋样、船样、匹头样开关（只允许取消匹头样）；服装显示产前样、船样必需项，不能提供“是否需要”开关。样品尺码、件数和实物形态不在主单录入时强制编造，在实际发起样品 QC/登记样品时记录准确送审信息。

## 7. 订单审批

### 7.1 提交校验

草稿保存后点击 **“提交订单审批”**。只有主单全部条目可用且数据完备才提交。审批对象为订单主单、一次覆盖所有行；如果一份 PO 分成面料订单和成衣订单，两张主单分别审批。

校验至少包括：

- 订单至少一行、产品板块与当前入口一致。
- PO/合同号和必需附件有值；若内部订单，无外部 PO 附件不构成阻断，但内部用途和需求团队必须完整。
- 每个条目产品描述、数量、单位、币种/价格（适用时）、交付日期、履约模式及 QC/样品要求有效。
- 成衣尺码矩阵总数与行总数一致；供应工厂/生产分配尚未创建时，不因未分厂阻止订单审批。
- 全包成衣行可先审批，但在履约中进入产前样前必须完成内部面料准确订单行和米数绑定。
- 条目内部面料供货对象、款色与实际面料条目兼容；准确兼容字段等订单联动规格确认。

提交时内容锁定并向该业务域所有授权审批者创建同一审批待办。

### 7.2 审批待办和结果

- 面料订单待办发给面料负责人及具有面料审批范围的大老板/授权人；成衣订单发给成衣负责人及具有成衣审批范围的大老板/授权人。
- 审批者可以审批自己创建或负责的单；禁止“自己不能批自己”的人为限制。
- 有审批权者点 **“批准正式订单”** 或 **“退回修改”**。第一位完成动作的审批者决定结果；其他待办关闭并显示处理人、时间、结果，不可重复决定。
- 批准后订单变成正式订单；所有条目各自解锁首个履约步骤，业务员仍需在条目内按步骤点击继续。
- 退回必须写原因；草稿恢复可改，原审批记录保留；业务员修改后重新提交会产生新审批轮次和差异摘要。
- 审批意见、申请人、审批人、角色范围、时间、批准/退回、原始数据快照和后续重提都不可覆盖。

### 7.3 待确认的审批范围字段

真实的面料负责人、成衣负责人和大老板账号授权列表需要与生产账号、角色文档对齐；不能按旧文档中的单人限制或广泛 `ADMIN` fallback 擅自设计。领导/主管是否在业务批准之外拥有直接编辑正式订单的权限尚未由对话确认，不将审批权推导成直接改单权。

## 8. 条目履约详情与进度式界面

### 8.1 页面交互

条目详情顶部固定订单、客户、PO/合同、产品规格、数量/尺码、履约模式和工厂分支摘要。其下是一条水平阶段轨迹：

- 已完成步骤可点开回看历史。
- 当前步骤是唯一显示详情区，可以编辑并完成。
- 后续步骤只显示名称和顺序，不可点击进入、不可展开内容、不可滚动预览未来表单。
- 通过 QC 或需求方确认只解锁下一步；由业务员点击 **“确认继续”** 后进入新步骤。
- 当前步骤缺字段/被阻断时，页面直接显示原因和对应待办入口；不只用灰色按钮让用户猜。
- 履约分支可有自己的步骤/门禁，条目页汇总各分支状态；分支可分开推进。

### 8.2 成衣履约步骤建议

1. **检查订单与履约模式**：已审批资料可读；确认责任模式及客户要求。
2. **材料/供应组织**：全包模式绑定面料组内部订单行和分配米数；辅料+CMT 录辅料；纯 CMT 明确含料/含辅料范围。每一模式仅显示相应工作字段。
3. **分配工厂/生产线**：建立工厂分支，填写尺码数量矩阵、工厂/联系人、计划开产、交期及工厂专属要求；已分配量不能超过行尺码矩阵。
4. **产前样**：每条实际生产线创建/登记产前样，记录准确尺码/件数，发起成衣 QC；QC 通过后业务记录需求方确认并手动继续。
5. **正式开产**：只有所有必要材料/产前样门禁满足的生产线解锁；确认开产动作。
6. **生产检验**：成衣 QC 对实际有量尺码逐码覆盖，持续追加 OK/NOK；NOK 暂停受影响产线，复验通过后由业务确认恢复。
7. **完成生产**：工厂确认分支全部生产完成后，由业务员记录最终完成件数；按客户允差优先、内部允差兜底判断；超出标准处理客户接受/补产。
8. **船样**：在对应工厂/出运批次登记送审实物的尺码/件数，QC 与需求方完成门禁后解锁本批出运。
9. **发起出运**：从条目/工厂分支提交给货运单证；后续真实数量与文件步骤见出运方案。

某些条目分支可能先准备船样、后登记最终生产完成信息；准确操作时间应遵循该批货样品实际可取得且 QC 通过，不通过时不能发运。成衣产前样门禁必须先于该线开产。

### 8.3 面料履约步骤建议

1. **检查订单/供给方式**：成品采购、原料+加工、佣金三者之一。
2. **面料生产安排**：一条目一生产工厂；按供给模式建立采购/加工/佣金数据及供应交期。
3. **先锋样**：生产启动后的早期面料样登记并发 QC；QC 通过后需求方确认、业务确认继续，才解锁后续大货生产。
4. **生产检验**：QC 持续记录，不固定每道工序；阶段米数预警不替代整理后最终数量。
5. **完成生产**：工厂确认完全生产结束，业务员按面料计量单位登记最终数量，执行条目允差校验。
6. **船样及可选匹头样**：船样为必需；勾选匹头样的条目，需额外完成 QC 和需求方确认。二者均解锁本条目的出运流程。
7. **发起出运**：交给货运单证；分批出运累计到订单条目。

有的面料采购为成品直接到货、不经过我方生产线；需在采购/仓库方案中确定“先锋样在何时从供应方出现以及实际送审对象”。本方案不假设采购成品必然产生我方生产工序。

## 9. 内部供给面料订单与成衣联动

1. 成衣组不能在服装订单里直接建立面料采购。
2. 面料组从面料订单入口建立内部订单，交易/需求对象选内部成衣组和需求负责人；正常填面料产品、供给数量、币种/费用、交期和履约方式，走面料订单审批与履约。
3. 成衣订单的全包条目在材料步骤点 **“关联内部面料”**，搜索状态可供给该需求组的面料订单行。
4. 用户选中准确面料订单行，系统显示面料编码/颜色/供应方、订单量、已分配米数、剩余量和当前进度；成衣业务录本条分配米数。
5. 面料行可供多个成衣条目消费；总分配量不能超过面料订单行数量；保存时并发重新校验，超量阻止保存。
6. 双方互见准确链接：成衣行可读面料供货进度；面料业务能看到内部接收方/已分配成衣行；但面料采购/生产责任和成衣履约责任分属各自模块。
7. 若内部面料行尚未生产完成，成衣全包条目保持材料等待，不允许跳过前置材料门槛进入产前样/开产。

内部面料是否向内部服装组“销售”时仍需正式商业 CI、内部金额和结算如何处理，未在当前讨论定稿；MVP 不得凭空创建客户应收或假设跨组免单。

## 10. 订单履约样品进入统一仓库

- 成衣/面料订单中实际登记产前样、先锋样、船样、匹头样及生产样后，来源模块创建或关联样品仓库同一实体；不重复登记。
- 成衣样逐件独立样品身份；面料样按其准确产品/订单来源档案内分形态记录份数/长度。此粒度引用[样品仓库方案](./09-样品仓库开工方案.md)，订单无需复制一套仓库数量。
- 船样、产前样/先锋样由来源条目发起 QC，QC 报告引用同一实物/样品身份。QC 通过不等于已寄给客户；业务在需求方确认流程中记录实际结果。
- 条目可按出运批次发起业务寄样/船样；数量单位、扣减规则按样品档案适用类别执行。

## 11. 订单变更

### 11.1 普通订单编辑

- 审批前草稿可以编辑；修改后提交最新版本审批。
- 审批中字段锁定；需要修改时先撤回或由审批人退回，原申请和差异留痕。
- 正式订单的商业/履约承诺变更从订单主单/对应产品条目点 **“申请订单变更”**，保持原订单身份和编号；不能直接覆盖或要求作废重建。
- 变更表单显示被选中的条目、字段原值、新值、变更原因及修订 PO/邮件等证据。可对条目行、数量/尺码、规格、价格、币种、交期、目的地、付款条件、履约模式等选差异。
- 提交后展示变更前后对比、受影响条目/生产分支及无法影响的已完成事实，送与原订单相同的授权审批范围批准。
- 获批后只改变未完成且受影响的后续工作。已完成生产、QC、出运、CI、收付款记录保留为历史事实。改量/改规格与已生产/已出运冲突时，业务员先处理未完余量；已出运货物走单独售后。
- 不改变商业承诺的联系人、普通备注可直接改并留下字段级修改历史。

### 11.2 冻结状态

履约中的正式订单是否仍允许修改已有关联的客户/收货方、已下发采购/加工订单和已生成发票等具体对象，按变更审批影响分析；系统必须阻止对已经发生且外部可见的 CI/PL/供应商合同做静默覆盖。文件更正应产生新版本并保留旧版。

## 12. 生产完成和短溢装

生产数量规则在条目级执行，不靠出运批次猜生产完成：

- 每个成衣工厂/生产分支分别完成登记；只有整个实际分支完工时，业务员点击 **“完成生产”**、录最终实产量。成衣默认只录总件数；订单客户标准明确按尺码时才展开尺码完工矩阵。
- 每个面料订单行唯一工厂生产分支全部完成时，业务员以订单单位录最终长度/数量。
- 条目下成衣各分支完成后，系统聚合并跟订单总量比；面料用唯一工厂的最终数。最终允差按客户标准优先，客户无标准才用内部标准。
- 数量在适用标准内即通过。超出标准时，业务员提交需求方接受证据；未接受的短产需要补产/重新投产补足。超产未接受后的处置尚待定，不许系统自动吸收或退仓。
- QC 生产检验可报告阶段数量/风险，通知业务负责人；QC 不决定客户是否接受，不替代最终完工量。
- 分批出运是交付进度；生产完成是生产事实。未全部生产完时不对尚未生产量判短产；全产完但分批发运仍按最终完工总量判断生产允差。

## 15. 异常、空态和防重

- 无 PO 文件：如果外部客户订单规则要求附件，阻止提交审批并提示补附件；内部订单以内部用途和负责人资料替代外部附件。文件证据仅存档，不尝试 OCR。
- 尺码矩阵不平衡：提示“尺码数量合计 {a} 件，订单总数量为 {b} 件”，无法审批。
- 分配超量：显示当前已分配/申请数量/行总量，阻止保存并保留未分配量。
- 内部面料余额不足：明确显示剩余米数和已分配成衣条目，阻止超额。
- QC NOK：工作区只显示被阻断的准确分支和问题；旁边其他可推进分支仍可操作。
- 门禁未完成：未来步骤维持锁定，并显示“需完成 {具体样品 QC / 需求方确认 / 面料关联 / 变更审批} 后继续”。
- 订单审批被并发处理：先提交成功的授权审批人获得最终处理权；其他人刷新看到处理人/结果。
- 重复转单/网络重试：依据来源报价/开发版等唯一幂等键回读原草稿或用户确认重复建新，而不是重复建单。
- 订单条目删除只允许审批前的草稿；正式订单变更只走申请/审批。已做过 QC/生产/出运的行不物理删除。
- 服务异常时草稿内容保留且显示可重试；涉及正式审批/变更/履约的写入需防止重复提交。

## 16. 需用户评判的订单方案

以下任一项没有冻结前，订单规格不能交给 coding agent 自行决定：

1. **主单字段层级：**币种、贸易方式/付款方式、收货方、信用证附件等建议主单提供默认值，确有条款差异时允许条目覆盖；是否支持不同条目币种/收货方/贸易或付款条件？建议一份合同同一主单统一，只有实际合同逐行不同才允许例外。
2. **最终主单/行必填项：**目前建议以上表字段为基线；需决定供应方 PO/正式销售合同是否作为独立单据节点、编号方式、日期/单位和金额精度。
3. **订单行的面料/成衣结构字段：**建议以产品档案/开发规格作为主要数据源，手工规格需要最小通用字段和规格附件；需要确定面料与成衣表单的实际字段目录及行拆分规则。
4. **供应商/工厂分配发生时点：**成衣工厂分支是在订单审批前还是审批通过后创建？建议审批前只需有可审批的履约模式和计划数，获批后再拆分工厂分支；若合同已指定工厂，可记录计划工厂但仍保留后续分支安排。
5. **成衣样品节点顺序：**产前样每条产线必需在开产前；船样在实际出运前；生产检验贯穿生产。需评判在条目进度条中 ship sample 是产量完成后单独步骤，还是允许与生产检查并行显示为当前分支任务。
6. **面料直接采购成品时先锋样的来源/门禁时点：**建议由供应方提供的最初成品/色样登记为先锋样，先 QC、再需求方确认、通过后允许继续该批采购/供应履约；实际供应不经过我方生产环节时，需要明确“解锁什么动作”。
7. **允差数据字段与接受记录：**需要用户给定常见允许短产/溢装字段、单位或公司内部标准来源；客户标准覆盖内部标准已确认，字段值和例外证据未定。
8. **领导/主管权限：**对应负责人/老板可审批自己的订单已确认；是否也能直接编辑他人或自己的正式订单未确认，建议所有承诺变更仍走有差异、留证据的正式变更审批。
9. **来源订单证据不足时的审批：**PO/销售合同必须附件还是订单确认邮件/微信记录可代替；口头确认能否暂建内部草稿、不得生产？需要精确冻结。
10. **内部供给面料的商业结算：**面料组为成衣组供面料使用正常面料履约链已确认；跨组应收、内部单价、付款/财务处理未定，不应生成虚构的客户 CI。
11. **取消/拒单/终止订单：**审批退回已确认；正式订单在没有生产但不再执行、部分履约后终止的操作及原料/成本处理待后续订单异常方案。
12. **小订单生产检验例外：**是否可不做持续 QC、由谁决定以及如何仍保留必要样品 QC，待用户决定。

## 17. 必须覆盖的订单端到端验收

1. 同一 PO 同含面料和成衣：业务建两张订单、保留相同 PO 附件/编号；订单类型入口、审批对象和后续履约隔离正确。
2. 手工 PO 上传：文件原样保存，页面不出现识别/自动填单，业务员逐字段录入并提交主单审批。
3. 报价/开发版本/产品档案转订单：来源信息准确预填；开发转单精确锁定某一版本，不合并相邻版本；未满足准确版本及订单所需的 QC/需求方确认时不能开产；复制历史订单不会复制任何审批、QC、生产、出运或财务完成事实。
4. 内部备货订单无客户 PO 仍可走主单审批；内部面料订单由面料组创建、供给成衣组，后续成衣条目只链接准确面料行。
5. 授权业务负责人批准自己录入的订单；两个审批人同时打开时只有一人处理成功，另一个显示真实处理人和结果；退回理由、修订和再审批历史保留。
6. 一张主单两条产品行履约模式不同：每行显示独立路径/进度；某行 NOK 不冻结另一条行。
7. 成衣同一行含多尺码矩阵、拆给多工厂/多产线；已分配和未分配数量精确，不能任一尺码超分；每条产线只有自己的产前样通过后才能开产。
8. 面料订单不允许多个工厂生产分支；若安排多批出运，则同一面料履约条目仍累计其出运批次，而不是误生多工厂生产支线。
9. 全包订单链接内部面料行并分配米数；上限校验并发安全；未关联面料前，不能在产前样未来步骤跳过材料约束。
10. 每条目样品要求按板块生成正确控件；不能新增服装 TOP、不能对各样品分别勾选 QC/确认；生产 QC 仅 QC 通过，客户样品确认是独立门禁。
11. QC NOK 报告暂停准确生产分支；复验 OK 后业务员手动恢复；成功后在工作条目显示摘要和历史。
12. 工厂分支部分生产和分批出运独立登记；全部生产完成后业务员记录最终数量，允差逻辑按客户/内部标准处理，出运量不覆盖生产量。
13. 条目进入“发起出运”时跳转到同一条出运请求并可添加兼容订单行，CI/PL、业务发送、财务应收各自回写，不改变条目生产阶段。
14. 主单待审批、退回、正式、部分条目完成、部分条目阻断等状态下，列表的条目进度和动作数准确，不以整单聚合隐藏阻断或放行错误。
15. 正式订单变更只影响批准范围内的未完成后续步骤；已完成 QC、生产、单据、出运和资金信息保持原历史。

## 18. 当前代码对照提醒（不是实现确认）

- 当前订单管理存在以主单聚合进度和主单状态驱动的旧结构，不能仅通过局部加进度标签就视为完成条目履约模型。
- `OrderManager` 及订单相关组件/服务同时含订单行与主单级操作；需要检查每个按钮实际写入对象和外部读取，不凭页面结构推断后台履约实体。
- 订单确认/审批、业务内部面料供货关联、供货数量预留、样品门禁、逐条目出运等必须作为同一条身份链可回读。
- PO 导入/API 与人工录入可能共存；按总账关闭任何自动识别或自动填单可见入口和后端写入捷径。
- 本方案是业务和交互规格草案。无测试、真实角色权限、订单到出运连续浏览器用例的结果，不能登记为已实现。
