## §2 写操作三阶段闭环

所有写操作工具遵循 **draft → approval → commit** 三阶段闭环，这是 Agent OS 区别于「直接调 REST API」的核心安全机制：

```
LLM call_tool (toolId, input)
  │
  ▼
toolRuntime.executeAgentTool
  │ ① draftPhase: 生成 ProcessDraft（六字段，含 before/after diff）
  │ ② 落库 ApprovalRequest (status=pending, payload.processDraft)
  │ ③ 返回 { approvalRequired:true, approvalId, processDraft }
  ▼
agentLoop 挂起 → emitApprovalBlock → 前端审批气泡
  │
  ▼  用户审批 (POST /agent/approvals/:id/resolve)
approvalEventBus.emit('resolved', approvalId, {decision})
  │
  ▼  decision=approved
agentLoop 重跑 (skipApprovalCheck:true, approvalId)
  │
  ▼
commitTransaction.commitXxx (prisma.$transaction, Serializable)
  │ ④ 从 ApprovalRequest.payload 恢复 ProcessDraft
  │ ⑤ hash 校验（防篡改）+ 语义校验（业务规则）
  │ ⑥ $transaction 原子提交（写 AgentCommitReceipt + 业务实体 + AuditLog）
  │ ⑦ 返回 CommitResult (ok/committed/entityLinks/audit)
  ▼
agentLoop emit tool_call_end (complete) → 前端工具卡变绿
```

> **设计决策**：draft 在审批前生成，commit 从审批 payload 恢复 draft——保证「审批什么就提交什么」。draft 的 `idempotencyKey` 是内容 hash（`computeProcessDraftHash`），任何字段篡改都会导致 hash 不匹配，fail-closed。

## §3 ProcessDraft 六字段契约

`ProcessDraft` 是审批卡内容 + commit 事务输入的唯一真源。六字段全部必填，硬性验收：

| 字段 | 类型 | 说明 |
|------|------|------|
| `subOperations` | `SubOperation[]` | 子操作列表（toolId/entityId/action/before/after） |
| `beforeAfterDiff` | `FieldDiff[]` | 字段级变更 diff（entity/entityId/field/before/after） |
| `impactScope` | `string[]` | 影响域（如 `['orders','invoices']`） |
| `irreversible` | `boolean` | 是否不可逆 |
| `postCommitHooks` | `PostCommitHook[]` | 后置钩子（email/sms/webhook/notification） |
| `idempotencyKey` | `string` | 内容 hash（`pd:xxxx`），幂等防重主键 |

### 3.1 SubOperation 结构

```typescript
{
  toolId: 'orders.update_status',   // 子操作工具
  entityId: 'PO-001',                // 操作实体
  action: 'update_status',           // 动作
  before: { status: 'Pending' },     // 变更前快照
  after: { status: 'Confirmed' },    // 变更后目标
}
```

### 3.2 idempotencyKey 计算

`computeProcessDraftHash` 用稳定 JSON 序列化（递归 key 排序）+ djb2 hash，覆盖前五字段内容：

```typescript
const canonical = stableStringify({
  subOperations, beforeAfterDiff, impactScope, irreversible, postCommitHooks
});
// djb2 hash → "pd:a1b2c3d4"
const idempotencyKey = `order.confirm:PO-001:pd:a1b2c3d4`;
```

> 内容相同 → hash 相同 → 幂等；任何字段变化 → hash 不同 → 视为新操作。

## §4 commit 事务引擎

### 4.1 commitOrderConfirm 流程（基准实现）

`commitTransaction.commitOrderConfirm` 是所有写操作 commit 的基准范式：

| 步骤 | 校验/操作 | 失败语义 |
|------|-----------|---------|
| ① 恢复 draft | `recoverProcessDraftFromPayload(payload)` | draft 缺失 → fail-closed |
| ② 语义校验 | `validateProcessDraftSemantics(draft)` | 缺 update_status/缺 invoice/状态非 Pending→Confirmed → fail-closed |
| ③ hash 校验 | `verifyProcessDraftHash(draft)` | hash 不匹配（篡改）→ fail-closed |
| ④ 写 receipt | `agentCommitReceipt.create(status='committing')` | P2002 唯一冲突 → 返回已提交结果 |
| ⑤ 状态流转 | `orderStatusTransition.create` + `order.update` | STATUS_DRIFT → fail-closed |
| ⑥ 创建发票 | `invoice.create(status=Issued)` + `syncInvoiceReferences` | 金额无效/币种缺失 → fail-closed |
| ⑦ 审计 | `auditLog.create(action='order_confirm_committed')` | 审计失败 → 事务回滚 |
| ⑧ 更新 receipt | `agentCommitReceipt.update(status='committed', result)` | — |

### 4.2 并发安全（Serializable 隔离）

```typescript
await prisma.$transaction(async (tx) => {
  // check-then-act 在 Serializable 下由 SSI 中止并发方
  const order = await tx.order.findFirst({ where: { poNumber } });
  if (order.status !== previousStatus) throw new Error('STATUS_DRIFT');
  // ... 写入
}, {
  isolationLevel: Prisma.TransactionIsolationLevel.Serializable,
});
```

| 并发场景 | 隔离级别 | 结果 |
|----------|----------|------|
| 两审批并发确认同一订单 | Serializable | SSI 中止一方（P2034）→ 安全回滚 → 可重试 |
| 同一 idempotencyKey 重放 | AgentCommitReceipt 唯一约束 | P2002 → 返回已提交结果（幂等） |

### 4.3 fail-closed 原则

任何步骤失败 → Prisma `$transaction` 自动回滚 → 不留部分主数据。返回结构化 `errorFeedback`：

```typescript
{
  ok: false,
  committed: false,
  error: 'COMMIT_TRANSACTION_FAILED: ...',
  errorFeedback: {
    code: 'STATUS_DRIFT',           // 稳定错误码
    message: '...',                  // 技术详情
    userAction: '订单状态已被并发修改，请刷新后重新确认。',  // 用户指引
    retryable: false,                // 是否可重试
  },
  audit: { approvalId, idempotencyKey, subOperationsSummary, impactScope },
}
```

## §6 ProcessSpec 流程规格

复合流程工具（如 `order.confirm`）额外注册 `ProcessSpec`，定义三阶段规格：

```typescript
processSpec: {
  composedOf: ['orders.update_status', 'finance.create_invoice'],  // 组合子操作
  draftPhase: { produces: 'ProcessDraft' },
  approvalPhase: {
    consumes: 'ProcessDraft',
    approvalCard: { changeList: true, irreversibleMarkers: true, impactScope: true },
  },
  commitTransaction: {
    consumes: 'ProcessDraft',
    wrapper: 'prisma_transaction',
  },
  postCommitHooks: [],   // P1-A scope 排除 email/EmailQueue
  partialFailurePolicy: {
    draftFail: 'abort_no_approval',      // draft 失败 → 不创建审批
    transactionFail: 'rollback',          // 事务失败 → 全回滚
    postCommitFail: 'queue_retry',        // 后置钩子失败 → 入队重试
  },
}
```

### 6.1 部分失败策略

| 失败阶段 | 策略 | 结果 |
|----------|------|------|
| draftPhase | `abort_no_approval` | 不创建 ApprovalRequest，直接返回错误 |
| commitTransaction | `rollback` | Prisma `$transaction` 回滚，不留部分主数据 |
| postCommitHooks | `queue_retry` | 入 AgentJob 队列重试，不影响主事务 |

## §7 订单快照与字段优先级

写操作 draftPhase 从 DB 读取订单快照时，遵循字段优先级规则（避免硬编码）：

| 字段 | 优先级 | 说明 |
|------|--------|------|
| `amount` | `totalActual > totalNet > quoteAmount` | 取第一个有效非零值 |
| `currency` | `salesCurrency > currency > 'USD'` | 出口 ERP 默认 USD |
| `customerRelationId` | `billToRelationId > customerRelationId` | 账单方优先 |
| `customerName` | `billToName > customer` | 账单方名称优先 |
| `lineCount` | `OrderLine.count()` | 订单行数量 |

### 7.1 前置条件校验

`validateOrderSnapshot` 校验订单快照满足确认前置条件：

| 校验项 | 失败码 | 说明 |
|--------|--------|------|
| 订单存在 | `ORDER_NOT_FOUND` | 订单不存在或已删除 |
| 客户关系 | `MISSING_CUSTOMER_RELATION` | customerRelationId 为空 |
| 订单行 | `NO_ORDER_LINES` | lineCount ≤ 0 |
| 金额有效 | `INVALID_AMOUNT` | amount ≤ 0 |
| 状态正确 | `STATUS_NOT_PENDING` | order.confirm 要求 Pending 状态 |

## §8 反馈契约（Feedback Contract）

每个写操作工具有独立的三态反馈契约（以 `order.confirm` 为基准）：

### 8.1 三态联合类型

```typescript
type OrderConfirmFeedback =
  | { status: 'approval_required'; approvalId; processDraft; message; editableFields? }
  | { status: 'committed'; orderId; poNumber; invoiceId; invoiceNumber; amount; currency; entityLinks[]; audit }
  | { status: 'failed'; error: OrderConfirmError; approvalId? }
```

### 8.2 稳定错误码

| 错误码 | 含义 | userAction |
|--------|------|-----------|
| `APPROVAL_REJECTED` | 审批被拒绝 | 确认是否重新发起审批 |
| `PROCESS_DRAFT_MISSING` | payload 缺 draft | 重新生成 draft |
| `PROCESS_DRAFT_HASH_MISMATCH` | draft 被篡改 | 重新发起审批 |
| `SEMANTIC_VALIDATION_FAILED` | 业务语义校验失败 | 检查订单状态/发票字段 |
| `STATUS_DRIFT` | 订单状态被并发修改 | 刷新后重新确认 |
| `INVOICE_AMOUNT_INVALID` | 发票金额无效 | 检查订单金额字段 |
| `COMMIT_TRANSACTION_FAILED` | 事务提交失败 | 稍后重试或联系管理员 |
| `COMMIT_CONFLICT` | 并发冲突（P2034） | 已安全回滚，可重试 |

## §10 幂等防重机制

### 10.1 AgentCommitReceipt 表

| 字段 | 类型 | 说明 |
|------|------|------|
| `idempotencyKey` | `String @unique` | ProcessDraft 内容 hash，全局唯一 |
| `toolId` | `String` | 工具 ID |
| `approvalId` | `String` | 关联审批 |
| `status` | `String` | `committing`/`committed`/`failed` |
| `result` | `Json?` | commit 结果快照 |

### 10.2 重放安全

同一 `idempotencyKey` 重放时：
1. `$transaction` 内先 `agentCommitReceipt.create` → P2002 唯一冲突
2. 捕获 P2002 → 查询已提交的 `receipt.result` → 直接返回（幂等）
3. 若 `receipt.status='committed'` → 返回原结果；若 `='committing'` → 说明另一进程正在提交，等待
