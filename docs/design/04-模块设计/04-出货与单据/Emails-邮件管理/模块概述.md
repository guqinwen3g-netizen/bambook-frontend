## §3 模块范围与核心能力

### 3.1 范围内（In Scope）

| 能力 | 说明 | 代码入口 |
|------|------|---------|
| IMAP 实时代理 | 前端凭据直连 IMAP（imap.qiye.aliyun.com:993），实时拉取邮件头与正文，兼容旧路径 | `EmailManager.handleSync` + `server/src/email/route.ts` IMAP-proxy 端点 |

| 意图可视化 | 列表徽标层（intent/customerSignal/labels/客户订单链接），薄覆盖层失败静默 | `emailIntelligenceService.fetchEmailIntents` |

- ❌ 客户档案字段编辑（仅按 fromAddress/toAddress 自动归档到 Relation，不修改客户主档）

- ❌ 富文本 HTML 正文通道（react-quill 已移除，纯文本 bodyText 主线，避免与 flat 设计系统冲突）

- ❌ 跨邮箱账号管理（当前单账号凭据本地 localStorage，多账号切换为 P2 缺口）

## §4 双轨数据契约（IMAP 代理 + DB 落库）

邮件模块采用"双轨数据契约"——同一封邮件在两个数据空间中各有投影，前端按场景选择读取口径：

### 4.1 轨道 A：IMAP 实时代理（前端兼容保留）

```
前端凭据 ──▶ /email/fetch (IMAP-proxy) ──▶ imap-simple 直连 ──▶ 邮件头/正文/附件
特点：
  • 实时性强，IMAP 服务器即真源
  • 前端凭据本地持有（password 不持久化到 localStorage）
  • 邮件 id 形如 `${physicalBox}-${uid}`（IMAP uid，非 DB id）
  • 不写库，仅做读取与状态回写（mark_read/mark_starred/mark_important/move）
```

### 4.2 轨道 B：DB 落库归档（业务真源）

```
/email/sync (DB-backed) ──▶ syncEmailsFromImap ──▶ Email 表落库
特点：
  • messageId RFC 2822 唯一去重，uid/uidValidity 跨会话稳定
  • 落库即自动归档（relationId/orderId）+ 规则分类（labels）
  • 邮件 id 形如 `EML__${shortId}`（DB 主键）
  • 写审计（imap_sync_email / email_auto_link / email_classify / email_create_followup）
  • 同步幂等：同 messageId 跳过，P2002 唯一冲突跳过
```

### 4.3 双轨叠加：意图覆盖层

前端列表渲染时叠加一层"DB 投影"覆盖层，将两条轨道的信息合并展示：

| 渲染元素 | 数据来源 | 失败降级 |
|---------|---------|---------|
| 邮件头/正文/附件 | IMAP 实时（轨道 A） | 失败回退 IndexedDB 缓存 |
| 意图徽标（询价/订单/投诉…） | DB 覆盖层 `intentByUid`（轨道 B） | 失败静默，列表无徽标 |
| 业务标签 chips（urgent/customer/bulk…） | DB `labels`（轨道 B） | 失败静默 |
| 客户/订单关联徽章 | DB `relationId`/`orderId`（轨道 B） | 失败静默 |
| 智能分类/建跟进按钮 | DB `id`（EML__xx，轨道 B） | 未同步邮件不显示按钮 |

**关键不变量**：覆盖层是增强层，失败绝不阻断列表主流程；IMAP uid 仅在单箱内唯一，跨箱切换必须清空 `intentByUid`（见 `intentFetchBoxRef`）。

## §5 核心业务流程图

```
┌──────────────┐
│ IMAP 服务器  │ (imap.qiye.aliyun.com:993, TLS)
└──────┬───────┘
       │ ① imap-simple connect + openBox + search ALL
       ▼
┌──────────────────────────────────────────────────┐
│ emailSyncService.syncEmailsFromImap               │
│  • messageId 唯一去重 / uid uidValidity 稳定      │
│  • 索引加载：Relation 地址索引 + Order PO 候选     │
│  • 事务内：Email.create + syncEmailReferences     │
│           + writeRouteAuditLog（三写原子）         │
└──────┬───────────────────────────────────────┬───┘
       │ ② 自动归档（C2）                       │ ② 规则分类（C8）
       ▼                                       ▼
┌──────────────────────┐               ┌─────────────────────┐
│ emailLinkService     │               │ emailClassification │
│  • relationId 匹配   │               │  • 规则层（零 LLM）  │
│    （地址→客户索引）  │               │  • labels 并集写入   │
│  • orderId 匹配       │               │  • complaint → urgent│
│    （主题含 PO 号）   │               └──────────┬──────────┘
│  • 手工优先不覆盖     │                          │
└──────────────────────┘                          │ ③ 投诉/紧急自动建跟进
                                                  ▼
                                       ┌─────────────────────┐
                                       │ emailFollowUpService│
                                       │  • 幂等：notes 含    │
                                       │    [email:<id>] 标记  │
                                       │  • 无 relationId 拒绝│
                                       │  • FollowUpRecord    │
                                       │    type='Email'      │
                                       └──────────┬──────────┘
                                                  │
                                                  ▼
                                       ┌─────────────────────┐
                                       │ 逾期看门狗巡检闭环  │
                                       │ (crmFollowUpWatchdog│
                                       │  nextFollowUpAt)    │
                                       └─────────────────────┘

并行支线（用户主动操作）：
  ④ Compose/Reply → emailOutboxMutationService → Outbox 邮件
  ⑤ Outbox 显式 SMTP 发送 → outboxSend → Sent 落库（messageId 回填）
  ⑥ 列表手动「智能分类」按钮 → applyEmailClassification(withAi=true)
  ⑦ 列表手动「建跟进」按钮 → createFollowUpFromEmail（幂等复用反馈）
  ⑧ 同步到 ERP 按钮 → 全箱批量同步（INBOX/Sent/Drafts/Trash/Spams）
```

**闭环不变量**：
1. **幂等**：messageId 去重 + 跟进 notes 标记 + P2002 唯一冲突跳过
2. **事务原子**：Email.create + syncEmailReferences + writeRouteAuditLog 在同一 `$transaction` 内，任一失败回滚
3. **降级链**：自动归档索引加载失败 → 同步继续不阻断；AI 抽取失败 → 降级纯规则分类；通知失败 → 不阻断同步主流程
4. **审计完备**：同步/归档/分类/建跟进四类操作均写 AuditLog（actorId/source/operation/targetId/after）

## §6 数据模型概要

邮件模块的持久化真源由 4 个核心模型组成（全量字段见 schema.prisma L2528-L2655 + L3792-L3811）：

| 模型 | 角色 | 关键约束 |
|------|------|---------|
| `Email` | 邮件主表（30+ 字段，含 IMAP 元数据 + 关联 snapshot + AI 抽取） | `id` PK / `messageId` `@unique` / `direction` (inbound/outbound/draft) / `status` / 11 索引（direction/status/fromAddress/mailbox/uid+uidValidity/threadId/relationId/orderId/invoiceId/sentAt/hasAttachments） / 软删 `deletedAt` |
| `EmailAttachment` | 邮件附件（含内嵌图片 CID + OCR 抽取文本 + AI 分析） | `emailId` FK `onDelete: Cascade` / 3 索引（emailId/contentType/filename） |
| `EmailTemplate` | 业务场景模板（5 类 + 通用） | `type` (quote/payment_reminder/delivery_notice/inspection_report/greeting/general) / `variables` 自动解析 / `usageCount`+`lastUsedAt` 使用统计 / 软删 |
| `EmailSignature` | 邮件签名（多语言） | `language` (zh/en/bilingual) / `variables` 自动解析 / `isDefault` 同语言唯一（服务端事务保证） / 软删 |

**关联模型**：
- `FollowUpRecord`（type='Email'，relationId 必填，notes 含 `[email:<emailId>]` 幂等标记）—— 见 schema L453
- `Relation`（地址索引源：email + primaryContactEmail） / `Order`（PO 号匹配源：poNumber） / `AuditLog`（四类操作审计） / `EntityLink`（syncEmailReferences 双写图谱）

## §7 凭据与多级缓存策略

### 7.1 凭据边界

| 项 | 策略 | 真源 |
|----|------|------|
| password 持久化 | ❌ 不写 localStorage（仅内存 state 持有） | `handleSaveConfig` 解构 `password` 后存 `safeConfig` |
| password 读取 | 启动时从 localStorage 读 `aliyun_mail_config`，password 强制置空 | `useState` 初始化逻辑 |
| 服务端透传 | password 通过请求体传给 IMAP-proxy 端点；服务端 `sanitizeMessage` 脱敏错误日志 | `emailSyncService.sanitizeMessage` |
| 账号脱敏 | 同步结果/审计日志中 `maskAccount` 仅显示前 2 字符 + `***` | `emailSyncService.maskAccount` |

### 7.2 多级缓存（防 localStorage Quota Exceeded）

```
IndexedDB (EmailDB)         ← 邮件正文 + 附件（大对象，单封独立键）
    ↑ miss
localStorage (nexus_emails_v2_${box})  ← 轻量头（body 剥离 + snippet 200 字 + flags）
    ↑ miss
React state (emails)        ← 当前箱可见列表（与 localStorage 双向同步）
```

**关键策略**：
- `saveEmailsToLS` 写入前剥离 `body` 与 `attachments`，仅保留 `snippet`（避免 Quota Exceeded）
- `prefetchDetails` 批量补全 snippet（BATCH_SIZE=5，间隔 200ms），IDB 命中优先，网络兜底
- `folderCounts` 持久化到 localStorage（INBOX/Sent Messages/Drafts/Trash 四箱）
- 后台同步（silent=true）每 60 秒触发，INBOX + 当前箱双拉取，新邮件 console.log 提醒

## §9 权限矩阵概要

邮件模块的权限分两层：**读**（IMAP-proxy + DB 查询 + 意图覆盖层 + 模板/签名列表）允许 JWT 或 API-Key；**写**（同步触发/状态更新/分类/建跟进/Outbox 创建发送/模板签名 CRUD）必须 JWT（`requireJwtForWrite`）。

| 角色 | 邮件读取 | 状态回写 | 同步触发 | 智能分类/建跟进 | 模板/签名写 |
|------|---------|---------|---------|--------------|-----------|
| owner/admin/manager | ✅ | ✅ | ✅ | ✅ | ✅ |
| sales | ✅ | ✅（自己的凭据） | ✅ | ✅ | ✅ |
| merchandiser | ✅ | ✅ | ✅ | ✅ | ❌（只读模板/签名） |
| finance | ✅（仅发票相关） | ❌ | ❌ | ❌ | ❌ |
| qc | ✅ | ❌ | ❌ | ❌ | ❌ |

**特殊约束**：
- 凭据边界：所有 IMAP 操作要求 `emailConfig.email` + `emailConfig.password` 非空，否则引导用户进入"邮箱设置"Modal
- Outbox 回复边界：`originalEmailId` 必须是 DB id（`EML__` 前缀），纯数字 IMAP uid 会 404，前端校验后提示"请先同步到 ERP"

## §10 设计系统约束

本模块遵循 BDS RDL 中性契约（详见各子文档 §10）：
- 禁止硬编码 hex 颜色 / `rounded-[Npx]` / `box-shadow`，全部走 CSS 变量 + Tailwind 语义类
- 意图 chip 使用 `INTENT_CHIP_CLASS`（`bg-[var(--recessed-bg)] text-[var(--text-tertiary)]`），**意图区分靠文字而非颜色**（RDL flat 纪律）
- 信号 chip 前置 `AlertTriangle` 图标表达紧急/风险，保持中性色板
- 空态不使用插画/吉祥物，仅文字 + Lucide 图标
- 邮件正文渲染使用 `prose prose-slate` + DOMPurify 清洗（防 XSS）
- 富文本编辑器已移除（react-quill 与 flat 设计冲突），改纯文本 textarea

## §12 移动端适配

移动端不使用三栏并排，改用 `mobileView` 三态切换（list / detail / compose）：
- 列表态：全屏卡片列表，顶部 Header 含 Compose + Sync 按钮
- 详情态：`fixed inset-0 z-[60]`，顶部含返回按钮（ChevronDown rotate-90）
- 编辑态：Compose 覆盖层
- 切换：`isMobile` props 控制布局分支，详情态 `translate-x-full → translate-x-0` 滑入

**侧边栏自适应**：`window.innerWidth < 1280` 时自动折叠 Workspace Rail 到 68px（图标模式）。
