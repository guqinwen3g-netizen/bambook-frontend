> **核心设计纪律**：薪资结构变更采用"生效区间留痕"模式，新结构生效时旧结构 effectiveTo 自动封闭，当前生效恒为 effectiveTo=null。工资单明细生成时取当前生效结构，保证薪资发放依据的是生成时的最新结构。

## §3 数据模型

### 3.1 SalaryStructure（薪资结构 — 生效区间留痕）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | String | @id `sal_${ts}_${rand}` | 主键 |
| userId | String | — | 关联用户 |
| baseSalary | Float | — | 基本工资 |
| positionAllowance | Float | @default(0) | 岗位津贴 |
| currency | String | @default("CNY") | 币种 |
| effectiveFrom | String | YYYY-MM-DD | 生效起始日期 |
| effectiveTo | String? | YYYY-MM-DD | 生效结束日期（null=当前生效） |
| note | String? | — | 备注 |
| createdAt | DateTime | @default(now()) | 创建时间 |
| updatedAt | DateTime | @updatedAt | 更新时间 |

索引：`@@index([userId])`。无软删（生效区间封闭替代删除，历史完整保留）。

### 3.2 PayrollRun（工资单批次 — period 唯一）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | String | @id `payrun_${ts}_${rand}` | 主键 |
| period | String | @unique YYYY-MM | 工资期间（如 2026-08） |
| status | String | @default("Draft") | 状态：Draft / Confirmed / Paid |
| totalNet | Float | @default(0) | 应发合计 |
| headcount | Int | @default(0) | 人数 |
| note | String? | — | 备注 |
| confirmedAt | DateTime? | — | 确认时间 |
| paidAt | DateTime? | — | 发薪时间 |
| createdAt | DateTime | @default(now()) | 创建时间 |
| updatedAt | DateTime | @updatedAt | 更新时间 |

关系：`items PayrollItem[]`。索引：`@@unique([period])`（每期间仅一个批次）。无软删（批次不可删除，状态流转记录完整）。

### 3.3 PayrollItem（工资单明细 — runId+userId 唯一）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | String | @id `payitem_${ts}_${rand}` | 主键 |
| runId | String | — | 关联批次（外键，onDelete: Cascade） |
| userId | String | — | 关联用户 |
| base | Float | @default(0) | 基本工资（取自 SalaryStructure.baseSalary） |
| allowance | Float | @default(0) | 津贴（取自 SalaryStructure.positionAllowance） |
| overtimePay | Float | @default(0) | 加班费（手工录入） |
| commission | Float | @default(0) | 佣金（可引用 P2 佣金结算额，手工录入） |
| bonus | Float | @default(0) | 奖金（手工录入） |
| deduction | Float | @default(0) | 扣款（手工录入） |
| net | Float | @default(0) | 应发合计（自动重算） |
| note | String? | — | 备注 |
| createdAt | DateTime | @default(now()) | 创建时间 |
| updatedAt | DateTime | @updatedAt | 更新时间 |

关系：`run PayrollRun @relation(onDelete: Cascade)`。
索引：`@@unique([runId, userId])`（批次内每人仅一条）/ `@@index([userId])`。无软删（明细不可删除，仅可调整）。

## §4 薪资结构生效区间

```
时间轴 ──────────────────────────────────────────▶
       │                   │                   │
       │ effectiveFrom     │ effectiveFrom     │
       │ (旧结构)          │ (新结构)          │
       │                   │                   │
       └── effectiveTo ────┘                   │
           (旧结构封闭)                        │
                                              │
                                 effectiveTo=null
                                 (当前生效)
```

### 4.1 setSalaryStructure 流程

```
setSalaryStructure(input)
  │
  ├─ 校验
  │   ├─ userId 非空
  │   ├─ baseSalary ≥ 0
  │   └─ effectiveFrom YYYY-MM-DD
  │
  ├─ current = salaryStructure.findFirst({ where: { userId, effectiveTo: null } })
  │
  ├─ current 存在且 effectiveFrom ≤ current.effectiveFrom
  │     → VALIDATION_FAILED（新生效起点必须晚于当前生效起点）
  │
  ▼ 事务（原子操作）
  ┌─────────────────────────────────────────────────────────────┐
  │ prisma.$transaction([                                       │
  │   // 1. 封闭当前生效结构                                     │
  │   db.salaryStructure.updateMany({                           │
  │     where: { userId, effectiveTo: null },                   │
  │     data: { effectiveTo: input.effectiveFrom },             │
  │   }),                                                       │
  │   // 2. 创建新结构                                           │
  │   db.salaryStructure.create({                               │
  │     data: {                                                 │
  │       id, userId, baseSalary, positionAllowance,            │
  │       currency: 'CNY', effectiveFrom, effectiveTo: null,    │
  │       note,                                                 │
  │     },                                                      │
  │   }),                                                       │
  │ ])                                                          │
  └─────────────────────────────────────────────────────────────┘
  │
  └─ 返回 { structure: created, previousClosed: !!current }
```

**事务原子性**：封闭旧结构与创建新结构在同一事务内，保证不会出现"旧结构已封闭但新结构未创建"的中间状态。

### 4.2 当前生效结构查询

```typescript
// 查询某用户当前生效的薪资结构
const structure = await db.salaryStructure.findFirst({
  where: { userId, effectiveTo: null }
});
```

> **effectiveTo=null 为当前生效标识**：任何时刻每用户至多一条 effectiveTo=null 的结构。setSalaryStructure 保证事务内封闭旧的、创建新的。

### 4.3 薪资历史查询

```typescript
getSalaryHistory(userId)
  │
  └─ salaryStructure.findMany({
       where: { userId },
       orderBy: { effectiveFrom: 'desc' }  // 最新在前
     })
```

## §5 工资单批次状态机

```
Draft ──(confirm)──▶ Confirmed ──(pay)──▶ Paid
  │
  └─ 仅 Draft 可生成/修改明细（generatePayrollItems / updatePayrollItem）
```

| 状态 | bds-badge 变体 | 可执行操作 | 说明 |
|------|---------------|-----------|------|
| Draft | warning（黄） | 生成明细 / 调整明细 / 重算合计 / 确认 | 草稿态，可调整 |
| Confirmed | info（蓝） | 标记已发薪 | 已锁定，不可修改明细 |
| Paid | active（绿） | — | 终态，已发薪 |

### 5.1 状态流转校验

- **generatePayrollItems**：仅 Draft 可生成（其他状态抛 `INVALID_TRANSITION`）
- **updatePayrollItem**：仅 Draft 可调整（明细的 run.status 必须为 Draft）
- **confirmPayrollRun**：仅 Draft 可确认 + 空批次不可确认（items.length === 0 抛 `VALIDATION_FAILED`）
- **markPayrollPaid**：仅 Confirmed 可发薪

### 5.2 批次创建

```
createPayrollRun(period, note?)
  │
  ├─ 校验 period 格式 YYYY-MM
  ├─ existing = payrollRun.findUnique({ where: { period } })
  │   existing 存在 → DUPLICATE_PERIOD（每期间仅一个批次）
  │
  └─ 创建 PayrollRun（status 默认 Draft）
```

> **period @unique 唯一约束**：每个工资期间（YYYY-MM）仅允许一个批次，避免重复发薪。

## §6 明细生成流程

```
generatePayrollItems(runId)
  │
  ├─ 校验：批次存在 + status=Draft
  │
  ├─ 查在职员工（employmentStatus ∈ [Probation, Regular, Suspended]）
  │
  ▼ 遍历每位员工
  ┌─────────────────────────────────────────────────────────────┐
  │ for p of profiles:                                          │
  │   structure = salaryStructure.findFirst({                   │
  │     where: { userId: p.userId, effectiveTo: null }          │
  │   })                                                        │
  │                                                             │
  │   ├─ structure 不存在 → 跳过（无薪资结构者不进入工资单）    │
  │   │                                                         │
  │   ├─ base = structure.baseSalary                            │
  │   ├─ allowance = structure.positionAllowance ?? 0           │
  │   ├─ net = Math.round((base + allowance) * 100) / 100       │
  │   │                                                         │
  │   └─ payrollItem.create({ ... })                            │
  │       └─ P2002 冲突 → 跳过（已生成，幂等）                  │
  └─────────────────────────────────────────────────────────────┘
  │
  ├─ recalcRunTotals(runId) 重算合计
  └─ 返回 { generated, totalNet, headcount }
```

### 6.1 生成范围

| employmentStatus | 是否生成明细 | 说明 |
|-----------------|------------|------|
| Probation | ✅ | 试用期员工 |
| Regular | ✅ | 正式员工 |
| Suspended | ✅ | 停职员工（仍发基本工资） |
| Resigned | ❌ | 已离职，不生成 |
| Terminated | ❌ | 已终止，不生成 |

> **Suspended 仍生成明细的原因**：停职员工可能仍需发放基本工资（视公司政策），故纳入生成范围。具体是否发放可在明细调整时手工 deduction 扣除。

### 6.2 幂等性

- **@@unique([runId, userId])**：批次内每人仅一条明细
- **P2002 冲突处理**：重复生成时捕获 P2002 错误跳过，不抛异常
- **多次生成**：首次生成全部明细，后续生成仅补充新增员工（已生成的不重复）

### 6.3 初始 net 计算

```
net = Math.round((base + allowance) * 100) / 100
```

生成时 net 仅含 base + allowance，其他项（overtimePay/commission/bonus/deduction）默认 0，需后续 updatePayrollItem 手工调整。

## §7 明细调整与 net 重算

### 7.1 updatePayrollItem 流程

```
updatePayrollItem(itemId, patch)
  │
  ├─ 校验：明细存在 + run.status=Draft
  │
  ├─ merged = {
  │     overtimePay: patch.overtimePay ?? item.overtimePay,
  │     commission: patch.commission ?? item.commission,
  │     bonus: patch.bonus ?? item.bonus,
  │     deduction: patch.deduction ?? item.deduction,
  │   }
  │
  ▼ net 自动重算
  ┌─────────────────────────────────────────────────────────────┐
  │ net = Math.round(                                            │
  │   (item.base + item.allowance +                              │
  │    merged.overtimePay + merged.commission + merged.bonus -   │
  │    merged.deduction) * 100                                   │
  │ ) / 100                                                      │
  └─────────────────────────────────────────────────────────────┘
  │
  ├─ payrollItem.update({ ...merged, net, note? })
  ├─ recalcRunTotals(runId) 重算批次合计
  └─ 返回 { item: updated }
```

### 7.2 net 计算公式

```
net = base + allowance + overtimePay + commission + bonus - deduction
```

| 项 | 符号 | 来源 | 说明 |
|----|------|------|------|
| base | + | SalaryStructure.baseSalary | 基本工资（生成时写入） |
| allowance | + | SalaryStructure.positionAllowance | 岗位津贴（生成时写入） |
| overtimePay | + | 手工录入 | 加班费 |
| commission | + | 手工录入 | 佣金（可引用 P2 佣金结算额） |
| bonus | + | 手工录入 | 奖金 |
| deduction | - | 手工录入 | 扣款（迟到/早退/社保/公积金等） |

### 7.3 批次合计重算

```
recalcRunTotals(runId)
  │
  ├─ items = payrollItem.findMany({ where: { runId } })
  ├─ totalNet = Math.round(sum(items.net) * 100) / 100
  ├─ headcount = items.length
  ├─ payrollRun.update({ totalNet, headcount })
  └─ 返回 { totalNet, headcount }
```

每次明细调整后自动重算批次合计，保证 totalNet 与明细 net 之和一致。

## §8 批次确认与发薪

### 8.1 confirmPayrollRun（确认锁定）

```
confirmPayrollRun(runId)
  │
  ├─ 校验：批次存在 + status=Draft
  ├─ 空批次不可确认（items.length === 0 → VALIDATION_FAILED）
  ├─ payrollRun.update({ status: 'Confirmed', confirmedAt: new Date() })
  └─ 返回 { run: updated }
```

确认后批次状态变为 Confirmed，明细不可再修改（updatePayrollItem 会抛 `INVALID_TRANSITION`）。

### 8.2 markPayrollPaid（标记发薪）

```
markPayrollPaid(runId)
  │
  ├─ 校验：批次存在 + status=Confirmed
  ├─ payrollRun.update({ status: 'Paid', paidAt: new Date() })
  └─ 返回 { run: updated }
```

发薪后批次状态变为 Paid（终态），不可再变更。

| GET | `/api/v1/hr/payroll-runs` | 双 scope | 批次列表 |

| POST | `/api/v1/hr/payroll-runs` | 双 scope + 写权限 | 创建批次（period YYYY-MM） |
| POST | `/api/v1/hr/payroll-runs/:id/generate` | 双 scope + 写权限 | 生成明细（仅 Draft） |
| POST | `/api/v1/hr/payroll-runs/:id/confirm` | 双 scope + 写权限 | 确认批次（Draft→Confirmed） |
| POST | `/api/v1/hr/payroll-runs/:id/pay` | 双 scope + 写权限 | 标记已发薪（Confirmed→Paid） |

> **明细调整**：updatePayrollItem 经 PATCH /payroll-runs/:id/items/:itemId 或类似端点（当前路由层未单独暴露，可能内嵌于批次详情更新），守卫同双 scope。

### 10.3 守卫口径（决策点4-A 薪酬双 scope 机制）

薪酬域所有 API 统一要求双 scope 同时命中：
- `requireScope('hr:salary:read')`（HR 薪酬读 scope）
- **AND** `requireScope('sensitive:salary')`（敏感字段-薪酬 scope）

**默认角色 scope 集**：
- SuperAdmin（老板）：默认同时拥有两个 scope → 可正常访问
- Admin（系统管理员=总领导）：默认**不含** `sensitive:salary` → 默认看不了薪酬（薪酬绝密）

**指定HR 授权机制（overrides）**：
SuperAdmin 可通过 `user_permission_overrides` 表给指定用户追加 `hr:salary:read` + `sensitive:salary` 双 scope，例：
- 财务负责人（需要看工资单做发薪）
- 老板娘（需要看薪酬）
- 专职 HR 专员（负责维护薪资结构）

> 原文档「HR 路由全程 requireRole('owner','admin')」对薪酬域**不再适用**；薪酬守卫升级为以上双 scope 机制，比其他 HR 功能（员工档案/考勤等用 `requireRole('SUPER_ADMIN','ADMIN')`）更严格。

### 10.4 错误码

| 错误码 | 触发场景 |
|--------|---------|
| `VALIDATION_FAILED` | baseSalary 非法 / effectiveFrom 格式 / period 格式 / 空批次确认 |
| `DUPLICATE_PERIOD` | 期间已存在批次 |
| `RUN_NOT_FOUND` | 批次不存在 |
| `ITEM_NOT_FOUND` | 明细不存在 |
| `INVALID_TRANSITION` | 状态非法流转（非 Draft 生成/调整、非 Draft 确认、非 Confirmed 发薪） |

## §11 权限矩阵（决策点4-A 双 scope 机制）

| 角色 | 查看薪资/工资单（读） | 设置薪资结构（写） | 生成/调整明细（写） | 确认批次（写） | 标记发薪（写） |
|------|----------------------|------------------|------------------|-------------|-------------|
| SuperAdmin（老板） | ✅（默认 scope 集含 `hr:salary:read`+`sensitive:salary` 双 scope） | ✅ | ✅ | ✅ | ✅ |
| Admin（总领导） | ❌（默认无 `sensitive:salary`，薪酬绝密） | ❌ | ❌ | ❌ | ❌ |
| 销售主管 SalesManager | ❌ | ❌ | ❌ | ❌ | ❌ |
| 财务 Finance | ⚠️ 需 SuperAdmin 给该用户通过 `user_permission_overrides` 追加双 scope（指定HR机制） | ⚠️ 同左 + 写 scope | ⚠️ 同左 | ⚠️ 同左 | ⚠️ 同左 |
| 指定HR（通过 overrides 授权的用户） | ✅（SuperAdmin 追加双 scope `hr:salary:read`+`sensitive:salary`） | ✅（双 scope + 写权限组合） | ✅ | ✅ | ✅ |
| 销售 Sales / QC / 后勤 Logistics | ❌ | ❌ | ❌ | ❌ | ❌ |

> **决策点4-A 核心原则**：
> 1. 薪酬守卫不使用固定角色（owner/admin/finance），统一走双 scope 机制 `requireScope('hr:salary:read') AND requireScope('sensitive:salary')`
> 2. Admin（总领导）默认**看不到员工薪酬**（绝密），不赋 `sensitive:salary` scope
> 3. 原「finance 角色放行」升级为：SuperAdmin 通过 `user_permission_overrides` 给财务负责人等**具体用户**追加双 scope，不直接给 Finance 角色硬编码赋 scope（避免未来角色调整时权限泄露）
