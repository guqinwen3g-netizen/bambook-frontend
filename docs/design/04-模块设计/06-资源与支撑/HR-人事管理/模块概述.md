## §2 模块边界与职责

人事管理模块是组织与人员的统一治理中枢，其核心职责矩阵：

| 职责域 | 已实现 | 规划增强 | 上下游依赖 |
|--------|--------|----------|-----------|
| **组织架构** | ✅ Department 树（parentId 自引用 + status active/inactive）+ JobPosition 岗位（headcount 编制 + departmentId 关联）+ Team 跨部门团队（leaderId + departmentId 可选）+ Project 项目（teamId 可选 + priority + startDate/endDate）+ 树形导航（部门→团队→项目三级展开 + 搜索过滤） | ⚠️ 组织架构图可视化、岗位编制预警 | 上游 Department/JobPosition；下游员工档案/团队 |
| **员工档案** | ✅ EmployeeProfile 与 UserAccount 1:1（userId @unique）+ employeeNo 自动生成（EMP0001 格式 + P2002 重试兜底）+ upsertProfile 建档/更新 + 软删（deletedAt）+ 状态/部门/姓名搜索 | ⚠️ 员工自助档案修改、电子合同附件 | 上游 UserAccount；下游生命周期事件/薪资/绩效 |
| **生命周期事件** | ✅ EmploymentEvent 历史流水（8 类事件 Onboard/Regularize/Transfer/Promote/Suspend/Resume/Resign/Terminate）+ EVENT_TARGET_STATUS 状态映射 + EVENT_ALLOWED_FROM 前置状态校验 + 唯一状态变更入口（禁止直接改 Profile.employmentStatus）+ publishBusinessEvent 事件发布 | ⚠️ 试用期转正提醒、合同到期提醒 | 上游 EmployeeProfile；下游通知引擎 |
| **考勤打卡** | ✅ AttendanceRecord 每人每日一条（userId+date @unique upsert）+ deriveAttendanceStatus 自动推导（Normal/Late/EarlyLeave/LateAndEarly，显式 status 优先）+ computeWorkHours 工时计算 + attendanceSummary 月度汇总 | ⚠️ 自动打卡（设备对接）、考勤报表导出 | 上游人工录入；下游薪资加班费 |
| **请假管理** | ✅ LeaveRequest 状态机（Pending→Approved/Rejected/Cancelled）+ 6 类假期（Annual/Sick/Personal/CompTime/Maternity/Other）+ decideLeaveRequest 审批 + cancelLeaveRequest 撤销 + enumerateDates 日期枚举 + 软删 | ⚠️ 请假余额扣减、假期余额台账 | 上游员工申请；下游考勤 Leave 状态 |
| **薪资结构** | ✅ SalaryStructure 变更留痕（effectiveFrom/To 区间，当前生效 effectiveTo=null）+ setSalaryStructure 新结构生效时旧结构自动封闭 + getSalaryHistory 历史查询 | ⚠️ 薪资审批流、调薪提醒 | 上游人工录入；下游工资单生成 |
| **工资单批次** | ✅ PayrollRun 月度批次（period YYYY-MM @unique + status Draft/Confirmed/Paid + totalNet/headcount 汇总）+ generatePayrollItems 自动生成明细（取当前生效薪资结构）+ updatePayrollItem 手工调整 + recalcRunTotals 重算合计 + confirmPayrollRun 锁定 + markPayrollPaid 发薪 | ⚠️ 银行代发文件、薪资条邮件推送 | 上游 SalaryStructure/AttendanceRecord；下游财务 |
| **绩效考核** | ✅ PerformanceCycle 周期（period @unique + Open/Closed）+ PerformanceReview 评定（Draft→Submitted→Confirmed 三阶段：自评→提交→主管终评）+ kpi Json 弹性指标 + grade A/B/C/D + closePerformanceCycle 周期关闭 | ⚠️ 360°评估、KPI 模板库 | 上游人工录入；下游薪资 bonus |
| **培训管理** | ✅ TrainingCourse 课程（Internal/External + Planned/Ongoing/Completed/Cancelled + capacity 容量）+ TrainingEnrollment 报名（Enrolled/Completed/Absent/Cancelled + score 成绩 + certificate 证书）+ @@unique([courseId, userId]) 防重报名 + 软删 | ⚠️ 培训预算、在线学习平台对接 | 上游人工录入；下游员工发展档案 |

## §5 员工生命周期状态机

员工在职状态（employmentStatus）通过生命周期事件（EmploymentEvent）变更，禁止直接改 Profile 字段：

```
                    Onboard
                       │
                       ▼
                  ┌─────────┐
        ┌────────▶│Probation│────────┐
        │         └────┬────┘        │
        │              │             │
        │   Regularize │             │ Suspend
        │              ▼             │
        │         ┌─────────┐◀───────┘
        │         │ Regular │
        │         └────┬────┘
        │              │
        │   Transfer/Promote（不改状态，仅改岗位/部门）
        │              │
        └──────────────┘
                       │
            Resign/Terminate
                       │
                       ▼
              ┌─────────────────┐
              │Resigned/Terminated│（终态，不可回退）
              └─────────────────┘

    Suspend → Resume → Regular（仅 Suspended 可 Resume）
```

### 5.1 事件 → 目标状态映射

| 事件类型 | 目标状态 | 说明 |
|---------|---------|------|
| `Onboard` | Probation | 入职（试用期），允许无档案自动建档 |
| `Regularize` | Regular | 转正，写入 regularDate |
| `Transfer` | （不改状态） | 调岗，仅改 positionId + primaryDeptId |
| `Promote` | （不改状态） | 晋升，仅改 positionId |
| `Suspend` | Suspended | 停职 |
| `Resume` | Regular | 复职（仅 Suspended 可发起） |
| `Resign` | Resigned | 离职（终态） |
| `Terminate` | Terminated | 终止（终态） |

### 5.2 事件前置状态校验

| 事件 | 允许的前置状态 |
|------|--------------|
| `Regularize` | Probation |
| `Transfer` | Probation, Regular |
| `Promote` | Probation, Regular |
| `Suspend` | Probation, Regular |
| `Resume` | Suspended |
| `Resign` | Probation, Regular, Suspended |
| `Terminate` | Probation, Regular, Suspended |

> **终态保护**：Resigned/Terminated 为终态，任何事件均不可再发起（抛 `INVALID_TRANSITION`）。

## §6 考勤与请假状态机

### 6.1 考勤状态自动推导

```
deriveAttendanceStatus(checkIn, checkOut, explicit?)
  │
  ├─ explicit 非空且合法 → 直接返回（Absent/Leave/Holiday/Overtime 等人工标记不被覆盖）
  │
  ├─ checkIn > 09:30 且 checkOut < 17:30 → LateAndEarly
  ├─ checkIn > 09:30 → Late
  ├─ checkOut < 17:30 → EarlyLeave
  └─ 否则 → Normal
```

| 常量 | 值 | 含义 |
|------|---|------|
| `WORK_START` | `09:30` | 标准上班时间 |
| `WORK_END` | `17:30` | 标准下班时间 |

### 6.2 请假状态机

```
Pending ──(approve)──▶ Approved
   │                     │
   │──(reject)──▶ Rejected
   │
   └──(cancel)──▶ Cancelled
```

| 状态 | bds-badge 变体 | 可执行操作 |
|------|---------------|-----------|
| Pending | warning | 审批通过 / 驳回 / 撤销 |
| Approved | success | — |
| Rejected | danger | — |
| Cancelled | neutral | — |

## §7 薪资与工资单状态机

### 7.1 薪资结构生效区间

```
时间轴 ──────────────────────────────────────────▶
       │                   │                   │
       │ effectiveFrom     │ effectiveFrom     │
       │ (旧结构)          │ (新结构)          │
       │                   │                   │
       └── effectiveTo ────┘                   │
           (旧结构封闭)                        │
                                              │
                                 effectiveTo=null
                                 (当前生效)
```

**setSalaryStructure 逻辑**：
1. 查用户当前生效结构（effectiveTo=null）
2. 若存在，将其 effectiveTo 封闭为新结构的 effectiveFrom 前一天（实际实现为直接设为新 effectiveFrom，区间语义为左闭右开）
3. 创建新结构（effectiveFrom=输入值，effectiveTo=null）

### 7.2 工资单批次状态机

```
Draft ──(confirm)──▶ Confirmed ──(pay)──▶ Paid
  │
  └─ 仅 Draft 可生成/修改明细（generatePayrollItems / updatePayrollItem）
```

| 状态 | 可执行操作 | 说明 |
|------|-----------|------|
| Draft | 生成明细 / 修改明细 / 重算合计 / 确认 | 草稿态，可调整 |
| Confirmed | 标记已发薪 | 已锁定，不可修改明细 |
| Paid | — | 终态，已发薪 |

## §8 绩效与培训状态机

### 8.1 绩效周期

```
Open ──(close)──▶ Closed
  │
  └─ Open 时可创建/更新评定
```

### 8.2 绩效评定三阶段

```
Draft ──(submit)──▶ Submitted ──(confirm)──▶ Confirmed
  │                    │
  │ 自评阶段            │ 主管终评阶段
  │ selfScore          │ managerScore → finalScore → grade
  │                    │
  └─ Draft 可反复修改   └─ Submitted 等待主管终评
```

| 阶段 | 操作角色 | 字段 |
|------|---------|------|
| Draft（自评） | 员工本人 | selfScore + kpi + comment |
| Submitted（待终评） | 主管 | managerScore → finalScore + grade |
| Confirmed（已确认） | — | 终态，不可修改 |

### 8.3 培训课程状态

```
Planned ──(开课)──▶ Ongoing ──(结课)──▶ Completed
  │                    │
  └─(取消)──▶ Cancelled ◀──(取消)──┘
```

### 8.4 培训报名状态

```
Enrolled ──(结课)──▶ Completed（写入 score + certificate）
   │
   ├──(缺席)──▶ Absent
   └──(取消)──▶ Cancelled
```

### 10.6 守卫口径（分层守卫，决策点4-A）

- **认证**：`createModuleAuthGuard`（JWT 优先，API-Key 次之，默认 requireAuth=true）
- **分层守卫**：
  - **薪酬（salary）字段/页面/API**：`requireScope('hr:salary:read')` **AND** `requireScope('sensitive:salary')`（双 scope 同时命中）
    - 默认 SuperAdmin 角色 scope 集包含这两个 scope；Admin（系统管理员总领导）默认**不含**（即总领导默认看不了薪酬）
    - SuperAdmin 可通过 `user_permission_overrides` 给指定用户追加 `hr:salary:read` + `sensitive:salary` 双 scope，实现"指定HR"授权机制（例：财务负责人、老板娘、HR专员等）
    - 原文档中「HR专员、财务主管可见薪酬」的描述，统一改为以上双 scope + overrides 授权机制
  - **HR 模块除薪酬外的其他功能**（员工档案、入职离职、部门、考勤、绩效、培训等）：`requireRole('SUPER_ADMIN','ADMIN')`，即系统管理员（总领导）默认可见（HR 归系统管理员宽泛职能容器）
- **审计**：所有写操作经 `writeRouteAuditLog` 记录审计日志

## §11 权限矩阵（决策点4-A 双 scope 薪酬守卫）

| 角色 | 查看组织/档案/考勤/绩效/培训（非薪酬） | 建档/录考勤/录绩效（非薪酬写入） | 生命周期事件 | 请假审批 | 绩效终评 | **查看薪资结构/工资单（薪酬读）** | **设置薪资/生成工资单/确认/发薪（薪酬写）** |
|------|--------------------------------------|--------------------------------|------------|---------|---------|----------------------------------|------------------------------------------|
| SuperAdmin（老板） | ✅ requireRole | ✅ requireRole | ✅ | ✅ | ✅ | ✅（默认 scope 集含 `hr:salary:read`+`sensitive:salary`） | ✅（双 scope 默认） |
| Admin（总领导） | ✅ requireRole(SUPER_ADMIN,ADMIN) | ✅ requireRole | ✅ | ✅ | ✅ | ❌（默认无 `sensitive:salary`，薪酬绝密不可见） | ❌ |
| 销售主管 SalesManager | ⚠️ 仅本部门（数据范围 department 限制） | ❌ | ❌ | ✅（自己的下属） | ✅（自己的下属） | ❌ | ❌ |
| 财务 Finance | ❌（财务域非人事） | ❌ | ❌ | ❌ | ❌ | ⚠️ 需 SuperAdmin 通过 `user_permission_overrides` 追加双 scope 才可见（指定HR机制） | ⚠️ 同左，写操作需额外 scope |
| 指定HR（通过 overrides 授权） | ❌（不赋人事管理权，仅薪酬 scope） | ❌ | ❌ | ❌ | ❌ | ✅（SuperAdmin 追加 `hr:salary:read`+`sensitive:salary`） | ✅（双 scope + 写 scope 组合） |
| 销售 Sales / QC / 后勤 Logistics | ✅（仅自己的档案，self 范围） | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

> **分层守卫原则**：
> 1. HR 除薪酬外的宽泛职能归 Admin（总领导）容器 + SuperAdmin，用 `requireRole('SUPER_ADMIN','ADMIN')`
> 2. **薪酬是绝密域**：采用双 scope 机制 `requireScope('hr:salary:read') AND requireScope('sensitive:salary')`，默认仅 SuperAdmin 同时命中
> 3. **指定HR 授权机制**：SuperAdmin 通过 `user_permission_overrides` 给指定用户（财务负责人、老板娘、HR 专员等）追加 `hr:salary:read` + `sensitive:salary` 双 scope，实现按需授权，不依赖固定角色硬编码
> 4. 原「HR 路由全程 requireRole('owner','admin')」改为以上分层守卫；薪酬守卫比其他 HR 功能更严格（Admin 默认看不了薪酬）
