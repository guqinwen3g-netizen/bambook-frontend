## §2 业务定位与目标

### 2.1 业务定位

`FactoryProfile` 是供应商工厂属性扩展档案，1:1 挂 Relation（category=Supplier 的组织）。承载工厂专属的产能、专长、评分、银行、黑名单等业务属性，而身份信息（名称、联系人、地址等）真源在 Relation。

### 2.2 核心目标

1. **一厂一档**：`relationId @unique`，保证一个 Supplier 组织对应一个 FactoryProfile。
2. **产能可视**：月产能 + 单位 + 设备 + 工人数量，支撑产能日历与排产。
3. **专长可搜**：`specialties String[]` 原生数组，支持按品类筛选工厂。
4. **评分缓存**：`qualityScore / deliveryScore` 缓存分，避免每次列表查询重算。
5. **银行信息**：开户行 + 收款账户 + SWIFT，支撑采购付款。
6. **黑名单管控**：拉黑时间 + 原因 + 操作人，拉黑后禁新建 PO。
7. **合作历史**：首次合作日期 + 累计订单数 + 累计金额，沉淀合作轨迹。

### 4.2 ER 关系图

```
Relation (1)  ← 身份真源
    │ 1:1 @unique (relationId, onDelete: Cascade)
    ▼
FactoryProfile (1)
    │ 1:N (factoryId)
    ├─► FactoryEvaluation (N)  ← 评分明细 append-only 真源
    │     └─► 事务内重算 → FactoryProfile.qualityScore / deliveryScore
    ├─► FactoryCertification (N)  ← 认证 + 有效期
    └─► FactoryCapacity (N)  ← 月产能日历（@@unique [factoryId, month]）
                                └─► occupied 实时聚合 PurchaseOrder
```

### 4.3 关键约束

- `relationId @unique`：保证 1:1，且 Relation 删除时级联删除 FactoryProfile。
- `qualityScore / deliveryScore` 默认 0，仅由服务端 `addEvaluation` 事务内重算。
- `totalOrders / totalAmount` 默认 0，由采购单事件触发更新。
- `specialties` 为 PostgreSQL 原生 `String[]`，支持数组查询。

## §5 关键流程

### 5.1 工厂档案创建流程

```
1. 用户在 SuppliersManager 点击「新建工厂档案」
2. ProfileForm 弹窗：
   a. 选择供应商（前端 listRelations 过滤 category=Supplier, isOrganization, 未删除, 未建档案）
   b. 填产能：monthlyCapacity + capacityUnit (PC/M)
   c. 填工人数量、设备清单
   d. 填擅长品类（逗号分隔，前端 split 后传 String[]）
   e. 填价位水平、首次合作日期
   f. 填银行信息：bankName / bankAccount / bankSwift
   g. 填备注
3. 提交 → POST /api/factories
4. 服务端：
   a. 校验 relationId 存在且 Relation 是未删除的 Supplier 组织
   b. 校验 FactoryProfile 未存在（防重复建档）
   c. $transaction 写入 FactoryProfile + AuditLog
5. 返回档案详情，前端刷新列表
```

### 5.2 工厂档案更新流程

```
用户在详情头部点击「编辑档案」
  │
  ▼
ProfileForm 弹窗（预填现有值）
  │
  ▼
提交 → PUT /api/factories/:id
  │
  ▼
服务端：
  a. 校验档案存在且未软删
  b. $transaction 更新（白名单字段过滤）+ AuditLog
  │
  ▼
前端 refreshAll() 刷新列表 + 详情
```

> 注意：`relationId` 不可更新（1:1 绑定身份真源），如需换供应商需删除重建。

### 5.3 评分缓存重算流程

```
触发：FactoryEvaluation 追加（手动或自动）
  │
  ▼
addEvaluation(factoryId, { kind, score, ... })
  │
  ▼
$transaction {
  1. 写入 FactoryEvaluation
  2. 同事务查询所有 inspectionRows / deliveryRows
  3. avg(rows) = sum(score) / rows.length  // 0 if empty
  4. FactoryProfile.update({ qualityScore, deliveryScore, updatedAt })
}
```

### 5.4 合作历史自动更新流程

```
采购单创建/收齐事件触发
  │
  ▼
updateCooperationStats(relationId, { orderAdded, amountAdded })
  │
  ▼
FactoryProfile.update({
  totalOrders: { increment: orderAdded ? 1 : 0 },
  totalAmount: { increment: amountAdded },
  firstOrderAt: profile.firstOrderAt ?? today  // 首次合作自动回填
})
```

### 5.5 黑名单流程

```
拉黑：
  setBlacklist(factoryId, reason, actorId)
    │
    ▼
  $transaction {
    1. 校验 actorId 权限（owner/admin/manager）
    2. FactoryProfile.update({
         blacklistedAt: now,
         blacklistReason: reason,
         blacklistedById: actorId
       })
    3. AuditLog
  }

解除：
  clearBlacklist(factoryId, actorId)
    │
    ▼
  FactoryProfile.update({
    blacklistedAt: null,
    blacklistReason: null,
    blacklistedById: null
  })
```

### 5.6 360° 总览加载流程

```
getOverview(factoryId)
  │
  ▼
1. db.factoryProfile.findUnique({ where: { id: factoryId }, include: { relation: true } })
2. 若不存在或已软删 → return null
3. Promise.all([
     listEvaluations(factoryId),       // take: 200
     listCertifications(factoryId),   // 全部
     listCapacity(factoryId),         // 含 occupied 实时聚合
   ])
4. return { profile, evaluations: top20, certifications, capacity }
```

## §6 API 与服务契约

### 6.1 专属端点

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/api/factories` | 列表（search / sort / blacklisted / limit） |
| GET | `/api/factories/:id` | 详情 |
| GET | `/api/factories/by-relation/:relationId` | 按 Relation 反查 |
| POST | `/api/factories` | 创建 |
| PUT | `/api/factories/:id` | 更新（不含 relationId） |
| DELETE | `/api/factories/:id` | 软删除 |
| GET | `/api/factories/:id/overview` | 360° 总览 |
| POST | `/api/factories/:id/blacklist` | 拉黑 |
| POST | `/api/factories/:id/unblacklist` | 解除拉黑 |

### 6.2 服务层契约（factoryService.ts）

- `createFactoryService(prisma)` 工厂函数返回所有方法。
- `createProfile(input, actorId)`：校验 Relation → 写入 + AuditLog。
- `updateProfile(factoryId, patch, actorId)`：白名单过滤 → 更新 + AuditLog。
- `getProfile / getProfileByRelation / listProfiles`：查询方法。
- `setBlacklist / clearBlacklist / assertNotBlacklisted`：黑名单三件套。
- `getOverview(factoryId)`：360° 聚合查询。

### 6.3 输入校验

- `relationId`：必填，服务端二次校验 Relation 是 Supplier 组织。
- `monthlyCapacity`：非负数字（>= 0）。
- `capacityUnit`：`PC` / `M` 枚举（前端下拉，服务端宽容）。
- `workerCount`：非负整数。
- `specialties`：String[]，前端逗号分隔 split。
- `priceLevel`：`High` / `Mid` / `Low` 枚举。
- `firstOrderAt`：YYYY-MM-DD 格式。

### 6.4 业务事件

- `FactoryProfileCreated`：建档后发布。
- `FactoryProfileUpdated`：更新后发布。
- `FactoryBlacklisted`：拉黑后发布（采购单模块订阅，禁新建 PO）。
- `FactoryUnblacklisted`：解除拉黑后发布。

## §8 权限与审计

### 8.1 权限

- 工厂档案创建：登录用户均可（但需 Relation 是 Supplier 组织）。
- 工厂档案更新：登录用户均可。
- 工厂档案删除：登录用户均可（软删除，可恢复）。
- **黑名单操作**：owner / admin / manager 权限（服务端 `assertPermission` 强制）。
- 银行信息查看：登录用户均可（敏感字段，建议后续加密 + 权限分级）。

### 8.2 审计

- 所有 mutation 通过 `writeRouteAuditLog` 同事务写入 `AuditLog`。
- `source` 字段标记来源（`factory-service:create_profile` / `update_profile` / `blacklist` / `unblacklist`）。
- `targetType = 'FactoryProfile'`，`targetId = factoryId`。
- 黑名单操作含 `actorId`（拉黑人）。
- before/after 快照完整记录字段变更。

## §9 性能与扩展性

### 9.1 索引

- `relationId`：unique，1:1 反查。
- `blacklistedAt`：黑名单筛选。

### 9.2 扩展性

- `specialties` 为 String[]，可任意扩展品类。

### 9.3 已知性能优化点

- 列表查询不展开 evaluations / certifications / capacity，详情才 `include`。
- 360° 总览并行查询，避免串行。
- 排名列表 `limit: 100` 分页。

## §10 错误处理与边界

### 10.1 错误场景

| 场景 | 错误信息 |
| --- | --- |
| relationId 缺失 | `relationId required` |
| Relation 不存在 | `Relation ${relationId} not found` |
| Relation 非 Supplier | `Relation 不是 Supplier 组织` |
| Relation 已删除 | `Relation 已删除` |
| FactoryProfile 已存在 | `工厂档案已存在（同 relationId）` |
| FactoryProfile 不存在 | `工厂档案不存在` |
| monthlyCapacity 负数 | `monthlyCapacity 必须是非负数字` |
| 权限不足拉黑 | `无权限执行拉黑操作` |

### 10.2 边界

- `qualityScore / deliveryScore` 默认 0（无评分时），列表展示 0 分（danger 色阶）。
- `totalOrders / totalAmount` 默认 0。
- `firstOrderAt` 可由首次采购单事件自动回填。
- `bankAccount` 明文存储（敏感，建议后续加密）。
- 软删除后查询默认过滤，详情接口返回 `null`。

## §13 已知限制与技术债务

1. **银行信息明文**：`bankAccount / bankSwift` 未加密，存在泄露风险。建议引入字段级加密。
2. **合作历史自动更新依赖事件**：`totalOrders / totalAmount / firstOrderAt` 由采购单事件触发更新，事件丢失会导致数据不准。建议定期对账任务。
3. **评分缓存重算仅追加触发**：评分软删除后未自动重算，需手动触发或定期重算任务。
4. **specialties 数组无标准化**：自由文本数组，无标准品类字典约束（如「西装」与「西服」混用）。
5. **无工厂档案删除恢复**：软删除后无恢复接口，需 DBA 手动恢复。
6. **无工厂档案导入导出**：批量建档需手动逐条。

## §14 演进路线

1. **银行信息加密**：引入字段级 AES 加密，权限分级查看。
2. **合作历史对账任务**：定期扫描 PurchaseOrder 重新计算 totalOrders / totalAmount。
3. **评分删除重算**：评分软删后自动重算缓存分。
4. **专长标准化**：引入品类字典，约束 specialties 取值。
5. **档案恢复接口**：管理员可恢复软删档案。
6. **批量导入导出**：支持 CSV / Excel 批量建档。
7. **工厂档案完整度评分**：基于字段填写率自动计算完整度。
8. **AI 工厂画像**：基于历史订单 + 评分 + 产能生成工厂画像标签。
