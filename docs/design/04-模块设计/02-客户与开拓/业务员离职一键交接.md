# 业务员离职一键交接 (Salesperson Offboarding Handover)

> **REQ2-13** · 痛度 26 ▲资产安全类 · 来源 X-07 L0 · 批次三 B 级
> **甲方场景**：业务员离职——客户/商机/跟进/邮件归属批量移交，账号停用但历史留痕，客户资料不可导出带走。当前：停用账号端点已有（disable-account），但归属移交 L0（只能逐个客户手改 ownerId），且停用后旧 JWT 仍有效（7 天 TTL 只验签不查库）。
> **验收标准**：X-07——移交后新归属人完整接管历史，离职者立即失去访问；SEC-01——业务员不可批量导出客户档案。

## §1 元信息

| 项 | 值 |
|---|---|
| **模块名** | 离职一键交接 Offboarding Handover |
| **定位** | 管理员发起的一次性原子交接：归属字段批量移交 + 账号停用（可选）+ append-only 交接单留痕 + 停用即时失效 |
| **核心实体** | HandoverRecord（交接单，append-only） |
| **需求编号** | REQ2-13（批次三 B 级，资产安全类） |
| **关联代码** | server/src/handover/handoverService.ts / route.ts / auth/accountStatusGuard.ts / relations/routeV2.ts export 端点 / AdminPanel 用户管理「离职交接」 |
| **依赖** | RBAC（requirePermission users:admin / data:export:full）；T-38 订单锚定客户继承；既有 disable-account 端点（复用语义不双轨） |

## §2 关键设计决策（DR-056）

### DR-056-① 移交面 = 归属字段五类 + 无锚订单兜底；锚定资产自动继承（T-38 复用）

| 资产 | 移交动作 | 依据 |
|---|---|---|
| Relation.ownerId = 离职者 | ownerId → 接收人；salesRepIds 剔除离职者、补入接收人 | 客户档案归属主字段（dataScope 行级权限锚） |
| Relation.salesRepIds 含离职者（ownerId ≠ 离职者） | salesRepIds 剔除离职者、补入接收人（协同跟进职责移交，档主不变） | 跟进人变更后写权限随之（orderServiceV2.buildOrderWriteScopeWhere） |
| Opportunity.salesRepId = 离职者 | salesRepId → 接收人，salesRepName 冗余快照同步 | 商机管线归属 |
| FollowUpRecord.salesRepId = 离职者 | salesRepId → 接收人，salesRepName 同步 | 接管历史跟进线索（内容不变，责任人口径移交；原始事实经 HandoverRecord 留痕可溯） |
| Order.ownerId = 离职者 且 customerRelationId = null | ownerId → 接收人 | 无锚遗留订单仅有创建者可见性，不移交即成孤儿（资产安全兜底） |

**不单独移交（自动继承或非个人归属）**：
- **订单（有客户锚）/邮件/报价可见性**：T-38（DR-042 §5.1 L2）——订单可见性锚 = 跟进客户 ∪ 团队共享，客户 ownerId/salesRepIds 变更后历史订单视野**自动继承**，无需字段改写；Email 按 relationId 锚定客户（模型无个人归属字段），随客户走；Quotation 同经 customerRelationId 关联呈现。
- **MarketingLead**：线索归属 MarketingCampaign（ownerId 在活动上），非个人资产，不在移交面。
- **部门主管/团队成员**：Department.headId / TeamMember 属组织架构（HR 域），预览出警示但不自动改写——组织调整是独立人工决策。

### DR-056-② 一次性原子交接：预览→执行两段式 + HandoverRecord append-only

- **GET /api/v2/handover/preview**（只读零写路径）：返回离职者五类资产计数 + 警示（接收人非 active / 离职者任部门主管 / from=to / 离职者账号已停用——已停用仍可补交接）
- **POST /api/v2/handover**：单个 `prisma.$transaction` 原子执行全部移交 + 可选停用 + 写交接单；失败整体回滚（不允许半移交状态）
- **HandoverRecord**（append-only 单表）：from/to/操作人/双方姓名快照/五类计数 detail JSON/是否停用/备注——交接即出单，重复执行出零计数新单（操作幂等友好，历史不可篡改）
- 校验：from ≠ to；接收人必须 active 且未软删；离职者不存在 → 404；操作者须持 `users:admin`（用户删除/权限矩阵同级高危 scope，仅 SuperAdmin/Admin）

### DR-056-③ 停用即时失效：组合根账号状态守卫（根因修复）

- **既有缺口**：`extractActorFromRequest` 仅 `jwt.verify` 验签，不查 UserAccount.status；token TTL 7 天——停用后旧 token 在过期前仍持有全部 API 权限，违反"立即失去访问"
- **修复**：`accountStatusGuard` 挂载于组合根（index.ts cookieParser 之后、全部路由之前）——凡携带 JWT 的请求查账号状态（30s TTL 内存缓存），`disabled`/软删 → 401 ACCOUNT_DISABLED 并清 cookie
- **缓存即时失效**：停用/交接路径调用 `invalidateAccountStatusCache(userId)`，同进程立即生效（单节点部署成立）；DB 查询异常 fail-open（可用性优先，行为与修复前一致）；token 对应用户不存在 fail-open（兼容既有测试与遗留 token，验签仍有效）
- 交接单可选 `disableAccount`（默认 true）：同事务置 status='disabled' + metadata 记 disabledAt/disabledBy/handoverId 联链——与既有 admin disable-account 端点同一语义不双轨（该端点同步接入缓存失效）

### DR-056-④ 防批量导出 = 受控导出通道 + 全量审计（SEC-01 双向可验）

- 现状：relations/crm 域**无任何批量导出端点**——"业务员不可导出"仅空缺式成立，无法正向验收
- 新增 **GET /api/v2/relations/export.csv**，门禁 `data:export:full`（矩阵既定仅 SuperAdmin 的高危 scope）：
  - 业务员/普通角色 → 403 INSUFFICIENT_SCOPE（负向验收实证）
  - SuperAdmin → 输出客户档案 CSV（含 confidential，SuperAdmin 本即全权），**每次导出写审计**（actor/行数/过滤条件）
  - 敏感字段分级可见沿用 DR-042 §4.4（sensitivity normal/confidential），不在导出层重造
- 导出范围遵循既有列表过滤参数（category/stage/搜索词），不引入新真源

## §3 模块边界

| 包含 | 不包含 |
|------|--------|
| 五类归属字段批量移交（单事务原子） | 逐客户选择性移交（增强：按筛选拆分多接收人） |
| 账号停用（可选同事务）+ 交接单/审计双留痕 | 抹除个人数据（既有 erase-personal-data 端点） |
| 停用即时失效守卫（组合根 + 缓存失效） | 组织架构调整（Department.headId/TeamMember 仅预览警示） |
| 客户档案受控导出（SuperAdmin + 审计） | 供应商/联系人档案导出（同模式后续按需扩展） |

## §4 数据模型

```prisma
// ============================================================================
// REQ2-13 业务员离职一键交接（X-07 资产安全类）
// ============================================================================
/// 交接单（append-only 留痕）：一次离职交接的完整快照——谁在何时把哪些
/// 客户资产移交给谁、是否停用账号、各类资产计数。历史不可篡改。
/// 设计真源：docs/design/04-模块设计/02-客户与开拓/业务员离职一键交接.md
model HandoverRecord {
  id             String   @id // 格式：HO_${shortId}
  fromUserId     String // 离职者
  toUserId       String // 接收人
  operatedBy     String // 操作人（管理员）
  fromUserName   String // 冗余快照：离职者显示名
  toUserName     String // 冗余快照：接收人显示名
  disableAccount Boolean  @default(true) // 交接时是否同步停用离职者账号
  note           String? // 交接备注
  /// 五类资产计数快照：{ relationsOwned, relationsCoFollowed, opportunities, followUpRecords, unanchoredOrders }
  detail         Json?
  createdAt      DateTime @default(now())

  @@index([fromUserId])
  @@index([toUserId])
  @@index([createdAt])
}
```

## §5 API 合约

挂载 `/api/v2/handover`（moduleAuthGuard requireAuth + requirePermission('users:admin')）：

| 端点 | 方法 | 入参 | 出参 |
|---|---|---|---|
| `/api/v2/handover/preview` | GET | `fromUserId`（必）、`toUserId`（可选，给则追加接收人侧警示） | `{ fromUser, counts{relationsOwned,relationsCoFollowed,opportunities,followUpRecords,unanchoredOrders}, warnings[] }` |
| `/api/v2/handover` | POST | `{ fromUserId, toUserId, disableAccount?, note? }` | `{ ok, handoverId, counts, accountDisabled }` |
| `/api/v2/handover/records` | GET | `limit?`（默认 20） | `{ records[] }`（倒序） |

`/api/v2/relations/export.csv`（GET，requirePermission('data:export:full')）：复用列表过滤参数，CSV 首行表头，审计 action='relations_export_csv'。

错误码：`VALIDATION_FAILED`(400) / `NOT_FOUND`(404) / `SAME_USER`(400) / `INACTIVE_SUCCESSOR`(400) / `UNAUTHORIZED`(401) / `INSUFFICIENT_SCOPE`(403)。

## §6 验收脚本锚点（scripts/acceptance-req2-13.mjs）

1. 管理员登录 → preview 计数与造数一致（含协同跟进/无锚订单）
2. 执行交接 → 五类字段全部改写（DB 断言）+ 交接单落库 + 审计两条（handover_execute/disable_account）
3. 接收人登录 → 客户列表/订单可见性接管（T-38 继承实证）
4. 离职者旧 token 请求任意受保护端点 → 401 ACCOUNT_DISABLED（即时失效实证）
5. 离职者重新密码登录 → 403 DISABLED（既有链路回归）
6. 业务员 token 调 export.csv → 403；SuperAdmin 调 → 200 + 审计落库（SEC-01 双向）
7. from=to / 接收人停用 / 无 users:admin scope → 对应 4xx
