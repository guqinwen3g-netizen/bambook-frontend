# 订单状态机 (Order State Machine)

## §1 元信息

> **2026-10-06 当前设计决策优先于下方旧状态机细节：** 订单主状态按「草稿 → 待订单审批 → 正式订单（审批通过）→ 履约中 → 部分交付 → 已交付」设计，并保留「已取消」。业务员只能提交审批，不能自行确认成正式订单；整张订单统一审批，审批通过后才成为正式订单并可进入履约；审批退回时回到草稿并记录原因。草稿可以暂缺正式 PO/合同附件；外部客户订单提交审批前须关联客户书面确认依据（PO、合同或其他客户确认文件），文件只留证、不做 OCR 或自动填表；内部订单不适用客户文件要求，具体内部审批依据待设计。审批权限按业务范围：面料负责人可审批面料订单，服装负责人可审批成衣订单，大老板可审批两类订单；有权限的人可审批自己的订单，不设自审禁令。提交后，为该订单范围内所有有权审批的人创建/展示同一待办；任一授权审批人先批准或退回即完成该审批，其他人看到处理结果、审批人和时间，不能重复处理；不要求串行双签。正式订单变更单修改客户、产品/准确版本、履约方案、数量/单位、价格/币种、交期、交货地点或付款条件时需重新审批；纯内部备注或经手人调整只留痕、不重审。变更审批通过后才更新正式订单，未通过时原已批准内容继续有效。QC、生产、样品与财务状态由各自专业节点维护并回显，不合并为订单主状态；不设笼统“异常”订单状态。下方原 6 态状态机及 QC 门禁是历史方案，在新矩阵定稿前不得作为当前实施依据。

## §2 6 态定义

| 状态 | 中文 | 语义 | 是否终态 |
|------|------|------|---------|
| `Pending` | 待确认 | PO 录入后初始态；需客户确认 PO | 否 |
| `Confirmed` | 已确认 | 客户确认 PO；可转生产 | 否 |
| `Production` | 生产中 | 厂内生产/加工进行中 | 否 |
| `Shipping` | 出运中 | 已发运；等待客户收货 | 否 |
| `Delivered` | 已交付 | 客户收货完成 | **是**（终态，不可变更） |
| `Alert` | 异常 | 独立异常分支；可恢复到任一非终态 | 否（可恢复） |

**枚举真源**：`VALID_ORDER_STATUSES = ['Pending', 'Confirmed', 'Production', 'Shipping', 'Delivered', 'Alert']`（6 态，不新增 Cancelled）。

**状态徽章语义**（`STATUS_BADGE_VARIANT`）：Pending=neutral / Confirmed·Production·Shipping=info / Delivered=success / Alert=warning。

## §3 合法推进矩阵

**后端真源** `ORDER_TRANSITIONS`（`Record<string, Set<string>>`）：

| 当前状态 (from) | 可推进到 (to) | 说明 |
|----------------|--------------|------|
| Pending | Confirmed / Alert | PO 录入后初始态；需客户确认 PO |
| Confirmed | Production / Alert | 确认后转生产（受 PreCutChecklist 门禁） |
| Production | Shipping / Alert | 厂内生产完成转等待出运（受 Final QC 门禁） |
| Shipping | Delivered / Alert | 已发运；客户收货后转交付 |
| Delivered | — | **终态**，无任何推进（空 Set） |
| Alert | Pending / Confirmed / Production / Shipping | 异常恢复；可选回到任一非终态（业务上通常回到上一态） |

**前端镜像** `ORDER_ALLOWED_TRANSITIONS`：与后端矩阵完全一致，仅做可行动性提示（按钮高亮/禁用），**唯一状态真源仍是后端**。

**步骤条主轴**（`ORDER_FLOW_STEPS`）：`['Pending', 'Confirmed', 'Production', 'Shipping', 'Delivered']` 5 步线性主轴；Alert 作为独立异常分支出现在末尾右侧。

```
Pending ──▶ Confirmed ──▶ Production ──▶ Shipping ──▶ Delivered
   │            │              │             │
   └────────────┴──────────────┴─────────────┘
                       │
                       ▼
                    ╳ Alert ╳  ──▶ 可恢复到 Pending/Confirmed/Production/Shipping
```

## §4 门禁规则（QC 强校验）

> 门禁在后端 `transitionOrderStatus` 内强校验；前端步骤条视觉高亮"下一步可操作"，但点击推进若门禁未过 → toast danger 提示具体缺口。

### 4.1 门禁 1：Confirmed → Production（裁剪前检查）

| 项 | 说明 |
|----|------|
| 校验对象 | `PreCutChecklist` where orderId |
| 通过条件 | 4 项 boolean 全为 true：gradingConfirmed(推码) + consumptionConfirmed(耗料) + patternConfirmed(样板) + preProductionMeeting(产前会议) |
| 未通过 | 409 `裁剪前检查未全部通过，禁止进入生产阶段` |
| 模型 | `PreCutChecklist` `orderId @unique`（一单一表） |

### 4.2 门禁 2：Production → Shipping（最终验货）

| 项 | 说明 |
|----|------|
| 校验对象 | `InspectionReport` where orderId AND inspectionType='final' |
| 通过条件 | `result = 'pass'` |
| 未通过 | 409 `最终验货未通过或未执行，禁止进入出运阶段` |
| 模型 | `InspectionReport` `@@unique([orderId, inspectionType])`（每单 final + midline 各一份） |

### 4.3 门禁 3：产前样双签（在 Sample 模块，非订单状态机内）

| 项 | 说明 |
|----|------|
| 校验对象 | `SampleNode` where developmentCase.linkedOrderId = orderId AND level='pp' |
| 通过条件 | status='approved' + ProductionStage.pp_sample_approved 双签（signedByProduction + signedByBusiness） |
| 位置 | 生产管线 10 阶段的 `pp_sample_approved` 阶段，非订单状态机直接校验 |

### 4.4 待实现门禁（P0 缺口）

| 门禁 | 规则 | 状态 |
|------|------|------|
| 客户逾期 60 天冻结 | `AccountReceivable.dueAge > 60` → 禁止新下单 + 禁止 Pending→Confirmed 推进 | ⚠️ 未实现 |
| 交期锁死 | Shipping/Delivered 阶段 delivery/production 字段只读 | ⚠️ 未实现 |

## §6 后端契约（强校验真源）

`POST /api/v1/orders/:id/transition` → `transitionOrderStatus(params)`：

```
1. 枚举校验: toStatus ∈ VALID_ORDER_STATUSES
   └─ 否 → { code: 'INVALID_STATUS', 400 }

2. 查询 Order（含 deletedAt 校验）
   └─ 不存在/已删 → { code: 'ORDER_NOT_FOUND', 404 }

3. 幂等校验: existing.status === toStatus
   └─ 是 → { code: 'NO_CHANGE', 400 }（前端视为成功，不重写 transition）

4. 合法矩阵校验: ORDER_TRANSITIONS[fromStatus].has(toStatus)
   └─ 否 → { code: 'INVALID_TRANSITION', 400 }

5. （事务内）
   a. Order.update status + updatedAt
   b. OrderStatusTransition.create（id/fromStatus/toStatus/note/operator/lineId/createdAt）
   c. syncOrderEntityReferences（更新 orderedBy/suppliedBy active link）
   d. writeRouteAuditLog（operation: transition_order_status，before/after status）

6. 事务提交后（fire-and-forget，永不阻断业务）
   a. publishBusinessEvent OrderStatusChanged（所有变更都发）
   b. 若 Pending→Confirmed → 额外发 OrderConfirmed（触发生产单创建联动）
```

**错误码**：`ORDER_NOT_FOUND` / `ORDER_ALREADY_DELETED` / `INVALID_STATUS` / `INVALID_TRANSITION` / `NO_CHANGE` / `TRANSITION_FAILED`。

## §7 双校验契约

| 层 | 职责 | 失败行为 |
|----|------|---------|
| **前端** `ORDER_ALLOWED_TRANSITIONS` | 交互级拦截——非法态按钮视觉禁用（不可点击） | 用户无法点击非法推进 |
| **后端** `ORDER_TRANSITIONS` | 强校验真源——事务内合法性 + 门禁 + 审计留痕 | 返回错误码 + 不写入任何数据 |

**设计原则**：前端镜像仅做可行动性提示，**唯一状态真源是后端**。即使前端被绕过（直接调 API），后端事务校验仍拦截。

## §8 OrderStatusTransition 时间线

每次合法推进写入一条 `OrderStatusTransition` 记录：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | `OST_${ts}_${random}` |
| orderId | String | FK → Order（Cascade） |
| fromStatus | String | 推进前状态 |
| toStatus | String | 推进后状态 |
| note | String? | 推进备注（如"客户签字回传 PO"） |
| operator | String? | 操作人（'desktop-user' / actorId / 'api'） |
| lineId | String? | 行级推进标记（可选） |
| createdAt | BigInt | epoch ms |

**查询**：`GET /api/v1/orders/:id/status-history` → `orderBy: { createdAt: 'asc' }`（升序，旧→新）。

**详情页时间线渲染**：圆点（最新=accent 点亮，其余=灰）+ `[最新]` badge + 中文化状态名 + 备注 + 操作人。

## §12 软删归档（deleteOrder）

`DELETE /api/v1/orders/:id` → `deleteOrder(params)`：

```
1. 查询 Order
   └─ 不存在 → ORDER_NOT_FOUND 404
   └─ 已删 → ORDER_ALREADY_DELETED 409

2. 关联保护校验（任一存在则禁止）
   ├─ Invoice.count(orderId, deletedAt=null) > 0
   ├─ Shipment.count(orderId, deletedAt=null) > 0
   └─ PaymentVoucher.count(orderId, deletedAt=null) > 0
   └─ 有 → HAS_DEPENDENTS 400

3. （事务内）
   a. Order.update deletedAt = now + updatedAt
   b. deactivateEntityLinks('order', orderId)（order 发出的所有 active link 置 inactive）
   c. writeRouteAuditLog（operation: delete_order）
```

**注**：归档后订单从默认列表移除（`deletedAt: null` 过滤），可通过"显示已归档"筛选找回；已归档订单不能推进状态或编辑。
