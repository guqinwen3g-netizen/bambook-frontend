## §4 订单类型分层概要

订单类型采用"主类型 + 业务线"二级分层：

```
Order.type ∈ { Fabric, Garment, Other }（3值主分类，Prisma String）
├── Fabric   面料订单（默认 unit=Meter，MOQ 800M）
├── Garment  成衣订单（默认 unit=Pcs，  MOQ 200Pcs）
│   └── Order.businessLine = 'capsule'  Capsule 子视图（设计师小单，MOQ 20Pcs；仅对 type=Garment 生效的子类型透镜）
└── Other    其他订单（DR-028 其他贸易，默认 unit=KG，businessLine=other）
```

**分层规则**：
- 主类型 `Order.type ∈ { Fabric, Garment, Other }（3值主分类）` 决定**字段簇可见性**（`fabric` cluster 仅 Fabric；`materials` cluster 仅 Other；`garmentProduction`/`sampleGarment` cluster 仅 Garment）
- 业务线 `businessLine ∈ { garment, capsule, fabric, other }（4值业务线标签）` 仅对 Garment 生效时 capsule 作为子类型透镜，作为列表 Capsule 子视图透镜与 MOQ 阈值切换依据；未标记的成衣归"大货"
- 详细字段差异矩阵见 [`./订单类型分层.md`](./订单类型分层.md)

## §5 核心业务流程图

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  报价     │───▶│  订单     │───▶│  开发/   │───▶│  BOM     │───▶│  采购     │───▶│  生产     │
│ Quotation │    │  Order   │    │  样衣     │    │          │    │  PO      │    │  Stage   │
│ (conv orderId)│ │ (FK 源)  │    │ DevCase  │    │ (orderId)│    │ (orderId)│    │ (orderId)│
└──────────┘    └────┬─────┘    │ SampleNode│    └──────────┘    └──────────┘    └────┬─────┘
                     │          └──────────┘                                      │
                     │                                                            │
                     │   ┌──────────────────────────────────────────────────────┘
                     │   ▼
                     │  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
                     │  │ QC 验货  │───▶│  出运     │───▶│  发票     │───▶│ 财务凭证 │
                     │  │ Inspect  │    │ Shipment │    │ Invoice  │    │ Voucher  │
                     │  │ (orderId)│    │ (orderId)│    │ (orderId)│    │ (orderId)│
                     │  └──────────┘    └──────────┘    └──────────┘    └──────────┘
                     │
                     │  ┌──────────────────────┐
                     └─▶│  外协 OutsourcingOrder│ (orderId + bomId snapshot FK)
                        └──────────────────────┘

订单状态机（贯穿上述链路的生命周期标记）：
  Pending ──▶ Confirmed ──▶ Production ──▶ Shipping ──▶ Delivered
                                                         
                     ╳ Alert ╳ （异常态：可恢复到任一非终态）

门禁强校验（后端 orderLifecycleService + 前端步骤条双轨）：
  • Confirmed → Production 前：PreCutChecklist 4 项全通过
  • Production → Shipping 前：InspectionReport(final).result = pass
```

**链路关联双轨制**：
1. **EntityLink 图谱**（横向发现）：`/api/v1/relations/by-target?type=order&id={orderId}` → 关联视图面板
2. **直接查表聚合**（纵向生命周期）：`/api/v1/orders/:id/context` → 360° 全链路面板

两轨互补：图谱服务"跨模块横向发现任意实体关联"；聚合查询服务"按业务阶段纵向还原完整生命周期"。

## §6 数据模型概要

订单管理模块的持久化真源由 3 个核心模型 + 6 个履约关联模型组成（全量字段表见数据模型组文档）：

| 模型 | 角色 | 关键约束 |
|------|------|---------|
| `Order` | 订单主表（80+ 字段，含 7 关系快照 + 业务档案） | `id` PK / `code` `poNumber` 双唯一 / `deletedAt` 软删 / 9 索引 |
| `OrderLine` | 订单行（含成衣 JSON 扩展） | `@@unique([orderId, itemNo])` / `onDelete: Cascade` |
| `OrderStatusTransition` | 状态变更时间线事件 | `orderId` FK Cascade / `createdAt` 升序查询 |
| `DevelopmentCase` | 开发案（linkedOrderId snapshot FK） | `code` unique / 软删 |
| `SampleNode` | 三级样衣节点（确认/产前/大货） | `@@unique([developmentCaseId, level])` |
| `ProductionStage` | 生产管线 10 阶段 | `@@unique([orderId, stageKey])` / 双签字段 |
| `PreCutChecklist` | 裁剪前检查（QC 门禁 1） | `orderId @unique` / 4 boolean |
| `InspectionReport` | QC 验货报告（QC 门禁 2） | `@@unique([orderId, inspectionType])` |
| `OutsourcingOrder` | 外协单（orderId/bomId snapshot FK） | `orderNumber @unique` / 软删 |

## §7 字段词典真源约定

所有订单字段的"存在性 / 标签 / 分组 / 类型 / 可见入口 / 适用订单类型"均在 [orderSchema.ts](file:///Users/qinwengu/WorkBuddy/Claw/apps/Bambook/lib/orderSchema.ts) 的 `ORDER_FIELDS` 数组中登记一次，订单详情卡与手动录入弹窗共享字段真源。客户 PO/合同文件只作为证据附件，不参与字段识别或自动填表。

- 当前设计只有详情与手动录入两种订单字段视图；旧实现中的 `shownInImportPreview` / `ImportWizard` 属于历史实现，不能解释为 MVP 自动识别或导入方案
- `cluster` 决定分组（13 cluster），`ORDER_CLUSTERS` 决定组内顺序（detailOrder / manualOrder 分离）
- `applicableTypes` 决定类型分层（undefined = 通用；显式列表 = 仅列出的类型可见）
- `level`（'order' / 'line'）+ `lineScope`（'first' / 'each' / 'aggregate'）决定 OrderLine 级字段渲染策略
- `relationFk` + `autoFillFrom` 决定 Relation 下拉选择后的字段联动填充

新增字段的强制流程：先在 `ORDER_FIELDS` 登记 → 再在 `types.ts` 的 `Order` / `OrderLineLite` 接口加列 → 编译器用 `keyof Order` 约束保证不跑偏。

## §10 设计系统约束

本模块遵循 BDS RDL 中性契约（详见各子文档 §14）：
- 禁止硬编码 hex 颜色 / `rounded-[Npx]` / `box-shadow`，全部走 CSS 变量 + Tailwind 语义类
- 子组彩色竖条已废除（买卖四方仅靠文字层级 + kicker 分组）
- 空态不使用插画/吉祥物，仅文字 + line-height 小 Lucide 图标
- 状态徽章通过 `STATUS_BADGE_VARIANT` 映射 bds-badge 语义变体（neutral/info/success/warning）
