## §2 二级分层模型

```
Order.type (主类型，Prisma String，必填)
├── Fabric   面料订单
│   适用 cluster: basic + parties + delivery + fabric + sales + purchase + instructions
│   默认 unit: Meter
│   MOQ: 800 Meter（待实现）
│
├── Garment  成衣订单
│   适用 cluster: basic + parties + delivery + sales + purchase + instructions
│   + OrderLine 级专属: garmentProduction + sampleGarment
│   默认 unit: Pcs
│   MOQ: 200 Pcs（大货）/ 20 Pcs（Capsule）
│   │
│   └── Order.businessLine = 'capsule'  Capsule 子标记（设计师小单业务线）
│       列表 Capsule 子视图透镜：capsuleActive = (orderType==='garment' && capsuleOnly)
│       MOQ 降至 20 Pcs（待实现）
│
└── Other    其他订单（辅料/纱线/其他物料）
    适用 cluster: basic + parties + delivery + materials + sales + purchase + instructions
    默认 unit: KG
    MOQ: 待定
```

**分层规则核心**：
- **主类型 `type`** 决定 cluster 可见性（`fabric` 仅 Fabric；`materials` 仅 Other；`garmentProduction`/`sampleGarment` 仅 Garment 且在 OrderLine 级）
- **业务线 `businessLine`** 仅对 Garment 生效，作为列表 Capsule 子视图过滤 + MOQ 阈值切换依据；未标记的成衣归"大货"

## §3 类型键值映射

| UI key | DB 值（Prisma Order.type）| 中文 | 转换函数 |
|--------|--------------------------|------|---------|
| `fabric` | `Fabric` | 面料 | `ORDER_TYPE_DB_VALUE` |
| `garment` | `Garment` | 成衣 | `ORDER_TYPE_DB_VALUE` |
| `other` | `Other` | 其他 | `ORDER_TYPE_DB_VALUE` |
| `all` | — | 全部 | 仅视图状态，非订单内在类型（`OrderViewType = OrderTypeKey \| 'all'`） |

**反向映射**：`dbValueToTypeKey(dbValue)` —— Garment→garment / Other→other / 其余（含 null/undefined/未知）兜底为 fabric。

**业务线值**：`Order.businessLine` 字符串快照，取值 `businessLine ∈ { garment, capsule, fabric, other }`（4值业务线标签；snapshot，不强制外键；capsule 仅对 type=Garment 生效，作为子类型透镜）。设置端点 `POST /api/v1/orders/:id/set-business-line`。

## §5 Other 贸易（DR-028）

> **DR-028 决策点 5-A 方案**：轻量归集，共用表单透镜过滤，不独立建视图。`Order.type=Other` + `businessLine=other`，字段最少化，流程压缩为 4 阶段。

### 5.1 录入表单：字段最少化

字段最少化（详见核心业务流程§6.3最小必填字段簇）：
- **仅保留通用 cluster**：basic 基础档案 + parties 买卖四方 + delivery 交期与物流 + sales 销售与收汇 + purchase 采购与供应商 + instructions 特别说明
- **隐藏专属 cluster**：fabric 面料规格（仅 Fabric）、materials 物料信息（保留 materialCategory/materialSpecNotes 作为精简扩展）、sampleShipment/sampleFabric（样品相关，Other 不强制）、garmentProduction/sampleGarment（成衣专属，全部隐藏）
- **最小必填字段**：订单编号(自动)、负责人(默认当前用户所属部门)、业务方向(自由文本)、交易对方名称与国家(关联Customer但不强制CRM建档)、订单总金额(币种+金额)、预期交付日期(可选)、备注说明(自由文本)

### 5.2 阶段状态机：压缩为 4 阶段

Order 状态机压缩为 4 阶段（前端按 `Order.type=Other` 条件渲染，其余状态隐藏）：

```
Draft → Confirmed → Fulfilled → Closed
```

| 阶段 | 含义 | 触发条件 |
|------|------|---------|
| Draft | 草稿 | 新建订单默认状态 |
| Confirmed | 确认 | 业务确认后推进（无 PreCutChecklist/PP 双签门禁） |
| Fulfilled | 履约完成 | 采购 + 出运完成后推进（无 QC 终期验货门禁） |
| Closed | 关单 | 收付款结清后关单 |

原 6 态状态机中的 Production / Shipping / Delivered / Alert 对 Other 订单不显示、不创建、不推进。

### 5.3 生产管线 ProductionStage 模型

对 `Order.type=Other` 的订单，创建时仅生成以下 4 个阶段记录，其余 10 阶段（order_placed / materials_confirmed / production_planned / in_production / materials_arrived / pre_cut_checked / pp_sample_approved / manufacturing / final_review / qc_shipped）**不创建、不显示**：

| stageKey | stageSeq | 默认 status | 说明 |
|----------|:--------:|:-----------:|------|
| PENDING | 1 | pending | 预创建（Draft 态对应） |
| CONFIRMED | 2 | pending | 业务确认（Confirmed 态对应） |
| FULFILLED | 3 | pending | 履约完成（Fulfilled 态对应） |
| CLOSED | 4 | pending | 关单（Closed 态对应） |

后端 Service 层：创建 Order 后检测 `type=Other` → 仅 upsert 上述 4 行 ProductionStage，跳过 10 阶段标准初始化。

### 5.4 QC 门禁：不启用任何 QC 门禁

QC InspectionReport 对 Other 订单的处理：
- **UI 隐藏创建按钮**：在订单详情页 360° / QC 工作台的「新建验货报告」按钮，按 `Order.type=Other` 条件隐藏
- **后端校验**：POST `/api/v1/inspection-reports` 时检测 order.type=Other → 返回 400「Other 贸易订单不支持 QC 验货」
- **查询只读**：若历史数据有 InspectionReport（误操作创建），列表仍可查询但无新建入口

## §7 OrderLine 级成衣扩展字段（JSON）

成衣类型专属字段存储在 `OrderLine` 模型（非 Order），因为一个成衣订单可能有多个款号/色号 line：

| 字段 | 类型 | 结构 | 用途 |
|------|------|------|------|
| sizeBreakdown | Json? | `{ S: 100, M: 200, L: 200, XL: 100, XXL: 50 }` | 尺码配比数量 |
| productionSteps | Json? | `[{ step: "cutting"\|"sewing"\|"qc"\|"packing"\|"shipping", status: "pending"\|"in_progress"\|"done", date?, note? }]` | 生产工序泳道 |
| styleNo | String? | — | 款号 → 关联 ProductAsset/GarmentProfile |
| colorName | String? | — | 色号名称 |
| bomItems | Json? | `[{ type: "fabric"\|"lining"\|"trim"\|"packaging", name, spec?, qty, unit }]` | BOM 物料清单 |
| garmentSampleStages | Json? | `[{ stage: "proto"\|"photo"\|"sizeSet"\|"pp", status: "pending"\|"sent"\|"confirmed"\|"rejected", sentDate?, confirmedDate?, comments? }]` | 成衣样衣 4 阶段 |

**前端类型**（types.ts）：`ProductionStep` / `BomItem` / `GarmentSampleStage` 接口约束 JSON 结构。

**`level: 'line'` + `lineScope`**：
- `lineScope: 'first'` —— 渲染首行（如 styleNo 从首行带出）
- `lineScope: 'each'` —— 每个 line 独立渲染（如 sizeBreakdown）
- `lineScope: 'aggregate'` —— 聚合所有 line（如 bomItems 合并）

## §9 Capsule 子视图透镜

Capsule 是成衣业务线下的设计师小单子标记，**仅对 Garment 类型生效**：

| 项 | 说明 |
|----|------|
| 触发 | 成衣 Tab 下 `capsuleOnly` 开关开启 |
| 条件 | `capsuleActive = orderType === 'garment' && capsuleOnly` |
| 过滤 | `o.businessLine === 'capsule'`（未标记的成衣归大货，不显示） |
| 设置端点 | `POST /api/v1/orders/:id/set-business-line`（body: businessLine='capsule'\|'garment'） |
| 详情页切换 | 概览区下方 `bds-segment` 双段开关（成衣大货 / Capsule），仅 Garment + 非编辑模式显示 |
| MOQ 差异 | Capsule 20 Pcs（待实现）vs 大货 200 Pcs |

**业务语义**：Capsule = 设计师小单业务线，单量小、款多、快反；与成衣大货共享 Garment 字段簇，但 MOQ 阈值与列表视图独立。
