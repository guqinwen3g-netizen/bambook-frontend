## §1 域分割：设计确认 vs 生产确认

| | **设计确认（开发管理域）** | **生产确认（样品管理/生产管理域）** |
|---|---|---|
| 服装 | 开发样 → 确认样（封样） | 产前样 PP1/PP2（多轮客户确认）→ 大货样 |
| 面料 | 色样 / 手织样 / 米样 → 封样 | 先锋样 / 船样 / 匹头样 |
| 本质 | **确认设计是否匹配客户** | **确认大货生产是否达标** |

**分割点**：样品生命周期里，"封样=确认样"是设计确认的终点；之后（转档案→转大货订单）进入生产确认——产前样/大货样/船样等是对大货生产的确认，**不属于开发管理**。

## §2 样品生命周期与类型演进

```
开发管理域（设计确认）           样品管理域（生产确认）            生产
  开发样/色样/手织样/米样           ├─ 产前样 PP1/PP2（按档案复刻）
    → 寄样/反馈 → 封样=确认样        ├─ 大货样（首件留档）
    → 【开发管理结束】              ├─ 先锋样/船样/匹头样（订单产生）
        ▼                          └─ 每个样品对象 = 发票触点
  转数字档案（产品）
        ▼
  转大货订单 ───────────────────►（产前样批准=开裁前置）
```

**类型可演进 / 可合并**：理论上开发样→产前样→大货样渐进，但实际开发样可能就是产前样（合并）。确认样 = 大货生产标准/模板。样品对象支持**复刻（fork）**：确认样封存 → 大货订单后按档案复刻出产前样（新样品对象，关联订单+大货工艺差异）。

## §3 核心实体：Sample（统一样品对象）

```prisma
/// 设计真源：样品管理域设计.md（DR-052）
/// 统一样品对象：承载设计确认产物与生产确认产物，类型可演进，产物级开票触点。
model Sample {
  id   String @id // 格式：SMP__${shortId}
  code String @unique // 业务号：SMP-YYYYMMDD-001

  // ── 类型（可演进） ──
  type String // dev(开发样) | seal(确认样/封样) | pp(产前样) | top(大货样)
              //  | ship(船样) | head(匹头样) | pioneer(先锋样)
  subType String? // 面料：lab-dip/handloom/yardage；成衣：fit/pp/size-set 等（对齐开发管理样品类型）

  // ── 来源（设计确认 ↔ 开发案；生产确认 ↔ 订单） ──
  sourceCaseId  String? // 设计确认样品：来源开发案
  sourceOrderId String? // 生产确认样品：来源大货订单
  productAssetId String? // 关联产品档案（封样后转档回填）

  // ── 归属 ──
  supplierRelationId String? // 打样/生产工厂（多工厂场景）
  customerRelationId String? // 客户（可空=内部）

  // ── 状态机（按 type 语境，见 §4） ──
  status String @default("draft") // 设计确认：draft/making/sent/confirmed/sealed
                                  // 生产确认：draft/making/qc/submitted/confirmed/approved
  round  Int @default(1) // 轮次（PP1/PP2…；开发样复样轮次）

  // ── 寄样 / 反馈 / 批准 ──
  sentDate       String?
  courier        String?
  trackingNumber String?
  shippingFee    Float?
  recipientName/Company/Address/Phone String? // 寄样收件信息
  feedback       String?
  feedbackDate   String?
  approvedAt BigInt?
  approvedBy String?

  // ── 生产确认门禁（产前样：QC + 客户确认） ──
  qcStatus       String? // null/passed/failed
  qcInspectionReportId String? // QC 报告
  customerStatus String? // null/approved/rejected/needs_revision

  // ── 复刻（类型演进） ──
  forkedFromSampleId String? // 由哪个样品复刻（确认样 → 产前样）
  // ── 开票触点 ──
  invoiceId String? // 产物级发票关联（每个样品可开票）

  notes String?
  createdAt BigInt
  updatedAt BigInt
  deletedAt BigInt?

  @@index([sourceCaseId])
  @@index([sourceOrderId])
  @@index([productAssetId])
  @@index([supplierRelationId])
  @@index([type])
  @@index([status])
}
```

## §4 状态机（按类型语境）

**设计确认样品**（dev/seal）：`draft → making → sent → confirmed → sealed（封样终态）`，`revising（→making round+1）`——对应开发管理的"确认样/封样"。
**生产确认样品**（pp/top/ship/head/pioneer）：`draft → making → qc(通过) → submitted(客户) → confirmed → approved(批准)`；产前样 **approved = 开裁前置**（生产放行门禁消费）。

## §5 类型演进 / 复刻

- **封样（sealed）**：设计确认样品封存 = 开发管理结束；回填 `productAssetId`（转档案）
- **复刻（fork）**：大货订单后，样品管理里基于确认样/档案**复刻**出产前样（`type=pp`，`forkedFromSampleId` 溯源，`sourceOrderId` 关联订单，可带大货工艺差异）→ 多轮（PP1/PP2）→ 批准
- **大货样（top）**：产前样首件留档（复刻/升级）
- **船样/匹头样/先锋样**：从订单产生（`sourceOrderId`），走生产确认状态机

## §6 发票触点（产物级开票）

每个样品对象（无论开发样/确认样/产前样/船样…）都是**独立开票触点**：
- 从样品开票 → 自动带出客户（或内部部门）、默认条目（该样品数量/邮寄费等登记信息）
- 条目可手动删减（登记多、开票不一定全要）
- 回填 `Sample.invoiceId`，详情可直达发票

> 取代"开发案/订单级笼统开票"：开票以**实际产物为触点**。

### §12.1 主场景全链路走查（同案两厂 → 部分确认 → 分档案 → 选版本下单 → 产前样返修放行 → 样品费部分免收/抵货款）

> 约定："版本"不预设新对象。现系统里"已确认的开发成果"由 **封样（SealSample）/ 确认样（Sample seal）→ 转换的产品档案（ProductAsset）** 表达——这就是版本载体。推演即把这条已存在的关系显式化。

| # | 步骤 | 谁操作 | 操作哪个对象 | 产生什么记录 | 确认什么版本 | 下一模块接收 | 失败/撤回 |
|---|---|---|---|---|---|---|---|
| 0 | 同案两厂立项 | 开发负责人 | DevelopmentCase(type=fabric, source=customer-sample) | 开发案 + DevelopmentSupplier 挂 A、B 两厂 | — | 开发详情按厂展示试样任务 | 案取消（stage=cancelled） |
| 1 | A/B 两厂打样 | 开发业务员 | SampleBatch（supplierRelationId=A / B 各一条） | 批次 pending→making→sent（寄样/邮费留痕） | 未确认 | 寄样信息进开发详情（批次级） | 批次 revising 开新轮 |
| 2 | 部分确认 | 客户判定（业务员登记） | SampleBatch | A 批 `customerStatus=approved`+`approvedAsSealed`；B 批 rejected/needs_recast | **A 批 = 确认批次**（缸号/评级/疵点/照片证据链） | 封样入口（只能组 A 批） | B 批 needs_recast → 新轮 |
| 3 | 封样 + 转档 | 开发业务员 | SealSample（组 A 批，同厂强校验）→ convert-to-asset | SealSample sealed→converted + `convertedProductAssetId`；ProductAsset+FabricProfile | **A 封样 = 确认版**（sealCode 唯一） | 产品档案 | 转档终态不可逆 |
| 4 | 选版本与工厂下单 | 业务员 | 转单（现状：convertService 认单一 productAssetId+原供应商） | Order + OrderLine（`materialCode=sku`，**无 productAssetId/版本**） | 应选 B 封样/档案+B 厂 | 生产管线 | 订单取消（DR-010 控制） |
| 5 | 产前样返修后放行 | 工厂/生产/业务 | production stage `pp_sample_approved` + 统一样品 Sample(type=pp) | 双签 + Sample(pp,approved)（若从封样复刻） | 产前样版本 | 开裁前置放行 | 返修 round+1 |
| 6 | 样品费部分免收/抵货款 | 业务员/财务 | 现状：invoiceSample 直接建 Receivable Draft | Invoice(Receivable)+Sample.invoiceId 回填 | — | 财务 AR | 回填失败仍返成功 → 重试重复建票 |

**关键卡点（推演暴露）**：
- **步骤 4 是三处断裂汇合点**：① `DevelopmentCase.productAssetId` 单一——A 封样已回填，B 封样转档后无处可存；② `linkedOrderId` 判重——客户先向 B 下单、后向 A 返单时第二次转单被 `ALREADY_CONVERTED` 拒绝；③ OrderLine 无档案/版本字段——订单不知道自己用了哪个确认版。
- **步骤 5 确认状态机脱节**：生产管线双签与统一样品批准是两套独立事实，互不读取；返修后 Sample(pp) 与 production stage 各自推进。
- **步骤 6 收费无来源**：默认金额=邮寄费，无法表达"多轮合并收费 / 部分免费 / 开发失败仍收开发费 / 样品费抵货款"。

### §12.2 三检查场景

**场景 A 内部开发**（source=internal，departmentId）：无外部客户。确认版照常转档；收费承担方应是**内部部门**（DR-005 内部交易口径），或免收。现状 `invoiceSample` 只认 `sample.customerRelationId`（可空=内部），无内部部门/承担方维度 → 收费事项需"承担方（客户/内部部门/供应商）"字段。

**场景 B 开发终止但需收费**（stage=cancelled 后收费）：案取消不阻断收费——A/B 厂已发生的试样/邮寄费仍需向客户收。推演结论：**收费资格不绑"开发案状态"也不绑"开发成果"**，绑"费用发生事实"（样品/封样/批次/开发案取消均可在终止后触发收费）。

**场景 C 已有产品直接返单**（不经开发）：客户对已有 ProductAsset 直接下单。现状 OrderLine 无 `productAssetId` 字段 → 直接返单无法记录"用了哪个档案"。推演结论：**订单行引用档案/版本是订单域通用能力，与开发案解耦**——返单只需选档案+工厂建订单行，不走 convertService。

### §12.3 最小实体关系（显式化既有关系，不新增"开发成果"对象）

以下为首轮推演假设，已由 §12.8 修正；阶段 2 实施以 §14 为准。首轮曾认为现有系统已具备版本载体（封样/确认样 + 产品档案），缺的是**两个连接器**：

```
DevelopmentCase ──多对多── DevelopmentSupplier(A/B 厂)          （已有）
DevelopmentCase ──1..N──── SampleBatch ──SealSample ──ProductAsset（已有，productAssetId 仅存单一快照）
DevelopmentCase ──1..N──── Sample(seal/pp)                        （DR-052 已有）
ProductAsset ──1..N──────── OrderLine.productAssetId              （缺失：OrderLine 现仅 materialCode=sku）
OrderLine ──0..1─────────── Sample(pp,approved)                   （缺失：生产放行依据引用）
费用发生事实(样品/封样/案取消) ──1..N── 收费事项 ──应收草稿(Draft) ──签发(Issued) （缺失：收费事项层；PI 仅外贸可选前置）
```

**收费四层表达（DR-053 阶段 0 起统一口径）**：
1. **费用发生**＝成本记录（实际打样/邮寄花费，归集口径）；
2. **收费决定**＝收费事项（客户应承担金额、免收/抵扣决定、内部归集）；
3. **应收草稿**＝Invoice(status=Draft)——收费决定确认后才生成，费用发生**不自动**形成应收；
4. **正式签发**＝Invoice(status=Issued)——对客户生效；**PI（Proforma）仅是外贸场景的可选前置**（quotation→PI→签发），**不设为所有应收的必经步骤**（内销/简单场景：收费决定→应收草稿→直接签发）。

**改动原则**：
1. `DevelopmentCase.productAssetId` / `linkedOrderId` **降级为快照**（最近一次/主档案），不承担唯一商品、唯一订单；多档案/多订单关系由各封样`convertedProductAssetId` + OrderLine 引用承载。
2. **OrderLine 新增 `productAssetId` + `confirmedSampleId` + `version`**：订单行显式记录用了哪个确认版——这是打通多方案/返单/直接下单的公共能力，与开发案解耦。
3. **生产放行绑"订单×产前样确认依据"**（OrderLine/Sample pp approved 或 stage 双签同源），不绑开发案、不绑开发成果。
4. **收费资格绑"费用发生事实"**：新增收费事项（来源=样品/封样/开发案/订单行、费用类型、承担方、金额币种、免收/抵扣决定）→ 生成**应收草稿**；外贸场景可选 PI 前置，不强制。

### §12.8 结论修正（相对 §12.3）

"已有版本载体、只缺两个连接器"**部分成立，需修正为四点能力缺口**：

1. **版本引用**：版本载体=**封样/确认样确认记录**（稳定 ID + 不可变），非档案；订单行需 `sealSampleId/sampleId` + 规格快照（或引用封样取规格）——补"档案可变导致历史订单依据漂移"。
2. **转单入口按确认成果选择**：`GET /cases/:id/outputs`（封样→档案列表）+ convert 带 `sealSampleId|sampleId` + 成果归属工厂 ID（修"显示 B 厂实际关联 A 厂"）+ 解除 `linkedOrderId` 单次判重（改多订单关系，`linkedOrderId` 降级快照）。
3. **生产放行行级化 + 失效联动**：放行维度补 orderLineId/样品绑定；返修/撤销 → 放行资格失效（当前实施方案以 §14 为准：追加失效事件并重算范围资格，保留历史 stage 完成事实）。
4. **成本与应收解耦**：新增成本记录（费用发生）+ 收费事项（收费决定）两层；应收草稿只在收费决定确认后生成，**PI 仅外贸可选前置，非必经**。

**最小改造方案（按依赖排序）**：
- **阶段 0（独立缺陷修复）✅ 已完成（2026-09-07）**：invoiceSample 权限对齐 `invoices:write` + Invoice 来源唯一约束防并发/重试重复建票（按权限、并发重复请求、失败重试、审计一致性验收；**不代表业务链路打通**）。
- **阶段 1**：OrderLine 加 `sealSampleId/sampleId/version/规格快照` + 转单改选确认成果 + 工厂取成果归属 + 多订单关系。
- **阶段 2**：生产放行行级化 + 返修失效联动（Sample(pp)↔订单行绑定为单一事实源；历史批准保留，返修后新增失效/暂停记录，不抹历史）。
- **阶段 3**：成本记录 + 收费事项（应承担/免收/抵扣/内部归集）→ 应收草稿（Draft）→ 签发（Issued）；PI 仅外贸可选前置。
- **阶段 4**：前端同规则展示（结果/缺口/下一步/生成物）。

## §13 阶段 1：订单行版本引用 + 按成果与工厂转单（DR-053 ✅ 已实现 2026-09-07）

> **性质**：2026-09-07 已确认并实施（仅后端契约）。打通"同案双厂分别下单 / 同成果多次返单 / 直接返单 / 档案修改不影响历史订单 / 错误工厂拒绝 / 重复请求不重复建单"。**前端转单弹窗改造为后续子步骤（未做）**。
> **五项要求逐条落点**：①版本引用建模；②按成果选工厂+关系验证；③多次下单+幂等；④无开发案下单；⑤旧数据不伪造版本。

### §13.1 数据模型草案

```prisma
// ── Order 新增（幂等 + 来源快照）──
model Order {
  // ...既有字段不变
  sourceCaseId   String?  // 来源开发案（冗余快照；开发案→订单列表直接反查；linkedOrderId 降级为最近一次快照）
  clientRequestId String?  // 调用方幂等键（UUID；每次真实操作生成一次，重试复用）——防重复提交建单

  @@unique([clientRequestId]) // PG 对 NULL 不互斥，历史订单安全
}

// ── OrderLine 新增（版本引用，结构化解——不堆可空业务字段）──
model OrderLine {
  // ...既有字段不变（itemNo/materialCode 保留兼容，退出路径见 §13.5）

  // 版本引用（单一来源语义，三选一互斥）：
  confirmedSourceType String? // 'SealSample'(封样) | 'Sample'(统一样品) | 'Asset'(直接返单·无确认记录)
  confirmedSourceId   String? // 对应类型 ID
  confirmedAt         BigInt? // 确认依据（选择该版本的时间）
  confirmedBy         String? // 确认人
  // 不可变规格快照（从确认成果拷贝；档案后续修改不影响历史订单）
  specSnapshot        Json?   // { composition, weight, width, ... } 面料/成衣同构
  // productAssetId 冗余（由 confirmedSourceId 推导，服务端保证一致性，不手填）

  @@index([confirmedSourceType, confirmedSourceId]) // 成果→订单反查
}
```

**关键取舍 T1 — 版本引用结构**：`confirmedSourceType+confirmedSourceId` 一对字段承载来源（枚举 + ID），**不**堆 `sealSampleId/sampleId/version` 三个可空列。`version` 不单独建模——**版本载体=确认记录本身**（SealSample 的 sealCode / Sample 的 code 即版本标识）；`specSnapshot` 承载不可变规格，档案可变不再影响历史订单。`productAssetId` 为派生冗余，`confirmedSourceType∈{SealSample,Sample}` 时服务端校验其 === 成果转档档案，**互斥**（不能同时手工指定 asset）。

### §13.2 工厂选择与关系验证（取舍 T2）

- 输入改传 **`millRelationId`（工厂 ID）**，不再只传 millName。
- 后端统一校验链：成果 sealed/approved → **成果归属工厂 === millRelationId**（否则 `409 MILL_MISMATCH`）→ 从成果取 `convertedProductAssetId`（SealSample）或 `productAssetId`（Sample）→ 统一生成名称快照（product=档案名 / millName=工厂 Relation 名 / materialCode=sku）。
- 修掉阶段 1 前的问题："显示 B 厂、实际关联 A 厂"（此前前端传名、后端取 case 原供应商）。

### §13.3 多次下单 + 幂等（取舍 T3）

- **解除单次限制**：`DevelopmentCase.linkedOrderId` 判重移除（降级为"最近一次"快照）；Order 新增 `sourceCaseId` 冗余快照——开发案→订单列表直查；成果→订单反查走 `OrderLine.confirmedSourceId`。
- **幂等**：Order 新增 `clientRequestId` + unique；autoCreate 模式 convert 必传（link 模式传 orderId 天然幂等）。同 clientRequestId 重试 → 返回已有订单（`recovered=true`），**不重复建单**。
- **区分合法返单 vs 重复提交**：合法返单 = 新 clientRequestId（同成果可多次下单）；重复提交 = 同 clientRequestId（幂等恢复）。

### §13.4 无开发案下单（取舍 T4：直接返单走同一契约）

- `confirmedSourceType='Asset'`：已有 ProductAsset 直接建订单行（无确认记录，`specSnapshot` 从档案当前规格拷贝，标注"档案当前版本快照"）。
- 新端点 `POST /api/v1/orders/lines`（不经过 convertService/开发案），输入：`confirmedSourceType/confirmedSourceId(=Asset id)/millRelationId/clientRequestId/quantity/dueDate/quoteAmount`。
- 与开发案转单共用同一校验链（成果→档案→工厂一致性 + 幂等键）。

### §13.5 旧数据不伪造版本（取舍 T5）

- 历史 OrderLine：`confirmedSource*` 为 null → 列表/详情显示 **「未标注版本（历史订单）」**，不推导不伪造。
- 补录：`PATCH /api/v1/orders/:id/lines/:lineId/version`（补 `confirmedSourceType/Id` + `specSnapshot`，可选，留审计）。
- 旧字段退出：`itemNo/materialCode` 保留兼容（sku 快照仍写），但**版本依据只认 `confirmedSourceId`**；新建行不再从旧字段推导版本。

### §13.6 API 草案

| 端点 | 说明 |
|---|---|
| `GET /cases/:id/outputs` | 确认成果列表（封样/样品 → 档案 → 归属工厂），供转单/返单选择 |
| `POST /cases/:id/convert`（改造） | body：`confirmedSourceType/confirmedSourceId/millRelationId/clientRequestId/quantity/dueDate/quoteAmount`；建 OrderLine 写版本引用 + 规格快照 |

### §13.7 迁移草案

手写幂等 SQL（对齐阶段 0 惯例）：Order 加 `sourceCaseId`/`clientRequestId`（+ unique 索引）、OrderLine 加 `confirmedSourceType/confirmedSourceId/confirmedAt/confirmedBy/specSnapshot`（+ `(confirmedSourceType, confirmedSourceId)` 索引）。**不迁移旧数据**（历史行保持 null，见 §13.5）。

### §13.8 验收场景映射

| 场景 | 判定 |
|---|---|
| 同案两厂分别下单 | convert 选 SealSample(A)/SealSample(B)，各建单，Order.sourceCaseId 同案、OrderLine.confirmedSourceId 不同 |
| 同成果多次返单 | 同 SealSample 两单（不同 clientRequestId）→ 合法 |
| 多行不同版本 | 一单多行，各行 confirmedSourceId 不同 |

| 重复请求不重复建单 | 同 clientRequestId 重试 → 返回已有订单（recovered），不新建 |

## §14 阶段 2：生产放行范围化 + 返修失效联动（DR-053 ✅ 后端核心已实现 2026-09-07）

> **性质**：2026-09-07 经用户授权修订的设计方案；**后端核心已实现**（数据库、服务、API、权限、返修联动、门禁汇总、7 测试用例）。**前端展示、影子对账、历史补证、生产执行端点接入（开裁等受控动作的 scope 级检查）为后续子步骤（未做）**——§14.8 完成标准要求前端操作/历史处理/执行前门禁/恢复路径共同成立，本批次仅达成后端契约与资格判定 API。
> **目标**：生产动作按订单行／实际批次判断资格；批准证据不可变；返修、撤销及版本变化即时使受影响资格失效；已发生的生产事实保留。
> **实施前置**：§13 目前记载的是阶段 1 后端契约，前端成果选择尚未完成。实施时核对真实 schema/API；补齐前端成果、工厂、历史版本展示后才可宣称端到端交付。Sample.code/sealCode 仅标识对象，不能单独证明其内容不可变。

### §14.1 适用范围与领域边界

1. **实际执行单位为 ReleaseScope（放行范围）**：必须归属一个有效订单行和生产工厂；可覆盖整行，也可绑定实际生产批次稳定 ID。订单级无行记录不能作为新放行依据。batchKey、批次名称仅供展示，不承担身份。
2. 未拆批时使用整行 scope；拆批后整行 scope 退出当前适用集合，新批次各自建立 scope。禁止整行和其子批次同时作为有效覆盖，禁止重叠数量。范围保存数量、单位与修订号，校验批次归属及总量；拆批／增量不自动继承批准。
3. **订单级 ProductionStage 是汇总视图**：全部当前 scope 有效则 ready，部分有效则 partial，均不有效则 blocked；历史 done 时间作为历史事实保留。不得用整单未 ready 阻止已放行的无关行／批次。整单暂停是另一个有原因、权限、历史的控制动作，可覆盖全部 scope。
4. 本阶段控制产前样依据下的开裁及适用生产启动动作。其他验货／出运门禁继续独立判定。并非所有品类都需要产前样：是否适用由服务端业务规则明确判定；不适用必须返回规则依据，缺少样品不能默认为不适用。
5. 一个批准样可用于多个 scope，但每个 scope 都必须明确校验与绑定。不能仅凭同订单、同款号或同开发案推断覆盖。

### §14.2 数据模型与不可变边界

以下为逻辑实体契约，实施时复用语义一致的既有实体；不要求机械新增同名表。

| 实体 | 必要字段／约束 | 写入规则 |
|---|---|---|
| ReleaseScope | id、orderId、orderLineId、factoryRelationId、productionBatchId（整行可空）、quantity、unit、scopeRevision、当前规格依据 ID/摘要、适用状态 | 行/批次稳定身份；数量、工厂、规格、拆批变化递增 revision，使旧批准不再匹配 |
| SampleEvidenceRevision | id、sampleId、round、证据修订号、工厂、规格快照及摘要、QC 报告版本/结论、客户确认记录、来源记录 | 冻结后不修改；新轮次、补充或更正关键证据生成新修订；附件须稳定版本或内容摘要，不能只存可变 URL |
| ReleaseRequest | id、scopeId、scopeRevision、evidenceRevisionId、规格依据快照、规则版本、requestRevision、状态 | 固定本次审批输入；输入变化作废待签请求，重新发起 |
| ReleaseSignature | id、requestId、role、actorId、signedAt、签署输入摘要 | 追加；同请求同角色唯一；身份来自认证上下文，两角色分别签署且由不同人员承担 |
| PpSampleRelease | id、requestId、scopeId、scopeRevision、evidenceRevisionId、规格摘要、签字引用、approvedAt、规则版本 | 两签齐备且服务端重验通过后写入；requestId 唯一；批准事实禁止覆盖／删除 |
| ReleaseEvent | id、scopeId、releaseId（批准前可空）、sequence、kind、reason、actorId、occurredAt、触发源及幂等键 | 仅追加；kind 包括 granted/paused/resumed/revoked/invalidated/superseded；scope 内 sequence 唯一；同触发源不得重复处理 |
| ReleaseCurrent | scopeId（唯一）、releaseId、state、lastSequence、revision | 可更新的当前投影，非历史真源；随事件同事务更新，可由事件重建 |

**版本衔接**：订单行的 confirmedSourceType/Id 提供来源追溯，specSnapshot 提供下单规格。审批必须锁定该订单行当前受控规格修订／摘要以及产前样证据修订；不能把来源对象 ID 或“选择该版本时间”当作原始客户确认凭据。历史订单缺规格依据时显示 missing_evidence，补录留审计，不伪造历史批准。

**状态语义**：paused 表示可恢复的行政/执行暂停；invalidated 表示返修、证据或范围变化使依据失效，不能直接 resume；revoked 表示主动撤销，也不可恢复原批准。新批准建立后可追加 superseded 事件引用被替代批准。暂停不是批准，不创建带虚构批准人的占位记录。

### §14.3 统一资格判定与执行约束

统一后端服务 `evaluateProductionRelease(scopeId, action)` 返回 `eligible`、原因码、scopeRevision、releaseId、evidenceRevisionId、状态版本及缺项。页面、生产 API、批量操作和 Agent 共用同一判定；读取结果仅供展示，不是可长期复用的通行证。

有效资格必须同时满足：

- 当前 scope 有效且与订单行、生产批次、工厂、数量范围一致；
- 批准锁定的 scopeRevision、订单规格依据与当前一致；
- 样品证据来自正确工厂，规格差异已明确评审并纳入批准快照；QC 和客户确认满足规则，证据没有失效；
- 两角色签字针对同一请求修订及证据摘要，具备相应授权；
- 当前批准未暂停、撤销、失效，且不存在适用的整单暂停；
- 当前生产动作的其他独立门禁也通过。

**执行前复核**：开裁／生产启动等受控写操作在同一事务中锁定 scope/current、核验修订并写执行记录，记录使用的 releaseId 与证据。禁止仅检查 pp_sample_approved 历史 done。订单级批量操作展开到明确 scope，返回每个范围的结果，不隐式放行未批准范围。

**已经开工**：返修使后续受控动作暂停，并创建生产处置待办（责任人、影响范围、在制数量、原因）。记录人工决定的停工、返工或经授权的新放行；不删除开工／完工事实，不声称软件状态变化等于实体工厂已经停机。整单暂停解除也不恢复已失效的样品批准。

### §14.4 返修、并发与恢复

1. Sample revise、旧 garmentSampleGate 返修、客户撤回、QC 结论失效、样品关键证据修改，以及订单行工厂／规格／范围变更，必须走受控领域命令。通用 PATCH 禁止直接覆盖受保护字段绕过此链路。
2. 触发命令在同一数据库事务内更新源修订，追加受影响 scope 的 invalidated 事件、更新 Current，并写审计。只影响明确关联范围；共享依据失效时覆盖所有引用它的 scope，包括跨订单引用。
3. 请求签字、生成批准、返修和执行使用统一锁顺序及 expectedRevision 乐观并发检查；签字结束再校验输入没有变化。数据库约束确保每个请求仅生成一份批准，scope 只有一个当前投影。冲突返回 409 并要求刷新，不能吞错返回成功。
4. 每个写命令具有幂等键及请求摘要，按权限作用域隔离；同键同内容返回原结果，同键异内容返回冲突。事件及审计与主业务事务一起提交。
5. 通知、待办派发、外部系统暂停使用事务 outbox，可重试并展示送达状态。安全资格失效不能依赖异步通知成功；大规模影响时先使共享证据修订失效，执行判定立即拒绝旧修订，投影重建可异步且必须可观察。
6. 旧 garmentSampleGate 接入统一命令是**兼容层**，只负责旧来源的修订与证据适配；不得继续独立授权放行。风险是双写漂移，以同事务与对账发现；保留原因是历史数据尚未迁移，完成证据迁移与调用方切换后退出。

### §14.5 API 与权限契约

下列为拟定路由；正式挂载遵循现有 `/api/v1` 约定。所有资源验证所属订单、订单行和当前用户数据权限。

| 端点／命令 | 输入与行为 |
|---|---|
| `POST /orders/:id/lines/:lineId/release-scopes` | 创建整行或实际批次 scope；服务端验证工厂、批次、数量和不重叠范围 |
| `POST /release-scopes/:scopeId/requests` | evidenceRevisionId、expectedScopeRevision、clientRequestId；服务端固定审批快照，不接受客户端写批准状态 |
| `POST /release-requests/:requestId/signatures` | role、expectedRequestRevision、clientRequestId；actor 从认证上下文获取；最终签字时重验并生成批准 |
| `POST /releases/:releaseId/pause`、`/resume`、`/revoke` | 原因、expectedRevision、clientRequestId；resume 仅适用于可恢复暂停且需完整重验 |
| `GET /orders/:id/releases` | 当前范围资格、缺项、批准历史及事件；汇总不替代范围判定 |
| `GET /release-scopes/:scopeId/eligibility?action=...` | 只读预检；实际生产命令提交时再次检查 |
| 样品返修／证据修订／规格变更命令 | 使用统一失效服务，不提供可由前端随意设置 active 的通用接口 |

权限按提交请求、生产签署、业务签署、暂停／撤销、恢复分别定义并接入现有权限矩阵。签字权限必须在后端强制；产品写权限或订单写权限不能代替签署权限。审批服务和 Agent 调用执行相同授权。前端不能提交 signedByProduction/signedByBusiness 指定他人签字。

### §14.6 前端与历史迁移

- 订单行展示工厂、批次范围、规格依据、样品证据版本、双签进度、当前资格和阻塞原因，并提供可定位的补证／签署／处置入口。
- 订单头显示“已放行范围数／适用范围数”和整单暂停；有无批准与是否实际开工分别呈现。
- 旧 ProductionStage 双签保留为历史资料，**不自动生成新有效批准**。已在制订单保留执行事实；切换后继续执行前须补证或走显式、限范围、有期限和授权的例外审批，不能静默全量放行。
- 先影子计算并列出受影响在制订单，完成补证和差异核对，再按可追踪配置启用强制门禁。旧门禁仅是迁移期**兼容层**，风险是粒度不足，不能作为新能力验收；停用条件是全部入口消费统一判定。回滚可回滚界面与部署，不得恢复已失效资格或删除批准历史。

### §14.7 验收场景

| 场景 | 必须验证的结果 |
|---|---|
| 多行／多批次部分放行 | 已批准范围可启动，未批准范围拒绝；订单汇总为 partial |
| 一行返修 | 仅关联范围失效；无关行仍可执行；共享同证据的其他范围一并失效 |
| 错工厂／错版本／错批次 | 后端拒绝，不能用同款、同订单或名称匹配放过 |
| 历史批准与重新批准 | 旧批准及签字不变，追加失效事件；新证据修订重新双签生成新批准 |
| 暂停、恢复、撤销 | 暂停可经重验恢复；失效／撤销不能 resume；整单暂停覆盖全部范围 |
| 越权与冒名签字 | 无权限、传他人 ID、同人占两角色均拒绝；API/Agent 一致 |
| 并发签字与返修 | 不产生对旧依据仍有效的批准；冲突明确返回；重复请求不重复记录 |
| 执行预检后发生返修 | 实际开裁提交重新检查，拒绝旧资格；不能复用预检结果绕过 |
| 已开工后返修 | 保留已执行事实，后续受控动作暂停，产生可追踪处置待办 |
| 拆批／增量／改厂／改规格 | 旧范围批准不自动覆盖新范围，必须重新评估批准 |
| 故障恢复 | 事务回滚不留半份批准；通知失败不影响资格失效，outbox 可重试 |
| 历史缺证／不适用品类 | 缺证明确阻断；不适用有服务端规则依据，不能因空引用默认通过 |

## §15 阶段 3：收费事项 + 应收链路（DR-053 ✅ 后端已实现 2026-09-07）

> **性质**：2026-09-07 实施（后端契约 + 前端样品详情展示）。对应 §12.8 结论修正第 4 点「成本与应收解耦」。
> **费用四层表达**（§12.3 统一口径）：
>   ① **费用发生**＝CostRecord（成本记录）——实际打样/邮寄/测试/开发花费，归集口径，可独立登记；
>   ② **收费决定**＝BillingItem（收费事项）——应承担金额、免收/抵货款/内部归集决定；**确认（confirm）后锁定**；
>   ③ **应收草稿**＝Invoice(status=Draft, sourceType='BillingItem')——收费决定确认后才生成，费用发生**不自动**形成应收；
>   ④ **正式签发**＝Invoice(status=Issued)——对客户生效；**PI(Proforma) 仅外贸可选前置**（既有 proformaInvoiceService Quotation→PI→convertToReceivable 链路，不强制收费事项必经），内销/简单场景直接 收费决定→应收草稿→签发。
> **边界明确**：抵货款（offsetAmount）在收费事项上记录「抵扣到哪个订单」的决定，应收草稿金额已扣除，订单发票结算时由财务据此冲抵——**不做自动跨票核销**（超出本阶段范围）。

### §15.1 数据模型

```prisma
// 费用发生层（成本记录）：一条实际花费事实，供收费决定参考
model CostRecord {
  id            String  @id // CR__${shortId}
  recordNo      String  @unique // CR-YYYYMMDD-001
  sourceType    String  // Sample | SealSample | SampleBatch | DevelopmentCase | OrderLine | Quotation
  sourceId      String
  costType      String  // sample_making | shipping | testing | development | other
  amount        Decimal @db.Decimal(18,4)
  currency      String  @default("CNY")
  incurredAt    String  // YYYY-MM-DD
  bearerType    String  @default("customer") // customer | internal | supplier（归集口径）
  bearerRelationId String?
  notes         String?
  @@index([sourceType, sourceId])
}

// 收费决定层（收费事项）：确认后锁定，生成应收草稿
model BillingItem {
  id            String  @id // BI__${shortId}
  itemNo        String  @unique // BI-YYYYMMDD-001
  sourceType    String  // Sample | SealSample | SampleBatch | DevelopmentCase | OrderLine
  sourceId      String
  costRecordId  String? // 关联主成本记录（多成本合并收费时选主记录，收费金额可独立合计）
  chargeType    String  // sample_fee | shipping_fee | testing_fee | development_fee | other
  bearerType    String  @default("customer") // customer | internal | supplier（向谁收）
  bearerRelationId String?
  bearerName    String? // 冗余快照
  amount        Decimal @db.Decimal(18,4) // 应收费总额
  currency      String  @default("CNY")
  waivedAmount  Decimal @default(0) // 免收
  offsetAmount  Decimal @default(0) // 抵货款
  offsetOrderId String? // 抵扣到哪个订单
  offsetOrderNumber String? // 快照
  status        String  @default("draft") // draft → confirmed → invoiced；draft/confirmed → cancelled
  invoiceId     String? // 回填（应收草稿）
  confirmedAt   BigInt?
  confirmedBy   String?
  @@index([sourceType, sourceId])
}
```

**派生不落库**：净应收 = amount − waivedAmount − offsetAmount，服务端计算返回（对齐 actualPaymentAmount 漂移教训，避免双源不一致）。

### §15.2 关键决策

| 决策 | 方案 |
|---|---|
| 承担方维度（场景 A 内部开发） | bearerType=customer/internal/supplier + bearerRelationId；内部部门承担时生成应收草稿 customerRelationId 留空 |
| 案取消收费（场景 B） | 收费资格绑来源（DevelopmentCase 可 stage=cancelled 后收费），不绑开发案状态；来源 resolveSource 从开发案带出客户 |
| 抵货款（场景 A/B） | offsetAmount+offsetOrderId 记录决定，净应收扣除；订单发票结算财务据此冲抵（不做自动跨票核销） |
| PI 非必经 | 不强制收费事项经 PI；外贸需 PI 走既有 Quotation→PI→convertToReceivable 链路 |
| 幂等 | BillingItem→Invoice 复用阶段 0 来源唯一约束（sourceType='BillingItem'+@@unique）；重试 recovered，建票回填失败 BACKFILL_FAILED |
| 权限 | 读 invoices:read；写（创建/编辑/确认/开票/取消/成本登记）invoices:write——对齐「业务员不登账」 |

### §15.3 API 契约

| 端点 | 说明 |
|---|---|
| `POST /api/v1/cost-records` | 登记成本记录（费用发生） |
| `GET /api/v1/cost-records?sourceType=&sourceId=` | 成本记录列表 |
| `POST /api/v1/billing-items` | 创建收费事项（来源带出默认客户/金额；可选 registerCost 联动登记成本） |
| `GET /api/v1/billing-items?sourceType=&sourceId=&status=` | 列表（netAmount 派生） |
| `GET /api/v1/billing-items/:id` | 详情 + flow（costRecords + invoice + stage） |
| `PATCH /api/v1/billing-items/:id` | 编辑（draft 态；confirmed 后 409 LOCKED） |
| `POST /api/v1/billing-items/:id/confirm` | 确认收费决定（锁定） |
| `POST /api/v1/billing-items/:id/invoice` | 生成应收草稿（幂等；净应收≤0 → noReceivable 闭环不开票） |
| `POST /api/v1/billing-items/:id/cancel` | 取消（已开票需先作废发票） |

flow.stage 取值：`decision_draft`（收费决定草稿）→ `decision_confirmed`（已确认待开票）→ `draft_receivable`（应收草稿）→ `issued`（已签发）；`no_receivable`（免收/抵货款全额冲抵）；`cancelled`。

### §15.4 验收映射

| 场景 | 判定 |
|---|---|
| 费用四层 | CostRecord(费用发生) → BillingItem(收费决定) → Invoice Draft(应收草稿) → Issued(签发)；UI 区分四态 |
| 部分免收/抵货款 | waivedAmount+offsetAmount ≤ amount（超限 400 INVALID_WAIVED）；净应收派生正确 |
| 案取消收费 | sourceType=DevelopmentCase 可在 cancelled 后建收费事项 |
| 确认锁定 | confirmed 后编辑 409；重复 confirm 409 |
| 开票幂等 | 重复 invoice → recovered，不重复建票；成功后重试返回已有票 |
| 净应收≤0 | noReceivable 闭环，不开票，flow.stage=no_receivable |
| 权限 | 无 invoices:write 403；读仅 invoices:read（sales 只读） |

### §15.5 迁移与回填

- 手写幂等 SQL `20260907060000_billing_item_cost_record`（CREATE TABLE IF NOT EXISTS，可重复执行）。
- **不迁移旧数据**：历史样品发票（sourceType='Sample'）保持兼容路径 invoiceSample；收费事项是新入口，旧数据不伪造收费决定。
- 兼容：invoiceSample（样品快速开票）保留——直接建应收草稿（跳过收费决定层），作为「快捷路径」；收费事项为「正式收费决定」路径。
