## §2 模块定位与范围

### 2.1 在 ERP 全链路中的位置

```
客户询价 → 报价单(Quotation) → 【开发案例(DevelopmentCase)】 → 样衣验证(SampleNode) → 量产订单(Order) → BOM/采购/生产/出运/财务
                                    ↑                              ↑
                                    └── 发起报价 prime 跳转回报价 ──┘
```

开发管理是"从样品到量产"的过渡漏斗：
- **上游**：报价单（Quotation）或客户直接需求 → 创建开发案例
- **中游**：样衣三级节点（确认样 → 产前样 → 大货样）状态机跟踪
- **下游**：开发案例转大货订单（Order），同时可发起报价（prime 跳转）

### 2.2 模块边界

| 包含 | 不包含 |
|------|--------|
| 开发案例 CRUD | 报价单本身（在 Quotation 模块） |
| 6 态开发阶段状态机 | 量产订单本身（在 Order 模块） |
| 三级样衣节点状态机（成衣链） | BOM 物料清单（在 BOM 模块，但详情页可展示草稿） |
| 5A 重点样衣评审门禁 | 生产管线 10 阶段（在 Order 详情页） |
| 转订单（link/autoCreate 双模式） | 客户/供应商档案（在 Relations 模块） |
| 发起报价 prime 跳转 | 产品档案（在 Products 模块） |
| EntityLink 关联图谱同步 | 审计日志本身（在 Audit 模块） |
| 面料链（多供应商×批次×封样×强制建档） | 见 [面料开发流程.md](./面料开发流程.md)（DR-050，仅面料，未实现） |

## §3 核心概念与术语

### 3.1 DevelopmentCase（开发案例）

一个开发案例代表"为某个客户/产品做的一次开发努力"，可能经历多轮样衣修改。

| 概念 | 说明 | 代码真源 |
|------|------|---------|
| **code** | 业务编号（DEV-2026-001），唯一 | `schema.prisma` L1832 `@unique` |
| **type** | 开发类型：fabric(面料) / garment(成衣) / pp(产前) / trim(辅料) | `types.ts` L977 `DevelopmentType` |
| **stage** | 6 态：developing / shipping / feedback / revision / approved / cancelled | `types.ts` L978 `DevelopmentStage` |
| **currentRound** | 当前样衣轮次（进入 revision 时 +1） | `schema.prisma` L1850 |
| **sampleCategory** | normal(普通) / 5a(5A 重点样衣) | `schema.prisma` L1856 |
| **reviewStatus** | 5A 评审：null / pending / passed / failed | `schema.prisma` L1857 |
| **linkedOrderId** | 转订单后的订单 ID（转单后非空，幂等防重） | `schema.prisma` L1873 |

### 3.2 SampleNode（三级样衣节点）

每个 DevelopmentCase 固定 3 个样衣节点，幂等创建（`ensureSampleNodes`）。

| 级别 level | 中文名 | 业务含义 |
|-----------|--------|---------|
| `confirmation` | 确认样 | 客户确认款式/尺寸的初样 |
| `pp` | 产前样 (PP Sample) | 大货开裁前的最终确认样（产前样批准是开裁前置条件，DR-008：生产放行前置） |
| `top` | 大货样 (TOP) | 从大货首件抽取留档 |

**DR-008 高端服装多轮样品**：

| 项 | 说明 |
|---|---|
| 最少轮次 | 高端服装客户首单开发阶段至少两轮正式样品 |
| 轮次完成条件 | 每轮必须同时满足：QC 记录 + 版师归档 + 业务归档 + 客户版本号 |
| 当前限制 | 当前 SampleNode 固定 3 节点（confirmation/pp/top），不支持多轮扩展（缺口见 §14） |

**节点状态机**：`pending → making → sent → approved / revising（→ making 下一轮 round+1）`

**节点完成门禁**（DR-008）：

| 条件 | 说明 |
|------|------|
| QC 记录 | 每轮样品必须有独立 QC 检验记录 |
| 版师归档 | 版师确认样品版型/工艺已归档 |
| 业务归档 | 业务员确认客户反馈已记录 |
| 客户版本号 | 每轮样品必须记录客户侧版本号（如 V1/V2/V3） |

### 3.3 关键术语对照

| 术语 | 英文 | 代码字段 |
|------|------|---------|
| 开发单 | Development Case | `DevelopmentCase` |
| 样衣节点 | Sample Node | `SampleNode` |

## §4 核心流程

### 4.1 主流程：客户需求 → 量产转单

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 客户需求  │───▶│ 创建开发 │───▶│ 样衣验证 │───▶│ 5A 评审  │───▶│ 转大货   │
│ /报价单   │    │ 案例    │    │ (3节点)  │    │ (5A only)│    │ 订单    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
                       │                                              │
                       │  发起报价 prime 跳转                          │
                       └──────────────▶ 报价管理 ──────────────────────┘
```

### 4.2 开发案例 6 态状态机

```
developing ──▶ shipping ──▶ feedback ──▶ approved (终态)
    │             │             │
    │             │             └──▶ revision ──▶ shipping (下一轮)
    │             │
    └─────────────┴─────────────▶ cancelled (终态)
```

**合法转换矩阵**（`DEV_STAGE_TRANSITIONS`）：

| 当前态 | 可推进到 |
|--------|---------|
| developing | shipping, cancelled |
| shipping | feedback, cancelled |
| feedback | revision, approved, cancelled |
| revision | shipping, cancelled |
| approved | （终态） |
| cancelled | （终态） |

**5A 评审门禁**：`sampleCategory === '5a'` 的样衣，进入 `shipping` 阶段前必须 `reviewStatus === 'passed'`，否则返回 `REVIEW_REQUIRED` 错误。

**DR-008 双门禁**：

| 门禁 | 位置 | 前置条件 | 说明 |
|------|------|---------|------|
| 生产放行门禁 | 产前样（pp）approved | 产前样 QC 通过 + 客户确认 + 版师归档 + 业务归档 | 产前样是生产放行前置，未通过不得开裁 |
| 出运放行门禁 | 大货 QC | 大货出运前 QC 评审通过 | 大货出运前 QC 是出运放行前置，独立于样品 QC |

### 4.3 三级样衣节点状态机

```
pending ──start──▶ making ──send──▶ sent ──approve──▶ approved (终态)
                       │               │
                       └──revise───────┴──▶ revising ──start──▶ making (round+1)
```

**action 规则**（`ACTION_RULES`）：

| action | 前置状态 | 目标状态 | 副作用 |
|--------|---------|---------|--------|
| start | pending, revising | making | revising→making 时 round+1 |
| send | making | sent | 记录 sentDate / courier / trackingNumber |
| approve | sent | approved | 记录 approvedAt / approvedBy / feedback |
| revise | sent, making | revising | 记录 feedback / feedbackDate，清空 approvedAt |

### 4.4 转订单双模式

| 模式 | 触发条件 | 行为 |
|------|---------|------|
| `link` | 传入 `orderId` / `orderPo` | 校验订单存在 → 关联到现有订单 |
| `autoCreate` | 传入 `autoCreate: true` 或未传 orderId | 自动创建新订单（沿用客户/供应商/产品） |

两种模式均在同事务内：更新 DevelopmentCase（stage→approved, linkedOrderId, convertedAt）+ syncEntityReferences + writeAuditLog，fail closed。

### 6.1 案内来样与寄厂字段契约（2026-10-12 当前候选实现）

适用§19.4/19.13的参考来样、选实物寄工厂；工厂实际返样沿原批次收样契约，不能混同。入口为开发案准确工厂版本区域的「登记来样 / 寄样给工厂 / 实物记录」，业务员从开发主线进入，保存后刷新本案及仓库同一实物；查看实物可跳仓库准确编号，返回仍沿既有跨模块来源。未登记实物提供同案来样入口；已登记却不可寄时核对原实物，分页仅说明本页并保留后页，不诱导重复登记。当前界面是留白方向候选，功能证据与视觉认可分开，运行验收见决策总账§20.1.4。

命令端点均位于`/v1/development`，仅当前用户会话；读取按当前开发案/实物授权，写入另核产品与仓库写权限。

| 方法 | 案内端点 | 行为 |
|---|---|---|
| POST | `/:id/incoming-samples` | 实际来样、同一实物与准确成功回执 |
| POST | `/:id/factory-sample-shipments` | 准确任务、扣库、物流与正邮费同事务 |
| GET | `/:id/physical-sample-commands` | 本案成功事实分页历史 |
| GET | `/:id/physical-sample-commands/:kind/:requestKey` | 原准确成功回执；不存在不等于未执行 |
| POST | `/:id/physical-sample-commands/:kind/:requestKey/resolve` | 以冻结原正文核成功或不可逆取消尚未完成原请求 |
| GET | `/:id/physical-sample-commands/:kind/:requestKey/resolution` | 只读核原成功/取消终态，丢失回执可恢复 |

| 字段 | 填写者与必填时点 | 输入、校验及传递 |
|---|---|---|
| 开发案 | 当前案内入口确定，不允许另选或手填 | `caseId`与当前源授权及实物归属核对；写入同一`SampleCardItem.devCaseId` |
| 来样实物名称 / 分类 | 业务员实际收到后登记，必填 | 名称1–200字；分类选现有面料/成衣/色卡/辅料/其他，不按案型推断材质 |
| 件数 / 单位 | 登记实际数量，必填 | 正整数；成衣逐件建档，每次1件。复用仓库`PC/YD/M/KG/SET/BOOK/ROLL/张/米/份`，不预选未知单位；原整数库存上限2147483647 |
| 实际长度 | 面料/色卡按`M/米`登记时必填 | 实物段数为1，实际米数>0、最多四位小数；不能把整数件数当米数，也不凭YD猜米数 |
| 来样日期 / 实物形态 | 实际收到后必填 | 日期为有效本地年月日且不晚于今天，不默认今天冒充事实；形态为1–120字实际说明 |
| 真实来源 / 实际来样方 | 实际收到后必填 | 来源复用`SAMPLE_SOURCES`五项：内部留样、客户来样、供应商/他人推荐、采购参考样、其他；来样方1–200字，不根据角色或工厂任务自动推断 |
| 仓库 / 存放位置 / 说明 | 登记时选填 | 仓库读取当前有效仓库；位置最多200字、说明最多500字。未指定保持缺失，不假造库位 |
| 来样照片 | 同一来样成功回执确认后上传 | 只关联该回执准确`photoUploadItemId`；JPEG/PNG/WebP走既有私有照片端点，读取经授权Blob预览；上传结果未知先核对原照片，不重复建来样 |
| 准确工厂任务 | 寄厂时必选 | 当前案真实`trialTask.id/updatedAt`，显示轮次/工厂/版本及原要求资料；不得用批次戳代替任务戳；原版本锁后重读CAS |
| 实际寄出实物 / 数量 | 寄厂时必选、必填 | 仅本案有当前读取权限的实物，真实可用量为零不能选；件数正整数，米样最多四位小数。API来源单位保留`item.unit`，实际扣库及回执单位由库存helper决定，不互相冒充 |
| 寄出日期 / 收件人 / 地址 | 实际寄出时必填 | 日期同来样约束；人名1–200字、地址1–2000字；联系方式选填最多200字，不自动复制客户地址替代工厂收件事实 |
| 快递商 / 快递单号 | 实际寄出时必填 | 各1–200字；与准确任务、实物及扣库回执同事务留痕 |
| 我方邮寄费 / 币种 | 主动寄样时必填 | 允许明确填写0，金额非负且最多14位整数/4位小数；币种明确3位大写字母。不从缺失猜免费。正额随本次寄厂同事务创建同案`shipping/internal`费用，保留原金额/币种/寄出日期；明确0无支出记录，不自动生成客户应收 |
| 寄样说明 | 寄厂时选填 | 最多2000字，冻结到本次实际物流回执 |

写入要求当前用户会话、`products:write + sample:room:write`及当前来源/实物授权，新实物与重提还受开发生命周期门禁；读取要求`products:read`及当前来源/实物授权。只读与结束/暂停后的原终态核对独立于新事实门禁。未知结果保留冻结原正文与编号；精确成功回执或不可逆取消凭据核实后才可清除。当前案内页面不内嵌整个仓库，原请求编号和内部任务戳退到核对明细。

源码锚点：`components/DevelopmentManager.tsx`、`components/development/DevelopmentPhysicalSampleDialog.tsx`、`services/developmentPhysicalSampleUiService.ts`、`services/developmentPhysicalSampleService.ts`、`server/src/development/developmentPhysicalSample{Service,Route}.ts`、`developmentFactoryShipmentCost.ts`、`developmentCostRegistration.ts`及`server/src/samples/sampleRoomService.ts`。不新增迁移；来样/寄厂沿原实物和库存同一实体，正邮费同事务进入canonical费用及同案按币种汇总；不自动发起QC、AR或客户确认。

## §7 状态机总览

### 7.1 DevelopmentCase 6 态状态机

见 §4.2，代码真源：`developmentCaseMutationService.ts` 的 `DEV_STAGE_TRANSITIONS` + `updateDevelopmentStage()`。

### 7.2 SampleNode 5 态状态机

见 §4.3，代码真源：`sampleNodeService.ts` 的 `ACTION_RULES` + `advanceSampleNode()`。

### 7.3 双状态机的关系

- DevelopmentCase.stage 是"粗粒度"阶段（6 态），由人工或状态推进 API 变更
- SampleNode.status 是"细粒度"节点状态（每级 5 态），由样衣节点推进 API 变更
- 两者独立但语义关联：三级样衣全 approved 通常对应 DevelopmentCase.stage = approved
