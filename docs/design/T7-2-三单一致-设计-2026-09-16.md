## 一、行业实务：三单一致到底是什么

外贸「三单一致」是**审单实务**（信用证项下叫「单单一致、单证一致、单货一致」），
核的是**同一票货在三份单据上的描述是否自洽**：

| 项 | 装箱单 Packing List | 商业发票 Commercial Invoice | 报关单 Customs Declaration |
|---|---|---|---|
| 数量 QTY | ✓（核心） | ✓（QTY / UNIT PRICE / AMOUNT 三列是发票的标准结构） | ✓（申报数量） |
| 件数/箱数 | ✓（核心） | ✗ | ✓ |
| 毛重/净重/体积 | ✓（核心） | ✗ | ✓ |
| 金额 | **✗（行业上装箱单不列金额）** | ✓（核心） | ✓（申报总额） |
| 品名/规格 | ✓ | ✓ | ✓ |
| HS / 原产国 | ✗ | ✗ | ✓ |

**关键行业事实**：
1. **装箱单不含金额**——它是包装/数量清单。真库 48 张 `PackingList` 的 `totalAmount` **全为空**，
   这不是数据缺失，而是**正确业务状态**。
2. **商业发票有数量列**——只是本系统 `InvoiceLine` 没建 `quantity`（真库仅 1 条行级明细）。
3. **报关单是「对外申报」数据**，装箱单/发票是「对内业务」数据。**三单一致核对的价值恰恰在于
   核对外报数据与内部发货事实是否相符**（报关行照单录入，填错是常态）。

## 二、数据源映射（业务方描述的实际流程 ⇒ 系统真源）

业务方原话流程：
> 「工厂那边结束生产 → 业务员申请发货/选择要发货的内容（发货通知给后勤）→
> 后勤跟工厂要**码单**（确认这批货的数量 + 大致包装方式）→ 他再填**装箱单**和**出运发票**，
> 还包括**订舱**（可能在此之前就完成了）」

这条链说明一件事：**装箱单和出运发票的数量/品名都来自「码单」＝实际发货事实**，
而实际发货事实在系统里的真源就是**运单**（`Shipment` + `ShipmentLine` + `ShipmentCarton`）。
所以：

| 行业单据 | 系统真源（数量/品名/包装） | 系统真源（金额） |
|---|---|---|
| 装箱单 | `Shipment.totalPackages/grossWeight/netWeight/volume` + `ShipmentLine` + `ShipmentCarton` | ——（装箱单无金额，不参与） |
| 商业发票 | 同上（**同源**：发票的 QTY 就是这批货的数量） | `Invoice.amount/currency`（财务 Invoice 为唯一真源，经 `TradeDocument.sourceInvoiceId` 回链） |
| 报关单 | `CustomsDeclarationLine`（`productName/quantity/unit/hsCode`）+ `CustomsDeclaration.totalPackages/grossWeight/netWeight` | `CustomsDeclaration.totalValue/currency` |

**这不是妥协，是正确建模**：箱单/发票在系统里没有独立的行级明细，是因为它们的明细与运单同源；
强行给 `TradeDocument` 加一套重复的数量字段，等于**同一事实存两处**，日后必然不一致。

## 三、核对项（8 项，全部 severity = warning）

锚点 = **运单**（`shipmentId`；三单都挂它，真库 48 组齐全）。

**组 A · 单据完整性**
| # | 核对 | 说明 |
|---|---|---|
| 1 | 三单是否都已生成且挂同一运单 | 缺哪单报哪单（`missing_document`） |

**组 B · 对外一致性（报关单 ↔ 内部发货事实）—— 这是最有价值的一组**
| # | 核对 | 期望（内部） | 实际（报关） |
|---|---|---|---|
| 2 | 数量合计 | `Σ ShipmentLine.quantity` | `Σ CDLine.quantity` |
| 3 | 件数 | `Shipment.totalPackages` | `CD.totalPackages` |
| 4 | 毛重 | `Shipment.grossWeight` | `CD.grossWeight` |
| 5 | 净重 | `Shipment.netWeight` | `CD.netWeight` |
| 6 | 金额 | `Invoice.amount` | `CD.totalValue` |
| 7 | 币种 | `Invoice.currency` | `CD.currency` |
| 8 | 品名 | `ShipmentLine.productName` | `CDLine.productName`（按 `productCode` 匹配；无 code 时按行序匹配） |

**跨币种处理**（与 T7-1 同口径）：金额项仅在**币种一致**时比对；币种不一致 → 只报 `currency` 差异
（`currency_mismatch`），**不产出金额差异**（避免拿 USD 金额与 CNY 金额相减）。

**容差**：数量/重量用 `EPS = 0.0001`（与 `reconciliationService` 同口径）；金额同。

**严重度**：**全部 warning**（口径 C：只预警不阻断）。缺单（组 A）也是 warning——不阻断交单。

## 四、接口与实现

- 新建只读服务 `server/src/customs/tripleDocumentConsistency.ts`
  - `export async function checkTripleConsistency(prisma, shipmentId): Promise<TripleConsistencyResult | null>`
  - 返回 `{ shipmentId, shipmentNumber, documents: { packingList, commercialInvoice, customsDeclaration }, discrepancies: TripleDocDiscrepancy[], checkedAt }`
  - `null` = 运单不存在/已软删（路由转 404）
- 路由 `GET /api/v1/customs/shipments/:shipmentId/triple-consistency`（只读，`customs:read`）
- 纯只读：不写库、不触发重算；Decimal 累加；与 `reconciliationService` 同风格（便于维护者迁移认知）
- 前端挂载点：**本批不做 UI**（先落服务端 + 测试 + 真库验收；UI 挂载点下批按需加，避免一次改太大）

## 五、验收口径

1. 真库 48 组（CI+PL+BL+CD 齐全）逐组跑：应报出**可解释的差异**（演练数据的报关金额与发票金额未必相等）。
2. 缺单场景：只有发票无报关单 → 报 `missing_document`（warning）。
3. 跨币种场景：报关 USD / 发票 EUR → 只报币种差异，**不报金额差异**。
4. 数量/件数/重量一致时不产出差异（零差异）。
5. 全部差异 `severity === 'warning'`（**不得出现 critical** —— 口径 C 只预警）。
