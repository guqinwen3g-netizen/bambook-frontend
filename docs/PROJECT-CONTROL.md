# Bambook 全项目协调与接续

本文件按用户 2026-10-16 的要求建立，保存全项目协调上下文：把 Notion 规划与核验、仓库实现、在途交付和验收缺口放在同一入口。它是持续更新的工作台，不是“全站已完成”的证明。

首页保留项目概况；本文件保留跨模块队列、来源对账和下一步；具体实现、测试、评审证据仍留在对应任务 / PR；临时技术停点留在 [进度记录](mist-atelier/LIVE-PROGRESS.md)。不复制多套相同状态。

## 1. 接续时先核实什么

1. 读取 [AGENTS](../AGENTS.md)、[首页](../README.md) 和本文件；核对 main、在途分支 / PR、实际部署版本。下面的版本和状态均为有时间点的观察，不能代替现场查询。
2. 本次源码盘点基线：`570d5192e6813918afafb649b3d9b48e108f527e`（2026-10-16，报价正式 PDF 批次合入后）。功能代码没有在本次文档整理中改动。
3. 当前协调范围为整个公司端：35 个主模块，以及审批、通知、搜索；客户 / 供应商独立平台不是默认新增范围。
4. 从业务员登录首页开始，贯穿客户需求、开发、报价、订单、采购、生产、质检、出运和财务。每个节点同时核对数据来源、状态、岗位权限、交接、回程、退回 / 取消 / 部分完成，遵守[业务驱动原则](design/global/2026-10-06/08-2026-10-06-对话设计决策总账.md#business-driven-design)。
5. 区分“已实现”“自测通过”“独立复核通过”“真实业务验收通过”“已部署”。没有相应证据就保留待核验，不按文件数量或历史测试数计算完成百分比。

## 5. 推进顺序与交付门槛

这是协调建议和接续队列；未定业务规则先查有效决策，不能自行编造后启动实现。

| 顺序 | 可独立验收的目标 | 交付证据 / 依赖 |
|---|---|---|
| 先收口在途交付 | 开发修正 / 版本关联复核，订单执行推进，报价成果纳入跨模块验收 | 准确提交、适用测试、最新 CI、关键 UI 操作；开发按用户要求独立复核后合入 |
| 跑通两类真实业务链 | 成衣与面料分别走客户需求→开发 / 样品→报价→订单→采购 / 生产→QC→出运 / 单据→票款 | 明确操作岗位与测试数据，覆盖部分完成、退回、修改、取消；记录中断点，不按菜单依次机械开发 |
| 处理阻断和一致性问题 | 来源断链、错单 / 错版本、权限、数量 / 金额、重复操作、状态及通知回程 | 以可复现问题拆小批次；保留原始业务事实与修复回归证据 |
| 补横向能力与真实集成 | 按业务依赖排统一审批、财务经营口径、邮箱、报表、组织权限等缺口 | 每项先确认范围；实际服务连接与真实操作另有验收证据 |
| 核实运行与数据安全 | 真实数据库并发、迁移、备份恢复、开发部署版本、桌面行为 | 本地文件模式不替代 PostgreSQL；正式发布、真实资金和外部客户操作仍须单独授权 |

日常实现按影响范围自测；完整 CI 在准备合入的准确提交上执行。等待 CI 时做独立核对与收尾，避免同一版代码重复全量跑。仓库已有大量历史代码 / 测试不在当前 Mist CI 的直接选择范围，不能因此把全部旧测试加入每批流程，也不能宣称全仓已验证。范围以 [工作流](../.github/workflows/mist.yml) 和当前 package 脚本为准。

开发发布有版本健康检查及失败回切；发布脚本不自动迁移 / 重置数据库。备份脚本存在不代表恢复演练已成功。准确版本查 CI、部署状态及[运维回执](ops/dev-server-access.md)，不拿本地已同步代替开发服务器已部署。

## 6. 每次推进如何更新

- 有明确进展才更新：任务确认接手、交付 / 复核结果、合入、部署、业务验收、阻塞或优先级决定；无变化不重复抄写状态。
- 状态记录使用“日期 + 范围 + 已发生事实 + 证据 + 剩余问题 / 下一步”；分清资料自述、源码核实、测试证据与人工业务验收。
- 新 Notion 资料先记录标题、链接和读取边界，再对照 main；解决的缺口标明对应结果，不静默删除历史依据。
- 刚完成一批后收口依赖，从更新后的 main 开下一批；不要继续叠在已等待合入的旧批次上。
- 本文件随协调工作的实际推进维护，不是无人运行时自动更新的监控服务。若另行设置自动检查，应明确频率、范围、通知条件与授权。
